## 2026-10-19 — Этап M2, задача 11: комплекты CPU и GPU, zam-models, zam-cuda
- `cargo xtask package --flavor cpu|gpu [--with-models] [--cuda] [--no-kit]`. GPU-комплект содержит ORT с CUDA EP и не содержит библиотек NVIDIA. `zam-models` собирается по архиву на модель: вместе модели больше 2 ГиБ. `zam-cuda` — это каталог `cuda/` со штампами: после распаковки `cuda fetch` ничего не скачивает. Каждый архив и каждый файл релиза проверяются на предел 2 ГиБ. Отчёт: `.superpowers/sdd/2026-10-19-m2-index-ml/task-11-report.md`.
- Найдено при упаковке:
  - на Windows `onnxruntime.dll` (с M1) и CUDA EP импортируют MSVC runtime, поэтому на чистой системе ORT не загружался и сервер молча работал в режиме FTS-only. Решение: app-local `msvcp140*` и `vcruntime140*` в комплекте, smoke проверяет импорты через dumpbin;
  - на Windows управляемый Qdrant падал из-за MAX_PATH, если каталог данных длиннее ~80 символов (файлы gridstore payload-индекса). Решение: пути хранилища в `zam.yaml` теперь `\\?\`-абсолютные.
- Smoke обоих flavor: 5 заметок, перефраз без общих подстрок находит цель в top-3 только векторным каналом, устройство и завершение Qdrant проверяются по `--json`. Ручной прогон на RTX 3090: GPU-комплект + `zam-cuda` (CUDA Toolkit убран из PATH) → device=cuda:0; без `zam-cuda` — device=cpu с причиной.
- Fix round 1 по ревью:
  - пробный прогон релиза без публикации: ветка `release-dry-run` и `workflow_dispatch`; задача `dist` проверяет состав, 2 ГиБ и SHA256SUMS, `publish` выполняется только на теге;
  - `package.yml`: одна задача на платформу (сборка один раз, оба flavor), отдельная задача `models`, артефакты с `compression-level: 0`;
  - `qdrant status --json`, `cuda fetch --json`;

- Найдено и исправлено:
  - **Поиск после падения Qdrant ждал 2–4 с** (Windows: отказ соединения с закрытым портом localhost — ~2 с на попытку, клиент повторяет; супервизор меняет состояние только после разбора журнала процесса). Замер до исправления: первый ответ после убийства — 1,7–4,1 с. Теперь при `Ready` доступность сверяется с живостью процесса (`Supervisor::process_alive`), соединение — 300 мс: первый ответ 24–56 мс, весь простой (~1,9 с до перезапуска) — FTS-only с `qdrant_down`. Тесты: `search_right_after_qdrant_kill_degrades_without_waiting` (без исправления — 4,07 с), `process_alive_drops_right_after_kill`.
  - **`POST /nodes` → 500 «database is locked»** при загрузке 10 тыс. заметок во время индексации на HDD: фоновый `RESTART` checkpoint держал блокировку записи дольше 5 с. Писатель ждёт до 30 с; тест `writer_waits_out_long_foreign_write_lock`. Остаётся хвост: отдельные записи ждут до 10–11 с (p95 — 14–26 мс).

- Не выполнено — причины и предложения:
  - **FTS-only 30 мс при цели 20** на 10 тыс. заметок: сам FTS (`fts_ms` p50 16–17, p95 27–28 мс) — `ORDER BY bm25 LIMIT 400` считает bm25 для каждого совпадения, частые слова дают тысячи строк. На 1000 заметок (M1) — 8,5 мс. Предложения: ранний отсев по IDF (частые слова — не в строгом AND, а в ранжировании), уменьшение `OVERSAMPLE` при больших списках, `detail=column` для trigram; копии в корпусе завышают частоту редких слов — замерить на реальных 10 тыс. заметок.
  - **RSS с моделью**: CPU 1,42 ГБ — две сессии ORT (индексация и запросы) держат по копии весов int8; `PrepackedWeights` для `MatMulInteger` ничего не разделяет. Опыт с общими initializers (`AddInitializer`, Python ORT 1.23) на bge-m3 int8 экономии не дал (1,20 против 1,17 ГБ на две сессии), на jina — 0,1 ГБ. Одна сессия на оба пути сэкономила бы ~0,55 ГБ, но поиск при полной очереди ждал бы текущий текст индексации (до 0,3 с) и нарушил бы 120 мс. Предложение владельцу: цель 1,5 ГБ для двух сессий или режим «одна сессия» для машин с малой памятью. GPU: рабочий набор 0,78–1,22 ГБ (частный 0,64–1,08 ГБ) — в основном библиотеки CUDA/cuDNN и память хоста CUDA EP, растёт после первых запросов; способа снизить его в рамках задачи не найдено, предложение — замерить на Linux и пересмотреть цель.
  - **RSS без моделей на 10 тыс. заметок 53 МБ при 50**: кэш страниц SQLite (по 2 МБ на соединение, 6 соединений на базу) — можно урезать `cache_size` читателей ценой FTS.
  - **Реранкер jina +0,96 ГБ при 0,5**: 2 сессии по копии весов (одна — +0,6 ГБ и 1,9 с, нарушает цель времени). Обе цели вместе с этой моделью не достигаются; варианты — `rerank_sessions = 1` на машинах с малой памятью, общая память весов (не поддерживается ORT для этого графа), другая CPU-модель.
  - **Запись до векторного индекса на GPU p95 1,26 с при 1 с**: p50 0,33 с, хвост — запись `wait=true` в Qdrant и fsync checkpoint SQLite на HDD (на 10 тыс. заметок у воркера инференс 17 % времени, Qdrant 27 %). На SSD ожидается в пределах цели; на HDD цель недостижима без отказа от `wait=true`.
  - **Индексация 400-токенных чанков на CPU** — ≈ 1,8 чанка/с (3,5 по ~200 токенов): цель «≥ 3 чанка/с, чанк 400 токенов» выполнена только для реальных чанков корпуса (~200 токенов).
  - **Хвост записи до FTS 10–11 с** при массовой загрузке во время индексации на HDD (фоновый `RESTART` с переносом остатка WAL): предложение — не делать принудительный `RESTART` с переносом, а дробить checkpoint.
