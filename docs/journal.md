## 2026-10-19 — Этап M2, задача 11: комплекты CPU и GPU, zam-models, zam-cuda
- `cargo xtask package --flavor cpu|gpu [--with-models] [--cuda] [--no-kit]`. GPU-комплект содержит ORT с CUDA EP и не содержит библиотек NVIDIA. `zam-models` собирается по архиву на модель: вместе модели больше 2 ГиБ. `zam-cuda` — это каталог `cuda/` со штампами: после распаковки `cuda fetch` ничего не скачивает. Каждый архив и каждый файл релиза проверяются на предел 2 ГиБ. Отчёт: `.superpowers/sdd/2026-10-19-m2-index-ml/task-11-report.md`.
- Найдено при упаковке:
  - на Windows `onnxruntime.dll` (с M1) и CUDA EP импортируют MSVC runtime, поэтому на чистой системе ORT не загружался и сервер молча работал в режиме FTS-only. Решение: app-local `msvcp140*` и `vcruntime140*` в комплекте, smoke проверяет импорты через dumpbin;
  - на Windows управляемый Qdrant падал из-за MAX_PATH, если каталог данных длиннее ~80 символов (файлы gridstore payload-индекса). Решение: пути хранилища в `zam.yaml` теперь `\\?\`-абсолютные.
- Smoke обоих flavor: 5 заметок, перефраз без общих подстрок находит цель в top-3 только векторным каналом, устройство и завершение Qdrant проверяются по `--json`. Ручной прогон на RTX 3090: GPU-комплект + `zam-cuda` (CUDA Toolkit убран из PATH) → device=cuda:0; без `zam-cuda` — device=cpu с причиной.
- Fix round 1 по ревью:
  - пробный прогон релиза без публикации: ветка `release-dry-run` и `workflow_dispatch`; задача `dist` проверяет состав, 2 ГиБ и SHA256SUMS, `publish` выполняется только на теге;

**Найдено и исправлено.**

1. **Поиск после падения Qdrant ждал 2–4 с.**
   - Причина (Windows): отказ соединения с закрытым портом localhost приходит лишь через ~2 с на попытку, клиент повторяет запрос, а супервизор меняет состояние только после разбора журнала процесса.
   - До исправления: первый ответ после убийства Qdrant — 1,7–4,1 с.
   - Исправление: при `Ready` доступность сверяется с живостью процесса (`Supervisor::process_alive`), соединение ограничено 300 мс.
   - После: первый ответ — 4–56 мс, весь простой (~1,9 с до перезапуска) поиск отвечает из FTS с `qdrant_down`.
   - Тест `search_right_after_qdrant_kill_degrades_without_waiting` (предел 250 мс). Без исправления — 4,07 с; только с пределом соединения, без проверки процесса — 624 мс.
2. **Эмбеддинг запроса на GPU ждал батч индексации** (p95 74 мс при полной очереди).
   - Исправление: батч не больше 2048 токенов вместо 8192, перед батчем индексация ждёт запросы (до 100 мс).
   - При полной очереди на 3 тыс. заметок: p95 поиска 93 → 39 мс, эмбеддинга 74 → 25 мс.
   - На 10 тыс.: 112 → 53 мс. Остаток — FTS (`fts_ms` p95 35).
3. **`POST /nodes` отвечал 500 «database is locked»** при загрузке 10 тыс. заметок во время индексации на HDD.
   - Причина: фоновый `RESTART` checkpoint держал блокировку записи дольше 5 с.
   - Исправление: писатель ждёт до 30 с. Тест `writer_waits_out_long_foreign_write_lock`.
   - Остаётся хвост: отдельные записи ждут до 10–12 с (p95 — 15–26 мс).
4. **jina считалась батчем.**
   - Граф квантует активации динамически (`DynamicQuantizeLinear`), но признака в манифесте не было — баллы зависели от соседей по батчу.
   - Теперь пары идут по одной в `ml.rerank_sessions` параллельных сессиях (по умолчанию 2). p95 1,96 → 1,26–1,34 с, nDCG@10 на eval 0,831 → 0,829 (в пределах шума).
   - Устаревший `model.toml` установленной модели видно в `models status` и по WARN при загрузке.
5. **Старт до готовности Qdrant** занимал «загрузка модели + Qdrant» (на GPU — 11 с).
   - Теперь Qdrant запускается параллельно с моделью, а `model_id` (sha256 файла 0,5–1,1 ГБ) кэшируется в `model.onnx.sha8`.
   - Обычный старт — 0,8–2,0 с. Загрузка модели — 1,8 с на CPU, 3,1–3,3 с на GPU.
6. **FTS-only: p95 76 → 30 мс.**
   - `leaf_term_hits` (выбор листа вместо сводки) соединял каждое совпадение слова с `chunks`: частое слово — 16 тыс. строк и 25 мс.
   - `pending_count` обходил все узлы (6 мс). Добавлен частичный индекс `nodes_pending` (миграция user 0006).

**Не выполнено: причины и предложения.**

- **Индексация «чанк 400 токенов» на CPU.**
  - Замер: 690–750 токенов/с ≈ 1,7–1,9 чанка по 400 при цели 3. Цель «≥ 3 чанка/с» выполняется только для реальных чанков корпуса (~200 токенов, 3,5/с).
  - Причина: инференс занимает 84–95 % времени воркера. bge-m3 int8 с динамическим квантованием прогоняет тексты по одному на одной сессии.
  - Предложение — решение владельца:
    - несколько сессий индексации, как у реранкера (+~0,55 ГиБ на сессию — конфликт с целью по RSS);
    - или int8 со статическим квантованием (батчи).
- **Поиск при полной очереди на GPU: 53 мс при 50.** Эмбеддинг после исправления — p95 30 мс, остаток — FTS (p95 35 мс) под конкуренцией записи на HDD. Предложение — то же, что для FTS-only.
- **FTS-only: 30 мс при 20** на 10 тыс. заметок.
  - Время уходит на сам FTS (`fts_ms` p50 16–17, p95 27–28 мс): `ORDER BY bm25 LIMIT 400` считает bm25 для каждого совпадения, частые слова дают тысячи строк. На 1000 заметок (M1) — 8,5 мс.
  - Предложения: отсев частых слов по IDF из строгого AND, меньший `OVERSAMPLE` при длинных списках.
  - Копии в корпусе завышают частоту редких слов — замерить на реальных 10 тыс. заметок.
- **RSS с моделью на CPU: 1415–1436 МиБ при 1,1 ГБ.**
  - Сессии индексации и запросов держат по копии весов int8. `PrepackedWeights` для `MatMulInteger` ничего не разделяет.
  - Проверено на Python ORT 1.23: общие initializers (`AddInitializer`) на bge-m3 int8 экономии не дали (две сессии — 1204 против 1167 МиБ), на jina — ~0,1 ГиБ.
  - Одна сессия на оба пути сэкономила бы ~0,55 ГиБ. Но поиск при полной очереди ждал бы текущий текст индексации (до 0,3 с), а это нарушает 120 мс.
  - **Ожидает решения владельца:** цель 1,5 ГБ для двух сессий или режим «одна сессия» для машин с малой памятью.
- **RSS с моделью на GPU: 784–1220 МиБ при 0,6 ГБ** (частный набор — 649–1080 МиБ).
  - В основном это библиотеки CUDA/cuDNN и память хоста CUDA EP; растёт после первых запросов. Снизить в рамках задачи не удалось.
  - **Ожидает решения владельца:** замер на Linux и пересмотр цели.
- **RSS без моделей на 10 тыс. заметок: 53–54 МиБ при 47,7 МиБ (50 МБ).** Это кэш страниц SQLite (по 2 МиБ на соединение, 6 соединений на базу). Можно урезать `cache_size` читателей ценой скорости FTS.
- **Реранкер jina: +959 МиБ при 0,5 ГБ.**
  - Две сессии, у каждой своя копия весов. Одна сессия — +0,59 ГиБ и 1,9 с, то есть нарушает цель по времени.
  - С этой моделью обе цели вместе не достигаются.
  - **Ожидает решения владельца:** `ml.rerank_sessions = 1` на машинах с малой памятью, приоритет времени над памятью или другая CPU-модель.
- **Старт до готовности Qdrant после массовой индексации: 8,5–9,9 с** в трёх GPU-прогонах подряд (на CPU — 4,8).
  - Это первый старт после жёсткой остановки, когда оптимизатор Qdrant ещё не доделал сегменты 34 тыс. точек на HDD. Обычный старт — 0,8–2,0 с.
  - Предложение: перед остановкой ждать простоя оптимизатора (или делать снапшот). На Windows Qdrant останавливается только через `TerminateProcess`.
- **Хвост записи до FTS: 10–12 с** при массовой загрузке во время индексации на HDD.
  - Причина: фоновый `RESTART` с переносом остатка WAL.
  - Предложение: дробить checkpoint вместо принудительного `RESTART` с переносом.
