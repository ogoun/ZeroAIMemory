## 2026-10-19 — Этап M2, задача 11: комплекты CPU и GPU, zam-models, zam-cuda
- `cargo xtask package --flavor cpu|gpu [--with-models] [--cuda] [--no-kit]`. GPU-комплект содержит ORT с CUDA EP и не содержит библиотек NVIDIA. `zam-models` собирается по архиву на модель: вместе модели больше 2 ГиБ. `zam-cuda` — это каталог `cuda/` со штампами: после распаковки `cuda fetch` ничего не скачивает. Каждый архив и каждый файл релиза проверяются на предел 2 ГиБ. Отчёт: `.superpowers/sdd/2026-10-19-m2-index-ml/task-11-report.md`.
- Найдено при упаковке:
  - на Windows `onnxruntime.dll` (с M1) и CUDA EP импортируют MSVC runtime, поэтому на чистой системе ORT не загружался и сервер молча работал в режиме FTS-only. Решение: app-local `msvcp140*` и `vcruntime140*` в комплекте, smoke проверяет импорты через dumpbin;
  - на Windows управляемый Qdrant падал из-за MAX_PATH, если каталог данных длиннее ~80 символов (файлы gridstore payload-индекса). Решение: пути хранилища в `zam.yaml` теперь `\\?\`-абсолютные.
- Smoke обоих flavor: 5 заметок, перефраз без общих подстрок находит цель в top-3 только векторным каналом, устройство и завершение Qdrant проверяются по `--json`. Ручной прогон на RTX 3090: GPU-комплект + `zam-cuda` (CUDA Toolkit убран из PATH) → device=cuda:0; без `zam-cuda` — device=cpu с причиной.

**Найдено и исправлено.**

1. **Поиск после падения Qdrant ждал 2–4 с.**
   - Причина (Windows): отказ соединения с закрытым портом localhost приходит лишь через ~2 с на попытку, клиент повторяет запрос, а супервизор меняет состояние только после разбора журнала процесса.
   - До исправления: первый ответ — 1,7–4,1 с.
   - Исправление: доступность сверяется с живостью процесса (`Supervisor::process_alive`), соединение ограничено 300 мс.
   - После: первый ответ — 10–19 мс, весь простой (~1,8–2,1 с до перезапуска) поиск отвечает из FTS с `qdrant_down`.
   - Тест `search_right_after_qdrant_kill_degrades_without_waiting`, предел 250 мс. Без исправления — 4,07 с; без проверки процесса, с одним пределом соединения — 624 мс.
2. **Эмбеддинг запроса на GPU ждал батч индексации** (p95 74 мс при полной очереди).
   - Исправление: батч инференса не больше 2048 токенов (было 8192). Перед батчем — ожидание, пока идут эмбеддинги запросов, но не дольше 100 мс; у `dynamic_quant` — один раз на вызов.
   - Ожидание учитывается отдельно: `worker.yield_ms`, в `embed_ms` не входит.
   - Полная очередь на GPU: p95 112 → 52 мс (эмбеддинг — 28 мс, FTS — 37 мс).
   - Скорость индексации при непрерывном потоке запросов почти не падает: CPU — 1,13 против 1,20 задания/с (−6 %), уступка 186 мс за 14 с; GPU — 12,9 против 12,8/с, уступка 362 мс за 7 с.
3. **`POST /nodes` отвечал 500 «database is locked»** при загрузке 10 тыс. заметок во время индексации на HDD.
   - Причина: фоновый `RESTART` checkpoint держал блокировку записи дольше 5 с.
   - Исправление: писатель ждёт блокировку до 30 с. Тест `writer_waits_out_long_foreign_write_lock`.
   - Остаётся хвост: отдельные записи ждут до 8–10 с.
4. **jina считалась одним батчем.**
   - Граф квантует активации динамически (`DynamicQuantizeLinear`), но в манифесте не было признака `dynamic_quant`. Баллы зависели от соседей по батчу.
   - Теперь пары идут по одной в `ml.rerank_sessions` параллельных сессиях (по умолчанию 2). p95 было 1,96 с, стало 1,45 с; nDCG@10 на eval не изменился (0,831 → 0,829).
   - Устаревший `model.toml` видно в `models status` и по WARN при загрузке.
5. **Старт до готовности Qdrant** = загрузка модели + Qdrant (на GPU — 11 с).
   - Исправление: Qdrant запускается параллельно с загрузкой модели; `model_id` кэшируется в `model.onnx.sha8`.
   - Обычный старт — 1,1–2,0 с.
6. **FTS-only: p95 76 → 30 мс.**
   - `leaf_term_hits` соединял каждое совпадение слова с `chunks`.
   - `pending_count` обходил все узлы — добавлен частичный индекс `nodes_pending` (миграция user 0006).

**Не выполнено — причины и предложения.**

- **Индексация «чанк 400 токенов» на CPU.**
  - Замер: 690–770 токенов/с, это ≈ 1,7–1,9 чанка по 400 при цели 3. По реальным листам корпуса (~200 токенов) — 3,45–3,85 чанка/с.
  - Причина: инференс занимает 86–97 % времени воркера. bge-m3 int8 с динамическим квантованием считает тексты по одному на одной сессии.
  - Варианты: несколько сессий индексации (+~0,55 ГиБ на каждую — конфликт с целью RSS) или int8 со статическим квантованием, которое можно батчить. **Решение владельца (2026-10-20):** принять 690–770 токенов/с как есть.
- **Полная очередь на GPU: 52 мс при 50.** Эмбеддинг после исправления — p95 28 мс. Остаток — FTS (p95 37 мс) под конкуренцией записи на HDD. Предложение — то же, что для FTS-only. **Решение владельца (2026-10-20):** принять 52 мс как есть.
- **FTS-only: 30–32 мс при 20** на 10 тыс. заметок.
  - Сам FTS (`fts_ms`) — p50 15–18, p95 28–37 мс: `ORDER BY bm25 LIMIT 400` считает bm25 для каждого совпадения. На 1000 заметок было 8,5 мс.
  - Предложения: отсев частых слов по IDF из строгого AND; меньший `OVERSAMPLE` для длинных списков; замер на реальном корпусе 10 тыс. заметок (копии завышают частоту редких слов). **Решение владельца (2026-10-20):** принять 30 мс как есть.
- **RSS с моделью на CPU: 1416–1439 МиБ при 1,1 ГБ.**
  - Сессии индексации и запросов держат по копии весов int8. `AddInitializer` проверен опытом на Python ORT 1.23: экономии нет (1204 против 1167 МиБ на две сессии).
  - Одна общая сессия сэкономила бы ~0,55 ГиБ, но нарушила бы 120 мс при полной очереди.
  - **Решение владельца (2026-10-20):** цель 1,5 ГБ на две сессии (ТЗ v1.7): в простое 1416 МиБ (1,485 ГБ) — выполнено; после поиска 1439 МиБ (1,509 ГБ) — превышение на 0,6 % (вопрос владельцу: ГБ или ГиБ).
- **RSS с моделью на GPU: 808–1248 МиБ при 0,6 ГБ** (частный набор — 673–1103 МиБ). Это в основном библиотеки CUDA/cuDNN и память хоста CUDA EP. Предложение — замер на Linux и пересмотр цели; **открыто** (журнал решений M2, «Уточнить у владельца»).
- **RSS без моделей на 10 тыс. заметок: 54 МиБ при 47,7 МиБ.** Причина — кэш страниц SQLite. Можно урезать `cache_size` читателей ценой FTS.
- **Реранкер jina: +955 МиБ при 0,5 ГБ.** Одна сессия даёт +0,59 ГиБ, но 1,9 с — это нарушает цель по времени. **Решение владельца (2026-10-20):** память jina — по факту при `ml.rerank_sessions`.
- **Первый старт после массовой индексации: CPU 9,6 с, GPU 5,4 с.** Разбор по журналу Qdrant на финальном коде:
  - **GPU.** Повтор 39 операций WAL — 3,3 с, загрузка коллекции — 0,5 с.
  - **CPU.** Загрузка коллекции — 3,4 с. Повтор 7 операций WAL — 5,6 с: после 1,7 ч записи кэш ОС вытеснен, а модель грузилась тут же 9,1 с с HDD.
  - **Последующие старты.** В WAL — 1 операция, старт ≤ 2 с.
  - **Причина — поведение Qdrant**: повтор неподтверждённого WAL после жёсткой остановки, которая на Windows всегда идёт через `TerminateProcess`, плюс чтение сегментов с HDD. Батч эмбеддинга (2048) на число операций WAL не влияет: запись в Qdrant по-прежнему одна на пачку из 8 заданий.
  - **Разброс.** 4,2 с на `0bb32f7` против 8,5–9,9 с на `4018ae3` объясняется тем, сколько операций WAL осталось к моменту остановки.
  - Варианты: перед остановкой ждать сброса WAL (по умолчанию `flush_interval_sec` = 5 с) или уменьшить `wal_capacity_mb` коллекции; оба нужно замерить. **Решение владельца (2026-10-20):** цель 5 с относится к штатному перезапуску; этот сценарий — исследовать (сброс и размер WAL, очерёдность: Qdrant раньше модели на HDD).
- **Хвост записи до FTS: 8–10 с** при массовой загрузке во время индексации на HDD — это фоновый `RESTART` checkpoint. Предложение: дробить checkpoint.
