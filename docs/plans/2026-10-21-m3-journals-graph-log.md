## Решения

Решения исполнителя, принятые без владельца; каждое можно пересмотреть.

- **План, редакция 2:**
  - Qdrant без пересборки: тенант остаётся `user_id` владельца базы, участнику — фильтр `(user_id владельца, space_id решения)`. Новые payload-индексы добавляются в существующую коллекцию. Фильтр статуса исключающий (`must_not superseded/retracted`), чтобы точки M2 без поля `status` проходили (задача 4).
  - Конфликт одного GUID у двух пользователей при регистрации решений M1–M2: локальное решение второго переименовывается под новый GUID, его данные остаются у него, а к исходному GUID ставится запрос `pending` (задача 2).
  - Режим участника при одобрении по умолчанию — `rw`. Повторный запрос после отклонения или отзыва состояние не сбрасывает (задача 2).
  - Человеческий токен (`tokens.human`): выпускает только администратор; хранится в `~/.zeroaimemory/config.toml`, не в CLAUDE.md; используется CLI только с флагом `--human`. По умолчанию insight человека — `axiom`, агента — `hypothesis` (задача 9).
  - Агенту запрещено любое изменение заметки или записи `axiom`, включая перенос и удаление (задача 9).
  - Vault — отдельные таблицы `vault_items`/`vault_revisions` вне конвейера индексации (задача 12).
  - Рёбра графа только внутри одной базы; участнику отфильтровываются узлы вне пространства решения (задача 10).
  - Раскладка ELK: `elkjs` из зависимостей `mermaid` 12; EPL-2.0 разрешается точечно этому пакету, а не всему списку `ALLOWED` (задача 14).

- **Задача 2 (реестр решений и доступ):**
  - `SolutionGuid`/`TargetRef` разбираются с ошибкой `ParseIdError` (в плане — `IdError`; отдельный тип не заводился). `TargetRef` в serde — строка `n:<id>` | `e:<id>`, как `Display`.
  - Режим в новом запросе доступа — режим токена запроса (только токен того же пользователя), без токена — `rw`; при одобрении владелец всё равно задаёт режим явно.
  - Аудит `solution.access.request` пишется только при создании запроса (повтор идемпотентен и аудита не даёт); actor — id токена или `system`. `solution.access.mode` — повторное одобрение уже одобренного (смена режима).
  - `solution_role` для незарегистрированного GUID — `None` (как «нет доступа»); `list_access` для него — `NotFound`.
  - `accessible_solutions` не фильтрует `archived_at`: архивации решений пока нет.
  - Конфликт GUID: сначала одной транзакцией `system.db` — регистрация нового GUID, запрос к исходному, аудит `solution.guid_conflict`; затем переименование в базе пользователя. Прерванное переименование довершается при следующем вызове: пространство уже в реестре за пользователем (`solution_by_space`).
  - `rename_solution_guid` ставит `upsert` живым индексируемым заметкам пространства (новый `solution_guid` в payload Qdrant); точки папок (`folder` L0) получат новый GUID при пересборке индекса.
  - `Attribution.user_id`: сервер пишет `user_id` пользователя токена; администратор (WebUI) — `NULL`, как у ревизий до M3. `RevisionInfo` отдаёт `user_id`.

- **Задача 3 (сервер: доступ к решениям, `agent_solution_id`, CLI, настройки):**
  - Узел по id без заголовка ищется в личной базе, затем в базах владельцев решений, где у пользователя есть запрос доступа **в любом состоянии** (`SystemStore::member_solutions`): узел отозванного или ожидающего решения отвечает 403 `solution-access` (Review Focus 1), а не 404. Узел владельца вне пространства решения — 404. Вложения (`GET /blobs/…`) — так же, через `blob_meta_in_space`.
  - Пользователь без запроса к зарегистрированному чужому решению получает по GUID 404 (не 403 со `state`), как и для незарегистрированного GUID.
  - Администратор по GUID чужого решения работает в базе владельца без `X-Zam-User` (роль `admin`); узлы чужих решений он находит по id так же, как участник.
  - Роль `Member(ro)` с `rw`-токеном на запись — 403 с пояснением «доступ участника к решению — ro» (новый вариант `ApiError::Denied`); `ro`-токен — прежний 403.
  - Рендер для участника: вики-ссылки и вложения разрешаются только в пространстве решения (`AttachScope.only_space`, вид зрителя `Viewer::Member` в ключе кэша); ключ кэша и поколения ссылок — по владельцу базы.
  - Аудит операций над узлом пишет `user_id` действующего пользователя, а владельца базы — в `details.owner`, если это чужое решение.
  - `GET /trash` без `space` — по-прежнему только личная база; корзина решения — `GET /trash?space=<GUID>`.
  - `POST /solutions/{guid}/access/{user}/…` отвечает 200 с записью доступа пользователя (`AccessEntry`); `{user}` — только id (имя разрешает CLI по списку запросов, без учёта регистра).
  - `GET /spaces`: у личных пространств `role: personal`, у своих решений `role: owner` и `shared` (есть одобренные участники); у чужих — `role: member`, `access`, `owner {id, name}`; `access_requests_pending` — число ожидающих запросов к решениям пользователя.
  - `PATCH /admin/settings` принимает только `{rules: {agent_write: bool}}` (лишние поля — 400); аудит `settings.update` — только при изменении значения.
  - Регистрация решений при старте (`bootstrap::register_solutions`): ошибка базы пользователя или пространства — WARN и счётчик `failed` (`RegistryReport.failed`), старт продолжается; итог — одна строка INFO. Гонка в ветке «GUID свободен» `register_user_solutions`: при чужой записи в реестре — ветка конфликта.
  - `zam status` печатает «Роль в решении: владелец | участник (rw/ro) | нет доступа (запрос: …) | не зарегистрировано» и «Ожидают подтверждения доступа: N (zam solution access requests)» при N > 0; в `--json` — `solution_role`, `access_requests_pending`.

- **Задача 4 (индекс: области владельцев, поля записей в payload):**
  - Область `VectorScope` без пространств фильтр не пропускает (fail-closed) — в поиске, `nearest_dense`, подсчёте и удалении по области. В M2 пустой `space_ids` означал «все пространства пользователя»; теперь «вся база» — это явный перечень её пространств: reindex из кэша берёт его из `list_spaces`, `/index/status` считает точки одним запросом по областям всех видимых баз. Защита от ошибки вызывающего: она не открывает чужую базу целиком (Review Focus 2). Без областей Qdrant получил бы пустой фильтр, который пропускает всё, поэтому адаптер в этом случае в Qdrant не ходит.
  - Одна область кладётся прямо в `must` (как в M2: условие на тенанта верхнего уровня), несколько — `should` из вложенных `must[user_id, space_id ∈ …]`.
  - `delete_nodes` заменён на `delete_targets` (узлы по `node_id`, записи по `entry_id`, тенант обязателен); `delete_node` остался удобной обёрткой трейта.
  - Точка обязана иметь ровно одну цель (`node_id` или `entry_id`): иначе upsert отклоняется целиком (`IndexError::Other`), а выдача с повреждённой точкой — `Corrupt`.
  - `IndexChunk.entry: Option<EntryPayload>` — форма полей записи для payload; у всех чанков пока `None`, заполняет задача 6.
  - Тест `ensure_adds_indexes_to_existing_collection` — только для managed Qdrant (`tests/qdrant.rs`, а не общий макрос): он читает схему payload мимо трейта; Edge досоздаёт индексы тем же кодом `ensure`.
  - `/index/status`: точки базы, которая не открылась (`unavailable_dbs`), в `points` больше не входят — без базы неизвестны её пространства.
  - Тестовая обвязка Qdrant (отдельный коммит `test:`): реестр выданных портов в процессе и повтор запуска до 3 раз при занятом адресе (флейк полного прогона zam-server, os error 10048).

- **Задача 5 (поиск по личной базе и базам владельцев решений):**
  - `api/search.rs` разделён на `api/search/{mod.rs, targets.rs, merge.rs}`; поведение M2 в одной базе не изменилось (регрессия `tests/search.rs`, `tests/hybrid.rs` без правки ожиданий).
  - `FtsHit.node_id`, `ChunkMeta.node_id`, `Ranked.node_id` → `target: TargetRef`; лимит `max_per_node` — по цели. В JSON выдачи поле прежнее — `node_id` (для будущих записей — `entry_id`); в карточке md — `n:<id>` из `TargetRef`.
  - `FtsHit.raw_score` — сырой `bm25()` канала (меньше — лучше); `merge_channels` сливает каждый канал баз по нему (стабильно: при равенстве — порядок целей, внутри — порядок канала), обрезает каждый канал до предела одной базы (bm25 — 50, trigram — 20) и ставит балл `1/место`. Баллы bm25 разных баз считаются по IDF и avgdl своей базы — сравнение приближённое; статистика FTS владельца зависит от всей его базы (в том числе от Knowledge, Rules, Human), но сам балл наружу не выходит — в ответе только `1/место` слитого канала и итоговый RRF. Альтернатива, если eval задачи 18 покажет плохой порядок между базами, — RRF по местам внутри каждой базы вместо сравнения сырых bm25.
  - Строгий bm25 хотя бы в одной базе отбрасывает ослабленные (OR) выдачи других баз: в общей базе ослабленный запрос не выполнился бы, а баллы AND и OR несравнимы; trigram берётся из всех баз. Известная неточность: база с пустым bm25 даёт trigram по всей фразе, а база с находками — нет (или по идентификаторам), и эти выдачи смешиваются в одном канале trigram.
  - Чужое решение — отдельная цель (база владельца, одно пространство) только для одобренного участника и администратора; `pending|rejected|revoked` — исключение и `warnings: ["solution access …"]` при явной ссылке (`scope.solution`, `X-Zam-Solution`, GUID или `Id` пространства в `scope.spaces`); без запроса доступа или незарегистрированное — молча (как неизвестное решение в M2). `all_solutions` берёт одобренные чужие без предупреждений о прочих.
  - `scope.spaces` с `Id` пространства чужой базы находит только пространство решения из реестра (`solution_by_space`): Knowledge, Rules, Human владельца по `Id` не находятся.
  - Любой сбой чтения базы чужого решения — открытие, FTS, проверка векторных хитов, листы сводок и их добор, `expand` (текст секции, соседи), L0, `pending_count` — исключает решение целиком (`Health::soft`): WARN в журнал (`skip_foreign`), `warnings: ["solution unavailable"]`, элементы этой цели убираются из выдачи, её `pending_count` не прибавляется; сбой личной базы — ошибка запроса (fix round 1 ревью).
  - Векторный канал — один запрос с областями всех целей без Human; цель без других пространств в фильтр не входит (fail-closed область без пространств). Хит засчитывается, только если `live_chunks` нашёл его в базе своего владельца (`VectorHit.user_id`) в пространствах цели.
  - Элемент выдачи из решения (своего или чужого) несёт `agent_solution_id` (§9.2 ТЗ).
  - Замер `is_tenant` (ревью задачи 4): тестовый Qdrant 1.19.2 (managed, Windows, HDD), ≈190 коротких заметок в трёх базах, 100 гибридных запросов после прогрева (`search_multi::bench_vector_scopes`, `--ignored`): одна область (условие `user_id` в `must`) — p50 1,88 мс, p95 2,53 мс; три области (`user_id` внутри `should`) — p50 2,08 мс, p95 2,54 мс. На малой коллекции разница ~10 % p50 и в пределах шума по p95. Оптимизация `is_tenant` проявляется на больших коллекциях с многими тенантами; повторить замер на рабочем объёме в задаче 18 (eval) и, если проигрыш заметен, разбивать запрос на области параллельными вызовами с одним тенантом.

- **Задача 6 (записи журналов: хранение, ревизии, чанки, индексация, поиск):**
  - Миграция user `0008_entries.sql`: `entries`, `entry_revisions` (append-only триггерами, как `revisions`), `triggers` — по схеме плана; дополнительно частичные индексы `entries_pending` (`pending_count` поиска без обхода записей) и `chunks_entry` (пересборка чанков записи).
  - Модуль `zam_store::entries` (`mod.rs`, `write.rs`, `read.rs`, `chunks.rs`). Хранилище проверяет только целостность: статус есть только у insight (`CHECK` в схеме и `BadInput` в коде), новый insight — `active` по умолчанию, при создании только `active`/`revisit`; `active ↔ revisit` — правкой, `superseded` — только `supersede_entry`, `retracted` — только `retract_entry` с непустой причиной; из `superseded`/`retracted` статус не возвращается (`Conflict`). `certainty` разрешён только у insight **[решение исполнителя]**: у changelog/release он смысла не имеет; задача 9 может ослабить. Права на `certainty` — сервер (задача 9).
  - Пределы **[решение исполнителя]**: заголовок ≤ 500 символов (непустой после обрезки), область ≤ 128 печатных (как `X-Zam-Area`), до 50 тегов по ≤ 100 символов (обрезка, пустые и повторы выбрасываются), `Idempotency-Key` ≤ 200, причина ≤ 2000; `data` — только JSON-объект.
  - `Idempotency-Key` уникален в базе: повтор с тем же ключом, пространством и видом возвращает ту же запись (`false`), иначе `Conflict`. Повтор `supersede` с тем же ключом возвращает ту же пару.
  - Правка без изменений ревизию не создаёт; `if_rev` — оптимистичная блокировка (`Conflict`). `append_body` дописывает через пустую строку (хвостовые переводы строк тела срезаются); вместе с `body` — `BadInput`.   - Чанки записи: документ `# <title>\n\n<body>` → `chunk_note`; `context_prefix` — `[<пространство>/<kind>] <title> | <теги>` (без пути заголовков — по плану); чанки с `entry_id` и без `node_id`, id — та же формула `blake3(id ‖ ordinal ‖ text_hash)`.
