### Задача 2 — сервер: создание отчёта, multipart и JSON, ссылки, лимиты `[reports]` (2026-11-02)

- **Маршрут.** `POST /spaces/{space}/entries`: `multipart/form-data` → отчёт
  (`api/reports.rs::create`, вход `ReportInput::Multipart`), JSON с `kind: report` → отчёт с
  `images: [{name, data}]` (`ReportInput::Json`), остальное — прежний путь. JSON читается
  обработчиком (`reports::read_limited`) с пределом `entries_json_max` = `note_body_max +

  `note_body_max` — 413, как раньше.
- **Порядок проверок:** `space_scope(Mode::Write)` (токен и участник `ro` — 403, Human по токену —
  404) → не решение — 422 → сессия WebUI (пользователь и администратор) — 403 «отчёты пишет агент»

  notes, tasks}`, массивы строк до 200 × 1000 символов), размер тела (413) → ссылки тела
  (`report_refs`) → файлы. Форма JSON (неизвестные поля, `images`) — 400 до доступа, как у прочих
  записей.
- **Multipart:** первая часть `meta` (иначе 400 «первой должна идти часть meta»; больше
  `note_body_max + 64 КиБ` — 413), затем части `file`: имя не из тела — 422 до записи байт, повтор
  — 400, файлов больше `max_files` — 422, картинка с MIME не из пяти — 422, иначе поток в

## Решения

Решения контроллера и исполнителя, принятые без владельца; каждое можно пересмотреть.

- **Триггер `entries_report_immutable` защищает все колонки, кроме `deleted_at`, `updated_at`,
  `index_state` (исполнитель, задача 1).** Бриф перечислял содержимое (`kind … current_rev`);
  добавлены `id`, `space_id`, `superseded_by_id`, `retract_reason`, `idempotency_key`, атрибуция
  (`author_kind`, `user_id`, `token_id`, `session_id`, `machine`) и `created_at`: подмена автора
  или даты — тоже «тихое изменение» (анти-цель спецификации §3). Ни один путь кода эти колонки у
  записей не меняет (проверено `grep "UPDATE entries"`).
- **`entry_attachments.blob_sha256 REFERENCES blobs (sha256)` (исполнитель, задача 1)** — как у
  `attachments`; строка `blobs` вставляется до пары в той же транзакции.
- **Пространство отчёта проверяет и хранилище (исполнитель, задача 1):** `create_report` вне
  пространства решения → `BadInput` (сервер отвечает 422 раньше, задача 2; здесь — защита
  глубины).
- **Повтор пары (имя, sha256) в `files` — одна строка (исполнитель, задача 1)**, как повторная
  привязка вложения заметки; отпечаток `Idempotency-Key` — множество пар (порядок файлов не важен).
- **`ReportImmutable` раньше `If-Match` (исполнитель, задача 1):** у отчёта нет допустимой правки,
  поэтому проверка ревизии ему не нужна; пустой `EntryPatch` — тоже `ReportImmutable`. Задачи и
  вопросы: отчёт — `ReportImmutable`, а не `NotTask`/`NotQuestion` (бриф).
- **FTS-фильтр видов (`search.rs`, исполнитель, задача 1):** `report` входит в фильтр целей поиска
  только явным видом (`kinds ∋ report`); пустой список видов (умолчание) отчёт не включает. Нужен
  тесту брифа «FTS находит» и даёт безопасное умолчание хранилища; отсечение вида у токена —
  сервер (задача 4).
- **Миниатюра `first_images` (исполнитель, задача 1):** первая ссылка-картинка тела
  (`zam_markdown::parse`, `LinkKind::Image`, `attachment_ref`), для которой у записи есть файл с
  MIME `image/*`; ссылка-картинка на файл другого MIME или без файла пропускается.
- **Размер файла против `blobs.size` — `BadInput`, а не `debug_assert` (исполнитель, раунд правок
  1).** Расхождение означает неверное описание файла вызывающим (сервер посчитал размер не того
  потока); в релизе проверка должна действовать, иначе `size` пары и блоба разойдутся навсегда.
- **Корзина ленты (исполнитель, задача 1):** `deleted_only` меняет ключ порядка и курсора на
  `deleted_at`; фильтры `since`/`until` по-прежнему по `created_at`.

- **Предел слоя маршрута записей — сумма, а не максимум (исполнитель, задача 2):**
  `note_body_max + 64 КиБ + max_total_bytes + 1 МиБ`. Законный отчёт — часть `meta` до
  `note_body_max + 64 КиБ` и файлы до `max_total_bytes`; при `max(…)` из плана отчёт с большим
  телом и файлами на пределе обрывался бы слоем. Точные пределы проверяет обработчик.
- **JSON записи читается своим потоковым чтением (исполнитель, задача 2)** —
  `reports::read_limited` вместо `axum::body::to_bytes` из плана: так 413 не требует разбора
  ошибки `http-body-util` (новой зависимости сервера не нужно).
- **Имя файла отчёта = путь из тела после percent-декодирования без ведущих `./` (исполнитель,
  задача 2).** `<figs/my plot.png>`, `figs/my%20plot.png` и `./figs/my plot.png` — один файл
  `figs/my plot.png`. Имя части `file` и `images[].name` не декодируется: у него снимаются только
  ведущие `./`, остальное сравнивается побайтно (раунд правок 1). CLI (задача 5) отправляет
  декодированный путь.
- **Пути и схемы (исполнитель, задача 2).** Кроме правил брифа отказ (422) получают: символы
  `" : * ? < > |` в пути (запрещены в именах Windows, `?` — запрос), сегменты `.`, пустые
  сегменты, управляющие символы (правила пути узла), любая схема, кроме `http`, `https`, `mailto`
  (`javascript:`, `file:`, `ftp:`, `C:/…`), каталог `_attachments/` в пути. Неизвестная часть
  multipart (не `file`) — 422 (Review Focus 3), часть `file` без имени — 400.
- **Расхождение по `Idempotency-Key` — 422 `/problems/idempotency-mismatch`, как у всех записей
  (исполнитель, задача 2).** Бриф назвал тест `…_mismatch_409`; 409 у записей — только ключ
  удалённой записи. Тест назван `report_idempotency_repeat_200_mismatch_422`.
- **Тест лимитов — `max_files = 3`, а не 2 (исполнитель, задача 2):** при двух файлах по 512 Б
  сумма (1024 Б) не превышает 1 КиБ, и предел суммы непроверяем.
- **Адрес без `Host` и `server.public_url` (исполнитель, задача 2)** — путь от корня сервера
  (`<base_path>/#/u/…`), а не 400: отчёт уже проверен, отказывать из-за адреса для человека
  нельзя (внутренние вызовы MCP и тесты `oneshot` без `Host`).
- **Проверки до записи байт; multipart — потоком (исполнитель, задача 2, раунд правок 1).** До
  первого `put`: доступ, `data`, заголовок, атрибуция и `Idempotency-Key`, ссылки тела, число
  файлов тела против `max_files`, длина переписанного тела (длина ссылки `_attachments/<sha16>/…`
  от sha256 не зависит). JSON проверяет и декодирует все файлы до записи первого. Сиротами
  остаются байты при отказе после `put`: multipart — следующая часть не прошла (имя, MIME,
  размер, повтор) или нет файла по ссылке; оба входа — отказ `create_report` (расхождение
  `Idempotency-Key`, гонка). Их убирает сборщик мусора M7 (см. «Отложенные замечания»).
- **Пределы разбора ссылок (исполнитель, раунд правок 1 задачи 2).** `LINKS_MAX` = 4096 ссылок на
  файлы (с повторами) — больше 422; определения `[метка]: путь` собираются одним проходом для
  всех меток, на метку — первые `DEFS_PER_LABEL_MAX` = 16 по тексту (дальше не смотрим: действует
  первое вне кода); проверочных разборов — не больше 17; поиск назначений тратит не больше
  `4 × |тело| + 1 МиБ` байт диапазонов (глубокое вложение картинок — 422); разбор идёт в
  `spawn_blocking`. Тест: 10 000 ссылок × 10 000 определений — 422 быстрее 10 с; 4000 ссылок
  × 10 000 определений (10 первых — в коде) — разбирается быстрее 10 с.
- **Вид JSON-записи без построения `Value` (исполнитель, раунд правок 1 задачи 2).**
  `Content-Length` больше `entries_json_max` — 413 без чтения; тело больше `note_body_max` —
  `reports::json_is_report` (`kind` строкой, прочие поля — `IgnoredAny`), не отчёт — 413 до
  `Value`; повтор `kind` — не отчёт.
- **base64 файлов MCP (исполнитель, раунд правок 1 задачи 2):** стандартный алфавит с
  выравниванием, пробельные символы (переносы MIME/PEM) отбрасываются; URL-safe не принимается
  (MCP-клиенты кодируют стандартно, двусмысленность алфавитов не нужна).
- **Якорь переписанной ссылки (исполнитель, раунд правок 1 задачи 2):** пробел, `( ) < > & \ " '
  [ ]` и управляющие — `%XX`; `%` не трогается (якорь — как в исходнике).
- **`attachment_link` кодирует `&` и `\` (исполнитель, раунд правок 1 задачи 2):** иначе имя
  `x&copy;.png` Markdown читал как сущность и ссылка теряла файл; затронуты и новые ссылки
  вложений заметок (старые тела не меняются, разбор `%XX` прежний).
- **`![[…]]` в отчёте — 422 (исполнитель, раунд правок 1 задачи 2)** с подсказкой
  `![подпись](путь)`: разбор не видит встраивание ни картинкой, ни ссылкой; проверка — разбором
  копии тела с `!` → пробел (в коде — не отказ).
- **Предел тела `/mcp` — `entries_json_max` (исполнитель, раунд правок 1 задачи 2):** иначе
  MCP-отчёт до `mcp_max_bytes` отбивался транспортом раньше REST. Предел действует на **все**
  инструменты MCP (rmcp строит `Map<String, Value>` из любого тела до 32,5 МБ при умолчаниях);
  пределы заметок и записей по-прежнему проверяют маршруты REST, память ограничивает семафор
  больших тел (ниже).
- **Семафор больших тел (контроллер по ревью, раунд правок 2 задачи 2).** `api::big_body`:
  тело больше `note_body_max` (по `Content-Length` до чтения или по прочитанному без него)
  занимает одно из 2 разрешений, общих для `POST /spaces/{space}/entries` и `/mcp` (слой после
  аутентификации), на время обработки; не получено за 500 мс — 503 `/problems/busy`,
  `Retry-After: 2`. Тела до `note_body_max` идут без семафора. В памяти — не больше двух больших
  тел одновременно.
- **JSON отчёта — типы без `Value` (раунд правок 2 задачи 2).** `ReportRequest`
  (`deny_unknown_fields`: `kind`, поля `ReportMeta`, `images`, `refs` — только для 422) из байт;
  лишнее поле — 400 на первом же ключе. `tags` — до `TAGS_MAX` (50), `images` — до 1024, длиннее
  — 400 при разборе. `data` по спецификации §4 — только `refs {commits, files, notes, tasks}`
  (в ТЗ и спецификации других ключей у отчёта нет): `ReportData` проверяется при разборе,
  значения вне схемы пропускаются `IgnoredAny`, элементы сверх 200 не хранятся, первое
  нарушение — 422 после проверки доступа (как раньше). `ReportInput::Json` несёт байты.
- **`match_bracket` без квадратичности (раунд правок 2 задачи 2):** закрывающая
  последовательность `` ` `` той же длины ищется по индексу начал по длине (как в CommonMark),
  индекс строится лениво один раз на вызов.
- **`\![[…]]` — не встраивание (раунд правок 2 задачи 2):** нечётное число `\` перед `!`.
- **Текст 413 называет сработавший предел (раунд правок 1 задачи 2):** поток обрывается на
  меньшем из `blob_max_bytes` и остатка `max_total_bytes` — его ключ и назван; в JSON сначала
  файл, затем сумма.
- **MIME картинки — по имени (`mime_guess`), затем по типу части (исполнитель, задача 2);**
  содержимое не проверяется: HTML под именем `.png` отдаётся с `nosniff` и CSP `sandbox` (задача 3).
- **Сессия администратора — тоже 403 (исполнитель, задача 2):** «отчёты пишет агент» относится
  к любой cookie-сессии WebUI.
- **Определения ссылок-сносок ищутся только в начале строки с отступом до 3 пробелов
  (исполнитель, задача 2):** определение внутри цитаты или пункта списка не находится — 422
  «назначение не найдено — используйте [текст](путь)», а не тихая потеря картинки.

## Отложенные замечания

- **M7: сборщик мусора блобов.** Снять триггеры `entry_attachments_no_update` /
  `entry_attachments_no_delete` вместе с окончательным удалением отчёта из корзины и очисткой
  блобов (`refcount`) и триггер `entry_attachments_report_only` (если открепление потребует
  вставок). Позднюю вставку файла отличает время: строка принимается только с `created_at`
  отчёта (раунд правок 1, Minor 1); подделать такое время прямым SQL можно, но единственный
  писатель кода — `create_report`.
- **M7: байты блоба при откате (Minor 5).** Сервер пишет блоб в `BlobStore` до транзакции
  `create_report`; при её откате файл остаётся на диске без строки `blobs` — его убирает сборщик
  мусора блобов M7.
- **Риск до M7: заполнение диска сиротами (ревью задачи 2).** Агент с `rw`-токеном может
  многократно слать multipart, где после крупных файлов идёт отказ (лишняя часть, нет файла по
  ссылке, расхождение ключа): каждый раз до `max_total_bytes` байт остаётся на диске без строки
  `blobs`. До сборщика мусора M7 защиты нет (кроме прав токена); смягчение — сборщик сирот
  `.incoming`/блобов без строки при старте или квота на пользователя.
- **Задача 5: имя файла части multipart.** CLI шлёт `filename="<путь>"` в UTF-8 без
  `filename*=` (multer `filename*` не разбирает), путь — как в теле после percent-декодирования
  и без `./`; кавычка и `\` в пути запрещены правилами ссылок, экранирование не нужно.
- **Задачи 3–4: видимость раньше хранилища (Minor 3).** Сервер обязан проверить видимость отчёта
  для токена до вызова хранилища и отвечать 404 на PATCH, supersede, retract, triggers, claim,
  answer, `POST /edges` и `links` insight с концом-отчётом; иначе ответы хранилища 422/409
  (`BadInput`, `ReportImmutable`) выдают существование отчёта.
- **Корзина без индекса (Minor 6).** `deleted_only` — проход записей пространства с
  `deleted_at IS NOT NULL` без своего индекса (`entries_feed` частичный, `deleted_at IS NULL`);
  при росте корзины — частичный индекс `(space_id, deleted_at) WHERE deleted_at IS NOT NULL`.
- **Не вливать ветку между задачами 2 и 4 (Minor 7).** После задачи 2 отчёт создаётся через API,
  а невидимость для токена готова только в задаче 4.
- ~~**Задача 3: ответ сервера на `StoreError::ReportImmutable`.**~~ Сделано в задаче 2:
  `ApiError::ReportImmutable` — 409 `/problems/report-immutable`. Задача 3 по-прежнему
  отвечает 409 раньше хранилища на изменяющих маршрутах (`deny_report_mutation`).
- **Задача 4: буква `p` уже принимается разбором ссылок** (`/read`, кэш, MCP — общий
  `is_entry_ref_letter`); невидимость отчёта для токена по всем путям — задача 4.
