### Задача 1 — хранилище: вид `report`, миграция 0022, `entry_attachments`, неизменность (2026-11-02)

- **Миграция `0022_reports.sql`** (`rebuild: true`, по образцу 0015). Пользовательские 0019–0021
  заняты M5, поэтому номер — 22. Схема `entries` снята с базы на 0021 через `sqlite_master`: с 0015
  не менялась (индексы `entries_feed`, `entries_title`, `entries_pending`, автоиндексы PRIMARY KEY
  и UNIQUE, триггеров нет; дочерние FK — `entry_revisions`, `triggers`, самоссылки). M5 менял

  пересборка не касается. CHECK: `kind` += `report`; `(status IS NULL) = (kind IN ('changelog',
  'release', 'report'))`; `kind <> 'report' OR (certainty, supersedes_id, superseded_by_id,
  retract_reason — NULL)`. Индексы `entries_*` созданы заново.
- **`entry_attachments`** `(entry_id → entries, blob_sha256 → blobs, filename, mime, size,

## Решения

Решения контроллера и исполнителя, принятые без владельца; каждое можно пересмотреть.

- **Триггер `entries_report_immutable` защищает все колонки, кроме `deleted_at`, `updated_at`,
  `index_state` (исполнитель, задача 1).** Бриф перечислял содержимое (`kind … current_rev`);
  добавлены `id`, `space_id`, `superseded_by_id`, `retract_reason`, `idempotency_key`, атрибуция
  (`author_kind`, `user_id`, `token_id`, `session_id`, `machine`) и `created_at`: подмена автора
  или даты — тоже «тихое изменение» (анти-цель спецификации §3). Ни один путь кода эти колонки у
  записей не меняет (проверено `grep "UPDATE entries"`).
- **`entry_attachments.blob_sha256 REFERENCES blobs (sha256)` (исполнитель, задача 1)** — как у
  `attachments`; строка `blobs` вставляется до пары в той же транзакции.
- **Пространство отчёта проверяет и хранилище (исполнитель, задача 1):** `create_report` вне
  пространства решения → `BadInput` (сервер отвечает 422 раньше, задача 2; здесь — защита
  глубины).
- **Повтор пары (имя, sha256) в `files` — одна строка (исполнитель, задача 1)**, как повторная
  привязка вложения заметки; отпечаток `Idempotency-Key` — множество пар (порядок файлов не важен).
- **`ReportImmutable` раньше `If-Match` (исполнитель, задача 1):** у отчёта нет допустимой правки,
  поэтому проверка ревизии ему не нужна; пустой `EntryPatch` — тоже `ReportImmutable`. Задачи и
  вопросы: отчёт — `ReportImmutable`, а не `NotTask`/`NotQuestion` (бриф).
- **FTS-фильтр видов (`search.rs`, исполнитель, задача 1):** `report` входит в фильтр целей поиска
  только явным видом (`kinds ∋ report`); пустой список видов (умолчание) отчёт не включает. Нужен
  тесту брифа «FTS находит» и даёт безопасное умолчание хранилища; отсечение вида у токена —
  сервер (задача 4).
- **Миниатюра `first_images` (исполнитель, задача 1):** первая ссылка-картинка тела
  (`zam_markdown::parse`, `LinkKind::Image`, `attachment_ref`), для которой у записи есть файл с
  MIME `image/*`; ссылка-картинка на файл другого MIME или без файла пропускается.
- **Корзина ленты (исполнитель, задача 1):** `deleted_only` меняет ключ порядка и курсора на
  `deleted_at`; фильтры `since`/`until` по-прежнему по `created_at`.

## Отложенные замечания

- **M7: сборщик мусора блобов.** Снять триггеры `entry_attachments_no_update` /
  `entry_attachments_no_delete` вместе с окончательным удалением отчёта из корзины и очисткой
  блобов (`refcount`). Прямая вставка строки `entry_attachments` к существующему отчёту триггерами
  не запрещена (транзакцию создания от последующей SQL не отличить); единственный писатель —
  `create_report`.
- **Задача 3: ответ сервера на `StoreError::ReportImmutable`.** До задачи 3 ветка попадает в общий
  `other => Internal` `From<StoreError> for ApiError` (500); отчёт через API до задачи 2 не
  создаётся, поэтому на поведение M5 это не влияет.
- **Задача 4: буква `p` уже принимается разбором ссылок** (`/read`, кэш, MCP — общий
  `is_entry_ref_letter`); невидимость отчёта для токена по всем путям — задача 4.
