## Задачи

### Task 14 — eval (§18.2): корпус, запросы, метрики, гейт качества int8

**Набор.** 160 заметок (ru 82, en 78) собственного текста в 8 областях — Windows и кодировки,
git, Linux и Docker, Rust, документы проекта своими словами, исследования поиска и ML,
инструменты разработки, эксплуатация и БД; в каждой — «трудные соседи». 197 запросов:
paraphrase 61 (из них без общих слов 46 — 23 %), exact 31, identifier 42, cross-lang 38,
broad 25. «Без общих слов» проверяется автоматически по словоформам (первые min(5, длина)
символов слова от 3 букв, без служебных) — тест `eval_set_is_valid` и `cargo xtask eval
--check`. Корпус писали восемь параллельных субагентов по правилам и одному проверяющему exe.

**Инструмент.** `cargo xtask eval` (xtask/src/eval.rs и eval/): сервер из target/release на
`target/eval/<прогон>` через обвязку smoke (`smoke::Server`, `SmokeEnv::for_model`,
`wait_health_for`, `api_timeout` — общие, не копия), модели из target/models, ORT и Qdrant из
target/deps, для CUDA — без CUDA Toolkit в `PATH`. Метрики — recall@5, MRR@10, nDCG@10 на
уровне заметок (`mode = notes`), 95 % интервалы бутстрепа, парный бутстреп для сравнений.

**Найденный дефект продукта.** Запись заметки падала с 500: сегментатор предложений
(`zam-markdown/sentences.rs`) резал `&str` по байтовому индексу внутри UTF-8 при незакрытой
обратной кавычке перед многобайтовым символом (`` `--target — … ``) — паника в потоке
записи. Исправлено (сравнение побайтовое), тест `unclosed_backtick_before_multibyte_char`.

Файлы — `eval/results/2026-10-19-*.{json,md}`. Интервалы ±0,05–0,06: при 197 запросах это шум
набора; разница прогонов сравнивается парно.

**Наблюдение: шум ослабленного bm25.** Векторный канал сам по себе (`w_fts = w_trigram = 0`)
давал nDCG@10 0,758 > гибрид 0,719. Причина: запрос без совпадений всех слов уходит в
ослабленный bm25 (любое слово), тот возвращает 50 случайных заметок, и при равных весах RRF
они вытесняют векторные находки (перефразы без общих слов: 0,25 → 0,06). Проверено, что
модель здорова: косинусы запрос–заметка ранжируют верно, но с малым зазором (перефразы
намеренно трудные).

**Гейт качества int8** (`eval/results/2026-10-19-quality-gate*.md`):

| Кандидат | dense: средний / мин. | sparse ρ | Δ recall@5 / Δ nDCG@10 к fp32 | индексация |
|---|---|---|---|---:|
| Xenova int8 (динамическое, per-channel, 7 бит, Gather int8) | 0,978 / 0,965 | 0,972 | −0,005 / −0,001 (после подбора весов: 0,000 / +0,003) | 211–236 с |
| собственное динамическое per-channel, 8 бит, Gather fp32 | 0,984 / 0,969 | 0,977 | 0,000 / +0,001 | 279 с* |
| собственное только веса (MatMulNBits 8 бит, вычисления fp32) | 0,9997 / 0,9989 | 0,999 | 0,000 / 0,000 | 669 с* |
| то же, accuracy_level 4 | 0,9992 / 0,9980 | 0,997 | 0,000 / +0,002 | 849 с* |
| fp16 CUDA (справочно) | 1,0000 / 0,9998 | 1,000 | 0 / 0 | 26 с |
| fp32 CPU (эталон) | — | — | — | 479–594 с |

\* под параллельной нагрузкой (сетка на GPU); порядок величин устойчив.

- Порог косинуса dense (средний ≥ 0,99, минимальный ≥ 0,97) **не проходит ни одно динамическое
  int8**: ошибку даёт квантование активаций одним масштабом на тензор (`DynamicQuantizeLinear`),
  а не точность весов — per-channel без reduce_range улучшает лишь до 0,984. Это совпадает с
  опубликованными замерами (raludi per-channel: 0,989/0,986).
- `gpahal/bge-m3-onnx-int8` не проверялся: он динамический **per-tensor** (грубее обоих
  проверенных per-channel) и отдаёт готовые головы `dense_vecs/sparse_vecs`, а не скрытые
  состояния — нужен второй путь пулинга в zam-ml без шанса пройти порог.
- Квантование только весов проходит все пороги с запасом, но ядро `MatMulNBits` 8 бит в ORT на
  CPU в 2,8–3,6 раза медленнее Xenova int8 и медленнее fp32 — проваливает §17 (≥ 3 чанка/с:
  846 чанков за 669 с ≈ 1,3/с против 3,6/с у Xenova).
- По поиску все варианты неотличимы от fp32 (|Δ| ≤ 0,5 п. п. при шуме ±5 п. п.).

**Решение (исполнитель, на проверку владельцу):** оставить Xenova int8 для CPU. Порог косинуса
был заменителем качества поиска; прямые метрики поиска гейт проходит. int8 и fp16 считаются
разными моделями (`model_id` с sha8 файла, CPU-вариант на GPU не запускается) — по правилу
исследования 05 §3.3 (косинус int8–fp16 0,978 < 0,99). Инструмент гейта оставлен строгим: он
по-прежнему сообщает «не пройден» по порогу косинуса. Скрипт собственного квантования —
`tools/quantize-bge-m3.py` (оба метода), если владелец предпочтёт точность скорости.
Варианты на будущее: статическое квантование с калибровкой (SmoothQuant) — активации со
статическими масштабами; ORT с быстрым 8-битным `MatMulNBits`.

**Шаг 3: веса и чанкинг** (`eval/grid.toml`, 12 конфигураций, bge-m3-fp16 CUDA;
`eval/results/2026-10-19-grid-bge-m3-fp16.md`). Парный бутстреп разности nDCG@10 с базой:

| Конфигурация | Δ nDCG@10 [95 %] | Δ без общих слов | итог |
|---|---|---|---|
| `w_fts = 0.25` | +0,032 [+0,016…+0,048] | +0,100 | лучше |
| `w_fts = 0.5` | +0,010 [+0,001…+0,021] | +0,035 | лучше (меньше) |
| `w_vector = 1.5` / `2.0` | +0,003 / +0,009 | | шум |
| `w_trigram = 0.3` / `1.0` | +0,002 / −0,000 | | шум |
| `rrf_k = 20` | +0,001 | | шум |
| чанки 150–300 | +0,007 [+0,001…+0,015] | +0,031 | лучше (на грани) |
| чанки 500–800 | +0,002 | | шум |
| перекрытие 0 / 2 предложения | +0,002 / 0,000 | | шум |

Проверка выбора (`eval/grid-confirm.toml`, база — `w_fts = 0.25`): чанки 150–300 поверх неё —
+0,004 [−0,004…+0,012], `w_fts = 0.1` — +0,010 [−0,004…+0,024]: оба в пределах шума.
Повтор одной конфигурации на свежем индексе даёт разброс ±0,003 (HNSW, порядок индексации).

**Побочный эффект глобального `w_fts = 0.25`.** Полный прогон тестов упал на
`human_deleted_and_excluded_not_in_vector_channel`: заметка Human (в Qdrant её нет никогда)
с точным словом запроса пропала из выдачи. Причина в арифметике RRF: векторный канал отдаёт
до 60 кандидатов на любой запрос, его худший балл 1/(60+60) ≈ 0,0083, а лучший балл bm25 при
весе 0,25 — 0,25/61 ≈ 0,0041: FTS-only находка (Human, заметка до векторизации, деградация
одного канала) не обгоняет ни одного векторного кандидата. Eval этого не видел — все его
заметки векторизованы. Решение — разделить вес: шум даёт только **ослабленный** bm25 (ни один
чанк не содержит всех слов запроса, сработал запрос «любое слово»), ему и нужен малый вес.
Новый ключ `search.w_fts_relaxed` (zam-store сообщает `FtsChannels::relaxed`), строгий
`w_fts` остаётся 1.0. Проверка (`eval/grid-relaxed.toml`, парно с `w_fts_relaxed = 0.25`):
глобальный `w_fts = 0.25` — −0,002 [−0,005…+0,000] (тот же выигрыш), прежнее поведение
(`w_fts_relaxed = 1.0`) — −0,033 [−0,048…−0,018], хуже.

**Выбрано:** `search.w_fts_relaxed = 0.25`, остальные веса прежние (`w_vector = 1.0`,
`w_fts = 1.0`, `w_trigram = 0.7`, `rrf_k = 60`); чанкинг прежний — 300–500 токенов, предел
800, перекрытие 1 предложение, склейка < 100: выигрыш 150–300 мал (< 1 п. п.), исчезает вместе
с новым весом и удвоил бы число векторов. Пороги чанкинга вынесены в `[index]` (`chunk_*`),
чтобы их можно было менять без сборки; новые значения действуют на заметки, записанные после
перезапуска, старые перенарезает `zam-server reindex --full` (так же, как при смене счётчика
токенов) — автоматической перечанковки при смене порогов нет. Веса действуют при поиске,
переиндексация не нужна.

После подбора (`--label tuned`): fp16 hybrid nDCG@10 0,752 (было 0,719), hybrid+rerank 0,838
(было 0,775); int8 CPU hybrid — 0,748 (было 0,718), hybrid+rerank jina — 0,827 (было 0,778);
перефразы без общих слов в hybrid — 0,15–0,16 вместо 0,06. Файлы
`eval/results/2026-10-19-*-tuned.*`.
