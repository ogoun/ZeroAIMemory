### Task 14 — eval (§18.2): корпус, запросы, метрики, гейт качества int8

**Набор.** 160 заметок (ru 82, en 78) собственного текста в 8 областях — Windows и кодировки,
git, Linux и Docker, Rust, документы проекта своими словами, исследования поиска и ML,
инструменты разработки, эксплуатация и БД; в каждой — «трудные соседи». 197 запросов:
paraphrase 61 (из них без общих слов 46 — 23 %), exact 31, identifier 42, cross-lang 38,
broad 25. «Без общих слов» проверяется автоматически по словоформам (первые min(5, длина)
символов слова от 3 букв, без служебных) — тест `eval_set_is_valid` и `cargo xtask eval
--check`. Корпус писали восемь параллельных субагентов по правилам и одному проверяющему exe.

**Инструмент.** `cargo xtask eval` (xtask/src/eval.rs и eval/): сервер из target/release на
`target/eval/<прогон>` через обвязку smoke (`smoke::Server`, `SmokeEnv::for_model`,
`wait_health_for`, `api_timeout` — общие, не копия), модели из target/models, ORT и Qdrant из
target/deps, для CUDA — без CUDA Toolkit в `PATH`. Метрики — recall@5, MRR@10, nDCG@10 на
уровне заметок (`mode = notes`), 95 % интервалы бутстрепа, парный бутстреп для сравнений.

**Найденный дефект продукта.** Запись заметки падала с 500: сегментатор предложений
(`zam-markdown/sentences.rs`) резал `&str` по байтовому индексу внутри UTF-8 при незакрытой
обратной кавычке перед многобайтовым символом (`` `--target — … ``) — паника в потоке
записи. Исправлено (сравнение побайтовое), тест `unclosed_backtick_before_multibyte_char`.

модель здорова: косинусы запрос–заметка ранжируют верно, но с малым зазором (перефразы
намеренно трудные).

**Гейт качества int8** (`eval/results/2026-10-19-quality-gate*.md`):

| Кандидат | dense: средний / мин. | sparse ρ | Δ recall@5 / Δ nDCG@10 к fp32 | индексация |
|---|---|---|---|---:|
| Xenova int8 (динамическое, per-channel, 7 бит, Gather int8) | 0,978 / 0,965 | 0,972 | −0,005 / −0,001 (после подбора весов: 0,000 / +0,003) | 211–236 с |
| собственное динамическое per-channel, 8 бит, Gather fp32 | 0,984 / 0,969 | 0,977 | 0,000 / +0,001 | 279 с* |
| собственное только веса (MatMulNBits 8 бит, вычисления fp32) | 0,9997 / 0,9989 | 0,999 | 0,000 / 0,000 | 669 с* |
| то же, accuracy_level 4 | 0,9992 / 0,9980 | 0,997 | 0,000 / +0,002 | 849 с* |
| fp16 CUDA (справочно) | 1,0000 / 0,9998 | 1,000 | 0 / 0 | 26 с |
| fp32 CPU (эталон) | — | — | — | 479–594 с |

\* под параллельной нагрузкой (сетка на GPU); порядок величин устойчив.

- Порог косинуса dense (средний ≥ 0,99, минимальный ≥ 0,97) не прошёл ни один проверенный
  динамический int8: Xenova (per-channel, 7 бит) — 0,978, собственный per-channel 8 бит с fp32
  Gather — 0,984. Вероятный источник ошибки — квантование активаций одним масштабом на тензор
  (`DynamicQuantizeLinear`): точность весов per-channel почти ничего не добавила. Это согласуется
  с опубликованными замерами (raludi per-channel: 0,989/0,986).
- Квантование только весов проходит все пороги с запасом, но ядро `MatMulNBits` 8 бит в ORT на
  CPU в 2,8–3,6 раза медленнее Xenova int8 и медленнее fp32 — проваливает §17 (≥ 3 чанка/с:
  846 чанков за 669 с ≈ 1,3/с против 3,6/с у Xenova).
- **Не проверялись** (варианты для владельца): mixed precision — fp32 для чувствительных узлов
  (`nodes_to_exclude`: первые/последние слои, внимание); статическое QDQ с калибровкой
  (SmoothQuant или обычные статические масштабы активаций); `gpahal/bge-m3-onnx-int8`
  (динамический per-tensor, отдаёт готовые `dense_vecs/sparse_vecs` — нужен второй путь
  пулинга в zam-ml).
- По поиску разница int8 − fp32 статистически не отличима от нуля: парный бутстреп по 197
  запросам (fix round 1, `eval/results/2026-10-20-quality-gate.md`): Δ recall@5 = 0,000 [−0,015…+0,015], Δ nDCG@10 = +0,002 [−0,007…+0,012]. Это «ухудшения не обнаружено», а не равенство: нижняя граница интервала recall@5 (−1,5 п. п.) ниже порога −1 п. п., то есть набор из 197 запросов не может исключить падение в 1–1,5 п. п.

**Решение (исполнитель; утверждено владельцем 2026-10-20 — «Оставляй int8»):** оставить Xenova int8 для CPU. Критерий гейта владелец не менял: порог косинуса остаётся строгим, «не пройден» — информационно. Порог косинуса
был заменителем качества поиска; по прямым метрикам поиска интервал разности с fp32 включает
ноль, точечные оценки в пределах порога −1 п. п. (интервал recall@5 — нет). int8 и fp16 считаются разными моделями
(`model_id` с sha8 файла, CPU-вариант на GPU не запускается) — по правилу исследования 05 §3.3
(косинус int8–fp16 0,978 < 0,99). Инструмент гейта оставлен строгим: он по-прежнему сообщает
«не пройден» по порогу косинуса. Скрипт собственного квантования — `tools/quantize-bge-m3.py`
(оба проверенных метода).

Проверка выбора (`eval/grid-confirm.toml`, база — `w_fts = 0.25`): чанки 150–300 поверх неё —

Повтор одной конфигурации на свежем индексе даёт разброс ±0,003 (HNSW, порядок индексации).

**Побочный эффект глобального `w_fts = 0.25`.** Полный прогон тестов упал на
`human_deleted_and_excluded_not_in_vector_channel`: заметка Human (в Qdrant её нет никогда)
с точным словом запроса пропала из выдачи. Причина в арифметике RRF: векторный канал отдаёт
до 60 кандидатов на любой запрос, его худший балл 1/(60+60) ≈ 0,0083, а лучший балл bm25 при
весе 0,25 — 0,25/61 ≈ 0,0041: FTS-only находка (Human, заметка до векторизации, деградация
одного канала) не обгоняет ни одного векторного кандидата. Eval этого не видел — все его
заметки векторизованы. Решение — разделить вес: шум даёт только **ослабленный** bm25 (ни один
чанк не содержит всех слов запроса, сработал запрос «любое слово»), ему и нужен малый вес.
Новый ключ `search.w_fts_relaxed` (zam-store сообщает `FtsChannels::relaxed`), строгий
`w_fts` остаётся 1.0. Проверка (`eval/grid-relaxed.toml`, парно с `w_fts_relaxed = 0.25`):
глобальный `w_fts = 0.25` — −0,002 [−0,005…+0,000] (тот же выигрыш), прежнее поведение
(`w_fts_relaxed = 1.0`) — −0,033 [−0,048…−0,018], хуже.

**Выбрано:** `search.w_fts_relaxed = 0.25`, остальные веса прежние (`w_vector = 1.0`,
`w_fts = 1.0`, `w_trigram = 0.7`, `rrf_k = 60`); чанкинг прежний — 300–500 токенов, предел
800, перекрытие 1 предложение, склейка < 100: выигрыш 150–300 мал (< 1 п. п.), исчезает вместе
с новым весом и удвоил бы число векторов. Пороги чанкинга вынесены в `[index]` (`chunk_*`),
чтобы их можно было менять без сборки; новые значения действуют на заметки, записанные после
перезапуска, старые перенарезает `zam-server reindex --full` (так же, как при смене счётчика
токенов) — автоматической перечанковки при смене порогов нет. Веса действуют при поиске,
переиндексация не нужна.

После подбора (`--label tuned`): fp16 hybrid nDCG@10 0,752 (было 0,719), hybrid+rerank 0,838
(было 0,775); int8 CPU hybrid — 0,748 (было 0,718), hybrid+rerank jina — 0,827 (было 0,778);
перефразы без общих слов в hybrid — 0,15–0,16 вместо 0,06. Файлы
`eval/results/2026-10-19-*-tuned.*`.

  запросы на устаревание добавить вместе с ними.
- CPU-реранк jina: p50 2,0 с на 20 кандидатах при цели 1,5 с — задача 15.
- `w_fts_relaxed` ниже 0,25 (0,1: +0,07 на перефразах, в целом не значимо) — набор с 23 %

- Порог косинуса гейта int8 — решение владельца (принять отклонение или переходить на

### Task 14 — fix round 1 (ревью)

- **`w_fts_relaxed` только там, где есть с кем соревноваться.** Вес ослабленного bm25
  применяется, только если векторный канал работает (`SearchInputs::vector` есть) и чанк ему
  виден: не Human и узел проиндексирован (`FtsHit::index_state = indexed`). FTS-only поиск,
  Human и заметки в очереди индексации ранжируются с `w_fts`. Без этого в смешанной области
  (Knowledge + Human) FTS-only находка ослабленного запроса (0,25/61) проигрывала всем
  векторным кандидатам (худший 1/120). Тесты: `relaxed_fts_weight_only_for_vector_visible_chunks`
  (zam-search), в `tests/hybrid.rs` — Human-заметка находится ослабленным запросом в смешанной
  области (без исправления тест падает) и порядок FTS-only совпадает с `w_fts`. На eval
  поведение не меняется: все заметки набора векторизованы, `fts` — тот же 0,686.
- **Проверка «без общих слов» строже:** слова от 2 символов (кроме служебных) и основы
  Snowball (`rust-stemmers =1.2.0`, MIT/BSD-3-Clause, без unsafe, только xtask) в дополнение к
  префиксу. Переписаны d-02, d-05, f-01, f-07, h-05 (общие «fn», «редко/редкие», «уроки»,
  «DB»; f-01 — по ревью). Доля disjoint — 46 из 197 (23 %). Отпечаток запросов теперь пишется в
  результат (`queries_fingerprint`), как и действующие `[search]`/`[index]` сервера
  (`server_config` — из строки журнала сервера «параметры поиска и индексации»); время
  индексации считается от начала загрузки корпуса.
- **Перепрогоны** на исправленных запросах (`eval/results/2026-10-20-*`): fts 0,686; hybrid int8
  0,746, с реранком 0,831; hybrid fp16 0,749, с реранком 0,834; гейт — интервалы выше.
- **Оценка завышена (in-sample).** Веса и пороги подобраны на этом же наборе, контрольной части
  нет: прирост `tuned` (+0,03 nDCG@10) — верхняя оценка; выбор между близкими конфигурациями
  тоже может быть подогнан под набор. Нужна отложенная выборка запросов (следующая ревизия
  набора).

### Task 15 — производительность §17 и бюджеты

> Числа этого раздела и fix round 1 сняты с кода `0bb32f7` и `4018ae3` — справочно.
> Финальные (код `d1d2521`) — в fix round 2 ниже и в `docs/journal.md`.

**Инструмент.** `cargo xtask bench --profile cpu|gpu` поверх обвязки `eval` (`Session`, `RunSpec`,
`build_server`). Корпус — 160 заметок eval и 9 840 компактных копий (окно абзацев ≥ 1600
символов, ~200 токенов на чанк, 23,6 тыс. чанков, 34,5 тыс. точек Qdrant). Копии дублируют
тексты исходников — частоты редких слов в FTS завышены, частых — примерно как в реальном
корпусе. Замеряемый проход — после перезапуска с прогревом двумя посторонними запросами: LRU-кэш
эмбеддингов запросов (1024) не подменяет инференс (повторный проход GPU — p95 35 против 38 мс,
CPU — 35 против 65 мс). `index_secs` — от начала загрузки (как в eval, fix round 1 задачи 14).
Итоги — `eval/results/2026-10-20-bench-{cpu,gpu}.*`, таблица — `docs/journal.md`.

**Решения:**
- **Qdrant упал → поиск сразу FTS-only.** Замер до исправления (Windows): первый поиск после
  убийства — 1,7–4,1 с (отказ соединения ~2 с × повтор клиента; ответ иногда даже не
  деградированный — клиент дожидался перезапуска). Супервизор меняет состояние только после
  разбора журнала (до 2 с). Сделано: `Supervisor::process_alive()` (pid жив по ОС) в
  `vector_available()` при `Ready`, `CONNECT_TIMEOUT` 300 мс. Цель — «не дольше бюджета
  поиска без реранка + FTS-only» (140 / 70 мс): эмбеддинг считается до обращения к Qdrant,
  отказ должен быть мгновенным, иначе каждая секунда простоя Qdrant — секунды ожидания
  агентов. Итог: max 50 / 47 мс за весь простой (1,8–1,9 с до перезапуска). Одиночный запрос,
  застигнутый смертью процесса в полёте, ждёт не больше двух попыток по 300 мс.
- **jina — `dynamic_quant = true`.** В манифесте не было признака, модель шла одним батчем:
  баллы зависели от соседей (масштаб активаций — на весь тензор, паддинг тоже). Теперь пары по
  одной, параллельно в `ml.rerank_sessions` сессиях с общим `PrepackedWeights`. Перебор на 12
  ядрах (20 × 256): батч — 1,70 с / +1159 МиБ; по одной: 1 сессия — 1,91 с / +609 МиБ, 2 —
  1,42 / +905, 3 — 1,25 / +1229, 4 — 1,15 / +1552, 6 — 1,18 / +2200 МиБ; отключение
  `memory_pattern` и prepacking на память не влияет — каждая сессия держит свои веса int8.
  Авто — 2 сессии (до 2, не меньше двух физических ядер на сессию): единственный вариант,
  укладывающийся во время §17, и всё равно меньше памяти, чем батч. eval hybrid+rerank int8:
  nDCG@10 0,829 (было 0,831), p50 1,13 с, p95 1,26 с (было 1,80 / 1,96).
- **Qdrant параллельно с моделью** (`ml::model_installed` → `IndexRuntime::start_supervisor`
  до `ml::load`), **кэш `model_id`** в `model.onnx.sha8` (размер + mtime). Старт до
  готовности Qdrant: было = загрузка модели + Qdrant (11 с на GPU), стало 0,8–2,0 с, max 4,8 с
  (первый старт после жёсткой остановки во время массовой записи — повтор WAL Qdrant; на
  Windows Qdrant всегда останавливается `TerminateProcess`).
- **Писатель SQLite — `busy_timeout` 30 с.** Фоновый `RESTART` с переносом остатка WAL
  (WAL > 32 МиБ, M1) на HDD под индексацией держит блокировку записи дольше 5 с — `POST /nodes`
  получал 500. Хвост записи 10–11 с остаётся (p95 14–26 мс); принудительный RESTART не снят:
  без него WAL дорастает до 64 МиБ и RESTART делает писатель (выброс 0,9 с в M1).
- **FTS-only на 10 тыс. заметок: p95 76 → 30 мс.** `pending_count` — частичный индекс
  `nodes_pending` (миграция user 0006, 6 → 0,1 мс). `leaf_term_hits` — листы узлов окна и проход
  одних `rowid` FTS на слово (проверка `MATCH … AND rowid = c.seq` по листу — 0,05–0,1 мс на
  лист и слово — оказалась хуже на окнах с сотнями листов: fuse p95 55 мс).
- **Цель GPU для индексации** — по замеру на RTX 3090 с данными на HDD: 30,3 чанка/с на
  корпусе eval (~200 токенов), 17,6 — на 10 тыс. заметок (инференс 17 % времени воркера,
  Qdrant 27 %, остальное — SQLite и ожидание HDD). Предложение (уточнено в fix round 1) — в токенах: ≥ 3000
  токенов/с ≈ 7,5 чанка по 400 (ТЗ v1.5, ожидает решения владельца; окончательно — задача 17).

**Не выполнено** — финальный список в fix round 2 и в `docs/journal.md`. Общие initializers
(`AddInitializer`) проверены опытом на Python ORT 1.23: на bge-m3 int8 экономии нет (каждая

### Task 16 — прототип Qdrant Edge и ADR

- **`EdgeIndex`** (`crates/zam-index/src/edge.rs`, feature `edge`): `qdrant-edge =0.8.0` собирается на Windows и Rust 1.99.1 без правок. Решения:
  - метаданные коллекции — в `zam_meta.json` рядом с шардом (у Edge их нет); шард без файла — «не наш»;
  - все вызовы — `spawn_blocking`, паника Edge → `IndexError::Other`; `OperationError::ServiceError` → `Unavailable`, `InconsistentStorage`/`FileNotFound` → `Corrupt`;
  - `optimize()` — фоновый поток с дебаунсом 2 с после последней записи; `optimize_now()` — для замеров и тестов; `drop_all` ждёт освобождения шарда (идущую оптимизацию не отменить);
  - `EdgeOptions`: 2 потока поиска и 2 потока HNSW — как `max_search_threads` и `optimizer_cpu_budget` managed.
- **Тесты.** Общие случаи контракта `VectorIndex` вынесены в `tests/common/cases.rs` (макрос `vector_index_cases!`), `tests/qdrant.rs` и `tests/edge.rs` их подключают. Каталог теста — первые 8 символов имени: длинные имена выводили путь сегментов Qdrant за MAX_PATH на Windows.
- **Bench.** `cargo xtask bench --edge` (`xtask/src/bench/edge.rs`) и пример `zam-index/examples/index_bench.rs`: отдельная чистая сборка на вариант, отдельный процесс на каждый замер.
- **Итог** (`eval/results/2026-10-20-bench-edge.*`): p95 13,7 против 21,9 мс (1,60×), RSS 9,2 против 4,3 ГиБ, пересборка 101 против 27 мин. Критерий исследования 05 не выполнен → **не переходить** (`docs/adr/0001-qdrant-edge.md`). В основной CI feature не добавлена (только недельный `edge.yml`, см. fix round 1).
- **Fix round 1 (ревью):** по исходнику qdrant-edge 0.8.0 подтверждены два дефекта долговечности:
  - WAL не усекается — `ack`/`prefix_truncate` нигде не вызываются. Отсюда лишние ≈ 5,7 ГиБ на диске, а при открытии весь WAL мапится и прочитывается для CRC: +5,3 ГиБ RSS и 5,9 с;

  - недельный `.github/workflows/edge.yml` (clippy `--features edge`, Linux).
