### Задача 2 — права `certainty`, обязательная ревизия записей, без человеческого токена (2026-10-26)

- **Матрица §7.5 (решение владельца 2026-10-26)** — `zam-store/src/certainty.rs`: проверяется только агент (любой токен): создание `theorem` — с доказательством, любой переход статуса (в том числе `→ axiom`, `axiom →`, снятие) — с `reason`, `→ theorem` — ещё и с доказательством; человек (сессия WebUI) и `system` — без проверок; `theorem` в итоговом состоянии правки агента — с полным доказательством (`check_final_state`, теперь только агент). `CertaintyError` — только `EvidenceRequired` и `ReasonRequired` (оба 422); коды `axiom-requires-human` и `invalid-transition` и ответ 403 удалены. `default_certainty`: insight агента — `hypothesis`, человека и `system` — без статуса.
- **Ревизия записей (§11.3)**: `PATCH`/`DELETE /entries/{id}` без `If-Match` — 428 `/problems/precondition-required` («передайте If-Match: <rev> текущей ревизии»); расхождение — 409 `/problems/conflict` с полем `rev` (новая `StoreError::StaleRevision {expected, current}`); `supersede`, `retract`, `restore` — `If-Match` необязателен. Проверка — в транзакции писателя хранилища, раньше прав (`check_rev` в `entries/write.rs`), поэтому из двух параллельных PATCH с одной ревизией проходит ровно один. `ApiError::PreconditionRequired(String)`; 428 у `PUT /nodes` получил тот же `type` и текст.
- **Человеческий токен упразднён (§11.4)**: `TokenInfo.human`, `AuthToken.human` и параметр `issue_token(…, human)` удалены, колонка `tokens.human` не читается (миграции нет); `POST /admin/users/{id}/tokens` с `human: true` — 400, `human: false` принимается для совместимости; поле `human` убрано из ответов токенов, аудита `token_issue`, `/auth/me` и `GET /spaces`. При старте — одна строка WARN «токены <префиксы> были человеческими, теперь агентские» (`SystemStore::legacy_human_token_prefixes`, `bootstrap::warn_legacy_human_tokens`). CLI: `--human`, `human_gate`, `connect_human`, `human_target` и ключ `human_token` удалены; `zam insight certify|append|revisit` берут `rev` из `GET /entries/{id}` и шлют `If-Match`, на 409 с `rev` — «запись изменилась (rev N → M): перечитайте», код 4 (`EXIT_CONFLICT`, R7). WebUI: флажок «для человека» убран; `InsightsView` шлёт `If-Match` открытой записи (на 409 перечитывает карточку и объясняет), причина смены статуса и доказательство `theorem` необязательны (R8), новая запись в форме замены — «без статуса» по умолчанию. `cargo xtask eval` создаёт `axiom` набора токеном прогона.
- **Рёбра от `axiom` (§8.5)**: агенту разрешены создание и удаление (R10 снят); проверки `ModifyOther` в транзакциях рёбер, триггеров, вложений, переноса/удаления узлов оставлены как точки матрицы (сейчас всегда разрешают).

### Задача 3 — Vault при блокировке, триггеры как поиск, `PATCH /solutions` (2026-10-27)

- **Vault при блокировке (§7.6).** `api/vault.rs`: `ready()` (503) вызывается только там, где нужен мастер-ключ — создание, правка, удаление, `reveal=1` у записи и у ревизий; список, `GET /vault/{id}` и `GET /vault/{id}/revisions` без `reveal` читают открытые поля из базы пользователя и добавляют в корень ответа `locked` (`true` + `reason` при блокировке, иначе `false`). Проверки доступа к области и записи не менялись (404 для `rules`/`human`, 403 `solution-access`). CLI: `zam vault list` пишет строку «Vault заблокирован: <причина>» в stderr (stdout остаётся списком для скриптов), `--json` выдаёт ответ целиком вместе с `locked`. WebUI: `listVault` отдаёт `locked`/`reason`, `VaultView` показывает список с баннером и неактивной «Показать»; 503 при раскрытии по-прежнему включает баннер.
- **`GET /triggers` как поиск (§10.3).** `api/triggers.rs` больше не использует `space_scope` (403/404 на весь ответ): `pending|rejected|revoked` → `solution access <state>`; нет решения в реестре или нет запроса доступа → `solution unknown` (существование чужого решения не раскрывается); пропавшее пространство владельца → `solution unknown`, сбой базы владельца → `solution unavailable` (WARN в журнал, `skip_foreign`). Knowledge пользователя отдаётся всегда. Параметр `solution` не GUID — 400, заголовок — игнорируется. Ответ несёт `warnings` всегда (пустой массив без предупреждений) **[решение исполнителя]**: клиенту не нужна проверка наличия поля; ETag — blake3 канонического JSON `{triggers, warnings}` (смена только предупреждения меняет ETag; `If-None-Match` со старым значением даёт 200). Тесты M3 `insights.rs` (отзыв — 403, неизвестное решение — 404) переписаны на новое поведение.
- **`PATCH /solutions/{guid} {name}`.** Права — `managed(.., write=true)` (как у `approve|reject|revoke`): владелец с `rw`-токеном или администратор, участник и запросивший доступ — 403, посторонний и неизвестный GUID — 404, `ro`-токен владельца — 403. Имя — 1..=200 символов без управляющих (при регистрации прежний предел 128 не менялся **[решение исполнителя]**: ТЗ задаёт 200 только для переименования). Реестр (`SystemStore::rename_solution`, аудит `solution.rename` `{from, to}` в той же транзакции) обновляется первым, затем имя пространства в базе владельца (`rename_solution_space`); прерванное переименование довершается повтором запроса. Ответ — решение в форме `GET /solutions/{guid}`. CLI `zam solution rename <имя> [--solution GUID]` (новый `Client::patch_json`).
- **Проверки.** Тесты: `vault_list_when_locked_returns_metadata`, `vault_reveal_and_write_when_locked_503`, `triggers_revoked_solution_returns_knowledge_with_warning`, `triggers_unknown_solution_warning`, `triggers_etag_changes_with_warnings` (новый `tests/triggers.rs`), `patch_solution_rename_owner_ok_participant_403`, CLI `solution_rename_owner_only`, юнит `locked_line_from_listing`, E2E WebUI «Vault: заблокирован — список виден…» и «503 при раскрытии». ### Задача 6 — чтение пачкой `POST /read` (2026-10-27)

- **Сервер.** `api/read.rs`: `POST /read` в `service_routes` (R12 — не запись в память). Разбор `id` (`n:`, `i:|c:|r:|e:`, голый — узел, затем запись; `<пространство>:/<путь>` через `space_scope` и `get_node_by_path`), доступ — теми же `node_scope`/`entry_scope`/`space_scope` (Human по токену и чужая база вне решения — `not_found`, решение без доступа — `solution_access`). Ошибка элемента — `Failure::Item` (в ответе 200), сбой хранилища — `Failure::Fatal` (500). Упаковка `pack`: места под заголовки и `(budget)` следующих элементов резервируются заранее (суффиксные суммы), первый элемент обрезается, но отдаётся. Отметка `mark_seen` — одна транзакция с касанием сессии; WARN при сбое. В `nodes/read.rs` открыты `Tier`, `parse_tier`, `l1`, `section_slice` (`pub(crate)`), в `search` — `md_inline`. Конфигурация: секция `[read]` (`max_items`, `budget_tokens`), `deploy/config.example.toml`. `ApiError::LocatorUnsupported` — 422 `/problems/locator-unsupported`.
- **CLI.** `zam read` без новых флагов побайтный, как в M1 (тесты CRLF и BOM); `--batch`, `--max-tokens`, `--budget`, `--if-rev` включают одну `POST /read` (md сервера как есть или `--json`); ошибки элементов дают код выхода первой (`not_found` — 5, `forbidden`/`solution_access` — 3, иначе 6); `--rev` с пачкой — 6.
- **Решения исполнителя.** (1) `format` по умолчанию `json`, как у поиска (§12 не уточняет; MCP задачи 9 просит `md`). ## Решения

Решения контроллера и исполнителя, принятые без владельца; каждое можно пересмотреть.

- **R1 (контроллер, задача 1).** Таблица `sessions` получает `memory_writes INTEGER NOT NULL DEFAULT 0`: сервер увеличивает счётчик при любой записи в память (узел, запись журнала, связь, Vault, `cache_put`) с `X-Zam-Session`; `GET /sessions/{id}` отдаёт `memory_writes`; хук `checkpoint` напоминает записать итоги, только если в сессии были Write/Edit и `memory_writes == 0`. Уточняет Interfaces задач 5 и 10 (в плане — `GET /sessions` списком и признак «не было записи в память» без источника). ТЗ §6.3, §10.3, §12.
- **R2 (контроллер, задача 1).** `zam hook session-start` читает версию блока из маркера `<!-- zeroaimemory:begin vN -->` ближайшего CLAUDE.md/AGENTS.md и передаёт `agent_block_version` в `/recall`. ТЗ §10.3, §15.5.
- **R4 (решение контроллера, ревью задачи 1) — таймаут остановки службы.** `TimeoutStopSec = max(90, ceil(shutdown_flush_wait_ms/1000) + 80)` (запас 80 с: пачка инференса до 60 с + перенарезка 10 с + SIGTERM Qdrant 10 с; при умолчаниях 94 с); SCM — `wait_hint` 10 с с `checkpoint` каждые 2 с, пока идёт остановка; таймаут `Preshutdown` — та же величина; проверка при старте под службой сравнивает таймаут службы с ней. Заменяет `+30 с` (юнит), `+15 с` (`wait_hint`), `+30 с` (`Preshutdown`) и `+5 с` (проверка) Interfaces задачи 14. ТЗ §4.3, §13.3, §16.2.
- **R5 (решение контроллера, ревью задачи 1) — переключатели типов подсказок.** Клиент: `[hooks] session_start|prompt|pre_tool|post_tool|checkpoint = true|false` в `~/.zeroaimemory/config.toml` и `.zeroaimemory/config.toml` проекта (проект сильнее). WebUI: настройка пользователя на сервере `hooks.<тип>`, отдаётся в ответе `/recall(session_start)` полем `hooks: {…}` и кэшируется рядом с триггерами. Тип выключен, если выключен где-либо. Делают задачи 10 и 13. ТЗ §10.3.
- **R6 (решение контроллера, ревью задачи 1).** `GET /sessions/{id}` (с `memory_writes`) — в задаче 5; в ТЗ §12 уже записан.
- **Мелкие правки ревью (решение контроллера).** §13.2: `zam log insight --certainty axiom|theorem|hypothesis` (агенту `axiom` — по указанию пользователя); §19: в статусе M3 тест «`axiom` отзывает только человек» помечен «тест M3; в M4 переписан»; §17: контрольный замер на новых умолчаниях — ABBA против прежних 5 с / 10 000.
- **Блок инструкции v2 ужат до предела 500 токенов (исполнитель, задача 1).** Счётчик bge-m3 (`target/models/bge-m3-int8/tokenizer.json`): блок v1 из ТЗ v1.11 — 584 токена (предел §14.2 уже превышался); черновик v2 с правилами владельца дословно поверх v1 — 698. Текст в §14.2 сокращён без потери правил: 454 токена с заглушками, около 495 с реальным токеном `zam_` из 44 символов и адресом по IP. Длинный `server.public_url` может вывести блок за 500 — тест задачи 11 должен считать токены после подстановки URL и токена; при превышении — сокращать шаблон, а не поднимать предел.
- **§5.2: кэш триггеров — JSON, а не `rkyv`/mmap (план M4, отражено в ТЗ).** ТЗ v1.11 обещало `regex-automata` с предкомпилированными DFA и `rkyv` с чтением через mmap; Interfaces задачи 10 задают `triggers.json` и `globset` + `regex`. В ТЗ записано: `rkyv`/DFA — только если замер бюджета `pre-tool` (≤ 5 мс сопоставление, ≤ 50 мс процесс) покажет нужду.
- **§19: из M6 в M4 перенесены `promote` и проверка устаревания блока инструкции** — их делают задачи 7 и 11; в строке M6 вместо них — наборы eval по ответам владельца п. 16–17.
- **§15.5: варианты агента — Claude Code / AGENTS.md / Codex** (вместо «универсальный»), по параметру `agent=claude|agents|codex` задачи 11.
- **Удаление записи кэша — мягкое** (`deleted_at`, задача 7): записано в §9.4.
- **Точки проверки `certainty` оставлены (исполнитель, задача 2).** `check_certainty(author, current, change, …)` сохранил сигнатуру M3 (параметр `current` матрица M4 не использует) и вызовы `ModifyOther` в транзакциях правки, удаления, переноса, вложения, триггеров и рёбер: правило по-прежнему проверяется в транзакции каждой операции, и будущее ограничение не потребует обходить все пути записи заново. Цена — одно чтение `certainty` на узел в переносе/удалении поддерева.
- **Понижение `axiom` при дозаполнении M3 не тронуто (исполнитель, задача 2).** `backfill_certainty` (миграция 0009) по-прежнему понижает `axiom` заметок, текущая ревизия которых записана не человеком: это перенос данных до M3, когда статус ничего не значил, а не матрица прав (ТЗ §7.5 так и описывает дозаполнение). Правка агентом такой заметки с `axiom` во frontmatter — переход `hypothesis → axiom` с причиной.
- **`supersedes_id` при создании — без сверки ревизии (исполнитель, задача 2).** `If-Match` у `POST /spaces/{space}/entries` относился бы к новой записи; ревизия замещаемой сверяется только у `POST /entries/{id}/supersede`. Повтор замещения по `Idempotency-Key` ревизию не сверяет (после первого ответа она уже выросла).
- **409 ревизии записи — с полем `rev` (исполнитель, задача 2).** У заметок 409 несёт `current_rev` и дифф; у записей журнала — `rev` текущей (имя поля записи), `detail` «ревизия записи N, а не M». CLI на 409 с `rev` печатает «запись изменилась (rev N → M): перечитайте», код выхода 4 — как у заметок (R7).
- **`human: false` при выпуске токена — принимается (исполнитель, задача 2)**: 400 только на `human: true`, старые клиенты с явным `false` не ломаются.
- **R7 (решение контроллера, ревью задачи 2) — код выхода конфликта ревизии записи — 4** (`EXIT_CONFLICT`, как у заметок), а не 1 (`EXIT_CONFIG`) из ТЗ v1.12; ТЗ §11.3 исправлено.
- **R8 (решение контроллера, ревью задачи 2) — WebUI: доказательство для `theorem` от человека необязательно**, как и на сервере: поля формы остаются с подписью «(необязательно)», заполненные — уходят в `data.evidence`, пустые — не шлются и не блокируют сохранение.
- **`rechunk` по базам — список `dbs: [{user_id, rechunk}]` (исполнитель, задача 4).** ТЗ §8.2 задаёт `rechunk: {…} | null` «по каждой базе» без формы контейнера; администратор без `X-Zam-User` видит все базы, поэтому значение лежит в элементе списка видимых баз (база, не открывшаяся, — по-прежнему в `unavailable_dbs`). `rechunk` не `null`, пока идёт фоновая перенарезка, начатая при открытии базы этим процессом. ТЗ §8.2, §12 уточнены.
- **Причина `unknown` с ключами из отпечатка M3 (исполнитель, задача 4).** База M3 не хранит JSON параметров, но её отпечаток (`v2;…;lambda=…;cohesion=…;h4=…;l0=…;tok=…`) разбирается: при обновлении на `0.0.5-m4` WARN и баннер называют `chunk_boundary_lambda`, а не «параметры нарезки». Отпечаток до задачи 17 M3 не разбирается — список пуст, в WARN — «изменились параметры нарезки».
- **Деление при переполнении после реранка — по переставленным (исполнитель, задача 4).** Хвост за `rerank_top` (без балла реранкера) сохраняет балл слияния — другая шкала, его порядок после переставленных не меняется. ТЗ §9.2 п. 5 уточнён.
- **Баннер перенарезки — на странице «Индекс», а не в `IndexBadge.svelte` (исполнитель, задача 4).** `IndexBadge` — значок состояния одной заметки в дереве и карточке; «индикатор индекса» WebUI — страница `#/admin/index` (опрос `GET /index/status` раз в 5 с). Баннер — по базе, с именем пользователя. Для пользователей без доступа к странице «Индекс» (вход пользователей — задача 12) баннер стоит вывести там же, где им покажут состояние индекса.
- **Заглушка реранкера — `RerankSlot::install` под фичей `test-hooks` (исполнитель, задача 4; fix round 1 по ревью).** Интеграционные тесты zam-server не видят `cfg(test)`, поэтому у zam-server фича `test-hooks`, её включает dev-зависимость пакета на себя (`zam-server = { path = ".", features = ["test-hooks"] }` — cargo это принимает): `cargo test --workspace` и CI собирают тесты с фичей без отдельного шага, обычная и release-сборка — без неё (`cargo tree -e features,normal` — ни одной `test-hooks`). Трейт `PassageScorer` — в рабочем коде. Альтернатива — фича `test-hooks` у zam-ml с фиктивным `Reranker` — тянула бы ONNX-типы в заглушку.

- **R11 (решение контроллера, ревью задачи 5) — гранулярность `session_seen`.** В ключ добавлена колонка `part TEXT NOT NULL DEFAULT ''` (миграция 0013 ещё не выпущена): `chunk_id` чанка, выданного целиком (`mode=chunks`), или `''` — полный текст цели (`/read` задачи 6 при полном L2 без `section` и без обрезки). Элемент поиска получает `seen: true`/`(seen)`, только если в той же ревизии отмечены его чанки (`chunk_ids`) или цель целиком. Заменяет пункт ниже о гранулярности «по цели». ТЗ §6.3, §9.3.
- **R12 (решение контроллера, ревью задачи 5) — счётчик `memory_writes` и MCP.** MCP задачи 9 вызывает REST-маршруты через внутренний `Router` (`oneshot`), поэтому слой `memory_routes` срабатывает и для MCP без отдельного кода. Обязательство: любой новый путь записи в память — только через маршруты `memory_routes` (`cache_put`/`promote` задачи 7 — туда же); прямой вызов `zam_store` в обход маршрутов счётчик не увидит. Записано в doc-комментариях `api/sessions.rs` и `api/mod.rs`.
- **Известное: `l0` у `seen`-элемента в `mode=notes` (исполнитель, задача 5, по ревью — оставить).** В `mode=notes` у элемента с `seen: true` в JSON остаётся `l0` (сводка, а не выданный текст); `snippet`/`text` снимаются.
- **Каждая оценка — отдельная строка `usage` (исполнитель, задача 5, по ревью).** Повторные `feedback` одного пользователя по одной записи не схлопываются: счётчики `useful`/`useless` считают все оценки.
- **`skip_seen` по умолчанию `true`; у `seen`-элемента нет фрагмента и текста (исполнитель, задача 5).** Пример §9.1 задаёт `"skip_seen": true`, протокол экономии токенов (§9.3) опирается на «не выдавать повторно». Пометка ставится до упаковки: снятый текст освобождает `budget_tokens` для остальных элементов; `tokens` элемента — стоимость полного чтения. `skip_seen: false` отдаёт текст и `seen: false`.
- **В `session_seen` — только текст, отданный целиком (исполнитель, задача 5).** Чанк, усечённый бюджетом, агент прочёл не полностью; отметка скрыла бы его в следующих поисках. Гранулярность — по `chunk_id` или цели целиком (R11 выше).
- **`POST /sessions` для существующей сессии — 201 и дописывание полей (исполнитель, задача 5).** Хук `session-start` при возобновлении сессии вызывает его повторно; ошибка или отдельный код ответа ему не нужны. `PATCH {ended: false}` снимает отметку конца (возобновление). Токен `ro` сессии ведёт — это учёт, а не запись в память.
- **`memory_writes` считает и удаление, и вложения (исполнитель, задача 5).** «Любая запись в память» (R1) — любое успешное изменение маршрутов памяти: узлы (создание, правка, перенос, удаление, восстановление, откат), вложения, записи журналов (включая замещение и отзыв, кроме `feedback`), связи, Vault. Повтор по `Idempotency-Key` (200) считается ещё раз — для хука важно «было ли», а не сколько.
