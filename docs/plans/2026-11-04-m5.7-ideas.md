# M5.7. Идеи — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Редакция 2 (2026-11-04) — по рецензии контроллера к `8584457` (CHANGES REQUESTED: C1, I1–I9,
замечания 1–13; разбор — журнал этапа). Пункты «ждёт ответа владельца» реализуются по варианту по
умолчанию из спецификации, пока нет ответа.

**Goal.** Журнал «Идеи» (`idea`, ссылка `w:`) в решении и в Knowledge.
- Человек записывает замыслы в WebUI, агент — по диктовке или свои (с пометкой «от агента»).
- Агент предлагает начать идею двумя путями: раздел дайджеста `### Идеи` (до 3, на первом
  `session_start` сессии) и подсказка по смыслу в `/recall prompt` (отдельный лёгкий поиск). Каждая
  идея — один раз за сессию.
- Предложение — вопрос с вариантами «начать / отложить / отказаться». Ответ человека переводит идею
  по статусам; «начать» одной транзакцией создаёт `task` с ребром `derived_from`.

**Architecture.**
- **Новый вид записи, а не новая подсистема.** `EntryKind::Idea` хранится в `entries`.
  - Миграция `0024_ideas.sql` пересобирает `entries` по образцу 0015/0022. До пересборки она снимает,
    а после пересоздаёт три триггера 0022, которые ссылаются на `entries`.
  - Модуль `zam_store::ideas` повторяет устройство `tasks.rs`/`questions.rs`: `IdeaData`, проверка
    переходов, транзакции `propose_idea`, `decide_idea`, `adopt_idea`.
  - Шаги транзакции разделены. `questions::answer_tx` отвечает вопрос (ревизия, решение `decision`,
    ребро). `ideas::apply_decision_tx(…, answered: Option<Id>)` переводит идею и создаёт задачу.
    `answer_question` вызывает сначала `answer_tx`, затем `apply_decision_tx(Some(decision))`;
    `decide_idea` вызывает `apply_decision_tx(None)`, и тот сам отвечает открытый вопрос. На любом
    пути — одна транзакция писателя и не больше одного решения `decision`.
- **Связь с задачей** — ребро `derived_from` задача → идея; ставит его только сервер. В той же
  транзакции работают два хука:
  - правка статуса задачи в `update_entry` вызывает `ideas::on_task_status_tx`;
  - удаление записи в `delete_entry` вызывает `ideas::on_entry_deleted_tx` (§5.6 спецификации).
- **Проактивность — внутри существующего `/recall`.**
  - Кандидатов отбирает `zam_store::ideas::proactive_ideas` с предикатом `idea_candidate`: только
    `origin: human`, статус `new` или `deferred` с наступившим `horizon`, нет в `seen`.
  - Раздел дайджеста добавляется в `arrange()` после строки открытых вопросов.
  - Подсказка — отдельный поиск `kinds: [idea]` после основного поиска `prompt`; основной поиск не
    меняется.
  - Выключатели — `[ideas] proactive` сервера и `ideas.proactive` пользователя (`user_settings`).
- **Пути клиента** — по шаблону вопросов:
  - REST `POST /entries/{id}/{propose,decide,adopt}`;
  - MCP `memory_update_entry action=propose|decide` (инструментов по-прежнему 11);
  - CLI `zam idea …`;
  - страница WebUI «Идеи».

  Блок инструкции v6 — одна строка; детали — в протоколе `zam guide`.

**Tech Stack.** Новых зависимостей нет. Rust: rusqlite, axum, serde, jiff, thiserror, proptest — всё
уже в workspace. WebUI: Svelte 5, без новых пакетов.

## Review Focus

1. **Атомарность «начать» и ровно одно решение.**
   - **Пути:** `decide accept` (WebUI, CLI, MCP); ответ `accept` на вопрос-предложение; `decide` по
     идее с открытым вопросом.
   - **Ожидание при сбое.** Вставку задачи или ребра роняет тестовый триггер `RAISE(ABORT)`. Не
     меняется ничего: статус и ревизия идеи, вопрос, решение `decision`, рёбра.
   - **Ожидание при успехе.** Решений `decision` ровно одно на ответ и на `decide` при открытом
     вопросе, ноль — на `decide` без вопроса. Повторный `accept` — 409 `already-decided` с тем же
     `task_id`; повторный `defer` — 200 с новым `horizon`.
   - **Тесты** (задача 1): `accept_rolls_back_when_task_insert_fails`,
     `answer_accept_on_proposal_is_one_tx`, `exactly_one_decision_per_path`,
     `transitions_table`.
2. **Пересборка `entries` не теряет защиту отчёта — ни на `entries`, ни на дочерних таблицах.**
   Триггеры `entry_revisions_report_once` и `entry_attachments_report_only` ссылаются на `entries`
   и ломают `RENAME`, а `DROP TABLE entries` уносит `entries_report_immutable`.
   - **Ожидание.** Миграция проходит. Множество объектов `sqlite_master` до и после совпадает (кроме
     ожидаемых правок `entries`). Прямой SQL срабатывает на все пять триггеров отчёта:
     - `UPDATE` отчёта;
     - `INSERT entry_revisions` с `rev = 2`;
     - поздний `INSERT entry_attachments`;
     - `UPDATE` и `DELETE` `entry_attachments`.

     `foreign_key_check` пуст, строки и `idempotency_key` сохранены.
   - **Тест** (задача 1): `migrate_0024_keeps_report_triggers_and_rows`.
3. **Один показ за сессию.**
   - **Сценарий:** `session_start` → `prompt` → повторный `session_start` (`source=compact`) одной
     сессии.
   - **Ожидание.** Идея показана ровно один раз. После compact раздела нет совсем (ждёт ответа
     владельца). Новая сессия показывает снова. При `record: false` и истёкшем сроке учёта показ не
     отмечается — это допустимо и задокументировано.
   - **Тесты** (задача 3): `digest_ideas_only_on_first_session_start`,
     `prompt_skips_idea_seen_in_digest`.
4. **Кто решает и кто правит.** Проверяемые случаи:
   - токен с `by: agent` на `accept`, `defer`, `reopen` и на `decline` идеи человека;
   - ответ `by: agent` на вопрос-предложение — проверка до чтения идеи;
   - токен на `adopt`, на правку тела идеи человека и на её удаление;
   - клиентское ребро `derived_from` на идею.

   **Ожидание:** 403/422 с нужной проблемой, без побочных записей (ни ревизии, ни аудита изменения).
   `decline` своей идеи с `by: agent` — 200.

   **Тесты** (задача 2): `token_by_agent_cannot_decide_human_idea`,
   `token_cannot_adopt_rewrite_or_delete_human_idea`, `agent_declines_own_idea`,
   `client_derived_from_to_idea_rejected`.
5. **Идея не вытесняет память и не меняет поиск.**
   - **Не появляются** ни в дайджесте, ни в подсказке: идеи «от агента», `declined`, `proposed`,
     `deferred` до `horizon`, общие Knowledge без условия §6.2.
   - **Выключенный `ideas.proactive`:** дайджест побайтно равен дайджесту без идей.
   - **Подсказки insight** с идеями и без них совпадают по набору и баллам: отдельный поиск.
   - **Кэш выжимок:** `scope_key` WebUI не изменился.
   - **Тесты:** задача 3 — `proactive_off_digest_byte_equal`,
     `prompt_insight_hints_unchanged_with_ideas`, `never_proposed_kinds_matrix`; задача 2 —
     `scope_key_ignores_idea_kind_and_statuses`.

## Решения составителя плана

Каждое решение записывается в журнал этапа и переносится в ТЗ (задача 6). В спецификации эти
решения помечены «[решение составителя]». Пункты, которые ждут ответа владельца, реализуются по
варианту по умолчанию.

1. **Модель.** Вид `idea` — запись `entries`, буква ссылки `w:` (`d:` занята документом вложения).
2. **Миграция** `0024_ideas.sql`, `rebuild: true`. Три триггера 0022 снимаются до пересборки и
   пересоздаются после; проверка — `schema_objects` и прямой SQL (по рецензии, C1).
3. **Происхождение.** `data.origin` у токена обязателен — по образцу обязательного `by` (§7.9,
   I-2).
4. **Статус** меняется только операциями `propose|decide|adopt`; `PATCH status` → 422.
5. **Вопрос-предложение.**
   - Варианты фиксирует сервер (`accept|defer|decline`), проверки дублей нет.
   - Повторный `propose` возвращает тот же открытый вопрос.
   - `propose {space?}` сохраняет `task_space` в вопросе (по рецензии, I8).
6. **Шаги транзакции** разделены: `answer_tx` и `apply_decision_tx(answered)`. На каждом пути — не
   больше одного решения `decision` (по рецензии, I5).
7. **Идея «от агента».** Ни `propose`, ни `accept` до «принять как свою»; свою идею агент
   отклоняет с `by: agent`.
8. **Защита идеи человека от токена.** Содержимое не правится и в корзину не удаляется (403
   `idea-human-owned`); `append` можно. Клиентское ребро `derived_from` на идею → 422.
9. **Задача идеи Knowledge.** `accept` может создать её в решении той же базы; другая база → 422.
   WebUI предупреждает, если решение общее.
10. **Тупики** (ждёт ответа владельца). Задача `dropped` или удалена → идея остаётся `accepted`;
    разрешены `reopen` (с `prev_task_ids`) и `decline`. `done` → идея `done`, переоткрытие задачи →
    идея `accepted`.
11. **Корзина** (§5.6 спецификации):
    - удаление идеи → её вопрос `obsolete`;
    - удаление вопроса → идея `new`;
    - ответ по удалённой идее → 409.
12. **`already-decided`** — только у `accept`; повторный `defer` разрешён (по рецензии, I7).
13. **`deferred` после `horizon`** статус не меняет: фоновых заданий нет, идея сама становится
    кандидатом.
14. **Раздел `### Идеи`** — в `arrange()` после строки открытых вопросов, со строкой-указанием.
    - Показывается только на первом `session_start` сессии (ждёт ответа владельца).
    - Отметка — `session_seen` без эпохи (условие для M6).
    - Нет в `recovery` и `brief`.
15. **Подсказка идей** — отдельный лёгкий поиск (по рецензии, I1). Общая идея Knowledge проходит по
    косинусу векторного канала ≥ X или по явной связи (ждёт ответа владельца).
16. **Выключатель двухуровневый:** `[ideas] proactive` && пользовательский `ideas.proactive`.
17. **Блок.**
    - v6 в M5.7, M6 делает v7.
    - В блоке одна строка идей. Правило «без ответа не начинай» — в разделе дайджеста и в строке
      подсказки.
    - В протокол переносятся «(409 — перечитай)», «перед работой», «в чате», «заметке — `l0`» (по
      рецензии, I3).
    - Пояснения MCP — в `description` полей схемы.
18. **CLI.**
    - `propose` (с `--space`) — сверх списка владельца; `reopen` и «принять как свою» — только в
      WebUI.
    - `resolve_human_agent` обобщает `resolve_by`.
    - 403 → код 3.
19. **Лента и поиск.**
    - Фильтры ленты `origin` и `priority` — новые поля `EntryFilter` (по `json_extract`).
    - Статусы поиска по умолчанию для `idea` — `new, proposed, deferred, accepted`.
    - В умолчания `kinds` идея входит у сессии WebUI, у токена — нет.
    - `idea` и её статусы исключены из `scope_key` (по рецензии, I9).
