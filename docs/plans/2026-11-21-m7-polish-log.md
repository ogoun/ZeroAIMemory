### M7.1 · Задача 1 — ONNX Runtime из NuGet

Спецификация §4.1; проверка источника — `i:01M7ZB9N2QER1R4NA0XA2ZBK6E` (материалы исследования —
вне git). Ветка задачи `m7.1-t1`.

- **Манифесты.** `deploy/onnxruntime.toml` и `deploy/onnxruntime-gpu.toml` — пакеты NuGet 1.31.0
  `Microsoft.ML.OnnxRuntime` (CPU, один пакет на обе платформы: записи ссылаются на него, кэш по
  sha256 общий), `.Gpu.Windows`, `.Gpu.Linux`; адреса `api.nuget.org/v3-flatcontainer/…/….nupkg`,
  sha256 и `size` пакета, пути `runtimes/<rid>/native/…`, без `rename`. sha256 и размеры
  исполнитель пересчитал по скачанным nupkg — совпали с исследованием: CPU `7e35fdb4…` / 159 626 085,
  GPU Windows `6ef71832…` / 160 447 640, GPU Linux `7cd256a2…` / 244 928 869. В шапках —
  «файлы побайтово равны архивам GitHub v1.31.0, проверено 2026-11-21», без ссылок на `.tmp/`.
- **`zam-fetch`.** `format_of`: `.nupkg` (любой регистр) → zip. `download(url, dest, size)` —
  предел длины тела и точная проверка размера в одной функции: прежние `download_limited` и
  `check_size` после неё слиты, `fetch_file` и `install_archive` зовут её же (поведение то же).
- **`xtask fetch-deps` проверяет `size`.** При загрузке — `download_part(…, entry.size)`: длиннее —
  обрыв, короче — ошибка, `*.part` удаляется, в кэш ничего не попадает. У архива из `deps-cache` —
  размер до хэша и распаковки: «<имя>: файл кэша <путь> — N байт, а size в манифесте — M;
  исправьте size в манифесте или удалите файл кэша и повторите».
- **`xtask fetch-deps --prune-cache`.** `fetch::manifest_hashes(deploy/)` — sha256 всех
  `deploy/*.toml`; `fetch::prune_cache(target/deps-cache, keep)` удаляет файлы с другим именем
  (прежние версии и `*.part`), подкаталоги не трогает, нет каталога — `(0, 0)`. Печать —
  «<кэш>: удалено файлов — N (X МБ)».
- **Лицензия.** `deploy/licenses/ONNXRUNTIME-THIRD-PARTY-NOTICES.txt` — `ThirdPartyNotices.txt`
  пакета: во всех трёх nupkg один и тот же файл (344 457 байт, CRLF, sha256 `c53a7650…`), он же — в
  прежнем архиве GitHub `onnxruntime-win-x64-1.31.0.zip`. В репозитории — дословно с LF: 338 088
  байт, sha256 `143764b9…`. Каталог `deploy/licenses/` копируется в `LICENSES/` комплекта целиком,
  поэтому кода упаковки правка не требует.
- **CI.** `package.yml`: ключ кэша `deps-v2-<платформа>-<хэш манифестов>` и `restore-keys`
  `deps-v2-<платформа>-` (первый прогон — без кэша, §4.1 п. 6); шаг «чистка deps-cache»
  (`cargo xtask fetch-deps --prune-cache`) сразу после `fetch-deps` — кэш сохраняет post-шаг
  `actions/cache` в конце задачи. Прогон CI — координатор.
- **Документы.** `deploy/cuda.toml` — строка об источнике ORT GPU (NuGet, те же байты, набор и
  проверка импортов в силе); README — «Лицензия» и таблица команд xtask; CHANGELOG
  `[Unreleased]`.
- **[решение исполнителя, задача 1]** `DepManifest::validate` отвергает адрес с неизвестным
  форматом архива. Ловушка исследования («неизвестный формат архива» у `.nupkg») иначе
  обнаруживалась только после скачивания 160–245 МБ; сейчас — до загрузки, и
  `real_manifests_are_valid` ловит её без сети. Тест — `validation_rejects_bad_hash_and_url`
  (`.exe` — ошибка, `.nupkg` — ок).
- **[решение исполнителя, задача 1]** `manifest_hashes` собирает значения ключей `sha256` на любой
  глубине всех `deploy/*.toml` (зависимости, `cuda.toml`, `models.toml`; `config.example.toml`
  разбирается, но `sha256` в нём нет), а не разбирает три схемы по отдельности. Так выполняется
  интерфейс «ни в одном манифесте `deploy/*.toml`», и новый манифест не требует правки чистки.
  Нечитаемый TOML — ошибка: по неполному списку чистка удалила бы нужный архив.
- **[решение исполнителя, задача 1]** `--prune-cache` — отдельный режим без загрузки: clap
  запрещает сочетание с `--platform`, `--print-hashes`, `--flavor`. Чистка идёт после проверки
  манифестов — при неверном манифесте кэш не трогается.
- **[решение исполнителя, задача 1]** `--print-hashes` печатает и размер: под комментарием
  `# <имя>.toml [platform.<плат>]` строки `sha256 = "<hex>"` и `size = N` — TOML, вставляется как
  есть (круг правок 1). Без этого обновление версии давало бы sha256 без `size`, и
  `fetch-deps` падал бы на прежнем `size`. Размер при `--print-hashes` не проверяется: в
  манифесте он может быть от прежней версии.
- **[решение исполнителя, задача 1]** размер файла кэша проверяется до хэша, как в `fetch_file`
  («чужой файл не хэшируется»). Поэтому сообщение называет обе причины — неверный `size` в
  манифесте или испорченный файл кэша.
- **[решение исполнителя, задача 1]** `ci.yml` и `release.yml` не менялись: они кэшируют
  `target/deps` (распакованное, заменяется по штампу `<имя>.sha256`), а не `deps-cache`, и прежние
  версии там не копятся. Первый прогон после смены манифестов перекачает ORT с NuGet по
  несовпавшему штампу — это тоже проверка источника.
- **[решение исполнителя, задача 1]** smoke (`docs_layout`) лицензии ORT не проверяет, как и до
  задачи: состав `LICENSES/` закреплён тестом упаковки `licenses_include_ort_third_party`
  (настоящий `deploy/`). Если нужна проверка и на готовом архиве CI — одна строка в `smoke.rs`.
- **Для задачи 10 (ТЗ v1.27):** §16.3, пункты «Откуда берутся зависимости» (ORT из NuGet,
  проверка `size`, `--prune-cache`) и «Лицензии» (в `LICENSES/` комплекта сервера добавлен
  `ONNXRUNTIME-THIRD-PARTY-NOTICES.txt`; было 13 файлов в dev).

  - Причина цепочки фикстуры `scan_depth_capped.txt`: по виду с масками значение ключа склеивало
    короткий остаток с маской другого правила (`pwd=:‹secret›@…`; в тексте `:` упирался в `` ` ``).

    звенья ``"pwd=:`@`` сверх фикстуры ничего не меняют (`scan_depth_capped_no_warning`).
    Маскировка фикстуры — ``x://pwd=:‹secret›@pwd=‹secret›"pwd=:`@``.
  - Гарантия для любого текста: после `FIXPOINT_MAX` (4) обычных повторов находки расширяются
    (`WIDEN_STEPS` = 3, `widen`): повтор 5 — до пробелов вокруг, 6 — до строки, 7 — весь текст.
    Весь текст под одной маской новых находок не даёт, поэтому неподвижная точка достигается всегда,
    за постоянное число линейных сканов. Находка ровно на метке вида не считается (вид не меняет).
    `ScanOutcome::depth_capped` теперь значит «находки расширены», а не «не идемпотентна».

    проза 0,44 мс, ru 0,71 мс, значения 1,36/1,39 мс.
- **Одно определение «кода» (решение координатора).** Реализация перенесена из
  `zam-markdown/src/code.rs` в `zam-secrets` (`zam_secrets::code`: `lines_of`, `fence_of`,
  `fence_blocks`, `fenced_lines`, `code_spans`, `inline_spans`, `code_regions`); `zam-markdown`
  берёт её оттуда (маска прозы, сегментация предложений). Правила — по CommonMark: отступ забора
  до трёх пробелов; забор в цитате (`> ```sh`, вложенные) — блок той же цитаты, строка с меньшей
  глубиной его закрывает; инлайн-код — до пустой строки (многострочный; пустая строка — и с
  одиночным `\r`); одиночный `\r` — перевод строки; блок с отступом в четыре пробела кодом **не**
  считается (в списках это продолжение абзаца — без разбора контейнеров их не различить). Время
  линейно. Тесты `zam-markdown` — без смены ожиданий; образцовый поиск инлайн-кода (оракул
  `inline_scan_matches_oracle*`) переехал вместе с реализацией, его правило пустой строки
  обобщено так же (после перевода строки — сразу ещё один).
- **Авто-L0 вне правила (I2, остаток).** comrak снимает обратные кавычки инлайн-кода, и маска
  готового первого абзаца флаг не видела: `` Подключение: `mysql -uroot -pX prod`. `` давало L0
  с паролем. `zam_markdown::first_paragraph_masked`: маскируются исходные строки абзаца (с
  кавычками), текст берётся из них — не вся заметка до 5 МиБ ради одной строки. `note_meta`
  строит так авто-L0; перемаскировка базы (`rescan_secrets`, `remask_note` при росте
  `RULES_VERSION`) у авто-L0 строит его заново по исходнику, а не маской записанного текста.
  Заголовки секций в индексе и так берутся из маскированного исходника (`note_chunks`). Тесты:
  `zam-markdown` (три вида флагов), `zam-store` (`auto_l0_masks_flags_in_inline_code`,
  `rescan_rebuilds_auto_l0_with_inline_flag`), `zam-index` (сводка воркера и свёртка L0 папок),
  `zam-server` (L0 узла, `/read` L0, карточка поиска, дерево — агенту и человеку).
- **Minor 1, остаток.** Лист предпросмотра (`header`/`rows` до 1000 строк), эхо операций идей
  (`propose`, `decide`, `review`) и ответа на вопрос — через пул при объёме больше 64 КиБ
  (`agent_view::view_json_owned`, новый `view_entries_in`).
- **Косметика значений.** Значение не захватывает обратную кавычку (`` `mysql -pX` ``, `` echo
  `mysql -pX` ``) и закрывающую скобку без пары (`$(mysql -pX)`); заглушки из заглавных букв и
  `_` от трёх знаков (`TOKEN`, `PASSWORD`, `PASS_WORD`) — не секрет. Правила значения общие и
  для `mask_flags` клиента (тесты `zam-cli` прошли без правок).
- **Authorization в JSON и YAML** внутри кода: `{"Authorization": "Bearer …"}`,
  `Authorization: "Bearer …"`, `authorization: Bearer …`.
- Proptest идемпотентности — с атомами цитат, многострочного инлайн-кода, одиночного `\r`,
  заглушек, JSON-заголовка и `$(…)`; пробы ревьюера (`edge`, `idem` 200 000 случаев — 0 сбоев,
  `perf`) — все ожидания выполнены.

#### Круг правок 3 (повторное ревью круга 2: находки 1–6 закрыты; два Important, четыре Minor)

- **N1 — квадратичная обрезка скобки.** На каждую снятую `)` значение пересчитывалось целиком
  (100 КБ `-p` + `)`×N — 18,7 с, 1 МБ — около 30 мин; обрезка шла до ворот — её проходили все
  правила и `mask_flags`). Теперь — один подсчёт `(` и `)`, снятие хвостовых `)` с уменьшением
  счётчика. Бенч `bench_scan_paren_flags`: `-p)))`, `--password )))`, `Authorization: )))`,
  `curl -u a:)))` — 0,75–1,0 мс на 100 КБ, 8–11 мс на 1 МБ; `mask_flags` — линейно.
- **N3.** Скобка у значения в кавычках — часть значения (`-p'X)'` → `-p'‹secret›'`).
- **N2 — заборы в пунктах списка.** Решение координатора: в `zam_secrets::code` — стек колонок
  содержимого пунктов (`- ` — 2, `1. ` — 3, вложенные — больше); забор — если его отступ минус
  колонка текущего пункта не больше 3; забор на строке маркера — тоже. Пункт закрывается
  непустой строкой левее его колонки — после пустой строки или если строка начинает блок
  (маркер, заголовок, ограждение); иначе это ленивое продолжение абзаца, и пункт остаётся (в
  сомнении — шире код). Блок в пункте кончается непустой строкой левее колонки пункта. Вне
  списка забор с отступом 4 — по-прежнему не забор. Ожидания тестов `zam-markdown` не менялись.
- **Расхождения маски прозы `zam-markdown` с версией до круга 2** (проба ревьюера `mdcmp`): на
  текстах без `>` и `\r` — 0 из 300 000; с ними — отличия, и все по правилам CommonMark,
  принятым в круге 2: (1) забор в цитате (`> ~~~`, `> ```) — блок, прежде — проза; (2) пустая
  строка с одиночным `\r` (`\r\r`, `\r\r\n`, `\n\r` + знак) обрывает инлайн-код, прежде
  обрывали только `\n\n` и `\n\r\n` — спан через такую строку раньше считался кодом. Ожидания
  явных тестов не менялись; оракул инлайн-кода обобщён так же (круг 2).
- **N4.** Заглушка из заглавных — не длиннее 24 знаков: `-pXKQZJWPRMVNBTLHGFDSAYUEIOC`
  маскируется.
- **N5 — идемпотентность `mask_flags`.** Причина — отвергнутое совпадение (пустое значение,
  ссылка, заглушка, закрытые ворота, метка) «съедало» текст и прятало соседнее, а маска другого
  правила его убирала. Теперь отвергнутое совпадение ничего не прячет: флаги с дефисом — взятое
  закрывает только флаги, начатые внутри него (знак перед флагом может быть концом прежнего
  значения); заголовок — поиск следующего за началом отвергнутого, а при метке в значении —
  сразу за последней меткой (все заголовки до неё отвергнуты бы по той же метке; поиск
  линейный). Заглушка `<…>` — без `:` внутри (с двоеточием — уже не заглушка, а в значении
  заголовка — ещё и соседний заголовок; так и `<…>`-отказы не перечитывают длинные значения).
  Пересёкшиеся значения разных правил в `mask_flags` — одной меткой. Proptest
  `mask_flags_idempotent` (атомы пробы ревьюера, 2048 случаев) и проба `idem` (200 000 случаев):
  `mask_flags` — 0 неидемпотентных (прежняя версия — 45), `mask_text` — 0. Полная
  идемпотентность — без перестройки функции.
- **N6.** В тесте авто-L0 поиск сначала проверяет, что карточка заметки есть в выдаче.
- Остаток (не в рамках находок, по пробе `perf`): входы, где каждое значение — настоящая
  находка (открытые ворота `mysql -px` строками, `x-api-key:` подряд, `Authorization:` подряд
  без значения, строки с одиночным `\r`), — 3–6 мс на 100 КБ, линейно (30–60 мс на 1 МБ): цена
  маскировки и повторного скана вида с масками, в том числе общих правил ключ-значение.
