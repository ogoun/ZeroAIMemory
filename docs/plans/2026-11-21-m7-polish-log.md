### M7.1 · Задача 1 — ONNX Runtime из NuGet

Спецификация §4.1; проверка источника — `i:01M7ZB9N2QER1R4NA0XA2ZBK6E` (материалы исследования —
вне git). Ветка задачи `m7.1-t1`.

- **Манифесты.** `deploy/onnxruntime.toml` и `deploy/onnxruntime-gpu.toml` — пакеты NuGet 1.31.0
  `Microsoft.ML.OnnxRuntime` (CPU, один пакет на обе платформы: записи ссылаются на него, кэш по
  sha256 общий), `.Gpu.Windows`, `.Gpu.Linux`; адреса `api.nuget.org/v3-flatcontainer/…/….nupkg`,
  sha256 и `size` пакета, пути `runtimes/<rid>/native/…`, без `rename`. sha256 и размеры
  исполнитель пересчитал по скачанным nupkg — совпали с исследованием: CPU `7e35fdb4…` / 159 626 085,
  GPU Windows `6ef71832…` / 160 447 640, GPU Linux `7cd256a2…` / 244 928 869. В шапках —
  «файлы побайтово равны архивам GitHub v1.31.0, проверено 2026-11-21», без ссылок на `.tmp/`.
- **`zam-fetch`.** `format_of`: `.nupkg` (любой регистр) → zip. `download(url, dest, size)` —
  предел длины тела и точная проверка размера в одной функции: прежние `download_limited` и
  `check_size` после неё слиты, `fetch_file` и `install_archive` зовут её же (поведение то же).
- **`xtask fetch-deps` проверяет `size`.** При загрузке — `download_part(…, entry.size)`: длиннее —
  обрыв, короче — ошибка, `*.part` удаляется, в кэш ничего не попадает. У архива из `deps-cache` —
  размер до хэша и распаковки: «<имя>: файл кэша <путь> — N байт, а size в манифесте — M;
  исправьте size в манифесте или удалите файл кэша и повторите».
- **`xtask fetch-deps --prune-cache`.** `fetch::manifest_hashes(deploy/)` — sha256 всех
  `deploy/*.toml`; `fetch::prune_cache(target/deps-cache, keep)` удаляет файлы с другим именем
  (прежние версии и `*.part`), подкаталоги не трогает, нет каталога — `(0, 0)`. Печать —
  «<кэш>: удалено файлов — N (X МБ)».
- **Лицензия.** `deploy/licenses/ONNXRUNTIME-THIRD-PARTY-NOTICES.txt` — `ThirdPartyNotices.txt`
  пакета: во всех трёх nupkg один и тот же файл (344 457 байт, CRLF, sha256 `c53a7650…`), он же — в
  прежнем архиве GitHub `onnxruntime-win-x64-1.31.0.zip`. В репозитории — дословно с LF: 338 088
  байт, sha256 `143764b9…`. Каталог `deploy/licenses/` копируется в `LICENSES/` комплекта целиком,
  поэтому кода упаковки правка не требует.
- **CI.** `package.yml`: ключ кэша `deps-v2-<платформа>-<хэш манифестов>` и `restore-keys`
  `deps-v2-<платформа>-` (первый прогон — без кэша, §4.1 п. 6); шаг «чистка deps-cache»
  (`cargo xtask fetch-deps --prune-cache`) сразу после `fetch-deps` — кэш сохраняет post-шаг
  `actions/cache` в конце задачи. Прогон CI — координатор.
- **Документы.** `deploy/cuda.toml` — строка об источнике ORT GPU (NuGet, те же байты, набор и
  проверка импортов в силе); README — «Лицензия» и таблица команд xtask; CHANGELOG
  `[Unreleased]`.
- **[решение исполнителя, задача 1]** `DepManifest::validate` отвергает адрес с неизвестным
  форматом архива. Ловушка исследования («неизвестный формат архива» у `.nupkg») иначе
  обнаруживалась только после скачивания 160–245 МБ; сейчас — до загрузки, и
  `real_manifests_are_valid` ловит её без сети. Тест — `validation_rejects_bad_hash_and_url`
  (`.exe` — ошибка, `.nupkg` — ок).
- **[решение исполнителя, задача 1]** `manifest_hashes` собирает значения ключей `sha256` на любой
  глубине всех `deploy/*.toml` (зависимости, `cuda.toml`, `models.toml`; `config.example.toml`
  разбирается, но `sha256` в нём нет), а не разбирает три схемы по отдельности. Так выполняется
  интерфейс «ни в одном манифесте `deploy/*.toml`», и новый манифест не требует правки чистки.
  Нечитаемый TOML — ошибка: по неполному списку чистка удалила бы нужный архив.
- **[решение исполнителя, задача 1]** `--prune-cache` — отдельный режим без загрузки: clap
  запрещает сочетание с `--platform`, `--print-hashes`, `--flavor`. Чистка идёт после проверки
  манифестов — при неверном манифесте кэш не трогается.
- **[решение исполнителя, задача 1]** `--print-hashes` печатает и размер: под комментарием
  `# <имя>.toml [platform.<плат>]` строки `sha256 = "<hex>"` и `size = N` — TOML, вставляется как
  есть (круг правок 1). Без этого обновление версии давало бы sha256 без `size`, и
  `fetch-deps` падал бы на прежнем `size`. Размер при `--print-hashes` не проверяется: в
  манифесте он может быть от прежней версии.
- **[решение исполнителя, задача 1]** размер файла кэша проверяется до хэша, как в `fetch_file`
  («чужой файл не хэшируется»). Поэтому сообщение называет обе причины — неверный `size` в
  манифесте или испорченный файл кэша.
- **[решение исполнителя, задача 1]** `ci.yml` и `release.yml` не менялись: они кэшируют
  `target/deps` (распакованное, заменяется по штампу `<имя>.sha256`), а не `deps-cache`, и прежние
  версии там не копятся. Первый прогон после смены манифестов перекачает ORT с NuGet по
  несовпавшему штампу — это тоже проверка источника.
- **[решение исполнителя, задача 1]** smoke (`docs_layout`) лицензии ORT не проверяет, как и до
  задачи: состав `LICENSES/` закреплён тестом упаковки `licenses_include_ort_third_party`
  (настоящий `deploy/`). Если нужна проверка и на готовом архиве CI — одна строка в `smoke.rs`.
- **Для задачи 10 (ТЗ v1.27):** §16.3, пункты «Откуда берутся зависимости» (ORT из NuGet,
  проверка `size`, `--prune-cache`) и «Лицензии» (в `LICENSES/` комплекта сервера добавлен
  `ONNXRUNTIME-THIRD-PARTY-NOTICES.txt`; было 13 файлов в dev).

  - Причина цепочки фикстуры `scan_depth_capped.txt`: по виду с масками значение ключа склеивало
    короткий остаток с маской другого правила (`pwd=:‹secret›@…`; в тексте `:` упирался в `` ` ``).

    звенья ``"pwd=:`@`` сверх фикстуры ничего не меняют (`scan_depth_capped_no_warning`).
    Маскировка фикстуры — ``x://pwd=:‹secret›@pwd=‹secret›"pwd=:`@``.
  - Гарантия для любого текста: после `FIXPOINT_MAX` (4) обычных повторов находки расширяются
    (`WIDEN_STEPS` = 3, `widen`): повтор 5 — до пробелов вокруг, 6 — до строки, 7 — весь текст.
    Весь текст под одной маской новых находок не даёт, поэтому неподвижная точка достигается всегда,
    за постоянное число линейных сканов. Находка ровно на метке вида не считается (вид не меняет).
    `ScanOutcome::depth_capped` теперь значит «находки расширены», а не «не идемпотентна».

### M7.1 · Задача 7 — Надёжность Qdrant и тестов

Спецификация §4.7; сбой `i:01M7Y3C3A6E069FQ3QJXGZZGTQ`, задача `k:01M7GAQQJFE19B8VSHAZ5X30YA`. Ветка
`m7.1-t7`.

**Разбор `delete_collection` (Qdrant 1.19.2, `lib/storage/src/content_manager/toc/
collection_meta_ops.rs`).** `delete_collection` сначала убирает коллекцию из списка (TOC) и
останавливает её, потом переносит каталог в `.deleted` (`safe_delete_in_tmp`); сбой переноса —
`Err` (gRPC `Internal`, текст `fs_err` «failed to rename file from … to …»), а коллекция уже не в
списке, каталог — на месте. Повторный `delete_collection` идёт другой веткой: коллекции в списке
нет, но каталог есть — Qdrant удаляет его («not loaded, but its directory still exists. Deleting
it», ответ `false`). Поэтому повтор действительно доделывает удаление. `create_collection` поверх
такого остатка Qdrant отклоняет («Can't create collection with name zam_chunks. Collection data
already exists at …», `bad_input` → `InvalidArgument`) — тест `ensure_over_half_deleted_…`
воспроизводит это на настоящем Qdrant (каталог с `config.json` удалённой коллекции).

Сделано:
- `QdrantIndex::delete_collection_retry` (`qdrant.rs`): до 5 попыток, паузы 0,5 → 1 → 2 → 2 с
  (`delete_pause`), только `Internal` со словом «rename» без учёта регистра (`rename_failure`);
  каждая попытка — `WARN` с номером и паузой, удача после повтора — `INFO «коллекция удалена с
  повтора»`. Все пять неудачны — `IndexError::Corrupt` «delete_collection: коллекция zam_chunks
  удалена частично — Qdrant за 5 попыток не переименовал её каталог (…); остановите zam-server и
  выполните `zam-server qdrant reset --yes` — при старте индекс пересоберётся из кэша эмбеддингов».
  `reindex` прерывается на `drop_all` (`?`), до `ensure`, — коллекция поверх не создаётся.
- Проверка перед `create_collection`: `ensure` по-прежнему спрашивает `collection_exists`, а отказ
  Qdrant «Collection data already exists» (коллекции нет в списке, каталог остался) теперь —
  тот же `Corrupt` с советом (`create_err`), а не `Other("create_collection: InvalidArgument…")`.
- Тестовые сбои `test_hooks::DeleteFaults` + `QdrantIndex::with_delete_faults` (фича `test-hooks`,
  на клиента, а не на процесс: параллельные тесты бинарника не мешают друг другу): взведённые
  попытки отвечают настоящей `QdrantError::ResponseError { Internal }` без запроса к Qdrant —
  классификация и повтор проверяются целиком; журнал — число попыток с последнего взвода. Тесты
  пакета включают фичу dev-зависимостью на себя (как `zam-server`).
- Документация: `deploy/README-install.md` («Состояние индекса и reindex»), CHANGELOG, модульные
  комментарии `qdrant.rs`, `reindex.rs`, `IndexError::Corrupt`.

Решения:
- **[решение исполнителя, задача 7]** «Три попытки в журнале» — журнал попыток тестового хука
  (`DeleteFaults::attempts`, считает и удачные), а не разбор строк `tracing`: подписчик `tracing`
  глобален на бинарник, а тесты `worker.rs` идут параллельно (строки чужих тестов не отделить).
  Строки `WARN`/`INFO` повтора в журнале есть, их видно в выводе упавшего теста.
- **[решение исполнителя, задача 7]** Частично удалённая коллекция — `IndexError::Corrupt`
  («индекс повреждён: …»), не новый вариант: воркер записывает его в итог reindex
  (`last_reindex.result`, `/index/status`, WebUI) и не повторяет, как прочие не-сетевые ошибки.
- **[решение исполнителя, задача 7]** Сам `ensure` остаток не удаляет (хотя Qdrant 1.19 удалил бы
  его тем же `delete_collection`): по спецификации — понятная ошибка с советом. Самовосстановление

Решения:
- **[решение исполнителя, задача 8]** «Пустой stderr» у Claude Code. `PostToolUseFailure.error` —
  строка `Exit code N` и **слитые** stdout и stderr (журнал событий этой рабочей копии: листинги
  `ls -l`, вывод `grep -c` и сообщения `bash:` идут одним текстом). Строгое «кроме строки кода
  ничего» (так в разборе claude-note) пропустило бы главные случаи — `diff a b` (разница в
  stdout), `grep -c` («0»), `cmp` («a b differ»). Поэтому stderr — строка, первое слово которой до
  `:` (без пробелов) — сама программа, оболочка (`bash`, `sh`, `zsh`, `dash`, `ksh`, и с путём)
  или `error`/`fatal`/`warning`/`usage`. Строки `diff` и `git diff` начинаются с `<`, `>`, `+`,
  `-`, ` `, `@@`, номеров — под правило не попадают. У Codex `error` — сам непустой stderr без
  строки кода: не ожидаемый (пустой stderr Codex и раньше не был ошибкой).
- **[решение исполнителя, задача 8]** Ожидаемый код — успешная команда журнала (`Ev::Cmd {ok:
  true}`), а не пропуск события: это исход команды, а не сбой. Пару он не открывает (нет `error`);
  закрыть пару может — как и код 0 той же программы.
- ~~[решение исполнителя, задача 8] «Без запроса к серверу» (тест задания) — буквально: на
  классифицированный сбой хук `/recall(post_tool)` не зовёт~~ — заменено решением координатора
  (ниже).
- **[решение координатора, задача 8]** «Локально, без сети» (§4.6 п. 2) относится к самой строке
  класса: её строит клиент без обращения к серверу. Запрос `/recall(post_tool)` на 401, 403, квоту,
  ENOSPC, 429 и 400/422 остаётся, как раньше: связанные ловушки по ним приходят из памяти. Строка
  класса добавляется после подсказок сервера и локальных `error_regex`, раз за сессию на класс и
  отпечаток; сервер недоступен — строка класса и локальные `error_regex` всё равно выводятся.
  Бюджет хука не растёт.
- **[решение исполнителя, задача 8]** Строка класса — подсказка типа `post_tool` (выключен — её
  нет). Шаблоны — только явные формы кода (`HTTP 401`, `status: 401`, `returned
  error: 401`, `401 Unauthorized`), голое «401» — нет: урок claude-note (ранняя версия срабатывала
  на `grep` по файлу со словом 401). Порядок проверки: диск, квота, 429, 401, 403, 400/422
  (`insufficient_quota` приходит с 429, «API rate limit exceeded» — с 403).
- **[решение исполнителя, задача 8]** Строка `Exit code N` снимается на сервере и из запроса FTS,
  а не только из покрытия: строгий запрос по «Exit code» (ошибка `grep` без вывода у клиента без
  правила п. 1, например нативного) находил бы любую запись со словами exit и code.
- **[решение исполнителя, задача 8]** Служебные фразы вывода — одна: «No such file or directory»
  (пример спецификации). «Permission denied», «File exists» и подобные — нет: это ключевые слова
  записей набора (`h20`, docker в тестах сервера); их отсекает правило частоты, если они частые.
- **[решение исполнителя, задача 8]** «Имена каталогов из команды». Сервер команды не получает (и
  не должен: журнал хранит только `exe`, в аргументах бывают секреты), поэтому слова путей
  выделяет клиент и шлёт новым необязательным полем `path_words`. Слова — всех аргументов с `/`
  или `\` (каталоги и имена файлов, набранные в команде, — не предмет ошибки) и аргументов без
  разделителя, если это существующий каталог; адреса и `user@host` пропускаются; команда до
  выделения маскируется сканером и правилами флагов снимка.
- **[решение исполнителя, задача 8]** Код ошибки — 1–4 латинские буквы и 4–6 цифр (`sha256`,
  `x86`, `e2e` — не коды). Коды не входят в `n` порога: их совпадение проверяется целиком и

- **[решение исполнителя, задача 8]** Сбой чтения частоты или срок сбора — без частых слов (WARN):

- **Для задачи 10 (ТЗ §10.3):** `post-tool` (режим ошибки) — ожидаемый код 1 простых `grep`,

### M7.1 · Задача 6 — Восстановление секретов при записи агентом

Спецификация M7 §4.3.2; worktree `.tmp/m71/wt-t6`, ветка `m7.1-t6` от `43718886` (задача 5

**Единая точка** — `crates/zam-server/src/api/secret_restore.rs`: `restore(base, new_masked) ->
Restored {text, kept}`; `MaskedBase` — вид `mask_text(base)` и для каждой метки вида диапазон

«сама метка», напротив себя он не новый). Решает принципал (`agent_view::masks`): сессия WebUI
пишет как раньше.

Выравнивание (детерминировано, без сроков по часам — повтор `PUT` с `Idempotency-Key` даёт тот же
текст и тот же отпечаток ключа):
1. дифф строк — `similar` Майерс на номерах строк (одинаковые строки — один номер); середина
   больше 4096 строк — деление по строкам, единственным в обоих текстах (LIS, как patience diff),
   до глубины 4; работа всех вызовов Майерса ограничена `Σ(n+m)² ≤ 2·10⁸`;
2. перенос строки с метками целиком — пара по точному совпадению [решение исполнителя, задача 6];
3. правленые строки — пары по похожести слов (общих слов не меньше половины слов более короткой
   строки; слова меток не считаются), самые похожие первыми, при равной — ближайшие по месту;
   внутри пары — дифф «символов» Майерсом по токенам: слово, пробелы, знак, метка — один токен
   [решение исполнителя, задача 6: «символы» спецификации — слова и знаки, так участок до 8192
   токенов вмещает в 4–5 раз больше текста, а метку одинаково видят оба способа]. Сначала было
   выравнивание по всему изменённому участку сразу — случайная проба (ниже) показала, что
   удалённая соседка правленой строки забирает её значение (у соседки больше общих знаков);
   затем динамика похожести внутри участка — перенесённая и правленая строка брала значение
   ближней похожей; итог — общий жадный выбор пар по всему тексту;
4. остаток изменённого участка (строка переписана другими словами, строки склеены) — дифф
   токенов по всем его строкам с метками без пары; больше 8192 токенов или работа исчерпана — по
   порядку появления, если меток поровну; иначе — как есть.
