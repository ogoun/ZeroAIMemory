Каталог данных — на HDD (Seagate ST4000NE001, SATA).

| Операция | p50, мс | p95, мс | Цель p95 | Итог |
|---|---|---|---|---|
| чтение по id `GET /nodes/{id}?format=md` | 0.41–0.47 | 0.58–1.05 | ≤ 5 | выполнено |
| FTS `POST /search` (1–3 слова, top_k 10) | 4.5–5.3 | 8.5–11.0 | ≤ 20 | выполнено |
| запись до FTS `POST /nodes` | 1.5–1.6 | 33–66 | ≤ 30 | не выполнено на HDD |

- Запись «до FTS»: 201 возвращается после фиксации ревизии, чанков и обеих FTS-таблиц; последняя записанная заметка сразу находится поиском (проверка в скрипте).
- Причина хвоста записи: 7–10 % запросов ждут 370–720 мс при CPU сервера ≈ 0 — ожидание ввода-вывода. Это fsync автоматического checkpoint WAL (`wal_autocheckpoint` по умолчанию 1000 страниц), который выполняет писатель в конце транзакции. Контрольный прогон с `wal_autocheckpoint = 1000000` (локальная правка, откачена, не в git): p95 записи 2.84 мс, max 24.8 мс, загрузка 1000 заметок 2.7 с вместо 21 с; чтение и FTS без изменений.
- Предложение (не сделано в M1, решение владельца): писатель с `wal_autocheckpoint = 0` и фоновый `PRAGMA wal_checkpoint(PASSIVE)` с отдельного соединения (по таймеру/по размеру WAL), `TRUNCATE` при простое — цена: рост WAL между checkpoint и одно фоновое соединение на БД. На SSD хвост должен быть заметно меньше; замер на SSD не выполнен (данные — только в каталоге проекта, он на HDD).
