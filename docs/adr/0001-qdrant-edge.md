# ADR 0001. Qdrant Edge вместо managed Qdrant: прототип и решение

- **Статус:** принято — не переходить; Edge остаётся прототипом под feature `edge`.
- **Дата:** 2026-10-20.
- **Задача:** M2, задача 16. ТЗ §4.3 (режим `edge`), §19 (M2). Исследование 05 §8.
- **Замер:** `eval/results/2026-10-20-bench-edge.{json,md}` (`cargo xtask bench --edge`, код `2e7387a`;
  пометка `dirty` в отчёте — неподготовленная правка `CHANGELOG.md`, на код не влияет).

## Контекст

Векторный индекс ZeroAIMemory — локальный Qdrant 1.19 отдельным процессом. Им управляет
супервизор `zam-server`: Job Object или PDEATHSIG, перезапуск, метка хранилища, случайный
API-ключ, gRPC. Это работает, но процесс приносит издержки:

- второй процесс и его RSS;
- старт до готовности (1–10 с на HDD, замер задачи 15);
- gRPC на каждый запрос;
- сложный супервизор.

Qdrant Edge (`qdrant-edge`) — тот же движок сегментов, что у сервера, но встраиваемой
библиотекой без процесса и сети. Если он заметно быстрее и легче, супервизор становится не нужен.

Состояние Edge на 2026-10-20:

- последняя версия на crates.io — 0.8.0 от 2026-08-05 (0.6 — март, 0.7 — май–июнь 2026);
- лицензия Apache-2.0, около 19 тыс. загрузок;
- на сайте Qdrant продукт помечен как бета: «The API and functionality may change in future
  releases»; о версии 1.0 и политике совместимости ничего нет;
- Windows официально не заявлена, но крейт собирается.

Критерий исследования 05: **не переходить до 1.0, если выигрыш p95 меньше 2× или RSS выше
managed-варианта.**

## Варианты

1. **managed Qdrant** (текущий) — процесс под супервизором, `QdrantIndex` по gRPC.
2. **Qdrant Edge в процессе сервера** — `EdgeIndex` за тем же трейтом `VectorIndex`.
3. **Edge сейчас, managed запасным режимом** — два движка в поставке. Два формата
   хранилища, удвоенные тесты и сборка. Имеет смысл, только если вариант 2 даёт выигрыш
   по критерию.

## Прототип

`crates/zam-index/src/edge.rs`, feature `edge` (не по умолчанию; в сервер и комплекты не входит).

- **Схема коллекции** — та же, что у `QdrantIndex`:
  - `dense`: Cosine, оригиналы на диске (mmap, `ChunkedMmap` — то же, что `Memory::Cold`), int8 scalar
    quantization quantile 0,99 в RAM, поиск с rescoring;
  - `sparse`: на диске;
  - HNSW m=16, ef_construct=100, payload_m=16; payload на диске; 2 сегмента;
  - payload-индексы те же, `user_id` с `is_tenant`;
  - гибридный запрос: prefetch dense и sparse по чанкам и dense по сводкам, RRF k=60.
- **Метаданные `{model_id, schema, dim}`**: в Edge их нет, поэтому они лежат в `zam_meta.json` рядом
  с шардом (атомарная запись). Шард без файла считается «не нашим», как коллекция чужой модели.
- **Синхронный API**: каждый вызов идёт через `spawn_blocking`. Паника внутри Edge становится
  ошибкой, а не роняет сервер (в managed-варианте сбой Qdrant изолирован процессом).
- **Индексация**: Edge строит HNSW только по явному `optimize()`, который блокирует до конца.
  Его запускает фоновый поток после паузы в записи (дебаунс 2 с).
- **Тесты**: общий набор контракта `VectorIndex` — `crates/zam-index/tests/common/cases.rs`, 11 случаев.
  Он прогоняется для managed Qdrant (`tests/qdrant.rs`) и для Edge (`tests/edge.rs`). Ещё у Edge
  3 своих теста: переоткрытие, `optimize`, фоновый оптимизатор с `drop_all`. Все проходят на
  Windows с Rust 1.99.1. Тесты, специфичные для процесса (ключ, недоступность, падение), есть
  только у managed.

## Методика замера

`cargo xtask bench --edge`, пример `crates/zam-index/examples/index_bench.rs`.

**Стенд:** Ryzen 9 5900X (24 логических ядра), 128 ГБ ОЗУ, данные на HDD, Windows 11.

**Сборки:**

- каждый вариант собран с нуля в своём `CARGO_TARGET_DIR`;
- профиль release поставки: thin LTO, 1 codegen unit, `crt-static`;
- для managed — без Edge в бинарнике.

**Изоляция:** каждый замер — отдельный процесс. RSS managed — сумма рабочих наборов процесса
Qdrant и клиента.

**Данные:** 1 000 000 точек × 1024, детерминированные.

- Dense — смесь 1024 кластеров на единичной сфере: точка = центр + шум, нормировано.
  Косинус соседей по кластеру ≈ 0,5.
- Sparse — 761 окно по 200 токенов bge-m3 из корпуса eval (160 заметок, словарь 10 970 токенов,
  в среднем 118 ненулевых). Вес растёт с IDF токена (0,02–0,35). У каждой точки выпадает 20 %
  токенов, веса разбросаны на ±20 %.
- Payload — как у сервера: один тенант, 4 пространства, 3-уровневые пути, уровни
  chunk / section / note (85 / 10 / 5 %).

**Пересборка** — как `reindex` из кэша `embeddings`:

- пустая коллекция;
- upsert пачками по 256 точек, до 8 одновременно;
- ожидание конца индексации: managed — статус коллекции green три опроса подряд, Edge — `optimize()`;
- потоков индексации 2, как `optimizer_cpu_budget` сервера;
- потоков поиска 2.

**Поиск:**

- 3 прогона на вариант, каждый в новом процессе на готовом индексе;
- 100 запросов прогрева, затем 1000 гибридных запросов подряд;
- запрос — возмущённая точка-цель (косинус ≈ 0,9) и 12 её sparse-токенов;
- фильтр: тенант и 4 пространства, у четверти запросов ещё и папка (1/8 корпуса).

Наблюдения:

- **Поиск.** Edge быстрее на 37–40 % по всем квантилям: нет gRPC и сериализации. Разброс
  прогонов мал (≤ 5 %), так что до 2× далеко. Качество одинаковое: цель в топ-10 у обоих
  всегда, выдачи совпадают на 93 %. Расхождение — порядок близких по RRF кандидатов
  из 1024-мерных кластеров.
- **Память.** Edge держит в процессе вдвое больше. 8 ГиБ уже сразу после загрузки шарда, хотя
  оригиналы векторов те же `ChunkedMmap`/Cold, что у managed. Вероятные причины (не
  разбирались, на решение не влияют):
  - загрузка сегментов с проверкой и восстановлением (`check_consistency_and_repair`)
    читает хранилище целиком;
  - payload-индексы и граф HNSW у Edge по умолчанию в RAM;
  - пиковые 25 ГиБ — построение HNSW в том же процессе.

  Для сервера это означает: RSS индекса добавляется к RSS `zam-server` с моделью, а цели §17
  по RSS и так не выполнены (задача 15).
- **Пересборка** в 3,8 раза дольше. Upsert в 8 раз медленнее, и темп падал по ходу записи
  (по журналу прогресса, засечки примерно раз в 10 мин: от ~200 тыс. точек за 10 мин
  в начале до ~100 тыс. в конце).
  Пока идёт запись, Edge не
  оптимизирует (`optimize()` только явный и блокирующий), и все точки копятся в одном
  растущем appendable-сегменте. Managed Qdrant оптимизирует параллельно с записью.
  Прототип можно ускорить, вызывая `optimize()` каждые N точек, но это свой планировщик
  оптимизаций, которого в сервере Qdrant писать не нужно.
- **Диск** почти вдвое больше: WAL Edge не усекается до сброса, так как нет фонового flush.
  Это не проверялось отдельно.
- **Открытие** вдвое дольше, чем старт процесса Qdrant: та же загрузка сегментов, но
  в потоке сервера.

## Аудит зависимости

- **`qdrant-edge =0.8.0`, Apache-2.0** (совместима с MIT проекта).
  - Это один крейт примерно в 247 тыс. строк: внутрь скопированы `segment`, `shard`,
    `sparse`, `quantization`, `wal`, `posting_list`, `blobstore` сервера Qdrant.
  - `unsafe` — 616 вхождений в 84 файлах: SIMD, mmap, bytemuck.
  - C/C++ код квантования собирается через `cc`, MSVC-ветка с `/arch:AVX2` есть.
- **Дерево `zam-index`**: +198 крейтов на хосте, +253 на всех целях (235 → 433 и 276 → 529).
  - Лицензии новых крейтов: MIT / Apache-2.0 / BSD / ISC / Zlib / CC0 / BSL / Unlicense —
    всё из `about.toml`. `self_cell` под «Apache-2.0 OR GPL-2.0-only» берём как Apache-2.0.
  - Без сопровождения (RUSTSEC unmaintained):
    - `serde_cbor` 0.11 (RUSTSEC-2021-0127);
    - `bincode` 2.0 (RUSTSEC-2025-0141);
    - `docopt` 1.1 (архивирован).
  - Тяжёлые зависимости, ненужные для нашего сценария:
    - `charabia`, `jieba-rs`, `vaporetto`, `whatlang` — токенизация китайского, японского,
      тайского и иврита для полнотекстового индекса Edge;
    - `geo`, `tonic` с `tls-ring`, `tokio` с `full`, `rand` 0.7 и 0.10 рядом с нашим 0.9,
      `nix`, `sysinfo`, `env_logger`.
  - Фичами всё это не отключается: у крейта нет `[features]`.
- **Сборка:** чистая release-сборка в 5 раз дольше (101 → 500 с), exe больше на 23,6 МиБ.
- **Зрелость API** — замечания при работе с 0.8.0:
  - `JsonPath::new` доступен только с фичей `testing`;
  - флаги функций и проверку multi-mmap нельзя инициализировать извне. Edge пишет WARN
    «Feature flags not initialized!» на каждой операции; в замере заглушено через
    `qdrant_edge=error`;
  - `optimize()` блокирует без отмены, поэтому `drop_all` ждёт его конца;
  - логирование через `log`, а не `tracing`;
  - на HDD создание шарда занимает около 3 с, каждый payload-индекс — 0,4–2,7 с
    (тесты Edge идут 65–85 с против 110–120 с у managed с запуском процессов).
- **Поддержка:** Qdrant выпускает минорные версии раз в 2–3 месяца. Формат хранилища и API
  между ними меняются: 0.6 → 0.7 → 0.8 за 5 месяцев.

## Решение

**Не переходить на Qdrant Edge.** Сервер остаётся на managed Qdrant под супервизором.
`EdgeIndex` остаётся прототипом под feature `edge`:

- не входит в сервер, комплекты и CI;
- проверяется вручную: `cargo test -p zam-index --features edge`.

По критерию исследования 05 не выполнены оба условия, и Edge ещё не 1.0:

- p95 выигрывает **1,60×** (нужно ≥ 2×);
- RSS Edge **в 2,16 раза выше** (нужно не выше).

Сверх критерия Edge в 3,8 раза дольше пересобирает индекс, занимает на 80 % больше диска,
добавляет около 200 крейтов (из них три без сопровождения) и в 5 раз дольше собирается.
Выигрыш около 8 мс p95 на запросе не окупает этого: бюджет поиска §17 — 50–120 мс, большая его
часть приходится на эмбеддинг запроса и SQLite.

CI отдельно с `--features edge` не проверяется. Feature нужна только для пересмотра этого
решения, а сборка с ней добавляет около 8 минут на каждую ОС. Риск, что прототип отстанет
от трейта, принят: при изменении `VectorIndex` проверку с `--features edge` проводит
исполнитель.

## Условия пересмотра

Пересмотр по любому из событий:

- выход `qdrant-edge` 1.0 или объявленная политика совместимости формата хранилища;
- Edge получает фоновую оптимизацию во время записи или отменяемый `optimize()`;
- проект уходит от отдельного процесса по другим причинам: мобильные или встраиваемые
  платформы, запрет второго процесса.

При пересмотре:

1. Обновить версию (`=`) и пройти общий набор тестов `VectorIndex` с `--features edge`.
2. Повторить `cargo xtask bench --edge` на том же стенде.
3. Переход — только если одновременно:
   - p95 выигрывает ≥ 2×;
   - RSS после запросов не выше managed;
   - полная пересборка не дольше managed более чем на 25 %;
   - дерево зависимостей проходит аудит: нет крейтов без сопровождения в рабочем пути.
