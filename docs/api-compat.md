# Совместимость API `/api/v1` и возможности сервера

Документ для разработчиков собственных клиентов ZeroAIMemory: агентов, которые ходят в REST
`/api/v1` или в MCP `/mcp` напрямую, без `zam` и его хуков. Он отвечает на два вопроса: что
сервер обещает не ломать и как клиент узнаёт, что умеет конкретный сервер.

Введён в M6 (`0.0.11-m6`, задача 19) по запросам проекта zero-agent
([CR-9](research/2026-11-06-zero-agent-memory-requests.md), часть; ответ —
[`…-answer.md`](research/2026-11-06-zero-agent-memory-requests-answer.md)). Схема OpenAPI —
этап M7.

## Правило совместимости

- **Без смены версии пути** (`/api/v1`) сервер может:
  - добавлять маршруты, необязательные поля запроса и поля ответа;
  - добавлять значения в поля-перечни ответа (`warnings`, `reason`, `kind` …);
  - добавлять строки в `features` (раздел ниже).
- **Только в `/api/v2`**: удалить маршрут или поле, сделать необязательное поле обязательным,
  поменять смысл, тип или единицы существующего поля, поменять код ответа существующего случая
  успеха.
- **Клиент обязан**: пропускать неизвестные поля ответа и неизвестные строки `features`, не
  полагаться на порядок полей JSON и на текст `title`/`detail` ошибок (смысл ошибки — HTTP-код и
  поле `type` problem+json).
- **Тела запросов** части маршрутов (около половины структур тел) разбираются строго
  (`deny_unknown_fields`): неизвестное поле — 400. Поэтому новое поле запроса клиент шлёт, только убедившись по
  `features`, что сервер его знает. Исключения — `POST /recall` и `PUT /sessions/{id}/snapshot`:
  неизвестные поля их тел игнорируются (клиент хуков бывает новее сервера). Тело
  `POST /sessions` разбирается строго: сервер до M6 на `new_epoch` и `holdout` отвечает 400 —
  шлите их отдельным запросом, как хуки `zam`.
- **Ошибки** — `application/problem+json` с `type`, `title`, `status`, `detail`.
- **Ответы MCP** — Markdown для агента; стабильный контракт — у REST и у `format: "json"` MCP
  (JSON ответа REST в тексте).

## Как узнать возможности

`GET /api/v1/health` (без аутентификации) →
`{status, version, git, features, token_counter, tokenizer_id, uptime_s}`.

- `features` — массив строк: каждая строка — возможность этой сборки. Поля нет у выпусков до
  M6 (`v0.0.10-m5.7` и раньше отдают только `status, version, git, uptime_s`): у них нет ни
  одной возможности из таблицы ниже.
- Возможность определяется **только** по `features`, без пробных запросов и без сравнения
  версий: ветка с частью M6 называет себя прежней версией (`0.0.10-m5.7`), а флаг появляется
  в той же сборке, что и функция.
- Флаг, однажды появившись, не удаляется, пока жив `/api/v1`.

Правило для разработки сервера: задача, которая вводит возможность или ключ конфигурации,
добавляет строку в `FEATURES` (`crates/zam-server/src/api/health.rs`) и строку в эту таблицу;
тест `boot::health_features_documented` сверяет таблицу с `FEATURES` в обе стороны. Ключи
конфигурации, которые переопределяет замер, помечаются тем же флагом в
`xtask/src/eval/caps.rs` (`KEYS`).

## Явная сессия

- REST: `X-Zam-Session: <id>` или `session_id` в теле `/search`, `/read`, `/recall`,
  `/feedback` (тело сильнее заголовка, как и прежде).
- MCP (`mcp_session_arg`): заголовок `X-Zam-Session` или аргумент `session_id` у
  `memory_recall`, `memory_search`, `memory_read`. Оба заданы и совпадают — эта сессия; оба
  заданы и различаются — ответ-ошибка `400` (запрос в REST не уходит, учёт ответа — в сессии
  заголовка). **Изменение поведения M6:** до `0.0.11-m6` у `memory_recall` при разных значениях
  побеждал аргумент (учёт же шёл в сессию заголовка); теперь такой вызов — ошибка. Учёт выданного (`session_tokens`, событие `mcp`), отметки «уже выдавалось» и
  счётчик записей идут в эту сессию.
- Без явной сессии MCP подставляет последнюю сессию хуков только для счётчика записей, а
  выданное учитывает в `GET /sessions/unattributed`. Подставляется незавершённая сессия **верхнего
  уровня** (не субагента) пользователя токена, к которой обращались не позже 12 ч назад; с
  `X-Zam-Machine` — только той же машины, с `X-Zam-Solution` — того же решения. Отметок «уже
  выдавалось» неявная сессия не ставит.
- `session_id` — один постоянный id на сессию, до 128 символов.

## Срок `/recall` (`recall_timeout`)

`POST /recall {…, timeout_ms}` — срок сбора подсказок этого запроса, мс. Без поля у хука действует
`recall.timeout_ms` сервера (200: бюджет хуков), у явного вызова — `max(recall.max_timeout_ms,
recall.timeout_ms)` (с 0.0.13-m6.6, M6.6 §5.1). Хук — запрос без происхождения MCP с событием
`session_start`, `prompt`, `post_tool` или с полем `code_map` (его шлют хуки `session-start` и
`subagent-start`); явные — все вызовы MCP `memory_recall` и `recovery`, `brief`, `idea_review` из
REST без `code_map`. Допустимо 1..=`max(recall.max_timeout_ms,
recall.timeout_ms)` (`recall.max_timeout_ms` по умолчанию — 2000), иначе 400: если срок сервера больше предела поля
(сетки замера ставят 60000), явно попросить можно и его. Нативный агент, который может подождать, шлёт, например, `timeout_ms: 1000`
и получает полный дайджест там, где хук получил бы собранное и `warnings: ["recall timeout"]`.

## Идемпотентность записи (`idempotent_nodes`)

`Idempotency-Key: <ключ>` (1–200 печатных символов; пустой — как без заголовка):

| Маршрут | Первый запрос | Повтор с тем же ключом и тем же запросом |
|---|---|---|
| `POST /spaces/{space}/entries` | 201 | 200, та же запись |
| `POST /entries/{id}/supersede` | 201 | 200, та же новая запись |
| `POST /nodes` | 201 | 200, тот же узел |
| `PUT /nodes/{id}` | 200 | 200, без новой ревизии (прежний `If-Match` не даёт 409) |
| `PATCH /nodes/{id}` | 200 | 200, без второй правки (два `append` — одна вставка) |

- Повтор отдаёт **текущее** состояние записи или узла (как у записей журнала с M3): если
  после первого запроса цель правили, в ответе — последняя ревизия.
- Тот же ключ с другим запросом (другое тело, другая цель, другой метод) — 422
  `/problems/idempotency-mismatch`, ничего не записано. Сверяются: у `POST /nodes` —
  пространство, путь, `content`, `l0`; у `PUT` — узел, `If-Match`, `content`, `l0`; у
  `PATCH` — узел, `base_rev`, `ops`. `message` в сверку не входит (как у записей журнала).
- Цель по ключу удалена в корзину: повтор `POST /nodes` (и запись журнала) — 409, повтор `PUT`
  и `PATCH` — 404 (узел в корзине для правки не виден, как и без ключа); восстановите цель или
  возьмите новый ключ.
- Ключ действует в границах автора (пользователь токена) и базы владельца пространства;
  хранится, пока жива цель (как ключ записи журнала), — отдельного срока нет.
- Параллельные запросы с одним ключом: сверка ключа и запись — одна транзакция единственного
  писателя базы, поэтому запись одна, остальные получают повтор.
- Неуспешный запрос (400, 409, 413, 422, 428 и др.) ключ не занимает: повтор выполнится заново.
- `POST /nodes` папки (`kind: folder`) с ключом — 400: ключ есть только у заметок.
- Без ключа всё как раньше: повтор `PATCH append` с тем же `base_rev` допишет текст ещё раз
  (`append` и `prepend` применяются к текущему тексту при любом `base_rev` не новее текущей).
- MCP: `memory_write {…, idempotency_key}` и `memory_log {…, idempotency_key}`.

## Разбор идей (`idea_review`)

Введён в M6.5 (`0.0.12-m6.5`, спецификация `docs/specs/2026-11-15-m6.5-idea-review.md`). Всё
ниже клиент использует, только увидев флаг `idea_review` в `features`.

- **Статус идеи `returned`** («На доработку»). Сервер без флага его не знает: фильтр ленты
  `status=returned` у него — 400. `zam idea list` без `--status` на таком сервере повторяет запрос
  без `returned`.
- **`POST /entries/{id}/review`** — разбор идеи агентом, только по токену. Тело (строгий
  разбор): `{outcome, summary, missing?, basis?, similar?, task?, space?, message?}`.
  - `outcome` — `plan | return | decline | done`; `summary` — 200 (`[ideas] review_min_chars`)
    — 8000 символов; `missing` — только у `return` и обязателен у него, ≤ 2000.
  - `basis` — на что опирался разбор: ссылки на живые записи и заметки того же пространства
    (`n: i: c: r: t: k: q: w:`), `file:<путь от корня решения без ..>`, `commit:<hex 7–64>`; у
    `done` нужна хотя бы одна ссылка на сделанное (`c:`, `r:`, `commit:`, `k:` задачи `done`).
  - `similar` — похожие идеи: **только** `w:<id>` живых идей того же пространства (любого
    статуса, в том числе отклонённые), не сама разбираемая идея; другой префикс — 422.
  - В каждом из полей `basis` и `similar` — не больше 50 ссылок (`REVIEW_REFS_MAX`): предел
    считается по присланному списку до схлопывания повторов (51 одинаковая ссылка — 422), затем
    повторы схлопываются — хранится первое вхождение; неверная ссылка — 422 с именем поля. Рёбер
    графа ссылки не создают — они хранятся только в `data.review`. Импорт пространства
    переписывает их (`basis`, `similar`, `task` в `data.review` и `data.reviews`) на новые id;
    `by_user` — голый id пользователя исходного сервера, импорт его не переписывает.
  - Тексты `summary`, `missing`, `task.body` — не больше `limits.note_max_bytes` байт (как тело
    записи): больше — 413 `/problems/too-large`, `detail` начинается с имени поля.
  - `task` у `plan`: `{title?, body?, priority?}` — новая задача `open` (план шагов в `body`), или
    `{id: "k:<id>"}` — привязать к открытой задаче (`open | in_progress | blocked`) того же
    пространства.
  - Ответ — 200 `{entry, task?, replay}`. `Idempotency-Key` — на один вызов разбора: повтор с тем
    же ключом — 200 с `replay: true`, без второй задачи и аудита, только пока идея не менялась
    после того разбора и исход тот же. Ключ, уже использованный разбором этой идеи тем же
    пользователем, в остальных случаях (идею после разбора правили, другой исход, ключ прежнего
    разбора из истории) — 422 `/problems/idempotency-mismatch`: новому разбору — новый ключ.
  - Ошибки: сессия WebUI и идея Knowledge — 422; токен `ro` — 403; идея «от агента» — 409
    `/problems/idea-agent-origin`; статус не `new` (в том числе после решения человека и второй
    разбор) — 409 `/problems/conflict` с `code: transition-not-allowed`; режим `propose` владельца
    базы — 409 `/problems/idea-mode`; неверное поле — 422, `detail` начинается с имени поля
    (`summary:`, `missing:`, `basis:`, `task.id:` …); неизвестное поле тела — 400.
- **Режим `ideas.mode`**: `GET/PATCH /auth/settings` → `{ideas: {proactive, mode}}`, `mode` —
  `review` (по умолчанию — `[ideas] default_mode` сервера) или `propose`; не строка — 400,
  другая строка — 422; токен свою настройку не меняет (403). Значение, равное умолчанию сервера,
  не хранится: правка на него удаляет сохранённый выбор (пользователь снова идёт за `[ideas]
  default_mode`), аудит `{key, from, to}` — как у любой правки. В общем решении действует режим
  владельца базы. В режиме `review` `POST /entries/{id}/propose` идеи `new` — 409
  `/problems/idea-mode`.
- **`PATCH /entries/{id}` `by: "human" | "agent"`** — только у токена и только вместе с правкой
  заголовка или тела идеи (иначе 422): правка возвращённой идеи со словами человека (`by:
  human`) переводит её в `new`, правка агентом статус не меняет. MCP `memory_update_entry
  action=append` передаёт `by`; CLI — `zam insight append <id> --by human|agent`.
- **`GET /entries/{id}` идеи с разборами** — поле `reviewers {<id пользователя>: <имя>}`: имена
  пользователей `by_user` разборов (`data.review` и `data.reviews`) для подписи «чей агент
  разбирал»; только в ответе, в `data` не хранится; пользователя нет — его id в поле нет.
- **`POST /recall {event: "idea_review", limit?}`** — пакет разбора: до `limit` (1..=20, по
  умолчанию 5; иначе 400) идей очереди с историей разборов, доводами человека и до 5 похожих
  записей решения; `items[]` — `kind: idea`, `reason: idea_review`. Бюджет — `budget_tokens`
  (по умолчанию 3000), срок по умолчанию — `max(recall.max_timeout_ms, recall.timeout_ms)`. Без
  идей — строка-уведомление (очередь пуста, решение не задано, нет права записи, режим
  `propose`; с 0.0.13-m6.6 решение передано, но не в области: «нет доступа к решению (см.
  warnings)» или «решение <GUID> не зарегистрировано на сервере»). В режиме `review` у `session_start` раздел `### Идеи на разбор` и строка «План из
  идей: …», у `prompt` подсказка к идее `new` — с `reason: idea_review`.
- **Лента для WebUI**: `GET /spaces/{space}/entries/counts?kind=<вид>` → `{<статус>: n}` — все
  статусы вида, нулевые тоже, с фильтрами ленты (`area`, `tag`, у идей `origin` и `priority`, у
  задач `from_idea`); без `kind` или у вида без статусов — 400, фильтр не своего вида — 422.
  `from_idea=1` у `kind=task` — только задачи с системным ребром `derived_from` на живую идею.
  У задачи из идеи в `GET` и в ленте — `idea {id, title, status, space_id}` (исходная идея) и
  `ideas` (все, по времени ребра); участнику общего решения — только идеи пространства решения.
  У принятой идеи в ленте — `task {id, title, status}`.
- **MCP**: `memory_update_entry {id: "w:…", action: "review", outcome, summary, missing?, basis?,
  similar?, task?, idempotency_key?}` и `memory_recall {event: "idea_review", limit?}`;
  инструментов по-прежнему 11.
