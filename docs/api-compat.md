# Совместимость API `/api/v1` и возможности сервера

Документ для разработчиков собственных клиентов ZeroAIMemory: агентов, которые ходят в REST
`/api/v1` или в MCP `/mcp` напрямую, без `zam` и его хуков. Он отвечает на два вопроса: что
сервер обещает не ломать и как клиент узнаёт, что умеет конкретный сервер.

Введён в M6 (`0.0.11-m6`, задача 19) по запросам проекта zero-agent
([CR-9](research/2026-11-06-zero-agent-memory-requests.md), часть; ответ —
[`…-answer.md`](research/2026-11-06-zero-agent-memory-requests-answer.md)). Схема OpenAPI —
этап M7.

## Правило совместимости

- **Без смены версии пути** (`/api/v1`) сервер может:
  - добавлять маршруты, необязательные поля запроса и поля ответа;
  - добавлять значения в поля-перечни ответа (`warnings`, `reason`, `kind` …);
  - добавлять строки в `features` (раздел ниже).
- **Только в `/api/v2`**: удалить маршрут или поле, сделать необязательное поле обязательным,
  поменять смысл, тип или единицы существующего поля, поменять код ответа существующего случая
  успеха.
- **Клиент обязан**: пропускать неизвестные поля ответа и неизвестные строки `features`, не
  полагаться на порядок полей JSON и на текст `title`/`detail` ошибок (смысл ошибки — HTTP-код и
  поле `type` problem+json).
- **Тела запросов** большинства маршрутов разбираются строго (`deny_unknown_fields`):
  неизвестное поле — 400. Поэтому новое поле запроса клиент шлёт, только убедившись по
  `features`, что сервер его знает. Исключение — `POST /recall`: неизвестные поля его тела
  игнорируются (клиент хуков бывает новее сервера).
- **Ошибки** — `application/problem+json` с `type`, `title`, `status`, `detail`.
- **Ответы MCP** — Markdown для агента; стабильный контракт — у REST и у `format: "json"` MCP
  (JSON ответа REST в тексте).

## Как узнать возможности

`GET /api/v1/health` (без аутентификации) →
`{status, version, git, features, token_counter, tokenizer_id, uptime_s}`.

- `features` — массив строк: каждая строка — возможность этой сборки. Поля нет у выпусков до
  M6 (`v0.0.10-m5.7` и раньше отдают только `status, version, git, uptime_s`): у них нет ни
  одной возможности из таблицы ниже.
- Возможность определяется **только** по `features`, без пробных запросов и без сравнения
  версий: ветка с частью M6 называет себя прежней версией (`0.0.10-m5.7`), а флаг появляется
  в той же сборке, что и функция.
- Флаг, однажды появившись, не удаляется, пока жив `/api/v1`.

| `budget` | M6 §4.2 | `budget_tokens` в `/search` и `/read` считается счётчиком выдачи (`token_counter`), карточки поиска v2 с порогом `search.brief_min_rel`. |
| `snippet` | M6 §4.3 | Фрагмент под подсказкой `/recall` (`recall.snippet_tokens`). |
| `focus` | M6 §6 | Фокусное чтение: `items[].focus` и `tier: "focus"` в `POST /read` и `memory_read`. |
| `digest` | M6 §8 | Дайджест `session_start` по разделам: Rules — резерв сверх бюджета, `recall.digest_entries`, захваченные задачи `open`. |
| `hint_thresholds` | M6 §9 | Пороги подсказок: `recall.prompt_min_score_fts`, `recall.post_tool_coverage`. |

Правило для разработки сервера: задача, которая вводит возможность или ключ конфигурации,
добавляет строку в `FEATURES` (`crates/zam-server/src/api/health.rs`) и строку в эту таблицу;
тест `boot::health_features_documented` сверяет таблицу с `FEATURES` в обе стороны. Ключи
конфигурации, которые переопределяет замер, помечаются тем же флагом в
`xtask/src/eval/caps.rs` (`KEYS`).

## Явная сессия

- REST: `X-Zam-Session: <id>` или `session_id` в теле `/search`, `/read`, `/recall`,
  `/feedback` (тело сильнее заголовка, как и прежде).
- MCP (`mcp_session_arg`): заголовок `X-Zam-Session` или аргумент `session_id` у
  `memory_recall`, `memory_search`, `memory_read`. Оба заданы и совпадают — эта сессия; оба
  заданы и различаются — ответ-ошибка `400` (запрос в REST не уходит, учёт ответа — в сессии
  заголовка). Учёт выданного (`session_tokens`, событие `mcp`), отметки «уже выдавалось» и
  счётчик записей идут в эту сессию.
- Без явной сессии MCP подставляет последнюю сессию хуков только для счётчика записей, а
  выданное учитывает в `GET /sessions/unattributed`.

## Срок `/recall` (`recall_timeout`)

`POST /recall {…, timeout_ms}` — срок сбора подсказок этого запроса, мс. Без поля действует
`recall.timeout_ms` сервера (200: бюджет хуков). Допустимо 1..=`recall.max_timeout_ms`
(2000), иначе 400. Нативный агент, который может подождать, шлёт, например, `timeout_ms: 1000`
и получает полный дайджест там, где хук получил бы собранное и `warnings: ["recall timeout"]`.

## Идемпотентность записи (`idempotent_nodes`)

`Idempotency-Key: <ключ>` (1–200 печатных символов; пустой — как без заголовка):

| Маршрут | Первый запрос | Повтор с тем же ключом и тем же запросом |
|---|---|---|
| `POST /spaces/{space}/entries` | 201 | 200, та же запись |
| `POST /entries/{id}/supersede` | 201 | 200, та же новая запись |
| `POST /nodes` | 201 | 200, тот же узел |
| `PUT /nodes/{id}` | 200 | 200, без новой ревизии (прежний `If-Match` не даёт 409) |
| `PATCH /nodes/{id}` | 200 | 200, без второй правки (два `append` — одна вставка) |

- Повтор отдаёт **текущее** состояние записи или узла (как у записей журнала с M3): если
  после первого запроса цель правили, в ответе — последняя ревизия.
- Тот же ключ с другим запросом (другое тело, другая цель, другой метод) — 422
  `/problems/idempotency-mismatch`, ничего не записано. Сверяются: у `POST /nodes` —
  пространство, путь, вид, `content`, `l0`; у `PUT` — узел, `If-Match`, `content`, `l0`; у
  `PATCH` — узел, `base_rev`, `ops`. `message` в сверку не входит (как у записей журнала).
- Цель по ключу удалена в корзину — 409; восстановите её или возьмите новый ключ.
- Ключ действует в границах автора (пользователь токена) и базы владельца пространства;
  хранится, пока жива цель (как ключ записи журнала), — отдельного срока нет.
- Параллельные запросы с одним ключом: сверка ключа и запись — одна транзакция единственного
  писателя базы, поэтому запись одна, остальные получают повтор.
- Неуспешный запрос (400, 409, 413, 422, 428 и др.) ключ не занимает: повтор выполнится заново.
- `POST /nodes` папки (`kind: folder`) с ключом — 400: ключ есть только у заметок.
- Без ключа всё как раньше: повтор `PATCH append` с тем же `base_rev` допишет текст ещё раз
  (`append` и `prepend` применяются к текущему тексту при любом `base_rev` не новее текущей).
- MCP: `memory_write {…, idempotency_key}` и `memory_log {…, idempotency_key}`.
