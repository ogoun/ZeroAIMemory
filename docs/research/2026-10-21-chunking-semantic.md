# Семантична ли нарезка заметок на чанки; сравнение с ZeroTranslator

- Дата: 2026-10-21. Ветка `m3-journals`, коммит `c908977`.
- Метод: только чтение кода, ТЗ, журналов и результатов eval. Код не запускался. Утверждения про поведение кода, которые тестом не проверены, помечены «по чтению кода».
- ZeroTranslator (`H:\Desktop\TRANSLATOR\ZeroTranslator`) читался только для чтения. Это не git-репозиторий, поэтому ссылки на него — путь и строки.

## 1. Вывод

Нарезка в ZeroAIMemory **структурно-семантическая, но не embedding-семантическая**.

- **Где границы определяет смысл.** Крупные границы задаёт структура документа: секции H1–H3, блоки AST (абзац, код, таблица, список, цитата/callout), предложения. Это смысловые границы, которые разметил сам автор.
- **Где решает счётчик токенов.** Внутри секции счётчик решает, на какой из допустимых границ закрыть лист. При этом все границы между блоками для упаковщика равноценны.
- **Чего нет.** Сходство соседних фрагментов (косинус эмбеддингов, лексическая связность) нигде не учитывается.
- **Длинный абзац без структуры.** Делится по предложениям, а предложения жадно пакуются по токенам. Граница проходит по предложению, но место выбрано счётчиком.

Менять подход на embedding-based semantic chunking не нужно. Это следует из литературы, из стоимости инференса на CPU и из результатов M2. Но есть дешёвые улучшения без инференса: сила границы при упаковке и учёт H4–H6. Кроме того, нынешний eval почти не чувствителен к нарезке, и его нужно доработать. Обе вещи предлагаются задачей M3 (§5).

## 2. ZeroAIMemory: как режется сейчас

Код: `crates/zam-markdown/src/chunk.rs` (`chunk_note`), `sentences.rs` (`split_sentences`), `levels.rs` (L1), `doc.rs` (секции). Обвязка в хранилище: `crates/zam-store/src/nodes/chunks.rs` (`note_chunks`, `context_prefix`, `rebuild_chunks`). Пороги: `[index] chunk_*` в `crates/zam-server/src/config.rs:312–396`. По умолчанию `ChunkParams` = 300/500/800/100/1 (`chunk.rs:80–90`).

| Этап | Где | Граница | Чем определяется |
|---|---|---|---|
| Секции | `doc.rs:225` (только `level <= 3`) | H1–H3; H4–H6 остаются внутри секции | структура |
| Склейка коротких секций | `Chunker::groups`, `chunk.rs:376–438` | секция < `merge_below` (100) склеивается со следующим соседом того же родителя, пока сумма ≤ `target_max`; если соседа нет — с предыдущим | структура (родство) + токены |
| Блоки | `top_blocks`, `chunk.rs:249–304` | блоки верхнего уровня comrak: абзац (`prose`), fenced-код (повторяется строка ограждения), таблица (повторяется шапка), список/цитата (режутся по элементам), callout/alert (повторяется маркер) | структура |
| Дробление больших блоков | `atom_units` / `refine`, `chunk.rs:460–553` | абзац > `target_max` — по предложениям, затем по словам и символам; блок > `hard_max` — по элементам, строкам, словам, символам | структура → токены (фолбэк) |
| Предложения | `sentences.rs:1–75` | UAX #29 плюс правила: сокращения, инициалы, версии, URL/пути, inline-код; мягкий перенос строки — не граница | лингвистика |
| Упаковка в листы | `pack`, `chunk.rs:587–647` | жадно: цель `ceil(T / ceil(T/target_max))` в пределах [min, max]; лист закрывается, когда следующая единица перешагнула бы цель больше чем наполовину; короткий хвост приклеивается к предыдущему листу | **только токены** |
| Перекрытие | `add_overlap`, `chunk.rs:674–704` | последние `overlap_sentences` (1) предложений предыдущего листа, только если тот кончается абзацем, и только внутри группы | токены + предложения |
| L1 секции / заметки | `chunk.rs:183–216`, `levels.rs` | оглавление + первое предложение секции, ≤ 300 токенов; `section` — у H1–H2 из ≥ 2 листов | структура (иерархические «виртуальные чанки») |
| `context_prefix` | `zam-store/src/nodes/chunks.rs:159–176` | `[space/path] имя > H1 > H2 > H3 \| теги`, входит в эмбеддинг и FTS | детерминированный аналог Contextual Retrieval (ТЗ §8.2 п. 6) |

Что следует из таблицы:

- **Только по токенам решается:**
  - в какой момент закрыть лист внутри секции или группы;
  - где резать длинный абзац (между какими предложениями);
  - где резать длинный блок (между какими строками или пунктами);
  - фолбэк по словам и символам для «стены» без пунктуации.
- **Семантической близости нет нигде.** Embedding-модель при нарезке не используется (ТЗ §8.3 применяет эмбеддинги только для выбора L0 по центроиду). Лексической связности (TextTiling и т. п.) тоже нет.
- **Длинный абзац без структуры** делится на предложения (`Gran::Sentences`). Предложение длиннее `hard_max` дробится дальше по словам. Затем предложения пакуются жадно, по 300–500 токенов. Граница может пройти посреди мысли, если предложения о двух темах идут подряд. Перекрытие в 1 предложение частично сглаживает разрыв.
- **Дефект по чтению кода (не воспроизведён тестом): висячий заголовок H4–H6.**
  - Строка `#### Подзаголовок` — отдельный блок верхнего уровня, не `prose` (`chunk.rs:299`, ветка `_ => {}`).
  - Сценарий: P1 = 310 токенов, затем H4, затем P2 = 300, цель около 450. Лист закрывается после H4 (`est ≥ target_min`, а P2 переполняет `target_max`). Итог: первый лист кончается заголовком, а его содержимое уходит в следующий лист без этого заголовка.
  - `heading_path` и `context_prefix` знают только H1–H3. Последний лист кончается не абзацем, поэтому перекрытия тоже нет.
  - Та же беда грозит фразе-вводу вроде «Пример:» или «Выполните:» перед блоком кода или списком.
  - Тестов с H4 в `crates/zam-markdown/tests/chunk.rs` нет. В корпусе eval нет ни одного `####`.

### Что показал eval M2 (`eval/results/2026-10-19-grid-bge-m3-fp16.md`, журнал `docs/plans/2026-10-19-m2-index-ml-log.md:89–127`)

| Конфигурация | Δ nDCG@10 [95 % парный бутстреп] | Δ recall@5 |
|---|---|---|
| чанки 150–300 | +0,007 [+0,001…+0,015] (поверх `w_fts=0.25` — +0,004 [−0,004…+0,012]) | +0,010 |
| чанки 500–800 | +0,002 | +0,005 |
| перекрытие 0 / 2 | +0,002 / 0,000 | **+0,000 / +0,000** |

Нулевая разность recall@5 при смене перекрытия — признак того, что **eval почти не чувствителен к нарезке**:

- релевантность размечена на уровне заметки (`expect = [note]`), поиск группирует хиты по заметке;
- медиана заметки — 324 слова (по `eval/corpus`: минимум 120, максимум 1146), и большинство заметок укладывается в 1–2 листа;
- длиннее 600 слов только 32 заметки из 160;
- заголовков H4+ и длинных бесструктурных абзацев в корпусе нет.

Поэтому вывод M2 «пороги подтверждены» верен для этого корпуса. Качество границ внутри длинных заметок он не проверяет.

## 3. ZeroTranslator: как режется там

Там две независимые нарезки.

### 3.1. Фрагменты для перевода — `translator/core/chunker.py`

- **`segment()` (стр. 91–134), абзацы — неделимые единицы.**
  - Бюджет в словах: цель 1200, минимум 800, максимум 1700. Значения по умолчанию заданы в CLI, `translator/translate.py:150–155`.
  - Когда буфер ≥ цели, разрез ставится на ближайшей «сильной» границе сцены (score ≥ 2). При переполнении максимума разрез обязателен.
- **`_scene_break_score()` (стр. 65–88), эвристика силы границы:**
  - разделитель `***`, `---` или `[break]` — 3;
  - абзац начинается с маркера смены времени или места («Later,», «Meanwhile», «Тем временем», «На следующ…», «Через», «Вечером») — 2;
  - смена диалог ↔ повествование — 1 (на разрез не влияет, порог 2).
- **Чего нет:** эмбеддингов и перекрытия. Языки — ru/en (регулярки диалога и местоимений). `detect_tags` размечает POV и долю диалога.
- **Побочные наблюдения (для владельца, не по нашей задаче):**
  - Хвост главы короче `min_words // 2` (400 слов) отбрасывается (стр. 128–133). Глава короче 400 слов не даёт ни одного фрагмента. Судя по циклу перевода (`translate.py:369`, `567`), такой текст не переводится; нужно проверить.
  - Докстринг ссылается на `corpus_builder/core/fragments.py`, которого нет.
  - Абзац длиннее `max_words` не режется.

### 3.2. Чанки для поиска (глоссарий) — `glossary_builder/glossary/chunking.py` и `segmentation.py`

- **Сегменты L0 (`segmentation.py:40–227`).** Главы от загрузчика, сцены — по регуляркам `CorpusProfile.scene_break_patterns`.
  - Если регулярки ничего не нашли и включён `enable_scene_cpd`, работает `scene_detect.py:51–126`. Абзацы эмбеддятся (`paraphrase-multilingual-mpnet-base-v2` или bge-m3, `embeddings.py:27–33`). Ряд векторов размечается change-point detection: `ruptures.KernelCPD(kernel="rbf")`, `pen=8.0`, ≥ 3 абзацев между границами.
  - Пограничные кандидаты проверяет LLM: «новая сцена?» — сравнивается абзац до и абзац после.
  - По умолчанию выключено: `config.py:79` (`enable_scene_cpd = False`) с комментарием про стоимость GPU и задержку.
- **L1, семантический (`chunking.py:71–124`).** `chonkie.SemanticChunker` на локальном эмбеддере: `threshold = 0.68` (`L1_THRESHOLD`, стр. 39), `chunk_size = 900`. Соседние предложения объединяются, пока сходство не провалится ниже порога.
  - Включается только для сегмента длиннее `L1_MAX_CHARS = 2400` символов (≈ 600 токенов). В ТЗ глоссария указано «> 8K токенов» (`docs/glossary_builder/TZ_glossary.md:396`) — расхождение кода и ТЗ.
  - Переросший L1 режется по `\n\n`.
  - Если эмбеддера нет — фолбэк на `SentenceChunker`; при ошибке — по абзацам.
- **L2, поисковые чанки (`chunking.py:127–145`).** `chonkie.TokenChunker` на токенизаторе `gpt2` (фолбэк `cl100k_base` или символы): 400 токенов, перекрытие 48.
  - Это **чисто токенная нарезка** с разрезом посреди предложения и даже слова. В векторный индекс попадают именно L2.
  - Токенизатор чужой (не bge-m3), поэтому бюджет считается неточно.
- **L3, Contextual Retrieval (`chunking.py:149–168`, `226–231`).** LLM пишет одно предложение (≤ 30 слов) о том, кто, где и что делает. Контекст — ±2400 символов вокруг. Предложение ставится перед L2 при эмбеддинге (`iter_l2_chunks`, стр. 257–277). Предел — `MAX_CONTEXT_CHUNKS = 2500` вызовов.
- **Замеров качества нарезки не найдено** (поиск по `docs/`, `glossary_builder/docs/`). Ссылка на «+35–50 % recall» в ТЗ глоссария — это цифра Anthropic, а не собственный замер.

| Аспект | ZeroAIMemory | ZeroTranslator (поиск) | ZeroTranslator (перевод) |

| Итоговый индексируемый чанк | по границам блоков и предложений | **по токенам gpt2, посреди предложения** | — |
| Сила границы | нет (все границы равны) | нет на L2 | **есть** (`_scene_break_score`) |
| Код, таблицы, списки | неделимы, повтор шапки | не различаются | не различаются |

| Контекст чанка | детерминированный префикс-путь | LLM-предложение (L3) | — |
| Иерархия | leaf / section L1 / note L1 / folder | L0 / L1 / L2 (+L3) | — |
| Замер на eval | да (сетка M2, бутстреп) | нет | нет |

Итог сравнения:

- Встроенная «семантика» ZeroTranslator сосредоточена на L1, а в индекс попадают L2, нарезанные по токенам. На уровне индексируемого чанка нарезка ZeroAIMemory аккуратнее: границы блоков и предложений, неделимый код и таблицы, точный токенизатор модели.
- Переносить стоит две идеи. Первая — **ранжирование силы границы** из `translator/core/chunker.py` («после цели резать на ближайшей сильной границе»). Вторая — **CPD по ряду векторов** из `scene_detect.py`, как опциональный путь для длинных бесструктурных текстов: вложения, расшифровки, длинные записи журналов.

## 4. Современные подходы и применимость

- **Semantic chunking по провалу косинуса соседних предложений** (Kamradt, LangChain `SemanticChunker`, chonkie).
  - NAACL Findings 2025 «Is Semantic Chunking Worth the Computational Cost?» ([arXiv:2410.13070](https://arxiv.org/abs/2410.13070), [блог Vectara](https://vectara.com/blog/is-semantic-chunking-worth-the-computational-cost)): на реалистичных данных фиксированная нарезка не хуже или лучше. Выигрыш семантической появлялся в основном на искусственно склеенных документах.
  - Отчёт Chroma «Evaluating Chunking Strategies for Retrieval» (Smith, Troynikov, 2024; цифры по вторичным пересказам): recall у ClusterSemanticChunker около 200 токенов — ~89 %, у Recursive splitter — 88,5 %, у Kamradt-чанкера — худшая точность.
  - Для нас нужен эмбеддинг каждого предложения: ещё ~1× проход по корпусу. При 700 ток./с на CPU это вдвое удлиняет индексацию, которая и так не выполняет цель §17 на CPU. Как постоянный путь — **не оправдано**.
- **Late chunking** ([arXiv:2409.04701](https://arxiv.org/abs/2409.04701)): вся заметка прогоняется через модель, токенные векторы пулятся по границам чанков. Дала около +3 % на BEIR у моделей с mean-pooling.
  - Dense-вектор bge-m3 обучен на CLS. Пулинг по фрагменту — режим, на котором модель не училась; это уже отмечено в исследовании 03 (`docs/research/2026-10-17-03-stack-rag-language.md:33`).
  - Внимание на длине 8192 квадратично, по памяти и времени это дороже наших коротких проходов.
  - Кэш `embeddings` по `embed_key` ломается: вектор чанка зависит от всей заметки, правка одного абзаца инвалидирует все чанки.
  - **Не брать.**
- **Contextual Retrieval** ([Anthropic, 2024](https://www.anthropic.com/news/contextual-retrieval)): −35 % неудачных извлечений с контекстом, −49 % с BM25.
  - У нас детерминированный аналог — `context_prefix`. LLM в сервере нет, поэтому вариант ZeroTranslator (LLM-предложение) неприменим.
  - Дешёвое расширение: добавить в префикс **L0 заметки**, то есть одно предложение (agent, manual или auto). Это «контекст документа» без LLM, примерно +20–50 токенов на чанк (+5–15 % к инференсу). Проверять на eval.
- **Иерархические чанки** (RAPTOR, [arXiv:2401.18059](https://arxiv.org/abs/2401.18059); small-to-big) уже есть: L1 `section` и `note`, `folder`, группировка по заметке.
- **Лексическая сегментация без модели** (TextTiling, Hearst 1997; C99) даёт связность соседних окон через пересечение основ слов.
  - `rust-stemmers` уже есть в зависимостях (eval), токенизатор bge-m3 — тоже. Можно брать косинус sparse-мешков стемов или токен-id без инференса: дёшево, Rust, без новых тяжёлых зависимостей.
  - Применять только как тай-брейкер внутри длинного абзаца или серии абзацев без структуры.

## 5. Предложение для плана M3

**Задача «Границы чанков: сила границы, H4–H6, eval нарезки»** (одна задача, три шага; без нового инференса и новых тяжёлых зависимостей).

### Шаг 1. Eval, чувствительный к нарезке (сначала мерило)

1. Добавить в корпус 20–30 длинных заметок (2–5 тыс. слов, ru и en) с H4–H6, длинными бесструктурными абзацами, вводными фразами перед кодом и списками, сменой темы внутри секции.
2. Добавить 40–60 запросов к фактам из середины этих заметок, с полем `evidence = "<дословная подстрока>"`.
3. Новая метрика уровня чанка: **chunk-recall@5** — доля запросов, у которых среди топ-5 листов есть лист, целиком содержащий `evidence` (без учёта перекрытия), и **chunk-nDCG@10**. Плюс прежние recall@5 и nDCG@10 по заметкам.
4. Проверка `eval --check`: `evidence` дословно есть в заметке.
5. Прогнать базу и убедиться, что сетка overlap 0/1/2 теперь даёт ненулевые разности. Если не даёт — набор ещё слабый.

### Шаг 2. Упаковка с силой границы (`chunk.rs::pack`)

1. У каждой единицы — оценка силы границы **перед** ней:
   - перед H4–H6 — 4;
   - `---` или thematic break — 4;
   - между абзацами — 2;
   - перед или после кода, таблицы, списка — 2;
   - между предложениями — 1;
   - **после** заголовка H4–H6 или после абзаца, оканчивающегося «:», — штраф −5 (резать нельзя);
   - внутри слова — фолбэк, как сейчас.
2. Вместо жадного закрытия — выбор разреза динамическим программированием по точкам-кандидатам группы, по аналогии с переносом строк Knuth–Plass: минимизировать Σ((len − goal)/goal)² − λ·strength. Жёсткие ограничения: `hard_max`, `target_min` (кроме хвоста). Сложность O(n·k), где k — число единиц в окне `hard_max`; это дёшево. λ подбирается сеткой (0 = текущее поведение).
3. H4–H6 входят в `heading_path` листа (`H1 > H2 > H3 > H4`) и тем самым в `context_prefix`. Секции остаются по H1–H3, ТЗ §8.2 п. 2 не нарушается, нужно лишь уточнение формулировки.
4. Опционально, за флагом `[index] chunk_cohesion = false`: в длинном абзаце или серии абзацев без структуры добавить к силе границы лексическую связность (TextTiling по стемам `rust-stemmers` или по sparse-мешку токенов bge-m3; без инференса).
5. Тесты (TDD):
   - `h4_heading_never_ends_leaf`;
   - `colon_intro_stays_with_block`;
   - `dp_matches_greedy_when_lambda_zero`;
   - свойство `src[range] == text`;
   - фаззинг `chunk_note` (уже есть) — без паник и в пределах `hard_max`.

### Шаг 3. Префикс с L0 (эксперимент, за конфигом)

`context_prefix` + `" — " + L0` (≤ 50 токенов) за ключом `[index] chunk_prefix_l0`. Меняются `embed_key` и FTS-текст, нужен `reindex --full`. Расход токенов индексации — в отчёт.

### Как мерить и что принять

- Конфигурации сетки (`eval/grid-chunking.toml`):
  - база;
  - λ ∈ {0,5; 1; 2};
  - H4-путь вкл./выкл.;
  - cohesion вкл.;
  - prefix-L0 вкл.;
  - 150–300 поверх лучшей.
- Парный бутстреп по запросам, 95 %, разность с базой. Как в M2, прогон на fp16 CUDA, финальная проверка — int8 CPU.
- **Критерий принятия:**
  - нижняя граница 95 % интервала Δ chunk-recall@5 > 0 на новом подмножестве длинных заметок;
  - на всём наборе нижние границы Δ nDCG@10 и Δ recall@5 по заметкам ≥ −0,01 (та же планка, что у гейта int8, §18.2);
  - число чанков и токенов индексации ±5 % от базы (prefix-L0 — отдельной строкой).
- Шум свежего индекса — ±0,003 (журнал M2). Если эффект в пределах шума, оставить λ = 0 и закрыть задачу выводом «нарезка по структуре достаточна» — но с исправлением висячего H4, которое принимается по тесту, а не по eval.
- Embedding-based semantic chunking и late chunking в M3 **не включать**: обоснование в §4.
- Если позже понадобится нарезка вложений или расшифровок без структуры (TXT, PDF без заголовков), CPD по векторам абзацев в духе ZeroTranslator `scene_detect.py` можно сделать вторым проходом на GPU по флагу и мерить тем же eval.
