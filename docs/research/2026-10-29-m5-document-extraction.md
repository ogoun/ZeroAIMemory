# Исследование M5. Извлечение текста и просмотр документов (DOCX, XLSX, PPTX, PDF)

Дата: 2026-10-29. Цель — выбрать библиотеки и схему безопасности для этапа M5 «Документы» (ТЗ §19, §5, §15.3, §16, §9.3 `locator`).
Пометка «(по знаниям)» — не проверено по источникам в этой сессии. «Не измерено» — цифры нужно снять на `eval/docs/` (корпуса документов в репозитории пока нет: `eval/corpus/` содержит только `en`, `ru`).
Правило свежести: берём версию не новее 2026-10-15 (14 дней до даты исследования). Данные о версиях и датах — из crates.io API, npm registry, GitHub API и RustSec на 2026-10-29.

## 0. Что уже есть в проекте

- ТЗ §5: DOCX/PPTX — `zip` + `quick-xml`; XLSX/XLS/ODS — `calamine` 0.36; PDF — `pdfium-render` 0.9, `pdf_oxide` — кандидат на A/B. Отклонены `pdf-extract`, `lopdf`, `mupdf` (AGPL).
- `deploy/pdfium.toml`: pdfium закреплён на `chromium/8100` (2026-10-12) для Windows x64 и Linux x64; в комплект уже входит `pdfium.dll` / `libpdfium.so` (§16.2). Размер архивов: 3,9 МБ (win-x64) и 3,8 МБ (linux-x64) в `.tgz`.
- `Cargo.toml`: `zip = "9"` (deflate), в `Cargo.lock` — 9.0.5; `quick-xml` и `calamine` как прямые зависимости пока не подключены.
- `crates/zam-store/src/blobs.rs`: блобы — `<data_dir>/blobs/<user>/<aa>/<sha256>`, запись через `.incoming/*.part`, sha256 на лету, лимит `limit`; `attachments` (узел, sha256, имя, MIME, размер). Производные — `previews/<user>/<sha256>/…` (§6.1). Извлечение текста естественно привязывается к `sha256` блоба: ключ кэша = `sha256` + версия экстрактора.
- Рабочий toolchain 1.99.1, MSRV проекта 1.92.
- `/read` с `locator` сейчас отвечает 422 `locator-unsupported` (§9.3); чанки вложений должны получить `level=attachment` и `locator` (§8.2, п. 8).

### 1.2. DOCX и PPTX

**Рекомендация: своя реализация на `zip` + `quick-xml` (как в ТЗ §5), крейт `zam-docs`.**

Обоснование:
- Нужны не просто текст, а структура для `locator` и `heading_path`: DOCX — стили `Heading1…9` (через `word/styles.xml`, `w:outlineLvl`, `w:pStyle`), абзацы, таблицы (`w:tbl` → строки как блоки с шапкой), списки, сноски, колонтитулы (по желанию), текстовые рамки; PPTX — номера слайдов по порядку `ppt/presentation.xml` (не по имени файла `slideN.xml`), заголовок слайда (placeholder `title`), текст, таблицы, заметки докладчика (`notesSlides`). Это 800–1200 строк кода, поддерживаемых нами, и ровно тот набор тегов, который нужен.
- Не нужны запись, правка, форматирование, DOC/PPT (бинарные CFB), конвертация — а `office_oxide` это включает (`create.rs`, `edit.rs`, `convert_*`, `cfb`, `doc`, `ppt`, `ffi.rs`, `python.rs`, `wasm.rs`): большая поверхность атаки и сопровождения ради малой части функций.
- `office_oxide` молодой (первый коммит 2026-03-01, версия 0.1.x, выпуск каждые 2–10 дней, исправления вида «крафтовый файл 254 КБ занимал 6 с и 700 МБ» — то есть защиту от DoS до сих пор доделывают). IR у него богатая (стили абзацев, таблицы, колонтитулы, `PageSetup`, текстовые рамки), лимит вывода текста есть (`limits::set_max_text_chars`, 256 Mi символов по умолчанию), корпус проверки — 6062 файла (самоотчёт). Его 1,07 млн загрузок в основном транзитивные (зависимость `pdf_oxide`).
- Взаимная проверка: `office_oxide` держим как dev-зависимость тестов `eval/docs/` — сравниваем наш текст с его (оракул), без попадания в релиз.

Что делаем сами:
- чтение `[Content_Types].xml`, `_rels/*.rels`, порядок слайдов и листов по отношениям, а не по именам файлов;
- потоковый разбор (`quick_xml::Reader`, события, без DOM), счётчик глубины, лимиты (см. §3);
- нормализация: `w:tab` → `\t`, `w:br` → `\n`, `w:noBreakHyphen`, `w:sym` — пропуск, удалённые правки (`w:del`) не включать, вставленные (`w:ins`) включать; скрытый текст (`w:vanish`) — не включать;
- перевод абзацев и таблиц в Markdown-подобные блоки, чтобы переиспользовать чанкер `zam-index` (таблицы/списки не разрываются, §8.2).

Запасной вариант: `office_oxide` (взять версию 0.1.15 или новее после 2 недель), если на `eval/docs/` наша реализация теряет более X % текста; для устаревших `.doc`/`.ppt`/`.xls` — единственный известный чисто-Rust кандидат (вне M5).

### 1.3. XLSX / XLS / ODS

**Рекомендация: `calamine` 0.36.1.** Лицензия MIT, чистый Rust, 16,6 млн загрузок, поддерживает xlsx/xlsm/xlam, xls, xlsb, ods (https://docs.rs/calamine/0.36.1/calamine/). Версия 0.37.0 вышла 2026-10-18 и по правилу доступна с 2026-11-01.
- Locator: имя листа + диапазон `A1:K200` (блоки строк с шапкой, §8.2).
- Минусы: тянет `zip ^8.6` и `quick-xml ^0.41`, поэтому в графе будет две мажорные версии `zip` (8 и 9). Исправления RUSTSEC касаются только `extract()` на диск (мы им не пользуемся), так что риск мал; но надо учесть в аудите и ждать, когда calamine перейдёт на zip 9.
- Большие листы: общая строка (shared string), на которую ссылаются все ячейки, даёт «текстовую бомбу» (README `office_oxide` описывает ту же атаку); нужен свой потолок на число ячеек и суммарный размер текста независимо от библиотеки. Потоковое чтение листа — через `worksheet_cells_reader` (по знаниям; проверить на 500 тыс. строк), иначе весь лист грузится в память.
- Запасной вариант: свой разбор `xl/worksheets/sheetN.xml` + `sharedStrings.xml` на `quick-xml` (XLSX проще DOCX; ~400 строк), если calamine не уложится в память/время или навяжет дубль `zip`.
- CSV — через `csv` (по знаниям, уже тривиально), вне этого исследования.

### 1.4. PDF

**Рекомендация: `pdfium-render` 0.9.4 + pdfium chromium/8100 (как в ТЗ). Запасной вариант и объект A/B: `pdf_oxide` 0.3.78.**

Сравнение по критериям задания:

| Критерий | pdfium (`pdfium-render`) | `pdf_oxide` | Остальные чисто-Rust (`lopdf`, `pdf-extract`, `oxidize-pdf`) |
|---|---|---|---|
| Качество текста | эталон: движок Chrome; кодировки, ToUnicode, CID-шрифты, вертикальное письмо (по знаниям) | заявлено 99,5 % паритета с PyMuPDF/pypdfium2 на 3830 PDF (самоотчёт: README, не проверено независимо) | `pdf_oxide` приводит для `pdf_extract` 91,5 %, для `lopdf` 80,2 % (его же бенчмарк) |
| Порядок колонок | FPDFText отдаёт символы в порядке потока содержимого, не по колонкам; нужен собственный восстановитель раскладки по координатам символов (XY-cut) | встроен `ReadingOrder::ColumnAware` (XY-cut, v0.3.19) и `ReadingOrder::Structure` по Tagged PDF (v0.3.75, 2026-07-23); в выпусках 07-2026 чинят паники сортировки на сканах и вертикальном письме | нет |
| Кириллица | отлично (по знаниям) | поддержана через ToUnicode/кодировки; проверить на `eval/docs/ru` | — |
| CJK | отлично, вертикальный текст, предопределённые CMap (по знаниям) | `encoding_rs` для Shift-JIS/EUC-JP, режим tategaki; зрелость ниже, нужен eval | — |
| Сканы | текстового слоя нет → пустой текст, детектируем и помечаем | то же; есть опциональные `ocr`/`ml` через `tract`/`ort` | — |
| Скорость | миллисекунды на страницу (по знаниям), 500 страниц — порядка секунд; не измерено | 0,8 мс в среднем на файл, p99 9 мс (самоотчёт, малые файлы); на 500 страницах не измерено | `lopdf` быстр, но без извлечения |
| Память/безопасность | C++, регулярные CVE: heap buffer overflow в PDFium CVE-2026-2648 (02-2026), CVE-2026-4455 (03-2026), CVE-2026-6305/6306 (04-2026). Обновления через `pdfium-binaries` еженедельно. `pdfium-render` 0.9.4 (09-2026) исправил два double-free в обёртке | безопасный Rust, но unsafe в разборе шрифтов; паники и переполнение стека — реальные (`lopdf` RUSTSEC-2026-0187: рекурсия 10 000 уровней = SIGABRT, не ловится `catch_unwind`) | то же |
| Зависимости | `pdfium-render` + динамическая библиотека (уже в комплекте) | тяжёлое дерево по умолчанию: `nom`, `regex`, `taffy`, `image`, `brotli`, `ttf-parser` (помечен неподдерживаемым, RUSTSEC-2026-0192), `chrono`, `env_logger`, `office_oxide`, `serde_json`, `aes`, `sha2`; отключить ненужное фичами можно, но часть зависима безусловно; MSRV 1.88 | — |
| Размер | pdfium ≈ 3,9 МБ (.tgz), уже поставляется | прирост бинарника не измерен | — |

Почему pdfium остаётся основным: он уже в комплекте и в CI (манифест с хэшами), даёт лучшее качество на CJK/кириллице/нестандартных шрифтах и общий движок для миниатюр страниц. Цена — C++ в процессе и ежемесячная гонка с CVE (нужен регламент обновления `deploy/pdfium.toml`: раз в 2–4 недели, не новее 14 дней; при критическом CVE — вне очереди, это обоснованное исключение, фиксируем в ADR).

Почему `pdf_oxide` остаётся запасным: чистый Rust (нет нативной библиотеки, нет проблемы glibc-only, §16.4 п. 14), встроенная колоночная логика, но молодой (первый выпуск 2025-11-05, 78 версий за 11 месяцев), 309 открытых issue, один автор, почти все цифры — самоотчёт, а дерево зависимостей широкое. Решение «заменить ли» принимается по A/B на `eval/docs/` (метрики: доля извлечённых символов относительно эталона, порядок блоков в двухколоночных статьях, CJK, кириллица, время на 500 страниц, пиковая память).

Сканы без текстового слоя: OCR вне M5. В M5: детектор «страница без текста» (число символов на странице < порога при наличии изображений), статус `ocr_needed` в метаданных вложения, индексация по имени файла и подписи (§8.2). Для следующего этапа (OCR) кандидаты: `oar-ocr` 0.10.2 (2026-10-26, Apache-2.0; PP-OCRv6 на ONNX Runtime, но привязан к своей версии `ort` — у проекта `ort =2.0.0-rc.14`, возможен конфликт, проверить) или собственный конвейер на нашем `ort` с моделями PaddleOCR; `ocrs` 0.13.1 (MIT OR Apache-2.0) отклонён: только латиница (README), «ранний предпросмотр». Модели OCR — отдельные артефакты `models fetch`, как bge-m3.

Locator PDF: номер страницы (с 1) + при наличии метка страницы (`FPDF_GetPageLabel`, по знаниям); чанк не пересекает границу страницы (или хранит диапазон страниц `p.12-13`). Колонтитулы и номера страниц в тексте: эвристически убирать повторяющиеся строки сверху/снизу страницы (одинаковые на ≥ 50 % страниц) — делается нашим кодом поверх любого движка.

### 2.1. PDF в браузере против серверной растеризации

`pdf.js` 6.4.299 (https://www.npmjs.com/package/pdfjs-dist):
- лицензия Apache-2.0, зависимостей нет; расписание выпусков — раз в месяц (6.0.227 05-30, 6.1.200 06-27, 6.2.108 07-28, 6.3.289 08-29, 6.4.299 10-03);
- размер (jsDelivr): `pdf.min.mjs` 459 КБ, `pdf.worker.min.mjs` 1,26 МБ, CMap 1,17 МБ и стандартные шрифты 0,8 МБ (грузятся по требованию), `wasm/` (openjpeg 251 КБ, jbig2 104 КБ, qcms 97 КБ; `quickjs-eval.wasm` 469 КБ нужен только скриптам PDF — не поставляем); итого в WebUI около 2 МБ ядра + ленивые ресурсы;
- безопасность: CVE-2024-4367 (выполнение JavaScript через шрифты при `isEvalSupported: true`) исправлена в 4.2.67; в 6.x не воспроизводится, но всё равно задаём `isEvalSupported: false`, `enableScripting: false`, не поставляем `pdf.sandbox`, держим `pdfjs-dist` не старше актуального минора. Для WASM-декодеров CSP потребует `'wasm-unsafe-eval'` (в ТЗ §15 запрещён только `unsafe-inline` для скриптов, это не конфликт, но надо записать); без него pdf.js использует JS-фолбэки (`*_nowasm_fallback.js`, +445 и +152 КБ);
- поиск по тексту, масштаб, переход к странице по `locator` — штатные возможности;
- работает на клиенте, нагрузка и риск парсинга PDF переносятся с сервера в браузер пользователя (его песочница) — это плюс для безопасности сервера.

Серверная растеризация: нужна всё равно для миниатюр первой страницы (карточка вложения, §15.2) — `pdfium-render` уже есть. Для полного просмотра минусы: CPU сервера на 20 пользователей, кэш PNG на диске, нет выделения текста и поиска без текстового слоя. Решение: pdf.js — основной просмотр, серверный PNG — только миниатюры и режим «упрощённый просмотр» при отказе pdf.js.

### 2.2. DOCX и PPTX в браузере без внешних сервисов

- `docx-preview` 0.4.1 (https://github.com/VolodymyrBaydalka/docxjs, 2,1k звёзд, 100 открытых issue): сам `dist/docx-preview.min.js` 75 КБ; рендер в DOM, колонтитулы включены по умолчанию (`renderHeaders`), но пагинация и поля слабее, чем в Word; вёрстка «не пиксель-в-пиксель». Лицензия Apache-2.0; зависимость `jszip` 3.10.2 имеет двойную лицензию `(MIT OR GPL-3.0-or-later)` — в `LICENSES/` фиксируем выбор MIT.
- Безопасность вывода: ТЗ §15.2 допускает DOMPurify для превью DOCX. Практика: рендерить `docx-preview` в отсоединённый контейнер, пропускать `innerHTML` через DOMPurify и показывать в `<iframe sandbox>` без `allow-scripts`; в браузер отдавать только файл, уже прошедший серверные проверки лимитов (§3).
- `mammoth` 1.13.0: хорош для «читаемого» HTML, теряет оформление; 8 зависимостей. Только запас.
- PPTX: зрелого и проверенного клиентского просмотрщика не нашли. Кандидаты (все MIT, все молодые, фидельность — заявления авторов, не проверено): `pptx-glimpse` 5.3.1 (2026-09-21, SVG/PNG, `@resvg/resvg-wasm`), `PptxViewJS` 1.1.9 (2026-03-22, Canvas), `pptx-browser` 4.1.5 (2026-02-28), `slidecanvas` (тащит `next`, `react`, `fabric` — отклонён). Рекомендация: в v1 показывать текст слайдов (как в ТЗ §15.3), в v2 прогнать `pptx-glimpse` и `PptxViewJS` на `eval/docs/` и принять решение; серверной конвертации PPTX→PDF/HTML без LibreOffice нет, по ТЗ она запрещена.

## 3. Безопасность разбора недоверенных файлов

### 3.1. Zip (DOCX, XLSX, PPTX)

Факты из реестра уязвимостей (RustSec, 2026-10): `zip` — RUSTSEC-2025-0168 (симлинки при распаковке), RUSTSEC-2026-0367/0368/0369 (SUID/SGID, симлинки вне каталога, права через симлинки; исправлено в `>= 9.0.0`); все четыре касаются `extract()` на диск. Мы **никогда не распаковываем на диск** — читаем записи в память с лимитами. Дополнительно: `zip` 9.1.0 добавил `ExtractOptions::with_size_limit` и проверку согласованности заголовков, но только для `extract`; для чтения по записям лимиты наши.

Обязательные лимиты (значения — стартовые, в `[docs]` конфигурации):
- размер самого файла — лимит блоба (200 МБ, §10) и отдельно `docs.max_file_mb` (например, 100 МБ для извлечения);
- число записей архива ≤ 10 000;
- размер распакованной записи: XML-части ≤ 64 МБ, остальные не читаем вообще (читаем только нужные части по именам из `[Content_Types].xml` и отношений);
- суммарно распакованных байт ≤ 512 МБ, отношение распакованного к сжатому для записи > 1 МБ ≤ 200:1;
- читать только через `Read::take(лимит + 1)` и считать фактические байты: заявленный в заголовке размер не доверенный;
- отвергать зашифрованные записи, нестандартные методы (допустимы stored и deflate; в `Cargo.toml` уже `deflate` без остальных), записи с `..`/абсолютными путями/дубликатами имён (на диск не пишем, но дубликаты — приём обхода валидации);
- «перекрывающиеся записи» (бомба Фифилда, когда сотни записей указывают на одни и те же сжатые данные): защищает суммарный лимит фактически прочитанных байт, а не суммы заявленных размеров.

### 3.2. XML и XXE

- `quick-xml` не загружает внешние сущности и DTD и не разворачивает пользовательские сущности автоматически: `unescape` знает только пять предопределённых и числовые; неизвестная сущность — ошибка. Классический XXE невозможен, пока мы **не** используем `unescape_with` с собственным резолвером. Billion laughs также не срабатывает без резолвера. Открытый issue https://github.com/tafia/quick-xml/issues/1029 (2026-10-27, «Limit total entity expansion during attribute value normalization») — следить; у `quick-xml` нет встроенного лимита вложенности и токена.
- Правила: на событие `Event::DocType` в OOXML отвечать ошибкой `invalid-document` (в DOCX/XLSX/PPTX `<!DOCTYPE>` не бывает); не использовать `serialize`-DOM; потоковый разбор со своим счётчиком глубины (≤ 256), числом атрибутов на тег (≤ 256), числом `xmlns` (≤ 64) и длиной текстового токена; версия `>= 0.41` (RUSTSEC-2026-0194 — квадратичное время при проверке дублей атрибутов, RUSTSEC-2026-0195 — неограниченное выделение памяти на `xmlns` в `NsReader`); отключать проверку дублей атрибутов не нужно, достаточно версии с исправлением.
- Внешние ссылки (`TargetMode="External"`, `oleObject`, гиперссылки) не открываем и не резолвим: только извлекаем текст; сетевых запросов при разборе нет.
- Макросы (`vbaProject.bin`), встроенные OLE, DDE-поля Excel — игнорируем; в Excel значения, начинающиеся с `=`, `+`, `-`, `@`, при экспорте/показе в таблице не исполняются (browser просто текст) — защита от CSV-инъекции только если экспортируем в CSV.

### 3.3. Время, память, изоляция

1. Ограничения общие для всех форматов: тайм-аут разбора (например, 60 с на файл, 300 с на PDF в 500+ страниц), потолок суммарного текста (по умолчанию 64 Mi символов; для сравнения у `office_oxide` — 256 Mi), потолок числа чанков, число одновременных разборов ≤ 2 (семафор), приоритет ниже интерактивных запросов. Всё в `spawn_blocking`, не в async-исполнителе.
2. OOXML и XLSX (чистый Rust): в процессе, с кооперативной проверкой дедлайна каждые N событий и учётом выделенной памяти (счётчик байт на разобранные структуры). Паника — ловить `catch_unwind` (в workspace не должно быть `panic = "abort"` для этого пути; проверить профили).
3. PDF (pdfium): остановить вычисление нельзя, а повреждение памяти C++ и OOM обрушивают весь процесс, включая базу и очередь записи. Прямое следствие реестра CVE выше и случаев `lopdf` (стековое переполнение не ловится).
   - Вариант A: в процессе + семафор + тайм-аут «потерять результат». Не защищает от падения. Допустимо только для доверенных PDF.
   - Вариант B (рекомендуется): рабочий процесс — тот же бинарник, перезапуск себя как `zam-server doc-worker` на файл (или на пачку), обмен через stdin/stdout, ограничение памяти (Windows Job Object `JOB_OBJECT_LIMIT_PROCESS_MEMORY`, Linux `setrlimit(RLIMIT_AS)`/cgroup если доступно), тайм-аут с принудительным завершением, нулевая сеть (по возможности). Это не внешний сервис и не новая зависимость: механизм уже есть для Qdrant (`process-wrap`: Job Object и `PR_SET_PDEATHSIG`, §4.3). Требование «вещь в себе» сохраняется (один бинарник), но это решение владельца — **нужно подтверждение**.
   - Вариант C: заменить pdfium на `pdf_oxide` и остаться в процессе — снимает C++, но не снимает стековые переполнения/OOM (их нужно отдельно ограничивать размером стека потока и лимитами); для надёжности всё равно лучше B.
4. Браузерная сторона: файлы отдаются как `Content-Disposition: attachment` или в `<iframe sandbox>`/pdf.js; заголовки `X-Content-Type-Options: nosniff`, CSP из §15.

## 4. Итоговые рекомендации

| Формат | Основное решение | Запасное | Делаем сами / готовое |
|---|---|---|---|
| DOCX | `zip` + `quick-xml`, структура: заголовки, абзацы, таблицы | `office_oxide` ≥ 0.1.15 (также для DOC); после A/B | сами (≈ 1000 строк) |
| PPTX | то же: слайды по порядку из `presentation.xml`, заголовок слайда, текст, заметки | `office_oxide` | сами |
| XLSX / XLS / ODS | `calamine` 0.36.1; locator `Лист!A1:K200` | свой разбор XLSX на `quick-xml` | готовое + свои лимиты |
| PDF | `pdfium-render` 0.9.4 + pdfium chromium/8100, раскладка по координатам символов, рабочий процесс (вариант B) | `pdf_oxide` 0.3.78 по результатам A/B | движок готовый, раскладка и колонтитулы свои |
| Сканы PDF | M5: детектор + статус `ocr_needed` | отдельный этап: PaddleOCR на нашем `ort` (`oar-ocr` как образец) | — |
| Превью PDF | `pdf.js` 6.4.299 (клиент) + миниатюры pdfium (сервер) | серверные PNG-страницы | готовое |
| Превью DOCX | `docx-preview` 0.4.1 + DOMPurify + sandbox iframe | серверный HTML из нашей структуры; `mammoth` | готовое |
| Превью XLSX | JSON по листам из `calamine` | — | сами (UI) |
| Превью PPTX | v1 — текст; v2 — A/B `pptx-glimpse` / `PptxViewJS` | — | готовое при v2 |

Схема модуля `zam-docs` (предложение): трейт `Extractor { fn extract(&self, src: &mut dyn ReadSeek, limits: &Limits) -> Result<ExtractedDoc> }`, где `ExtractedDoc` — упорядоченный список `Block { kind: Heading(level)|Para|Table|List|Code, text, locator: Locator }`, `Locator ∈ { Page(n), Sheet{name, range}, Slide(n), Section(path) }`. Результат кэшируется по `sha256` блоба и версии экстрактора в `previews/` (или в БД), чанкер — общий с Markdown (§8.2). Выбор реализации PDF — за фичей/конфигурацией (`pdfium` / `pdf_oxide`), чтобы A/B не требовал переписывания.

## 5. Что нужно решить владельцу

1. Рабочий процесс (тот же бинарник, `zam-server doc-worker`) для разбора PDF — допускается ли по смыслу «вещь в себе, без внешних процессов»? Рекомендуется да; иначе остаётся вариант A или C.
2. Регламент обновления pdfium: фиксировать раз в 2–4 недели с исключением для критических CVE (нарушает правило «не новее 14 дней» в обратную сторону — нужно именно новее, чтобы закрыть уязвимость).
3. Состав `eval/docs/`: нужны DOCX/XLSX/PPTX/PDF на русском, английском и китайском/японском языках, двухколоночные статьи, сканы, PDF на 500 страниц, «враждебные» файлы (zip-бомба с перекрытием, глубоко вложенный XML, миллиард ссылок на общую строку XLSX).
4. Принять `'wasm-unsafe-eval'` в CSP WebUI для WASM-декодеров pdf.js (или отказаться от WASM ценой +0,6 МБ JS-фолбэков).
5. Дубли `zip 8` (через `calamine`) и `zip 9` в графе — принять до выхода `calamine` с `zip 9`.

## 6. Что не проверено

- Скорость и память на PDF в 500 страниц: цифры не измерены, нужен бенч на `eval/docs/` (pdfium против `pdf_oxide`).
- Качество порядка колонок и CJK на реальных документах: независимого сравнения pdfium и `pdf_oxide` за 2026 год не найдено; цифры `pdf_oxide` — самоотчёт.
- Фидельность `docx-preview` и PPTX-просмотрщиков на нашем корпусе.
- Репозиторий `oxidize-pdf` по ссылке crates.io не открылся (404), лицензия взята с crates.io.
- Версии на дату 2026-10-29 приведены по официальным API; для `oar-ocr` совместимость с `ort =2.0.0-rc.14` не проверялась.
