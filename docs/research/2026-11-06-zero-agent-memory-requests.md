# Предложения по доработке ZeroAIMemory от проекта zero-agent

**Кому:** разработка ZeroAIMemory (ZAM).
**От:** проект zero-agent, `H:\Documents\GitHub\ZeroAgent`.
**Дата и срез:** 2026-11-06, ветка `m6-token-economy`, HEAD `13b0bac` плюс незакоммиченная рабочая копия.

## Контекст

zero-agent — собственный агент на Rust, который работает с ZAM нативно как HTTP-клиент: без хуков, без `zam mcp`, с явной сессией `X-Zam-Session` на каждого агента и субагента. У него есть рой субагентов, которые одновременно читают и пишут в память, а также реестр переиспользуемых утилит в общем разделе.

**Как это получено.** Код и документы ZAM читались, сервер не запускался. Выводы о поведении получены чтением кода и тестов, две отдельные проверки сверяли их с исходниками. Пункты, которые стоит подтвердить тестом, отмечены. Строки указаны на срез выше и могут уехать.

**Статус.** Это предложения. Решение, объём и порядок за вами. Если задача уже закрыта в плане M6 или есть лучшее решение, предложение можно отклонить. Первый выпуск zero-agent не блокирует ни один пункт: для каждого есть обходной путь.

**Ограничение со стороны zero-agent.** В репозиторий zero-agent не подключается чужой код, поэтому общие крейты ZAM он использовать не будет. Отсюда форма пункта CR-5: описание и тестовые примеры, а не крейт.

**Нумерация** CR совпадает с `docs/specs/2026-11-06-zero-agent-tz/04-memory-contract.md`, номера идут с пропусками.

## P0

### CR-20. Идемпотентность создания и правки заметок

**Проблема.** `Idempotency-Key` работает только для записей журнала (`POST /spaces/{space}/entries`, `crates/zam-server/src/api/entries.rs:303`) и REST `/supersede` (`api/insights.rs:905`). У `POST /nodes` и `PATCH /nodes` защиты нет. Если клиент отправил `op: append`, а ответ потерялся, повтор задвоит текст. У zero-agent есть локальная очередь записи при обрыве связи, поэтому случай штатный.

**Предложение.** Принимать `Idempotency-Key` на `POST /nodes`, `PUT` и `PATCH /nodes/{id}` с той же семантикой, что у записей журнала: повтор возвращает 200 и исходный результат, расхождение тела 422. В MCP передать аргумент `idempotency_key` в `memory_write`.

**Готово, когда** два одинаковых `PATCH append` с одним ключом дают одну вставку.

**Обход.** Перед повтором агент сверяет ревизию заметки.

### CR-4. Лента изменений

**Проблема.** `since` в `GET /spaces/{s}/entries` фильтрует `created_at`, а не `updated_at` (`store/entries/mod.rs`, `EntryFilter`; `read.rs:41`). Смену статуса или `next_step` у существующей записи опросом не увидеть. Push-каналов нет: SSE, WebSocket и long-poll отсутствуют. Агент после разрыва связи не может досинхронизироваться.

**Предложение.** `GET /spaces/{s}/changes?since_seq=&limit=` с монотонным курсором и видом события (`created`, `updated`, `status`, `superseded`, `deleted`). Минимальный вариант: параметр `updated_since` в `/entries` с сортировкой по возрастанию.

**Готово, когда** смена статуса задачи видна следующим опросом, а курсор не пропускает записи при параллельной записи.

**Обход.** Перечитывать интересующие записи по id.

**Не просим:** превращать память в шину. Шина живёт в zero-agent.

### CR-7. Параметры `/recall` для нативного агента

**Проблема.** `recall.timeout_ms` = 200 мс рассчитан на бюджет хуков (`api/recall.rs:97-102`). Нативный агент на старте может подождать дольше и получить полный дайджест. Поле `source` принимается MCP-инструментом `memory_recall`, но не объявлено в схеме (`mcp/tools.rs:1428-1444`); то же у `agent_block_version`.

**Предложение.** Параметр `timeout_ms` в `RecallReq` с верхним пределом из конфигурации. Объявить `source` и `agent_block_version` в схеме MCP.

**Готово, когда** запрос с `timeout_ms: 1000` на медленном диске возвращает полный дайджест.

**Обход.** Один отложенный повтор при `warnings: ["recall timeout"]`.

### CR-8. Единый учёт явной сессии

**Проблема.** Учёт `account()` смотрит только заголовок (`mcp/mod.rs:257,301`), а `/recall` считает сессию явной и по полю тела (`api/sessions.rs:127-128`). По чтению кода `memory_recall` с `session_id` в аргументах, но без заголовка, уходит в `tokens_unattributed`. Тестом это не подтверждено, проверьте, пожалуйста. У `memory_search` и `memory_read` поля `session_id` в MCP нет.

**Предложение.** Согласовать: если сессия задана телом или заголовком, учёт идёт в неё. Добавить `session_id` в схемы `memory_search`, `memory_read`.

**Готово, когда** тест показывает учёт в нужной сессии при обоих способах задания.

**Обход.** zero-agent всегда шлёт заголовок.

### CR-9. Описание контракта и совместимость

**Проблема.** Схемы OpenAPI нет, форма JSON задаётся обработчиками. Ветка с частью M6 называет себя `0.0.10-m5.7`, поэтому версии недостаточно. Список `features` появился на ветке и пока не описан как официальный. В `v0.0.10-m5.7` `/health` отдаёт только `status, version, git, uptime_s`.

**Предложение.** Описать `/health.features` как официальный способ узнать возможности, с флагом на каждую функцию (`focus`, `snapshot`, `holdout`…). Публиковать OpenAPI для `/api/v1`. Записать обещание совместимости `/api/v1` или правило её нарушения.

**Готово, когда** клиент определяет наличие функции по `features` без пробных запросов.

**Обход.** zero-agent хранит снимки ответов и контрактные тесты у себя.

## P1

### CR-1. Вид записи `artifact`

**Проблема.** Заказчику нужен общий раздел скриптов и утилит: полное описание, чёткий контракт, версия языка, возможность заменить устаревшее. Такого раздела нет и он не запланирован. Ближе всего `insight` `pattern` со `scope: global`, но схема `data` свободна и не проверяется, а у заметок нет статуса и замещения.

**Предложение.** Новый вид записи `artifact`, ссылка `s:`:

```json
{
  "artifact_type": "script | utility | prompt",
  "name": "pdf-tables",
  "version": "1.2.0",
  "language": "python",
  "language_version": ">=3.12,<3.14",
  "entrypoint": "main.py",
  "input_schema": {},
  "output_schema": {},
  "effects": ["fs.read:input"],
  "network": false,
  "deps_lock": "sha256:…",
  "platforms": ["windows-x64", "linux-x64"],
  "sha256": "…",
  "verified_at": "2026-11-06",
  "eol": {"language": "2029-10"}
}
```

Статусы `active`, `revisit`, `deprecated`, `superseded`. Строгая проверка схемы. Тело или вложение с исходником. Фильтры поиска `artifact_type`, `language`, `name`. Живёт в Knowledge и действует между проектами. Индексация исходников как текста.

**Готово, когда** утилиту можно опубликовать, найти по назначению, заменить новой версией через `supersede`, а поиск отдаёт только действующую.

**Обход.** `insight` `pattern`, `scope: global`, контракт в `data.tool`, проверка на стороне агента.

### CR-18. Подсказки и проверенные команды из Knowledge

**Проблема.** Подсказка к запросу берёт только insight и Rules: заметки Knowledge в неё не попадают (ТЗ ZAM §10.3). «Проверенные команды» в дайджесте идут только из решения, не из Knowledge (ТЗ ZAM §7.10). Утилита из общего раздела не всплывёт сама.

**Предложение.** Настройка, включающая `verified_at`-заметки и записи `artifact` Knowledge в дайджест и подсказки с лимитом.

**Готово, когда** утилита из Knowledge показывается в другом проекте по триггеру или запросу.

**Обход.** Парный `insight` с триггером.

### CR-19. Происхождение записи

**Проблема.** Память — известный канал атаки: в публичных сообщениях автозамена заметки новой записью позволила отравленному README подменить факт в 216 из 216 попыток (источник вторичный). В Hermes есть CVE-2026-10223 о том же классе. В ZAM запись хранит автора, но не источник данных. `data` строгий у `task`, `question`, `term` (неизвестный ключ даёт 422, `store/tasks.rs:155`, `store/questions.rs:234`), а у `idea` поле `data.origin` — это строка `human|agent` (`store/ideas.rs:334`). Единого места нет.

**Предложение.** Поле верхнего уровня у всех записей и узлов:

```json
"provenance": {"source_kind": "user|tool|web|file|peer|agent",
               "source_url": "…", "tainted": true, "run": "…"}
```

Фильтр поиска `filters.tainted`. Бусты не поднимают tainted-записи над доверенными. Запись с `tainted: true` не может автоматически заменять `axiom` или `theorem`.

**Готово, когда** запись с происхождением видна в карточке, а `supersede` доверенной записи tainted-записью отклоняется или требует подтверждения.

**Обход.** Теги `src:*`, `tainted`, поле `message`, правила на стороне агента.

### CR-2. Токены с областью

**Проблема.** Токен принадлежит пользователю и имеет только `rw` или `ro` (`migrations/system/0001_init.sql:10-21`). Срока нет, привязки к решению нет. Он открывает всю память пользователя, кроме Human, включая Vault и другие решения. Токен не может выпустить токен, только WebUI или администратор (`auth/user.rs:220-226`).

**Предложение.** Поля токена: `solutions[]`, `spaces[]`, `expires_at`, необязательный `agent_id`. Маршрут выпуска дочернего токена с правами не шире родительского.

**Готово, когда** токен субагента не видит Vault и другие решения.

**Обход.** Ограничения на стороне агента: инструмент Vault не выдаётся, шлюз фильтрует решения.

### CR-3. Идентичность субагента

**Проблема.** Связь `parent_id` есть, индекс есть, но API выборки детей нет (`api/sessions.rs:377-382`, `deny_unknown_fields`). Автор ревизии хранит `session_id`, а сессии удаляются через 30 дней, поэтому тип автора теряется.

**Предложение.** `GET /sessions?parent_id=` или `GET /sessions/{id}/children`. `agent_id` и `agent_type` в ревизиях и `author`. Срок хранения с учётом дерева.

**Готово, когда** через год по записи видно, какой тип субагента её создал.

**Обход.** Дерево хранит агент у себя.

### CR-5. Описание триггеров и маскировки с тестовыми примерами

**Проблема.** Сопоставление триггеров, `err_fp` и символы живут только в клиенте `zam`. Нативный агент повторяет эту логику своим кодом и должен совпадать с ним. Тип `keyword` хранится и отдаётся, но ни сервер, ни хуки его не сопоставляют (`cli/cmd/insight.rs:41` только принимает).

**Предложение.** Документ с точными правилами `file_glob`, `command_regex`, `error_regex`, `keyword`, нормализации `err_fp` и маскировки секретов, плюс файл тестовых примеров вход–результат. Решить судьбу `keyword`: сопоставлять или убрать.

**Готово, когда** внешний клиент проходит тестовые примеры.

**Обход.** Контрактные тесты сверяют с поведением `zam`.

### CR-6. Атомарная выдача задачи

**Проблема.** `claim` рекомендательный, а «взять следующую» нет: список, попытка, при 409 следующий кандидат. Гарантия гонки двух `claim` в документах не описана, запись сериализована одним писателем, нагрузочных данных нет.

**Предложение.** `POST /entries/claim-next {space, filter, ttl_min}` возвращает захваченную задачу или 204. Необязательный строгий захват: чужая правка задачи даёт 409.

**Готово, когда** N параллельных клиентов получают разные задачи без 409.

**Обход.** Рабочая очередь живёт в SQLite агента, ZAM хранит долговременное зеркало.

### CR-10. Дедупликация под гонкой

**Проблема.** Проверка в `api/insights.rs` стоит до транзакции записи, а косинусная часть работает только после векторной индексации. По чтению кода два воркера могут записать близкие `insight` параллельно. Тестом не подтверждено.

**Предложение.** Ключ дедупликации, заданный клиентом (`dedup_key`), с уникальностью в транзакции. Либо проверка заголовка внутри транзакции записи.

**Готово, когда** параллельная запись с одним ключом создаёт одну запись и 409 для второй.

**Обход.** Шлюз агента сериализует запись на решение.

### CR-12. Пакетная запись

**Проблема.** Рой пишет много коротких фактов, каждая запись — отдельные HTTP и транзакция. Писатель один на базу, ожидание блокировки 30 с. Пакетный `files/changed` уже есть (до 500 файлов), для записей журнала пакета нет.

**Предложение.** `POST /spaces/{s}/entries:batch` до N записей в одной транзакции, результат по каждой, идемпотентность по элементам.

**Готово, когда** 100 записей пакетом занимают заметно меньше времени, чем 100 запросов.

**Обход.** Шлюз агента сливает записи и ограничивает частоту.

## P2

### CR-11. Ожидание индексации в поиске

**Проблема.** FTS видит запись сразу, вектор отстаёт. Семантический read-your-writes сейчас только опросом `pending_count`.

**Предложение.** Параметр `wait_indexed_ms` или `min_seq` в `/search`.

**Обход.** Чтение своей записи по id.

### CR-13. Общая область между пользователями

**Проблема.** Knowledge личный, участнику общего решения он не виден. Утилиты нельзя разделить между пользователями.

**Предложение.** Пространство `shared` или системное решение с ролями.

**Обход.** Сейчас не нужно: все агенты принадлежат одному владельцу.

### CR-14. Фильтр по тегам и `data`

**Проблема.** Тегов в поиске нет (`api/search/mod.rs`), они только в контекстном префиксе чанка. По `data` доступен только `data_kind`.

**Предложение.** `filters.tags`, выборка по ключам `data`.

**Обход.** Лента `GET /spaces/{s}/entries?tag=`, отбор на стороне клиента.

### CR-15. Сервисная выдача токенов

**Проблема.** Токены выпускаются только через WebUI или администратором. Автоматическое развёртывание и бенчмарки, где каждый прогон стартует со снимка памяти, упираются в это.

**Предложение.** Команда `zam-server token issue` на сервере и настройка лимитов на токен.

**Обход.** Копия каталога данных с заранее выпущенным токеном.

### CR-16. Структурные ответы MCP

**Проблема.** Ответ MCP — Markdown; `format: "json"` даёт JSON в тексте без `structuredContent`. Разбор текста хрупок.

**Предложение.** Поле `structuredContent` или стабильная схема при `format: json`.

**Обход.** Для разбора агент использует REST.
