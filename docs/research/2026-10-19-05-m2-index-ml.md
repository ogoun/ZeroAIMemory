## 1. `ort` (ONNX Runtime для Rust)

### 1.1. Факты
- **Версии на crates.io:** 2.0.0-rc.14 (2026-10-12) — последняя, до неё rc.13 (2026-07-28) и rc.12 (2026-03-05). MSRV у rc.14 — **1.92**, совпадает с нашим `rust-version`. Источник: https://crates.io/api/v1/crates/ort/versions.
- **rc.14** (https://github.com/pykeio/ort/releases):
  - собран под **ONNX Runtime 1.31.0**;
  - создавать `Environment` теперь обязательно: `ort::init()…build()?`, затем `Session::builder(&env)`;
  - `get_/set_gpu_device` удалены;
  - появился `ort::util::probe(path) -> Option<u32>`, он возвращает минорную версию dylib;
  - разработчики просят не хранить environment и сессии в глобальных переменных.
- **rc.13:** готовые CUDA-бинарники собраны только под CUDA 13 («ONNX Runtime has deprecated CUDA 12»). Структуры EP вроде `ep::CUDA` доступны только при включённой cargo-фиче.
- **rc.12:** `ORT_LIB_LOCATION` переименована в `ORT_LIB_PATH`. При `default-features = false` новые API требуют явной фичи `api-NN`.
- **Фичи rc.14** (по `Cargo.toml` крейта):
  - `default = [api-31, copy-dylibs, download-binaries, ndarray, std, tls-native, tracing]`;
  - `load-dynamic = [ort-sys/disable-linking, preload-dylibs, std]`;
  - `cuda = [ort-sys/cuda]`;
  - есть отдельные фичи `half`, `ndarray`, `tracing`, `api-17` … `api-31`.
- **Как загружается dylib** (`src/lib.rs`, `src/environment.rs`):
  - `ort::init_from<P: AsRef<Path>>(path) -> Result<EnvironmentBuilder, LoadDynamicError>` должен идти **до любого другого вызова ort**;
  - если `init_from` не вызывался, ort берёт `ORT_DYLIB_PATH`, а без неё — `onnxruntime.dll` / `libonnxruntime.so` по системному поиску;
  - если библиотека не загрузилась на пути через `ORT_DYLIB_PATH`, будет **panic** («Failed to load ONNX Runtime dylib»), а `init_from` возвращает `Err`. Поэтому используем только `init_from` с абсолютным путём рядом с exe;
  - относительный `ORT_DYLIB_PATH` считается от исполняемого файла (https://ort.pyke.io/setup/linking);
  - если минорная версия dylib меньше `MINOR_VERSION` (31 при `api-31`), ort пишет предупреждение «designed for ONNX Runtime 1.31.x…» и может не найти нужные символы API.
- **SessionBuilder** (`SessionBuilder::new(&env)`, он же `Session::builder(&env)`), значимые для нас методы:
  - `with_intra_threads(usize)`, `with_inter_threads(usize)`, `with_parallel_execution(bool)`;
  - `with_optimization_level(GraphOptimizationLevel::{Disable, Level1, Level2, Level3, All})`;
  - `with_execution_providers(impl AsRef<[ExecutionProviderDispatch]>)`;
  - `with_memory_pattern(bool)`, `with_intra_op_spinning(bool)`, `with_independent_thread_pool()`;
  - `with_prepacked_weights(&PrepackedWeights)`;
  - `with_optimized_model_path(..)`, `with_log_level(..)`;
  - `commit_from_file(path)` и `commit_from_memory(&[u8])`.
- **Исполнители (EP):**
  - `ep::CUDA::default().with_device_id(i32).with_memory_limit(usize).with_arena_extend_strategy(..).with_tf32(bool).with_cuda_graph(bool).build()`;
  - у `ExecutionProviderDispatch` есть `.error_on_failure()`;
  - трейт `ExecutionProvider` даёт `is_available() -> Result<bool>`: это `GetAvailableProviders`, он показывает только, что EP вкомпилирован;
  - без `error_on_failure` ошибка регистрации пишется в лог («An error occurred when attempting to register …»), и сессия молча работает на CPU.
- **Run и потокобезопасность:**
  - `Session: Send + Sync`;
  - **`run(&mut self, …)`**, `run_with_options(&mut self, …)`, `run_async(&mut self, …)`;
  - авторы объясняют `&mut` тем, что часть внутренностей ORT не потокобезопасна (аллокаторы EP, счётчики), и советуют держать по сессии на поток или батчить.
- **Тензоры без ndarray:**
  - вход: `TensorRef::from_array_view(([b, t], &ids[..]))?` или `Tensor::from_array(([b, t], vec))?`;
  - выход: `value.try_extract_tensor::<f32>() -> Result<(&Shape, &[f32])>`;
  - `try_extract_array` нужен только с фичей `ndarray`.
- **Библиотеки для CUDA EP** (`ep::cuda::CUDA_DYLIBS` и `CUDNN_DYLIBS`, функция `ep::cuda::preload_dylibs(cuda_dir, cudnn_dir)`):
  - Windows: `cudart64_13.dll`, `cublasLt64_13.dll`, `cublas64_13.dll`, `cufft64_12.dll`;
  - Linux: дополнительно `libnvrtc.so.13`, `libcurand.so.10`;
  - cuDNN 9: `cudnn64_9`, `cudnn_graph64_9`, `cudnn_ops64_9`, `cudnn_heuristic64_9`, `cudnn_adv64_9`, `cudnn_cnn64_9`, `cudnn_engines_precompiled64_9`, `cudnn_engines_runtime_compiled64_9`.

### 1.3. Рекомендация
```toml
ort = { version = "=2.0.0-rc.14", default-features = false, features = ["std", "load-dynamic", "api-31", "cuda", "half", "tracing"] }
```
- **Инициализация.** Окружение ORT создаётся лениво, один раз на процесс, через `init_from(<exe_dir>/onnxruntime.{dll|so})`. Хранится оно в `Arc` внутри сервиса `Embedder`, а не в `static`. До загрузки проверяем `ort::util::probe(path) == Some(31)`. Если библиотеки нет или версия не та, сервер переходит в режим FTS-only и пишет причину в `/index/status`. Panic через `ORT_DYLIB_PATH` исключаем: переменную не используем.
- **Выбор устройства при `ml.device=auto|cuda`:**
  1. `ep::cuda::preload_dylibs(Some(<exe>/cuda), Some(<exe>/cuda))` — так рядом лежащие DLL находятся без правки PATH;
  2. сессия с `CUDA…build().error_on_failure()`;
  3. при `Err` — пересборка без EP на CPU; причина ошибки идёт в лог и в `/index/status`.

  Этого достаточно, чтобы узнать, включилась ли CUDA: при `error_on_failure` успешный `commit` означает, что EP зарегистрирован. Отдельного API «какой EP активен» у `Session` нет.
- **Две сессии (запросы и индексация)** — в отдельных пулах потоков (`with_independent_thread_pool`), каждая под своим `Mutex`. Вызов `run` требует `&mut`, поэтому блокировка нужна и так. Веса между двумя сессиями дублируются (см. риски) — общий `PrepackedWeights` обязателен.
- **Оптимизации:** `GraphOptimizationLevel::Level3`. `with_optimized_model_path` не используем: результат зависит от CPU и от EP.

```rust
let env = ort::init_from(&ort_path)?.with_name("zam").build()?;             // Environment
let mk = |threads: usize, cuda: bool, pw: &PrepackedWeights| -> ort::Result<Session> {
    let mut b = Session::builder(&env)?
        .with_optimization_level(GraphOptimizationLevel::Level3)?
        .with_intra_threads(threads)?
        .with_independent_thread_pool()?
        .with_prepacked_weights(pw)?;
    if cuda {
        b = b.with_execution_providers([ep::CUDA::default().with_device_id(0).build().error_on_failure()])?;
    }
    b.commit_from_file(&model_path)
};
let pw = PrepackedWeights::new();
let index_sess = match mk(6, want_cuda, &pw) {
    Ok(s) => (s, Device::Cuda),
    Err(e) => { tracing::warn!(error=%e, "CUDA EP недоступен, CPU"); (mk(6, false, &pw)?, Device::Cpu) }
};
// вход без ndarray
let ids = TensorRef::from_array_view(([b, t], &input_ids[..]))?;      // i64
let mask = TensorRef::from_array_view(([b, t], &attn_mask[..]))?;     // i64
let out = sess.run(ort::inputs!["input_ids" => ids, "attention_mask" => mask])?;
let (shape, hidden) = out["last_hidden_state"].try_extract_tensor::<f32>()?; // [b, t, 1024]
```

### 1.4. Риски
- **RAM.** Две сессии с одной моделью int8 на 568 МБ — это примерно 1,1 ГБ только весов, то есть больше бюджета §17 в 1,1 ГБ. `PrepackedWeights` делит только «перепакованные» веса MatMul. Таблица эмбеддингов 250 002×1024 (Gather, около 256 МБ в int8) всё равно продублируется. Варианты:
  - (а) общий initializer через `with_external_initializer`/`with_initializer` для `embeddings.word_embeddings` (не проверено для квантованного графа);
  - (б) одна сессия и планировщик: запросы проходят между батчами индексации, а батч ограничен примерно 2–4 тыс. токенов.

  На M2 это нужно проверить замером. Решение записать в ADR.

  **Замер (задача 3 M2, 2026-10-19; Windows, Ryzen 9 5900X, CPU-сборка ORT 1.31, `Xenova/bge-m3` int8):** RSS процесса после загрузки — **1393 МБ**: токенизатор `tokenizers` ≈ 230 МБ (Unigram-trie на 250 тыс. токенов), сессия индексации ≈ 620 МБ, сессия запросов ≈ 510 МБ. `PrepackedWeights` на этом графе (`MatMulInteger` + `DynamicQuantizeLinear`) **ничего не экономит**: с ним и без него — те же 1393 МБ. Бюджет 1,1 ГБ не выполняется; нужны вариант (а), одна сессия с планировщиком (б) или свой токенизатор. Решение — ADR.
- **API нестабилен** (rc). Версию закрепляем через `=`.
- **Пиковая активационная память** растёт с размером батча. Квадратичная часть — внимание: B×16×T²×4 байта на слой. При 16×512 это около 270 МБ, поэтому ограничиваем `max_batch_tokens` (по умолчанию 8192) и сортируем чанки по длине перед батчингом.
- **Размер GPU-комплекта.** ORT GPU (около 215 МБ DLL) плюс cuBLAS/cuBLASLt (сотни МБ) плюс cuDNN (полный около 2 ГБ в распакованном виде) рискуют превысить лимит GitHub в 2 ГиБ на файл. Для энкодера-трансформера cuDNN почти не нужен, но `onnxruntime_providers_cuda` грузит `cudnn64_9.dll` при старте. Два шага:
  1. на M2 проверить минимальный набор: `cudnn64_9` + `cudnn_graph64_9` + `cudnn_ops64_9` + `cudnn_heuristic64_9` без `engines_*` (не проверено);
  2. запасной путь — команда `zam-server cuda fetch` с sha256 из `deploy/cuda.toml`, которая докачивает архивы NVIDIA redist. Это частично расходится с требованием «всё в комплекте», нужно решение владельца.

## 2. `tokenizers`

### 2.1. Факты
- **Версии:** 0.23.2 (2026-09-03); есть 1.0.0-rc.2 (2026-09-21). Источник: https://crates.io/api/v1/crates/tokenizers/versions.
- **Фичи:**
  - `default = ["progressbar", "onig", "esaxx_fast"]`;
  - `onig` (C-библиотека Oniguruma через `onig_sys`, собирается `cc`) и `fancy-regex` (чистый Rust) — обе опциональные;
  - `http` подключает hf-hub — нам не нужна.
- **Без regex-фичи сборка падает.** В `src/utils/mod.rs` 0.23.2 есть `compile_error!("One of the onig, or fancy-regex features must be enabled")`. Значит, `default-features = false` из ТЗ без явной фичи не соберётся.
- **Regex нужен и bge-m3.** Токенизатор bge-m3 (XLM-R, Unigram) содержит нормализатор `Sequence[Precompiled, Replace(Regex " {2,}")]`.
- **fastembed-rs** использует `features = ["onig"]`.
- **API** (`TokenizerImpl`):
  - `Tokenizer::from_file(p)`;
  - `with_truncation(Option<TruncationParams>) -> Result<&mut Self>`;
  - `with_padding(Option<PaddingParams>) -> &mut Self`;
  - `encode(input, add_special_tokens)`, `encode_fast(..)` (без offsets);
  - `encode_batch(Vec<E>, bool)`, `encode_batch_fast(..)`. Пакетные методы идут через rayon и управляются `TOKENIZERS_PARALLELISM`.
- **Настройки внутри `tokenizer.json`.** У bge-m3 (`BAAI/bge-m3` и Xenova) `truncation: null` и `padding: null`. У `all-MiniLM-L6-v2` (Xenova) там зашиты `truncation max_length=128` и `padding Fixed(128)`, поэтому параметры **всегда задаём явно**.

### 2.2. Рекомендация
```toml
tokenizers = { version = "=0.23.2", default-features = false, features = ["fancy-regex"] }
```
- **fancy-regex**, потому что он на чистом Rust: без C-сборки и одинаково на MSVC и Linux. Паттерн `" {2,}"` тривиален, расхождений с onig не будет.
- **Проверка в CI:** golden-тест «токенизация 50 русских и английских строк == ids из Python-эталона» на обеих ОС.
- **Два экземпляра токенизатора:** (1) для эмбеддинга — с truncation и padding; (2) для `token_count` — без них, с `encode_fast(text, false)`.


- Выход 1.0 может сломать API. Версию закрепляем.
- Пакетные методы используют rayon. Запускаем токенизацию в выделенном потоке воркера, а не в потоках tokio.

## 3. bge-m3 в ONNX

### 3.1. Как устроена модель
- **Архитектура** (`BAAI/bge-m3/config.json`):
  - XLM-RoBERTa large: 24 слоя, hidden 1024, 16 голов, FFN 4096;
  - словарь 250 002, `max_position_embeddings` 8194, то есть рабочий максимум 8192 токена;
  - `pad_token_id=1`, `bos=0` (`<s>`), `eos=2` (`</s>`), `unk=3`, `<mask>`=250001.

  Лицензия MIT.
- **Dense.** `normalize(last_hidden_state[:, 0])`: CLS-пулинг и L2-нормировка.
- **Sparse.** `relu(sparse_linear(h))`, где `Linear(1024 → 1)`. Затем max по совпадающим token-id, без спецтокенов {0, 1, 2, 3}. Так же сделано в FlagEmbedding, в экспорт-скрипте `gpahal` и в fastembed-rs.
- **ColBERT.** `normalize(colbert_linear(h[:, 1:]) * mask[:, 1:])`, `Linear(1024 → 1024)`. В v1 не нужен (§6.4).
- **Веса голов** (`BAAI/bge-m3@5617a9f61b028005a4858fdac845db406aefb181`):
  - `sparse_linear.pt` — 3516 Б, sha256 `45c93804d2142b8f6d7ec6914ae23a1eee9c6a1d27d83d908a20d2afb3595ad9`. Внутри zip **без сжатия** (torch pickle): `sparse_linear/data/0` — 2048 Б, это **fp16** weight [1, 1024]; `sparse_linear/data/1` — 2 Б, fp16 bias. Pickle проверен через `pickletools`: `torch HalfStorage`, shape (1, 1024).
  - `colbert_linear.pt` — 2 100 674 Б, sha256 `19bfbae3…9abb` (fp16 1024×1024 + bias).

  Читать их можно уже подключённым `zip` + `half`, без Python и pickle: файл закреплён sha256, поэтому достаточно взять `data/0` и `data/1` как сырые LE-f16. fastembed-rs держит то же самое в `sparse_linear.safetensors` (4236 Б, sha256 `a2601321…d690`).

### 3.3. Рекомендация
Один код для всех вариантов: модель выдаёт `last_hidden_state` (или `token_embeddings`), а пулинг и sparse делаются в Rust. Так один путь обслуживает int8, fp16, fp32 и тестовую модель.

- **(a) CPU int8:** `Xenova/bge-m3@4de13258303883538bd53b696b452bf8099f0858` → `onnx/model_int8.onnx` (sha256 `a206e10e…51d6`) + `tokenizer.json` (`6710678b…f790`) + `BAAI/bge-m3@5617a9f6…/sparse_linear.pt` (`45c93804…5ad9`). Если `model_int8` не пройдёт порог качества, пробуем `gpahal`; если не пройдёт и он, квантуем сами (см. ниже).
- **(b) GPU:** `Xenova/bge-m3@4de13258…` → `onnx/model_fp16.onnx` (sha256 `4f1a646a…55e9`), токенизатор и sparse-голова те же. Эталон для тестов качества — fp32 `BAAI/bge-m3/onnx/model.onnx` + `model.onnx_data` (sha256 `1eebfb28…16b4`) + `onnx/Constant_7_attr__value`.
- **`model_id`:** например `bge-m3@xenova-4de1325:int8`. Векторы int8 и fp16 немного различаются, поэтому при смене CPU ↔ GPU на одной базе нужна политика: считать их одной моделью или переиндексировать. Решение исполнителя — **одна модель, если dense-косинус int8 и fp16 ≥ 0,99 на eval**; иначе разные `model_id`.
- **Порог качества на M2:**
  - средний dense-косинус к fp32 ≥ 0,99, минимальный ≥ 0,97;
  - recall@5 и nDCG@10 на `eval/` падают не больше чем на 1 п.п.;
  - для sparse — корреляция Спирмена весов ≥ 0,95.
- **Если порог не пройден:** свой воспроизводимый int8 из BAAI fp32 — ORT `quantize_dynamic` per-channel или SmoothQuant, без квантования `word_embeddings` и последнего слоя. Скрипт хранится в `tools/`, результат публикуется в release-ассетах `zam-models` с sha256. Лицензия MIT это позволяет.
- **Пулинг и усечение:** dense = CLS + L2; sparse = `max(0, h·w+b)` с max-pool по id, без {0, 1, 2, 3}, затем отбрасываем веса < 1e-4 (не обязательно). Усечение: запрос — 512 токенов, чанк — 1024 (чанки ≤ 800 по §8.2); 8192 доступно, но для индексации не нужно.

```rust
// sparse_linear.pt -> (w[1024], b) без pickle (файл закреплён sha256)
let mut z = zip::ZipArchive::new(File::open(p)?)?;
let w: Vec<f32> = read(&mut z, "sparse_linear/data/0")?.chunks_exact(2)
    .map(|c| half::f16::from_le_bytes([c[0], c[1]]).to_f32()).collect();
let b = half::f16::from_le_bytes(read(&mut z, "sparse_linear/data/1")?[..2].try_into()?).to_f32();
// пулинг по [B,T,H]
for i in 0..bsz {
    let row = |t: usize| &hidden[(i * seq + t) * H..(i * seq + t + 1) * H];
    let dense = l2_normalize(row(0));                      // CLS
    let mut sp: HashMap<u32, f32> = HashMap::new();
    for t in 0..seq {
        let id = ids[i * seq + t];
        if mask[i * seq + t] == 0 || id <= 3 { continue; }
        let s = (dot(row(t), &w) + b).max(0.0);
        if s > 0.0 { sp.entry(id as u32).and_modify(|v| *v = v.max(s)).or_insert(s); }
    }
}
```

### 3.4. Риски
- **ORT не выбрасывает узлы для невыбранных выходов** (не проверено). Если брать `gpahal`, ColBERT-голова 1024×1024 и тензор [B,T,1024] будут считаться впустую (около +3 % FLOP и +B·T·4 КБ памяти). Это ещё одна причина выбрать `last_hidden_state`.
- **reduce_range=true у Xenova** (7-битные веса) рассчитан на CPU без VNNI. На VNNI это лишняя потеря точности. Решает гейт качества.
- **Hugging Face может удалить репозиторий или переписать ревизию.** Ревизия закреплена хэшем коммита, файл — sha256. Плюс есть архив `zam-models` (§16.3).

## 5. `qdrant-client` (Rust)

### 5.1. Факты
- **Версии:** 1.19.0 (2026-08-04) — последняя. Совместима с сервером ±1 минорная; в клиенте есть `skip_compatibility_check()`. Источник: https://crates.io/api/v1/crates/qdrant-client.
- **Фичи:**
  - `default = ["download_snapshots", "serde", "generate-snippets"]`;
  - `download_snapshots` тянет `reqwest` 0.13 — не нужна;
  - `serde` (serde_json для `Payload`) и `uuid` — опциональны.
- **Зависимости:**
  - `tonic ^0.14.6` с features `tls-ring`, `tls-native-roots`, `gzip` и default-фичами `router`/`transport`/`codegen`; `router` тянет **axum 0.8**;

- **Сборка:** `build.rs` у крейта нет, gRPC-код сгенерирован заранее (`tonic-prost-build` — только dev-зависимость). **protoc не нужен.**
- **Коллекция и векторы** (исходники 1.19.0):
  - `CreateCollectionBuilder::new(name)` с методами `.vectors_config(VectorsConfigBuilder)`, `.sparse_vectors_config(SparseVectorsConfigBuilder)`, `.on_disk_payload(bool)`, `.hnsw_config(..)`, `.optimizers_config(..)`, `.metadata(HashMap<String, serde_json::Value>)`;
  - `VectorsConfigBuilder::default().add_named_vector_params(name, VectorParamsBuilder)`;
  - `VectorParamsBuilder::new(size, Distance::Cosine)` с методами `.hnsw_config(HnswConfigDiffBuilder)`, `.quantization_config(ScalarQuantizationBuilder)`, `.memory(Memory::Cold|Cached)`, `.datatype(Datatype::Float16)`, `.on_disk(bool)`.
- **Уровни памяти в 1.19:**
  - `Memory::{Cold=1, Cached=2, Pinned=3}`;
  - для **хранилища dense-векторов `Pinned` не поддерживается** (комментарий в proto);
  - `ScalarQuantizationBuilder::default()` (тип Int8 по умолчанию) с `.quantile(f32)`, `.memory(Memory::Pinned)`; `always_ram` устарел;
  - `on_disk` устарел везде, вместо него `memory`.
- **Sparse:** `SparseVectorParamsBuilder::default().index(SparseIndexConfigBuilder::default().memory(..).datatype(..))`; `.modifier(Modifier::Idf)` не ставим.
- **HNSW:** `HnswConfigDiffBuilder::default().m(16).ef_construct(100).payload_m(16).memory(..)`.
- **Payload-индексы:**
  - `CreateFieldIndexCollectionBuilder::new(coll, field, FieldType::Keyword).field_index_params(KeywordIndexParamsBuilder::default().is_tenant(true)).wait(true)`;
  - `KeywordIndexParams` содержит `is_tenant`, `on_disk`, `enable_hnsw`, `prefix`, `memory`;
  - для `updated_at` и `rev` — `FieldType::Datetime` / `FieldType::Integer`.
- **Точки:**
  - `PointStruct::new(id, NamedVectors::default().add_vector("dense", Vector::new_dense(v)).add_vector("sparse", Vector::new_sparse(idx, vals)), payload)`;
  - `UpsertPointsBuilder::new(coll, points).wait(true)`; есть `upsert_points_chunked`.
- **Запрос** (Query API):
  - `QueryPointsBuilder::new(coll)` с `.add_prefetch(PrefetchQueryBuilder::default().query(Query::new_nearest(..)).using("dense").filter(f).limit(50u64))`;
  - для sparse — `VectorInput::new_sparse(idx, vals)` или `Vec<(u32, f32)>`;
  - слияние: `.query(Query::new_rrf(RrfBuilder::with_k(60).weights(vec![..])))` или `.query(Fusion::Rrf)`;
  - далее `.filter(..)`, `.limit(..)`, `.with_payload(true)`, `.score_threshold(..)`, `.timeout(..)`;
  - **у RRF есть параметр `k` (по умолчанию 60) и `weights` по prefetch** — это weighted RRF прямо в Qdrant.
- **Удаление:**
  - `DeletePointsBuilder::new(coll).points(Filter::must([Condition::matches("node_id", id)])).wait(true)`;
  - по id — `.points(PointsIdsList { ids })`.
- **Метаданные коллекции:** `metadata` в `CreateCollection`, `UpdateCollection` (слияние с уже сохранёнными) и в `CollectionConfig`, читается через `collection_info`.
- **Подключение:** `Qdrant::from_url("http://127.0.0.1:6334").api_key(key).timeout(..).connect_timeout(..).build()?`. Ключ уходит в gRPC-заголовке `api-key`. TLS выключен (localhost).

```rust
    .field_index_params(KeywordIndexParamsBuilder::default().is_tenant(true)).wait(true)).await?;

let r = client.query(QueryPointsBuilder::new("zam_chunks")
    .add_prefetch(PrefetchQueryBuilder::default().query(Query::new_nearest(q_dense.clone()))

        .using("sparse").filter(leaf).limit(50u64))
```

## 7. Супервизор процесса

### 7.1. Факты
- **`process-wrap` 10.0.1** (2026-09-23, Apache-2.0 OR MIT, watchexec, 20 млн загрузок). Фичи: `creation-flags`, `job-object`, `kill-on-drop`, `process-group`, `process-session`, `reset-sigmask`, `std`, `tokio1`, `tracing`. Что подтверждено по исходникам:
  - `JobObject` **всегда добавляет `CREATE_SUSPENDED`**;
  - после `AssignProcessToJobObject` он возобновляет потоки через ToolHelp32 (`Thread32First/Next` + `OpenThread` + `ResumeThread`); это нужно, потому что `std::process` не отдаёт handle первичного потока;
  - с обёрткой `KillOnDrop` ставится `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
  - `CreationFlags(CREATE_NO_WINDOW)` совмещается с job в любом порядке;
  - Windows-зависимость — крейт `windows` 0.62.2, Unix — `nix` 0.31.
- **`command-group` 5.0.1** — последний релиз 2023-11. Это предшественник process-wrap, не берём.
- **`win32job` 2.0.3** (2025-05) — только job, без логики suspended и resume.
- **`windows-sys` 0.61.2** — для ручной реализации нужны фичи:
  - `Win32_Foundation`;
  - `Win32_Security` (параметр `SECURITY_ATTRIBUTES`);
  - `Win32_System_JobObjects` (`CreateJobObjectW`, `SetInformationJobObject`, `AssignProcessToJobObject`, `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`, `JobObjectExtendedLimitInformation`, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`);
  - `Win32_System_Threading` (`CREATE_SUSPENDED`, `CREATE_NO_WINDOW`, `ResumeThread`, `OpenThread`, `TerminateProcess`);
  - `Win32_System_Diagnostics_ToolHelp`.
- **Упрощённый путь без suspended:** обычный spawn, сразу затем `AssignProcessToJobObject`. Окно гонки — микросекунды. Если `zam-server` умрёт именно в этот момент, Qdrant осиротеет; его подберёт очистка по pid-файлу и порту при следующем старте. Дочерних процессов у Qdrant нет, поэтому утечки «внуков» не будет. Такой вариант приемлем, но готовая библиотека убирает и это окно.
- **Linux, `PR_SET_PDEATHSIG`.**
  - Сигнал приходит при смерти **потока**, который сделал fork, а не процесса (`man 2 prctl`). В tokio `spawn_blocking`-потоки завершаются после простоя (по умолчанию около 10 с). Если `Command::spawn` вызвать из такого потока, Qdrant получит SIGKILL просто при простое пула. Поэтому ТЗ требует долгоживущий поток.
  - Вторая гонка: родитель может умереть до `prctl`. Поэтому в `pre_exec` после `prctl` сравниваем `getppid()` с заранее сохранённым pid и, если он другой, делаем `_exit`.
  - `prctl`, `getppid` и `_exit` безопасны для вызова из обработчика сигналов (async-signal-safe).

### 7.2. Рекомендация
- **Windows:** `process-wrap = { version = "=10.0.1", default-features = false, features = ["tokio1", "job-object", "kill-on-drop", "creation-flags"] }`.
- **Linux:** свой `pre_exec` плюс `process-group` (чтобы kill шёл по группе), `libc` 0.2.191 (уже есть в lock).
- **Где живёт процесс:** спавн и ожидание — в выделенном `std::thread` «qdrant-supervisor», у которого свой `current_thread` runtime tokio. Поток живёт столько же, сколько сервер.
- **Pipe stdout/stderr → tracing** читаем там же.

```rust
let mut cmd = process_wrap::tokio::CommandWrap::with_new(&qdrant_exe, |c| {
    c.current_dir(&qdir).args(["--config-path", "config/zam.yaml", "--disable-telemetry"])
     .env("QDRANT__SERVICE__API_KEY", &key).env("QDRANT_INIT_FILE_PATH", qdir.join(".qdrant-initialized"))
     .stdin(Stdio::null()).stdout(Stdio::piped()).stderr(Stdio::piped());
    #[cfg(unix)] {
        let parent = std::process::id() as libc::pid_t;
        unsafe { c.pre_exec(move || {
            if libc::prctl(libc::PR_SET_PDEATHSIG, libc::SIGKILL) != 0 { return Err(std::io::Error::last_os_error()); }
            if libc::getppid() != parent { libc::_exit(1); }
            Ok(())
        }); }
    }
});
#[cfg(windows)] { cmd.wrap(process_wrap::tokio::JobObject).wrap(process_wrap::tokio::KillOnDrop)
                     .wrap(process_wrap::tokio::CreationFlags(CREATE_NO_WINDOW)); }
#[cfg(unix)]    { cmd.wrap(process_wrap::tokio::ProcessGroup::leader()); }
let child = cmd.spawn()?;   // Box<dyn ChildWrapper>
```

### 7.3. Риски
- process-wrap выпускает новую мажорную версию каждые несколько месяцев (сейчас 10.x). Закрепляем через `=`.
- Обёртка `KillOnDrop` на tokio убивает дочерний процесс при drop. Это и есть нужное поведение, но в коде перезапуска нельзя случайно уронить handle.
- Нужен e2e-тест «`zam-server` убит → Qdrant завершился» на обеих ОС (§18.1).

## 11. Оценка производительности (§17)
Вычислительная стоимость bge-m3: (4d² + 8d²) × 24 слоя ≈ 302M MAC-параметров без эмбеддингов. На токен это 2 × 302M ≈ 0,60 GFLOP плюс внимание 4·T·d·24 ≈ 0,04 GFLOP при T = 400. Итого **≈ 0,64 GFLOP/токен, ≈ 257 GFLOP на чанк в 400 токенов**.

| Сценарий | Оценка | Основание |
|---|---|---|
| CPU fp32, 8 ядер AVX2 (около 0,9 TFLOPS пик, 40–50 % на ORT) | ≈ 1,5–1,8 чанка/с | расчёт |
| CPU int8 (VPMADDUBSW, около 3,6 TOPS пик, 25–35 % эффективно, минус около 30 % на неквантованные операции) | **≈ 2,5–4 чанка/с**; с AVX-512 VNNI / AVX-VNNI — 4–6 | расчёт; ускорение int8 к fp32 около 2× (карточка `skatzR/USER-BGE-M3-ONNX-INT8`: 0,75 → 0,35 с) |
| Эмбеддинг запроса (16–32 токена, 2 потока, int8) | ≈ 30–80 мс | расчёт; в arXiv-обзоре около 31 мс у bge-m3 на CPU без батча (железо не указано) |
| GPU fp16, RTX 3060 (25,6 TFLOPS fp16 с fp32-аккумулятором, около 40 % реально) | **≈ 30–50 чанков/с** | для ≥ 100 чанков/с нужно ≈ 26 TFLOPS устойчиво, то есть больше пика 3060 |
| GPU fp16, RTX 4090 / 5080 класса | ≥ 100 чанков/с достижимо | расчёт |

- **Вывод для CPU.** Цель ≥ 3 чанка/с на CPU достижима на современных 8 ядрах (AVX-VNNI / AVX-512) и на грани для старого AVX2. Порог фиксируем по бенчмаркам M2.
- **Вывод для запроса.** Эмбеддинг запроса съедает 30–80 мс из бюджета поиска `chunks` в 120 мс. Рекомендации:
  1. сессия запросов с 4 потоками, без spinning;
  2. LRU-кэш эмбеддингов запросов на 1024 записи;
  3. замерить p95 под полной нагрузкой индексации.
- **Вывод для GPU.** **Цель «≥ 100 чанков/с на GPU класса RTX 3060+» для чанков по 400 токенов — правка ТЗ.** Варианты: «≥ 30 чанков/с на RTX 3060» или «≥ 100 чанков/с на RTX 4080+».
- **Батчинг.** Чанки сортируем по длине, батч ≤ 8192 токенов (padding `pad_to_multiple_of=8`). Индексация уступает между батчами (§8.1).
- **Замер (задача 3 M2, 2026-10-19).** bge-m3 int8, CPU Ryzen 9 5900X (12 ядер / 24 потока): **3,7 чанка/с** при 24 потоках (3,1 — при 12 и при авто), запрос ≈ 29 мс. bge-m3 fp16 на RTX 3090 (CUDA 13.1 из системы): **141 чанк/с**, запрос ≈ 14 мс.
- **Динамическое квантование и батч.** У int8-графов Xenova (`DynamicQuantizeLinear`) масштаб активаций считается по всему тензору батча: вектор текста зависит от соседей (MiniLM: косинус 0,98–0,992 к одиночному прогону). Поэтому такие модели (`dynamic_quant = true` в `[model.spec]`) прогоняются по одному тексту, без паддинга. На CPU это не медленнее: батч ≤ 8192 токенов дал 3,5 чанка/с против 3,7 по одному. fp16 на GPU батчится, батч и одиночный прогон совпадают (косинус 1,0).

## 12. Сводка рисков M2
1. **RSS ≤ 1,1 ГБ при двух ONNX-сессиях** — нужен общий `PrepackedWeights` плюс замер. Запасной вариант — одна сессия с приоритетным планировщиком.
2. **Качество int8 bge-m3** — гейт на M2. Запасной вариант — свой SmoothQuant или per-channel int8.
3. **Размер GPU-комплекта** — может превысить 2 ГиБ (лимит GitHub на файл) и раздувает комплект. Нужен минимальный набор cuDNN или докачка CUDA. Нужно решение владельца.
4. **Цель GPU в §17** — на 3060 недостижима. Правка ТЗ.
5. **Лицензия Jina-реранкера** — CC-BY-NC. Замена на gte-multilingual-reranker-base или bge-reranker-v2-m3, правка ТЗ.
6. **`tokenizers` без regex-фичи не компилируется.** Правка §5.2: добавить `features = ["fancy-regex"]`.
7. **Panic Qdrant при несовместимом хранилище** — своя метка версии плюс детектор panic, затем wipe и rebuild.
8. **rc-версии `ort`, `process-wrap` 10.x, бета `qdrant-edge`** — закрепление через `=`, обновление отдельной задачей.
