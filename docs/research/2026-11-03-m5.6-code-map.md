# M5.6 «Карта кода» — исследование

Дата: 2026-11-03. Статус: исследование к спецификации `docs/specs/2026-11-03-m5.6-code-map.md`.
Основание: решение владельца 2026-10-28 (`docs/research/2026-10-27-memory-gaps-agent-view.md` §4,

лицензией допустимо, минимум зависимостей; ядро агентонезависимо.

Пометки достоверности: **[замер]** — измерено в этом исследовании (проба в `.tmp/m56/`),
**[источник]** — из документации или кода проекта по ссылке §9, **[оценка]** — вывод составителя.

## 1. Вопрос и итог в одном абзаце

Что даёт агенту карта кода в системе, где он и так свободно делает `Grep`/`Glob`/`Read` (а у Claude
Code есть ещё LSP-плагины)? Итог: **навигация** сама по себе даёт умеренную пользу (ориентация в
новом проекте и у субагента, центральные символы, «кто ссылается» без шума строк и комментариев), а
**уникальная** для ZeroAIMemory ценность — связь памяти с кодом на уровне **символа**: знание
(ловушка, решение, заметка) привязывается к `путь#Тип::метод`, показывается при работе с этим
символом и устаревает только при изменении **его** тела, а не любой строки файла. Рекомендация —
детерминированный экстрактор на tree-sitter в клиенте `zam` (машина агента), на сервер уходят только
метаданные символов (имена, виды, строки, хэши, короткие сигнатуры), ранжирование PageRank по
графу «определения/ссылки» (подход Aider) и выдача в бюджете токенов по запросу; в дайджест — одна
строка-указатель, не карта целиком. LLM, кластеризация и векторный поиск по коду — вне этапа.

## 2. Ценность для агента: что не дублирует Grep/Read

| # | Возможность | Чем агент делает это сейчас | Что даёт карта | Ценность [оценка] |
|---|---|---|---|---|
| 1 | Ориентация в проекте (с чего начать, где центр) | 3–10 вызовов `ls`/`Glob`/`Read README`/`Grep` в начале каждой сессии и у каждого субагента | Сжатая карта «файл → ключевые символы с сигнатурами» в 300–1000 токенов, ранжированная по связности | средняя: экономит вызовы, но стоит токенов, если выдаётся без запроса |
| 2 | Субагент с пустым контекстом | Задание пересказывает родитель вручную (наблюдение M4.5, research 2026-10-27 §5) | Раздел `### Код` пакета `/recall(brief)`: определения символов и файлов из текста задачи | средняя–высокая: субагенты — самый дорогой по повторной разведке случай |
| 3 | «Кто использует X», «где определено X» | `Grep X`: совпадения в строках, комментариях, одноимённых сущностях других модулей | Предвычисленные определения и ссылки по синтаксической роли (вызов, тип, импорт), сгруппированные по файлам | низкая–средняя: без разрешения типов точность близка к grep; у Claude Code с LSP-плагином — ниже нашей нет смысла конкурировать |
| 4 | **Знание о символе** | `file_refs` (M4.5) — только файл: знание о `foo()` показывается на любом чтении файла | Ссылка `путь#символ`; подсказка «о `Foo::bar` в памяти: …» называет символ | **высокая, уникальная** |
| 5 | **Устарелость по символу** | Любая правка файла помечает «возможно устарело» **все** ссылки на файл (ложные срабатывания на больших файлах) | Хэш тела символа: правка соседней функции ссылку не трогает; удаление символа — `symbol_removed` | **высокая, уникальная**: снижает шум G6 «возможно устарело» |
| 6 | Влияние изменения («что я могу сломать») | Нет; ревью вручную | Изменённые символы (по хэшам) → привязанные знания + файлы-потребители на 1 шаг (идея `understand-diff` Understand-Anything) | средняя |
| 7 | Обзор архитектуры для человека | Нет | Страница WebUI: центральные файлы и символы, зависимости верхнего уровня | средняя (для человека, не агента) |

**Чего карта не должна делать (анти-ценность).**
- Подменять поиск агента: Anthropic для Claude Code сознательно выбрала агентный поиск
  (grep/glob/read) вместо векторного индекса кода [источник: публичные выступления команды Claude
  Code 2025, §9]; векторный поиск по коду дублирует сильную сторону агента и тяжёл для HDD.
- Подталкивать перед каждым `Grep/Glob` (уже отвергнуто, review п. 22) и блокировать чтение
  (review п. 23, fail-open §10.3 ТЗ).
- Выдавать карту целиком в каждом дайджесте: при бюджете дайджеста 1500 токенов карта в 1000 токенов
  вытеснит правила и ловушки — главное содержимое памяти. Aider держит карту в 1k токенов по
  умолчанию, но у него нет другой памяти [источник].

**Доказательная база.** Работы 2024–2025 гг. показывают пользу структурного контекста репозитория
для локализации правки: Agentless (скелет файлов на этапе локализации), RepoGraph (ICLR 2025:
граф строк кода «определение/ссылка» как подключаемый модуль к существующим системам повышает долю
решённых задач SWE-bench Lite по данным авторов), LocAgent (ACL 2025: граф кода для локализации) и
repo map Aider [источник, §9]. Ограничение: все замеры — на SWE-bench-подобных задачах с другими
агентами; переносить их на Claude Code с его поиском напрямую нельзя. **Вывод:** пользу навигации
надо **измерить** у себя (агентный A/B — уже запланирован в M6, review п. 12), поэтому в M5.6
навигационная выдача — по запросу и малыми бюджетами, а безусловная ценность этапа — п. 4–5.

**Пересмотр прежней оценки.** Обзор 2026-10-28 относил «собственный построитель графа кода» к «не
брать: высокая стоимость при средней ценности». Решение владельца о встроенной карте снимает вопрос
«делать ли», и честная переоценка стоимости после пробы (§3.4) — **средняя**, а не высокая, если
ограничить объём: детерминированные теги tree-sitter (без LLM-проходов, кластеров и ~40 языков
graphify), 7 языков, ранжирование и выдача в бюджете. Высокой стоимость остаётся у того, что
отнесено «позже»: точное разрешение имён (stack-graphs/SCIP-уровень), кластеры и интерактивный граф,
LLM-сводки по файлам (Understand-Anything).

## 3. Состояние техники: разбор кода

### 3.1. tree-sitter (рекомендуется)

- **Рантайм** — крейт `tree-sitter` **0.27.1** (2026-10-08, MIT, MSRV 1.90) [источник: crates.io].
  Ядро на C (`lib.c`), собирается крейтом `cc`. Инкрементальный разбор, восстановление после
  ошибок (дерево строится и для синтаксически битого файла), запросы S-выражениями (`Query`,
  `QueryCursor` — с 0.25 через `streaming-iterator`; в 0.27 поля `QueryMatch` закрыты, доступ
  методами — [замер]: проба на 0.27 не собралась с `m.captures[i]`, нужен `m.captures()[i]`).
  Отмена долгого разбора — `parse_with_options` с обратным вызовом прогресса (старый
  `set_timeout_micros` убран) [источник].
- **Грамматики** — отдельные крейты, с 0.23 зависят от `tree-sitter-language`, а не от версии
  рантайма: обновления рантайма и грамматик развязаны [источник]. Все — MIT, репозитории
  организации `tree-sitter`. Каждый крейт экспортирует `LANGUAGE`, большинство — и `TAGS_QUERY`
  (запрос `queries/tags.scm` — тот же, что использует навигация GitHub и repo map Aider):

  «Объектный код» — размер `.lib` сборки пробы (MSVC, release); итоговый исполняемый файл пробы со
  всеми девятью грамматиками, `strip`, thin LTO — **17,0 МБ** [замер]. Нынешний `zam.exe` release —
  7,7 МБ [замер]. Даты последних выпусков TypeScript и C++ — 2024 г.: грамматики стабильны, но это
  риск поддержки, который снимается закреплением версий и собственными запросами.
- **Сборка C.** Нужен компилятор C11: на Windows — MSVC `cl.exe` (уже требуется: `rusqlite`
  `bundled` собирает SQLite из C), на Linux — gcc/clang (уже требуется по той же причине). Проба
  собралась без доработок, холодная сборка всех девяти грамматик и рантайма — ≈ 25 с при `-j 2` на
  HDD [замер]. Новой системной зависимости нет.
- **Вариант WASM** (фича `wasm` рантайма: грамматики как `.wasm`, исполнение в `wasmtime`): плюсы —
  грамматики изолированы песочницей WASM и подключаются без пересборки; минусы — `wasmtime` —
  десятки крейтов и мегабайты кода, медленнее нативного разбора, сложнее аудит. Для клиента с
  требованием «холодный старт ≤ 20 мс» и «минимум зависимостей» — **не брать**; держать как путь
  к изоляции, если разбор недоверенного кода станет угрозой (§6).
- **Чистый Rust-рантайм** `tree-sitter-c2rust` 0.25.2 (перевод C-рантайма c2rust) — грамматики
  всё равно на C, выигрыша по сборке нет, сопровождение слабее — не брать [источник].

### 3.3. Repo map Aider (образец ранжирования)

[источник: `aider/repomap.py`, Apache-2.0, документация repo map]
- Теги `definition.*`/`reference.*` из `tags.scm` по каждому файлу; кэш тегов по `mtime`.
- Граф **файлов**: ребро «файл, где идентификатор упомянут → файл, где он определён», вес —
  √(числа упоминаний) × множитель идентификатора: ×10 для упомянутых в разговоре, ×10 для «длинных»
  имён (≥ 8 символов в snake/camel), ×0,1 для `_приватных`, ×0,1 для имён, определённых во многих
  файлах (общие слова).
- PageRank с **персонализацией** (файлы в чате и упомянутые идентификаторы), ранг файла делится
  между его определениями пропорционально весам входящих рёбер.
- Вывод — файлы по рангу, в каждом — строки определений с контекстом (`⋮` вместо пропусков);
  бинарный поиск по числу тегов, чтобы уложиться в `--map-tokens` (1024 по умолчанию; без файлов в
  чате бюджет расширяется).
- **Что берём**: теги, граф файлов, веса идентификаторов, персонализированный PageRank, упаковку в
  бюджет. **Чего не берём**: показ строк тела (тела на сервер не уходят — ТЗ §7.10), кэш по `mtime`
  (меняется при checkout — урок M4.5: отпечаток содержимого).

## 5. Архитектура: где строится, где хранится, как обновляется

### 5.1. Где строить карту

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Сервер по пути проекта | один построитель, нет загрузки | сервер и проект обычно на **разных машинах** (LAN, §4.2 ТЗ); серверу пришлось бы читать ФС пользователя; разные машины — разные рабочие копии |
| **Б. Клиент `zam` на машине агента, на сервер — метаданные** | код там же, где агент и хуки; тела файлов не покидают машину (ТЗ §7.10); работает при сервере в LAN; карта доступна MCP, WebUI и участникам общего решения | грамматики в бинарнике `zam`; загрузка метаданных по сети |
| В. Только локально (кэш на машине) | ничего не уходит | MCP по HTTP и WebUI карты не видят; агентонезависимость по REST/MCP ломается; у `zam` нет SQLite (ТЗ §13.2) |

**Рекомендация — Б.** Разбор и вычисление хэшей — в клиенте; хранение, ранжирование, выдача,
связь с памятью — на сервере (принцип «ядро — REST»). Для хуков без сети достаточно уже имеющегося
кэша `file-refs.json`, дополненного символами.

**Что уходит на сервер.** Путь, язык, хэш содержимого и git-oid файла; по символу — имя,
квалифицированное имя (контейнер), вид, строки начала и конца, хэш тела (16 hex blake3
нормализованного текста), признак экспорта и **сигнатура** — первая строка определения, не длиннее
160 символов. Сигнатура — это фрагмент кода, отступление от «тела файлов на сервер не уходят
никогда»: без неё карта — список имён и теряет главное свойство repo map (сигнатуры вместо чтения
файла). Предлагается отправка по умолчанию с выключателем `code.send_signatures` и маскировкой
секретов сервером (`mask_text`, §7.6) — **вопрос владельцу**.

### 5.2. Хранение

SQLite базы **владельца решения** (как `file_refs`, ТЗ §6.3; участник общего решения пишет в базу
владельца), новая пользовательская миграция `0023_code_map.sql`: снимок решения, файлы, символы,
агрегированные ссылки, FTS5 по разбитым на слова именам (`getUserById` → `get user by id`), рёбра
файлов с весами и ранги. Qdrant не используется (векторов кода нет). Объём на проект уровня
ZeroAIMemory: ≈ 10 тыс. символов и ≈ 20–30 тыс. агрегированных ссылок — единицы мегабайт [оценка].

**Одна карта на решение** («последний снимок побеждает» пофайлово, с коммитом, веткой и машиной
загрузки в каждой строке файла). Разные машины на разных ветках будут перезаписывать файлы друг
друга — это показывается в заголовке карты («снимок: ветка, коммит, машина, возраст»). Карты по
веткам — позже: они умножают хранение и усложняют выдачу ради редкого случая.

### 5.3. Инкрементальность

- **Отпечаток файла.** В git-репозитории — `git ls-files -s -z` (oid блоба из индекса, без чтения
  файла — важно для HDD) плюс `git status --porcelain=v2 -z` для изменённых и неотслеживаемых
  (их — blake3 содержимого, как у `file_refs`); вне git — размер и `mtime` как предфильтр, затем
  blake3. Опора только на `mtime` отвергнута (меняется при checkout — урок M4.5, review п. 6).
- **Синхронизация в два шага.** `POST /code/sync` с манифестом `{path, hash}` → сервер отвечает,
  каких файлов у него нет или они другие, и удаляет из карты отсутствующие в манифесте; затем
  загрузка только нужных файлов пачками. Так ни локальный кэш, ни сервер не обязаны быть
  «правыми»: расхождение (другая машина, сброс кэша) исправляется первым же шагом.
- **Когда.** Вручную `zam code sync`; автоматически — фоновый отсоединённый процесс, который хук
  `session-start` (и `checkpoint` при наличии правок) запускает не чаще `code.auto_interval_min`
  (30 мин) или при смене `HEAD`, под файлом-замком. Хук не ждёт процесс: бюджеты §10.3 не
  меняются. Git-хуки репозитория не ставятся (вмешательство в чужую настройку) — позже по желанию.
- **Ранжирование** пересчитывается на сервере после синхронизации (флаг «ранги устарели»,
  пересчёт при первом запросе карты; PageRank на 10⁴ файлов — миллисекунды [оценка]).

### 5.4. Связь с памятью

- Ссылка на символ — `путь#квалифицированное_имя` (`crates/zam-store/src/refs.rs#mark_changed`,
  `src/app.ts#App.start`) в `refs.files` записей (`{path, symbol, hash?, symbol_hash?}`) и во
  frontmatter `refs:` заметок. `zam` (CLI и хуки) дописывает хэш тела символа, как сейчас хэш файла.
- **Устарелость по символу**: очередь изменённых файлов (`changed-<сессия>.jsonl`, §10.7 ТЗ) для
  файлов, у которых в `file-refs.json` есть ссылки на символы, несёт хэши этих символов (разбор
  одного файла в `post-tool` под отсечкой 20 мс и пределом 512 КиБ; не успел — без символов, и
  ссылка устаревает пофайлово, как сейчас). Сервер в `POST /files/changed`: символ не изменился —
  ссылка `ok` при изменённом файле; изменился — `stale`, `stale_reason = symbol_changed`; исчез —
  `symbol_removed`. Синхронизация карты применяет то же правило к загруженным файлам.
- **Знание о файле при чтении** (`post-tool Read`, `pre-tool`) называет символ: «о `Foo::bar` в
  `a.rs` в памяти: …». Сети по-прежнему нет — источник `file-refs.json`.
- Отчёты (M5.5) рёбер и `file_refs` не создают — и символьных тоже.

### 5.5. Выдача агенту

- **Карта по запросу** — `GET /code/map` (REST), инструмент MCP, `zam code map`: Markdown «файл →
  символы с сигнатурами и строками» в бюджете (по умолчанию 1000 токенов), персонализация по
  `focus` (пути, идентификаторы, текст задачи), заголовок со свежестью снимка.
- **Символ** — карточка: определение (путь, строки, сигнатура), кто ссылается (файлы, число),
  на что ссылается, **привязанные знания** (записи и заметки с `refs` на символ или файл).
- **Влияние** — по изменённым символам (клиент сравнивает хэши с картой): привязанные знания и
  потребители на 1 шаг.
- **Дайджест `session_start`** — одна строка (≤ 80 токенов): «Карта кода: N файлов, M символов,
  снимок <возраст>; центральные: A, B, C — `memory_code`/`zam code map`». Полная карта в дайджест
  не входит (анти-цель §2).
- **Пакет субагенту `/recall(brief)`** — раздел `### Код` (≤ 150 токенов внутри `brief_tokens`):
  определения идентификаторов и файлов, названных в задаче.
- **MCP.** Сейчас 10 инструментов (тест `mcp_tool_count_still_10`). Варианты: (а) новый инструмент
  `memory_code {action: map|symbol|refs|impact}` — понятная агенту семантика, +≈ 80 токенов описания
  в каждой сессии; (б) без нового инструмента: символы как вид `symbol` в `memory_search` и
  `memory_read s:<id>`, карта — `memory_recall event=code_map`. (б) смешивает структурные запросы с
  поиском по памяти и нарушает анти-цель «символы не шумят в поиске памяти». Рекомендация — (а),
  **вопрос владельцу**.

## 6. Безопасность разбора

Вход парсера — код рабочей копии на машине агента: обычно свой, но может быть клонированный чужой
репозиторий, сгенерированные и минифицированные файлы, бинарные данные с «кодовым» расширением.
Угроза — не утечка (данные и так на этой машине), а **отказ**: зависание, взрыв памяти, падение
C-кода грамматики (внешние сканеры грамматик на C фаззятся слабее рантайма) и, как следствие,
сбой хука или фонового процесса.

Меры (по образцу `doc-worker` M5, но без отдельного процесса):
- пределы: файл ≤ `code.max_file_bytes` (1 МиБ), файлов ≤ `code.max_files` (50 000), символов на
  файл ≤ 5000, агрегированных ссылок ≤ 20 000; отсечка разбора файла по времени 200 мс через
  обратный вызов прогресса; эвристика «минифицирован/сгенерирован» (средняя длина строки > 300 или
  строка > 10 000 символов) и «бинарный» (NUL в первых 8 КиБ) — пропуск с причиной;
- обход без рекурсии по дереву (курсор), без следования по символическим ссылкам, только внутри
  корня решения, только файлы `git ls-files` (учитывает `.gitignore`) плюс `code.exclude`;
- **журнал падений**: перед разбором файла его путь пишется в `cache/code-parsing.json`; если
  процесс упал (паника C-кода не ловится `catch_unwind`), следующий запуск видит незакрытую запись и
  пропускает файл с причиной `parser_crash` — один плохой файл не ломает карту навсегда;
- паника Rust-кода — `catch_unwind` на файл; хуки никогда не разбирают всё — только один файл под
  отсечкой, при любом сбое — fail-open;
- сервер проверяет вход как недоверенный: длины имён (≤ 256) и сигнатур (≤ 160), управляющие
  символы, пути по правилам `file_refs` (ТЗ §7.10), пределы запроса (≤ 500 файлов, ≤ 8 МиБ),
  маскировка секретов в сигнатурах;
- зависимости: версии грамматик закреплены (`=x.y.z`), лицензии MIT — в `deploy/licenses`,
  `cargo deny`/аудит как у остальных; fuzz-цель экстрактора (по образцу `fuzz-check` M5).

Отдельный рабочий процесс с лимитом памяти ОС (как `doc-worker`) — не в этапе: разбор идёт в
собственном процессе пользователя на его машине, падение затрагивает только фоновую синхронизацию;
песочница ОС — вместе с песочницей `doc-worker` в M7 **[решение составителя, на подтверждение]**.

## 8. Рекомендация

1. Экстрактор — tree-sitter 0.27 + грамматики Rust, TS/TSX, JS, Python, Go, Java (+C# по ответу
   владельца), запросы тегов — встроенные `TAGS_QUERY` с собственными дополнениями (контейнеры для
   квалифицированных имён, C#), новый крейт `zam-code` без tokio и SQLite.
2. Строит клиент `zam` на машине агента (`zam code sync`, фоновый запуск из хуков), на сервер —
   только метаданные символов; хранение — база владельца решения, миграция `0023`.
3. Ранжирование — персонализированный PageRank по графу файлов (веса Aider), выдача — по запросу
   в бюджете токенов; в дайджест — строка-указатель, в пакет субагента — раздел `### Код`.
4. Главная ценность — ссылки памяти на символы и устарелость по хэшу тела символа.
5. MCP — один новый инструмент `memory_code` (вопрос владельцу); WebUI — страница «Код» без
   интерактивного графа.
6. Пользу навигации измерить агентным A/B в M6 и по нему решать, расширять ли выдачу без запроса.
