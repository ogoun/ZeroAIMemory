# Чего не хватает памяти для работы «в бою»: взгляд агента

Дата: 2026-10-27. Повод — предложение владельца добавить словарь домена. Документ —
предложение на решение владельца; в ТЗ и план ничего не внесено.

Основа — собственный опыт этой разработки: за M3–M4 я вёл вручную ledger задач, список
«вопросов владельцу», журнал решений владельца, заметку о тестовом стенде, правила окружения
(`. scripts/dev-env.ps1`, `CARGO_TARGET_DIR`), и после каждого сжатия контекста
восстанавливался по этим файлам. Всё это — то, что должна была бы держать сама память.

## 1. Словарь домена (Glossary) — предложение владельца

**Зачем.** Термины проекта сейчас разбросаны по заметкам; агент угадывает смысл из
контекста, пишет одно понятие разными словами, и поиск по одному слову не находит записи,
сделанные с другим. Пример из этого проекта: «решение» = solution = проект = пространство
решения; «выжимка» = summary = cache entry; «перенарезка» = rechunk.

**Форма — встроенный журнал `glossary`** (рядом с Changelog, Releases, Insights), а не папка
заметок: нужны структура, дедупликация по термину и история замещения.

```jsonc
{
  "kind": "term",
  "term": "Выжимка",                       // каноническое имя, уникально в пространстве (без учёта регистра)
  "aliases": ["summary", "cache entry", "выжимка кэша"],   // синонимы, сокращения, другие языки
  "definition": "Ответ агента, собранный из нескольких источников и сохранённый в кэш (§9.4).",  // ≤ 1–2 фразы = L0
  "body": "markdown: подробности, примеры, границы понятия",
  "not_to_confuse": ["Сводка L1"],        // похожие, но другие понятия
  "code": ["answer_cache", "CacheHit"],    // как термин назван в коде, таблицах, API
  "related": ["term:<id>", "node:<id>"],
  "certainty": "axiom | theorem | hypothesis",  // термин от владельца — axiom
  "area": "…", "scope": "solution | global"     // global — словарь пользователя в Knowledge
}
```

**Что словарь даёт механически, а не только как справочник:**
1. **Расширение запроса в поиске.** Псевдонимы термина добавляются в FTS-запрос (с весом ниже
   исходного): поиск «summary» находит записи со словом «выжимка», RU↔EN. Самый большой
   выигрыш в полноте при нулевой цене для агента.
2. **Подсказка к промпту.** Термин или его псевдоним в промпте пользователя → в
   `/recall(prompt)` одна строка определения (как триггер `keyword`, по разу за сессию).
3. **Дайджест старта.** Строка «Словарь: N терминов — `zam glossary`»; сами определения —
   только по запросу или по совпадению, чтобы не съедать бюджет 1500 токенов.
4. **Единообразие записей.** При записи заметки или insight сервер возвращает
   `warnings: ["term: «cache entry» → «Выжимка»"]`, если использован псевдоним вместо
   канонического имени (мягко, без отказа). Агент правит текст или игнорирует.
5. **Ссылки.** `[[Выжимка]]` в Markdown разрешается в термин; в WebUI — всплывающее определение.
6. **Для человека** — страница «Словарь» в WebUI: алфавитный список, поиск, правка.

Инструменты: `memory_glossary` (MCP: list/get/upsert), `zam glossary [term]`, раздел в блоке
инструкции одной строкой («новое понятие проекта — в словарь; пиши каноническими терминами»).
Оценка: средняя (журнал по образцу insights + расширение FTS + предупреждения записи).

## 2. Что ещё нужно мне как агенту (по убыванию пользы)

### 2.1. Состояние работы и передача между сессиями (handoff) — критично
**Проблема.** Память хранит знания, но не «где я остановился». После сжатия контекста или в
новой сессии агент не знает текущую задачу, план, что сделано, что заблокировано. Я решал это
файлом ledger — его структура и есть требование.
**Предложение.** Журнал `worklog` решения: записи `task` со статусами
`open | in_progress | blocked | done | dropped`, полями `plan`, `next_step`, `blocked_by`,
`owner` (агент или человек), `links` на заметки и коммиты. Дайджест старта показывает
незакрытые (`in_progress`, `blocked`) первыми строками; `checkpoint` перед остановкой просит
обновить `next_step`. Инструмент `memory_task`.
**Цена ошибки отсутствия:** повторение сделанного — то самое «агент забывает пройденное»
(проблема 1 ТЗ), только на уровне задач.

### 2.2. Открытые вопросы к человеку и его ответы — критично
**Проблема.** 26 вопросов M3 я держал вручную в журнале этапа, ответы владельца — там же.
Агенту нужно: копить вопросы, не дёргая человека; не задавать уже отвеченное; видеть ответ как
решение с авторитетом человека.
**Предложение.** Запись `question` (в том же `worklog` или отдельно): `question`, `options`,
`recommendation`, `status: open | answered | obsolete`, `answer` (заполняет человек в WebUI —
страница «Вопросы» с ответом в один клик по варианту), `answered_by`. Ответ человека
автоматически становится insight `decision` с `certainty: axiom` и ссылкой на вопрос.
Дайджест: «Ответы владельца с прошлой сессии: …» — один раз.

### 2.3. Решения с обоснованием (ADR) — высокая
`decision` в insights есть, но без структуры: нет альтернатив, кто решил, последствий. В этом
проекте десятки «решение владельца 2026-10-26» живут в тексте ТЗ.
**Предложение.** `data.decision {context, options[], chosen, rationale, consequences,
decided_by: human|agent, revisit_if}`; фильтр «решения человека»; при попытке агента записать
противоречащее решение (векторная близость к `decision`-axiom) — предупреждение со ссылкой.

### 2.4. Привязка знаний к файлам кода и автоматическая устарелость — высокая
**Проблема.** Заметка «как устроен `init.rs`» тихо устаревает после правки файла. Триггеры
`file_glob` задаются вручную и только у insights.
**Предложение.**
- У заметок и записей — `refs.files` (путь в решении, опционально git-хэш содержимого на
  момент записи).
- `pre-tool` хук: правка файла → локально находит записи со ссылкой на этот путь и показывает
  их (как `file_glob`, но без ручной настройки) — «перед правкой init.rs: 2 записи».
- `post-tool` после Write/Edit сообщает серверу хэш файла (без содержимого); запись, чей
  `refs.files` хэш разошёлся, получает `stale: source_changed` — тот же механизм, что у кэша
  выжимок (§9.4), и видна в выдаче как «возможно устарело».
- Обратный запрос: «что память знает об этом файле» — `zam links file:<path>`.

### 2.5. Окружение и инфраструктура — высокая
Хосты, стенды, порты, учётки (ссылками на Vault), машины разработчиков, версии инструментов.
Сейчас это свободные заметки (я сам завёл заметку о стенде вне памяти проекта).
**Предложение.** Заготовка «Окружение» (папка с шаблоном) в каждом решении и в Knowledge;
шаблон записи: назначение, адрес, доступ (`vault:<id>`), ограничения («2 ГБ RAM, тайминги не
мерить»), кто выдал, дата. Секреты — только ссылкой на Vault.

### 2.6. Проверенные команды (runbook) — средняя
Как собрать, протестировать, развернуть, с подтверждённой датой и `certainty: theorem`
(evidence — «запущено, код 0»). Я каждую сессию заново вспоминаю `. scripts/dev-env.ps1`,
обход «занятых» exe через `CARGO_TARGET_DIR`, длительность полного прогона.
**Предложение.** Заготовка «Команды» + поле `verified_at` у заметок; дайджест старта
включает L0 заметки «Команды» решения. Устаревание — по `refs.files` (2.4) или по сроку.

### 2.7. Кандидаты в Rules от агента (черновики на подтверждение) — средняя
Rules пишет человек; агент замечает устойчивые предпочтения («отвечай по-русски», «без
Docker») и сейчас может только записать insight. В ТЗ это v2 (§10.6).
**Предложение:** поднять в ближайший этап узкую часть — `rule_proposal` от агента,
страница «Предложения» в WebUI, принять → правило в Rules (axiom), отклонить → больше не
предлагать.

### 2.8. Гигиена памяти — средняя
Со временем память зарастает: дубли заметок, записи с `useless` > `useful`, давно не
читанные, `stale` без пересмотра, `hypothesis` без проверки дольше N дней.
**Предложение.** Очередь «На пересмотр» в WebUI и `zam review` для агента (по запросу
пользователя: «прибери память»), отчёт без автоматических действий.

### 2.9. Импорт существующих документов проекта — средняя
При подключении к живому проекту в репозитории уже есть README, docs/, ADR. Агент должен
«прочитать проект» один раз: `zam import <dir> --into <path>` (Markdown — сразу; DOCX/PDF —
с M5), с `refs.files` на исходники (2.4), чтобы заметка устаревала вместе с файлом.

### 2.10. Мелочи, которые заметил в бою
- Абсолютные даты: сервер нормализует «вчера», «на прошлой неделе» в записях агента нельзя —
  только в инструкции; но в выдаче стоит показывать возраст записи («3 дня назад») рядом с датой.
- `zam read` по ссылке из выдачи — исправлено сегодня (B2): ссылки из выдачи должны
  читаться без преобразований везде (CLI, MCP, WebUI).
- Порядок ответов `zam mcp` — описан; зависимые операции агент делает последовательно.
