Статус: **перенесено в ТЗ v1.22** (2026-11-03, выпуск `0.0.9-m5.6`; §7.12 «Карта кода» и по разделам

**Отступления реализации от этой спецификации** (по коду; подробности — ТЗ и журнал этапа):
1. §6: столбцы коммита — `git_commit`; у снимка есть `gen`; у `code_symbols` нет `rank` — ранг символа
   = `code_files.rank` × доля из `code_files.shares` (BLOB); таблицы `code_file_edges` нет; FTS
   символов — с токеном решения `sol` и видом `kind` в `MATCH`, префиксы 2 и 3.
2. §7: счётчик токенов карты — `zam_store::count_tokens` (точный bge-m3 при загруженной модели), а
   не всегда `ApproxCounter` (решение составителя плана 12).
3. §8: `post-tool` кладёт в очередь хэши **всех** символов правленого файла (до 5000), а не только
   из ссылок (решение составителя плана 5); отсечка разбора 20 мс — на все файлы хука; контракт
   `symbols` — «присланный список полный, иначе поля нет» (поля `complete` нет); символов больше
   `code.max_symbols_per_file` у `/files/changed`/`/files/verified` — суд по хэшу файла, у
   `/code/impact` — 422; символьная ссылка при `ok` принимает новый хэш файла, удалённый файл —
   `symbol_removed`; `PUT /code/files` судит только ссылки на символы; причина `symbol_changed` /
   `symbol_removed` в `GET /file-refs` не отдаётся (только `state`).
4. §9: добавлены `GET /code/files?solution=&lang=&q=&offset=&limit=` (таблица файлов WebUI, `limit`
   ≤ 200) и параметр `files` (1..=1000) у `GET /code/map` (первые N файлов по рангу, рёбра только
   между ними, часть `ETag`); карточка — `GET /code/symbols/{id | путь#qual}` (id нестабилен);
   `ETag` — слабый `W/"…"`; формат знания карточки и влияния — `{path, id, kind, title, state,
   space, symbol?}` со схлопыванием (у записи со ссылками на файл и на его символ остаётся строка
   символа); `zam code sync --prune` (предохранитель массового удаления); у `/code/sync` свой предел
   тела (`max_files × 1100` байт, не меньше `code.max_request_bytes`).
5. §10: строка дайджеста — «ZeroAIMemory: карта кода: N файлов, M символов, снимок <возраст>
   (<ветка>@<коммит7>); центральные: A, B, C — `memory_code`/`zam code map`» (ветка до 40 символов,
   `qual` до 48, сокращение центральных до 0); поле `code_map` у `POST /recall` — гейт типа
   подсказок только у хуков; строка `### Код` — `<путь>:<line> <kind> <sig или qual>`; блок v5 —
   строка без `memory_code/` («карта — `zam code map`»), в протокол перенесены три фразы (решение 18).
6. §11: «Обзор» — до 120 **самых весомых** рёбер, порог `OVERVIEW_MIN_EDGE_WEIGHT = 0` со строгим `>`
   (а не «вес ≥ порога»); карточка в адресе — по `путь#qual`.
7. §12: сервер на символы и ссылки сверх `max_symbols_per_file`/`max_refs_per_file` отвечает 422
   (клиент сам отсекает до `partial`/`limit`); `max_request_bytes` — 1 КиБ..=256 МиБ,
   `rank_timeout_ms` — 0..=60000.
8. §13, §17 п. 7: журнал падений — без fsync; крючок обрыва — `ZAM_DEBUG_CODE_ABORT=<путь>`
   (debug); версия разбора `EXTRACT_VERSION` — перезагрузка карты при смене.
9. Финальное ревью ветки (2026-11-04): §8 — `split_ref` линеен и не разбирает строку длиннее
   `REF_MAX_BYTES` (путь, отвергается нормализацией); якорь строки GitHub (`путь#L10`,
   `путь#L10-L20`, `путь#L10-20`) — не символ, ссылка остаётся путём целиком, как в 0.0.8; §9, §12 —
   пересчёт рангов и чтение входов вне кэша — не больше 2 на сервер (ожидание слота — в пределах
   `rank_timeout_ms`, иначе `rank pending`); `PUT /code/files` — файлы из сырых срезов тела без
   промежуточного `Value`; `zam` шлёт `symbols` в `/files/verified` только путям со ссылками на
   символы и повторяет пачку без поля при 422 сервера 0.0.8.
10. §17 п. 3 **не выполнен**: 1/10 ключевых типов в первых 15 центральных (порог 6) — разбор в ТЗ
   §18.2 и журнале этапа, решение — за владельцем.

## 1. Назначение

Карта кода — детерминированный индекс **символов** решения (функции, методы, типы, модули) с
определениями, ссылками и рангом связности, построенный парсером на машине агента. Две задачи:

1. **Память ↔ код на уровне символа** (главная): знание привязывается к `путь#символ`,
   показывается при работе с файлом символа с его именем и устаревает только при изменении тела
   **этого** символа. Сейчас (M4.5) знание привязано к файлу целиком, и любая правка файла помечает
   все его ссылки «возможно устарело».
2. **Ориентация без лишних вызовов**: сжатая карта «файл → ключевые символы с сигнатурами» в бюджете
   токенов по запросу, раздел `### Код` в пакете субагенту, карточка символа (кто ссылается,
   привязанные знания), влияние изменения.

## 2. Цели, не-цели, анти-цели

**Цели.**
- Экстрактор символов на tree-sitter для Rust, TypeScript/TSX, JavaScript/JSX, Python, Go, Java
  (+C# — §15 п. 2) в клиенте `zam`; инкрементальная синхронизация с сервером по отпечаткам файлов.
- Хранение карты решения в базе владельца, ранжирование (персонализированный PageRank), выдача
  карты в бюджете, поиск и карточка символа, влияние изменения — REST, MCP, CLI.
- Ссылки памяти на символы и устарелость по хэшу тела символа.
- Страница «Код» в WebUI: состояние, поиск символа, карточка, обзор зависимостей Mermaid.

**Не-цели (этап).**
- Точное разрешение имён с типами (уровень LSP/SCIP/stack-graphs): ссылки разрешаются по имени с
  весами; неоднозначность видна, но не устраняется.
- LLM-сводки файлов, слои архитектуры, туры (на сервере нет генеративной модели, ТЗ §4.1 п. 2).
- Векторный и полнотекстовый поиск по **телам** кода: тела на сервер не уходят (ТЗ §7.10).
- Кластеры Leiden/Louvain, интерактивный граф кода, карты по веткам, C/C++, Svelte/Vue (§14).

**Анти-цели** (провал, даже если «работает»).
- Карта вытесняет память: полная карта в дайджесте `session_start`, символы в выдаче
  `memory_search`, подсказки «посмотри карту» перед `Grep/Glob`.
- Хук ждёт построения карты или разбирает больше одного файла: бюджеты §10.3 ТЗ не меняются.
- Тела файлов на сервере (кроме сигнатур в пределе §4 — §15 п. 1).
- Один плохой файл (минифицированный, бинарный, роняющий грамматику) ломает синхронизацию навсегда.
- Ложная устарелость растёт: правка файла должна давать **не больше** устаревших ссылок, чем в M4.5.

## 3. Языки и экстрактор

**[решение составителя, на подтверждение владельцу]** Новый крейт `zam-code` (без tokio и SQLite):
- фича `parse` (по умолчанию выключена) — рантайм `tree-sitter` 0.27 и грамматики (версии
  закреплены `=x.y.z`, все MIT; аудит — исследование §3.1); её включает только `zam-cli`;
- без фичи — чистые функции, общие для клиента и сервера: типы протокола, нормализация имён (разбиение
  `camelCase`/`snake_case` для FTS), ранжирование и упаковка карты в бюджет (§7). Так сервер не тянет
  C-код грамматик.

| Язык | Расширения | Запрос тегов |
|---|---|---|
| Rust | `.rs` | `TAGS_QUERY` грамматики + контейнеры `impl`/`trait`/`mod` |
| TypeScript, TSX | `.ts .mts .cts`, `.tsx` | `TAGS_QUERY` + контейнеры `class`/`interface`/`namespace` |
| JavaScript, JSX | `.js .mjs .cjs .jsx` | `TAGS_QUERY` + контейнер `class` |
| Python | `.py .pyi` | `TAGS_QUERY` + контейнер `class` |
| Go | `.go` | `TAGS_QUERY` + получатель метода |
| Java | `.java` | `TAGS_QUERY` + контейнеры `class`/`interface`/`enum` |
| C# (§15 п. 2) | `.cs` | собственный запрос (в крейте `TAGS_QUERY` нет) |

Собственные запросы — `crates/zam-code/queries/<язык>.scm` (дополнения к встроенным, лицензия
исходных `tags.scm` — MIT, уведомление в `deploy/licenses`).

**Символ**: `name`; `qual` — квалифицированное имя через `::` по цепочке контейнеров
(`Store::open`, `App.start` → `App::start`; разделитель единый для всех языков); `kind` —
`function | method | class | struct | enum | interface | trait | type | const | module | macro`;
`line`, `end_line` (с 1); `sig` — первая непустая строка определения без хвостовых пробелов,
≤ 160 символов (обрезка по символу с `…`); `body_hash` — 16 hex blake3 текста узла определения, в
котором строки обрезаны по краям и пустые строки убраны (переформатирование отступов хэш не меняет);
`exported` — признак публичности, где язык его выражает (`pub`, `export`, заглавная буква Go,
`public`), иначе `null`. Одноимённые символы одного файла (`impl` для разных типов, перегрузки)
различаются `qual` и, при совпадении, суффиксом `#2`, `#3` по порядку в файле.

**Ссылка** (агрегированно): `(name, kind ∈ call | type | import | impl | other, count, first_line)`
на файл. Ссылки внутри символа к нему не привязываются (точность «кто именно вызывает» без
разрешения типов — позже).

## 4. Где строится и что уходит на сервер

**[решение составителя, на подтверждение владельцу]** Строит клиент `zam` на машине агента (сервер и
проект обычно на разных машинах; хуки — на машине агента). На сервер уходят **только метаданные**:
путь (правила `file_refs`, ТЗ §7.10), язык, `hash` (blake3 содержимого, 64 hex), `git_oid` (если
файл чистый в git), размер, состояние разбора и причина пропуска, символы (поля §3, в том числе
`sig`) и агрегированные ссылки. Содержимое файлов — никогда. Сигнатуры — с выключателем
`code.send_signatures` (`true`; `false` — поле `sig` не отправляется, карта показывает только имена
и виды) и маскировкой секретов сервером (`zam_markdown::mask_text`) — §15 п. 1.

**Отпечатки и обход.** Корень — корень решения хуков (ТЗ §10.3, «корень»). В git — список и oid из
`git ls-files -s -z`, изменённые и неотслеживаемые (не игнорируемые) — из
`git status --porcelain=v2 -z`, у них — blake3 содержимого; вне git — обход каталогов с пропуском
`.git`, `.zeroaimemory`, `target`, `node_modules`, `dist`, `build`, скрытых каталогов, предфильтр
размер+`mtime`, затем blake3. Символические ссылки не обходятся. `code.exclude` — маски `globset`.
Локальное состояние — `.zeroaimemory/cache/code-state.json` `{server, solution, files: {path:
{fp, size, mtime, sent_at}}}` (запись атомарно, права 0600, как кэши M4).

## 5. Синхронизация

1. `POST /code/sync {solution, commit?, branch?, machine?, manifest: [{path, hash}]}` (до
   `code.max_files`) → `{need: [path], removed: N, etag}`: сервер удаляет из карты файлы, которых
   нет в манифесте, и возвращает пути, которых у него нет или чей `hash` другой.
2. Клиент разбирает только `need` и отправляет пачками `PUT /code/files {solution, commit?,
   branch?, machine?, files: [...]}` (до 500 файлов и `code.max_request_bytes` 8 МиБ на запрос) →
   `{accepted, stale_refs, warnings}`; файл с изменившимися символами применяет правило
   устарелости §8 к ссылкам на него.
3. После загрузки ранги помечаются устаревшими и пересчитываются при первом запросе карты
   (§7; не дольше 1 с на 50 тыс. файлов, иначе — старые ранги и `warnings: ["rank pending"]`).

**Одна карта на решение** — «последний снимок побеждает» пофайлово; каждая строка файла хранит
`commit`, `branch`, `machine`, `user_id`, `updated_at`; заголовок карты называет преобладающий снимок
и долю файлов из других **[решение составителя, на подтверждение владельцу]** (§15 п. 6).

**Когда.** `zam code sync` вручную; автоматически при `code.auto = true` (клиент) — хук
`session-start` и `checkpoint` (если были правки) запускают **отсоединённый** процесс
`zam code sync --background` и не ждут его: не чаще `code.auto_interval_min` (30) после прошлой
успешной синхронизации или сразу при смене `HEAD`; замок `cache/code-sync.lock` (живой — второй не
запускается; брошенный старше 30 мин — снимается); вывод фонового процесса — только строка итога
или ошибки в `hooks.log` **[решение составителя, на подтверждение владельцу]** (§15 п. 5). Запуск
стоит хуку ≤ 10 мс; сбой запуска — fail-open.

**Права.** Синхронизация — владелец решения и участник с `rw` (токен или cookie); чтение карты —
любой с правом чтения решения (в том числе `ro`); `DELETE /code?solution=` (очистить карту) —
только владелец решения в WebUI; отозванный доступ — как у поиска (ТЗ §11.6). Карта существует
только у пространств решений; Knowledge, Rules, Human — 422.

## 6. Модель данных (пользовательская миграция `0023_code_map.sql`)

| Таблица | Поля (кратко) |
|---|---|
| `code_snapshots` | `solution_guid` PK, `commit`, `branch`, `machine`, `updated_at`, `files`, `symbols`, `etag`, `rank_state` (`ok`/`pending`), `ranked_at` |
| `code_files` | `id`, `solution_guid`, `path`, `lang`, `content_hash`, `git_oid`, `size`, `parse_state` (`ok`/`partial`/`skipped`), `skip_reason` (`too_large`/`minified`/`binary`/`timeout`/`parser_crash`/`limit`/`lang`), `symbols`, `rank`, `commit`, `branch`, `machine`, `user_id`, `updated_at`; уникальность `(solution_guid, path)` |
| `code_symbols` | `id`, `file_id` → `code_files` (каскад), `name`, `qual`, `kind`, `line`, `end_line`, `sig`, `body_hash`, `exported`, `rank`; индексы `(file_id)`, `(name)`, `(qual)` |
| `code_symbols_fts` | FTS5 по `name`, `qual`, `terms` (разбиение имени на слова, §3) |
| `code_refs` | `file_id`, `name`, `kind`, `count`, `first_line`; уникальность `(file_id, name, kind)` |
| `file_refs` (+) | `symbol TEXT NULL` (квалифицированное имя), `symbol_hash TEXT NULL`; уникальный индекс владельца пересоздаётся как `(owner_kind, owner_id, path, COALESCE(symbol, ''))`; `stale_reason` += `symbol_changed`, `symbol_removed` |

Граф файлов не хранится (таблицы `code_file_edges` нет): рёбра считаются по запросу из
`code_refs` **[решение контроллера по ревью задачи 2]**.

Системных миграций нет. Карта — производные данные: в бэкап входит, но восстанавливается полной
синхронизацией; удаление решения удаляет карту. Номер миграции фиксирует план.

## 7. Ранжирование и карта в бюджете

**[решение составителя]** По образцу repo map Aider (Apache-2.0; алгоритм переписан, атрибуция в
коде):
- граф файлов: для каждой ссылки `(name, count)` файла A и каждого файла B, где `name` определён,
  ребро A → B с весом `√count × m(name) / d(name)`; `m` = 10 для имён ≥ 8 символов в
  snake/camel-регистре, 0,1 для имён с `_` в начале; `d(name)` — число файлов, где имя определено
  (имя, определённое в > 5 файлах, дополнительно × 0,1 — общие слова); ссылки файла на собственные
  определения не учитываются;
- PageRank (затухание 0,85, до 50 итераций, точность 1e-6); с `focus` — персонализация: файлы из
  `focus.paths` и файлы, определяющие `focus.idents` (и идентификаторы, извлечённые из
  `focus.text` — слова-идентификаторы длиной ≥ 3, совпадающие с именами символов), получают
  массу перезапуска;
- ранг символа = ранг файла × доля входящего веса по его имени (символы без входящих ссылок —
  малая доля по виду: типы и экспортируемые выше локальных);
- **центральные символы** (аналог «узлов-богов» graphify) — первые по рангу символа, не больше
  трёх из одного файла.

**Карта** (`GET /code/map`) — Markdown: заголовок снимка, затем файлы по рангу, в каждом —
символы по рангу строками `  <kind> <sig или qual> :<line>`; символ без `sig` — `qual`. Упаковка в
`budget_tokens` (по умолчанию `code.map_tokens` = 1000, 1..=20000) — бинарным поиском по числу
символов счётчиком `ApproxCounter` сервера; хвост — строка «… ещё N файлов, M символов —
`memory_code action=map focus=…`». Ответ ≤ бюджета **всегда** (заголовок входит в бюджет).

## 8. Связь с памятью

- **Ссылка на символ.** Строка `путь#qual` везде, где принимается путь ссылки: `refs.files` записей
  — `{path, symbol?, hash?, symbol_hash?, commit?}`; frontmatter `refs:` заметок — `"путь#qual"`;
  `zam log|write --ref путь#qual`; `zam` дописывает `hash` файла и `symbol_hash` (разбор файла; нет
  символа — код 6 у команды, у хуков — пропуск). MCP-клиент хэшей не знает — ссылка без хэшей
  (ориентир берётся при первой проверке, как у файлов, ТЗ §7.10).
- **Устарелость** — `POST /files/changed {solution, files: [{path, hash, symbols?: [{qual,
  body_hash}]}]}`: для ссылок с `symbol` при присланных `symbols` — символ найден и `body_hash` равен
  записанному → `ok`; другой → `stale`/`symbol_changed`; символа нет → `stale`/`symbol_removed`; без
  `symbols` — по хэшу файла, как в M4.5. **Контракт (по реализации):** присланный `symbols` — полный
  список символов файла, иначе поля нет (клиент шлёт его только при полном разборе). Ссылки без `symbol` — без изменений. `PUT /code/files`
  применяет то же правило по загруженным символам. `POST /files/verified` принимает `symbols` так же.
- **Хуки.** `post-tool` после правки файла, у которого в `file-refs.json` есть ссылки с символом,
  разбирает этот один файл (≤ 512 КиБ, отсечка 20 мс) и кладёт в очередь `changed-<сессия>.jsonl`
  `{path, hash, symbols}` только по символам из ссылок; не успел — запись без `symbols`. Бюджет хука
  (50 мс) не меняется. Знание о файле при чтении и перед правкой называет символ: «ZeroAIMemory: о
  `Store::open` в crates/zam-store/src/lib.rs в памяти: <title> [<kind>] — <ref>».
- **`GET /file-refs`** несёт `symbol` у элементов; формат кэша — обратно совместим (поле
  необязательное).
- Карточка символа и `GET /graph?file=` показывают знания, привязанные к символу и к его файлу
  (символьные — первыми).

## 9. API

**REST (`/api/v1`).**

| Метод | Назначение | Права |
|---|---|---|
| `POST /code/sync` | манифест → `{need, removed, etag}` (§5) | владелец, `rw` |
| `PUT /code/files` | загрузка разобранных файлов | владелец, `rw` |
| `GET /code/status?solution=` | снимок: файлы по языкам, символы, пропуски с причинами, возраст, `rank_state`, центральные символы | чтение решения |
| `GET /code/map?solution=&budget_tokens=&files=&focus=&area=&format=md\|json` | карта в бюджете (§7); `focus` — JSON `{paths?, idents?, text?}` (`text` ≤ 2000 символов); `files` (1..=1000, по реализации) — не больше N первых файлов по рангу, рёбра JSON — только между ними | чтение решения |
| `GET /code/files?solution=&lang=&q=&offset=&limit=` (по реализации) | таблица файлов по рангу для WebUI: `{files: [{id, path, lang, rank, symbols}], total, offset, limit}`, `limit` ≤ 200 | чтение решения |
| `GET /code/symbols?solution=&q=&kind=&path=&limit=` | поиск символа (FTS по имени, точное совпадение `qual` — первым; `limit` ≤ 100) | чтение решения |
| `GET /code/symbols/{id}` | карточка: определение, кто ссылается (файлы, число), на что ссылается, привязанные знания (по реализации — и по адресу `путь#qual`; знание — `{path, id, kind, title, state, space, symbol?}`, файловая строка записи со ссылкой и на символ схлопывается) | чтение решения |
| `POST /code/impact {solution, files: [{path, symbols: [{qual, body_hash}]}]}` | изменённые и удалённые символы против карты → привязанные знания и файлы-потребители на 1 шаг | чтение решения |
| `DELETE /code?solution=` | очистить карту | владелец, cookie WebUI |

Ответы карты, символов и влияния — с `tokens` (счётчик сервера); ошибки — problem+json как везде.
`ETag`/`If-None-Match` у `status` и `map` (без `focus`). Маршруты — вне `memory_routes`:
`memory_writes` не растёт (карта — не запись памяти).

**MCP.** **[решение составителя, на подтверждение владельцу]** (§15 п. 3) Новый, 11-й инструмент
`memory_code` — `action: map | symbol | refs | impact`, `query?` (имя или `qual`), `path?`,
`focus?`, `budget_tokens?`; `impact` по MCP — по списку путей с `symbols`, присланных агентом (без
`zam` хэшей у агента нет — тогда сервер отвечает знаниями, привязанными к путям). Описание ≤ 300
символов; тест `mcp_tool_count_still_10` заменяется на `mcp_tool_count_11`. Инструкция
`initialize` называет инструмент одной фразой.

**CLI.**

```
zam code sync [--full] [--background] [--json]        # отпечатки → /code/sync → разбор need → /code/files
zam code status [--json]
zam code map [--focus <путь|имя>]… [--task <текст>] [--tokens N] [--json]
zam code sym <имя|qual> [--json]                      # карточка
zam code refs <имя|qual> [--json]                     # кто ссылается
zam code impact [--since <commit>] [--json]           # изменённые символы рабочей копии → /code/impact
```

`--since` сужает набор `git diff --name-only <commit>..HEAD` плюс `git status`; без него —
изменённые относительно `code-state.json`. Коды выхода — как у прочих команд (ТЗ §13.2).

## 13. Безопасность

- Тела файлов на сервер не уходят; сигнатуры — §4 (≤ 160 символов, выключатель, маскировка
  секретов на сервере).
- Разбор недоверенного кода: пределы §12; обход дерева без рекурсии; без символических ссылок и путей
  вне корня; **журнал падений** `cache/code-parsing.json` (путь пишется до разбора, снимается после;
  незакрытая запись при следующем запуске — пропуск файла `parser_crash`); `catch_unwind` на файл;
  в хуках — только один файл под отсечкой, fail-open **[решение составителя, на подтверждение
  владельцу]**: отдельный процесс с лимитом памяти ОС не делается — разбор идёт в процессе
  пользователя на его машине; песочница ОС — вместе с `doc-worker` в M7 (§15 п. 7).
- Сервер: вход — недоверенный (длины имён ≤ 256, `qual` ≤ 512, управляющие символы — 422, пути по
  правилам `file_refs`, пределы §12); карта видна только имеющим доступ к решению; аудит
  `code.clear` у `DELETE /code`.
- Поставка: версии грамматик закреплены, лицензии MIT — в `deploy/licenses`; fuzz-цель
  `zam-code` (`extract` на случайных байтах для каждого языка) — короткий прогон в задаче, по
  образцу `fuzz-check`.

## 17. Критерии приёмки

1. **Точность экстрактора.** На эталонных фикстурах каждого языка первой очереди (≥ 40 размеченных
   определений на язык, в том числе вложенные, перегрузки, `impl`-блоки, стрелочные функции,
   декораторы) полнота и точность определений (имя + `qual` + вид + строка) — **≥ 0,95**.
2. **Скорость и инкрементальность** (репозиторий ZeroAIMemory, Windows 11, HDD, сервер локально):
   первая `zam code sync` — **≤ 15 с**; повтор без изменений — **≤ 2 с** и 0 загруженных файлов;
   правка одного файла — загружен ровно 1 файл; удаление файла — исчезает из карты после
   следующей синхронизации; вторая машина (другой каталог той же рабочей копии со сброшенным
   `code-state.json`) — загружает 0 файлов.
3. **Карта в бюджете.** Для бюджетов 200/500/1000/2000 ответ `GET /code/map` ≤ бюджета счётчиком
   сервера; с `focus.paths = [файл]` этот файл и файлы, на чьи определения он ссылается, — в
   первой пятёрке; на репозитории проекта в первых 15 центральных символах — ≥ 6 из 10 заранее
   названных в плане ключевых типов (список фиксирует план до реализации).
4. **Устарелость по символу.** Заметка с `refs: ["a.rs#foo"]` и запись с файловой ссылкой на
   `a.rs`: правка `bar` в `a.rs` через хук → файловая ссылка `stale`, символьная `ok`; правка `foo`
   → `stale`/`symbol_changed`; удаление `foo` → `symbol_removed`; знание о файле при чтении называет
   `foo`. Число устаревших ссылок при правке не больше, чем в M4.5 на том же сценарии.
5. **Пакет субагенту.** Задача с именем существующей функции → `### Код` с её сигнатурой и путём;
   весь пакет ≤ `recall.brief_tokens`; выключенный `code_map` — раздела нет.
6. **Невидимость в памяти.** `POST /search` и подсказки `prompt`/`post_tool` не выдают символы;
   строка дайджеста ≤ 80 токенов, без карты — строки нет.
7. **Устойчивость.** Набор враждебных фикстур (минифицированный JS 10 МБ, вложенность скобок
   100 000, бинарный файл `.rs`, невалидный UTF-8, символическая ссылка за пределы корня, файл,
   вызывающий отсечку времени) — синхронизация завершается, каждый файл пропущен с правильной
   причиной; имитация падения на файле (обрыв процесса после записи журнала) → следующий запуск
   пропускает его как `parser_crash`. Сервер на запросы сверх пределов §12 отвечает 413/422.
8. **Бюджеты.** `hook_budgets` (M4) зелёный с включённой картой; запуск фоновой синхронизации
   добавляет хуку ≤ 10 мс (p95); холодный старт `zam --version` — p95 **≤ 20 мс** (как ТЗ §13.2) при
   новом размере бинарника.
9. **Тела не уходят.** Тест перехватывает запросы `zam code sync`: только поля §4, `sig` ≤ 160
