## 1. Зачем

С 0.0.12-m6.5 память работает на рабочем сервере владельца: через неё ведутся этот репозиторий и
ZeroAgent. M7 по ТЗ — «Полировка»: правка в WebUI, администрирование, надёжность сервера, долги
этапов M4–M6.6. За обкатку к нему добавились задачи владельца в WebUI (мобильные устройства,
число записей в разделах), решения владельца 2026-11-21 (ключ по адресу сервера, строка очереди
идей, исполнитель внутренних работ, ночная проверка) и внешний риск: репозиторий ONNX Runtime
удалён с GitHub, сборки держатся на кэше CI.

Этап большой (около 40 задач), поэтому он идёт **волнами** с выпуском после каждой
**[решение координатора]**: память в работе, и каждая волна сразу приносит пользу на обоих
серверах, а не через недели. Очерёдность: сначала опора и безопасность, затем задачи владельца в
WebUI, затем внутренние работы, затем остальное.

## 4. Волна M7.1 «Опора и безопасность»

Ветка `m7.1-foundation` от `main`. Задачи плана — §4.1–§4.8 и итог волны (§4.9).

### 4.1. ONNX Runtime из NuGet

Репозиторий github.com/microsoft/onnxruntime с 2026-11-17 отвечает 404; сборки CI и выпуска
держатся на кэше. Проверка 2026-11-21 (`i:01M7ZB9N2QER1R4NA0XA2ZBK6E`): официальные пакеты
NuGet 1.31.0 — `Microsoft.ML.OnnxRuntime` (CPU, обе платформы в одном пакете),
`Microsoft.ML.OnnxRuntime.Gpu.Windows` и `.Gpu.Linux` — собраны под CUDA 13, и все нужные
нативные файлы **побайтово равны** прежним архивам GitHub (sha256, тот же коммит). Поэтому версия
остаётся 1.31.0, а поставляемые байты не меняются: повторная приёмка CUDA и замеры не нужны,
`deploy/cuda.toml` в силе.

1. Манифесты `deploy/onnxruntime.toml` и `deploy/onnxruntime-gpu.toml` — адреса
   `api.nuget.org/v3-flatcontainer/…/1.31.0/….nupkg`, sha256 и `size` пакета, пути
   `runtimes/<rid>/native/…` (корневого каталога нет), `rename` не нужен: в пакете Linux-библиотека
   уже `libonnxruntime.so`.
2. Загрузчик `zam-fetch` (`download.rs::format_of`) узнаёт `.nupkg` как zip.
3. `xtask fetch-deps` проверяет `size` из манифеста (сейчас не проверяет).
4. Чистка `target/deps-cache`: архивы с sha256, которых нет ни в одном текущем манифесте, удаляются
   (`xtask fetch-deps --prune-cache` в `package.yml`; иначе `restore-keys` копит прежние версии до
   лимита кэша репозитория 10 ГБ).
5. `ThirdPartyNotices.txt` пакета (тот же, что в прежних архивах) — в комплект:
   `deploy/licenses/ONNXRUNTIME-THIRD-PARTY-NOTICES.txt` (LF); сейчас он не поставлялся.
6. Проверка: CI с новым префиксом ключа кэша (без кэша) на обеих платформах, `package-smoke`;
   sha256 извлечённых файлов совпадает с прежними.

Переход на 1.31.1 и 1.32.0 — не в этой волне: у 1.32.0 другие импорты MSVC (`dxgi.dll`), нужен
отдельный прогон GPU **[решение координатора]**. Своё зеркало пакетов не делается (вопрос снят
владельцем в M6.6: источник — NuGet).

### 4.2. Сканер секретов

Дефекты: `i:01M7Z9C3FAE8ARBCX00WSZJ6SD` (русские слова-ключи) и «Передать в M7» задач 15b, 17b
журнала M6.

1. **Русские слова-ключи.** `KEY_VALUE` (`crates/zam-secrets/src/lib.rs`) узнаёт и `токен`,
   `пароль`, `секрет`, `ключ api`/`api-ключ`/`apikey`, а также падежные формы
   `токена|токеном|пароля|паролем|секрета` **[решение координатора: только формы, после которых
   естественно стоит значение]**. Слово «ключ» само по себе — не ключ-значение: «ключ
   идемпотентности: abc123» не маскируется. Граница слова для кириллицы — по Unicode.
2. **Значение после слова-ключа маскируется и тогда, когда оно состоит только из hex** (64 hex —
   типичный токен). Исключение hex остаётся только у правила энтропии, где оно нужно для хэшей и
   UUID без подписи.
3. **`Authorization: Digest …`** — маскируются `response="…"` и значения пар после схемы
   (`nonce`, `cnonce`, `opaque` — нет: это не секреты; `response` — да; `username` — нет).
4. **Предел цепочки «пароль в URL ↔ ключ-значение».** `mask_text` идемпотентна:
   `mask_text(mask_text(x)) == mask_text(x)` для любого `x` (proptest), фикстура
   `scan_depth_capped.txt` проходит без предупреждения `secrets_scan_depth`.
5. **Правила флагов снимка** (`mask_flags`, клиент: `--password X`, `-pXXX`, `-u user:pass`,
   `Authorization:`) переносятся в `zam-secrets`: их применяют и клиент, и сервер (§4.3). На
   сервере — только **внутри кода** Markdown (строки fenced-блоков и inline-спаны): находки флагов
   входят в общий скан, поэтому чанки, L0 и выдача агенту маскируются одним правилом; проза вне кода
   не трогается **[решение координатора, ревью задачи 5]**.
6. **Имена папок без живых заметок.** Разностная перепроверка секретов (`secrets_delta`) видит
   и имя папки, у которой нет живых заметок.
7. `RULES_VERSION` → 3: хранилище один раз перемаскирует заметки и записи с находками
   (механизм `secrets_scanned_v*`). Цена на рабочем сервере (CPU, около 2 тыс. записей) —
   замерить на копии базы, записать в журнал.

Сторожа (не маскируются): «ключ идемпотентности: abc123», «токенов: 1500», «токен — это строка»,
git SHA и sha256 без слова-ключа, `token_id: 01M7…` (base32-id), пути `/password/reset`.

### 4.3. Маскировка в выдаче агенту

Решение владельца 2026-11-06 (п. 9): агенту — `‹secret›` вместо значения, исходник остаётся в базе
и в WebUI, нужные ключи агент берёт из Vault; экспорт по токену — так же. Сейчас маскируется
только индекс (чанки, L0, payload); полный текст уходит агенту исходником. Карта мест выдачи —
`.tmp/m7/explore/read-paths.md` (вне git).

**Кто агент.** Запрос с `Principal::Token` (MCP, хуки, CLI `zam`); сессия WebUI (`User`,
`Admin`) — человек, ему исходник. Признак — `Principal::is_human()`, не поле `by` записи. Человек,
работающий через CLI по токену, тоже получает маску (исходник — в WebUI).

**4.3.1. Выдача (чтение).** Для токена текст проходит `mask_text` по всей ревизии **до** нарезки:
1. `POST /read`: L1, L2, `section`, `range`, фокус, дифф `since_rev` (каждая ревизия маскируется
   до диффа), L0 и L1 записей журналов, заголовки записей;
2. `GET /nodes/{id}` и по пути (`md`, `json` с `frontmatter` — `description`, `tags`, `l0`;
   `html` — маска до рендера; кэш уже разделён по зрителю), оглавление, ревизии и дифф истории,
   поле `diff` ответа 409;
3. `GET /entries` (лента, карточка, ревизии), словарь, сравнение релизов, дерево пространства
   (`frontmatter`), выжимки кэша, эхо ответов записи;
4. поиск: `expand=section` (сейчас отдаёт исходник секции — прямая утечка), заголовки записей в
   карточках;
5. `/recall`: заголовки в `entry_cand` (ловушки, решения, changelog, brief), `index_cand`, имя
   записи окружения Vault, заголовки терминов; напоминание `Stop` клиента
   (`checkpoint.rs`) — маска `zam-secrets` (задача памяти `k:01M7XTYJKSE7RAHM1NWWE7EMYW`);
6. экспорт архива по токену: текст заметок, `frontmatter`, тела, `data`, теги и `area` записей,
   история; опись получает `secrets_masked: true`, если маска что-то заменила (без находок архив
   равен исходнику); блобы — как есть (бинарь не маскируется — ограничение в
   руководстве); импорт архива с `secrets_masked: true` — предупреждение «секреты в архиве
   замаскированы и не восстановятся»;
7. предпросмотр вложений `kind=text|sheet` (`/previews`) — текст и ячейки для токена маскируются
   **[решение координатора]**; сам файл (`GET /blobs/…`) — как есть.

**Не маскируются:** пути узлов и имена файлов (это адреса; секрет в пути находит перепроверка
`secrets_delta`), раскрытие значения Vault (`reveal`, MCP `memory_vault get`) — оно и есть способ
получить ключ, текст для человека в сессии WebUI.

**Адреса `range` и фокус.** Смещения `range:r<rev>:S-E`, пропуски и их число токенов считаются по
маскированному тексту; дочитывание маскирует всю ревизию и только потом режет (маска куска ≠
кусок маски). Формат адреса не меняется **[решение координатора]**: правила сканера меняются
только с обновлением сервера, а адреса живут в пределах сессии; после смены `RULES_VERSION`
адрес старой выдачи может указать на сдвинутые байты — ограничение в руководстве. Плюс: листы с
`‹secret›` (чанки уже маскированы) начинают находиться, фокус работает и на заметках с секретами.

**Цена.** `mask_text` — до 2 мс на 100 КБ; текст больше 64 КиБ маскируется в `spawn_blocking`.

**4.3.2. Запись обратно** (иначе агент, правя маскированный текст, затрёт значение литералом).
Запись по токену — `PUT` и `PATCH` узла, правка и замещение записи журнала — проходит
**восстановление по метке** **[решение координатора, ревью задачи 6, круг 2]**: сопоставление
меток с значениями эвристикой (дифф, похожие строки, ключ) в трёх кругах ревью давало новые случаи
тихой подмены и потери значения, потому что у метки не было личности.
1. **Метки с личностью в редактируемом тексте.** В тексте, который агент может вернуть записью, —
   L2 узла (`/read` L2, `section`, `range`, фокус, `GET /nodes` `md`/`json`) и поля записи
   (`title`, `body`, строки `data`, `tags`, `area` в `GET /entries`), — каждая маска выводится как
   `‹secret-T-N›`: T — метка объекта и ревизии (6 шестнадцатеричных знаков хэша `id объекта ‖
   ревизия ‖ RULES_VERSION ‖ версия zam-secrets` — после обновления сканера старые метки не
   подставят значение по сдвинувшемуся номеру), N — порядковый номер маски в объекте (1, 2, …) **сквозной по всем редактируемым
   полям объекта** в постоянном порядке (у записи: `title`, `body`, строки `data`, `tags`,
   `area`), детерминированно **[решение координатора, ревью задачи 6, круг 4]**: номер с 1 в
   каждом поле и в каждой заметке давал тихую подмену при переносе строки между полями или
   заметками. `section`, `range` и фокус вырезаются из вида всего объекта. Метки — только у
   **текущей** ревизии: вид старой ревизии (`?rev=N`, история, куски `range:r<старая>`) —
   `‹secret›` (смещения `range` — по виду с метками). В нередактируемой выдаче (карточки поиска,
   подсказки, дайджест, заголовки индекса, экспорт) — `‹secret›`. Литерал вида `‹secret›` или
   `‹secret-…›`, лежащий в исходнике, показывается `‹secret›`.
2. **Восстановление.** База — ревизия `base_rev` (у `PATCH` — ревизия, по которой агент строил
   операции; у замещения — `If-Match`/`supersedes_rev`; без ревизии — текущая). Метка
   `‹secret-T-N›`, у которой T — метка этого объекта и **любой его ревизии** (сервер находит
   ревизию по T; две ревизии с одним T — метка не восстанавливается), а N — номер маски той
   ревизии, заменяется значением этой маски в любом поле объекта **[решение координатора,
   финальное ревью M7.1]**: вторая правка подряд из того же контекста агента (прочитал r, записал
   r+1, пишет снова по `rev` из ответа) не теряет значения; личность метки — объект, ревизия и
   номер — точна, подмены нет. Повтор — повтор значения (явный выбор агента). Любая другая метка
   (чужой T, номер вне той ревизии, `‹secret›`, `‹secret-N›` без T) записывается как есть.
   Восстановление идёт после проверки доступа к объекту (пространство, вид записи) — как у
   чтения: о чужом объекте агент не узнаёт ничего, кроме 404. Прежних ревизий по меткам одной
   записи — не больше 8, ближайших к текущей, с исходником не больше 4 × `limits.note_max_bytes`
   (сверх — метки литералом с `secret_mark_kept`), а значение из ревизии, отличной от базовой,
   приходит с предупреждением `secret_mark_from_rev: <k>` **[решение координатора, повторное
   ревью волны правок M7.1, N-2 и N-3]**. Предупреждение `secret_mark_kept` — с числом меток-литералов в итоге
   поля сверх их числа в исходнике текущей ревизии этого поля (литералы из архивов с маской не
   предупреждают на каждой правке; чужая метка вместо значения — предупреждает). Маска базы,
   которую агент не вернул, — удалена агентом явно, как любой текст.
3. Операции `PATCH` по секциям применяются к исходнику текущей ревизии, метки операций
   восстанавливаются по маскам ревизий их меток (п. 2); адрес секции сопоставляется сначала точно с
   заголовками вида с метками, а если точного совпадения нет и в адресе есть `‹secret›` — с
   заголовками, где `‹secret-…›` заменены на `‹secret›` (одна секция — она, несколько — 422).
   То же сопоставление — у `/read section`. Замещение записи, тело которого несёт `‹secret-…›`,
   требует ревизию (`If-Match` или `supersedes_rev`; без неё — 428).
4. Запись человеком в сессии WebUI — без восстановления (он видит исходник).
5. **Покрытие по происхождению.** После сборки каждое изменённое поле сканируется заново; должна
   быть целиком покрыта находкой каждая позиция итога, где стоит секретное значение: (а)
   восстановленное из метки и (б) маска текущей ревизии, перенесённая в итог без правки (у
   `PATCH` — вне изменённых операциями мест; у `PUT` и правки поля записи таких нет — поле
   присылается целиком). Иначе запись отклоняется — 422 `secret_context_changed` с номерами строк
   итога, без значения: агент сменил окружение значения (снял или открыл забор кода, переписал
   `ключ: значение` прозой, разобрал URL), в том числе вне правленого места. Текст, набранный
   агентом, не проверяется: значения в нём нет, кроме угаданного, а угаданное агент знает
   **[решение координатора, ревью задачи 6, круг 4]**: правило «число непокрытых вхождений строки
   значения» давало обход и ложные 422 на слабых значениях (`postgres`, `pass`) и оракул подбора
   значения. Проверка одна для `PUT`, `PATCH`, правки и замещения записи; цена линейна (позиции
   известны, находки упорядочены).
6. Адреса `range` и фокус считаются по виду с метками; листы чанков (маска без меток)
   сопоставляются с ним с учётом меток.
7. **Ограничение.** Отказ 422 сообщает агенту, покрыто ли восстановленное значение правилом в
   новом окружении; нарочитый противник повторами узнаёт свойства значения (энтропия, префикс), но
   не само значение. Защита — от ошибки агента, а не от враждебного агента с токеном.

Признак `/health.features`: `agent_text_masked` (выдача и восстановление); строка в
`docs/api-compat.md`; протокол `zam guide` («секреты в выдаче — ‹secret›, ключ — из Vault;
при правке сохраняйте метки `‹secret-…›` как есть — значение сохранится; метка действует только для
объекта и ревизии, с которых прочитана»).

### 4.4. Ключ доступа по адресу сервера

Решение владельца `i:01M7Z4SBS0EJA816CCYPKPA4TA`: один проект ходит в один сервер, ключ берётся по
адресу этого сервера, ключ одного сервера на другой не отправляется.

1. Домашний `~/.zeroaimemory/config.toml`: `[servers."<адрес>"] token = "…"`; адрес нормализован
   (схема и хост в нижнем регистре, без `/` в конце, порт как есть). Прежние `url`/`token`
   верхнего уровня читаются как раньше: `token` верхнего уровня принадлежит `url` верхнего уровня.
2. `locate::resolve`: шаг 4 берёт ключ только для найденного адреса. Ключа нет → ошибка с
   подсказкой `zam init --url <адрес> --token …`; ключ другого адреса не отправляется.
3. `zam init --token` пишет `[servers."<адрес>"]` и не трогает другие адреса; старый формат при
   записи переводится в новый без потери ключа; прежнее предупреждение о замене ключа другого
   сервера уходит.
4. `zam status` — источник ключа `~/.zeroaimemory/config.toml [servers."<адрес>"]`.
5. Руководство: обход через `--url-to local` и `ZAM_TOKEN` для второго сервера больше не нужен
   (`deploy/README-install.md`, README, ТЗ §14.1).

Флаг `--token`, `ZAM_TOKEN` и ключ в файлах проекта — по-прежнему сильнее домашнего конфига.

### 4.5. Строка очереди идей и мелочи подсказок

1. **Одна строка за эпоху** (решение владельца `i:01M7Z53BM6EGK9Z9W5G18NYGAM`). Вместо строки на
   каждую идею — одна: «идей ждут разбора: N, первая «…» — список: `zam idea queue`» (текст —
   константа рядом с `REVIEW_QUEUE_LEAD`, ru/en, ≤ 60 токенов). Показ — раз за эпоху; новая
   эпоха (сжатие контекста) — снова, если очередь не пуста. **Рост очереди внутри эпохи** (пришла
   идея, которой не было при показе) — строка повторяется один раз с новым числом
   **[решение координатора: новая идея не должна ждать сжатия]**. Подсказки-идеи по близости к
   запросу не меняются.
2. **Слова-реплики** (`PROMPT_REPLY_WORDS`, `crates/zam-search/src/recall.rs` ≈:308): список
   дополнен формами («ладно», «сделай», «делай», «продолжаем», «продолжим», «хорошо», «хорош»,

   случаи тишины — в `eval/hints.toml`.
3. **`term_alias_broad`** не считает «слишком коротким» псевдоним-аббревиатуру из двух и более
   заглавных (`UI`, `DB`, `CI`): с M6.6 он сравнивается с учётом регистра.
4. **`memory_vault delete` по имени** удаляет только при точном совпадении имени (с учётом

### 4.6. Подсказки к ошибкам команд

1. **Ожидаемый ненулевой код** — не ошибка: простая команда (без `|`, `;`, `&&`, `||`) `grep`,

   тест RED на «Exit code 1» у `grep` без вывода.

   локально, без сети: 401/`invalid_grant` (проверь ключ, не повторяй тот же запрос), 403/scope,
   квота, `ENOSPC`/«No space left», 429 с `Retry-After`, 400/422 (проверь запрос, а не повторяй).

   по-прежнему достаточно. Порог — по набору `eval/hints.toml` (случаи `post_tool`), правило —

### 5.4. Подзадачи `part_of`: сервер и CLI

Идея `w:01M7MHR6F5EPHSC70M21PS6H72`: общая задача этапа сутки была «в работе», и по ленте не
видно, сколько шагов сделано.

**Что сейчас.** Шаги плана — задачи со связью `part_of` к общей (протокол
`crates/zam-server/src/agent_setup/guide.ru.md:68`, тест `agent_setup.rs:1376`); рёбра — таблица
`edges` (индексы `edges_src`, `edges_dst`); поля задачи в ответах — `duration_min`, `idea`,
`ideas` (`crates/zam-server/src/api/tasks.rs:66-87`, идеи задач ленты — одним запросом
`zam_store::ideas_of_tasks`, `crates/zam-store/src/ideas.rs:2200`); `zam task show` — карточка
без подзадач (`crates/zam-cli/src/cmd/task.rs:57-94`); в `web/src` слова `part_of` нет.

1. **Модель.** Подзадача — живая задача `S` с ребром `S part_of P`, где `P` — живая задача **того
   же пространства** (оба конца — `entry`); рёбра в другое пространство и базу в прогресс не
   входят **[решение координатора]**. Родитель — самое раннее ребро; задача с двумя родителями
   видна в списках обоих, поле `parent` — первый. **Цикл** (`A part_of B`, `B part_of A`, любой
   длины) ищется полным поиском по всем рёбрам `part_of` задач пространства (компоненты сильной
   связности, O(V+E), без предела глубины): у задачи на цикле рёбра `part_of` для дерева не
   учитываются — задачи цикла на верхнем уровне, ни одна не пропадает с доски; верхний уровень —
   ровно задачи без учтённого ребра к родителю **[решение координатора; уточнено по пре-флайту
   плана]**. Дерево — `zam_store::task_tree(db, space)`: все рёбра `part_of` между живыми
   задачами пространства вместе с данными задач одним запросом, разбор в Rust (O(V+E)).
2. **Поля задачи** (`GET /entries/{id}`, лента `GET …/entries?kind=task`):
   - `parent: {id, title, status, subtasks: {total, done, dropped}} | null` — у подзадачи
     (сводка родителя — для «(8/13)» в п. 4 и §5.5 п. 2 без второго запроса);
   - `subtasks: {total, done, dropped, open, in_progress, blocked}` — у общей (прямые
     подзадачи); прогресс показывается как `done/(total − dropped)` — «8/13» в WebUI и CLI
     **[решение координатора]**;
   - `last_activity_at` — наибольшее из `updated_at` задачи и её прямых подзадач (захват ревизии
     не создаёт и `updated_at` не меняет — `crates/zam-store/src/tasks.rs:356-404`);
   - `stale: true` — статус `in_progress`, живого захвата нет (`claimed_by.until` в прошлом или

   Заголовки в `parent` и `subtasks.items` агенту по токену — через `agent_view` (`‹secret›`).
3. **Фильтры ленты задач**: `top_level=1` — без подзадач (п. 1), `parent=<id>` — прямые
   подзадачи в порядке создания ребра (порядок шагов, как `subtasks.items`), а не «новые

### 5.7. Импорт архива в WebUI

**Что сейчас.** Сервер: `POST /spaces/{space}/import` → 202 и задание,
`GET /spaces/{space}/imports/{job}` (`crates/zam-server/src/api/mod.rs:195-201`, `:255-259`;
`api/transfer/import.rs`); импортирует владелец пространства или администратор, участник — 403
(`import.rs:6-8`); отчёты пишутся только при импорте сессией WebUI (ТЗ §16.4). WebUI — только
«Экспорт (.zip)» (`Tree.svelte:229-261`).

1. **«Импорт (.zip)…»** — в меню пространства рядом с «Экспорт»: у своих пространств (`role`
   `personal`/`owner`) и у администратора — в пространства любого пользователя (`?user=`); у
   участника решения пункта нет.
2. **Диалог** (ленивый чанк `ImportDialog`): файл (`accept=".zip"`); «Это мой архив (перенос с
   другого сервера)» — `own`; «Если запись уже есть: пропустить / новой ревизией» —
   `on_conflict`; «Аксиомы чужого архива: понизить до theorem / оставить» — `axioms` («понизить»
   параметра не передаёт: сервер без него понижает только чужой архив, а явный `axioms=demote`
   понизил бы и свой по описи; «оставить» — `axioms=keep`; решение исполнителя задачи 8, принято
   координатором); кнопки
   «Проверить без записи» (`dry_run=true`) и «Импортировать». Тело — сам файл
   (`Content-Type: application/zip`, `X-Zam-Expected-Bytes` — размер файла) через
   `XMLHttpRequest` — у `fetch` нет хода отправки; CSRF — как у прочих запросов
   (`web/src/lib/api.ts` `request`). Подсказка: «отчёты переносятся только импортом из WebUI».
3. **Ход и итог.** После 202 — опрос задания раз в секунду: этап (в очереди N, проверка,
   вложения, запись), `progress {done, total}`; итог — создано, новых ревизий, пропущено,
   конфликты (первые 50 с причиной и «всего»), понижено аксиом, id заменено, связей пропущено,
   неразрешённых ссылок, предупреждения (в том числе «секреты в архиве замаскированы и не
   восстановятся»). Отказы приёма — понятным текстом по коду: 413 — «архив больше предела
   сервера (import.max_bytes)», 503 — «сервер занят, повторите через N с» (`Retry-After`), 507 —
   «мало места на сервере», 408 — «отправка слишком медленная», 403 — «импорт — только
   владельцу пространства».
4. После итога без `dry_run` — дерево и числа пространства перечитываются. Закрытие диалога
   задание не отменяет (оно на сервере, итог живёт час — ТЗ §16.4); итог после закрытия не
   показывается — диалог предупреждает **[решение координатора]**. Закрытие, пока архив ещё
   отправляется (до 202), спрашивает «Прервать отправку?»: прерванная отправка задания не
   создаёт **[решение координатора, ревью задачи 8]**.

Изменений сервера нет (если исполнитель найдёт дефект API — отдельным шагом с тестом).

1. **Умолчания.** Новая установка — `default_mode = "off"` **[решение координатора]**: без явного
   выбора данные не уходят к модели, а агент не тратит токены. Рабочий сервер памяти —

2. **Настройки пользователя** `works.*` (`user_settings`, по образцу `ideas.mode`; `PATCH

   to}`, у `works.model` — без `body_extra`):

   - `works.kind.<вид>` (`probes`, `rules`, `tidy`) — переопределение вида, `null` — снять;
   - `works.model` — подключение (§6.2 п. 1) или `null`;
   - `works.limits` — `{daily_tokens, monthly_tokens}`, не больше потолков сервера (больше — 422 с
     потолком в `detail`);
   - `works.check` — `on | off` (нет строки — `on`): ночная проверка базы пользователя.
   Действующий режим вида — чистая функция `works::mode(kind, user, server)`: вид пользователя →
   общий режим пользователя → `default_mode`; `enabled = false` — `off` у всех; `model` при
   `model_access = "off"`, без `works.model` или на паузе исполнителя (§6.2 п. 6) — `off` с причиной
   (в `GET /works` и WebUI). `PATCH` режима `model` без подключения или при `model_access = "off"` —
   422. По токену — 403 **[решение координатора]**: агент не может перенаправить память к другой
   модели; администратор — `/admin/users/{id}/settings`.
3. **Время с часовым поясом** (решение владельца). Общая функция `schedule::slot(now, at, tz)`
   (переезжает из `backup/schedule.rs`): сегодняшняя дата **в поясе `tz`**, время `at`, перевод в
   UTC; несуществующее местное время (переход на летнее) сдвигается вперёд на длину перехода,
   повторяющееся — первое из двух (правило `compatible` у `jiff`). Пояс проверяется при старте:
   неизвестное имя — ошибка конфигурации с примерами (`Europe/Moscow`, `UTC`, `+03:00`; на Linux без
   `/usr/share/zoneinfo` — пакет `tzdata` или смещение). `[backup] tz` (по умолчанию `UTC` —
   поведение прежнее) — та же функция **[решение координатора]**: время копии тоже задаётся по
   поясу владельца, а не только в UTC.
4. **Окно ночи.** Ночная часть идёт, только пока `now` в `[slot, slot + window_min)`: проверка —
   если у базы пользователя в этом окне ещё не было ночного прогона (`check_runs.trigger =
   'nightly'`), постановка работ — если не было ночной постановки (`works.origin = 'nightly'`).
   Отдельного состояния нет: перезапуск сервера в окне продолжает ночь, а работы модели в состоянии
   `running` при старте возвращаются в `queued`. Вне окна работы модели не выполняются; пропущенная
   ночь днём не догоняется **[решение координатора]**: нагрузка CPU и модели — только ночью. Шаг —
   тот же воркер обслуживания раз в минуту (`WORKS_TICK`), решение «пора ли» — чистая функция
   `works::schedule::tick`, как у копий.

**Проверка.** `works_config_defaults_and_bounds`; `slot_tz_moscow_0430_is_0130_utc`,
`slot_dst_gap_and_fold` (`America/New_York`: 02:30 в день перехода — 03:30, в день возврата —
первое 01:30), `slot_fixed_offset`, `backup_tz_default_utc_unchanged` (прежние
`schedule_tick_cases` — зелёные); `works_settings_patch_and_defaults` (выбор, равный умолчанию, не
сохраняется), `works_settings_token_403`, `works_model_mode_requires_connection_422`,
`works_mode_resolution_cases` (таблица функции); `works_tick_window_no_catch_up`,
`works_tick_restart_in_window_continues`.

### 6.2. Подключённая модель: протоколы, данные наружу, пределы

**Что сейчас.** Исходящих обращений к моделям нет; исходящий HTTP — только загрузка зависимостей
`zam-fetch` (`ureq`, прокси из окружения, кроме петли — `crates/zam-fetch/src/download.rs:62-91`).
У записи Vault — имя, открытые поля `data` (`url`, `address`, … —
`crates/zam-store/src/vault.rs:33-41`) и значение-шифротекст (`vault_get`, `vault.rs:374`).

1. **Подключение** `works.model = {protocol: "openai" | "anthropic", vault: "v:<id>", model, auth:
   "key" | "none", max_tokens, token_field: "auto" | "max_tokens" | "max_completion_tokens",
   anthropic_version, body_extra}`:
   - адрес и ключ — **запись личного Vault пользователя** (решение владельца): базовый адрес —
     `data.url` (иначе `data.address`), ключ — значение записи; `auth = "none"` — заголовок
     авторизации не шлётся (локальный сервер без ключа). `PATCH` принимает имя записи или `v:<id>` и
     хранит id **[решение координатора]**: переименование записи подключение не ломает; запись
     удалена или Vault заблокирован — пауза `vault` (п. 6);
   - `model` — имя модели у поставщика (1..=200 символов); `max_tokens` — предел ответа
     (256..=32000, 4000);
   - `body_extra` — JSON-объект до 4 КиБ, сливается в тело запроса верхним уровнем; ключи `model`,
     `messages`, `system`, `stream`, `max_tokens`, `max_completion_tokens` — 422. Так задаются
     особенности поставщика: `{"chat_template_kwargs": {"enable_thinking": false}}` (Qwen на
     llama.cpp или vLLM — модель владельца), `{"enable_thinking": false}` (DashScope),
     `{"response_format": {"type": "json_object"}}`, `{"output_config": {"effort": "low"}}`
     (Anthropic). Пресетов поставщиков в коде нет — таблица рецептов в руководстве (п. 4)
     **[решение координатора]**.
2. **OpenAI Chat Completions** (OpenAI и совместимые): `POST <url>/chat/completions` (`url` — с
   `/v1`, как его дают поставщики), `Authorization: Bearer <ключ>`, тело `{model, messages: [{role:
   "system", content}, {role: "user", content}], <предел>, stream: false}` и `body_extra`. Предел
   ответа при `token_field = "auto"` — `max_completion_tokens` для хоста `api.openai.com` (новые
   модели OpenAI отвергают `max_tokens`), иначе `max_tokens` (его понимают совместимые серверы).
   Ответ — `choices[0].message.content` (строка; массив частей — склеиваются текстовые);
   `finish_reason`: `stop` — итог, `length` — нехватка предела, `content_filter` — отказ. Поле
   `reasoning_content` (DeepSeek, Qwen, llama.cpp) ответом не считается: `content = null` при
   `finish_reason = length` и непустом `reasoning_content` — класс `thinking` с подсказкой про
   `body_extra` (ловушка `i:01M7Z97PABEAW994XHSSW8A9DE`). Учёт — `usage.prompt_tokens`,
   `usage.completion_tokens`; без `usage` (часть локальных серверов) — оценка счётчиком выдачи
   (`tokenizer.json` bge-m3, ТЗ §5.2) с пометкой `estimated`. Ошибка — `{"error": {"message",
   "type", "code"}}` или `{"error": "<строка>"}` (Ollama); `code = "insufficient_quota"` — класс
   `quota`.
3. **Anthropic Messages**: `POST <url>/v1/messages` (`url` — без `/v1`, например
   `https://api.anthropic.com`), заголовки `x-api-key`, `anthropic-version`, `content-type:
   application/json`; тело `{model, max_tokens, system, messages: [{role: "user", content}]}` и
   `body_extra`. `anthropic_version` по умолчанию — `2023-06-01` **[решение координатора]**: её
   понимают и Anthropic-совместимые входы других поставщиков; версия `2026-10-21` отвергает
   `temperature`, `top_p`, `top_k` — сервер их не шлёт ни в одной версии. Поле `thinking` не шлётся
   (у новых моделей размышления не выключаются; глубина — `output_config.effort` через
   `body_extra`). Ответ — склейка блоков `content[]` с `type = "text"` (блоки `thinking` и прочие
   пропускаются); `stop_reason`: `end_turn` и `stop_sequence` — итог, `max_tokens` — нехватка
   предела, `refusal` — отказ, `pause_turn` и `tool_use` — класс `bad_response`. Учёт —
   `usage.input_tokens` (+ `cache_creation_input_tokens`, `cache_read_input_tokens`) и
   `usage.output_tokens`. Ошибка — `{"type": "error", "error": {"type", "message"}}`; HTTP 529
   `overloaded_error` — как 503; 429 без `retry-after` (предел расходов) — класс `quota`.
4. **Поставщики** — таблица «Подключённая модель» в `deploy/README-install.md` (каждую строку
   задача плана сверяет с документацией поставщика): OpenAI (`https://api.openai.com/v1`, openai),
   Anthropic (`https://api.anthropic.com`, anthropic), DeepSeek, Kimi (Moonshot), Qwen (DashScope,
   compatible-mode), OpenRouter, Ollama (`http://<хост>:11434/v1`), llama.cpp server, vLLM, LM
   Studio (все — openai) — с рецептами `body_extra` (размышления, JSON) и `auth = "none"` для
   локальных. Приёмка волны — на локальной модели владельца (OpenAI-совместимый API); прочие —
   подставными серверами в тестах по тем же двум протоколам.
5. **Ответ — JSON.** Инструкция пакета (§6.3 п. 3) требует ответ одним JSON-объектом; разбор
   берёт первый блок кода `json` или первый сбалансированный объект текста. Не разобрался —
   **один** повтор той же беседы с сообщением «ответ не JSON: <ошибка разбора>; верни только JSON
   по схеме» **[решение координатора]**; второй сбой — работа `failed` с классом `bad_json`.
   Содержимое проверяет та же проверка, что итог агента (§6.3 п. 4): отказ отдельного элемента
   повтором не исправляется.
6. **Классы ошибок и реакция** (в журнале и аудите — класс и код HTTP, без текста ответа):

   | Класс | Когда | Реакция |
   |---|---|---|
   | `auth` | 401, 403 | пауза исполнителя пользователя до правки `works.model` или успешной проверки подключения (п. 10) |
   | `not_found` | 404 (модель или адрес) | пауза, как у `auth` |
   | `bad_request` | 400, 413, 422 | работа `failed`, ночь идёт дальше (обычно ошибка `body_extra`) |
   | `quota` | 402, `insufficient_quota`, 429 без `retry-after` | стоп до следующей ночи |
   | `rate` | 429 с `retry-after` ≤ 60 с | ожидание и один повтор, иначе стоп до следующей ночи |
   | `unavailable` | 5xx, 529, таймаут, отказ соединения | два повтора (через 10 и 60 с); три таких вызова за ночь — стоп до следующей ночи |
   | `thinking`, `max_tokens` | ответ обрезан пределом | работа `failed`, подсказка в WebUI («увеличьте `max_tokens` или выключите размышления») |
   | `refused`, `bad_response`, `bad_json` | отказ, иной ответ, не JSON | работа `failed` |
   | `secret_in_payload`, `blocked`, `limit`, `vault` | п. 7, п. 8, п. 1 | запрос не отправляется; `blocked` и `vault` — пауза |

   Пауза — в `GET /works` (`paused: {class, since}`), на странице «Внутренние работы» и в аудите
   `works.model.paused {class}`; агенту она не показывается — снять её он не может.
7. **Данные наружу.**
   - Отправляется только пакет работы (§6.3 п. 3) — маскированный вид агента без перечня «Общего
     для волны» (Human, Vault, вложения, …); пакет собирают функции видов работ, и тест проверяет,
     что сборщики не берут пространство Human и записи вне базы пользователя.
   - **Второй скан**: всё тело запроса (системное и пользовательское сообщения) проходит
     `zam_secrets::scan_secrets` (`crates/zam-secrets/src/lib.rs:987`); любая находка — запрос не
     отправляется, работа `failed` с классом `secret_in_payload` и номером элемента, без текста
     **[решение координатора]**: тело собрано из нескольких источников, и «не отправлять при
     сомнении» дешевле утечки.
   - **LAN или вне LAN** — по всем адресам имени после разрешения: `10/8`, `172.16/12`,
     `192.168/16`, `100.64/10` (CGNAT, оверлейные сети), `127/8`, `169.254/16`, `::1`, `fc00::/7`,
     `fe80::/10` — LAN; хотя бы один адрес вне их — «вне LAN». `model_access = "lan"` — обращения
     вне LAN не делаются (класс `blocked`, причина в WebUI); `"off"` — режима `model` нет. Схема
     `http://` — только для LAN: ключ во внешнюю сеть открытым текстом не уходит (422 при `PATCH`,
     та же проверка перед каждым обращением) **[решение координатора]**.
   - **Предупреждение вне LAN** (набросок, п. 4): `PATCH` подключения отвечает `warnings:
     ["works_model_external: <хост>"]`, страница «Внутренние работы» показывает постоянную плашку
     «данные памяти уходят за пределы локальной сети: <хост>», аудит — `works.model.external
     {host}`; строки журнала отправок — с `external: true`.
   - Прокси — из окружения, как у `zam-fetch`; для петли и LAN — без прокси. TLS — `rustls` с
     корнями `webpki-roots` (как у `ureq` сейчас); своих корневых сертификатов в волне нет
     (локальные серверы — `http` в LAN).
8. **Пределы.**
   - перед вызовом — оценка «вход (счётчик выдачи) + `max_tokens`»; не помещается в остаток суток
     или месяца пользователя (`works.limits` и потолки `[works]`) — запрос не отправляется, класс
     `limit`, стоп до следующей ночи;
   - сутки и месяц — UTC, расход — сумма по журналу отправок (п. 9), отдельного счётчика нет;

9. **Журнал отправок** `work_calls` (база пользователя): `ts, work_id, kind, protocol, host, model,

10. **Проверка подключения** `POST /works/model/test` (сессия пользователя или администратор):

### 6.3. Очередь работ и режим «агент»

**Что сейчас.** Образец — разбор идей (ТЗ §7.14): очередь — идеи `new` (`zam_store::review_queue`,
`crates/zam-store/src/ideas.rs:2650`), строка дайджеста «Непросмотренных идей: N…»
(`crates/zam-server/src/api/recall/ideas.rs:60`), пакет `memory_recall event=idea_review`
(`Event::IdeaReview`, `crates/zam-server/src/api/recall/mod.rs:372-383`; до 5 идей, бюджет 3000
токенов — `recall/ideas.rs:78-83`), итог — `memory_update_entry action=review` с проверкой сервера.

1. **Работа** — строка `works`: `id (j:), kind (probes | rules | tidy), space_id, mode (agent |
   model), origin (nightly | manual), state, items (JSON: ссылки и ревизии кандидатов пакета),
   claimed_session, claimed_until, attempts, created_at, started_at, finished_at, result (JSON:
   принято, отклонено с причинами, пропущено), error_class`. Состояния: `queued → running → done |
   failed`; `expired` — агентская работа без итога 7 суток; `cancelled` — снял человек, вид
   выключен или агент отказался (п. 4). Захват агентом — аренда на 2 ч: истекла — снова `queued`,
   `attempts + 1`, после третьей — `failed`. В очереди — не больше **одной** незакрытой работы вида
   на пространство **[решение координатора]**: долг не копится, следующую работу сборщик ставит
   только после итога прежней. Пространство работы — пространство её кандидатов; у `rules` — Rules
   пользователя (источники — из решений и Knowledge, §6.7 п. 3).
2. **Постановка.** В окне ночи (§6.1 п. 4) для каждого пользователя и вида с действующим режимом
   `agent` или `model` сборщик вида (§6.4 п. 2, §6.7 п. 3, §6.8 п. 1) детерминированно отбирает до
   `batch_records` кандидатов пространства; пусто — работы нет. Режим `model` — работы выполняются
   сразу, по одной: пробы, затем кандидаты в Rules, затем уборка; у вида — не больше 4 пакетов за
   ночь, до конца окна или стопа (§6.2 пп. 6, 8). Режим `agent` — работа ждёт агента. Ручной запуск
   — `POST /works/run {kind, space?}` (человек): та же постановка вне окна, `origin = manual`.
3. **Пакет** — `memory_recall {event: "work", kind?}` (MCP), `POST /recall` с тем же телом,
   `zam work next [--kind K]`: сервер захватывает старейшую работу `queued` пространств сессии
   (решение сессии, если пользователь — его владелец; Knowledge; Rules) и отдаёт Markdown: заголовок
   «Внутренняя работа j:<id> · <вид>», инструкция вида (константа рядом с пакетом, ru/en, ≤ 300
   токенов), элементы (ссылка, вид, заголовок, L1 или текст до 1500 символов, сигналы вида), схема
   итога и строка «Итог: memory_log {kind: "work", data: {work: "j:<id>", items: […]}}». Бюджет
   пакета — 6000 токенов (`budget_tokens` 1..=20000); элементы сверх бюджета уходят в следующую
   работу. Работы нет — «Внутренних работ нет.»; участнику общего решения работ нет (база и
   настройки — владельца) **[решение координатора]**. Учёт — `session_tokens`, событие `work`;
   показы в `usage` не пишутся (это не подсказка). Тот же текст — запрос модели: системное
   сообщение — инструкция и схема, пользовательское — элементы.
4. **Итог** — `memory_log {kind: "work", data: {work: "j:<id>", items: […], skip?: "<причина>"}}`,
   `POST /works/{id}/result`, `zam work put <файл.json>`:
   - принимается только от сессии, захватившей работу `running` (иначе 409
     `/problems/work-not-claimed`); повтор с тем же `Idempotency-Key` — прежний ответ;
   - каждый элемент проходит проверку вида (§6.4 п. 2, §6.7 п. 3, §6.8 п. 2): принятые
     записываются (пробы, предложения), отклонённые возвращаются с причиной (`rejected: [{n,
     target, reason}]`), элементы пакета без итога — пропущены;
   - работа `done` с `result`, ответ — `{work, accepted, rejected, skipped}`; второй итог — 409;
   - `skip` без элементов — работа `cancelled`, сборщик поставит её снова следующей ночью;
   - `POST /works/{id}/release` — вернуть в очередь без итога.
5. **Строка дайджеста** (режим `agent`, очередь не пуста): «Внутренние работы ждут: пробы 1, уборка
   1 — memory_recall event=work, когда закончишь текущий шаг.» (≤ 30 токенов, константа ru/en) — на
   первом `session_start` сессии, после строки идей; к запросу и после сжатия — нет **[решение
   координатора]**: работа памяти — не дело человека, напоминать о ней чаще раза за сессию — шум.
   Выключатель — `hooks.session_start` (как у всего дайджеста).
6. **Протокол `zam guide`** — раздел «Внутренние работы»: когда (после текущего шага и после разбора
   идей человека, не посреди ответа человеку), шаги (пакет → работа по инструкции → итог одним
   вызовом), правила качества видов (кратко, §6.4 п. 2, §6.7 п. 3, §6.8 п. 2), «итог не меняет
   знания: предложения решает человек», отказ — `skip`.
7. **Режим `model`** выполняет ту же работу: пакет (п. 3) → вызов (§6.2) → разбор JSON → та же
   проверка (п. 4) → те же записи; автор — `model:<имя модели>`, у агента — его сессия. Один
   построитель пакета и одна проверка итога для обоих режимов **[решение координатора]**: правила
   качества одинаковы, а тест с подставной моделью проверяет и путь агента.
8. **REST и CLI.** `GET /works?state=&kind=&limit=` — очередь и последние работы с итогами

### 6.4. Пробы ночной проверки

1. **Проба** — строка `probes`: `id (x:), space_id, question, kind (probe | cache | negative |
   manual), targets (JSON: [{ref, rev}]; у negative — []), split (dev | test), overlap, author_kind
   (agent | model | human | system), author, work_id, status (active | retired), retired_reason,
   created_at, retired_at`. Вне поиска, дайджеста, подсказок, выжимок и экспорта (§6 «Общее»). Цель
   удалена, замещена или отозвана — проба `retired` (`target_gone`) при следующем прогоне;
   изменённая цель пробу не снимает (вопрос — о той же записи). Пределы: активных — 500 на
   пользователя (`PROBES_MAX`), новых вида `probe` за ночь — 40 **[решение координатора]**.
2. **Вид работы `probes`** (агент или модель):
   - **сборщик** — записи без активной пробы; слои — insight по `data.kind`, заметки Rules, заметки
     решений и Knowledge, термины; по кругу слоёв, внутри слоя — порядок `blake3("probes" ‖ дата ‖
     id)` (детерминированно и каждую ночь иначе); задачи, вопросы, идеи, changelog и отчёты не
     берутся — они быстро устаревают и агент не ищет их как знание;
   - **инструкция** (правила claude-note, обзор §2.4): вопрос, который коллега задал бы, **ещё не
     зная** о записи; своими словами; 8–25 слов; без путей, ссылок, id, дат, URL и кода в обратных
     кавычках; на языке записи; одна проба на запись, две — на длинную заметку; запись, о которой
     нельзя спросить, — `skip`;

     `\` с расширением файла), ссылки `<буква>:<26 знаков base32>`, даты `ГГГГ-ММ-ДД`, URL, обратных
     кавычек; `overlap` — доля предметных слов вопроса (без стоп-слов `zam_core::text`, нормализация
     — как у слов подсказок) среди слов заголовка цели, больше 0,5 — отказ «пересказ заголовка»
     **[решение координатора]**; та же нормализованная строка вопроса уже есть — отказ;
   - **разбиение** dev/test — по цели: `test`, если `blake3("probes-v1" ‖ ref) mod 3 = 0` (⅓; по
     первой цели), по образцу `xtask/src/eval/split.rs`; правило переезжает в `zam-search::eval`, и
     xtask берёт его оттуда — функция одна.
3. **Пробы из кэша выжимок** (без исполнителя, каждую ночь перед прогоном): действующие выжимки

5. **Ручные пробы** — `POST /check/probes {question, targets}` (человек в WebUI или токен;

### 6.5. Ночная проверка: прогон, регрессии, показ

1. **Прогон.** В окне ночи — **первым**, до работ модели **[решение координатора]**: нагрузка модели
   и записи работ не искажают задержек. Идёт копия (`BackupRunner`,
   `crates/zam-server/src/backup/runner.rs:140`) — ждать, проверяя раз в минуту, до конца окна;
   идёт переиндексация (`IndexRuntime::reindexing`, `crates/zam-server/src/index_state.rs:332`) —
   прогон `skipped`: выдача неполна, сравнение бессмысленно. Пользователи — по одному, пробы —
   последовательно с паузой 25 мс; предел — `check_max_min`, превышен — `timeout` (метрики по
   пройденным, без вердикта). Ручной запуск — `POST /check/run` (человек или токен `rw`; второй
   прогон пользователя, пока идёт первый, — 409), `zam check run`.
2. **Тем же путём, без следов.** Каждый вопрос идёт кодом агента и хука — `/search mode=brief`
   (`search_with`, `crates/zam-server/src/api/search/mod.rs:2517`) и `/recall(prompt)` (`recall`,
   `recall/mod.rs:3489`) — изнутри процесса; принципал — агент пользователя без сессии (`ro`, маска
   `agent_view`) **[решение координатора]**; решение — пространство пробы (`X-Zam-Solution`; у
   Knowledge и Rules — без решения). Учёта нет: `usage`, `session_seen`, `session_tokens`,
   `tokens_unattributed` не пишутся, у выжимок кэша не меняются `hits` и `last_used_at`. Поиск —
   один на пробу: `top_k = 50`, ранг цели и граница бюджета — число карточек, которые поместились
   бы в `search.budget_tokens` той же выдачи (та же упаковка); карточка `[cache]` с целью в
   `sources` — попадание на её месте.
3. **Метрики** (по `dev`, `test` и всем; у `negative` — свои): `hit_search` — доля проб с целью в
   пределах бюджета; `mrr10`; `none` — цель не нашлась в 50; `beyond` — нашлась за границей бюджета;
   `hit_prompt` — цель среди подсказок `prompt` (до 3) — только у проб с целью, которая может прийти
   подсказкой (insight, заметки Rules — ТЗ §10.3), прочие в знаменатель не входят;
   `negatives_shown` — доля посторонних, к которым `prompt` показал хоть одну подсказку; `hard` —
   `hit_search` проб с `overlap < 0,2`; задержки `p50`/`p95` поиска и подсказки; `degraded` — поиск
   шёл без векторов. Функции — в `zam-search::eval` рядом с правилом разбиения (`score` из
   `xtask/src/eval/metrics.rs:78` переезжает туда же).
4. **Отпечаток** (`fingerprint`, его хэш — `fp_hash`): версия сервера, модель эмбеддингов
   (`model_id`) и устройство, реранкер, режим Qdrant, хэши итоговых секций `[search]` и `[recall]`,
   `check_version` (правила метрик и набор посторонних). Набор проб в отпечаток не входит: сравнение
   идёт по общим пробам.
5. **Вердикт** (правило записано до первого прогона; пороги — стартовые из claude-note, обзор §2.4)
   **[решение координатора]**:
   - сравнимые — 5 последних завершённых прогонов с тем же `fp_hash`; меньше — `baseline` (N/5);
   - **регрессия** — по `test` на пробах, общих для текущего прогона и всех пяти: `hit_search` или
     `hit_prompt` ниже медианы на 8 п. п. и больше; `negatives_shown` выше медианы на 10 п. п. и
     больше; `p95` поиска больше медианы в 1,5 раза **и** на 500 мс; **потеря устойчивых** — из
     проб, найденных во всех пяти, не нашлось 10 % и больше, но не меньше 3 (ловит порчу индекса и
     на малом наборе); `degraded` — регрессия всегда (агент сейчас ищет так же плохо);
   - в `test` меньше 20 проб — только «потеря устойчивых» и `degraded`, вердикт с пометкой `few`;
   - отпечаток сменился (обновление, правка умолчаний) — `changed`: разница с медианой 5 последних
     прогонов прежнего отпечатка, без флага регрессии; дальше база копится по новому отпечатку;

### 6.7. Кандидаты в Rules

**Что сейчас.** Rules пишет человек; агент — только при `rules.agent_write` (по умолчанию выключено;
`crates/zam-server/src/api/scope.rs:148`, ТЗ §7.1), иначе 403; потока «агент предлагает — человек
принимает» нет (задача `k:01M7GAQQGBERPTY57K706BBTBS`; ответ владельца M6 п. 20 — «в M7»).

1. **Предложение** — строка `proposals` (общая с уборкой, §6.8): `id (o:), space_id, type, status
   (proposed | accepted | declined | withdrawn | stale | skipped), targets (JSON: [{ref, rev}]),
   payload (JSON по типу), reason, basis, dedup_key, author_kind (agent | model), author, work_id,
   session_id, created_at, decided_at, decided_by, decision_note, result_ref`. Кандидат в Rules —
   `type = rule`, `space_id` — Rules пользователя, `payload {path, content}`. Таблица, а не новый
   вид записи журнала **[решение координатора]**: предложение — служебный шаг до решения человека;
   вид записи потребовал бы пересборки `entries` (CHECK вида — как в `0026_idea_review.sql`),
   журналов у Rules нет (`crates/zam-store/src/counts.rs:63`), а поиск, ревизии и экспорт
   кандидатам не нужны. `skipped` — исполнитель решил «правила здесь нет»: человеку не
   показывается, нужен для отсева повторов.
2. **Агент предлагает сам** (основной поток задачи): `memory_write {path: "rules:/<путь>", content,
   propose: "<почему это правило для всех проектов>"}`, REST `POST /proposals {type: "rule", path,
   content, reason, basis?}`, CLI `zam rules propose <путь> --file F --reason R [--basis ID]…` →
   `{proposal: "o:<id>"}`. Токен `rw`; `content` — до 200 токенов (правило читается L1 в каждом
   дайджесте, ТЗ §7.1); путь — как у заметки Rules (заметка по пути уже есть — 409 с советом другого
   пути); `reason` — 20..=2000 символов; открытых кандидатов — не больше 50 на пользователя (409
   `/problems/proposals-full`); тот же путь и текст — прежнее предложение. Запись в Rules без права
   (`rules.agent_write = false`) — по-прежнему 403, в `detail` — «предложите правило:
   memory_write … propose» **[решение координатора]**. С `rules.agent_write = true` агент пишет в
   Rules прямо, как сейчас; `propose` работает и тогда.
3. **Вид работы `rules`** (агент или модель):
   - **сборщик** — источники без предложения (`dedup_key` — по ссылке и ревизии источника):
     действующие insight `decision` с `certainty = axiom` (решения владельца) и insight `gotcha |
     pattern` Knowledge с `useful ≥ 2` или `opened ≥ 3`; в пакете — ещё заголовки действующих
     заметок Rules (до 50, L0), чтобы не повторять их;
   - **инструкция**: правило ли это для **всех** проектов агента (поведение, а не факт одного
     проекта); да — `{target, rule: {path, title, content}, reason}`: повелительно, до 200 токенов,
     без путей проекта, без противоречия заметкам Rules; нет — `{target, skip: "почему"}`;
   - **проверка**: `content` до 200 токенов (счётчик выдачи); путь — допустимый и свободный путь
     Rules; не почти-дубль заметки Rules (тот же нормализованный заголовок или dense-косинус не ниже
     `insights.dedup_threshold` — `nearest_dense`, как дедупликация insight,
     `crates/zam-server/src/api/insights.rs:15-27`); `skip` — строка `skipped`.
4. **Решает человек** — «Предложения → Кандидаты в Rules» (§6.9): путь и текст (правятся до
   принятия), основание (ссылки), довод, автор (сессия агента или имя модели). «Принять» —
   `POST /proposals/{id}/accept {path?, content?}` (только сессия WebUI; токен — 403): заметка Rules
   создаётся тем же кодом, что заметка из WebUI, автор — человек; предложение `accepted`,
   `result_ref: n:<id>`; путь занят к моменту принятия — 409 с подсказкой. «Отклонить» —
   `POST /proposals/{id}/decline {note?}`: `declined`, тот же источник больше не предлагается. Автор
   отзывает своё — `POST /proposals/{id}/withdraw` (токен того же пользователя). Аудит
   `proposal.accept | proposal.decline {id, type, result?}` — без текста.

### 6.8. Уборка памяти

Кандидат К5 обзора claude-note — наш аналог их ночного слияния, но без автоматики, которая у них
делала поправки шире нужного.

1. **Сборщик кандидатов** (детерминированно, без модели; решения и Knowledge владельца базы; до 20
   за ночь):
   - **почти-дубли** — пары действующих insight одного пространства, вида и области с
     dense-косинусом в `[0,80; insights.dedup_threshold)` (`nearest_dense`, как дедупликация при
     записи: порог 0,90 ловит дубли только при записи); инкрементально — записи, изменённые после
     прошлой ночи, против всех; у терминов — тот же нормализованный заголовок или псевдоним;
   - **неразрешённые противоречия** — связи `contradicts` старше 3 суток, оба конца действующие;
   - **устаревшие** — insight с пометкой «возможно устарело» (изменились `refs.files`, ТЗ §7.10) или
     в статусе `revisit` 14 суток и дольше;
   - **шумные** — `shown ≥ 10` за 30 суток, `opened = 0`, `useful = 0` (§6.6);
   - **непроходящие пробы** — цель не нашлась три ночных прогона подряд (§6.5 п. 6).
   Кандидат, по `dedup_key` которого (тип, ссылки, ревизии) уже есть предложение, не повторяется.
2. **Вид работы `tidy`** (агент или модель): в пакете — тип кандидата, тексты записей (L1),
   сигналы (косинус, показы, пометка устарелости, провалы проб) и допустимые операции типа; итог —
   одна операция на кандидата с доводом. Проверка элемента — схема операции, ссылки — только из
   кандидата, `reason` 20..=2000 символов, тексты — в пределах записи (`limits.note_max_bytes`),
   `triggers` — по правилам триггеров insight.

   | Операция | Поля | Применение человеком |
   |---|---|---|
   | `merge` | `keep`, `drop`, `text?` | с `text` — `keep` замещается новой записью с этим телом (`supersede_entry`), `drop` отзывается «дубль i:<новая>»; без `text` — `drop` отзывается «дубль i:<keep>» |
   | `retract` | `target`, `reason` | отзыв (`retract_entry`) |
   | `revisit` | `target`, `reason` | статус `revisit` |
   | `triggers` | `target`, `triggers` | замена триггеров (как `action=triggers`) |
   | `term` | `title`, `definition`, `aliases` | новый термин или псевдонимы к существующему |
   | `append` | `target`, `text` | дописка (как `action=append`) |
   | `keep` | `reason` | ничего: кандидат отсеян (`skipped`) |

3. **Ничего не применяется само** **[решение координатора]**: каждое предложение — в «Предложения →
   Уборка» (§6.9) рядом с текстами записей (у `merge` — дифф); «Применить» — сессия WebUI, операция
   — от имени человека, аудит `proposal.accept`; «Отклонить» — `declined`. Удаления в уборке нет
   вовсе: операции замещают, отзывают, дописывают — история остаётся (ТЗ §4.1 п. 4). Запись с
   `certainty = axiom` в предложении помечена «решение человека». Цель изменилась после предложения
   (ревизия не та) — `stale`, «Применить» — 409; кандидат вернётся следующей ночью.
4. **Перенос insight решения в Knowledge** (обзор К5, «похоже на общее знание») — не в волне
   (§6.13): у записей журналов нет операции переноса.

  запросу.
- **Судья ответов с контролем** (К7) → после M7 (калибровка и агентный A/B).
- **Поток (`stream`), инструменты модели, кэш промптов, пакетные API поставщиков** — ночным работам
  малыми пакетами не нужны → по замеру.
- **Свои корневые сертификаты TLS** для модели в LAN по `https` → по запросу.
- **Пробы по вложениям и карте кода** → после M7.5.
- **Калибровка порогов регрессии** — после 14 ночных прогонов (§6.5 п. 5; задача в памяти).

## 12. Решения координатора (на проверку владельцу)

1. Этап волнами с выпуском после каждой. Цена: накладные расходы выпуска (полный прогон, CI,
   развёртывание) шесть раз вместо одного.
2. Очерёдность волн: опора → WebUI → внутренние работы → администрирование → поиск → клиенты.
   Цена: если важнее другое, его ждут дольше.
3. Волну можно делить и сливать по объёму. Цена: номера выпусков не совпадут с таблицей §2.
4. Русские слова-ключи — только формы, после которых естественно стоит значение (§4.2 п. 1).
   Цена: редкие формы («токенами: …») не маскируются.
5. Строка очереди повторяется один раз при росте очереди внутри эпохи (§4.5 п. 1). Цена: +1
   строка ≈ 50 токенов на рост очереди.
6. Порог задержки `prompt` — к предыдущему выпуску, а не к M5.7 (§4.8 п. 3). Цена: медленный
   накопленный рост ловят только абсолютные пороги.
7. Формат адреса `range` не меняется при маскировке (§4.3.1). Цена: после обновления сервера со
   сменой правил сканера адрес, выданный до обновления, может указать на сдвинутые байты.
8. `‹secret›` в добавленном агентом тексте сохраняется с предупреждением, а не отказом (§4.3.2
   п. 2). Цена: литерал `‹secret›` в тексте, если агент сам его вписал.
9. Экспорт по токену маскируется, блобы — нет (§4.3.1 п. 6). Цена: полная копия с секретами —
   только из WebUI или `zam-server backup`; секрет внутри бинарного вложения уходит в архив.
10. Восстановление при записи — по метке `‹secret-T-N›` (объект, ревизия, номер), а не
    эвристикой выравнивания (§4.3.2); покрытие проверяется по происхождению значений, а не по
    вхождениям строки. Цена: формат меток в редактируемой выдаче агенту отличается от `‹secret›`
    прочей выдачи; агент, переписавший метку или перенёсший её в другую заметку, теряет значение
    в текущей ревизии (с предупреждением, значение остаётся в истории).
11. Флаги командной строки на сервере — только внутри кода (§4.2 п. 5). Цена: флаг в прозе
    (`mysql -pX` без обратных кавычек) не маскируется.
12. Классы ширины: телефон < 720, планшет 720–1023 (дерево — выдвижная панель), настольный ≥ 1024
    (дерево 260 px до 1279, 300 px дальше); раскладка журнала — по ширине области журнала (840 px)
    (§5.1). Цена: на планшете в портрете дерево не видно постоянно — лишнее касание ☰.
13. Цели касания 44 px и шрифт полей 16 px — только при `(pointer: coarse)` (§5.1 п. 2). Цена:
    ноутбук с сенсорным экраном и мышью как основным указателем получает мелкие цели.
14. Карточка записи: рядом со списком при области ≥ 840 px, иначе вместо списка с «←»; у доски
    задач — боковая панель поверх доски (§5.1 п. 5). Цена: на ноутбуке 1024 px карточка
    закрывает список, к списку — «←».
15. Новых зависимостей npm нет; граф и жесты — своим кодом (§5 «Общее», §5.10). Цена: своя
    раскладка графа на поддержке, качество раскладки ниже `d3-force` на больших графах.
16. Сбой ленивого чанка — «Обновить страницу», а не повтор `import()` (§5.1 п. 9). Цена:
    перезагрузка теряет несохранённое в соседних полях (редактор предупреждает, как сейчас).
17. `highlight.css` — `ETag` по содержимому и `no-cache` без признака (§5.1 п. 10). Цена: на
    каждой загрузке страницы — условный запрос (304).
18. Доска задач на узкой области — вкладки статусов (не аккордеон), по умолчанию «В работе»
    (§5.2 п. 1). Цена: два статуса рядом не сравнить — только переключением.
19. Доска грузит каждый статус отдельно, по 50, вместо 200 новых всех статусов (§5.2 п. 1).
    Цена: до пяти запросов при открытии доски вместо одного.
20. Число в разделах — все живые записи журнала без корзины, у «Вопросов» ещё «открыто N»;
    опроса по таймеру нет (§5.3). Цена: запись агента появится в числе при следующем открытии
    журнала или возврате на вкладку.
21. Подзадача — только по `part_of` к задаче того же пространства; у задач цикла `part_of`
    (любой длины, полный поиск по всем рёбрам) рёбра для дерева не учитываются — они на верхнем
    уровне; прогресс — `done/(total − dropped)` (§5.4 п. 1–2). Цена: шаги в другом пространстве
    (решение ↔ Knowledge) в прогресс общей не входят; задача на цикле не видна подзадачей ни одной
    общей, даже вне цикла.
22. «Давно без обновлений» — `in_progress` без живого захвата и без изменений задачи и её
    подзадач 12 ч, константа сервера (§5.4 п. 2). Цена: порог не настроить без выпуска.
23. Подзадачи на доске свёрнуты под общей, переключатель возвращает прежний вид (§5.5 п. 1).
    Цена: подзадачу без раскрытия общей на доске не видно (видна в поиске и по ссылке).
24. Копия из WebUI — в процессе сервера, один замок с автокопией; ротация `keep` — только при
    `schedule = "daily"`; удалить готовую копию можно, скачать и восстановить — нет (§5.6 п. 1).
    Цена: при `schedule = "off"` копии из WebUI копятся до ручного удаления; перенос копии — только
    с машины сервера.
25. Журнал аудита — без серверных фильтров, фильтр по загруженному (§5.6 п. 4). Цена: старое
    событие ищется листанием.
26. Итог импорта виден, пока открыт диалог (§5.7 п. 4). Цена: закрыв диалог, итог не увидеть —
    только по записям в журналах и аудиту.
27. `xtask ab`: память прогона — с субагентами, `memory_session` — без них (§5.8 п. 4). Цена:
    поле `memory` несопоставимо с отчётами 0.0.14 у прогонов с субагентами.
28. Волна не делится (≈ 1,5 ожидаемого), линия отсечения — правка журналов и граф → M7.4 при
    отставании (§5.12). Цена: «правка журналов» строки M7 может уйти на волну позже.
29. Общий граф пространства, формы Vault, серверные фильтры аудита, PWA, гибридный режим
    редактора — перенесены (§5.13). Цена: часть строки M7 ТЗ §19 («граф», «правка») закрывается
    не полностью в M7.2; на телефоне правка заметки — переключением «Текст | Предпросмотр».
30. Корзина любого журнала — с правами восстановления вида: у отчётов — прежние, у прочих —
    право записи пространства (§5.9 п. 3). Цена: участник `rw` общего решения видит удалённые
    записи решения (восстановить их он мог и раньше — по id).
31. Подзадачи и «давно без обновлений» в Markdown-выдаче агенту (MCP, дайджест, хуки) в волне не
    показываются — только JSON и `zam task` (§5.4). Цена: агент видит прогресс общей задачи
    только через `zam task show` или JSON; строка в дайджесте — отдельным решением с замером.
32. Один построитель пакета и одна проверка итога для режимов «агент» и «модель» (§6.3 п. 7).
    Почему: правила качества одинаковы, а тест с подставной моделью проверяет и путь агента. Цена:
    сильная модель работает в рамках пакета — без поиска и инструментов, её итог не лучше пакета.
33. Итог внутренних работ — только пробы и предложения человеку; знания (Rules, записи журналов)
    меняет человек (§6 «Общее», §6.7 п. 4, §6.8 п. 3). Почему: урок claude-note («поправки шире
    нужного») и «ничего не удаляется без человека». Цена: очередь решений на человеке — без него
    кандидаты и уборка стоят.
34. Разбор идей — без режима «модель», остаётся агенту (`ideas.mode`) (§6, вступление). Почему:
    разбор сверяет идею с репозиторием, у модели только пакет. Цена: без агента идеи человека не
    разбираются, даже если модель подключена.
35. Настройки исполнителя — у пользователя (`works.*`, как `ideas.mode`), подключение — запись его
    личного Vault по id, умолчание `off` и потолки — у сервера; по токену — 403 (§6.1 п. 2, §6.2
    п. 1). Почему: память и ключ — пользователя, агент не должен перенаправлять память. Цена: на
    сервере с несколькими пользователями модель подключает каждый — общего подключения
    администратора нет.
36. Два протокола (OpenAI Chat Completions, Anthropic Messages) без потока и инструментов; JSON —
    инструкцией с проверкой и одним повтором; особенности поставщика — `body_extra`, пресетов в коде
    нет (§6.2 пп. 1–5). Почему: малые пакеты, минимум кода, любой совместимый сервер. Цена:
    поставщик с особыми полями настраивается вручную по таблице руководства; без `response_format`
    слабая модель чаще ошибается в JSON (один повтор на работу).
37. `anthropic-version: 2023-06-01` по умолчанию (настраивается); параметры выборки не шлются ни в
    одной версии (§6.2 п. 3). Цена: при снятии версии поставщиком — правка `anthropic_version`;
    `temperature` у Anthropic не задать.
38. `model_access = "any"` с предупреждением; `http://` — только в LAN; LAN — по всем адресам имени
    после разрешения (§6.2 п. 7). Почему: владелец просил предупреждение, а не запрет; ключ не идёт
    в интернет открытым текстом. Цена: внешний поставщик разрешён по умолчанию; свой сервер модели в
    интернете по `http` не подключить; подмена DNS после проверки не ловится.
39. Второй скан всего тела перед отправкой: находка — запрос не отправляется (§6.2 п. 7). Цена:
    ложная находка сканера держит работу до правки записи.
40. Время — `[works] at` и `tz` (IANA, `UTC`, `±HH:MM`), по умолчанию 04:30 UTC; работы — только в
    окне `window_min`, пропущенная ночь днём не догоняется; `[backup] tz` — та же функция (§6.1
    пп. 3–4). Цена: сервер, выключенный в окне, пропускает ночь до следующей.
41. Ночь — сначала проверка, потом работы модели; при копии — ждать, при переиндексации — проверка
    пропускается (§6.5 п. 1). Цена: долгая копия может съесть окно, и работы модели уйдут на
    следующую ночь.
42. Одна миграция 0027 на волну — шесть таблиц и пересборка `usage`; ссылки `j:`, `x:`, `o:` (§6
    «Общее»). Цена: один шаг отката `bak-v26`, сервер 0.0.15 базу 27 не откроет; ещё три буквы
    ссылок в протоколе.
43. Пробы, прогоны, работы, журнал отправок и предложения — в копии, но не в экспорте и архиве
    пространства (§6 «Общее»). Цена: перенос экспортом теряет пробы, историю проверки и нерешённые
    кандидаты.
44. Одна незакрытая работа вида на пространство; в режиме `model` — до 4 пакетов вида за ночь (§6.3
    пп. 1–2). Цена: большая память покрывается пробами и уборкой за недели, а не за ночь.
45. Строка о работах — раз за сессию на первом старте, к запросу и после сжатия — нет (§6.3 п. 5).
    Цена: агент в одной долгой сессии узнает о новых работах только в следующей.
46. Пробы: ⅓ — `test` по цели; `overlap > 0,5` — отказ; 500 активных и 40 новых за ночь; пробы из
    кэша и посторонние — без исполнителя (§6.4). Цена: вместе с пересказами заголовка отсеиваются
    и честные короткие вопросы со словами заголовка.
47. Проверка идёт тем же кодом изнутри процесса, принципал — агент без сессии, без учёта (§6.5
    п. 2). Цена: обвязка MCP и HTTP (сериализация, сеть) проверкой не покрыта.
48. Вердикт — к медиане 5 сравнимых по общим пробам плюс правило «потеря устойчивых»; `degraded` —
    всегда регрессия; смена отпечатка — `changed`; пороги claude-note — до калибровки после 14
    прогонов (§6.5 п. 5). Цена: первые 5 ночей и 5 ночей после каждого обновления регрессия по
    метрикам не ловится (кроме `degraded` и потери устойчивых после накопления).
49. Строка дайджеста — только при регрессии, пока она не снята; имена `/check` и `zam check` (§6.5
    п. 7). Цена: имена расходятся с текстом задачи памяти (`eval`).
50. «Открыл» — чтение по токену той же сессией после показа, одно на сессию и цель (§6.6). Цена:
    нижняя граница — агент, которому хватило фрагмента подсказки, считается «не открывшим».
51. Кандидаты в Rules и предложения уборки — таблица `proposals` и одна страница «Предложения», а
    не новый вид записи (§6.7 п. 1). Цена: у кандидатов нет ревизий, корзины, поиска и экспорта.
52. Спонтанный кандидат — `memory_write … propose`, а 403 записи в Rules подсказывает его; новые

    «только чтение» (§6 «Общее», §6.7 п. 2). Цена: описания инструментов плотнее; клиент, который
    разрешает «только чтение» без спроса, без спроса и захватывает работы.
53. Уборка — только операции из существующих (замещение, отзыв, `revisit`, триггеры, термин,

    (§6.8). Цена: дубль остаётся в истории отозванным, а не удалённым; общее знание в решении ждёт
    переноса.
54. Волна не делится (≈ 1,3–1,5 ожидаемого), линия отсечения — уборка → M7.4; три страницы WebUI —

    уходит на волну позже; шапка WebUI длиннее на два пункта.
