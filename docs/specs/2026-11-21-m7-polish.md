## 1. Зачем

С 0.0.12-m6.5 память работает на рабочем сервере владельца: через неё ведутся этот репозиторий и
ZeroAgent. M7 по ТЗ — «Полировка»: правка в WebUI, администрирование, надёжность сервера, долги
этапов M4–M6.6. За обкатку к нему добавились задачи владельца в WebUI (мобильные устройства,
число записей в разделах), решения владельца 2026-11-21 (ключ по адресу сервера, строка очереди
идей, исполнитель внутренних работ, ночная проверка) и внешний риск: репозиторий ONNX Runtime
удалён с GitHub, сборки держатся на кэше CI.

Этап большой (около 40 задач), поэтому он идёт **волнами** с выпуском после каждой
**[решение координатора]**: память в работе, и каждая волна сразу приносит пользу на обоих
серверах, а не через недели. Очерёдность: сначала опора и безопасность, затем задачи владельца в
WebUI, затем внутренние работы, затем остальное.

## 4. Волна M7.1 «Опора и безопасность»

Ветка `m7.1-foundation` от `main`. Задачи плана — §4.1–§4.8 и итог волны (§4.9).

### 4.1. ONNX Runtime из NuGet

Репозиторий github.com/microsoft/onnxruntime с 2026-11-17 отвечает 404; сборки CI и выпуска
держатся на кэше. Проверка 2026-11-21 (`i:01M7ZB9N2QER1R4NA0XA2ZBK6E`): официальные пакеты
NuGet 1.31.0 — `Microsoft.ML.OnnxRuntime` (CPU, обе платформы в одном пакете),
`Microsoft.ML.OnnxRuntime.Gpu.Windows` и `.Gpu.Linux` — собраны под CUDA 13, и все нужные
нативные файлы **побайтово равны** прежним архивам GitHub (sha256, тот же коммит). Поэтому версия
остаётся 1.31.0, а поставляемые байты не меняются: повторная приёмка CUDA и замеры не нужны,
`deploy/cuda.toml` в силе.

1. Манифесты `deploy/onnxruntime.toml` и `deploy/onnxruntime-gpu.toml` — адреса
   `api.nuget.org/v3-flatcontainer/…/1.31.0/….nupkg`, sha256 и `size` пакета, пути
   `runtimes/<rid>/native/…` (корневого каталога нет), `rename` не нужен: в пакете Linux-библиотека
   уже `libonnxruntime.so`.
2. Загрузчик `zam-fetch` (`download.rs::format_of`) узнаёт `.nupkg` как zip.
3. `xtask fetch-deps` проверяет `size` из манифеста (сейчас не проверяет).
4. Чистка `target/deps-cache`: архивы с sha256, которых нет ни в одном текущем манифесте, удаляются
   (`xtask fetch-deps --prune-cache` в `package.yml`; иначе `restore-keys` копит прежние версии до
   лимита кэша репозитория 10 ГБ).
5. `ThirdPartyNotices.txt` пакета (тот же, что в прежних архивах) — в комплект:
   `deploy/licenses/ONNXRUNTIME-THIRD-PARTY-NOTICES.txt` (LF); сейчас он не поставлялся.
6. Проверка: CI с новым префиксом ключа кэша (без кэша) на обеих платформах, `package-smoke`;
   sha256 извлечённых файлов совпадает с прежними.

Переход на 1.31.1 и 1.32.0 — не в этой волне: у 1.32.0 другие импорты MSVC (`dxgi.dll`), нужен
отдельный прогон GPU **[решение координатора]**. Своё зеркало пакетов не делается (вопрос снят
владельцем в M6.6: источник — NuGet).

### 4.2. Сканер секретов

Дефекты: `i:01M7Z9C3FAE8ARBCX00WSZJ6SD` (русские слова-ключи) и «Передать в M7» задач 15b, 17b
журнала M6.

1. **Русские слова-ключи.** `KEY_VALUE` (`crates/zam-secrets/src/lib.rs`) узнаёт и `токен`,
   `пароль`, `секрет`, `ключ api`/`api-ключ`/`apikey`, а также падежные формы
   `токена|токеном|пароля|паролем|секрета` **[решение координатора: только формы, после которых
   естественно стоит значение]**. Слово «ключ» само по себе — не ключ-значение: «ключ
   идемпотентности: abc123» не маскируется. Граница слова для кириллицы — по Unicode.
2. **Значение после слова-ключа маскируется и тогда, когда оно состоит только из hex** (64 hex —
   типичный токен). Исключение hex остаётся только у правила энтропии, где оно нужно для хэшей и
   UUID без подписи.
3. **`Authorization: Digest …`** — маскируются `response="…"` и значения пар после схемы
   (`nonce`, `cnonce`, `opaque` — нет: это не секреты; `response` — да; `username` — нет).
4. **Предел цепочки «пароль в URL ↔ ключ-значение».** `mask_text` идемпотентна:
   `mask_text(mask_text(x)) == mask_text(x)` для любого `x` (proptest), фикстура
   `scan_depth_capped.txt` проходит без предупреждения `secrets_scan_depth`.
5. **Правила флагов снимка** (`mask_flags`, клиент: `--password X`, `-pXXX`, `-u user:pass`,
   `Authorization:`) переносятся в `zam-secrets`: их применяют и клиент, и сервер (§4.3). На
   сервере — только **внутри кода** Markdown (строки fenced-блоков и inline-спаны): находки флагов
   входят в общий скан, поэтому чанки, L0 и выдача агенту маскируются одним правилом; проза вне кода
   не трогается **[решение координатора, ревью задачи 5]**.
6. **Имена папок без живых заметок.** Разностная перепроверка секретов (`secrets_delta`) видит
   и имя папки, у которой нет живых заметок.
7. `RULES_VERSION` → 3: хранилище один раз перемаскирует заметки и записи с находками
   (механизм `secrets_scanned_v*`). Цена на рабочем сервере (CPU, около 2 тыс. записей) —
   замерить на копии базы, записать в журнал.

Сторожа (не маскируются): «ключ идемпотентности: abc123», «токенов: 1500», «токен — это строка»,
git SHA и sha256 без слова-ключа, `token_id: 01M7…` (base32-id), пути `/password/reset`.

### 4.3. Маскировка в выдаче агенту

Решение владельца 2026-11-06 (п. 9): агенту — `‹secret›` вместо значения, исходник остаётся в базе
и в WebUI, нужные ключи агент берёт из Vault; экспорт по токену — так же. Сейчас маскируется
только индекс (чанки, L0, payload); полный текст уходит агенту исходником. Карта мест выдачи —
`.tmp/m7/explore/read-paths.md` (вне git).

**Кто агент.** Запрос с `Principal::Token` (MCP, хуки, CLI `zam`); сессия WebUI (`User`,
`Admin`) — человек, ему исходник. Признак — `Principal::is_human()`, не поле `by` записи. Человек,
работающий через CLI по токену, тоже получает маску (исходник — в WebUI).

**4.3.1. Выдача (чтение).** Для токена текст проходит `mask_text` по всей ревизии **до** нарезки:
1. `POST /read`: L1, L2, `section`, `range`, фокус, дифф `since_rev` (каждая ревизия маскируется
   до диффа), L0 и L1 записей журналов, заголовки записей;
2. `GET /nodes/{id}` и по пути (`md`, `json` с `frontmatter` — `description`, `tags`, `l0`;
   `html` — маска до рендера; кэш уже разделён по зрителю), оглавление, ревизии и дифф истории,
   поле `diff` ответа 409;
3. `GET /entries` (лента, карточка, ревизии), словарь, сравнение релизов, дерево пространства
   (`frontmatter`), выжимки кэша, эхо ответов записи;
4. поиск: `expand=section` (сейчас отдаёт исходник секции — прямая утечка), заголовки записей в
   карточках;
5. `/recall`: заголовки в `entry_cand` (ловушки, решения, changelog, brief), `index_cand`, имя
   записи окружения Vault, заголовки терминов; напоминание `Stop` клиента
   (`checkpoint.rs`) — маска `zam-secrets` (задача памяти `k:01M7XTYJKSE7RAHM1NWWE7EMYW`);
6. экспорт архива по токену: текст заметок, `frontmatter`, тела, `data`, теги и `area` записей,
   история; опись получает `secrets_masked: true`, если маска что-то заменила (без находок архив
   равен исходнику); блобы — как есть (бинарь не маскируется — ограничение в
   руководстве); импорт архива с `secrets_masked: true` — предупреждение «секреты в архиве
   замаскированы и не восстановятся»;
7. предпросмотр вложений `kind=text|sheet` (`/previews`) — текст и ячейки для токена маскируются
   **[решение координатора]**; сам файл (`GET /blobs/…`) — как есть.

**Не маскируются:** пути узлов и имена файлов (это адреса; секрет в пути находит перепроверка
`secrets_delta`), раскрытие значения Vault (`reveal`, MCP `memory_vault get`) — оно и есть способ
получить ключ, текст для человека в сессии WebUI.

**Адреса `range` и фокус.** Смещения `range:r<rev>:S-E`, пропуски и их число токенов считаются по
маскированному тексту; дочитывание маскирует всю ревизию и только потом режет (маска куска ≠
кусок маски). Формат адреса не меняется **[решение координатора]**: правила сканера меняются
только с обновлением сервера, а адреса живут в пределах сессии; после смены `RULES_VERSION`
адрес старой выдачи может указать на сдвинутые байты — ограничение в руководстве. Плюс: листы с
`‹secret›` (чанки уже маскированы) начинают находиться, фокус работает и на заметках с секретами.

**Цена.** `mask_text` — до 2 мс на 100 КБ; текст больше 64 КиБ маскируется в `spawn_blocking`.

**4.3.2. Запись обратно** (иначе агент, правя маскированный текст, затрёт значение литералом).
Запись по токену — `PUT` и `PATCH` узла, правка и замещение записи журнала — проходит
**восстановление по метке** **[решение координатора, ревью задачи 6, круг 2]**: сопоставление
меток с значениями эвристикой (дифф, похожие строки, ключ) в трёх кругах ревью давало новые случаи
тихой подмены и потери значения, потому что у метки не было личности.
1. **Метки с личностью в редактируемом тексте.** В тексте, который агент может вернуть записью, —
   L2 узла (`/read` L2, `section`, `range`, фокус, `GET /nodes` `md`/`json`) и поля записи
   (`title`, `body`, строки `data`, `tags`, `area` в `GET /entries`), — каждая маска выводится как
   `‹secret-T-N›`: T — метка объекта и ревизии (6 шестнадцатеричных знаков хэша `id объекта ‖
   ревизия ‖ RULES_VERSION ‖ версия zam-secrets` — после обновления сканера старые метки не
   подставят значение по сдвинувшемуся номеру), N — порядковый номер маски в объекте (1, 2, …) **сквозной по всем редактируемым
   полям объекта** в постоянном порядке (у записи: `title`, `body`, строки `data`, `tags`,
   `area`), детерминированно **[решение координатора, ревью задачи 6, круг 4]**: номер с 1 в
   каждом поле и в каждой заметке давал тихую подмену при переносе строки между полями или
   заметками. `section`, `range` и фокус вырезаются из вида всего объекта. Метки — только у
   **текущей** ревизии: вид старой ревизии (`?rev=N`, история, куски `range:r<старая>`) —
   `‹secret›` (смещения `range` — по виду с метками). В нередактируемой выдаче (карточки поиска,
   подсказки, дайджест, заголовки индекса, экспорт) — `‹secret›`. Литерал вида `‹secret›` или
   `‹secret-…›`, лежащий в исходнике, показывается `‹secret›`.
2. **Восстановление.** База — ревизия `base_rev` (у `PATCH` — ревизия, по которой агент строил
   операции; у замещения — `If-Match`/`supersedes_rev`; без ревизии — текущая). Метка
   `‹secret-T-N›`, у которой T — метка этого объекта и **любой его ревизии** (сервер находит
   ревизию по T; две ревизии с одним T — метка не восстанавливается), а N — номер маски той
   ревизии, заменяется значением этой маски в любом поле объекта **[решение координатора,
   финальное ревью M7.1]**: вторая правка подряд из того же контекста агента (прочитал r, записал
   r+1, пишет снова по `rev` из ответа) не теряет значения; личность метки — объект, ревизия и
   номер — точна, подмены нет. Повтор — повтор значения (явный выбор агента). Любая другая метка
   (чужой T, номер вне той ревизии, `‹secret›`, `‹secret-N›` без T) записывается как есть.
   Восстановление идёт после проверки доступа к объекту (пространство, вид записи) — как у
   чтения: о чужом объекте агент не узнаёт ничего, кроме 404. Предупреждение `secret_mark_kept` — с числом меток-литералов в итоге
   поля сверх их числа в исходнике текущей ревизии этого поля (литералы из архивов с маской не
   предупреждают на каждой правке; чужая метка вместо значения — предупреждает). Маска базы,
   которую агент не вернул, — удалена агентом явно, как любой текст.
3. Операции `PATCH` по секциям применяются к исходнику текущей ревизии, метки операций
   восстанавливаются по маскам ревизий их меток (п. 2); адрес секции сопоставляется сначала точно с
   заголовками вида с метками, а если точного совпадения нет и в адресе есть `‹secret›` — с
   заголовками, где `‹secret-…›` заменены на `‹secret›` (одна секция — она, несколько — 422).
   То же сопоставление — у `/read section`. Замещение записи, тело которого несёт `‹secret-…›`,
   требует ревизию (`If-Match` или `supersedes_rev`; без неё — 428).
4. Запись человеком в сессии WebUI — без восстановления (он видит исходник).
5. **Покрытие по происхождению.** После сборки каждое изменённое поле сканируется заново; должна
   быть целиком покрыта находкой каждая позиция итога, где стоит секретное значение: (а)
   восстановленное из метки и (б) маска текущей ревизии, перенесённая в итог без правки (у
   `PATCH` — вне изменённых операциями мест; у `PUT` и правки поля записи таких нет — поле
   присылается целиком). Иначе запись отклоняется — 422 `secret_context_changed` с номерами строк
   итога, без значения: агент сменил окружение значения (снял или открыл забор кода, переписал
   `ключ: значение` прозой, разобрал URL), в том числе вне правленого места. Текст, набранный
   агентом, не проверяется: значения в нём нет, кроме угаданного, а угаданное агент знает
   **[решение координатора, ревью задачи 6, круг 4]**: правило «число непокрытых вхождений строки
   значения» давало обход и ложные 422 на слабых значениях (`postgres`, `pass`) и оракул подбора
   значения. Проверка одна для `PUT`, `PATCH`, правки и замещения записи; цена линейна (позиции
   известны, находки упорядочены).
6. Адреса `range` и фокус считаются по виду с метками; листы чанков (маска без меток)
   сопоставляются с ним с учётом меток.
7. **Ограничение.** Отказ 422 сообщает агенту, покрыто ли восстановленное значение правилом в
   новом окружении; нарочитый противник повторами узнаёт свойства значения (энтропия, префикс), но
   не само значение. Защита — от ошибки агента, а не от враждебного агента с токеном.

Признак `/health.features`: `agent_text_masked` (выдача и восстановление); строка в
`docs/api-compat.md`; протокол `zam guide` («секреты в выдаче — ‹secret›, ключ — из Vault;
при правке сохраняйте метки `‹secret-…›` как есть — значение сохранится; метка действует только для
объекта и ревизии, с которых прочитана»).

### 4.4. Ключ доступа по адресу сервера

Решение владельца `i:01M7Z4SBS0EJA816CCYPKPA4TA`: один проект ходит в один сервер, ключ берётся по
адресу этого сервера, ключ одного сервера на другой не отправляется.

1. Домашний `~/.zeroaimemory/config.toml`: `[servers."<адрес>"] token = "…"`; адрес нормализован
   (схема и хост в нижнем регистре, без `/` в конце, порт как есть). Прежние `url`/`token`
   верхнего уровня читаются как раньше: `token` верхнего уровня принадлежит `url` верхнего уровня.
2. `locate::resolve`: шаг 4 берёт ключ только для найденного адреса. Ключа нет → ошибка с
   подсказкой `zam init --url <адрес> --token …`; ключ другого адреса не отправляется.
3. `zam init --token` пишет `[servers."<адрес>"]` и не трогает другие адреса; старый формат при
   записи переводится в новый без потери ключа; прежнее предупреждение о замене ключа другого
   сервера уходит.
4. `zam status` — источник ключа `~/.zeroaimemory/config.toml [servers."<адрес>"]`.
5. Руководство: обход через `--url-to local` и `ZAM_TOKEN` для второго сервера больше не нужен
   (`deploy/README-install.md`, README, ТЗ §14.1).

Флаг `--token`, `ZAM_TOKEN` и ключ в файлах проекта — по-прежнему сильнее домашнего конфига.

### 4.5. Строка очереди идей и мелочи подсказок

1. **Одна строка за эпоху** (решение владельца `i:01M7Z53BM6EGK9Z9W5G18NYGAM`). Вместо строки на
   каждую идею — одна: «идей ждут разбора: N, первая «…» — список: `zam idea queue`» (текст —
   константа рядом с `REVIEW_QUEUE_LEAD`, ru/en, ≤ 60 токенов). Показ — раз за эпоху; новая
   эпоха (сжатие контекста) — снова, если очередь не пуста. **Рост очереди внутри эпохи** (пришла
   идея, которой не было при показе) — строка повторяется один раз с новым числом
   **[решение координатора: новая идея не должна ждать сжатия]**. Подсказки-идеи по близости к
   запросу не меняются.
2. **Слова-реплики** (`PROMPT_REPLY_WORDS`, `crates/zam-search/src/recall.rs` ≈:308): список
   дополнен формами («ладно», «сделай», «делай», «продолжаем», «продолжим», «хорошо», «хорош»,
   «давай», «поехали», «приступай»). Сравнение остаётся точным, целым словом: по решению M6.6
   основа реплики не должна съедать предметное слово («продол» ↛ «продолжительность»). Новые
   случаи тишины — в `eval/hints.toml`.
3. **`term_alias_broad`** не считает «слишком коротким» псевдоним-аббревиатуру из двух и более
   заглавных (`UI`, `DB`, `CI`): с M6.6 он сравнивается с учётом регистра.
4. **`memory_vault delete` по имени** удаляет только при точном совпадении имени (с учётом
   регистра); совпадение без учёта регистра — 404 с подсказкой точного имени.

### 4.6. Подсказки к ошибкам команд

1. **Ожидаемый ненулевой код** — не ошибка: простая команда (без `|`, `;`, `&&`, `||`) `grep`,
   `rg`, `diff`, `cmp`, `test`, `[`, `git diff --quiet`/`--exit-code` с кодом 1 и пустым stderr —
   ни события `error`, ни пары «ошибка → исправление», ни петли, ни запроса к серверу. Первым —
   тест RED на «Exit code 1» у `grep` без вывода.
2. **Классы «не повторяй»** — одна строка до 30 токенов, раз за сессию на класс и отпечаток,
   локально, без сети: 401/`invalid_grant` (проверь ключ, не повторяй тот же запрос), 403/scope,
   квота, `ENOSPC`/«No space left», 429 с `Retry-After`, 400/422 (проверь запрос, а не повторяй).
3. **Точность подсказок к ошибкам** (замечание обкатки 37: на `ls` с кодом 2 пришла ловушка
   LNK1104). Покрытие считается по **предметным** словам ошибки: слова, частые в корпусе insight
   решения (доля документов выше порога), и служебные слова вывода (`No such file`, имена
   каталогов из команды) в покрытие не идут; одно совпадение кода ошибки (`LNK1104`, `E0432`)
   по-прежнему достаточно. Порог — по набору `eval/hints.toml` (случаи `post_tool`), правило —
   записать в журнал до прогона.
4. Бюджет хука §10.3 не растёт; блок v8 не меняется.

## 12. Решения координатора (на проверку владельцу)

1. Этап волнами с выпуском после каждой. Цена: накладные расходы выпуска (полный прогон, CI,
   развёртывание) шесть раз вместо одного.
2. Очерёдность волн: опора → WebUI → внутренние работы → администрирование → поиск → клиенты.
   Цена: если важнее другое, его ждут дольше.
3. Волну можно делить и сливать по объёму. Цена: номера выпусков не совпадут с таблицей §2.
4. Русские слова-ключи — только формы, после которых естественно стоит значение (§4.2 п. 1).
   Цена: редкие формы («токенами: …») не маскируются.
5. Строка очереди повторяется один раз при росте очереди внутри эпохи (§4.5 п. 1). Цена: +1
   строка ≈ 50 токенов на рост очереди.
6. Порог задержки `prompt` — к предыдущему выпуску, а не к M5.7 (§4.8 п. 3). Цена: медленный
   накопленный рост ловят только абсолютные пороги.
7. Формат адреса `range` не меняется при маскировке (§4.3.1). Цена: после обновления сервера со
   сменой правил сканера адрес, выданный до обновления, может указать на сдвинутые байты.
8. `‹secret›` в добавленном агентом тексте сохраняется с предупреждением, а не отказом (§4.3.2
   п. 2). Цена: литерал `‹secret›` в тексте, если агент сам его вписал.
9. Экспорт по токену маскируется, блобы — нет (§4.3.1 п. 6). Цена: полная копия с секретами —
   только из WebUI или `zam-server backup`; секрет внутри бинарного вложения уходит в архив.
10. Восстановление при записи — по метке `‹secret-T-N›` (объект, ревизия, номер), а не
    эвристикой выравнивания (§4.3.2); покрытие проверяется по происхождению значений, а не по
    вхождениям строки. Цена: формат меток в редактируемой выдаче агенту отличается от `‹secret›`
    прочей выдачи; агент, переписавший метку или перенёсший её в другую заметку, теряет значение
    в текущей ревизии (с предупреждением, значение остаётся в истории).
11. Флаги командной строки на сервере — только внутри кода (§4.2 п. 5). Цена: флаг в прозе
    (`mysql -pX` без обратных кавычек) не маскируется.
