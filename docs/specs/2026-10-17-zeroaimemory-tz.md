## 1. Назначение и мотивация

ZeroAIMemory — централизованная, человекочитаемая память для AI-агентов. Это самодостаточный сервис («вещь в себе»): работает без внешних энкодеров и облачных сервисов, все модели хранит и запускает сам. Записи образуют иерархическое дерево, как в Notion или Obsidian. Агенты работают через API по токену. Человек работает через собственный WebUI сервиса.

Какие проблемы решает (со слов владельца):

1. **Агент забывает пройденное.** В долгой работе над большими проектами агент повторяет уже разобранные ошибки. Пример: забывает, что перевод строки в Linux-скриптах делается иначе, чем в Windows, и не помнит, что эту ошибку уже разбирали.
2. **В исследованиях теряются проверенные гипотезы**, и агент заново пробует то, что уже провалилось.
3. **Память нужна везде.** Она должна быть общей для разных сессий, разных машин и разных мест, откуда ведётся один проект.
4. **Нужен мощный и контролируемый инструмент.** Человек видит всё, что агент «помнит», может это исправить и управлять этим.

### 1.1. Главный приёмочный сценарий «CRLF»

Сценарий проверяет решение проблемы 1 и оформляется как автоматический e2e-тест.

1. В проекте A агент сталкивается с ошибкой `/bin/bash^M: bad interpreter`, разбирается и записывает инсайт:
   - вид `gotcha`, область `global` (знания пользователя, а не одного проекта);
   - триггеры `file_glob: **/*.sh` и `error_regex: \^M|bad interpreter`.
2. Через неделю, на другой машине, в проекте B агент собирается создать `deploy.sh`.
3. Перед записью файла хук локально сопоставляет триггер и подмешивает в контекст агента напоминание: «ZeroAIMemory: для *.sh используйте LF; ранее разобрано — <ссылка>». Агент пишет файл правильно.
4. Если ошибка всё же произошла, хук после команды узнаёт текст ошибки и сообщает: «Эта ошибка уже разбиралась: <инсайт>».

Как это устроено, описано в §10.

## 2. Цели, не-цели, анти-цели

### 2.1. Цели
- **G1. Скорость и экономия памяти.** Приоритет №1. Конкретные значения — в §17.
- **G2. Собственный WebUI с полной поддержкой Markdown и медиа.**
  - Просмотр и правка заметок.
  - Встроенные изображения, видео и аудио.
  - Просмотр документов: как минимум DOCX, XLSX и PDF (§15).
  - Источник истины — Markdown, так что содержимое остаётся человекочитаемым и вне сервиса: экспорт в `.md` с вложениями.
- **G3. Централизация.** Один сервер в локальной сети. Агенты с любых машин обращаются к нему напрямую или через внешний прокси. Проект однозначно идентифицируется на всех машинах.
- **G4. Иерархический гибридный RAG** с точными ссылками на источники. Плюс граф связей между записями.
- **G5. Проактивное вспоминание.** Важные знания приходят к агенту автоматически, в момент, когда они нужны. Механизм построен на хуках и триггерах и отключается (§10).
- **G6. Контролируемость.**
  - Каждая запись атрибутирована: кто, когда, в какой сессии и на какой машине.
  - Ревизии сохраняются, их можно откатить; удаление мягкое.
  - Устаревшее не удаляется молча, а помечается.
- **G7. Самодостаточность.** Эмбеддинги и (опциональный) реранк работают на встроенных моделях. GPU используется, если он есть, без него всё работает на CPU. Текст сервер не генерирует.
- **G9. Выжимку делает сам агент, с экономией токенов.** Сервер отдаёт компактный список кандидатов. Агент сам выбирает нужное, дочитывает только необходимое и формирует выжимку. Готовую выжимку агент сохраняет в кэш, чтобы потом использовать повторно (§9.3–9.5).
- **G10. Быстрое подключение агента.** WebUI выдаёт готовый текст для CLAUDE.md или AGENTS.md. Его достаточно вставить, и агент начинает правильно пользоваться памятью (§15.5).
- **G8. Простота для одного владельца** с возможностью завести дополнительных пользователей (§11.4).

### 2.2. Не-цели (v1)
- Совместное редактирование в реальном времени (CRDT). Вместо него — оптимистическая блокировка (§11.3).
- Автоматическое извлечение памяти из диалогов. Запись всегда явная, её делает агент через инструменты; есть режим черновиков на подтверждение (v2, §10.6).
- Отдельная графовая СУБД. Граф хранится в SQLite (§8.5).
- Генеративные модели (LLM) на сервере. Выжимку, сводки и синтез знаний делает агент-клиент.
- TLS, публикация в интернет, OAuth. Сервер слушает локальную сеть; внешний доступ даёт внешний прокси (Traefik и т. п.).
- Офлайн-режим клиента (в v2 — очередь журнальных записей).
- OCR изображений и транскрибация видео и аудио.
- Регистрация пользователей самостоятельно.

### 2.3. Анти-цели: провал, даже если всё «технически работает»
- Знания тихо теряются: запись удалена или перезаписана без следа в истории.
- Содержимое Human или секреты vault попадают в векторный индекс, в выдачу поиска или в логи.
- Хуки заметно тормозят агента (больше 300 мс на событие) или засоряют контекст нерелевантными напоминаниями.
- Только что записанное не находится, и агент не знает почему.
- Сервер нельзя восстановить из бэкапа или переиндексировать.
- Агент «вспоминает» отменённое: отозванные или замещённые инсайты выдаются как действующие.
- Для работы нужен внешний сервис: энкодер, облако, отдельный Python.

## 3. Термины

| Термин | Определение |
|---|---|
| **Администратор** | Владелец сервиса. Логин и пароль задаются в конфигурации сервера. Входит в WebUI и видит все разделы, включая администраторские. Сам тоже является пользователем со своей памятью. |
| **Пользователь** | Владелец отдельной памяти: база `users/<user_id>.db`. Агенты пользователя работают с API по токену. Сам пользователь входит в WebUI по паролю, который задаёт администратор (смена при первом входе), и видит только свою память и доступные ему решения; администраторские разделы ему не видны (§11.4, §15.1) — **решение владельца 2026-10-26**. Первый пользователь — сам администратор. Остальных заводит администратор. |
| **Токен** | Bearer-токен доступа к API памяти конкретного пользователя. Прописывается агенту в CLAUDE.md или AGENTS.md. |
| **Пространство (Space)** | Корень дерева в памяти пользователя. Виды: `rules`, `human`, `knowledge`, `solution`. |
| **Решение (Solution)** | Пространство проекта в базе пользователя-владельца. Идентифицируется `agent_solution_id` (GUID) из `.zeroaimemory/solution.toml`. Каталоги с одинаковым GUID делят общую память. Решение может быть общим для нескольких пользователей (§11.6). |
| **Владелец решения** | Пользователь, первым зарегистрировавший `agent_solution_id`: решение лежит в его базе. Подтверждает и отзывает доступ участников; сам участником не бывает. |
| **Участник решения** | Другой пользователь, чей запрос на доступ к решению одобрен владельцем. Видит в базе владельца только пространство этого решения; режим доступа — `rw` или `ro` (§11.6). |
| **Область (Area)** | Подраздел решения, например отдельный сервис в монорепозитории. Это метка записей (§11.2). |
| **Заметка / Папка** | Узлы дерева. Заметка — Markdown-документ с ревизиями и frontmatter. Папка содержит только свёртку своих детей. |
| **Секция** | Часть заметки под заголовком H1–H3. |
| **Чанк** | Фрагмент текста для индекса: лист секции или сводка уровня секции, заметки или папки. |
| **Вложение (Blob)** | Файл: изображение, видео, аудио, документ. Хранится на диске, адресуется по SHA-256. |
| **Журналы** | Встроенные записи решения: `changelog`, `releases`, `insights`. Vault — отдельное хранилище секретов (§7.6). |
| **Эпистемический статус** (`certainty`) | Степень надёжности записи или заметки: `axiom` (установлено человеком — в WebUI или агентом по прямому указанию пользователя), `theorem` (проверено, есть доказательство), `hypothesis` (предположение). Не путать со статусом жизненного цикла insight (§7.5). |
| **Инсайт** | Запись об открытии, провале, ловушке, решении или эксперименте. Имеет статус и триггеры. |
| **Триггер** | Детерминированное условие показа инсайта: маска файла, regex команды, regex ошибки, ключевое слово. |
| **Связь (Edge)** | Типизированное ребро графа между заметками и записями (§8.5). |
| **Сессия** | Сессия агента. Идентификатор берётся у агента (например, `session_id` Claude Code) или генерируется сервером/CLI (UUIDv7); передаётся заголовком `X-Zam-Session`. Хранится в таблице `sessions` базы пользователя (§6.3). Не путать с cookie-сессией WebUI (`web_sessions`). |
| **L0 / L1 / L2** | Уровни детализации узла: L0 — абстракт до 50 токенов, L1 — обзор до 300 токенов, L2 — полный текст. |

## 4. Архитектура

### 4.1. Принципы
1. **Источник истины — SQLite и файлы вложений.** Qdrant — производный индекс, перестраивается из SQLite.
2. **На сервере нет генеративной модели.** Поиск, триггеры и хуки работают детерминированно. Выжимку из найденного делает агент (§9.3). Сервер хранит её в кэше и следит, чтобы она оставалась актуальной (§9.4).
3. **Запись явная и атрибутированная.**
4. **История только дописывается.** Ревизии и журналы не перезаписываются, удаление мягкое.
5. **Ядро — REST.** MCP, CLI и WebUI — тонкие адаптеры над одним ядром.
6. **Деградация вместо отказа.** Если Qdrant или модель недоступны, запись продолжает работать (векторы ставятся в очередь), а поиск идёт по FTS5 с флагом `degraded: true`.
7. **Самодостаточность.** Модели загружаются и исполняются сервером. Внешние ML-сервисы не нужны.

### 4.2. Компоненты

```
 ┌──────── машина 1..N ─────────┐                  ┌──────────── сервер (LAN) ─────────────────────────────┐
 │ Claude Code / Codex / …      │                  │ zam-server (Rust)                                     │
 │  ├─ MCP (HTTP) ──────────────┼─ HTTP(S) ───┐    │  ├─ REST /api/v1  ├─ MCP /mcp  ├─ WebUI (встроен)     │
 │  └─ хуки ─▶ zam (CLI, Rust) ─┼─ HTTP(S) ───┤    │  ├─ Auth: admin (конфиг), пароли, токены              │
 │       └─ кэш триггеров       │             │    │  ├─ Store: system.db + users/*.db (SQLite, FTS5)      │
 │ CLAUDE.md: URL + токен       │   [Traefik  ├───▶│  ├─ Blobs: data/blobs/<user>/<aa>/<sha256>            │
 │ .zeroaimemory/solution.toml  │   и т.п.,   │    │  ├─ Docs: извлечение текста, превью DOCX/XLSX/PDF     │
 └──────────────────────────────┘   снаружи]  │    │  ├─ ML: bge-m3, [реранкер] (ONNX; CPU/CUDA)           │
 ┌──── браузер ────┐                          │    │  ├─ Search: FTS5 + Qdrant + граф → RRF → [rerank]     │
 │ WebUI (люди)    │─────────────────────────-┘    │  ├─ Recall: хуки, триггеры, дайджесты, сессии         │
                                                   │  ├─ Cache: выжимки агентов + контроль актуальности    │
 └─────────────────┘                               │  └─ Qdrant client ──gRPC──▶ Qdrant (в составе поставки) │
                                                   └───────────────────────────────────────────────────────┘
```

Qdrant поставляется вместе с сервисом как нативный исполняемый файл, без Docker. Его запускает и контролирует сам `zam-server` (§4.3). Так сохраняется «вещь в себе».

### 4.3. Qdrant: поставка и управление процессом
Подробности и источники — в исследовании 04, §1.

- **Версия.** Версия Qdrant закрепляется в манифесте поставки `deploy/qdrant.toml`: версия и SHA-256 архива для каждой платформы. Стартовая версия — 1.19.2. `qdrant-client` берётся той же минорной версии.
- **Сборки:**
  - `x86_64-pc-windows-msvc` с копией `vcruntime140.dll` рядом с exe;
  - `x86_64-unknown-linux-musl`. Сборку gnu не берём: ей нужна glibc ≥ 2.39.
- **Где лежит бинарник:** `<install>/qdrant/<ver>/qdrant[.exe]`. Если его нет, `zam-server qdrant fetch` скачивает архив с GitHub Releases и проверяет SHA-256.
- **Режимы** (`qdrant.mode`):
  - `managed` (по умолчанию): процесс запускает и контролирует `zam-server`;
  - `external`: подключение к уже работающему Qdrant по URL;
  - `edge` — экспериментальный, под feature-флагом: встраиваемая библиотека `qdrant-edge`, сейчас в бете. Это второй адаптер за трейтом `VectorIndex` (`EdgeIndex`, feature `edge` у `zam-index`; в сервер и комплекты не входит; `qdrant.mode = "edge"` конфиг принимает, но сервер при нём выключает векторный поиск с причиной в журнале). Прототип M2 не прошёл критерий перехода: p95 быстрее в 1,6 раза (нужно ≥ 2×), RSS выше в 2,2 раза (`docs/adr/0001-qdrant-edge.md`). Пересмотр — по условиям ADR, не раньше версии 1.0.
- **Запуск в режиме `managed`:**
  - рабочий каталог — `<data_dir>/qdrant/`, явно: Qdrant подхватывает `config/*` из текущего каталога;
  - `--config-path` указывает на сгенерированный конфиг: `host: 127.0.0.1`, порты из настроек (по умолчанию 6333/6334), `enable_cors: false`, `telemetry_disabled: true`, `logger.format: json`;
  - `QDRANT__SERVICE__API_KEY` — случайный ключ, новый при каждом старте; передаётся только через переменную окружения;
  - `QDRANT_INIT_FILE_PATH` указывает внутрь `<data_dir>/qdrant/`;
  - stdout и stderr Qdrant через pipe попадают в `tracing` с полем `component=qdrant`.
- **Жизненный цикл:**
  - **Привязка к родителю.**
    - Windows: Job Object с `KILL_ON_JOB_CLOSE`, процесс создаётся с `CREATE_SUSPENDED` → назначается в job → `ResumeThread`, флаг `CREATE_NO_WINDOW`;
    - Linux: `PR_SET_PDEATHSIG` из долгоживущего потока-супервизора.
  - **Защита от второго экземпляра.** Свой лок-файл на `<data_dir>/qdrant/` и pid-файл. Осиротевший процесс находится по pid-файлу и порту и завершается.
  - **Готовность.** Сначала `/readyz`, затем статус коллекции через клиент. Версия из `GET /` сверяется с манифестом. Qdrant запускается параллельно с загрузкой модели эмбеддингов (если модель установлена): готовность Qdrant не ждёт чтения модели с диска (§17).
  - **Падение и поиск.** При состоянии `Ready` поиск сверяется с живостью процесса по pid (проверка ОС, без обращения к Qdrant): между смертью процесса и сменой состояния супервизором запрос не уходит в закрытый порт. Соединение с Qdrant ограничено 300 мс: на Windows отказ соединения с закрытым портом localhost приходит лишь через ~2 с на попытку, и до этого правила первый поиск после падения ждал 2–4 с **[решение исполнителя, задача 15 M2]**.
  - **Перезапуск при падении.** Экспоненциальная задержка от 1 до 60 с с jitter. После 5 падений за 10 минут — circuit breaker: сервер работает в режиме деградации (§4.1 п. 6) и показывает алерт в WebUI и в `/index/status`.
  - **Остановка.**
    1. Прекратить отправку записей (остановить воркер индексации); все записи идут с `wait=true`.
    2. Если после записи прошло мало времени — дождаться, пока Qdrant подтвердит её в WAL (`ack_index` в `wal/first-index` не меньше последнего `operation_id`), не дольше `qdrant.shutdown_flush_wait_ms` (14 с): иначе следующий старт повторяет неподтверждённый WAL и синхронно сбрасывает сегменты (на HDD ~5 с вместо ~2 с) **[решение исполнителя, задача 19 M3]**. Умолчания `qdrant.flush_interval_sec = 3` и `qdrant.shutdown_flush_wait_ms = 14000` (в M3 было 5 с и 10 000 мс) — **решение владельца 2026-10-26**: подтверждение WAL при интервале 3 с приходит за 4,4–8,7 с, предел ожидания взят на 40 % больше прежнего (§17).
    3. Linux: SIGTERM, ждать 10 с, затем SIGKILL. Windows: `TerminateProcess` — Qdrant на Windows слушает только Ctrl+C, а целостность обеспечивают его WAL и пересборка из SQLite.
    4. Сам `zam-server` останавливается по Ctrl+C, SIGTERM, (Windows) Ctrl+Break, а в режиме службы (§13.3, §16.2) — по `Stop`/`Shutdown`/`Preshutdown` SCM и `systemctl stop` (`KillSignal=SIGINT`): все пути ведут в один общий сигнал остановки сервера. Худший случай: пачка инференса воркера до 60 с, перечанковка до 10 с, WAL до 14 с, SIGTERM Qdrant до 10 с; обычно после записи — 10–20 с. Таймаут остановки службы — `T = max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с (при умолчаниях 94 с; запас 80 с покрывает пачку инференса, перенарезку и SIGTERM Qdrant) **[решение контроллера, R4]**: `zam-server service install` выставляет его по конфигу (§13.3), юнит в `deploy/systemd/` и NSSM (`AppStopMethodConsole`) в документах — не меньше этой величины, а при старте под службой сервер сверяет таймаут службы с ней и при нехватке пишет WARN с командой исправления; при ручном запуске проверки нет — **решение владельца 2026-10-26**.
- **Согласованность с SQLite.** Задания `index_jobs` работают как outbox: задание закрывается только после подтверждённого upsert. Повтор идемпотентен, потому что id точки детерминирован.
- **Обновление Qdrant.** Пропускать минорные версии формат хранения не позволяет. Индекс у нас производный, поэтому если новая версия старше хранилища больше чем на одну минорную, при откате или при ошибке миграции сервер удаляет `<data_dir>/qdrant/storage` и пересобирает индекс из таблицы `embeddings`, без инференса. Это событие пишется в аудит. При обновлении закреплённой версии (`deploy/qdrant.toml`) проверяется формат и путь `storage/collections/zam_chunks/0/wal/first-index` (`ack_index`; `zam_index::supervisor::wal_ack`): на нём держатся ожидание WAL при остановке и `qdrant.wal_pending_ops` **[решение исполнителя, задача 20 M3]**.
- **Ресурсы.** Пределы памяти и потоков Qdrant задаются в конфиге (`qdrant.max_search_threads`, `qdrant.optimizer_threads`), чтобы он не отбирал CPU у инференса.

### 5.3. Markdown на сервере: правила `zam-markdown`
- **Включённые расширения comrak:** GFM (таблицы, задачи, зачёркивание, автоссылки, tagfilter-эквивалент через ammonia), сноски, `wikilinks_title_after_pipe`, alerts, `math_dollars` + `math_code`, `front_matter_delimiter = "---"`, `header_id_prefix`, `sourcepos`.
- **Свои проходы по AST:**
  - callout в стиле Obsidian (`> [!info]-`, произвольные типы и сворачивание): comrak знает только 5 типов GitHub;
  - нормализация `[[Заметка#Секция|текст]]` в цель и якорь;
  - перевод `sourcepos` (строка и колонка в байтах) в байтовые оффсеты через таблицу начал строк. Учитываются CRLF и BOM.
- **Секция** — диапазон от заголовка уровня N до следующего заголовка уровня ≤ N на верхнем уровне документа. Заголовки внутри списков и цитат секций не образуют, setext-заголовки учитываются.
- **PATCH** — только байтовая замена фрагмента исходника (`splice`), затем повторный разбор и проверка. Обратная сериализация AST (`format_commonmark`) запрещена. Инвариант: байты вне изменённого диапазона совпадают с исходными.
- **Тесты:** golden-файлы, property-тесты инварианта PATCH и фаззинг (`cargo-fuzz`) разбора и позиций. Inline-позиции comrak исторически были хрупкими, поэтому в тестах их сверяют с `pulldown-cmark`, у которого точные байтовые диапазоны (dev-зависимость).
- **Один разбор — все потребители:** секции, чанки, оглавление, ссылки для графа, HTML для WebUI. HTML рендерится с `data-sourcepos`, проходит `ammonia` и кэшируется по `(content_hash, render_version)`.

### 6.1. Каталог данных

### 6.3. `users/<user_id>.db`

Идентификаторы — UUIDv7. Время — UTC, ISO-8601.

- **Состав базы пользователя:** Rules, Human, Knowledge (в том числе журнал insights с `scope=global`), его решения (пространства `solution`: заметки, ревизии, журналы, граф, чанки, индекс) и Vault. Решение, которым владеет другой пользователь, в базе участника не хранится: сервер обращается к базе владельца (§11.6).
- **Атрибуция.** `revisions.user_id`, `entries.user_id` и `entry_revisions.user_id` — пользователь, чьим токеном сделана запись; `NULL` означает владельца базы (так записаны данные M1–M2).
- **Эпистемический статус.** `nodes.certainty` (заметки, из frontmatter), `entries.certainty` (insight), в `entry_revisions` — `certainty` и `reason` (причина смены статуса или `certainty`) (§7.5).
- **Vault** — отдельные таблицы `vault_items`/`vault_revisions` вместо `entries.kind='vault'` **[решение исполнителя]**: значения секретов структурно вне конвейера индексации (у них нет чанков, FTS и заданий индексации).
- **Рёбра — только внутри одной базы.** Цель в другой базе (личная память участника и решение в базе владельца) отклоняется (422): межбазовые связи не делаются — нужное проекту знание кладут в проект (**решение владельца 2026-10-26**). Внутри базы владельца рёбра между его пространствами допустимы, но участнику рёбра за пределы пространства решения не видны (§8.5).
- **Сессии, показы, оценки, кэш выжимок (M4)** — где лежат:
  - `sessions`, `session_seen` — в базе пользователя запроса (сессия принадлежит пользователю, даже если цель лежит в чужом решении; `session_seen.owner_id` — владелец базы цели);
  - `usage` — в базе, где лежит цель: владелец решения видит показы и оценки записей своего решения, в том числе от участников;
  - `answer_cache`, `cache_deps` — в базе пространства кэша: выжимка по решению — в базе владельца решения (общая на решение), по личным пространствам (Knowledge, Rules) — в базе пользователя (§9.4);
  - срок хранения: `sessions` и `session_seen` без обращений (`last_seen_at`) дольше 30 дней удаляет воркер обслуживания раз в сутки; `usage` — бессрочно; кэш — §9.4;
  - `sessions.memory_writes` сервер увеличивает при любой записи в память с `X-Zam-Session` этой сессии (узел, запись журнала, связь, Vault, `cache_put`); его читает хук `checkpoint` (§10.3) **[решение контроллера, план M4]**. ### 6.4. Qdrant

Одна коллекция `zam_chunks`.

- **Именованные векторы:**
  - `dense` — 1024, cosine, HNSW (m=16). Оригиналы хранятся на диске (`memory: cold`, mmap), квантованная int8-копия закреплена в RAM (`pinned`), поиск идёт по int8 с пересчётом по оригиналам;
  - `sparse` — веса bge-m3, без IDF-модификатора;
  - `colbert` — в v1 не хранится: на 1 млн чанков это сотни гигабайт. Вариант для v2 — пересчёт ColBERT-векторов на лету для top-k кандидатов или хранение `cold`, uint8, без HNSW.
- **Оценка памяти Qdrant** на 1 млн чанков: около 1,5–2,5 ГБ RAM, около 5 ГБ на диске.
- **Payload и индексы:** `user_id` (`is_tenant`; владелец базы), `space_id`, `space_kind`, `solution_guid`, `node_id`, `entry_id`, `path_ancestors`, `area`, `level`, `kind`, `insight_kind`, `status`, `certainty`, `tags`, `updated_at`, `rev`, `text_hash`.
- **Область поиска.** Тенант точки — пользователь-владелец базы (`user_id`). Общее решение лежит в базе владельца, поэтому фильтр поиска — дизъюнкция областей: «`user_id` пользователя и его пространства» ИЛИ «`user_id` владельца и `space_id` решения» для каждого доступного общего решения (§11.6); `path_prefix` применяется внутри каждой области. Пустой набор областей даёт пустую выдачу **[решение владельца 2026-10-21]**; область без пространств тоже ничего не пропускает (а не «все пространства владельца»), и так же ведут себя подсчёт и удаление по области **[решение исполнителя]**.
- **Новые поля payload** (`entry_id`, `status`, `insight_kind`, `certainty`) добавляются в существующую коллекцию без пересборки; payload-индексы создаются для них и ещё для `kind` и `area` (`metadata.schema` остаётся 1). Фильтр статуса — исключающий («не `superseded` и не `retracted`»), поэтому точки без поля `status` (заметки, папки, точки M2) проходят. Фильтр `certainty` включается, только если запрошен.
- **Никогда не попадают в Qdrant:** пространство `human`, значения vault, узлы с `index: false`.
- **Идентификатор модели** (`model_id`) хранится в метаданных коллекции. Если он расходится с текущим, векторный поиск запрещается до переиндексации, и поиск явно сообщает об этом.

### 6.5. Вложения и ссылки
- **Хранение.** Вложения узла общего решения лежат в каталоге владельца базы; участник получает их через сервер в пределах пространства решения. Атомарная запись (временный файл → rename), подсчёт ссылок `refcount`. Сборщик мусора удаляет блобы с `refcount=0` старше 7 дней.
- **Ссылка в Markdown** относительна от корня пространства: `_attachments/<sha256[0..16]>/<имя>`. Сервер разрешает её через таблицу `attachments`. **[решение исполнителя]**
- **Встраивание** — стандартный синтаксис `![подпись](_attachments/…)`. Вид определяется по MIME (§15.2).
- **Лимит** по умолчанию 200 МБ на файл, настраивается. Отдача поддерживает `Range` (видео, аудио, большие PDF).

## 7. Пространства и журналы

### 7.1. Пространства пользователя
В дереве WebUI они закреплены сверху именно в этом порядке.

| Пространство | Кто пишет | Агент (по токену) | Векторный индекс |
|---|---|---|---|
| **Rules** | Человек (WebUI); агент — только с токеном `rw`, если в настройках включено `rules.agent_write` (по умолчанию выключено) | Читает; подмешивается при старте сессии | Да |
| **Human** | Только человек (WebUI) | **Нет доступа** | **Нет**. Только FTS5 для поиска в WebUI |
| **Knowledge** | Агент и человек | Читает и пишет | Да |
| **Solutions/** | Агент и человек; у общего решения — участники с режимом `rw` (§11.6) | Читает и пишет; у участника `ro` только читает | Да |

**Knowledge** — глобальные знания пользователя, общие для всех проектов: инсайты с `scope=global` (сценарий CRLF), приёмы, особенности окружения. В нём есть журнал `insights` (записи с `scope=global`) и личный Vault. Участникам общих решений Knowledge, Rules, Human и Vault владельца не видны. **[решение исполнителя]**

### 7.2. Встроенные журналы решения
При регистрации решения создаются `Changelog`, `Releases` и `Insights`; Vault журналом решения не является: он лежит в базе пользователя (§7.6). В дереве они выглядят как закреплённые виртуальные заметки. Их представление генерируется из таблицы `entries`. Под ними лежит обычное дерево заметок решения.

Журналы привязаны к **решению**, а не к сессии. Сессия хранится в каждой записи как атрибут. **[решение исполнителя]**: в наброске написано «для каждой сессии», но тогда память раздробилась бы.

### 7.3. Changelog — история изменений проекта
- **Поля:** `title`, `body` (Markdown), `data: {kind: feat|fix|refactor|docs|research|ops|other, refs: {commits, files, notes, issues}}`, `area`; атрибуция и дата проставляются автоматически.
- **Хранение.** Журнал только дописывается. Правки записей сохраняются в `entry_revisions`.
- **Отличие от ревизий заметок** (`revisions`): ревизии — это изменения самой памяти, а changelog — изменения в проекте.

### 7.4. Releases — история релизов
- **Поля:** `data: {version, date, git_tag?}`, `body` — заметки к релизу.
- **Сравнение** `GET …/releases/{id}/compare?with=prev|<id>` возвращает три части:
  1. записи changelog между релизами, сгруппированные по `kind`;
  2. дифф заметок к релизам;
  3. список коммитов, если CLI передал его из `zam release --from-git`. Сервер к git не обращается.
- **Без релизов** журнал пуст, сравнение недоступно.

### 7.5. Insights — открытия, провалы, эксперименты

```jsonc
{
  "kind":   "gotcha" | "failure" | "discovery" | "decision" | "experiment" | "pattern",
  "scope":  "solution" | "global",               // global → пространство Knowledge
  "status": "active" | "revisit" | "superseded" | "retracted",
  "certainty": "axiom" | "theorem" | "hypothesis",   // эпистемический статус; по умолчанию hypothesis у агента, без статуса у человека
  "title":  "Bash-скрипты должны иметь LF",
  "body":   "markdown: контекст, причина, как правильно, как проверить",
  "data": {
    "experiment": {"hypothesis": "…", "method": "…",
                   "result": "confirmed" | "refuted" | "inconclusive",
                   "metrics": {}, "revisit_if": "условие пересмотра"},
    "evidence": {"checked": "что проверено", "method": "как проверено", "result": "результат"}   // обязателен для theorem (§7.5)
  },
  "triggers": [{"type": "file_glob", "pattern": "**/*.sh", "tools": ["Write","Edit"]},
               {"type": "error_regex", "pattern": "\\^M|bad interpreter"}],
  "tags": ["bash", "line-endings"],
  "links": [{"type": "relates_to", "target": "node:<id>"}]
}
```

- **Создание:** `POST /spaces/{space}/entries` с `kind: "insight"`; вид инсайта — `data.kind`. `scope: global` пишет в Knowledge пользователя запроса (пространство пути при этом проверяется на чтение: отказ или отзыв доступа к решению — 403); без `scope` действует пространство пути — решение или Knowledge. Rules и Human — 422, если запись туда разрешена правами; иначе 403/404 по правилам доступа (§7.1). Содержимое insight в статусе `superseded` или `retracted` (заголовок, тело, `data`, теги, область, триггеры) не правится — 409: история только дописывается, для исправления создаётся новая запись **[решение контроллера]**.
- **Дедупликация при записи.**
  - Признак дубля: dense-косинус ≥ `insights.dedup_threshold` (0,90) с действующими (`active`, `revisit`) инсайтами той же области того же пространства или совпадение нормализованного заголовка (нижний регистр, всё кроме букв и цифр — пробел).
  - Векторная проверка: `embed_query(title + "\n" + body)` (усечение по модели) → ближайшие точки insight пространства без `superseded`/`retracted`; кандидаты перепроверяются по SQLite.
  - Сервер отвечает `409 /problems/possible-duplicate` с `candidates` (до 5: `id`, `title`, `status`, `certainty`, `reason: title | vector`, `score`) и `dedup: "full" | "degraded"`. Клиент выбирает: дописать к существующему (`PATCH {append_body}`), заменить его (`supersedes_id`) или записать всё равно (`force`).
  - Если модель недоступна, проверка идёт только по заголовку, а в ответе (и в успешном) `dedup: "degraded"`; при `force`, `supersedes_id` и повторе по `Idempotency-Key` — `dedup: "skipped"` **[решение исполнителя]**.
- **Замещение** (`POST /entries/{id}/supersede` или `supersedes_id` при создании). Старая запись получает `superseded` и `superseded_by_id`, новая — `supersedes_id`; всё одной транзакцией. Ничего не удаляется. Уже `superseded` или `retracted` — 409.
- **Отзыв** (`POST /entries/{id}/retract {reason}`, `retracted`) — отдельная операция с обязательной причиной (пустая — 422). Отзыв `superseded` разрешён: замещённый вывод тоже может оказаться ошибочным, а отзыв ничего не удаляет **[решение исполнителя]**.
- **`revisit`** — «пересмотреть при новых идеях». Такие записи показываются отдельным списком в дайджесте старта сессии.
- **Переходы статуса правкой** (`PATCH {status}`) — только `active ↔ revisit`; `superseded`/`retracted` правкой не ставятся, и из них статус не возвращается — 422 **[решение исполнителя]**.
- **Триггеры** (§10.3) задаются при создании и замещении или `PATCH {triggers}` (набор заменяется целиком): `file_glob` (`globset`), `command_regex` и `error_regex` (`regex` без обратных ссылок и lookaround, до 1 МиБ), `keyword` (1–200 символов); шаблон до 1000 символов, `tools` до 16, триггеров до 32 на запись. Ошибка — 422 `triggers[i]: …`. Действующие триггеры (`active`, `revisit`) отдаёт `GET /triggers?solution=` с `ETag` (поведение при недоступном решении — §10.3).
- **Ревизия при правке.** `PATCH`/`DELETE /entries/{id}` (в том числе смена `certainty` и триггеров) требуют `If-Match: <rev>` — §11.3.
- **Оценка полезности.** `POST /entries/{id}/feedback {value: useful|useless}` и счётчики `usage: {shown, useful, useless}` в `GET /entries/{id}` — §10.5.
- **Выдача.** Поиск по умолчанию возвращает `active` и `revisit`. Флаг `include_history` добавляет остальные статусы.
- **Перед исследованием** агент по инструкции (§14.2) проверяет `experiment` и `failure` по теме.

#### Эпистемический статус (`certainty`) **[решение владельца 2026-10-21; права — решение владельца 2026-10-26]**
`status` описывает жизненный цикл insight, `certainty` — насколько записи можно доверять. Поле есть у insight и у заметок (во frontmatter: `certainty:` и `evidence:`).
- **`axiom`** — установлено человеком: в WebUI или агентом по прямому указанию пользователя; опора для остальных выводов. **`theorem`** — проверено, есть доказательство: `data.evidence {checked, method, result}`, все три поля непустые. **`hypothesis`** — предположение или единичное наблюдение без проверки; значение по умолчанию для записей агента. Insight человека по умолчанию создаётся **без статуса**: в форме WebUI переключатель `certainty` по умолчанию пустой, аксиому человек ставит явно — **решение владельца 2026-10-26** (в M3 было `axiom` по умолчанию).
- **Кто автор.** Человек — сессия WebUI администратора или пользователя (§11.4, §15.1). Любой токен — агент: токенов с правами человека нет (флаг `tokens.human` M3 упразднён — **решение владельца 2026-10-26**). `system` — служебные операции сервера (миграции, импорт, восстановление).
- **Аксиомы и агент** — **решение владельца 2026-10-26** (отменяет инвариант M3 «агент не создаёт и не меняет `axiom`»):
  - по прямому указанию пользователя агент ставит, правит и снимает `axiom`;
  - по собственному выводу — нет: если агент не согласен с аксиомой, он создаёт рядом `hypothesis` или `theorem` с возражением (связь с аксиомой) и сообщает пользователю;
  - сервер `axiom` агента не блокирует, обязательного поля происхождения нет — правило «на совести агента» и закреплено в блоке инструкции (§14.2).
- **Права** — **решение владельца 2026-10-26**:

  | Действие | Агент (токен) | Человек (сессия WebUI) | `system` |
  |---|---|---|---|
  | создать без статуса / `hypothesis` / `axiom` | да | да | да |
  | создать `theorem` | только с `evidence` | да | да |
  | любой переход статуса (в том числе `→ axiom`, `axiom →`, снятие статуса) | с `reason`; `→ theorem` — ещё и с `evidence` | `reason` необязателен | без проверок |
  | правка, supersede, retract, delete, move, триггеры, вложение у `axiom` | да | да | да |
  | связь от `axiom` (§8.5) | да | да | да |

  Нехватка `evidence` или `reason` — 422 (`/problems/certainty`, поле `code`: `evidence-required` | `reason-required`); 403 по правилам `certainty` больше нет (коды M3 `axiom-requires-human` и `invalid-transition` упразднены).
- **Причина смены статуса.** Агенту `reason` обязателен при любой смене `certainty`, в том числе при `axiom` по указанию пользователя; человеку в WebUI — необязателен (поле есть, его можно оставить пустым) — **решение владельца 2026-10-26**.
- **Служебные операции** (`system`: миграции, импорт, восстановление) переносят статусы как есть и сами их не выставляют: импорт и восстановление сохраняют `certainty` с историей, миграции его не меняют, автоматического повышения нет — **решение владельца 2026-10-26**. Опция понижения чужих аксиом при импорте не из своего бэкапа — возможно, M7.
- **Где проверяется** **[решение исполнителя]**: в транзакции хранилища каждой операции, меняющей запись или заметку, по текущему состоянию цели — создание, правка (PUT, PATCH, `revert`), смена `certainty`, supersede, retract. Конфликт ревизии (`If-Match`/`base_rev`, 409; у записей журналов без `If-Match` — 428, §11.3) проверяется раньше прав. `theorem` агента требует полного доказательства и в итоговом состоянии любой правки (свежесть не проверяется). Ключ `certainty`/`evidence` в нераспознаваемом написании (в кавычках, с заглавными) статус не задаёт, ответ записи несёт `warnings: ["certainty_not_recognized"]`. Дозаполнение `nodes.certainty` при обновлении базы до M3 (живые и удалённые заметки) оставило `axiom` только заметкам, текущая ревизия которых записана человеком, иначе — `hypothesis`. У заметки без статуса установка `certainty:` — переход (агенту — с причиной, для `theorem` — с `evidence:`). Доказательство заметки — непустой `evidence:` (свободный текст).
- **История.** Каждая смена `certainty` — новая ревизия с `reason` (у человека причина может быть пустой); у заметок причина — сообщение ревизии (агенту обязательно).
- **Пример.** Агент прочитал статью, применил метод, метод не сработал: записывает `hypothesis` «метод X нерабочий». Перепроверка либо подтверждает вывод (`→ theorem` с `evidence`), либо выясняется, что параметры были неверны: запись замещается новой (`supersede`) или отзывается с причиной (`retract`). Устаревшее не удаляется и не выдаётся как действующее.
- **Поиск.** Статус виден в карточках и элементах выдачи, `filters.certainty` ограничивает выдачу, а бусты `axiom > theorem > hypothesis` поднимают надёжное выше предположения при равной релевантности (§9.2).

### 7.6. Vault — креды, токены, ссылки
Агент записывает секреты и сам ими пользуется. Администратор видит всё.

- **Поля:**
  - открытые: `title` (имя), `data: {type: password|token|ssh_key|connection_string|url|repo|note, username?, url?, description?}`;
  - шифрованное: `secret` (XChaCha20-Poly1305).
- **Ключи.** Мастер-ключ сервера берётся из файла `data_dir/master.key` (создаётся при первом запуске, права 0600) или из `ZAM_MASTER_KEY`. На каждого пользователя есть свой ключ данных, зашифрованный мастер-ключом. Бэкап без мастер-ключа не раскрывает секреты. Ключ резервируется отдельно — об этом предупреждают документация и WebUI. По умолчанию ключ лежит в `data_dir`, поэтому бэкап каталога данных целиком вместе с `master.key` раскрывает Vault: документация поставки рекомендует держать ключ вне `data_dir` (`[vault] master_key_file` или `ZAM_MASTER_KEY`) либо исключать `master.key` из бэкапа.
- **Формат** **[решение исполнителя, задача 12 M3]**: блоб `0x01 ‖ nonce(24) ‖ ciphertext‖tag`, AAD значения — `zam-vault-v1 ‖ user_id ‖ item_id ‖ rev` (id — 26 символов, `rev` — 8 байт big-endian), ключ пользователя обёрнут с AAD `zam-ukey-v1 ‖ user_id`, `vault.key_check` — шифротекст `zam-key-check`. Каждая ревизия — свой шифротекст (правка без нового значения перешифровывает прежнее). Файл ключа — `[vault] master_key_file` (по умолчанию `data_dir/master.key`, base64), `ZAM_MASTER_KEY` важнее файла; файл создаётся атомарно и без перезаписи (`master.key.tmp` → жёсткая ссылка, fsync каталога на Linux) до записи `vault.key_check`; права — 0600 на Linux, защищённый DACL (владелец, SYSTEM, администраторы) на Windows. Поведение при блокировке — ниже («Проверка мастер-ключа»). Значение — до 64 КиБ; прежние ревизии раскрывает только администратор (`GET /vault/{id}/revisions?reveal=1&rev=N`). В CLI адрес ресурса — `--link` (`--url` — адрес сервера).
- **Vault и общие решения.** Vault каждого участника лежит в его базе пользователя и привязан к `agent_solution_id` (`vault_items.scope='solution'`); он не разделяется никогда: ни владелец, ни другие участники не видят записей друг друга, администратор видит всё. Записи без привязки (`scope='knowledge'`) — личный Vault пользователя, глобальный для всех проектов.
- **Проверка мастер-ключа.** Первое же шифрование записывает в `settings` проверочный шифротекст (`vault.key_check`). Если ключ не подходит или файла ключа нет при существующих ключах пользователей, Vault блокируется (причина — в ответе и в журнале сервера одной строкой WARN), остальной сервер работает, а новый ключ молча не создаётся: иначе потеряются прежние секреты.
- **Заблокированный Vault** — **решение владельца 2026-10-26** (в M3 — 503 на все эндпоинты):
  - список и метаданные отвечают 200 с полем верхнего уровня `locked: true` и `reason`: `GET /spaces/{space}/vault`, `GET /vault/{id}` без `reveal`, `GET /vault/{id}/revisions`; метаданные — то, что хранится открыто (имя, вид, теги, привязка, даты), значений и шифротекста в ответе нет; при работающем Vault — `locked: false`;
  - значения (`?reveal=1`), создание, правка и удаление — `503 /problems/vault-locked`;
  - WebUI показывает список, кнопка «Показать» неактивна, баннер `vault-locked` прежний; `zam vault list` печатает список и строку «Vault заблокирован: <причина>».
- **Доступ агента.** С токеном пользователя агент читает и пишет vault своего пользователя:
  - `GET …/vault` — список записей и поиск по открытым полям (`title`, `url`, `description`), без значений;
  - `GET /vault/{id}?reveal=1` или `memory_vault` с `action: get` (§13.1) — значение.
- **Индексация.** Значения нигде не индексируются: ни в FTS, ни в Qdrant. Поиск по vault идёт только по открытым полям через отдельный эндпоинт.
- **Аудит.** Каждое раскрытие записывается: токен, сессия, машина, время.
- **WebUI.** Значения скрыты маской, раскрытие по клику.
- **Сканер секретов.** Перед индексацией любой заметки или записи сервер ищет похожее на секреты: известные префиксы ключей, высокоэнтропийные строки, `password=` и т. п. В индексе найденное заменяется на `‹secret›` — в тексте и префиксе чанков, L0, тегах payload точек Qdrant и во входе эмбеддинга папки (имя, путь, свёртка L0 детей) **[решение исполнителя, M3]**. Ответ на запись содержит предупреждение `secrets_detected` с предложением перенести значение в vault. Исходный текст заметки не меняется.

## 8. Индексация

### 8.1. Конвейер

```
запись узла / записи журнала
  └─ синхронно, одна транзакция SQLite:
       ревизия + узел + разбор (comrak) → секции → чанки + context_prefix → chunks + FTS5
       + auto-L0/L1 + рёбра из ссылок + задание index_jobs
вложение
  └─ синхронно: blob на диск + attachments; асинхронно: извлечение текста → чанки(level=attachment) → FTS5
воркеры эмбеддинга (асинхронно, низкий приоритет):
  ├─ чанки без вектора: embeddings по (text_hash, model_id) → при промахе — инференс батчами
  ├─ upsert/delete в Qdrant
  ├─ свёртка L0 вверх по дереву (дебаунс 2 с)
  ├─ answer_cache: stale «new_sources» по близости новых чанков (§9.4; изменение источника — в транзакции записи)
  └─ index_state = 'indexed'
```

- **Синхронная часть.** Чанкинг и FTS выполняются в транзакции записи. Сразу после записи заметка находится по словам.
- **Статус индексации.** Ответ записи содержит `index_state`. Ответ поиска содержит `pending_count` — сколько записей в этой области ещё ждут векторизации.
- **Хранилище эмбеддингов.** Таблица `embeddings` в SQLite: одинаковые тексты не прогоняются через модель повторно, а `reindex` пересобирает Qdrant без инференса. Модель снова прогоняется только при смене `model_id`. Ключ кэша — blake3 эмбеддируемой строки (префикс + текст, §8.2 п. 6) — хранится в `chunks.embed_key`; строки, на которые не ссылается ни один чанк, удаляет сборка мусора (после reindex базы и раз в час в простое). Служебные эмбеддинги (предложения L0, L0 папки) принадлежат своему узлу (`embeddings.owner`).
- **Reindex** (`POST /admin/reindex`, `zam-server reindex`): без `full` — точки области удаляются и пишутся из `embeddings` пачками по 256, заметки без эмбеддинга получают задания; с `full` — перечанковка и задания. Выполняет воркер последовательно с заданиями; коллекция другой модели пересоздаётся. Прерванный reindex повторяется при следующем запуске. База пользователя, повреждённая навсегда или не открывшаяся 5 раз при пересборке после стирания хранилища Qdrant, исключается (аудит `index.rebuild_skipped`, видна в `/index/status`); остальные пересобираются. Исключение хранится в `system.db` (переживает перезапуск) и снимается, когда база снова открылась и ей поставлен reindex. Обход всех баз (статус администратора, reindex) неоткрывающиеся базы пропускает и называет.
- **Приоритеты.** Эмбеддинг запросов идёт в отдельной ONNX-сессии с зарезервированными потоками (на CPU по умолчанию 2). Индексация уступает между батчами: батч инференса — не больше 2048 токенов, и перед каждым батчем индексация ждёт, пока выполняются эмбеддинги запросов (не дольше 100 мс) — на GPU сессии делят одно устройство, и батч 8192 токенов задерживал эмбеддинг запроса до 74 мс (p95) **[решение исполнителя, задача 15 M2]**. Цели §17 для поиска должны выполняться при полной очереди индексации.
- **Надёжность.** Задания переживают перезапуск. Повторы идут с экспоненциальной задержкой. После 5 неудач задание получает статус `failed` и становится видно в `/index/status` и в WebUI.

### 8.2. Чанкинг Markdown
1. **Frontmatter** (YAML) уходит в метаданные: `tags`, `description`, `index: false`, `l0`, `relations`.
2. **Секции** — по H1–H3. H4–H6 остаются внутри своей секции, но входят в путь заголовков листа (`H1 > H2 > H3 > H4`) и тем самым в `context_prefix`.
3. **Блоки** кода, таблицы, списки и callout не разрываются. Блок длиннее 800 токенов режется по строкам или элементам, и у каждой части повторяется заголовок блока.
4. **Листовые чанки** — 300–500 токенов, максимум 800. Перекрытие — 1–2 предложения, только внутри секции. Лист не кончается заголовком H4–H6 (заголовок уходит в следующий лист вместе со своим содержимым) и не отрывает вводную фразу на «:» от следующего блока (код, список, таблица).
5. **Короткие секции** (меньше 100 токенов) склеиваются с соседними.
6. **`context_prefix`.** К каждому чанку добавляется строка `[<space>/<path>] <заголовок заметки> > <путь заголовков> | теги`. Она участвует в эмбеддинге и FTS, но клиенту не возвращается. Это детерминированный аналог Contextual Retrieval.
7. **Записи журналов** — один документ на запись. Длинные режутся по тем же правилам.
8. **Вложения:**
   - PDF — текстовый слой постранично;
   - DOCX — абзацы с заголовками;
   - XLSX/XLS/ODS/CSV — по листам, блоками строк с шапкой;
   - PPTX — текст слайдов;
   - TXT, MD, исходный код — как есть.

   Чанки вложений получают `level=attachment` и `locator` (страница, лист и диапазон, слайд). Изображения, видео и аудио индексируются по имени файла и подписи.

Пороги задаются в конфигурации (`[index] chunk_target_min|chunk_target_max|chunk_hard_max|chunk_merge_below|chunk_overlap_sentences|chunk_boundary_lambda|chunk_cohesion|chunk_prefix_l0|chunk_heading_path_h4`), значения по умолчанию подбираются на eval (§18.2): на M2 сетка подтвердила 300–500/800 и перекрытие в одно предложение. Ключи `chunk_boundary_lambda` (сила границ при выборе разреза, 0 — жадная упаковка M2), `chunk_cohesion` (лексическая связность в длинных абзацах) и `chunk_prefix_l0` (L0 заметки в `context_prefix`) — эксперименты, их умолчания выбраны по eval M3 (`eval/grid-chunking.toml`, задача 17): `chunk_boundary_lambda = 0` — жадная упаковка M2 со структурными исправлениями M3, путь динамического программирования остаётся в коде и включается параметром λ > 0 (**решение владельца 2026-10-26**: собственный эффект λ = 0,5 поверх исправлений от нуля не отличим — Δ nDCG@10 +0,003 [−0,003…+0,010]; в M3 умолчание было 0,5); `chunk_cohesion` и `chunk_prefix_l0` выключены (`chunk_cohesion` действует только при λ > 0; если он включён при λ = 0, сервер пишет предупреждение при старте), размер листа 300–500/800 сохранён; `chunk_heading_path_h4` (по умолчанию включён) — переключатель H4–H6 в пути для сетки.

Сила границы перед единицей упаковки: перед H4–H6 и `---` — 4, между блоками (абзацы, код, таблица, список) — 2, между предложениями и элементами разрезанного блока — 1, внутри строки или слова — 0; после заголовка и после абзаца на «:» разрез запрещён, пока следующая единица умещается в `chunk_hard_max` (вводная фраза, которая вместе с блоком не помещается, дробится по предложениям — к блоку уходит хотя бы последнее). При λ > 0 разрез выбирает динамическое программирование по кандидатам группы: минимум Σ((len − цель)/цель)² + λ·Σ(4 − сила) при жёстком `chunk_hard_max`; лист короче `chunk_target_min` (кроме хвоста) не запрещён, а штрафуется — мягче запрета, но сильнее любой силы границы (жёсткое ограничение снизу бывает недостижимо), лист из нескольких единиц длиннее `chunk_target_max` тоже штрафуется, как в жадной упаковке **[решение исполнителя, M3]**. Embedding-нарезка и late chunking не применяются (исследование `docs/research/2026-10-21-chunking-semantic.md` §4).

Отпечаток нарезки (версия алгоритма, пороги и флаги `[index]`, идентификатор токенизатора — `sha256` содержимого `tokenizer.json`) хранится в `meta` базы пользователя отдельно для заметок (с флагом L0 в префиксе) и для записей журналов (без него); часть базы, нарезанная другим отпечатком (в том числе до M3), при первом открытии разово перенарезается в фоне — задания индексации получают только заметки и записи, чьи чанки изменились, а векторы пересчитываются только у листов, текст или префикс которых изменился (кэш `embeddings` по `embed_key`) **[решение исполнителя, M3]**. Пока счётчик токенов — оценка (модели нет), токенизатор в отпечатке не сравнивается. `reindex --full` по-прежнему перенарезает всё явно.

**Уведомление о перенарезке** — **решение владельца 2026-10-26**: автоматическая фоновая перенарезка при любой смене настроек нарезки остаётся, и о ней сообщается:
- рядом с отпечатком в `meta` хранится JSON параметров нарезки (`meta.chunker_params`, `meta.chunker_entries_params`); при расхождении определяется причина: `params` (изменились ключи `[index]`), `algorithm`, `tokenizer` или `unknown` (база M3 без сохранённых параметров); у `unknown` изменившиеся ключи восстанавливаются разбором отпечатка M3, если он разбирается (иначе список пуст) — при обновлении с M3 видно `chunk_boundary_lambda` **[решение исполнителя, задача 4 M4]**; база M1 после миграции v4 — `algorithm`, чанки по оценке при точном счётчике — `tokenizer`; число записей — живые заметки и записи журналов перенарезаемых частей;
- при открытии базы — одна строка WARN в журнале сервера: `перенарезка базы <user>: изменились <ключи> — <N> записей` (без текста заметок);
- `GET /index/status` отдаёт по каждой базе `rechunk: {reason, changed, total, done} | null` — в списке `dbs: [{user_id, rechunk}]` (администратору — все базы или база `X-Zam-User`, токену — своя; `rechunk` — пока идёт фоновая перенарезка, начатая при открытии базы этим процессом) **[решение исполнителя, задача 4 M4]**;
- WebUI показывает баннер «Идёт перенарезка: изменились <ключи>, N из M» в индикаторе индекса — на странице «Индекс» (`#/admin/index`), по баннеру на базу с именем пользователя.

Смена умолчания `chunk_boundary_lambda` на 0 меняет отпечаток: при обновлении до `0.0.5-m4` базы разово перенарезаются в фоне (инференс — только для изменившихся листов).

Токены считает токенизатор модели (`tokenizer.json`), в том числе без ONNX Runtime. `chunk_hard_max` не больше окна модели (`max_tokens_passage`) минус 64 токена на `context_prefix` и спецтокены (bge-m3: 960); пороги больше уменьшаются с предупреждением в журнале **[решение исполнителя, M2]**. Без установленной модели токены оцениваются (символы / 3,5); база с такими чанками отмечается (`meta.chunked_approx`), и при первом её открытии с точным счётчиком все живые заметки перенарезаются в фоне с повторной индексацией **[решение исполнителя, M2]**.

### 8.3. Уровни L0/L1/L2 и иерархия
- **Заметка.** L0 — ручной `l0` из frontmatter. Если его нет, используется самое информативное предложение заметки: оно выбирается экстрактивно, по близости к центроиду эмбеддингов секций, и обрезается до 50 токенов. Пока векторов нет, берётся первый абзац. L1 — оглавление плюс ключевое предложение каждой секции, до 300 токенов.
- **Папка или пространство.** Свёртка L0 детей, до 50 строк. Если строк больше, они ранжируются по `usage` и свежести.
- **Сводки от агента.** При записи заметки агент может передать `l0` (одно предложение). Инструкция (§14.2) это рекомендует. Такая сводка сохраняется с `l0_source=agent`, и сервер не перезаписывает её автоматикой, пока не изменится содержимое. Если содержимое изменилось, а новая сводка не пришла, `l0` снова вычисляется автоматически.
- **Индексация уровней.** L0 и L1 заметок и секций индексируются как отдельные чанки (`level=note|section|folder`). Это позволяет широким запросам находить тему целиком. Точки папок (`folder`) пишутся в Qdrant с M2, поиск по ним (§9.2, канал `w_folder`) — с M3.
- **Чтение по уровню.** `GET /nodes/{id}?tier=L0|L1|L2` экономит контекст агента.

### 8.4. Модели (встроенные)

| Роль | По умолчанию | Примечание |
|---|---|---|
| Эмбеддинги | **bge-m3**, ONNX, int8 (CPU) / fp16 (GPU) | Один проход даёт dense и sparse, плюс ColBERT опционально. CLS-токен в ColBERT отбрасывается, sparse собирается max-pool по token-id без спецтокенов. Источники весов: CPU — `Xenova/bge-m3` `onnx/model_int8.onnx` (per-channel QInt8), GPU — `Xenova/bge-m3` `onnx/model_fp16.onnx`; `tokenizer.json` оттуда же; sparse-голова `sparse_linear.pt` — из оригинала `BAAI/bge-m3`. Пулинг и sparse считаются в Rust по `last_hidden_state`. Int8 сверяется с fp32 `BAAI/bge-m3` гейтом качества `cargo xtask eval --quality-gate` (исследование 05, §3.3; §18.2): по поиску ухудшения int8 относительно fp32 не обнаружено (95 % интервал парного бутстрепа разности recall@5 и nDCG@10 включает ноль), а порог косинуса dense 0,99 не прошёл ни один проверенный динамический int8 (Xenova — 0,978, собственный per-channel — 0,984); int8 только весов проходит, но втрое медленнее. Не проверялись: mixed precision (`nodes_to_exclude`), статическое QDQ с калибровкой, `gpahal/bge-m3-onnx-int8`. Оставлен Xenova int8 — **решение владельца, 2026-10-20** (с M3 критерий гейта — по поисковым метрикам, §18.2: нижняя граница 95 % интервала парного бутстрепа Δ nDCG@10 и Δ recall@5 (int8 − fp32) ≥ −0,01; косинус dense и Спирмен sparse — справочно, решение владельца 2026-10-21; итог M3 на наборе M3 — «не пройден»: в первом прогоне по нижней границе Δ recall@5 (−0,018), в итоговом на поставляемых умолчаниях — по нижней границе Δ nDCG@10 (−0,011), а повторные прогоны int8 того же кода — «пройден»: вердикт зависит от шума индекса; **решение владельца 2026-10-26**: int8 Xenova на CPU остаётся, гейт пока информационный, с M4 прогоны гейта ищут точным поиском Qdrant `exact = true`, порог −0,01 прежний, §18.2). Векторы int8 и fp16 — разные `model_id` |
| Реранкер (опционально, по умолчанию выключен) | CPU: `jina-reranker-v2-base-multilingual` (278M, int8) — **CC-BY-NC-4.0, не входит в `zam-models`, загрузка только с согласием** (`--accept-nc-license`); граф квантует активации динамически, поэтому пары считаются по одной, параллельно в `ml.rerank_sessions` сессиях (по умолчанию 0 — авто: до 2, у каждой своя копия весов ~0,3 ГБ); GPU: `bge-reranker-v2-m3` (Apache-2.0, ONNX-экспорт `onnx-community`, fp16), пары — одним батчем | Основной реранк делает агент (§9.3). Модель нужна для поиска в WebUI и для агентов, которые просят `rerank=on`. Jina оставлена решением владельца; её лицензия разрешает только некоммерческое использование. Финальный выбор — по eval |

- **Исполнение.** `ml.device = auto|cpu|cuda`. При `auto` сервер пробует CUDA (NVIDIA), если она недоступна — CPU. Выбор и причина пишутся в лог и в `/index/status`. Других GPU-исполнителей (DirectML и т. п.) нет — решение владельца. Вариант модели для CPU (int8) на GPU не запускается, вариант для GPU (fp16) — на CPU: если CUDA недоступна, а int8 не установлена (или fp16 задана явно при `ml.device = cpu`), сервер работает в режиме FTS-only с причиной `gpu_model_on_cpu` и подсказкой `zam-server models fetch --device cpu` — векторы CPU и CUDA под одним `model_id` не смешиваются **[решение исполнителя, M2]**.
- **Поставка.** Сборки `cpu` и `gpu`. ONNX Runtime подгружается динамически (`load-dynamic`) из библиотеки, которая лежит рядом с бинарником. Поэтому GPU-сборка работает и без GPU, а без библиотеки ORT сервер всё равно стартует в режиме FTS-only. Библиотеки NVIDIA (CUDA 13, cuDNN 9) в GPU-сборку не входят: их ставит `zam-server cuda fetch` или архив `zam-cuda-*` (§16.3). Для CUDA нужен драйвер с поддержкой CUDA 13 (ветка R580+); в документации поставки это указано.
- **Загрузка моделей.** `zam-server models fetch` скачивает модели с Hugging Face и проверяет sha256. Модели, ревизии (коммит Hugging Face) и sha256 каждого файла закреплены в `deploy/models.toml`; при несовпадении загрузка падает. Есть и архив поставки `-models`, где модели уже внутри, — для машин без интернета. Без моделей сервер работает в режиме FTS-only и сообщает об этом.
- **Память.** Модель эмбеддингов загружается при старте сервера (до первого открытия баз: чанкер считает её токенизатором), реранкер — лениво, при первом запросе с `rerank=on`. Выгрузка по простою (`ml.unload_after`, по умолчанию выключена) на M2 не реализована: значение принимается, сервер пишет предупреждение и держит модели в памяти.

### 8.5. Граф связей
Отдельная графовая СУБД не нужна: на нашем масштабе хватает таблицы `edges` и рекурсивных CTE в SQLite. Трейт `GraphStore` оставляет возможность заменить хранилище позже. Готовые встраиваемые графовые движки в Rust-экосистеме нестабильны: Kùzu, например, свёрнут. **[решение исполнителя]**

- **Типы связей:** `links_to` (wiki-ссылка или Markdown-ссылка), `relates_to`, `depends_on`, `part_of`, `caused_by`, `fixes`, `supersedes`, `derived_from` (запись создана по заметке или вложению), `mentions`.
- **Откуда берутся связи:**
  - `[[Заметка]]` и `[[Заметка#Секция]]` в тексте — `origin=wikilink`; Markdown-ссылка `[текст](путь)` на относительный путь (от папки заметки; `/…` — от корня пространства; суффикс `.md` необязателен) — тоже `links_to` с `origin=wikilink`; внешние URL, якоря, вложения и картинки рёбер не дают **[решение исполнителя]**;
  - `relations:` во frontmatter — список строк `"<тип>: <цель>"` (flow или block), цель — `[[Имя]]` или путь в пространстве, например `relations: ["depends_on: [[Сборка]]", "fixes: notes/gotchas/crlf.md"]`; неизвестный тип пропускается с предупреждением в ответе записи **[решение исполнителя]**;
  - явные связи из API и инструмента `memory_link`, а также `links` insight (§7.5) — `origin=explicit`;
  - системные связи: `supersedes` (новая запись → старая, при замещении), связь «инсайт ↔ решение» — `origin=system`.
- **Жизненный цикл** **[решение исполнителя]**: рёбра `wikilink`/`frontmatter` выводятся из текущей ревизии и пересобираются при каждой записи узла (создание, правка, PATCH, откат, восстановление) в той же транзакции; `explicit` удаляются мягко и только они (`DELETE /edges/{id}`; выведенные и системные — 422). Неразрешённая ссылка хранится с ключом `dst_raw` (`[[Имя]]` или путь) и разрешается, когда цель появится: создание, переименование, перенос, удаление и восстановление узла перепроверяют ссылки пространства по старым и новым имени и пути. Разрешение — как в рендере (одна функция): путь, затем имя — первая живая заметка по `path`, только в пространстве источника. Удалённый источник прячет свои рёбра и обратные ссылки, восстановление возвращает их; ссылка на удалённую заметку становится неразрешённой. Базы M2 дозаполняются при открытии фоновой задачей.
- **Связи и `certainty`** — **решение владельца 2026-10-26** (ruling R10 M3 «явное ребро от `axiom` — только человек» снят): агент свободно добавляет связи от `axiom` и к `axiom` без указания пользователя — связь не меняет текст аксиомы; удаление явных связей — по общим правилам (`DELETE /edges/{id}`) **[решение исполнителя]**; выведенные рёбра следуют за текстом, запись которого уже проверена матрицей §7.5.
- **Где используются:**
  - в поиске: `expand=graph` добавляет соседей первых `top_k` элементов на 1 шаг в обе стороны в пределах области цели: до `ceil(top_k / 2)` новых элементов с баллом `родитель × search.graph_weight` (0,5); сначала действующие инсайты (`active`/`revisit`, по `certainty`: `axiom`, `theorem`, `hypothesis`), затем заметки; `superseded`/`retracted` — только с `include_history`; у элемента `sources: ["graph"]` и `via: {type, from}`;
  - в API: `GET /graph?node=&depth=` → `{nodes, edges, truncated}`; подграф (и соседи для `expand=graph`) — не больше 500 узлов (ближние к началу обхода — первыми) и 2000 рёбер, при обрезке `truncated: true` **[решение исполнителя, M3]**;
  - в WebUI: локальный граф узла и обратные ссылки (backlinks);
  - `doctor` находит битые ссылки.
- **Границы базы.** Рёбра существуют только внутри одной базы: цель в другой базе (личная память участника и решение в базе владельца) отклоняется (422) **[решение исполнителя]**; межбазовые связи не делаются — нужное проекту знание кладут в проект (**решение владельца 2026-10-26**). Граф, обратные ссылки и `expand=graph` для участника ограничены пространством решения: рёбра в другие пространства владельца ему не видны.
- **Связи от агента.** Связи и сущности предлагает агент через `memory_link`. В режиме подтверждения они попадают в черновики (§10.6).

## 9. Поиск, выжимка, кэш

### 9.1. Запрос

```jsonc
POST /api/v1/search
{
  "query": "как правильно писать bash-скрипты на windows",
  "scope": {"solution": "<guid>", "include_knowledge": true, "include_rules": true,
            "all_solutions": false, "path_prefix": null, "area": null},
  "filters": {"kinds": ["note","insight","changelog","release","attachment"], "insight_kinds": [],
              "tags": [], "status": ["active","revisit"], "since": null},
  "mode": "brief" | "chunks" | "notes",       // по умолчанию brief (§9.3)
  "top_k": 10, "budget_tokens": 800,
  "rerank": "off" | "on",                     // серверный реранк, по умолчанию off
  "expand": "none" | "section" | "neighbors" | "graph",
  "include_history": false, "no_cache": false, // no_cache: пропустить шаг 0 — кэш выжимок (§9.3)
  "skip_seen": true,                           // не повторять текст, уже выданный этой сессии
  "session_id": "…", "format": "md" | "json"   // session_id — из тела или X-Zam-Session; md — по умолчанию для агентов
}
```

Режимы:
- `brief` — компактные карточки кандидатов (§9.3, шаг 1). Основной режим для агентов.
- `chunks` — карточки вместе с текстом чанков в пределах бюджета. Для простых вопросов, когда хочется получить ответ за один вызов.
- `notes` — список узлов с L0, без текста.

Область и заголовки:
- `scope.solution` — `agent_solution_id`; решение входит в поиск только для владельца и одобренных участников, иначе оно исключается, а в `warnings` идёт `solution access pending|rejected|revoked` (§11.6). `all_solutions` — все доступные решения. Knowledge и Rules берутся из личной базы.
- `X-Zam-Area` — текущая область для буста (§11.2, §9.2 п. 4) и область по умолчанию для новых записей. `scope.area` — строгий фильтр: только узлы и записи этой области (FTS, Qdrant и проверка векторных хитов; пустая — без фильтра).
- `filters.certainty` — подмножество `axiom | theorem | hypothesis`; по умолчанию без ограничения.
- `filters.kinds` по умолчанию — `note, insight, changelog, release` (вложения `attachment` — с M5), без `folder`; карточки папок (`folder`) выдаются только по явному `filters.kinds: ["folder"]` — иначе папки работают как канал подъёма (§9.2).

### 9.2. Алгоритм
Генеративная модель на этом пути не используется.

1. **Фильтр области** — общий для всех каналов: дизъюнкция областей «владелец базы + пространства» (личные пространства и доступные общие решения, §6.4, §11.6), префикс пути, область, статус, надёжность.
2. **Кандидаты:**
   - (a) Qdrant: `dense` top-50 и `sparse` top-50 по `chunk|attachment`, плюс `dense` top-10 по `note|section|folder` (точки папок дают канал `w_folder`); слияние RRF внутри Qdrant;
   - (b) FTS5: `bm25` top-50 (unicode61) и `trigram` top-20, если в запросе есть код или идентификаторы; запрос идёт по каждой базе владельца отдельно в пределах её пространств, результаты баз сливаются по `raw_score` каждого канала.
3. **Слияние** (a) и (b) — weighted RRF (k=60) в приложении. Веса задаются в конфигурации; у bm25, найденного только ослабленным запросом (любое слово), — свой вес `w_fts_relaxed` (0,25 по eval): случайные совпадения по одному слову не должны вытеснять векторные находки.
4. **Поправки:**
   - буст для `gotcha` и `failure` (`search.boost_gotcha`, `search.boost_failure`, по умолчанию 1,05 — по сетке eval M3 буст вида ниже буста `theorem`: с 1,15 и 1,10 гипотеза вида `gotcha` обходила противоречащую ей `theorem`) и для текущей области из `X-Zam-Area` (`search.boost_area`, 1,10; набором eval не проверяется) — множители слитого балла (сразу после слияния, бусты перемножаются, порядок — по полному баллу); если лучший балл после бустов и канала папок больше 1, все баллы выдачи делятся на него (порядок и отношения прежние, лучший — 1; без переполнения шкала прежняя) **[решение исполнителя, M3]**;
   - буст надёжности: `search.boost_axiom` (1,20) > `search.boost_theorem` (1,10) > `search.boost_hypothesis` (1,00), подтверждён сеткой eval M3; карточки и элементы выдачи показывают `certainty`;
   - канал точек папок: чанку узла, лежащего под путём найденной папки (того же пространства), прибавляется `w_folder / (k + место папки)` — один раз, по лучшей папке-предку. Папка не занимает место в выдаче, а поднимает листы своих потомков (иерархическое вспоминание); точки папок проверяются по SQLite (жива, не в корзине, не Human, в области цели). Значение `w_folder` выбрано сеткой eval M3 из `{0; 0,3; 0,5; 1,0}`: 0 (выдача как в M2) — 0,3–1,0 устойчиво хуже, потому что канал поднимает только узлы, и заметки обходят записи журналов (у них нет папки). Карточка папки (`filters.kinds ∋ folder`, не больше `search.max_folders` = 2): `f:<id> <пространство>/<путь>/  [score] · <N> детей` и L0 папки **[решение исполнителя, M3]**;
   - затухание по свежести с полупериодом 180 дней: множитель `0,5 + 0,5·2^(−возраст/полупериод)` — давняя заметка теряет не больше половины балла **[решение исполнителя, M2]**;
   - `superseded` и `retracted` исключаются, если история не запрошена.
5. **Серверный реранк** — только при `rerank=on`: 20 кандидатов по 256 токенов. Бусты п. 4 (вид, область, `certainty`) применяются и к баллу реранкера — **решение владельца 2026-10-26** (eval M3: без бустов `reliable_first` падал с 1,000 до 0,571): `score = rerank_score × boost_kind × boost_area × boost_certainty`, затем то же деление при переполнении, что в п. 4 (по баллам переставленных реранкером; хвост за `rerank_top` сохраняет балл слияния) **[решение исполнителя, задача 4 M4]**; затухание по свежести и канал папок к баллу реранкера не применяются; одна функция бустов на оба пути. В элементе ответа `rerank_score` — сырой балл реранкера, `score` — с бустами. Цель — `reliable_first` 1,000 при `rerank=on` без потери nDCG@10 (eval M4). В хуках не используется никогда. По умолчанию реранжирует агент (§9.3).
6. **Группировка.** Не больше 3 чанков с одного узла. Если сработала сводка уровня заметки, вместо неё берётся лучший листовой чанк.
7. **Расширение контекста (`expand`):**
   - `section` — подставить всю секцию;
   - `neighbors` — соседние чанки;
   - `graph` — по §8.5.
8. **Упаковка в `budget_tokens`.**
   - Каждый элемент: `node_id|entry_id`, `space`, `path`, `heading_path`, `locator`, `rev`, `chunk_ids`, `score`, `rerank_score` (при `rerank=on`), `updated_at`, `status`, `kind` (`cache` — выжимка шага 0, §9.3), `seen` (выдан этой сессии в той же ревизии, §9.3), `text`.
   - Весь ответ: `degraded`, `pending_count`, `warnings`, `timings` (`fts_ms`, `embed_ms`, `vector_ms`, `fuse_ms`, `rerank_ms`, `expand_ms`, `pending_ms`, `total_ms`). `warnings` — коды предупреждений: `reranker not installed`, `reranker failed`, `index rebuilding` (идёт reindex или пересборка индекса после потери хранилища Qdrant — векторная выдача может быть неполной) **[решение исполнителя, M2]**; `solution access pending|rejected|revoked` (§9.1) и `solution unavailable` — база владельца решения не открылась или не читается, решение исключено, ответ строится по остальным базам **[решение исполнителя, M3]**; `section unavailable` — для `expand=section` разбор заметки или поиск секции листа прерван сбоем, элемент отдан с текстом листа без секции (а не 500 на весь запрос) **[решение исполнителя, M3]**. Элемент из решения (своего или чужого) несёт `agent_solution_id`.

### 9.3. Выжимку делает агент: протокол с экономией токенов

Сервер ищет и хранит. Решает, что из найденного важно, сам агент: он знает свою задачу лучше любой модели на сервере. Протокол состоит из четырёх шагов. Каждый следующий шаг выполняется, только если на предыдущем не хватило данных.

```
 шаг 0  memory_search ─▶ есть актуальная выжимка в кэше?  ── да ──▶ готово (≈ 100–400 токенов)
                                   │ нет
 шаг 1                    карточки кандидатов (brief)            (≈ 30–50 токенов на карточку)
                                   │ агент выбирает нужные
 шаг 2  memory_read [id…] ─▶ только нужные секции/уровни         (L0/L1/секция, а не вся заметка)
                                   │ агент формирует выжимку
 шаг 3  memory_cache_put ─▶ выжимка + источники с ревизиями ─▶ доступна следующим запросам
        (опционально)  promote ─▶ выжимка становится заметкой или инсайтом
```

**Шаг 0 — кэш.** `memory_search` сначала ищет в кэше действующую выжимку для похожего запроса (§9.4). Если такая есть, первым элементом ответа идёт:

```
[cache] «Как деплоим parser-сервис» — выжимка 2026-10-12, 3 источника, все актуальны (id: c_…)
<текст выжимки>
```

Для типового вопроса этого достаточно, дальше идти не нужно. Подробности шага 0:
- `POST /search` без `no_cache` сначала вызывает поиск по кэшу; действующие выжимки (не больше 2) идут первыми элементами с `kind: "cache"`;
- у выжимки другой сессии в строке ещё автор, машина и дата;
- недействительная выжимка выдаётся строкой `[cache, stale: <изменившиеся источники>]` без текста — агент перечитывает только изменившееся и обновляет выжимку.

**Шаг 1 — карточки (`mode=brief`).** Ответ компактный и машиночитаемый, по одной строке на кандидата:

```
1. n:01J… Solutions/parser/deploy.md › Docker › Сборка  [0.82] rev7 · 2026-10-10 · ~340 tok
   Сборка образа идёт multi-stage; для arm64 нужен buildx…
2. i:01J… insight/gotcha «Bash-скрипты должны иметь LF»  [0.77] active · hypothesis · ~120 tok
3. a:01J… report.pdf p.4  [0.61] · ~500 tok   (seen)
```

- В карточке: тип и id, путь и секция, оценка, ревизия, дата, размер полного текста в токенах, 1–2 строки фрагмента. У записи журнала вместо пути и ревизии — вид (`insight/<data.kind>`, `changelog/<data.kind>`, `release`), заголовок, `status` и `certainty`; префикс id — `i:`, `c:`, `r:`.
- Если запись уже выдавалась этой сессии в той же ревизии, вместо фрагмента стоит пометка `(seen)`, в JSON — `seen: true` (`session_seen`, `skip_seen=true`). Сессия — `session_id` из тела или заголовка `X-Zam-Session`; при `mode=chunks` выданный текст записывается в `session_seen`. Уточнения **[решение исполнителя, задача 5 M4]**: `skip_seen` по умолчанию `true`; у элемента с `seen: true` в JSON нет `snippet` и `text` (место в `budget_tokens` освобождается для остальных), `tokens` — по-прежнему стоимость полного чтения; в `session_seen` пишется только текст, отданный целиком (усечённый бюджетом — нет); карточки папок не отмечаются; хранится большая из выданных ревизий цели.
- Агент сам ранжирует карточки по смыслу своей задачи. Серверный реранк для этого не нужен.

**Шаг 2 — точечное чтение.** `memory_read` (`POST /read`) принимает список id. Для каждого id можно указать:
- `tier=L0|L1|L2`;
- `section` — путь заголовков;
- `locator` — страница или лист (этап M5; до него — 422 `locator-unsupported`);
- `max_tokens` — обрезка с пометкой «…ещё N токенов»;
- `if_rev` — если ревизия не изменилась, вернётся `unchanged`, без текста.

Так агент читает ровно то, что нужно, и не перечитывает то, что уже есть в его контексте. Правила `POST /read`:
- `id` — `n:<id>`, `i:|c:|r:<id>` (запись журнала), голый id (узел или запись — по таблицам) или путь `<space>:/<path>`; не больше 20 элементов (`read.max_items`), иначе 422;
- `budget_tokens` — на весь ответ, по умолчанию 1500 (`read.budget_tokens`); элемент, не влезший целиком, обрезается с пометкой `…ещё N токенов`, следующие — только заголовок и `(budget)`;
- ошибка по элементу — в самом элементе (`error: not_found | forbidden | solution_access`), а не 4xx на весь ответ; Human — `not_found`;
- md: на элемент заголовок `### n:<id> <space>/<path> › <section>  rev<N> · ~<T> tok` (у записи журнала — как карточка шага 1) и текст; последняя строка — `~<total> tok`;
- выданные элементы записываются в `session_seen`.

**Шаг 3 — сохранение выжимки.** Агент вызывает `memory_cache_put` с параметрами:
- `query`;
- `summary` — Markdown, до 600 токенов (`cache.summary_tokens`; больше — 413), со ссылками на источники;
- `sources` — id и ревизии или секции того, на чём выжимка реально основана.

Сервер проверяет, что все источники существуют и доступны, фиксирует их текущие ревизии и хэши и строит зависимости для инвалидации (`cache_deps`). Источники должны лежать в той же базе, что и пространство кэша (иначе 422 `cache-cross-db`); источник из Human или Vault — 422 `cache-forbidden-source`. Если выжимка ценна надолго, её можно превратить в запись: `memory_cache_put(promote: …)` или `POST /cache/{id}/promote {as: note|insight, path?|kind?}`. Тогда она становится полноценной заметкой или инсайтом со связями `derived_from` на источники, а у записи кэша заполняется `promoted_to`.

**Правила экономии токенов.** Все они закреплены в инструкции агенту (§14.2) и в описаниях инструментов:
- MCP по умолчанию отвечает в компактном Markdown, а не в JSON;
- `budget_tokens` по умолчанию — 800 для поиска и 1500 для чтения;
- сначала L0/L1 и оглавление (`outline`), полный текст — только при необходимости;
- одним вызовом читается несколько id;
- то, что агент уже получал, повторно не выдаётся (`seen`, `if_rev`);
- перед новым поиском по той же теме сначала проверяется кэш;
- в каждом ответе есть служебная строка `~N tok`, чтобы агент видел свой расход.

### 9.4. Кэш выжимок
Требование из наброска: запрос и выжимка хранятся в кэше, кэш инвалидируется, когда меняются источники.

- **Кто пишет.** Только агенты, через `memory_cache_put` (`POST /cache`). Сервер выжимки не генерирует.
- **Где лежит** (таблицы `answer_cache`, `cache_deps` — §6.3): в базе пространства запроса.
  - `scope.solution` задан — в базе владельца решения: кэш общий на решение; выжимка, сохранённая участником, доступна остальным (с пометкой автора) и инвалидируется изменением источников решения. Участнику кэш решения доступен только при действующем доступе (чтение — право `ro`, запись — `rw`); после отзыва доступа выжимки решения ему не выдаются.
  - Иначе (Knowledge, Rules) — в базе пользователя; участникам такие выжимки не видны, в поиске по общему решению личный Knowledge подмешивается только свой.
  - Источники выжимки лежат в той же базе (иначе 422 `cache-cross-db`); Human и Vault источниками быть не могут (422 `cache-forbidden-source`).
- **Ключ.** `scope_hash` — blake3 канонического JSON `{solution, include_knowledge, include_rules, path_prefix, area, filters}`; `query_norm` — запрос в нижнем регистре, NFKC, со схлопнутыми пробелами; `query_vec` — dense-вектор запроса.
- **Область видимости.**
  - Поиск в кэше идёт сначала по текущей сессии, затем по выжимкам других сессий той же области (`cache.cross_session`, по умолчанию `true`).
  - Чужая выжимка помечается автором, машиной и датой, и агент сам решает, доверять ли ей.
  - Использование между сессиями — **[решение исполнителя]**: выжимка стоит агенту токенов, а её актуальность гарантирует проверка источников. Отключается настройкой.
- **Попадание в кэш:**
  - точное совпадение `(scope_hash, query_norm)`;
  - или семантическое: dense-косинус к `query_vec` ≥ `cache.semantic_threshold` (0,92).

  Возвращается не больше 2 выжимок.
- **Проверка при чтении.** Ревизии и хэши всех источников (`cache_deps`) сверяются одним SQL-запросом. Если хоть один источник расходится, удалён, перенесён в корзину или недоступен, запись кэша считается недействительной. Агент получает пометку `stale` со списком изменившихся источников и может обновить выжимку точечно: перечитать только изменившееся. Цель — §17 (≤ 30 мс плюс эмбеддинг запроса).
- **Инвалидация при записи:**
  - изменение, удаление, перенос в корзину, замещение или отзыв источника — по обратному индексу `cache_deps`, в той же транзакции писателя, что и запись источника: `state = stale`, причина в `stale_reason` (`changed | deleted | superseded | retracted`);
  - появление нового релевантного источника — воркер индексации после upsert новых чанков сравнивает их dense-векторы с `query_vec` действующих записей кэша той же области; при косинусе ≥ 0,80 запись помечается `stale: new_sources`.
- **Срок жизни.** `cache.ttl_days = 30` без обращений; LRU по `last_used_at` — `cache.max_entries = 2000` на базу. Выжимки, превращённые в записи (`promoted_to`), не вытесняются. Чистку делает воркер обслуживания раз в сутки.
- **Удаление.** `DELETE /cache/{id}` — автор, владелец пространства или администратор; удаление мягкое (`deleted_at`).
- **WebUI.** Кэш доступен на просмотр (§15.4): выжимка, источники, автор, статус. Записи можно удалять и превращать в заметки.

### 9.5. Почему не «выжимка на сервере»
Принцип 2 и решение владельца: сервер работает без LLM. Агент всё равно читает результат, поэтому лучше один раз прочитать нужное и сохранить выжимку, чем каждый раз генерировать её второй моделью. Кэш делает повторные обращения дешёвыми для всех сессий и машин.

## 10. Проактивное вспоминание

### 10.1. Идея простыми словами
Агент не знает, чего он не помнит. Даже если урок записан в память, агент пойдёт его искать только тогда, когда сам заподозрит, что такой урок есть. Обычно именно этого и не происходит. Поэтому память сама подсказывает в четыре момента:
1. на старте сессии;
2. на каждый запрос пользователя;
3. перед действием над файлом или командой;
4. после ошибки.

Подсказки встраиваются в контекст агента через **хуки**: агент сам запускает внешнюю команду на событие (Claude Code, Codex и другие умеют это).

**Что здесь проверено практикой, а что ново.**
- *Проверено практикой:* подмешивание контекста хуками `SessionStart`, `UserPromptSubmit` и `PostToolUse`. Это документированная возможность Claude Code. На ней построены claude-mem и плагины OpenViking; OpenViking за счёт автоподгрузки получил основной прирост на LoCoMo.
- *Новое, наша разработка:* детерминированные **триггеры** на инсайтах (маска файла, regex команды или ошибки). Это сочетание проверенных механизмов. Поэтому каждый тип подсказок отключается по отдельности, а полезность измеряется (§10.5).

### 10.2. Как это выглядит для агента (сценарий CRLF)

### 10.3. События, бюджеты, правила

| Событие (Claude Code / Codex) | Команда | Что делает и выдаёт | Бюджет |
|---|---|---|---|
| `SessionStart` | `zam hook session-start` | `POST /sessions` и `/recall(session_start)`: дайджест не больше `recall.digest_tokens` (1500). Передаёт `agent_block_version` — версию из маркера `<!-- zeroaimemory:begin vN -->` ближайшего CLAUDE.md/AGENTS.md **[решение контроллера, план M4]**. Обновляет кэш триггеров (`If-None-Match`) | ≤ 300 мс |
| `UserPromptSubmit` | `zam hook prompt` | `/recall(prompt)`: 0–3 инсайта или правила с баллом ≥ `recall.prompt_min_score` (0,6), без реранка; пусто — тишина | ≤ 250 мс, иначе тишина |
| `PreToolUse` (matcher `Write\|Edit\|Bash`) | `zam hook pre-tool` | **Только локально, без сети**: `file_glob` по `tool_input.file_path` относительно корня решения, `command_regex` по `tool_input.command`; запись показывается не больше раза за сессию (`.zeroaimemory/cache/shown-<session>.json`, туда же — факт правок Write/Edit) | ≤ 5 мс на сопоставление, ≤ 50 мс весь процесс |
| `PostToolUseFailure` (Claude Code, matcher `Bash`) / `PostToolUse` с непустым `tool_response.stderr` (Codex, `Bash`) | `zam hook post-tool` | Локальный `error_regex`, затем `/recall(post_tool)`: ошибка нормализуется (пути, числа, хэши, UUID, длинные hex; ≤ 512 символов) и ищется FTS по insight | ≤ 250 мс |
| `Stop`, `PreCompact` | `zam hook checkpoint` | Одно напоминание «запиши итоги в changelog/insights» — только если в сессии были Write/Edit (по `shown-<session>.json`) и `memory_writes == 0` (`GET /sessions/{id}`) **[решение контроллера, план M4]**; при `stop_hook_active == true` — ничего; на `Stop` — `{"decision": "block", "reason": …}` один раз за сессию | ≤ 100 мс |

Тайм-аут HTTP каждого хука — его бюджет минус 30 мс.

**Контракт хуков** сверен с документацией Claude Code и Codex 2026-10-26 (`docs/research/2026-10-26-agent-hooks-contract.md`):
- **Регистрация — exec form:** `"command": "zam", "args": ["hook", "<команда>"]` (без shell, одинаково на Windows и Linux); `timeout` в настройках агента — в секундах: 1 у `pre-tool`, 2 у остальных. Фрагмент `.claude/settings.json` и `.codex/hooks.json` выдаёт `GET /agent-setup` (§15.5), сливает в файлы `zam init` (§14.1).
- **Вход** — JSON на stdin (читается не больше 1 МБ, остальное отбрасывается); пустой stdin, не-JSON и неизвестное событие — пустой вывод.
- **Вывод** — `{"hookSpecificOutput": {"hookEventName": "<событие из stdin>", "additionalContext": "<текст>"}}` или пусто; текст не длиннее 9000 символов (предел Claude Code — 10 000; у Codex ≈ 2500 токенов, дайджест 1500 токенов укладывается). Исключение — `checkpoint` на `Stop`: `{"decision": "block", "reason": …}` (один раз; при `stop_hook_active` — не блокировать).
- **Адаптер Codex** — флаг `--agent codex` (по умолчанию `claude`) задаёт формат: у Codex нет `PostToolUseFailure`, поэтому `post-tool` регистрируется на `PostToolUse` с matcher `Bash` и срабатывает только при непустом `tool_response.stderr`; остальные события и поля вывода совпадают. Изменённый хук Codex ждёт повторного подтверждения в `/hooks`.

**Серверная часть — `POST /recall`** `{event, session_id, solution?, area?, prompt?, error?, tool?, budget_tokens?, agent_block_version?}` → `{text, items: [{id, kind, title, certainty, reason}], tokens, timings, warnings?, hooks?}` (`hooks` — настройки типов подсказок пользователя, только у `session_start`); `text` — готовый md для `additionalContext`:
- `session_start` — дайджест: Rules (L1), L1 решения, до 5 действующих `gotcha`/`failure` решения и Knowledge, записи `revisit`, последние 5 записей changelog, ожидающие запросы доступа владельцу (`access_requests_pending`), напоминание об устаревшем блоке инструкции (по `agent_block_version`, §15.5);
- `prompt` — поиск `mode=brief` по `prompt` только по insight и Rules (без реранка);
- `post_tool` — нормализованная ошибка: FTS по insight плюс совпадения `error_regex`; формат «ZeroAIMemory: эта ошибка уже разбиралась: …»;
- бюджет сервера `recall.timeout_ms = 200`: по превышении отдаётся собранное и `warnings: ["recall timeout"]`; каждый показ записывается в `usage` (`recall_shown`, `source` — событие).

Общие правила:
- **Fail-open.** Ошибка, тайм-аут или недоступный сервер дают пустой вывод и код 0 — при любой ошибке, всегда. Агент никогда не блокируется. Ошибки пишутся строкой в `.zeroaimemory/logs/hooks.log` (ротация по 1 МБ, без текста промптов и содержимого файлов).
- **Общее решение.** Проактивное вспоминание для общего решения работает по тем же правилам: триггеры и дайджест берутся из решения, доступного пользователю, и из его собственного Knowledge; чужой Knowledge и Human не подмешиваются никогда; решение без доступа исключается с `warnings` (как поиск) **[решение исполнителя]**.
- **Без повторов.** Одна запись показывается не больше одного раза за сессию (`session_seen` на сервере, `shown-<session>.json` у `pre-tool`). Исключение — `post_tool`/`error_regex`: такая подсказка срабатывает при каждой ошибке.
- **Пометка.** Все подсказки начинаются с `ZeroAIMemory:` и содержат ссылку `i:<id>`: `ZeroAIMemory: <title> [<insight_kind>, <certainty>] — i:<entry_id>`, для `file_glob` — «для <маска>: …».
- **Кэш триггеров** — `.zeroaimemory/cache/triggers.json` `{etag, fetched_at, server, solution, triggers}`; запись — временный файл в том же каталоге и rename (атомарно); `zam triggers sync` — принудительное обновление. Источник — `GET /triggers?solution=<guid>` (или `X-Zam-Solution`): `{etag, triggers: [{id, entry_id, type, pattern, tools, title, insight_kind, certainty, space}], warnings?}` — действующие триггеры решения (в базе владельца) и Knowledge пользователя; `If-None-Match` → 304. Регулярные выражения — `regex` без обратных ссылок, поэтому ReDoS невозможен.
- **`GET /triggers` при недоступном решении** — как поиск, **решение владельца 2026-10-26** (в M3 — 403 на весь ответ): доступ `pending | rejected | revoked` — 200 с триггерами Knowledge и `warnings: ["solution access <state>"]`; неизвестный GUID — 200 без решения и `warnings: ["solution unknown"]`; некорректный параметр `solution` — 400, некорректный заголовок `X-Zam-Solution` игнорируется. `ETag` — blake3 канонического JSON фактического состава ответа `{triggers, warnings}`.
- **Настройки** **[решение контроллера, R5]**: каждый тип подсказок (`session_start`, `prompt`, `pre_tool`, `post_tool`, `checkpoint`) включается и выключается:
  - в клиенте — `[hooks] session_start|prompt|pre_tool|post_tool|checkpoint = true|false` в `~/.zeroaimemory/config.toml` и `.zeroaimemory/config.toml` проекта (проект сильнее);
  - в WebUI — настройка пользователя на сервере `hooks.<тип>`; сервер отдаёт её в ответе `/recall(session_start)` полем `hooks: {…}`, хук кэширует её рядом с триггерами (`.zeroaimemory/cache/`);
  - тип выключен, если он выключен где-либо; выключенный хук сразу выходит с пустым выводом и кодом 0.

### 10.4. Агенты без хуков
Подключаются через MCP и инструкцию в AGENTS.md: «перед созданием файла нового типа или после ошибки вызови `memory_recall`». Тот же `/recall` доступен как инструмент `memory_recall` (`event`, `prompt?`, `error?`, §13.1). Агентам без HTTP-транспорта MCP — stdio-прокси `zam mcp`.

### 10.5. Измерение пользы
- Каждый показ записывается: `usage(recall_shown, source)`, где `source` — `session_start | prompt | pre_tool | post_tool`. Таблица `usage` лежит в базе цели (§6.3): владелец решения видит показы и оценки записей своего решения.
- Явная оценка: `POST /entries/{id}/feedback {value: useful|useless, session_id?}` → 204 (право чтения цели) — от агента (`memory_update_entry` с `action: feedback`, `source: agent`) или кнопкой в WebUI (`source: webui`). `GET /entries/{id}` отдаёт `usage: {shown, useful, useless}`.
- WebUI показывает «шумные» записи — часто показываются, но ни разу не были полезны. Их можно поправить или отключить им триггер.
- Отчёт по доле полезных подсказок помогает подстраивать пороги.

### 10.6. Черновики на подтверждение (v2)
По хуку `checkpoint` агент может записывать не готовые записи, а черновики со статусом `proposed`, если в настройках решения включён режим «подтверждать записи агентов». Черновики попадают в очередь подтверждения в WebUI и не участвуют в поиске до одобрения. Формирует черновики сам агент, LLM на сервере нет.

### 11.3. Конкурентная запись
- **Заметки.** `PUT` требует `If-Match: <rev>`. При конфликте — `409` с текущей ревизией и диффом.
- **Правка по секциям.** `PATCH` с операциями `replace_section`, `append_to_section`, `insert_after_heading`, `append`, `prepend` (адресация — путь заголовков). Патч применяется к последней ревизии, если затронутая секция не менялась после `base_rev`.
- **Записи журналов** — **решение владельца 2026-10-26**: память решения общая для всех сессий с доступом, и параллельная правка одной записи не должна молча затирать чужую. `PATCH` и `DELETE /entries/{id}` (в том числе смена `certainty` и триггеров) требуют `If-Match: <rev>`: без него — `428 /problems/precondition-required` («передайте If-Match: <rev> текущей ревизии»), расхождение — `409` с текущей ревизией; проверка ревизии — раньше прав. `supersede`, `retract`, `restore` — `If-Match` необязателен, при наличии проверяется. Новые записи только дописываются и не конфликтуют. CLI и WebUI берут `rev` из `GET /entries/{id}`, инструменты MCP всегда передают ревизию; при 409 CLI печатает «запись изменилась (rev N → M): перечитайте» и выходит с кодом 4, как при конфликте ревизии заметки (**решение контроллера R7**).
- **Повтор.** Каждый запрос записи принимает `Idempotency-Key`, повтор безопасен.
- **Атрибуция машины.** Заголовок `X-Zam-Machine`. CLI подставляет hostname, для MCP значение задаётся в конфиге клиента.

### 11.4. Аутентификация и пользователи
Сервис рассчитан в первую очередь на одного владельца.

- **Администратор.** Логин и пароль задаются в конфигурации сервера:
  - `[admin] login = "…"`, `password_hash = "argon2id…"`;
  - хэш выдаёт `zam-server hash-password`;
  - для первого запуска допускается `ZAM_ADMIN_PASSWORD`, пароль из неё хэшируется в памяти.

  Только администратор управляет сервисом. В БД учётных данных администратора нет.
- **Пользователи.** При первом запуске автоматически создаётся пользователь администратора с собственной памятью и первым токеном (токен выводится в лог один раз и доступен в WebUI). Других пользователей администратор заводит в WebUI; при создании пользователю выдаётся токен. У пользователя может быть несколько токенов, их можно выпускать, отзывать и перевыпускать. Режимы токена: `rw` (по умолчанию) и `ro`.
- **Вход пользователей в WebUI** — **решение владельца 2026-10-26** (перенесено из M7 в M4):
  - пароль пользователю задаёт администратор (`POST /admin/users/{id}/password`), при первом входе пользователь обязан его сменить (`must_change_password`; до смены прочие маршруты его сессии — 403 `password-change-required`); `DELETE /admin/users/{id}/password` закрывает вход; пароль — argon2id в `system.db`, не короче 10 символов;
  - вход общий: `POST /auth/login {login, password}` сначала проверяет администратора из конфига, затем пользователя по `users.name` (без учёта регистра); отключённый пользователь — 401; лимит частоты — общий (5 попыток в минуту на IP); cookie-сессия с CSRF — та же, что у администратора (`web_sessions.user_id`);
  - сессия пользователя даёт тот же доступ, что `rw`-токен этого пользователя, плюс `author_kind = human`; свой Human ему в WebUI доступен; `X-Zam-User` другого пользователя — 403; администраторские маршруты — 403;
  - пользователь видит только свою память и доступные ему решения: управляет доступом к своим решениям, `certainty`, Vault и своими токенами (`GET/POST /auth/tokens`, `DELETE /auth/tokens/{id}`); администраторские разделы скрыты (§15.1);
  - аудит: `auth.login.user`, `user.password.set | clear | change`.
- **Кто человек.** Человек — сессия WebUI (администратор или пользователь). Любой токен — агент (`author_kind = agent`) — **решение владельца 2026-10-26**: токены с флагом `human` (M3) и флаг CLI для них упразднены, аксиомы ставятся в WebUI или агентом по прямому указанию пользователя (§7.5). Колонка `tokens.human` остаётся, но не читается; `POST /admin/users/{id}/tokens` с `human: true` — 400 с пояснением, что такие токены упразднены и аксиомы подтверждаются в WebUI; поле `human` убрано из ответов токенов, `/auth/me` и `GET /spaces`. При старте, если есть неотозванные токены с `human = 1`, сервер пишет одну строку WARN с их префиксами: теперь они агентские.
- **Агент** получает только токен. Логин и пароль ему не нужны. Токен открывает всю память пользователя, кроме Human, включая vault, и память общих решений, к которым у пользователя есть одобренный доступ (§11.6).
- **Где лежит токен — в CLAUDE.md или AGENTS.md** (решение владельца), в блоке ZeroAIMemory:
  ```
  ZeroAIMemoryUrl=http://memory.lan:7700
  ZeroAIMemoryToken=zam_…
  ```
  CLI `zam` находит URL и токен по порядку:
  1. флаг командной строки;
  2. переменная окружения `ZAM_TOKEN` / `ZAM_URL`;
  3. блок в ближайшем `CLAUDE.md`, `CLAUDE.local.md` или `AGENTS.md`;
  4. `~/.zeroaimemory/config.toml`.

  MCP-конфиг (`.mcp.json`), который пишет `zam init`, токен не содержит: заголовок `Authorization: Bearer ${ZAM_TOKEN}` подставляется агентом из переменной окружения, а `zam init` печатает, как её задать (§14.1). Если токен утёк, его отзывают и перевыпускают в WebUI в один клик.
- **Хранение токенов** — только sha256. В WebUI видны префикс, время последнего использования и IP.

### 11.5. Сеть
- **Где слушает сервер.** `server.bind`, по умолчанию `0.0.0.0:7700`; HTTP в локальной сети. TLS и внешний доступ — забота внешнего прокси (Traefik и т. п.).
- **Работа за прокси:**
  - `server.trusted_proxies` — список доверенных адресов, от которых сервер принимает `X-Forwarded-For` и `X-Forwarded-Proto`;
  - `server.base_path` — публикация под префиксом, например `/memory`;
  - корректные абсолютные ссылки и cookie `Secure`, если запрос пришёл через HTTPS.
- **Защита входа.** Ограничение частоты входа в WebUI (администратор и пользователи — общий лимит, 5 попыток в минуту на IP) и неверных токенов.


### 11.6. Совместный доступ к решению (M3, требование владельца 2026-10-19)
Владелец решения открывает его память другим пользователям с подтверждением. Решение владельца 2026-10-21: делать сразу в M3, чтобы не менять нижележащие уровни потом; память решения остаётся в базе владельца.

- **Идентификатор.** `agent_solution_id` (GUID, нижний регистр, с дефисами). Ключ в `.zeroaimemory/solution.toml` (старый `id` читается) и поле в API, CLI и WebUI.
- **Хранение.** Решение — пространство `solution` в базе владельца (§6.3). В `system.db` лежат реестр решений (`solutions`: GUID, владелец, пространство) и разрешения (`solution_access`: участник, режим, состояние). Сервер по GUID находит базу владельца и пускает участника **только в пространство этого решения**. Rules, Human, Knowledge и Vault владельца, его узлы вне решения и рёбра в другие пространства участнику недоступны (404).
- **Регистрация.** Первый зарегистрировавший GUID — владелец. Решения M1–M2 регистрируются при старте сервера по порядку создания пользователей. Если один GUID встретился у двух пользователей, владельцем становится первый, а пространство второго получает новый GUID (его заметки остаются на месте), и для исходного GUID создаётся ожидающий запрос второго пользователя; аудит `solution.guid_conflict` **[решение исполнителя]**.
- **Выдача.** Владелец узнаёт `agent_solution_id` из `solution.toml` (`zam init`) или `GET /solutions/{guid}` и передаёт его другим пользователям.
- **Переименование.** `PATCH /solutions/{guid} {name}` — владелец (`rw`-токен или сессия WebUI) или администратор; участник — 403; имя 1–200 символов без управляющих; аудит `solution.rename`; CLI — `zam solution rename <name> [--solution GUID]`.
- **Подключение.** Другой пользователь прописывает идентификатор в своём `solution.toml`. При первом `POST /solutions` со своим токеном создаётся запрос на доступ: ответ `202 {agent_solution_id, state: "pending"}`. Пока запрос не одобрен, доступа нет (403 `/problems/solution-access` с `state`), и своё решение с этим GUID пользователю не создаётся.
- **Состояния и переходы.** `pending → approved | rejected`; `approved → revoked`; `approved → approved` (смена режима); `rejected → approved`; `revoked → approved`. Остальные переходы — 409. Повторный запрос после `rejected` или `revoked` состояние не меняет, чтобы не засорять владельца **[решение исполнителя]**. Владелец участником быть не может.
- **Режимы.** `rw` и `ro`; при одобрении по умолчанию `rw` **[решение исполнителя]**. Действующее право записи — режим токена и режим участника одновременно. Управлять доступом может владелец своим `rw`-токеном или администратор.
- **Управление доступом.** Владелец управляет доступом из CLI, REST и (с M4) WebUI — раздел «Мои решения» в своей сессии (§11.4, §15.1):
  - `zam solution access list|requests|approve <user> [--ro]|reject <user> [--reason R]|revoke <user> [--solution GUID]`;
  - `GET /solutions/{guid}/access`, `POST /solutions/{guid}/access/{user}/approve|reject|revoke` (§12);
  - число ожидающих запросов — поле `access_requests_pending` в `GET /spaces`, строка в `zam status` и в дайджесте старта сессии (§10.3);
  - те же операции есть у администратора в WebUI.
- **Отзыв.** Действует со следующего запроса, в том числе для уже выданных токенов: роль читается из `system.db` на каждый запрос, кэша нет; решение исключается из поиска с предупреждением `solution access revoked`. Запрос, одобрение, отклонение, смена режима и отзыв пишутся в аудит (`solution.register`, `solution.access.request|approve|reject|revoke|mode`).
- **Атрибуция.** Каждая ревизия заметки и записи журнала в базе владельца хранит `user_id` и токен автора, рядом сессию и машину (G6).
- **Vault.** Vault участника для общего решения лежит в его собственной базе и привязан к `agent_solution_id` (§7.6); владелец и другие участники его не видят.
- **Индекс и поиск.** Точки общего решения принадлежат владельцу базы (`user_id`) и несут `space_id` решения; запрос идёт одним обращением к Qdrant с дизъюнкцией областей (§6.4), FTS5 — по каждой базе в пределах её пространств с последующим слиянием (§9.2).
- **Кэш выжимок, сессии и проактивное вспоминание.** Для общего решения кэш общий на решение и лежит в базе владельца, личный Knowledge подмешивается только свой; сессии и `session_seen` участника — в его базе, `usage` — в базе владельца (§6.3, §9.4, §10.3).
- **Не делается.** Связи между базами (§8.5; решение владельца 2026-10-26), общий Vault, совместное редактирование в реальном времени (§2.2).

## 12. REST API (`/api/v1`)

- **Аутентификация:** для агентов — `Authorization: Bearer zam_…`; для WebUI — cookie-сессия с CSRF администратора или пользователя (§11.4).
- **Формат:** JSON, ошибки по RFC 9457, пагинация курсором, gzip/br.
- **Заголовки:** `Idempotency-Key` на запись; `If-Match: <rev>` на правку (у записей журналов — обязателен, §11.3); `X-Zam-Session`, `X-Zam-Machine`, `X-Zam-Solution` (`agent_solution_id`) и `X-Zam-Area` для атрибуции и области по умолчанию (§11.2). Первый запрос с `X-Zam-Session` (поиск, `/read`, `/recall`) неявно создаёт сессию; запись в память с `X-Zam-Session` увеличивает `sessions.memory_writes` (§6.3).
- **Администратор** работает с API любого пользователя, указывая `X-Zam-User: <id>`; пользователь WebUI — только со своим (другой `X-Zam-User` — 403).

| Кэш выжимок | `POST /cache {query, summary, sources: [{id, rev?, section?}], solution?, promote?}` → 201 (выжимка больше `cache.summary_tokens` — 413; источник из другой базы — 422 `cache-cross-db`, из Human или Vault — 422 `cache-forbidden-source`), `GET /cache?q=&solution=&session=&state=` (свои области), `GET /cache/{id}`, `DELETE /cache/{id}` (автор, владелец пространства или администратор), `POST /cache/{id}/promote {as: note\|insight, path?\|kind?}` (§9.3–9.4) |
| Чтение пачкой | `POST /read {items: [{id, tier?, section?, locator?, max_tokens?, if_rev?}], session_id?, format?: md\|json, budget_tokens?}` — до 20 элементов, бюджет 1500, ошибки по элементу (§9.3) |
| Подключение агента | `GET /agent-setup?agent=claude\|agents\|codex&solution=<guid\|new\|auto>&mcp=&hooks=&rules_write=&lang=ru\|en` (токен — из запроса: bearer или `token=` администратору при выпуске) → `{version, block, solution_toml?, mcp_json?, claude_settings?, codex_hooks?, install: {windows, linux}, init_cmd}` (§15.5); `GET /agent-guide` — полный протокол §9.3 и §14 в md (`zam guide`); `GET /downloads/zam/{os}-{arch}` (`windows-x64`, `linux-x64`) — бинарник `zam` из каталога комплекта, без аутентификации, нет файла — 404 |
| MCP | `/mcp` — streamable HTTP, bearer (§13.1) |
| Индекс | `GET /index/status` (векторный канал с причиной и подсказкой, модель, устройство, RSS самого сервера `server.rss_bytes`, Qdrant: состояние, версия, `rss_bytes`, точки, перезапуски, `wal_pending_ops` — записей точек, ещё не подтверждённых в WAL (задача 19 M3); очередь, до 20 ошибок (у узла в корзине — `deleted_at`), время воркера `worker` (инференс, запись в Qdrant; администратору ещё `worker.batch_running` и `worker.rollups_pending` — покой воркера), последний reindex, исключённые базы, перенарезка по базам `dbs: [{user_id, rechunk: {reason, changed, total, done} \| null}]` (§8.2); токен — только свой пользователь). `POST /admin/reindex {user?, space?, full?}` → 202 `{job_count}` |
| Экспорт/импорт | `GET /spaces/{space}/export` (zip: `.md` + `_attachments/`), `POST /spaces/{space}/import` (zip или папка `.md`) |
| Служебное | `GET /health`, `GET /ready`, `GET /metrics` |

Таблица описывает целевой API. На `0.0.5-m4` в API ещё нет (этапы — по §19): `GET /blobs/{sha256}/preview` — M5; экспорт/импорт и `GET /admin/doctor` — M7; `GET /admin/stats` и `GET /metrics` — этап не назначен. Фактический список маршрутов — `crates/zam-server/src/api/mod.rs` (`router`).

Ошибки: `403 /problems/solution-access` (`state`: `pending | rejected | revoked`), `422 /problems/certainty` при нехватке `evidence` или `reason` (§7.5; 403 по правилам `certainty` с M4 нет), `428 /problems/precondition-required` — правка записи журнала без `If-Match`, `409` — устаревшая ревизия (с текущей), `503 /problems/vault-locked` (значения и запись Vault), `409 /problems/possible-duplicate` (дубль инсайта, §7.5), `403 password-change-required` — сессия пользователя до смены пароля (§11.4).

Как это закрывает пункты API из наброска:
- регистрация и вход → Auth и Админ (по новой схеме §11.4);
- поиск чанков и документов без саммаризации → `/search` с `mode=chunks` или `mode=notes`;
- получение документа по идентификатору → `/nodes/{id}`;
- получение вложений → `/blobs`;
- добавление записей → `/nodes` и `/entries`.

## 13. MCP и CLI

### 13.1. MCP (`/mcp`, streamable HTTP, bearer)
MCP — тонкий адаптер над REST (принцип 5): каждый инструмент вызывает те же функции сервиса, что REST, с тем же `Principal` и проверкой доступа.

- **Транспорт.** Streamable HTTP (`rmcp`) на `/mcp`: без сессий (stateless), если это поддерживает закреплённая версия, иначе сессии `rmcp` в памяти с тайм-аутом 30 мин. `Authorization: Bearer` проверяется тем же middleware, что REST.
- **Заголовки.** `X-Zam-Solution`, `X-Zam-Session`, `X-Zam-Machine`, `X-Zam-Area` HTTP-запроса задают решение по умолчанию и атрибуцию; решение по умолчанию прописывается в MCP-конфиге (`.mcp.json`, §15.5).
- **Ответы** — компактный Markdown (по параметру `format=json` — JSON); каждый ответ оканчивается строкой `~N tok`. Описания инструментов — русские, не длиннее 300 символов.
- **Ошибки сервиса** — результат инструмента с `isError: true` и текстом problem (`title`, `detail`), а не ошибка JSON-RPC; ответы 409 и 428 объясняют, что перечитать.
- **stdio.** Для агентов без HTTP-транспорта — `zam mcp` (§13.2).

|---|---|---|
| `memory_search` | `query`, `mode?`, `scope?`, `filters?`, `top_k?`, `budget_tokens?`, `expand?`, `rerank?` | `POST /search` (§9.1; шаг 0 — кэш выжимок, затем карточки `mode=brief`) |
| `memory_read` | `items: [{id, tier?, section?, max_tokens?, if_rev?}]` | `POST /read` (§9.3) |
| `memory_cache_put` | `query`, `summary`, `sources`, `promote?` | `POST /cache` (§9.3–9.4) |
| `memory_tree` | `space?`, `path?`, `depth?` | дерево с L0 |
| `memory_write` | `path`, `content?`, `ops?`, `base_rev?`, `message?`, `l0?` | `POST`/`PUT`/`PATCH /nodes` |

### 13.2. CLI `zam`
Один статический бинарник, без ONNX, tokio и SQLite. Холодный старт ≤ 20 мс. Сервер раздаёт его по `GET /downloads/zam/{os}-{arch}` (§15.5).

`zam mcp` читает JSON-RPC построчно со stdin, шлёт `POST /mcp` (bearer, заголовки решения из `solution.toml`) и пишет ответы в stdout; SSE-ответы разворачивает в отдельные строки.

```
zam init [--name] [--id] [--url --token] [--agent claude|codex|both] [--no-hooks] [--no-mcp] [--yes]
                                          # solution.toml (agent_solution_id), блок в CLAUDE.md/AGENTS.md, хуки, .mcp.json (§14.1)
zam status                                # в том числе: устарел ли блок инструкции (§15.5), ожидающие запросы доступа
zam guide                                 # полный протокол работы с памятью (GET /api/v1/agent-guide)
zam search <query> [--all] [--mode brief|chunks|notes] [--json]
zam read <id|path>… [--tier L1] [--section "A > B"] [--max-tokens N]
zam cache put --query … --sources id@rev,… [--promote note:<path>|insight:<kind>] < summary.md
zam cache list|show|rm
zam tree [path] [--depth N]
zam write <path> [--file f.md | stdin] [--message] [--base-rev N]
zam attach <path-заметки> <файл>
zam log changelog|insight|release …     # --trigger file_glob:**/*.sh, --link relates_to:node:<id>; insight: --certainty axiom|theorem|hypothesis (axiom — по указанию пользователя), --evidence-file F
zam insight list|show|supersede|retract|revisit|append   # правка — с rev из GET /entries/{id} (If-Match, §11.3)
zam insight certify <id> axiom|theorem|hypothesis|none --reason R [--evidence-file F]   # обычный токен (§7.5)
zam insight feedback <id> useful|useless [--session S]   # оценка полезности (§10.5); счётчики usage — в insight show
zam release add|compare [--from-git]
zam vault list|get|set [--global]       # значение — только из stdin или скрытого ввода; list при блокировке — с пометкой
zam link <src> <type> <dst>             # также: zam link rm <edge-id>, zam links <id>
zam solution access list|requests|approve|reject|revoke   # §11.6
zam solution rename <name> [--solution GUID]
zam hook session-start|prompt|pre-tool|post-tool|checkpoint [--agent claude|codex]   # §10.3; всегда код 0
zam triggers sync                         # принудительное обновление .zeroaimemory/cache/triggers.json
zam export|import                         # этап M7
zam mcp                                   # stdio-прокси к /mcp (§13.1)
```

### 13.3. `zam-server`

```

zam-server serve
zam-server hash-password                 # пароль из stdin → argon2id

zam-server backup | restore    # этап M7
zam-server service install [--name zam-server] [--config PATH] [--user USER (Linux)] [--print (Linux)]
```

Реализованы все команды, кроме `doctor` и `backup`/`restore` (этап M7); `service` — с `0.0.5-m4` (перенесено из M7, **решение владельца 2026-10-26**). `cuda fetch` при работающем сервере на Windows отказывает до загрузки (библиотеки заняты) с подсказкой остановить сервер.

**Режим службы.** Тот же бинарник работает и службой, и обычным процессом: ручной запуск `zam-server serve` в консоли — без изменений.
- **Windows (SCM).** `install` регистрирует службу (`OwnProcess`, автозапуск, `binPath = "<exe>" service run --config <абсолютный путь>`, описание; восстановление — перезапуск через 10 с, три раза); установка требует прав администратора — без них понятная ошибка и код 3. `run` — `service_dispatcher`; `Stop`/`Shutdown`/`Preshutdown` ведут в общий сигнал остановки (§4.3); статус `StopPending` с `wait_hint` 10 с и `checkpoint` каждые 2 с, пока идёт остановка; таймаут `Preshutdown` — таймаут остановки службы `T = max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с (94 с при умолчаниях) **[решение контроллера, R4]**. Журнал под службой — в файл `data_dir/logs/` (консоли нет). NSSM остаётся альтернативой (`deploy/README-install.md`).
- **Linux (systemd).** `install` пишет `/etc/systemd/system/<name>.service` из шаблона `deploy/systemd/zam-server.service` (`TimeoutStopSec = max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` — запас 80 с: пачка инференса до 60 с, перенарезка до 10 с, SIGTERM Qdrant до 10 с; при умолчаниях 94 с **[решение контроллера, R4]**; `KillSignal=SIGINT`, `Restart=on-failure`, `User=`), выполняет `systemctl daemon-reload` и `enable`; `start|stop|status` — обёртки `systemctl`; `--print` выводит юнит без записи.
- **Проверка таймаута остановки при старте** — только под службой: под SCM читаются параметры собственной службы, под systemd (`INVOCATION_ID` в окружении) — `systemctl show -p TimeoutStopUSec <unit>`; если таймаут службы меньше `T = max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с — WARN «таймаут остановки службы N с меньше ожидания Qdrant M с: выполните `zam-server service install` повторно». При ручном запуске проверки нет.

## 14. Интеграция с агентами

### 14.1. `zam init`
`zam init [--name] [--id] [--url --token] [--agent claude|codex|both] [--no-hooks] [--no-mcp] [--yes]` берёт текст и фрагменты у `GET /agent-setup` (§15.5):
1. Создаёт или читает `.zeroaimemory/solution.toml` и регистрирует решение (`POST /solutions`).
2. Вставляет или обновляет блок между `<!-- zeroaimemory:begin vN -->` и `<!-- zeroaimemory:end -->` в `CLAUDE.md` и/или `AGENTS.md` (по `--agent`); остальной текст файла сохраняется байт в байт. В блоке — URL, токен и правила работы (§14.2).
3. После подтверждения (или с `--yes`) сливает хуки (§10.3) в `.claude/settings.json` и/или `.codex/hooks.json` — чужие хуки сохраняются, наши заменяются по признаку `command == "zam"` и `args[0] == "hook"` — и MCP-сервер в `.mcp.json` (без токена: `Bearer ${ZAM_TOKEN}`; `zam init` печатает, как задать `ZAM_TOKEN`). `--no-hooks` и `--no-mcp` пропускают соответствующую часть.
4. Пишет `.zeroaimemory/.gitignore` (`cache/`, `logs/`).

Повторный запуск идемпотентен.

### 14.2. Блок инструкции v2

Блок генерируется сервером (§15.5) и вставляется пользователем вручную или через `zam init`. Он намеренно короткий (≤ 500 токенов по счётчику модели с подставленными URL и токеном, проверяется тестом), потому что CLAUDE.md загружается в каждую сессию: шаблон по умолчанию ниже — 454 токена bge-m3, с токеном `zam_` из 44 символов и адресом по IP — около 495 (блок v1 был 584 токена — превышал предел). Подробности протокола агент получает из описаний MCP-инструментов и по запросу `GET /api/v1/agent-guide` (или `zam guide`). Версия v2 (M4) добавляет к v1 правила владельца 2026-10-26: аксиомы — только по прямому указанию пользователя, правка записей — с ревизией. Шаблон по умолчанию ниже; администратор правит шаблоны в WebUI (§15.5), номер версии растёт при каждом сохранении.

```markdown
<!-- zeroaimemory:begin v2 -->
## Память ZeroAIMemory
ZeroAIMemoryUrl=http://memory.lan:7700
ZeroAIMemoryToken=zam_…
Решение: `.zeroaimemory/solution.toml` (`zam init`). Без MCP — CLI `zam`, без CLI — REST `/api/v1`.

Поиск:
1. `memory_search`: актуальную `[cache]`-выжимку используй; `stale` — перечитай изменившееся.
2. Иначе выбери карточки сам; `memory_read` нескольких id, сначала `tier=L1` или `section`.
3. Ответ из нескольких источников → `memory_cache_put` (выжимка ≤ 600 токенов, источники).

Правила:
- Перед задачей — `memory_search`; перед исследованием — `insight_kinds=[experiment,failure]`.
- Ошибка, ловушка → `memory_log insight` (gotcha|failure; scope=global, если не про проект) с триггерами; эксперимент — с результатом.
- Изменение проекта → `memory_log changelog`; устарело → `memory_update_entry` supersede/retract.
- Правка записи — с `rev`; на 409/428 перечитай.
- `axiom` ставь, правь, снимай только по прямому указанию пользователя; несогласен — `hypothesis`/`theorem` рядом и скажи пользователю. `certainty` — с `reason`.
- Секреты → `memory_vault`. Заметке — `l0`.
- «ZeroAIMemory:» — накопленные знания. Без хуков: перед новым типом файла и после ошибки — `memory_recall`.
<!-- zeroaimemory:end -->
```

## 15. WebUI

### 15.1. Общее
- **Вход:** общий для администратора (логин и пароль из конфигурации) и пользователей (пароль задаёт администратор, смена при первом входе) — **решение владельца 2026-10-26** (§11.4). Cookie `HttpOnly` + `SameSite=Strict` (+ `Secure` за HTTPS-прокси), CSRF.
- **Что видит пользователь** (не администратор): только свою память (Rules, свой Human, Knowledge, свои решения) и доступные ему общие решения. Разделов «Пользователи», «Администрирование», «Настройки сервиса» и полного «Индекса» у него нет — они скрыты в интерфейсе и закрыты на сервере (403). Есть «Мои решения» (управление доступом к своим решениям — те же REST, что у CLI, §11.6), «Аккаунт» (смена пароля, выпуск и отзыв своих `rw`/`ro`-токенов) и «Подключение агента» (§15.5). `certainty`, Vault и журналы он правит так же, как администратор свою память.
- **Левая панель — дерево:**
  - вверху закреплены `Rules`, `Human`, `Knowledge`;
  - ниже — `Solutions`. Каждое решение раскрывается: сначала закреплены `Changelog`, `Releases`, `Insights`, `Vault`, затем его дерево; общие решения других пользователей помечены владельцем и режимом доступа; у `Knowledge` закреплены `Insights` и `Vault`; управление доступом (запросы, участники, отзыв, §11.6) — «Администрирование → Решения» у администратора и «Мои решения» у пользователя;
  - корень дерева у администратора — «Пользователи»: сначала свой пользователь, под каждым — его поддерево; у пользователя — только его поддерево;
  - ленивая подгрузка, drag-and-drop, контекстное меню, значки статуса индексации.
- **Правая панель** — просмотр или правка выбранного узла. Вкладки: «Документ», «История», «Связи».
- **Поиск** (Ctrl+K) по всем пространствам, включая Human (FTS), с подсветкой и переходом к секции, странице или листу.
- **Тёмная и светлая тема.** Адаптивная вёрстка; на телефоне — в основном чтение.

### 15.2. Markdown — полная поддержка
- **Один парсер на всю систему.** Markdown разбирает только сервер (`zam-markdown`, §5.3). WebUI получает готовый санитизированный HTML (`GET /nodes/{id}?format=html`, предпросмотр — `POST /render`) и лишь «оживляет» его: формулы, диаграммы, медиа, копирование кода, якоря. Поэтому заголовки, секции, якоря и ссылки в интерфейсе совпадают с тем, что индексирует и патчит сервер, а в начальном бандле нет Markdown-парсера. Офлайн-предпросмотр через WASM-сборку `zam-markdown` отложен до v2. **[решение исполнителя]**
- **Синтаксис:** CommonMark + GFM (таблицы, задачи, зачёркивание, автоссылки, сноски), якоря заголовков, оглавление.
- **Расширения:**
  - подсветка кода на сервере (syntect, CSS-классы под светлую и тёмную тему);
  - формулы `$…$`, `$$…$$`, ```` ```math ````: сервер размечает, клиент рендерит KaTeX (лениво);
  - диаграммы ```` ```mermaid ````: Mermaid загружается лениво, работает в режиме `securityLevel: 'strict'`, итоговый SVG проходит DOMPurify; диаграмма с `layout: elk` рисуется ленивой раскладкой ELK (`elkjs`, EPL-2.0 — исключение, разрешённое владельцем 2026-10-21; текст лицензии и ссылка на исходники — в `THIRD-PARTY-NOTICES.txt`), раскладка по умолчанию — dagre;
  - callout-блоки: 5 типов GitHub (`> [!NOTE]`, `> [!WARNING]`, …) и синтаксис Obsidian с произвольным типом и сворачиванием (`> [!info]-`);
  - wiki-ссылки `[[…]]` с автодополнением и обратными ссылками;
  - отображение frontmatter (теги, связи, description).
- **Встроенные медиа:** `![](…)` выбирает вид по MIME:
  - изображения — с лайтбоксом и масштабом;
  - видео (mp4, webm) и аудио (mp3, ogg, wav, m4a) — встроенный плеер с перемоткой (Range);
  - документы — встроенная карточка-превью (§15.3) с раскрытием в полноэкранный просмотр.
- **Безопасность:**
  - comrak работает с `render.unsafe = false`, итоговый HTML проходит `ammonia` на сервере с явным списком тегов и атрибутов;
  - на клиенте DOMPurify применяется только там, где клиент сам вставляет разметку: SVG Mermaid, превью DOCX;
  - CSP без `unsafe-inline` для скриптов.

### 15.3. Просмотр документов (минимум DOCX, XLSX, PDF)

| Формат | Просмотр | Механизм |
|---|---|---|
| PDF | Постранично, масштаб, поиск по тексту, переход к странице из результатов поиска (`locator`) | `pdf.js` в браузере |
| DOCX | Вёрстка, близкая к оригиналу: стили, таблицы, изображения, колонтитулы | `docx-preview` в браузере |
| XLSX / XLS / ODS / CSV | Таблица с переключением листов, виртуальной прокруткой, закреплённой шапкой, переходом к диапазону | Сервер: `calamine` → JSON по листам (`/preview?kind=sheet`) → таблица в браузере |
| PPTX | v1: текст слайдов; v2: визуальный просмотр | Сервер: извлечение текста |
| TXT, JSON, YAML, исходный код | С подсветкой | Сервер: syntect → HTML (кэш в `previews/`) |
| Изображения | Миниатюры, полноэкранный просмотр | Сервер: `image` → миниатюры в `previews/` |

- **Производительность.** Тяжёлые просмотрщики (pdf.js, docx-preview, Mermaid, KaTeX, CodeMirror) загружаются лениво, при первой необходимости.
- **Подбор библиотек.** Если на тестовом наборе документов (`eval/docs/`) клиентская библиотека отображает формат неудовлетворительно, допускается замена на серверную конвертацию в HTML или PDF. Внешние офисные пакеты (LibreOffice) запрещены — нарушают «вещь в себе».

### 15.4. Правка и прочее
- **Правка:**
  - CodeMirror 6: `minimalSetup` + `@codemirror/lang-markdown`, подсветка кода во fenced-блоках через Lezer. Свои расширения Lezer добавляют подсветку wiki-ссылок, callout, формул и сносок. На семантику они не влияют: её определяет сервер;
  - три режима: исходник, предпросмотр рядом (`POST /render` с debounce около 150 мс) и гибридный live-preview. В гибридном режиме разметка скрыта на всех строках, кроме строки с курсором; сделан на декорациях CM6, свой. Готовые пакеты незрелые и используются только как образец;
  - WYSIWYG-редакторы на модели документа (ProseMirror, Tiptap, Milkdown) запрещены: они пересериализуют Markdown и ломают побайтовую сохранность исходника;
  - вставка изображений и файлов из буфера или перетаскиванием, с загрузкой в blobs и вставкой ссылки;
  - автодополнение `[[…]]`;
  - сохранение с `If-Match`, при конфликте — окно с диффом.
- **История:** ревизии, дифф любых двух, откат, имя версии.
- **Журналы:**
  - Changelog — лента с фильтрами (вид, область) и курсором;
  - Releases — список и сравнение (записи changelog интервала по видам, дифф текста релиза, коммиты);
  - Insights — таблица с фильтрами (вид, статус, `certainty`, область, теги) и значком статуса надёжности; столбец «показы / полезно / бесполезно» (`usage`) и кнопки оценки (`feedback`, `source: webui`, §10.5); действия «Заменить», «Отозвать», «Пересмотреть», «Сменить статус надёжности» (причина необязательна, для `theorem` — форма `evidence`); при создании insight переключатель `certainty` по умолчанию пустой (**решение владельца 2026-10-26**); правка — с `If-Match` текущей ревизии (§11.3); правка триггеров, цепочка замещения; отдельный список «шумных» записей и очередь `proposed` — v2;
  - Vault — маска и раскрытие с аудитом (значение видно до «Скрыть», не дольше 30 с **[решение исполнителя]**), баннер `vault-locked`; при заблокированном Vault список виден, «Показать» неактивна (§7.6).
- **Связи** (вкладка узла и карточка записи): исходящие связи, включая неразрешённые ссылки, и обратные ссылки — списком.
- **Граф:** локальный граф узла (на 1–2 шага) и обратные ссылки — `d3-force` (SVG). Общий граф пространства на тысячи узлов — `sigma` 4 + `graphology` (WebGL, раскладка ForceAtlas2 в воркере). Обе библиотеки загружаются лениво.
- **Администрирование:**
  - пользователи и их токены: создать, выпустить, отозвать, последнее использование; задать пароль входа в WebUI (с обязательной сменой при первом входе) или закрыть вход (§11.4);
  - решения: реестр, владельцы, участники и запросы доступа — одобрить `rw`/`ro`, отклонить с причиной, отозвать (§11.6);
  - настройки сервиса (`rules.agent_write`; «Шаблон инструкции» — §15.5);
  - состояние индекса, моделей и устройства; баннер перенарезки «Идёт перенарезка: изменились <ключи>, N из M» в индикаторе индекса (§8.2);
  - аудит;
  - doctor и reindex;
  - бэкап.
- **Кэш выжимок:** список с фильтрами (решение, статус `valid/stale`, автор), просмотр выжимки и её источников (у `stale` — причины), удаление, «Превратить в заметку» (`POST /cache/{id}/promote`, §9.4).
- **Бюджет:** начальный бандл ≤ 300 КБ gzip без учёта ленивых модулей. Ленивые чанки, по замерам аудита (gzip): редактор около 105–130 КБ, KaTeX около 77 КБ плюс шрифты, Mermaid около 200 КБ на flowchart, pdf.js — несколько МБ вместе с воркером. Размеры проверяются в CI (`size-limit`).

### 15.5. «Подключение агента» — готовый текст для CLAUDE.md / AGENTS.md
Отдельная страница WebUI. Доступна в меню и сразу открывается после создания нового пользователя или выпуска токена.

**Что выбирают** (администратор — для любого пользователя; пользователь — только для себя, §15.1):
- пользователя и его токен; токен можно тут же выпустить;
- агента: **Claude Code** (CLAUDE.md), **AGENTS.md** (Codex, Cursor и др.) или **Codex** (AGENTS.md и хуки Codex);
- решение: существующее, новое (WebUI сгенерирует GUID) или «агент создаст сам»;
- опции: MCP да/нет, хуки да/нет, разрешена ли запись в Rules, язык инструкции (ru/en).

**Что получает** — блоки с кнопкой «Копировать» у каждого:
1. **Текст для CLAUDE.md / AGENTS.md.** Блок §14.2 с подставленными `ZeroAIMemoryUrl` (из `server.public_url`, а если он не задан — из адреса, по которому открыт WebUI) и `ZeroAIMemoryToken`, плюс правила работы. Блок обёрнут в маркеры с версией шаблона (`<!-- zeroaimemory:begin v2 -->`).
2. **`solution.toml`**, если решение выбрано или создано.
3. **Фрагмент `.mcp.json`**, если включён MCP: `{"mcpServers": {"zeroaimemory": {"type": "http", "url": "<public_url>/mcp", "headers": {"Authorization": "Bearer ${ZAM_TOKEN}", "X-Zam-Solution": "<guid>"}}}}` — токен в файл не пишется, агент подставляет его из переменной окружения `ZAM_TOKEN`.
4. **Фрагмент хуков**, если они включены: `.claude/settings.json` (Claude Code) или `.codex/hooks.json` (Codex) — exec form `zam` + `args`, `timeout` в секундах (1 у `pre-tool`, 2 у остальных), события и matcher — §10.3:
   ```json
   {"hooks": {"SessionStart": [{"hooks": [{"type": "command", "command": "zam", "args": ["hook", "session-start"], "timeout": 2}]}],
              "UserPromptSubmit": [{"hooks": [{"type": "command", "command": "zam", "args": ["hook", "prompt"], "timeout": 2}]}],
              "PreToolUse": [{"matcher": "Write|Edit|Bash", "hooks": [{"type": "command", "command": "zam", "args": ["hook", "pre-tool"], "timeout": 1}]}],
              "PostToolUseFailure": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "zam", "args": ["hook", "post-tool"], "timeout": 2}]}],
              "Stop": [{"hooks": [{"type": "command", "command": "zam", "args": ["hook", "checkpoint"], "timeout": 2}]}],
              "PreCompact": [{"hooks": [{"type": "command", "command": "zam", "args": ["hook", "checkpoint"], "timeout": 2}]}]}}
   ```
   У Codex тот же состав с `--agent codex`, а `post-tool` — на `PostToolUse` с matcher `Bash`.
5. **Команды установки `zam`** для Windows и Linux. Бинарники раздаёт сам сервер: `GET /downloads/zam/{os}-{arch}` (`windows-x64`, `linux-x64`; из каталога комплекта, без аутентификации).
6. **Однострочник** `zam init --url … --token …`, который делает пункты 1–4 автоматически (§14.1).

**Шаблоны и версии:**
- Шаблоны текста хранятся в настройках сервиса (`settings`, ключ `agent_setup.template.<agent>.<lang>`), и администратор может их править: «Настройки → Шаблон инструкции», с предпросмотром, номером версии и сбросом к значению по умолчанию.
- Номер версии шаблона растёт при каждом сохранении.
- `zam status` и `/recall(session_start)` сравнивают версию блока в CLAUDE.md/AGENTS.md с текущей (`version` из `GET /agent-setup`): хук `session-start` читает её из маркера `<!-- zeroaimemory:begin vN -->` ближайшего CLAUDE.md/AGENTS.md и передаёт в `/recall` как `agent_block_version` **[решение контроллера, план M4]**. Если блок устарел, агент получает одно напоминание: «Блок ZeroAIMemory устарел (v1 → v2): обнови через `zam init` или WebUI».

**API.** Тот же текст и фрагменты отдаёт `GET /api/v1/agent-setup` (§12). Так им пользуется и `zam init`.

## 16. Безопасность и эксплуатация

### 16.1. Безопасность
- Пароль администратора хранится как argon2id-хэш в конфигурации, пароли пользователей — как argon2id-хэш в `system.db`; токены — как sha256 в БД.
- Логи не содержат текста заметок, записей, выжимок, секретов, токенов, паролей и промптов пользователя (токены маскируются до префикса); журнал хуков `.zeroaimemory/logs/hooks.log` — тоже (§10.3).
- В аудит пишутся: вход администратора и пользователей, операции с пользователями, паролями и токенами, каждое раскрытие vault, удаление, откат, reindex, переименование решения.
- Раскрытие секретов по токену частотой не ограничивается: секреты нужны агенту. Каждое раскрытие видно в аудите и в WebUI.
- Содержимое Human недоступно по токену ни в каком виде: его нет в выдаче по токену и MCP, в выжимках кэша (источник из Human — 422), в подсказках хуков и в логах. В WebUI свой Human видит только его владелец (и администратор).

### 16.2. Поставка и эксплуатация
- **Артефакты:**
  - **основной способ — архивы** `zam-server` (`cpu`/`gpu`, по желанию `-models`) для Windows x64 и Linux x64 (состав — §16.3). Docker не нужен;
  - `zam` для Windows x64 и Linux x64;
  - режим службы — с `0.0.5-m4` (перенесено из M7, **решение владельца 2026-10-26**): `zam-server service install|uninstall|start|stop|status` регистрирует службу Windows (SCM) или пишет юнит systemd с таймаутом остановки по конфигу (§13.3); Qdrant запускается сервером как дочерний процесс и отдельной службой не регистрируется. Таймаут остановки службы — `max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с по конфигу (R4, §13.3), при старте под службой сервер проверяет его и при нехватке пишет WARN. Ручной запуск в консоли — без изменений; NSSM и ручная установка по `deploy/README-install.md` остаются альтернативой;
  - **по желанию** — один Docker-образ `zam-server` с тем же нативным Qdrant внутри, в режиме `managed`. Отдельный контейнер Qdrant и docker-compose не нужны.
- **Бэкап** (`zam-server backup`, по расписанию из конфига; этап M7, на M2 не реализован):
  - `VACUUM INTO` каждой базы;
  - инкрементальный архив блобов;
  - манифест.

  Векторы приходят из таблицы `embeddings`, поэтому Qdrant восстанавливается через `reindex` без инференса. Мастер-ключ vault в бэкап не входит, его резервируют отдельно.
- **Миграции.** Каждая база имеет свою версию схемы (`PRAGMA user_version`). Миграция выполняется при открытии, перед ней делается копия файла.

### 16.3. Релизы: обязательные сборки (требование владельца)
Каждый релиз собирает **готовые к работе комплекты для Windows x64 и Linux x64**: в комплекте есть всё, что нужно для запуска. Релиз без любого из этих комплектов не публикуется.

- **Запуск.** Тег `vX.Y.Z` в git запускает конвейер CI (GitHub Actions; раннеры `windows-latest` и `ubuntu`). Результат — черновик GitHub Release со всеми файлами, `SHA256SUMS` и заметками к релизу из `CHANGELOG.md`.
- **Комплекты:**

  | Архив | Содержимое |
  |---|---|
  | `zam-server-<ver>-windows-x64-cpu.zip` | `zam-server.exe` (с встроенным WebUI), `onnxruntime.dll` (CPU), `pdfium.dll`, app-local MSVC runtime для ONNX Runtime (`msvcp140.dll`, `msvcp140_1.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`), `qdrant/<qver>/qdrant.exe` + `vcruntime140.dll`, `zam.exe` (для раздачи `GET /downloads/zam/…`), `config.example.toml`, `deploy/qdrant.toml`, `deploy/models.toml`, `README-install.md`, `LICENSES/` |
  | `zam-server-<ver>-windows-x64-gpu.zip` | то же, но ONNX Runtime с CUDA EP (`onnxruntime_providers_cuda`, `onnxruntime_providers_shared`), ещё `msvcp140_atomic_wait.dll` (его импортирует CUDA EP) и `deploy/cuda.toml`. Библиотек NVIDIA в комплекте нет (решение владельца): их ставит `zam-server cuda fetch` в `<exe_dir>/cuda/` по `deploy/cuda.toml` (sha256) или архив `zam-cuda-*`. Без GPU и без CUDA комплект работает на CPU |
  | `zam-server-<ver>-linux-x64-cpu.tar.gz` | `zam-server` (gnu; сборка на старой glibc, минимальная версия указывается в README), `libonnxruntime.so`, `libpdfium.so`, `qdrant/<qver>/qdrant` (musl), `zam` (musl, статический), юнит systemd, конфиг, лицензии |
  | `zam-server-<ver>-linux-x64-gpu.tar.gz` | то же + ORT CUDA EP и `deploy/cuda.toml`; библиотеки NVIDIA — так же, через `zam-server cuda fetch` или `zam-cuda-*` |
  | `zam-cuda-<ver>-windows-x64.zip`, `zam-cuda-<ver>-linux-x64.tar.gz` | каталог `cuda/`: redistributable-библиотеки CUDA 13 и cuDNN 9 по `deploy/cuda.toml` (cudart, cublas, cublasLt, cufft, cudnn; на Linux ещё curand и nvrtc), штампы `.<компонент>.sha256`, `cuda.toml` и лицензии NVIDIA — распаковывается в каталог `zam-server` (получается `<exe_dir>/cuda/`), после чего `cuda fetch` ничего не скачивает; для машин без интернета |
  | `zam-<ver>-windows-x64.zip`, `zam-<ver>-linux-x64.tar.gz` | только CLI |
  | `zam-models-<ver>-<id>.zip` | по архиву на ONNX-модель с `bundle = true` из `deploy/models.toml` (`bge-m3-int8`, `bge-m3-fp16`, `bge-reranker-v2-m3`): `<id>/` с файлами, `LICENSE` и `model.toml` плюс `models.toml` с sha256 — для машин без интернета, распаковывается в каталог моделей; при наличии интернета модели скачивает `zam-server models fetch`. Вместе модели больше 2 ГиБ, поэтому архив не один. Реранкер jina (CC-BY-NC-4.0) в архивы не входит |

  Каждый файл релиза меньше 2 ГиБ (предел GitHub): `cargo xtask package` и publish проверяют это до загрузки.

- **Откуда берутся зависимости.** Все сторонние бинарники скачиваются в CI по закреплённым версиям и SHA-256 из манифестов в `deploy/`: `qdrant.toml`, `onnxruntime.toml`, `onnxruntime-gpu.toml`, `pdfium.toml`, `cuda.toml`, `models.toml`. Без совпадения хэша сборка падает.
- **Проверка перед публикацией (smoke-тест, на обеих ОС, оба flavor).** Комплект распаковывается в чистый каталог и запускается с пустым `data_dir`. Тест проверяет, что Qdrant поднялся, записывает заметку, находит её через FTS и через векторный поиск (на маленькой тестовой модели: 5 заметок, перефраз в top-3 через векторный канал без `degraded`), запускает `zam status` и останавливает сервер. После остановки не должно остаться процессов Qdrant. GPU-комплект проверяется на CPU-раннере: без GPU он обязан работать на CPU; с распакованным `zam-cuda` команда `cuda fetch` не скачивает ничего. Архив `zam-cuda` проверяется отдельно (штампы, состав, формат библиотек). На Windows smoke проверяет, что MSVC runtime, который импортируют библиотеки комплекта, лежит рядом. Загрузка библиотек NVIDIA в CUDA EP проверяется вручную на машине с GPU (раннеров с GPU нет).
- **Версии.** SemVer для всех артефактов. `zam --version` и `GET /health` показывают версию, git-хэш и версии Qdrant и ORT.
- **Лицензии.** В `LICENSES/` комплекта лежат лицензии всех поставляемых в нём сторонних компонентов: Qdrant (Apache-2.0), ORT (MIT), pdfium (BSD/Apache), MSVC runtime (Windows), а также сводка Rust- и npm-зависимостей (`cargo-about`, `license-checker`). Библиотек NVIDIA в комплектах нет, поэтому лицензии CUDA/cuDNN (NVIDIA CUDA EULA, cuDNN SLA) лежат в архиве `zam-cuda` рядом с библиотеками, а `zam-server cuda fetch` печатает ссылку на них. Лицензия каждой модели — `LICENSE` в её архиве `zam-models` и в каталоге модели после `models fetch`.

Qdrant запускается параллельно с загрузкой модели; векторный канал готов, когда готовы оба. Замер M2 (код `d1d2521`): обычный старт — 1,1–2,0 с, выполнено. Первый старт после жёсткой остановки сразу за массовой индексацией 10 тыс. заметок на HDD — 5,4 с (GPU: повтор 39 операций WAL — 3,3 с) и 9,6 с (CPU: чтение сегментов 3,4 с и повтор 7 операций WAL 5,6 с при вытесненном кэше ОС); причина — повтор неподтверждённого WAL Qdrant после `TerminateProcess` (на Windows Qdrant иначе не останавливается) и конкуренция за HDD с чтением модели. Этот сценарий целью 5 с не покрывается; по решению владельца (2026-10-20) исследованы сброс WAL перед остановкой и меньший `wal_capacity_mb` (задача 19 M3, `eval/results/2026-10-25-bench-first-start.md`; RTX 3090, HDD, 10 тыс. заметок, чередование ABBA):
  - **штатная остановка сразу после записи** — внедрено ожидание подтверждения WAL (`qdrant.shutdown_flush_wait_ms = 10000`, `flush_interval_sec = 5`): старт на умолчаниях 2,1–2,5 с на GPU и 2,1–2,3 с на CPU, после индексации каталога с нуля — 2,1 с (GPU, 10 тыс. заметок) и 2,6 с (CPU, 5000), без ожидания — 8,3 с (GPU) и 4,9 / 7,6 с (CPU) (замеры 2026-10-26, `eval/results/2026-10-26-bench-first-start-deferred.md`); цель 5 с выполнена. Подтверждение приходит за 7,4–10,0 с — до предела 10 с запас 0–2,6 с; 6 с после исправления 19b недостаточно. Цена — остановка после записи дольше на 7,1–8,9 с (GPU) и 7,8–9,0 с (CPU); стоп-таймаут менеджера служб — 90 с (§4.3). **С M4 умолчания — `flush_interval_sec = 3`, `shutdown_flush_wait_ms = 14000`** (**решение владельца 2026-10-26**, вариант «3 с» с пределом ожидания на 40 % больше): при 3 с подтверждение приходило за 4,4–8,7 с, цена индексации −1,5…−5,2 % (медиана −3,2 %); контрольный замер «запись → штатная остановка → старт» × 4 на GPU — eval M4, ABBA новых умолчаний (3 с / 14 000) против прежних (5 с / 10 000): подтверждение WAL до 14 с, старт ≤ 5 с;
  - **жёсткая остановка во время записи** — GPU 6,6 / 13,8 с при любом размере блока WAL (`wal_capacity_mb` 32, 8, 4 — эффекта нет), CPU 13,7–18,9 с (медиана 15,2, 2026-10-26); интервал сброса 1 с — 4,7 / 12,0 с ценой индексации −11…−17 % на GPU: не внедрено, сценарий целью 5 с не покрывается — принято владельцем 2026-10-26: после жёсткой остановки поиск временно отвечает FTS с `degraded: true`, данные не теряются; интервал 3 с — индексация −1,5…−5,2 % (ABBA, 2026-10-26), принят умолчанием с M4;
  - **отложенные замеры выполнены 2026-10-26** (`8e30d7d`, `eval/results/2026-10-26-bench-first-start-deferred.md`): ABBA ожидания (без ожидания / 6 с / 10 с) и сценарий «с нуля → остановка → старт» на GPU, профиль CPU на 5000 заметок (`graceful` и `kill`), ABBA скорости для интервала сброса 3 с. Не выполнен прогон на Linux (только тесты CI).
- Замеры — `cargo xtask bench --profile cpu|gpu` (корпус eval с компактными копиями до 10 тыс. заметок, итог в `eval/results/<дата>-bench-<профиль>.md`); сводка и невыполненные цели — в `docs/journal.md`. Замеры M2 сделаны при тёплом кэше ОС (модели и данные читались незадолго до этого); холодный старт после перезагрузки не мерился.

## 18. Качество

### 18.1. Тесты
- **Модульные:** чанкинг (golden-файлы), патчи секций (property-тест: байты вне секции не меняются), позиции и секции `zam-markdown` (сверка с pulldown-cmark, фаззинг), санитизация HTML (набор XSS-векторов), RRF, права, сканер секретов, триггеры, разбор ссылок графа, извлечение текста из документов.
- **Интеграционные:** SQLite во временных каталогах внутри `target/`. Qdrant — нативный бинарник по манифесту `deploy/qdrant.toml`, кэшируется в `target/deps/<платформа>/qdrant/` (`cargo xtask fetch-deps`; там же ONNX Runtime и pdfium), тестовые модели — в `target/models/<id>/` (`cargo xtask fetch-models --test`). Тестовая обвязка запускает его через тот же супервизор, что и в продакшне, с данными в `target/`. Docker для тестов не нужен.
- **e2e:**
  - сценарий CRLF (§1.1);
  - конфликт двух машин: 409, затем патч секции;
  - Qdrant остановлен → деградация;
  - процесс Qdrant убит → автоматический перезапуск; `zam-server` убит → Qdrant завершается вместе с ним (Windows и Linux);
  - смена версии Qdrant через несколько минорных → пересборка storage из `embeddings`;
  - удаление коллекции → reindex из `embeddings`;
  - изоляция Human и vault: нет в Qdrant, в выдаче по токену, в логах; vault нет и в FTS;
  - агент записывает и читает секрет;
  - просмотр и поиск по DOCX/XLSX/PDF;
  - fail-open хуков при выключенном сервере (все пять команд);
  - бюджеты хуков (p95 в пределах §10.3; в CI — с запасом ×2);
  - изменение источника → выжимка кэша `stale`;
  - общее решение: участник видит общий кэш и подсказки решения и свой Knowledge, не видит чужой; после отзыва — ничего из решения.
- **CI:** Windows и Linux.

### 18.2. Eval
- **Набор `eval/`:**
  - корпус заметок и документов на русском и английском;
  - запросы с ожидаемыми источниками, включая запросы на устаревание (ожидается действующий инсайт, а не замещённый);
  - набор для подсказок: релевантно / нерелевантно.
- **Метрики:** recall@5, MRR@10, nDCG@10, доля «вспомнил отменённое», точность подсказок. На M2 набор `eval/` (160 заметок, 197 запросов) и `cargo xtask eval` измеряют первые три; «вспомнил отменённое» добавляется в M3 вместе с инсайтами и `supersedes` (запросы на устаревание в наборе); точность подсказок отложена до M4 (триггеры подсказок) — тогда же в набор добавляется набор «релевантно / нерелевантно». В M3 добавляются также «надёжное выше гипотезы» (`reliable_first`: запросы, где ожидается `theorem`/`axiom`, а не противоречащая `hypothesis`) и chunk-recall@5 на длинных заметках с H4–H6 (лист целиком содержит дословное доказательство) — на них проверяется нарезка по силе границ (§8.2).
- **Гейт качества int8** (`cargo xtask eval --quality-gate`, решение владельца 2026-10-21): «пройден», если нижняя граница 95 % интервала парного бутстрепа (10 000 выборок, фиксированный seed) разности int8 − fp32 не ниже −0,01 и для nDCG@10, и для recall@5. Косинус dense (порог 0,99) и корреляция Спирмена sparse остаются в отчёте как справочные и на вердикт не влияют. С M4 прогоны гейта ищут **точным поиском Qdrant** (`exact = true` в параметрах поиска, только в xtask; в продакшне — HNSW как прежде), порог −0,01 не меняется, гейт прогоняется заново на умолчаниях M4 — **решение владельца 2026-10-26**: так порог мерит квантование, а не шум HNSW-индекса. До нового вердикта гейт информационный, int8 Xenova на CPU остаётся.
- **Eval M4:** набор подсказок `eval/hints.toml` (≥ 60 случаев, половина «релевантно», половина «нерелевантно»: `hint_precision`, `hint_recall`, `silence_rate`; `cargo xtask eval --hints`); сценарии расхода токенов `eval/scenarios.toml` (≥ 15: протокол §9.3, повтор через кэш, «наивный» `mode=chunks` с бюджетом 4000) — базовая линия M4 для цели M6; прогоны на умолчаниях M4 (λ = 0; `rerank=on` с бустами — цель `reliable_first` 1,000 без потери nDCG@10).
- **Итоги M3** (задачи 16–18): набор `eval/` — 182 заметки (22 длинные с H4–H6, 12 FTS-only с `index: false`), 71 insight (14 цепочек замещения, 5 отзывов, 14 пар «`theorem`/`axiom` против `hypothesis`»), 326 запросов. Финальные прогоны на поставляемых умолчаниях (`eval/results/2026-10-25-*-m3-final.*`): FTS — nDCG@10 0,782; гибрид int8 CPU — recall@5 0,847, nDCG@10 0,824; fp16 CUDA — 0,845 / 0,824; с реранком на GPU — 0,906 / 0,869; `cancelled@5` 0,000 (с `include_history` — 1,000, контроль); `reliable_first` 1,000 (без бустов 0,429; с реранком 0,571 — реранк отменяет бусты); chunk-recall@5 0,971; FTS-only recall@5 1,000. Сетки: нарезка (`eval/grid-chunking.toml` и др.) — `chunk_boundary_lambda = 0,5` (с M4 умолчание 0 — решение владельца 2026-10-26, §8.2); веса поиска (`eval/grid-m3.toml`, `grid-m3-kind.toml`) — `w_folder = 0`, `boost_gotcha = boost_failure = 1,05`, бусты `certainty` 1,20/1,10/1,00. Гейт int8 (`eval/results/2026-10-25-quality-gate.*`) — «не пройден»: Δ nDCG@10 −0,0035 [−0,0108…+0,0035], Δ recall@5 +0,0046 [+0,0000…+0,0123]; повторные прогоны того же кода проходят — вердикт зависит от шума HNSW-индекса; int8 Xenova на CPU оставлен (решение M2); критерий — точный поиск Qdrant в прогонах гейта (решение владельца 2026-10-26, выше).
- **Регламент.** Прогон обязателен при изменении чанкинга, весов или моделей. Результаты сохраняются в `eval/results/`.

## 21. Решения исполнителя (на проверку владельцу)
1. UI — Svelte 5. Просмотрщики документов — pdf.js, docx-preview, `calamine` на сервере. Markdown разбирает и рендерит только сервер (comrak + ammonia + syntect); на клиенте Markdown-парсера нет (§15.2).
2. Пространство **Knowledge** для глобальных знаний.
3. Журналы привязаны к решению, а не к сессии.
4. Файл решения — `.zeroaimemory/solution.toml`; области задаются через `area.toml`.
5. Триггеры и хуки для проактивного вспоминания; каждый вид отключается отдельно.
6. Кэш выжимок работает и между сессиями одного решения (по умолчанию включено, отключается настройкой). Чужая выжимка помечается автором и датой. Серверный реранкер по умолчанию выключен.
7. Qdrant входит в поставку нативным бинарником, без Docker; процесс запускает и контролирует `zam-server` (§4.3). При отказе Qdrant поиск деградирует до FTS. Qdrant Edge — экспериментальный адаптер, решение о нём по прототипу на M2.
8. Граф хранится в SQLite (`edges`), без отдельной графовой СУБД.
9. Ссылки на вложения задаются относительно корня пространства.
10. Конкурентная запись — оптимистическая блокировка и патчи секций, без CRDT.
11. При первом запуске создаётся пользователь администратора с собственной памятью и первым токеном.
12. Rules по умолчанию пишет только человек (`rules.agent_write=false`).
13. Идентификаторы хранятся как UUIDv7, наружу отдаются в виде строки base32 из 26 символов.
14. Сервер `zam-server` на Linux собирается под glibc (`x86_64-unknown-linux-gnu`) на образе со старой glibc: ONNX Runtime и pdfium распространяются только под glibc, а musl-бинарник не может их загрузить. `zam` и Qdrant на Linux собираются под musl.
