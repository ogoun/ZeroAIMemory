## 1. Назначение и мотивация

ZeroAIMemory — централизованная, человекочитаемая память для AI-агентов. Это самодостаточный сервис («вещь в себе»): работает без внешних энкодеров и облачных сервисов, все модели хранит и запускает сам. Записи образуют иерархическое дерево, как в Notion или Obsidian. Агенты работают через API по токену. Человек работает через собственный WebUI сервиса.

Какие проблемы решает (со слов владельца):

1. **Агент забывает пройденное.** В долгой работе над большими проектами агент повторяет уже разобранные ошибки. Пример: забывает, что перевод строки в Linux-скриптах делается иначе, чем в Windows, и не помнит, что эту ошибку уже разбирали.
2. **В исследованиях теряются проверенные гипотезы**, и агент заново пробует то, что уже провалилось.
3. **Память нужна везде.** Она должна быть общей для разных сессий, разных машин и разных мест, откуда ведётся один проект.
4. **Нужен мощный и контролируемый инструмент.** Человек видит всё, что агент «помнит», может это исправить и управлять этим.

### 1.1. Главный приёмочный сценарий «CRLF»

Сценарий проверяет решение проблемы 1 и оформляется как автоматический e2e-тест.

1. В проекте A агент сталкивается с ошибкой `/bin/bash^M: bad interpreter`, разбирается и записывает инсайт:
   - вид `gotcha`, область `global` (знания пользователя, а не одного проекта);
   - триггеры `file_glob: **/*.sh` и `error_regex: \^M|bad interpreter`.
2. Через неделю, на другой машине, в проекте B агент собирается создать `deploy.sh`.
3. Перед записью файла хук локально сопоставляет триггер и подмешивает в контекст агента напоминание: «ZeroAIMemory: для *.sh используйте LF; ранее разобрано — <ссылка>». Агент пишет файл правильно.
4. Если ошибка всё же произошла, хук после команды узнаёт текст ошибки и сообщает: «Эта ошибка уже разбиралась: <инсайт>».

Как это устроено, описано в §10.

## 2. Цели, не-цели, анти-цели

### 2.1. Цели
- **G1. Скорость и экономия памяти.** Приоритет №1. Конкретные значения — в §17.
- **G2. Собственный WebUI с полной поддержкой Markdown и медиа.**
  - Просмотр и правка заметок.
  - Встроенные изображения, видео и аудио.
  - Просмотр документов: как минимум DOCX, XLSX и PDF (§15).
  - Источник истины — Markdown, так что содержимое остаётся человекочитаемым и вне сервиса: экспорт в `.md` с вложениями.
- **G3. Централизация.** Один сервер в локальной сети. Агенты с любых машин обращаются к нему напрямую или через внешний прокси. Проект однозначно идентифицируется на всех машинах.
- **G4. Иерархический гибридный RAG** с точными ссылками на источники. Плюс граф связей между записями.
- **G5. Проактивное вспоминание.** Важные знания приходят к агенту автоматически, в момент, когда они нужны. Механизм построен на хуках и триггерах и отключается (§10).
- **G6. Контролируемость.**
  - Каждая запись атрибутирована: кто, когда, в какой сессии и на какой машине.
  - Ревизии сохраняются, их можно откатить; удаление мягкое.
  - Устаревшее не удаляется молча, а помечается.
- **G7. Самодостаточность.** Эмбеддинги и (опциональный) реранк работают на встроенных моделях. GPU используется, если он есть, без него всё работает на CPU. Текст сервер не генерирует.
- **G9. Выжимку делает сам агент, с экономией токенов.** Сервер отдаёт компактный список кандидатов. Агент сам выбирает нужное, дочитывает только необходимое и формирует выжимку. Готовую выжимку агент сохраняет в кэш, чтобы потом использовать повторно (§9.3–9.5).
- **G10. Быстрое подключение агента.** WebUI выдаёт готовый текст для CLAUDE.md или AGENTS.md. Его достаточно вставить, и агент начинает правильно пользоваться памятью (§15.5).
- **G8. Простота для одного владельца** с возможностью завести дополнительных пользователей (§11.4).

### 2.2. Не-цели (v1)
- Совместное редактирование в реальном времени (CRDT). Вместо него — оптимистическая блокировка (§11.3).
- Автоматическое извлечение памяти из диалогов. Запись всегда явная, её делает агент через инструменты; есть режим черновиков на подтверждение (v2, §10.6).
- Отдельная графовая СУБД. Граф хранится в SQLite (§8.5).
- Генеративные модели (LLM) на сервере. Выжимку, сводки и синтез знаний делает агент-клиент.
- TLS, публикация в интернет, OAuth. Сервер слушает локальную сеть; внешний доступ даёт внешний прокси (Traefik и т. п.).
- Офлайн-режим клиента (в v2 — очередь журнальных записей).
- OCR изображений и транскрибация видео и аудио.
- Регистрация пользователей самостоятельно.

### 2.3. Анти-цели: провал, даже если всё «технически работает»
- Знания тихо теряются: запись удалена или перезаписана без следа в истории.
- Содержимое Human или секреты vault попадают в векторный индекс, в выдачу поиска или в логи.
- Хуки заметно тормозят агента (больше 300 мс на событие) или засоряют контекст нерелевантными напоминаниями.
- Только что записанное не находится, и агент не знает почему.
- Сервер нельзя восстановить из бэкапа или переиндексировать.
- Агент «вспоминает» отменённое: отозванные или замещённые инсайты выдаются как действующие.
- Для работы нужен внешний сервис: энкодер, облако, отдельный Python.

## 3. Термины

| Термин | Определение |
|---|---|
| **Администратор** | Владелец сервиса. Логин и пароль задаются в конфигурации сервера. Единственный, кто входит в WebUI. Сам тоже является пользователем со своей памятью. |
| **Пользователь** | Владелец отдельной памяти: база `users/<user_id>.db`. Работает с API по токену. Первый пользователь — сам администратор. Остальных заводит администратор. |
| **Токен** | Bearer-токен доступа к API памяти конкретного пользователя. Прописывается агенту в CLAUDE.md или AGENTS.md. |
| **Пространство (Space)** | Корень дерева в памяти пользователя. Виды: `rules`, `human`, `knowledge`, `solution`. |
| **Решение (Solution)** | Пространство проекта в базе пользователя-владельца. Идентифицируется `agent_solution_id` (GUID) из `.zeroaimemory/solution.toml`. Каталоги с одинаковым GUID делят общую память. Решение может быть общим для нескольких пользователей (§11.6). |
| **Владелец решения** | Пользователь, первым зарегистрировавший `agent_solution_id`: решение лежит в его базе. Подтверждает и отзывает доступ участников; сам участником не бывает. |
| **Участник решения** | Другой пользователь, чей запрос на доступ к решению одобрен владельцем. Видит в базе владельца только пространство этого решения; режим доступа — `rw` или `ro` (§11.6). |
| **Область (Area)** | Подраздел решения, например отдельный сервис в монорепозитории. Это метка записей (§11.2). |
| **Заметка / Папка** | Узлы дерева. Заметка — Markdown-документ с ревизиями и frontmatter. Папка содержит только свёртку своих детей. |
| **Секция** | Часть заметки под заголовком H1–H3. |
| **Чанк** | Фрагмент текста для индекса: лист секции или сводка уровня секции, заметки или папки. |
| **Вложение (Blob)** | Файл: изображение, видео, аудио, документ. Хранится на диске, адресуется по SHA-256. |
| **Журналы** | Встроенные записи решения: `changelog`, `releases`, `insights`. Vault — отдельное хранилище секретов (§7.6). |
| **Эпистемический статус** (`certainty`) | Степень надёжности записи или заметки: `axiom` (установлено человеком), `theorem` (проверено, есть доказательство), `hypothesis` (предположение). Не путать со статусом жизненного цикла insight (§7.5). |
| **Инсайт** | Запись об открытии, провале, ловушке, решении или эксперименте. Имеет статус и триггеры. |
| **Триггер** | Детерминированное условие показа инсайта: маска файла, regex команды, regex ошибки, ключевое слово. |
| **Связь (Edge)** | Типизированное ребро графа между заметками и записями (§8.5). |
| **Сессия** | Сессия агента. Идентификатор берётся у агента (например, `session_id` Claude Code) или генерируется CLI. |
| **L0 / L1 / L2** | Уровни детализации узла: L0 — абстракт до 50 токенов, L1 — обзор до 300 токенов, L2 — полный текст. |

## 4. Архитектура

### 4.1. Принципы
1. **Источник истины — SQLite и файлы вложений.** Qdrant — производный индекс, перестраивается из SQLite.
2. **На сервере нет генеративной модели.** Поиск, триггеры и хуки работают детерминированно. Выжимку из найденного делает агент (§9.3). Сервер хранит её в кэше и следит, чтобы она оставалась актуальной (§9.4).
3. **Запись явная и атрибутированная.**
4. **История только дописывается.** Ревизии и журналы не перезаписываются, удаление мягкое.
5. **Ядро — REST.** MCP, CLI и WebUI — тонкие адаптеры над одним ядром.
6. **Деградация вместо отказа.** Если Qdrant или модель недоступны, запись продолжает работать (векторы ставятся в очередь), а поиск идёт по FTS5 с флагом `degraded: true`.
7. **Самодостаточность.** Модели загружаются и исполняются сервером. Внешние ML-сервисы не нужны.

### 4.2. Компоненты

```
 ┌──────── машина 1..N ─────────┐                  ┌──────────── сервер (LAN) ─────────────────────────────┐
 │ Claude Code / Codex / …      │                  │ zam-server (Rust)                                     │
 │  ├─ MCP (HTTP) ──────────────┼─ HTTP(S) ───┐    │  ├─ REST /api/v1  ├─ MCP /mcp  ├─ WebUI (встроен)     │
 │  └─ хуки ─▶ zam (CLI, Rust) ─┼─ HTTP(S) ───┤    │  ├─ Auth: admin (конфиг) + токены пользователей       │
 │       └─ кэш триггеров       │             │    │  ├─ Store: system.db + users/*.db (SQLite, FTS5)      │
 │ CLAUDE.md: URL + токен       │   [Traefik  ├───▶│  ├─ Blobs: data/blobs/<user>/<aa>/<sha256>            │
 │ .zeroaimemory/solution.toml  │   и т.п.,   │    │  ├─ Docs: извлечение текста, превью DOCX/XLSX/PDF     │
 └──────────────────────────────┘   снаружи]  │    │  ├─ ML: bge-m3, [реранкер] (ONNX; CPU/CUDA)           │
 ┌──── браузер ────┐                          │    │  ├─ Search: FTS5 + Qdrant + граф → RRF → [rerank]     │
 │ WebUI (админ)   │─────────────────────────-┘    │  ├─ Recall: хуки, триггеры, дайджесты                 │
 │  ├─ Cache: выжимки агентов + контроль актуальности     │
 └─────────────────┘                               │  └─ Qdrant client ──gRPC──▶ Qdrant (в составе поставки) │
                                                   └───────────────────────────────────────────────────────┘
```

Qdrant поставляется вместе с сервисом как нативный исполняемый файл, без Docker. Его запускает и контролирует сам `zam-server` (§4.3). Так сохраняется «вещь в себе».

### 4.3. Qdrant: поставка и управление процессом
Подробности и источники — в исследовании 04, §1.

- **Версия.** Версия Qdrant закрепляется в манифесте поставки `deploy/qdrant.toml`: версия и SHA-256 архива для каждой платформы. Стартовая версия — 1.19.2. `qdrant-client` берётся той же минорной версии.
- **Сборки:**
  - `x86_64-pc-windows-msvc` с копией `vcruntime140.dll` рядом с exe;
  - `x86_64-unknown-linux-musl`. Сборку gnu не берём: ей нужна glibc ≥ 2.39.
- **Где лежит бинарник:** `<install>/qdrant/<ver>/qdrant[.exe]`. Если его нет, `zam-server qdrant fetch` скачивает архив с GitHub Releases и проверяет SHA-256.
- **Режимы** (`qdrant.mode`):
  - `managed` (по умолчанию): процесс запускает и контролирует `zam-server`;
  - `external`: подключение к уже работающему Qdrant по URL;
  - `edge` — экспериментальный, под feature-флагом: встраиваемая библиотека `qdrant-edge`, сейчас в бете. Это второй адаптер за трейтом `VectorIndex` (`EdgeIndex`, feature `edge` у `zam-index`; в сервер и комплекты не входит; `qdrant.mode = "edge"` конфиг принимает, но сервер при нём выключает векторный поиск с причиной в журнале). Прототип M2 не прошёл критерий перехода: p95 быстрее в 1,6 раза (нужно ≥ 2×), RSS выше в 2,2 раза (`docs/adr/0001-qdrant-edge.md`). Пересмотр — по условиям ADR, не раньше версии 1.0.
- **Запуск в режиме `managed`:**
  - рабочий каталог — `<data_dir>/qdrant/`, явно: Qdrant подхватывает `config/*` из текущего каталога;
  - `--config-path` указывает на сгенерированный конфиг: `host: 127.0.0.1`, порты из настроек (по умолчанию 6333/6334), `enable_cors: false`, `telemetry_disabled: true`, `logger.format: json`;
  - `QDRANT__SERVICE__API_KEY` — случайный ключ, новый при каждом старте; передаётся только через переменную окружения;
  - `QDRANT_INIT_FILE_PATH` указывает внутрь `<data_dir>/qdrant/`;
  - stdout и stderr Qdrant через pipe попадают в `tracing` с полем `component=qdrant`.
- **Жизненный цикл:**
  - **Привязка к родителю.**
    - Windows: Job Object с `KILL_ON_JOB_CLOSE`, процесс создаётся с `CREATE_SUSPENDED` → назначается в job → `ResumeThread`, флаг `CREATE_NO_WINDOW`;
    - Linux: `PR_SET_PDEATHSIG` из долгоживущего потока-супервизора.
  - **Защита от второго экземпляра.** Свой лок-файл на `<data_dir>/qdrant/` и pid-файл. Осиротевший процесс находится по pid-файлу и порту и завершается.
  - **Готовность.** Сначала `/readyz`, затем статус коллекции через клиент. Версия из `GET /` сверяется с манифестом. Qdrant запускается параллельно с загрузкой модели эмбеддингов (если модель установлена): готовность Qdrant не ждёт чтения модели с диска (§17).
  - **Падение и поиск.** При состоянии `Ready` поиск сверяется с живостью процесса по pid (проверка ОС, без обращения к Qdrant): между смертью процесса и сменой состояния супервизором запрос не уходит в закрытый порт. Соединение с Qdrant ограничено 300 мс: на Windows отказ соединения с закрытым портом localhost приходит лишь через ~2 с на попытку, и до этого правила первый поиск после падения ждал 2–4 с **[решение исполнителя, задача 15 M2]**.
  - **Перезапуск при падении.** Экспоненциальная задержка от 1 до 60 с с jitter. После 5 падений за 10 минут — circuit breaker: сервер работает в режиме деградации (§4.1 п. 6) и показывает алерт в WebUI и в `/index/status`.
  - **Остановка.**
    1. Прекратить отправку записей; все записи идут с `wait=true`.
    2. Linux: SIGTERM, ждать 10 с, затем SIGKILL. Windows: `TerminateProcess` — Qdrant на Windows слушает только Ctrl+C, а целостность обеспечивают его WAL и пересборка из SQLite.
- **Согласованность с SQLite.** Задания `index_jobs` работают как outbox: задание закрывается только после подтверждённого upsert. Повтор идемпотентен, потому что id точки детерминирован.
- **Обновление Qdrant.** Пропускать минорные версии формат хранения не позволяет. Индекс у нас производный, поэтому если новая версия старше хранилища больше чем на одну минорную, при откате или при ошибке миграции сервер удаляет `<data_dir>/qdrant/storage` и пересобирает индекс из таблицы `embeddings`, без инференса. Это событие пишется в аудит.
- **Ресурсы.** Пределы памяти и потоков Qdrant задаются в конфиге (`qdrant.max_search_threads`, `qdrant.optimizer_threads`), чтобы он не отбирал CPU у инференса.

## 5. Стек

### 5.1. Язык — Rust (stable, edition 2024). Утверждён владельцем.
Почему Rust:
- Наилучшие скорость и расход памяти.
- `ort` и `tokenizers` позволяют запускать bge-m3 внутри процесса и получать сразу три представления: dense, sparse и ColBERT.
- Официальные зрелые библиотеки: `qdrant-client`, `rmcp`, `rusqlite` (`bundled`, FTS5).

### 5.2. Библиотеки
Выбор проверен аудитом 2026-10-18 (исследование 04): версии, активность, лицензии, альтернативы. В таблице указаны версии на дату аудита. При старте реализации они фиксируются в `Cargo.lock` и `package-lock.json`. Библиотеки с нестабильным API закрепляются точной версией (`=`) и обновляются отдельной задачей: это `ort`, `tokenizers`, `qdrant-client`, `process-wrap`, `rmcp`, `jiff`, `qdrant-edge`. Спорные места подтверждаются прототипом на том этапе, где библиотека нужна.

### 5.3. Markdown на сервере: правила `zam-markdown`
- **Включённые расширения comrak:** GFM (таблицы, задачи, зачёркивание, автоссылки, tagfilter-эквивалент через ammonia), сноски, `wikilinks_title_after_pipe`, alerts, `math_dollars` + `math_code`, `front_matter_delimiter = "---"`, `header_id_prefix`, `sourcepos`.
- **Свои проходы по AST:**
  - callout в стиле Obsidian (`> [!info]-`, произвольные типы и сворачивание): comrak знает только 5 типов GitHub;
  - нормализация `[[Заметка#Секция|текст]]` в цель и якорь;
  - перевод `sourcepos` (строка и колонка в байтах) в байтовые оффсеты через таблицу начал строк. Учитываются CRLF и BOM.
- **Секция** — диапазон от заголовка уровня N до следующего заголовка уровня ≤ N на верхнем уровне документа. Заголовки внутри списков и цитат секций не образуют, setext-заголовки учитываются.
- **PATCH** — только байтовая замена фрагмента исходника (`splice`), затем повторный разбор и проверка. Обратная сериализация AST (`format_commonmark`) запрещена. Инвариант: байты вне изменённого диапазона совпадают с исходными.
- **Тесты:** golden-файлы, property-тесты инварианта PATCH и фаззинг (`cargo-fuzz`) разбора и позиций. Inline-позиции comrak исторически были хрупкими, поэтому в тестах их сверяют с `pulldown-cmark`, у которого точные байтовые диапазоны (dev-зависимость).
- **Один разбор — все потребители:** секции, чанки, оглавление, ссылки для графа, HTML для WebUI. HTML рендерится с `data-sourcepos`, проходит `ammonia` и кэшируется по `(content_hash, render_version)`.

## 6. Модель данных

### 6.1. Каталог данных

```
<data_dir>/
  system.db                      # пользователи, токены, аудит, настройки, реестр решений и доступа, ключи Vault
  users/<user_id>.db             # вся память пользователя, включая его решения
  blobs/<user_id>/<aa>/<sha256>  # вложения (дедупликация в пределах пользователя)
  previews/<user_id>/<sha256>/…  # производные: миниатюры, HTML-превью документов (кэш, можно удалить)
  models/<name>/…                # ONNX-модели + sha256-манифест
  qdrant/                        # данные управляемого Qdrant (если qdrant.managed)
  logs/  backups/
```

Решение лежит в базе пользователя-владельца (пространство `solution`), отдельных файлов у решения нет. Участник общего решения работает с этой базой через сервер и видит в ней только пространство решения (§11.6); реестр решений и разрешения хранятся в `system.db` **[решение владельца 2026-10-21]**.

### 6.2. `system.db`

```sql

### 6.3. `users/<user_id>.db`

Идентификаторы — UUIDv7. Время — UTC, ISO-8601.

- **Состав базы пользователя:** Rules, Human, Knowledge (в том числе журнал insights с `scope=global`), его решения (пространства `solution`: заметки, ревизии, журналы, граф, чанки, индекс) и Vault. Решение, которым владеет другой пользователь, в базе участника не хранится: сервер обращается к базе владельца (§11.6).
- **Атрибуция.** `revisions.user_id`, `entries.user_id` и `entry_revisions.user_id` — пользователь, чьим токеном сделана запись; `NULL` означает владельца базы (так записаны данные M1–M2).
- **Эпистемический статус.** `nodes.certainty` (заметки, из frontmatter), `entries.certainty` (insight), в `entry_revisions` — `certainty` и `reason` (причина смены статуса или `certainty`) (§7.5).
- **Vault** — отдельные таблицы `vault_items`/`vault_revisions` вместо `entries.kind='vault'` **[решение исполнителя]**: значения секретов структурно вне конвейера индексации (у них нет чанков, FTS и заданий индексации).
- **Рёбра — только внутри одной базы.** Цель в другой базе (личная память участника и решение в базе владельца) отклоняется (422): межбазовые связи — не в M3. Внутри базы владельца рёбра между его пространствами допустимы, но участнику рёбра за пределы пространства решения не видны (§8.5).
- Размещение кэша выжимок, сессий и `usage` для общего решения — этап M4 (§9.4).

### 6.4. Qdrant

Одна коллекция `zam_chunks`.

- **Именованные векторы:**
  - `dense` — 1024, cosine, HNSW (m=16). Оригиналы хранятся на диске (`memory: cold`, mmap), квантованная int8-копия закреплена в RAM (`pinned`), поиск идёт по int8 с пересчётом по оригиналам;
  - `sparse` — веса bge-m3, без IDF-модификатора;
  - `colbert` — в v1 не хранится: на 1 млн чанков это сотни гигабайт. Вариант для v2 — пересчёт ColBERT-векторов на лету для top-k кандидатов или хранение `cold`, uint8, без HNSW.
- **Оценка памяти Qdrant** на 1 млн чанков: около 1,5–2,5 ГБ RAM, около 5 ГБ на диске.
- **Payload и индексы:** `user_id` (`is_tenant`; владелец базы), `space_id`, `space_kind`, `solution_guid`, `node_id`, `entry_id`, `path_ancestors`, `area`, `level`, `kind`, `insight_kind`, `status`, `certainty`, `tags`, `updated_at`, `rev`, `text_hash`.
- **Область поиска.** Тенант точки — пользователь-владелец базы (`user_id`). Общее решение лежит в базе владельца, поэтому фильтр поиска — дизъюнкция областей: «`user_id` пользователя и его пространства» ИЛИ «`user_id` владельца и `space_id` решения» для каждого доступного общего решения (§11.6); `path_prefix` применяется внутри каждой области. Пустой набор областей даёт пустую выдачу **[решение владельца 2026-10-21]**; область без пространств тоже ничего не пропускает (а не «все пространства владельца»), и так же ведут себя подсчёт и удаление по области **[решение исполнителя]**.
- **Новые поля payload** (`entry_id`, `status`, `insight_kind`, `certainty`) добавляются в существующую коллекцию без пересборки; payload-индексы создаются для них и ещё для `kind` и `area` (`metadata.schema` остаётся 1). Фильтр статуса — исключающий («не `superseded` и не `retracted`»), поэтому точки без поля `status` (заметки, папки, точки M2) проходят. Фильтр `certainty` включается, только если запрошен.
- **Никогда не попадают в Qdrant:** пространство `human`, значения vault, узлы с `index: false`.
- **Идентификатор модели** (`model_id`) хранится в метаданных коллекции. Если он расходится с текущим, векторный поиск запрещается до переиндексации, и поиск явно сообщает об этом.

### 6.5. Вложения и ссылки
- **Хранение.** Вложения узла общего решения лежат в каталоге владельца базы; участник получает их через сервер в пределах пространства решения. Атомарная запись (временный файл → rename), подсчёт ссылок `refcount`. Сборщик мусора удаляет блобы с `refcount=0` старше 7 дней.
- **Ссылка в Markdown** относительна от корня пространства: `_attachments/<sha256[0..16]>/<имя>`. Сервер разрешает её через таблицу `attachments`. **[решение исполнителя]**
- **Встраивание** — стандартный синтаксис `![подпись](_attachments/…)`. Вид определяется по MIME (§15.2).
- **Лимит** по умолчанию 200 МБ на файл, настраивается. Отдача поддерживает `Range` (видео, аудио, большие PDF).

| **Solutions/** | Агент и человек; у общего решения — участники с режимом `rw` (§11.6) | Читает и пишет; у участника `ro` только читает | Да |

**Knowledge** — глобальные знания пользователя, общие для всех проектов: инсайты с `scope=global` (сценарий CRLF), приёмы, особенности окружения. В нём есть журнал `insights` (записи с `scope=global`) и личный Vault. Участникам общих решений Knowledge, Rules, Human и Vault владельца не видны. **[решение исполнителя]**

### 7.2. Встроенные журналы решения
При регистрации решения создаются `Changelog`, `Releases` и `Insights`; Vault журналом решения не является: он лежит в базе пользователя (§7.6). В дереве они выглядят как закреплённые виртуальные заметки. Их представление генерируется из таблицы `entries`. Под ними лежит обычное дерево заметок решения.

Журналы привязаны к **решению**, а не к сессии. Сессия хранится в каждой записи как атрибут. **[решение исполнителя]**: в наброске написано «для каждой сессии», но тогда память раздробилась бы.

### 7.3. Changelog — история изменений проекта
- **Поля:** `title`, `body` (Markdown), `data: {kind: feat|fix|refactor|docs|research|ops|other, refs: {commits, files, notes, issues}}`, `area`; атрибуция и дата проставляются автоматически.
- **Хранение.** Журнал только дописывается. Правки записей сохраняются в `entry_revisions`.
- **Отличие от ревизий заметок** (`revisions`): ревизии — это изменения самой памяти, а changelog — изменения в проекте.

### 7.4. Releases — история релизов
- **Поля:** `data: {version, date, git_tag?}`, `body` — заметки к релизу.
- **Сравнение** `GET …/releases/{id}/compare?with=prev|<id>` возвращает три части:
  1. записи changelog между релизами, сгруппированные по `kind`;
  2. дифф заметок к релизам;
  3. список коммитов, если CLI передал его из `zam release --from-git`. Сервер к git не обращается.
- **Без релизов** журнал пуст, сравнение недоступно.

### 7.5. Insights — открытия, провалы, эксперименты

```jsonc
{
  "kind":   "gotcha" | "failure" | "discovery" | "decision" | "experiment" | "pattern",
  "scope":  "solution" | "global",               // global → пространство Knowledge
  "status": "active" | "revisit" | "superseded" | "retracted",
  "certainty": "axiom" | "theorem" | "hypothesis",   // эпистемический статус; по умолчанию hypothesis у агента
  "title":  "Bash-скрипты должны иметь LF",
  "body":   "markdown: контекст, причина, как правильно, как проверить",
  "data": {
    "experiment": {"hypothesis": "…", "method": "…",
                   "result": "confirmed" | "refuted" | "inconclusive",
                   "metrics": {}, "revisit_if": "условие пересмотра"},
    "evidence": {"checked": "что проверено", "method": "как проверено", "result": "результат"}   // обязателен для theorem (§7.5)
  },
  "triggers": [{"type": "file_glob", "pattern": "**/*.sh", "tools": ["Write","Edit"]},
               {"type": "error_regex", "pattern": "\\^M|bad interpreter"}],
  "tags": ["bash", "line-endings"],
  "links": [{"type": "relates_to", "target": "node:<id>"}]
}
```

- **Создание:** `POST /spaces/{space}/entries` с `kind: "insight"`; вид инсайта — `data.kind`. `scope: global` пишет в Knowledge пользователя запроса (пространство пути при этом проверяется на чтение: отказ или отзыв доступа к решению — 403); без `scope` действует пространство пути — решение или Knowledge. Rules и Human — 422, если запись туда разрешена правами; иначе 403/404 по правилам доступа (§7.1). Содержимое insight в статусе `superseded` или `retracted` (заголовок, тело, `data`, теги, область, триггеры) не правится — 409: история только дописывается, для исправления создаётся новая запись **[решение контроллера]**.
- **Дедупликация при записи.**
  - Признак дубля: dense-косинус ≥ `insights.dedup_threshold` (0,90) с действующими (`active`, `revisit`) инсайтами той же области того же пространства или совпадение нормализованного заголовка (нижний регистр, всё кроме букв и цифр — пробел).
  - Векторная проверка: `embed_query(title + "\n" + body)` (усечение по модели) → ближайшие точки insight пространства без `superseded`/`retracted`; кандидаты перепроверяются по SQLite.
  - Сервер отвечает `409 /problems/possible-duplicate` с `candidates` (до 5: `id`, `title`, `status`, `certainty`, `reason: title | vector`, `score`) и `dedup: "full" | "degraded"`. Клиент выбирает: дописать к существующему (`PATCH {append_body}`), заменить его (`supersedes_id`) или записать всё равно (`force`).
  - Если модель недоступна, проверка идёт только по заголовку, а в ответе (и в успешном) `dedup: "degraded"`; при `force`, `supersedes_id` и повторе по `Idempotency-Key` — `dedup: "skipped"` **[решение исполнителя]**.
- **Замещение** (`POST /entries/{id}/supersede` или `supersedes_id` при создании). Старая запись получает `superseded` и `superseded_by_id`, новая — `supersedes_id`; всё одной транзакцией. Ничего не удаляется. Уже `superseded` или `retracted` — 409.
- **Отзыв** (`POST /entries/{id}/retract {reason}`, `retracted`) — отдельная операция с обязательной причиной (пустая — 422). Отзыв `superseded` разрешён: замещённый вывод тоже может оказаться ошибочным, а отзыв ничего не удаляет **[решение исполнителя]**.
- **`revisit`** — «пересмотреть при новых идеях». Такие записи показываются отдельным списком в дайджесте старта сессии.
- **Переходы статуса правкой** (`PATCH {status}`) — только `active ↔ revisit`; `superseded`/`retracted` правкой не ставятся, и из них статус не возвращается — 422 **[решение исполнителя]**.
- **Триггеры** (§10.3) задаются при создании и замещении или `PATCH {triggers}` (набор заменяется целиком): `file_glob` (`globset`), `command_regex` и `error_regex` (`regex` без обратных ссылок и lookaround, до 1 МиБ), `keyword` (1–200 символов); шаблон до 1000 символов, `tools` до 16, триггеров до 32 на запись. Ошибка — 422 `triggers[i]: …`. Действующие триггеры (`active`, `revisit`) отдаёт `GET /triggers?solution=` с `ETag`.
- **Выдача.** Поиск по умолчанию возвращает `active` и `revisit`. Флаг `include_history` добавляет остальные статусы.
- **Перед исследованием** агент по инструкции (§14.2) проверяет `experiment` и `failure` по теме.

#### Эпистемический статус (`certainty`) **[решение владельца 2026-10-21]**
`status` описывает жизненный цикл insight, `certainty` — насколько записи можно доверять. Поле есть у insight и у заметок (во frontmatter: `certainty:` и `evidence:`).
- **`axiom`** — установлено человеком; опора для остальных выводов. **`theorem`** — проверено, есть доказательство: `data.evidence {checked, method, result}`, все три поля непустые. **`hypothesis`** — предположение или единичное наблюдение без проверки; значение по умолчанию для записей агента. Insight человека по умолчанию создаётся как `axiom` **[решение исполнителя]**.
- **Кто автор.** Человек — сессия администратора в WebUI или «человеческий» токен (§11.4); любой другой токен — агент.
- **Права:**

  | Действие | Агент | Человек |
  |---|---|---|
  | создать `hypothesis` | да | да |
  | создать `theorem` | только с `evidence` | да |
  | создать `axiom` | нет (403) | да |
  | `hypothesis → theorem` | только с `evidence` и `reason` | да, с `reason` |
  | `theorem → hypothesis` (пересмотр) | да, с `reason` | да, с `reason` |
  | `* → axiom` | нет (403) | да, с `reason` |
  | любое изменение записи или заметки `axiom` (правка, смена `certainty`, supersede, retract, delete, move) | нет (403) | да |
  | снять `certainty` | только у `hypothesis`, с `reason` | да |

  Нарушение прав — 403, нехватка `evidence` или `reason` — 422 (`/problems/certainty`, поле `code`: `axiom-requires-human` | `evidence-required` | `reason-required` | `invalid-transition`).
- **Где проверяется** **[решение исполнителя]**: в транзакции хранилища каждой операции, меняющей запись или заметку, по текущему состоянию цели — создание, правка (PUT, PATCH, `revert`), смена `certainty`, триггеры, supersede, retract, delete, restore, move (вместе с поддеревом), вложение. Конфликт ревизии (`If-Match`/`base_rev`, 409) проверяется раньше прав; при актуальной ревизии запрос агента к `axiom` — 403, перенос — 403 раньше занятости пути (409). `theorem` агента требует полного доказательства и в итоговом состоянии любой правки (свежесть не проверяется). Ключ `certainty`/`evidence` в нераспознаваемом написании (в кавычках, с заглавными) статус не задаёт, ответ записи несёт `warnings: ["certainty_not_recognized"]`. Дозаполнение `nodes.certainty` при обновлении базы (живые и удалённые заметки) оставляет `axiom` только заметкам, текущая ревизия которых записана человеком, иначе — `hypothesis`. Внутренние операции (`author_kind = system`) имеют права агента. Снятие статуса и человеком — с `reason` (каждая смена — ревизия с причиной); у заметки без статуса установка `certainty:` — переход (причина; агенту для `theorem` — `evidence:`). Доказательство заметки — непустой `evidence:` (свободный текст).
- **История.** Каждая смена `certainty` — новая ревизия с `reason`; у заметок причина — сообщение ревизии (обязательно).
- **Пример.** Агент прочитал статью, применил метод, метод не сработал: записывает `hypothesis` «метод X нерабочий». Перепроверка либо подтверждает вывод (`→ theorem` с `evidence`), либо выясняется, что параметры были неверны: запись замещается новой (`supersede`) или отзывается с причиной (`retract`). Устаревшее не удаляется и не выдаётся как действующее.
- **Поиск.** Статус виден в карточках и элементах выдачи, `filters.certainty` ограничивает выдачу, а бусты `axiom > theorem > hypothesis` поднимают надёжное выше предположения при равной релевантности (§9.2).

### 7.6. Vault — креды, токены, ссылки
Агент записывает секреты и сам ими пользуется. Администратор видит всё.

- **Поля:**
  - открытые: `title` (имя), `data: {type: password|token|ssh_key|connection_string|url|repo|note, username?, url?, description?}`;
  - шифрованное: `secret` (XChaCha20-Poly1305).
- **Ключи.** Мастер-ключ сервера берётся из файла `data_dir/master.key` (создаётся при первом запуске, права 0600) или из `ZAM_MASTER_KEY`. На каждого пользователя есть свой ключ данных, зашифрованный мастер-ключом. Бэкап без мастер-ключа не раскрывает секреты. Ключ резервируется отдельно — об этом предупреждают документация и WebUI.
- **Формат** **[решение исполнителя, задача 12 M3]**: блоб `0x01 ‖ nonce(24) ‖ ciphertext‖tag`, AAD значения — `zam-vault-v1 ‖ user_id ‖ item_id ‖ rev` (id — 26 символов, `rev` — 8 байт big-endian), ключ пользователя обёрнут с AAD `zam-ukey-v1 ‖ user_id`, `vault.key_check` — шифротекст `zam-key-check`. Каждая ревизия — свой шифротекст (правка без нового значения перешифровывает прежнее). Файл ключа — `[vault] master_key_file` (по умолчанию `data_dir/master.key`, base64), `ZAM_MASTER_KEY` важнее файла; файл создаётся атомарно и без перезаписи (`master.key.tmp` → жёсткая ссылка, fsync каталога на Linux) до записи `vault.key_check`; права — 0600 на Linux, защищённый DACL (владелец, SYSTEM, администраторы) на Windows. Блокировка — 503 на все эндпоинты Vault. Значение — до 64 КиБ; прежние ревизии раскрывает только администратор (`GET /vault/{id}/revisions?reveal=1&rev=N`). В CLI адрес ресурса — `--link` (`--url` — адрес сервера).
- **Vault и общие решения.** Vault каждого участника лежит в его базе пользователя и привязан к `agent_solution_id` (`vault_items.scope='solution'`); он не разделяется никогда: ни владелец, ни другие участники не видят записей друг друга, администратор видит всё. Записи без привязки (`scope='knowledge'`) — личный Vault пользователя, глобальный для всех проектов.
- **Проверка мастер-ключа.** Первое же шифрование записывает в `settings` проверочный шифротекст (`vault.key_check`). Если ключ не подходит или файла ключа нет при существующих ключах пользователей, Vault блокируется (503, `vault-locked`; причина — в ответе и в журнале сервера одной строкой WARN), остальной сервер работает, а новый ключ молча не создаётся: иначе потеряются прежние секреты.
- **Доступ агента.** С токеном пользователя агент читает и пишет vault своего пользователя:
  - `GET …/vault` — список записей и поиск по открытым полям (`title`, `url`, `description`), без значений;
  - `GET /vault/{id}?reveal=1` или `memory_vault_get(name)` — значение.
- **Индексация.** Значения нигде не индексируются: ни в FTS, ни в Qdrant. Поиск по vault идёт только по открытым полям через отдельный эндпоинт.
- **Аудит.** Каждое раскрытие записывается: токен, сессия, машина, время.
- **WebUI.** Значения скрыты маской, раскрытие по клику.
- **Сканер секретов.** Перед индексацией любой заметки или записи сервер ищет похожее на секреты: известные префиксы ключей, высокоэнтропийные строки, `password=` и т. п. В индексе найденное заменяется на `‹secret›`. Ответ на запись содержит предупреждение `secrets_detected` с предложением перенести значение в vault. Исходный текст заметки не меняется.

## 8. Индексация

### 8.1. Конвейер

```
запись узла / записи журнала
  └─ синхронно, одна транзакция SQLite:
       ревизия + узел + разбор (comrak) → секции → чанки + context_prefix → chunks + FTS5
       + auto-L0/L1 + рёбра из ссылок + задание index_jobs
вложение
  └─ синхронно: blob на диск + attachments; асинхронно: извлечение текста → чанки(level=attachment) → FTS5
воркеры эмбеддинга (асинхронно, низкий приоритет):
  ├─ чанки без вектора: embeddings по (text_hash, model_id) → при промахе — инференс батчами
  ├─ upsert/delete в Qdrant
  ├─ свёртка L0 вверх по дереву (дебаунс 2 с)
  ├─ инвалидация answer_cache (§9.4)
  └─ index_state = 'indexed'
```

- **Синхронная часть.** Чанкинг и FTS выполняются в транзакции записи. Сразу после записи заметка находится по словам.
- **Статус индексации.** Ответ записи содержит `index_state`. Ответ поиска содержит `pending_count` — сколько записей в этой области ещё ждут векторизации.
- **Хранилище эмбеддингов.** Таблица `embeddings` в SQLite: одинаковые тексты не прогоняются через модель повторно, а `reindex` пересобирает Qdrant без инференса. Модель снова прогоняется только при смене `model_id`. Ключ кэша — blake3 эмбеддируемой строки (префикс + текст, §8.2 п. 6) — хранится в `chunks.embed_key`; строки, на которые не ссылается ни один чанк, удаляет сборка мусора (после reindex базы и раз в час в простое). Служебные эмбеддинги (предложения L0, L0 папки) принадлежат своему узлу (`embeddings.owner`).
- **Reindex** (`POST /admin/reindex`, `zam-server reindex`): без `full` — точки области удаляются и пишутся из `embeddings` пачками по 256, заметки без эмбеддинга получают задания; с `full` — перечанковка и задания. Выполняет воркер последовательно с заданиями; коллекция другой модели пересоздаётся. Прерванный reindex повторяется при следующем запуске. База пользователя, повреждённая навсегда или не открывшаяся 5 раз при пересборке после стирания хранилища Qdrant, исключается (аудит `index.rebuild_skipped`, видна в `/index/status`); остальные пересобираются. Исключение хранится в `system.db` (переживает перезапуск) и снимается, когда база снова открылась и ей поставлен reindex. Обход всех баз (статус администратора, reindex) неоткрывающиеся базы пропускает и называет.
- **Приоритеты.** Эмбеддинг запросов идёт в отдельной ONNX-сессии с зарезервированными потоками (на CPU по умолчанию 2). Индексация уступает между батчами: батч инференса — не больше 2048 токенов, и перед каждым батчем индексация ждёт, пока выполняются эмбеддинги запросов (не дольше 100 мс) — на GPU сессии делят одно устройство, и батч 8192 токенов задерживал эмбеддинг запроса до 74 мс (p95) **[решение исполнителя, задача 15 M2]**. Цели §17 для поиска должны выполняться при полной очереди индексации.
- **Надёжность.** Задания переживают перезапуск. Повторы идут с экспоненциальной задержкой. После 5 неудач задание получает статус `failed` и становится видно в `/index/status` и в WebUI.

### 8.2. Чанкинг Markdown
1. **Frontmatter** (YAML) уходит в метаданные: `tags`, `description`, `index: false`, `l0`, `relations`.
2. **Секции** — по H1–H3. H4–H6 остаются внутри своей секции, но входят в путь заголовков листа (`H1 > H2 > H3 > H4`) и тем самым в `context_prefix`.
3. **Блоки** кода, таблицы, списки и callout не разрываются. Блок длиннее 800 токенов режется по строкам или элементам, и у каждой части повторяется заголовок блока.
4. **Листовые чанки** — 300–500 токенов, максимум 800. Перекрытие — 1–2 предложения, только внутри секции. Лист не кончается заголовком H4–H6 (заголовок уходит в следующий лист вместе со своим содержимым) и не отрывает вводную фразу на «:» от следующего блока (код, список, таблица).
5. **Короткие секции** (меньше 100 токенов) склеиваются с соседними.
6. **`context_prefix`.** К каждому чанку добавляется строка `[<space>/<path>] <заголовок заметки> > <путь заголовков> | теги`. Она участвует в эмбеддинге и FTS, но клиенту не возвращается. Это детерминированный аналог Contextual Retrieval.
7. **Записи журналов** — один документ на запись. Длинные режутся по тем же правилам.
8. **Вложения:**
   - PDF — текстовый слой постранично;
   - DOCX — абзацы с заголовками;
   - XLSX/XLS/ODS/CSV — по листам, блоками строк с шапкой;
   - PPTX — текст слайдов;
   - TXT, MD, исходный код — как есть.

   Чанки вложений получают `level=attachment` и `locator` (страница, лист и диапазон, слайд). Изображения, видео и аудио индексируются по имени файла и подписи.

Пороги задаются в конфигурации (`[index] chunk_target_min|chunk_target_max|chunk_hard_max|chunk_merge_below|chunk_overlap_sentences|chunk_boundary_lambda|chunk_cohesion|chunk_prefix_l0`), значения по умолчанию подбираются на eval (§18.2): на M2 сетка подтвердила 300–500/800 и перекрытие в одно предложение. Ключи `chunk_boundary_lambda` (сила границ при выборе разреза, 0 — жадная упаковка M2), `chunk_cohesion` (лексическая связность в длинных абзацах) и `chunk_prefix_l0` (L0 заметки в `context_prefix`) — эксперименты, их умолчания выбираются по eval M3 (§18.2) и без выигрыша остаются выключенными. Правила H4–H6 и «:» меняют `embed_key` затронутых чанков и требуют `reindex --full`. Новые пороги действуют на заметки, записанные после перезапуска; записанные ранее перенарезает `reindex --full`.

Токены считает токенизатор модели (`tokenizer.json`), в том числе без ONNX Runtime. `chunk_hard_max` не больше окна модели (`max_tokens_passage`) минус 64 токена на `context_prefix` и спецтокены (bge-m3: 960); пороги больше уменьшаются с предупреждением в журнале **[решение исполнителя, M2]**. Без установленной модели токены оцениваются (символы / 3,5); база с такими чанками отмечается (`meta.chunked_approx`), и при первом её открытии с точным счётчиком все живые заметки перенарезаются в фоне с повторной индексацией **[решение исполнителя, M2]**.

### 8.3. Уровни L0/L1/L2 и иерархия
- **Заметка.** L0 — ручной `l0` из frontmatter. Если его нет, используется самое информативное предложение заметки: оно выбирается экстрактивно, по близости к центроиду эмбеддингов секций, и обрезается до 50 токенов. Пока векторов нет, берётся первый абзац. L1 — оглавление плюс ключевое предложение каждой секции, до 300 токенов.
- **Папка или пространство.** Свёртка L0 детей, до 50 строк. Если строк больше, они ранжируются по `usage` и свежести.
- **Сводки от агента.** При записи заметки агент может передать `l0` (одно предложение). Инструкция (§14.2) это рекомендует. Такая сводка сохраняется с `l0_source=agent`, и сервер не перезаписывает её автоматикой, пока не изменится содержимое. Если содержимое изменилось, а новая сводка не пришла, `l0` снова вычисляется автоматически.
- **Индексация уровней.** L0 и L1 заметок и секций индексируются как отдельные чанки (`level=note|section|folder`). Это позволяет широким запросам находить тему целиком. Точки папок (`folder`) пишутся в Qdrant с M2, поиск по ним (§9.2, канал `w_folder`) — с M3.
- **Чтение по уровню.** `GET /nodes/{id}?tier=L0|L1|L2` экономит контекст агента.

### 8.4. Модели (встроенные)

| Роль | По умолчанию | Примечание |
|---|---|---|
| Эмбеддинги | **bge-m3**, ONNX, int8 (CPU) / fp16 (GPU) | Один проход даёт dense и sparse, плюс ColBERT опционально. CLS-токен в ColBERT отбрасывается, sparse собирается max-pool по token-id без спецтокенов. Источники весов: CPU — `Xenova/bge-m3` `onnx/model_int8.onnx` (per-channel QInt8), GPU — `Xenova/bge-m3` `onnx/model_fp16.onnx`; `tokenizer.json` оттуда же; sparse-голова `sparse_linear.pt` — из оригинала `BAAI/bge-m3`. Пулинг и sparse считаются в Rust по `last_hidden_state`. Int8 сверяется с fp32 `BAAI/bge-m3` гейтом качества `cargo xtask eval --quality-gate` (исследование 05, §3.3; §18.2): по поиску ухудшения int8 относительно fp32 не обнаружено (95 % интервал парного бутстрепа разности recall@5 и nDCG@10 включает ноль), а порог косинуса dense 0,99 не прошёл ни один проверенный динамический int8 (Xenova — 0,978, собственный per-channel — 0,984); int8 только весов проходит, но втрое медленнее. Не проверялись: mixed precision (`nodes_to_exclude`), статическое QDQ с калибровкой, `gpahal/bge-m3-onnx-int8`. Оставлен Xenova int8 — **решение владельца, 2026-10-20** (с M3 критерий гейта — по поисковым метрикам, §18.2: нижняя граница 95 % интервала парного бутстрепа Δ nDCG@10 и Δ recall@5 (int8 − fp32) ≥ −0,01; косинус dense и Спирмен sparse — справочно, решение владельца 2026-10-21). Векторы int8 и fp16 — разные `model_id` |
| Реранкер (опционально, по умолчанию выключен) | CPU: `jina-reranker-v2-base-multilingual` (278M, int8) — **CC-BY-NC-4.0, не входит в `zam-models`, загрузка только с согласием** (`--accept-nc-license`); граф квантует активации динамически, поэтому пары считаются по одной, параллельно в `ml.rerank_sessions` сессиях (по умолчанию 0 — авто: до 2, у каждой своя копия весов ~0,3 ГБ); GPU: `bge-reranker-v2-m3` (Apache-2.0, ONNX-экспорт `onnx-community`, fp16), пары — одним батчем | Основной реранк делает агент (§9.3). Модель нужна для поиска в WebUI и для агентов, которые просят `rerank=on`. Jina оставлена решением владельца; её лицензия разрешает только некоммерческое использование. Финальный выбор — по eval |

- **Исполнение.** `ml.device = auto|cpu|cuda`. При `auto` сервер пробует CUDA (NVIDIA), если она недоступна — CPU. Выбор и причина пишутся в лог и в `/index/status`. Других GPU-исполнителей (DirectML и т. п.) нет — решение владельца. Вариант модели для CPU (int8) на GPU не запускается, вариант для GPU (fp16) — на CPU: если CUDA недоступна, а int8 не установлена (или fp16 задана явно при `ml.device = cpu`), сервер работает в режиме FTS-only с причиной `gpu_model_on_cpu` и подсказкой `zam-server models fetch --device cpu` — векторы CPU и CUDA под одним `model_id` не смешиваются **[решение исполнителя, M2]**.
- **Поставка.** Сборки `cpu` и `gpu`. ONNX Runtime подгружается динамически (`load-dynamic`) из библиотеки, которая лежит рядом с бинарником. Поэтому GPU-сборка работает и без GPU, а без библиотеки ORT сервер всё равно стартует в режиме FTS-only. Библиотеки NVIDIA (CUDA 13, cuDNN 9) в GPU-сборку не входят: их ставит `zam-server cuda fetch` или архив `zam-cuda-*` (§16.3). Для CUDA нужен драйвер с поддержкой CUDA 13 (ветка R580+); в документации поставки это указано.
- **Загрузка моделей.** `zam-server models fetch` скачивает модели с Hugging Face и проверяет sha256. Модели, ревизии (коммит Hugging Face) и sha256 каждого файла закреплены в `deploy/models.toml`; при несовпадении загрузка падает. Есть и архив поставки `-models`, где модели уже внутри, — для машин без интернета. Без моделей сервер работает в режиме FTS-only и сообщает об этом.
- **Память.** Модель эмбеддингов загружается при старте сервера (до первого открытия баз: чанкер считает её токенизатором), реранкер — лениво, при первом запросе с `rerank=on`. Выгрузка по простою (`ml.unload_after`, по умолчанию выключена) на M2 не реализована: значение принимается, сервер пишет предупреждение и держит модели в памяти.

### 8.5. Граф связей
Отдельная графовая СУБД не нужна: на нашем масштабе хватает таблицы `edges` и рекурсивных CTE в SQLite. Трейт `GraphStore` оставляет возможность заменить хранилище позже. Готовые встраиваемые графовые движки в Rust-экосистеме нестабильны: Kùzu, например, свёрнут. **[решение исполнителя]**

- **Типы связей:** `links_to` (wiki-ссылка или Markdown-ссылка), `relates_to`, `depends_on`, `part_of`, `caused_by`, `fixes`, `supersedes`, `derived_from` (запись создана по заметке или вложению), `mentions`.
- **Откуда берутся связи:**
  - `[[Заметка]]` и `[[Заметка#Секция]]` в тексте — `origin=wikilink`; Markdown-ссылка `[текст](путь)` на относительный путь (от папки заметки; `/…` — от корня пространства; суффикс `.md` необязателен) — тоже `links_to` с `origin=wikilink`; внешние URL, якоря, вложения и картинки рёбер не дают **[решение исполнителя]**;
  - `relations:` во frontmatter — список строк `"<тип>: <цель>"` (flow или block), цель — `[[Имя]]` или путь в пространстве, например `relations: ["depends_on: [[Сборка]]", "fixes: notes/gotchas/crlf.md"]`; неизвестный тип пропускается с предупреждением в ответе записи **[решение исполнителя]**;
  - явные связи из API и инструмента `memory_link`, а также `links` insight (§7.5) — `origin=explicit`;
  - системные связи: `supersedes` (новая запись → старая, при замещении), связь «инсайт ↔ решение» — `origin=system`.
- **Жизненный цикл** **[решение исполнителя]**: рёбра `wikilink`/`frontmatter` выводятся из текущей ревизии и пересобираются при каждой записи узла (создание, правка, PATCH, откат, восстановление) в той же транзакции; `explicit` удаляются мягко и только они (`DELETE /edges/{id}`; выведенные и системные — 422). Неразрешённая ссылка хранится с ключом `dst_raw` (`[[Имя]]` или путь) и разрешается, когда цель появится: создание, переименование, перенос, удаление и восстановление узла перепроверяют ссылки пространства по старым и новым имени и пути. Разрешение — как в рендере (одна функция): путь, затем имя — первая живая заметка по `path`, только в пространстве источника. Удалённый источник прячет свои рёбра и обратные ссылки, восстановление возвращает их; ссылка на удалённую заметку становится неразрешённой. Базы M2 дозаполняются при открытии фоновой задачей.
- **Права `certainty`** **[решение исполнителя]**: явное ребро от источника `axiom` создаёт и удаляет только человек (ребро — часть утверждения источника, 403 `axiom-requires-human`); ребро к цели `axiom` агенту разрешено; выведенные рёбра следуют за текстом, запись которого уже проверена матрицей §7.5.
- **Где используются:**
  - в поиске: `expand=graph` добавляет соседей первых `top_k` элементов на 1 шаг в обе стороны в пределах области цели: до `ceil(top_k / 2)` новых элементов с баллом `родитель × search.graph_weight` (0,5); сначала действующие инсайты (`active`/`revisit`, по `certainty`: `axiom`, `theorem`, `hypothesis`), затем заметки; `superseded`/`retracted` — только с `include_history`; у элемента `sources: ["graph"]` и `via: {type, from}`;
  - в API: `GET /graph?node=&depth=`;
  - в WebUI: локальный граф узла и обратные ссылки (backlinks);
  - `doctor` находит битые ссылки.
- **Границы базы.** Рёбра существуют только внутри одной базы: цель в другой базе (личная память участника и решение в базе владельца) отклоняется (422), межбазовые связи — не в M3 **[решение исполнителя]**. Граф, обратные ссылки и `expand=graph` для участника ограничены пространством решения: рёбра в другие пространства владельца ему не видны.
- **Связи от агента.** Связи и сущности предлагает агент через `memory_link`. В режиме подтверждения они попадают в черновики (§10.6).

## 9. Поиск, выжимка, кэш

### 9.1. Запрос

```jsonc
POST /api/v1/search
{
  "query": "как правильно писать bash-скрипты на windows",
  "scope": {"solution": "<guid>", "include_knowledge": true, "include_rules": true,
            "all_solutions": false, "path_prefix": null, "area": null},
  "filters": {"kinds": ["note","insight","changelog","release","attachment"], "insight_kinds": [],
              "tags": [], "status": ["active","revisit"], "since": null},
  "mode": "brief" | "chunks" | "notes",       // по умолчанию brief (§9.3)
  "top_k": 10, "budget_tokens": 800,
  "rerank": "off" | "on",                     // серверный реранк, по умолчанию off
  "expand": "none" | "section" | "neighbors" | "graph",
  "include_history": false, "no_cache": false,
  "skip_seen": true,                           // не повторять текст, уже выданный этой сессии
  "session_id": "…", "format": "md" | "json"   // md — компактный текст, по умолчанию для агентов
}
```

Режимы:
- `brief` — компактные карточки кандидатов (§9.3, шаг 1). Основной режим для агентов.
- `chunks` — карточки вместе с текстом чанков в пределах бюджета. Для простых вопросов, когда хочется получить ответ за один вызов.
- `notes` — список узлов с L0, без текста.

Область и заголовки:
- `scope.solution` — `agent_solution_id`; решение входит в поиск только для владельца и одобренных участников, иначе оно исключается, а в `warnings` идёт `solution access pending|rejected|revoked` (§11.6). `all_solutions` — все доступные решения. Knowledge и Rules берутся из личной базы.
- `X-Zam-Area` — текущая область для буста (§11.2, §9.2 п. 4) и область по умолчанию для новых записей. `scope.area` — строгий фильтр: только узлы и записи этой области (FTS, Qdrant и проверка векторных хитов; пустая — без фильтра).
- `filters.certainty` — подмножество `axiom | theorem | hypothesis`; по умолчанию без ограничения.
- `filters.kinds` по умолчанию — `note, insight, changelog, release` (вложения `attachment` — с M5), без `folder`; карточки папок (`folder`) выдаются только по явному `filters.kinds: ["folder"]` — иначе папки работают как канал подъёма (§9.2).

### 9.2. Алгоритм
Генеративная модель на этом пути не используется.

1. **Фильтр области** — общий для всех каналов: дизъюнкция областей «владелец базы + пространства» (личные пространства и доступные общие решения, §6.4, §11.6), префикс пути, область, статус, надёжность.
2. **Кандидаты:**
   - (a) Qdrant: `dense` top-50 и `sparse` top-50 по `chunk|attachment`, плюс `dense` top-10 по `note|section|folder` (точки папок дают канал `w_folder`); слияние RRF внутри Qdrant;
   - (b) FTS5: `bm25` top-50 (unicode61) и `trigram` top-20, если в запросе есть код или идентификаторы; запрос идёт по каждой базе владельца отдельно в пределах её пространств, результаты баз сливаются по `raw_score` каждого канала.
3. **Слияние** (a) и (b) — weighted RRF (k=60) в приложении. Веса задаются в конфигурации; у bm25, найденного только ослабленным запросом (любое слово), — свой вес `w_fts_relaxed` (0,25 по eval): случайные совпадения по одному слову не должны вытеснять векторные находки.
4. **Поправки:**
   - буст для `gotcha` и `failure` (`search.boost_gotcha`, `search.boost_failure`, по умолчанию 1,15) и для текущей области из `X-Zam-Area` (`search.boost_area`, 1,10) — множители слитого балла (сразу после слияния, бусты перемножаются; балл в ответе ограничен 1, порядок — по полному баллу), значения подтверждаются сеткой eval **[решение исполнителя, M3]**;
   - буст надёжности: `search.boost_axiom` (1,20) > `search.boost_theorem` (1,10) > `search.boost_hypothesis` (1,00); карточки и элементы выдачи показывают `certainty`;
   - канал точек папок: чанку узла, лежащего под путём найденной папки, прибавляется `w_folder / (k + место папки)` — один раз, по лучшей папке-предку. Папка не занимает место в выдаче, а поднимает листы своих потомков (иерархическое вспоминание); значение `w_folder` выбирается сеткой eval, без значимого выигрыша — 0;
   - затухание по свежести с полупериодом 180 дней: множитель `0,5 + 0,5·2^(−возраст/полупериод)` — давняя заметка теряет не больше половины балла **[решение исполнителя, M2]**;
   - `superseded` и `retracted` исключаются, если история не запрошена.
5. **Серверный реранк** — только при `rerank=on`: 20 кандидатов по 256 токенов. В хуках не используется никогда. По умолчанию реранжирует агент (§9.3).
6. **Группировка.** Не больше 3 чанков с одного узла. Если сработала сводка уровня заметки, вместо неё берётся лучший листовой чанк.
7. **Расширение контекста (`expand`):**
   - `section` — подставить всю секцию;
   - `neighbors` — соседние чанки;
   - `graph` — по §8.5.
8. **Упаковка в `budget_tokens`.**
   - Каждый элемент: `node_id|entry_id`, `space`, `path`, `heading_path`, `locator`, `rev`, `chunk_ids`, `score`, `updated_at`, `status`, `kind`, `text`.
   - Весь ответ: `degraded`, `pending_count`, `warnings`, `timings` (`fts_ms`, `embed_ms`, `vector_ms`, `fuse_ms`, `rerank_ms`, `expand_ms`, `pending_ms`, `total_ms`). `warnings` — коды предупреждений: `reranker not installed`, `reranker failed`, `index rebuilding` (идёт reindex или пересборка индекса после потери хранилища Qdrant — векторная выдача может быть неполной) **[решение исполнителя, M2]**; `solution access pending|rejected|revoked` (§9.1) и `solution unavailable` — база владельца решения не открылась или не читается, решение исключено, ответ строится по остальным базам **[решение исполнителя, M3]**. Элемент из решения (своего или чужого) несёт `agent_solution_id`.

### 9.3. Выжимку делает агент: протокол с экономией токенов

Сервер ищет и хранит. Решает, что из найденного важно, сам агент: он знает свою задачу лучше любой модели на сервере. Протокол состоит из четырёх шагов. Каждый следующий шаг выполняется, только если на предыдущем не хватило данных.

```
 шаг 0  memory_search ─▶ есть актуальная выжимка в кэше?  ── да ──▶ готово (≈ 100–400 токенов)
                                   │ нет
 шаг 1                    карточки кандидатов (brief)            (≈ 30–50 токенов на карточку)
                                   │ агент выбирает нужные
 шаг 2  memory_read [id…] ─▶ только нужные секции/уровни         (L0/L1/секция, а не вся заметка)
                                   │ агент формирует выжимку
 шаг 3  memory_cache_put ─▶ выжимка + источники с ревизиями ─▶ доступна следующим запросам
        (опционально)  promote ─▶ выжимка становится заметкой или инсайтом
```

**Шаг 0 — кэш.** `memory_search` сначала ищет в кэше действующую выжимку для похожего запроса (§9.4). Если такая есть, первым элементом ответа идёт:

```
[cache] «Как деплоим parser-сервис» — выжимка 2026-10-12, 3 источника, все актуальны (id: c_…)
<текст выжимки>
```

Для типового вопроса этого достаточно, дальше идти не нужно.

**Шаг 1 — карточки (`mode=brief`).** Ответ компактный и машиночитаемый, по одной строке на кандидата:

```
1. n:01J… Solutions/parser/deploy.md › Docker › Сборка  [0.82] rev7 · 2026-10-10 · ~340 tok
   Сборка образа идёт multi-stage; для arm64 нужен buildx…
2. i:01J… insight/gotcha «Bash-скрипты должны иметь LF»  [0.77] active · hypothesis · ~120 tok
3. a:01J… report.pdf p.4  [0.61] · ~500 tok   (seen)
```

- В карточке: тип и id, путь и секция, оценка, ревизия, дата, размер полного текста в токенах, 1–2 строки фрагмента. У записи журнала вместо пути и ревизии — вид (`insight/<data.kind>`, `changelog/<data.kind>`, `release`), заголовок, `status` и `certainty`; префикс id — `i:`, `c:`, `r:`.
- Если запись уже выдавалась этой сессии в той же ревизии, вместо фрагмента стоит пометка `(seen)` (`session_seen`, `skip_seen=true`).
- Агент сам ранжирует карточки по смыслу своей задачи. Серверный реранк для этого не нужен.

**Шаг 2 — точечное чтение.** `memory_read` принимает список id. Для каждого id можно указать:
- `tier=L0|L1|L2`;
- `section` — путь заголовков;
- `locator` — страница или лист;
- `max_tokens` — обрезка с пометкой «…ещё N токенов»;
- `if_rev` — если ревизия не изменилась, вернётся `unchanged`, без текста.

Так агент читает ровно то, что нужно, и не перечитывает то, что уже есть в его контексте.

**Шаг 3 — сохранение выжимки.** Агент вызывает `memory_cache_put` с параметрами:
- `query`;
- `summary` — Markdown, до 600 токенов (лимит настраивается), со ссылками на источники;
- `sources` — id и ревизии или секции того, на чём выжимка реально основана.

Сервер проверяет, что все источники существуют и доступны, фиксирует их текущие ревизии и хэши и строит зависимости для инвалидации. Если выжимка ценна надолго, её можно превратить в запись: `memory_cache_put(promote: {as: note|insight, path|kind})`. Тогда она становится полноценной заметкой или инсайтом со связями `derived_from` на источники.

**Правила экономии токенов.** Все они закреплены в инструкции агенту (§14.2) и в описаниях инструментов:
- MCP по умолчанию отвечает в компактном Markdown, а не в JSON;
- `budget_tokens` по умолчанию — 800 для поиска и 1500 для чтения;
- сначала L0/L1 и оглавление (`outline`), полный текст — только при необходимости;
- одним вызовом читается несколько id;
- то, что агент уже получал, повторно не выдаётся (`seen`, `if_rev`);
- перед новым поиском по той же теме сначала проверяется кэш;
- в каждом ответе есть служебная строка `~N tok`, чтобы агент видел свой расход.

### 9.4. Кэш выжимок
Требование из наброска: запрос и выжимка хранятся в кэше, кэш инвалидируется, когда меняются источники.

- **Кто пишет.** Только агенты, через `memory_cache_put`. Сервер выжимки не генерирует.
- **Общее решение.** Кэш выжимок общего решения общий на решение: выжимка, сохранённая участником, доступна остальным участникам (с пометкой автора) и инвалидируется изменением источников решения. Выжимки по личным пространствам (Knowledge, Rules) остаются в кэше пользователя и участникам не видны; в поиске по общему решению личный Knowledge подмешивается только свой. Реализация — этап M4 **[решение исполнителя]**.
- **Область видимости.**
  - Поиск в кэше идёт сначала по текущей сессии, затем по выжимкам других сессий того же решения (`cache.cross_session`, по умолчанию включено).
  - Чужая выжимка помечается сессией, машиной и датой автора, и агент сам решает, доверять ли ей.
  - Использование между сессиями — **[решение исполнителя]**: выжимка стоит агенту токенов, а её актуальность гарантирует проверка источников. Отключается настройкой.
- **Попадание в кэш:**
  - точное совпадение `(scope_hash, query_norm)`;
  - или семантическое: dense-косинус к `query_vec` ≥ 0,92 (порог настраивается).

  Возвращается не больше 2 выжимок.
- **Проверка при чтении.** Ревизии и хэши всех `sources` сверяются одним SQL-запросом. Если хоть один источник расходится, запись кэша считается недействительной. Агент получает пометку `stale` со списком изменившихся источников и может обновить выжимку точечно: перечитать только изменившееся.
- **Инвалидация при записи:**
  - изменение, удаление, замещение или отзыв источника — по обратному индексу `cache_deps`;
  - появление нового релевантного источника — при индексации новых чанков их dense-вектор сравнивается с `query_vec` действующих записей кэша той же области; при косинусе ≥ 0,80 запись помечается `stale: new_sources`.
- **Срок жизни.** TTL по умолчанию 30 дней без обращений. LRU — 2000 записей на пользователя. Выжимки, превращённые в записи (`promoted_to`), не вытесняются.
- **WebUI.** Кэш доступен на просмотр (§15.4): выжимка, источники, автор, статус. Записи можно удалять и превращать в заметки.

### 9.5. Почему не «выжимка на сервере»
Принцип 2 и решение владельца: сервер работает без LLM. Агент всё равно читает результат, поэтому лучше один раз прочитать нужное и сохранить выжимку, чем каждый раз генерировать её второй моделью. Кэш делает повторные обращения дешёвыми для всех сессий и машин.

## 10. Проактивное вспоминание

### 10.1. Идея простыми словами
Агент не знает, чего он не помнит. Даже если урок записан в память, агент пойдёт его искать только тогда, когда сам заподозрит, что такой урок есть. Обычно именно этого и не происходит. Поэтому память сама подсказывает в четыре момента:
1. на старте сессии;
2. на каждый запрос пользователя;
3. перед действием над файлом или командой;
4. после ошибки.

Подсказки встраиваются в контекст агента через **хуки**: агент сам запускает внешнюю команду на событие (Claude Code, Codex и другие умеют это).

**Что здесь проверено практикой, а что ново.**
- *Проверено практикой:* подмешивание контекста хуками `SessionStart`, `UserPromptSubmit` и `PostToolUse`. Это документированная возможность Claude Code. На ней построены claude-mem и плагины OpenViking; OpenViking за счёт автоподгрузки получил основной прирост на LoCoMo.
- *Новое, наша разработка:* детерминированные **триггеры** на инсайтах (маска файла, regex команды или ошибки). Это сочетание проверенных механизмов. Поэтому каждый тип подсказок отключается по отдельности, а полезность измеряется (§10.5).

### 10.2. Как это выглядит для агента (сценарий CRLF)

```
Claude Code                         zam (CLI, локально)                 zam-server
───────────                         ───────────────────                 ──────────
SessionStart ─────────────────────▶ hook session-start ───────────────▶ /recall(session_start)
                                    ◀─ дайджест: Rules, L1 решения, топ-гочи, revisit, последние изменения
                                    ├─ кэширует триггеры решения + Knowledge (.zeroaimemory/cache)
  [в контексте агента: «ZeroAIMemory: правила… ловушки: …»]

Пользователь: «напиши deploy.sh»
UserPromptSubmit ─────────────────▶ hook prompt ──────────────────────▶ /recall(prompt) — быстрый поиск
                                    ◀─ 0–3 записи выше порога (или ничего)

Агент → Write(deploy.sh)
PreToolUse ───────────────────────▶ hook pre-tool: glob **/*.sh совпал (без сети, ≤5 мс)
  [в контексте: «ZeroAIMemory: для *.sh — LF. Разобрано 2026-10-10, insight:…»]
Агент пишет файл с LF

(если всё же ошибка) Bash: ./deploy.sh → "bad interpreter: ^M"
PostToolUse(Failure) ─────────────▶ hook post-tool: error_regex совпал → «Эта ошибка уже разбиралась: …»

Stop / PreCompact ────────────────▶ hook checkpoint: были правки, но нет записей → одно напоминание
                                    «запиши итоги в changelog/insights» (не повторяется)
```

### 10.3. События, бюджеты, правила

| Событие | Команда | Что выдаёт | Бюджет |
|---|---|---|---|
| `SessionStart` | `zam hook session-start` | Дайджест не больше `digest_tokens` (по умолчанию 1500). Обновляет кэш триггеров | ≤ 300 мс |
| `UserPromptSubmit` | `zam hook prompt` | 0–3 инсайта или правила, если оценка выше порога. Без реранка | ≤ 250 мс, иначе тишина |
| `PreToolUse` (Write, Edit, Bash) | `zam hook pre-tool` | Совпадения `file_glob` и `command_regex` из локального кэша | ≤ 5 мс на сопоставление, ≤ 50 мс весь процесс |
| `PostToolUse` / `PostToolUseFailure` (Bash с ошибкой) | `zam hook post-tool` | Нормализует ошибку (убирает пути, числа, хэши), сопоставляет с `error_regex` локально, затем делает FTS-поиск по инсайтам | ≤ 250 мс |
| `Stop`, `PreCompact` | `zam hook checkpoint` | Одно напоминание записать итоги. Учитывает `stop_hook_active`, не зацикливается | ≤ 100 мс |

Общие правила:
- **Fail-open.** Ошибка, тайм-аут или недоступный сервер дают пустой вывод и код 0. Агент никогда не блокируется. Ошибки пишутся в `.zeroaimemory/logs/`.
- **Общее решение.** Проактивное вспоминание для общего решения работает по тем же правилам: триггеры и дайджест берутся из решения, доступного пользователю, и из его собственного Knowledge; чужой Knowledge и Human не подмешиваются никогда. Реализация — этап M4 **[решение исполнителя]**.
- **Без повторов.** Одна запись показывается не больше одного раза за сессию. Исключение — `error_regex`: такая подсказка срабатывает при каждой ошибке.
- **Пометка.** Все подсказки начинаются с `ZeroAIMemory:` и содержат ссылку на источник.
- **Кэш триггеров** обновляется с ETag: `GET /triggers?solution=<guid>` (или `X-Zam-Solution`) отдаёт `{etag, triggers: [{id, entry_id, type, pattern, tools, title, insight_kind, certainty, space}]}` — действующие триггеры решения (в базе владельца) и Knowledge пользователя; `ETag` — blake3 канонического JSON, `If-None-Match` → 304 (M3). Регулярные выражения — `regex` без обратных ссылок, поэтому ReDoS невозможен.
- **JSON-контракт хуков** (поля stdin, `hookSpecificOutput.additionalContext`, точные имена событий) сверяется с актуальной документацией Claude Code на этапе M4. Для других агентов делаются адаптеры по их формату.
- **Настройки.** Каждый тип подсказок включается и выключается в конфиге клиента и в WebUI.

### 10.4. Агенты без хуков
Подключаются через MCP и инструкцию в AGENTS.md: «перед созданием файла нового типа или после ошибки вызови `memory_recall`». Тот же `/recall` доступен как инструмент.

### 10.5. Измерение пользы
- Каждый показ записывается: `usage(recall_shown)`.
- Явная оценка: `memory_update_entry(feedback: useful|useless)` от агента или кнопка в WebUI.
- WebUI показывает «шумные» записи — часто показываются, но ни разу не были полезны. Их можно поправить или отключить им триггер.
- Отчёт по доле полезных подсказок помогает подстраивать пороги.

### 10.6. Черновики на подтверждение (v2)
По хуку `checkpoint` агент может записывать не готовые записи, а черновики со статусом `proposed`, если в настройках решения включён режим «подтверждать записи агентов». Черновики попадают в очередь подтверждения в WebUI и не участвуют в поиске до одобрения. Формирует черновики сам агент, LLM на сервере нет.

## 11. Многомашинность, идентификация, доступ

### 11.1. Файл решения
Заменяет каталог `claude_solution_id` из наброска на вариант, не привязанный к конкретному агенту. **[решение исполнителя]**

```toml
# <repo>/.zeroaimemory/solution.toml — коммитится
agent_solution_id = "0192f1c4-7a1e-7c3b-9a55-2b1f6f0d9e11"
name              = "TradingPlatform"
```

- Ключ называется `agent_solution_id` (в наброске — `claude_solution_id`); прежний ключ `id` читается для совместимости.

- Все клоны и каталоги с этим GUID делят одну память.
- `.zeroaimemory/.gitignore` исключает `cache/` и `logs/`.
- CLI ищет `solution.toml`, поднимаясь от текущего каталога вверх.
- Решение регистрируется при первом обращении с новым GUID (`zam init` или `POST /solutions`); регистрирующий становится владельцем. Обращение к уже зарегистрированному чужому GUID создаёт запрос на доступ (§11.6).

### 11.2. Области (монорепозиторий)
Сценарий из наброска: одно решение на C# плюс набор Python-сервисов.

- Решение одно, его `solution.toml` лежит в корне.
- Подкаталог объявляет область файлом `<subdir>/.zeroaimemory/area.toml` с содержимым `area = "services/parser"`.
- Записи помечаются областью автоматически.
- Поиск идёт по всему решению, текущая область (заголовок `X-Zam-Area`) получает буст. `scope.area` ограничивает поиск строго одной областью (§9.1).

### 11.3. Конкурентная запись
- **Заметки.** `PUT` требует `If-Match: <rev>`. При конфликте — `409` с текущей ревизией и диффом.
- **Правка по секциям.** `PATCH` с операциями `replace_section`, `append_to_section`, `insert_after_heading`, `append`, `prepend` (адресация — путь заголовков). Патч применяется к последней ревизии, если затронутая секция не менялась после `base_rev`.
- **Журналы** только дописываются, поэтому не конфликтуют. Каждый запрос записи принимает `Idempotency-Key`, повтор безопасен.
- **Атрибуция машины.** Заголовок `X-Zam-Machine`. CLI подставляет hostname, для MCP значение задаётся в конфиге клиента.

### 11.4. Аутентификация и пользователи
Сервис рассчитан в первую очередь на одного владельца.

- **Администратор.** Логин и пароль задаются в конфигурации сервера:
  - `[admin] login = "…"`, `password_hash = "argon2id…"`;
  - хэш выдаёт `zam-server hash-password`;
  - для первого запуска допускается `ZAM_ADMIN_PASSWORD`, пароль из неё хэшируется в памяти.

  Только администратор входит в WebUI и управляет сервисом. В БД учётных данных администратора нет.
- **Пользователи.** При первом запуске автоматически создаётся пользователь администратора с собственной памятью и первым токеном (токен выводится в лог один раз и доступен в WebUI). Других пользователей администратор заводит в WebUI; при создании пользователю выдаётся токен. У пользователя может быть несколько токенов, их можно выпускать, отзывать и перевыпускать. Режимы токена: `rw` (по умолчанию) и `ro`.
- **Агент** получает только токен. Логин и пароль ему не нужны. Токен открывает всю память пользователя, кроме Human, включая vault, и память общих решений, к которым у пользователя есть одобренный доступ (§11.6).
- **Человеческий токен** (`human`) **[решение исполнителя]**: токен, записи которого считаются записями человека (`author_kind = human`, §7.5), нужен для `axiom` и правок надёжного вне WebUI. Выпускает только администратор (флажок «для человека» с предупреждением). В CLAUDE.md и AGENTS.md его класть нельзя: CLI берёт его из `~/.zeroaimemory/config.toml` (`human_token`) только для команд с флагом `--human`; адрес сервера для них — тоже только из этого файла (`url`), флаг `--url`, `ZAM_URL` и файлы проекта игнорируются (при расхождении — предупреждение в stderr), чтобы подменённый адрес не получил токен. **Ruling контроллера (до ответа владельца):** `--human` работает только в интерактивном терминале (stdin и stderr — TTY) и после подтверждения вводом id записи; без терминала — отказ (код 3) «подтверждение аксиом — только человеком: WebUI или интерактивный терминал». Агент, вызывающий CLI неинтерактивно, человеческим токеном воспользоваться не может.
- **Где лежит токен — в CLAUDE.md или AGENTS.md** (решение владельца), в блоке ZeroAIMemory:
  ```
  ZeroAIMemoryUrl=http://memory.lan:7700
  ZeroAIMemoryToken=zam_…
  ```
  CLI `zam` находит URL и токен по порядку:
  1. флаг командной строки;
  2. переменная окружения `ZAM_TOKEN` / `ZAM_URL`;
  3. блок в ближайшем `CLAUDE.md`, `CLAUDE.local.md` или `AGENTS.md`;
  4. `~/.zeroaimemory/config.toml`.

  MCP-конфиг, который пишет `zam init`, берёт токен из того же блока. Если токен утёк, его отзывают и перевыпускают в WebUI в один клик.
- **Хранение токенов** — только sha256. В WebUI видны префикс, время последнего использования и IP.

### 11.5. Сеть
- **Где слушает сервер.** `server.bind`, по умолчанию `0.0.0.0:7700`; HTTP в локальной сети. TLS и внешний доступ — забота внешнего прокси (Traefik и т. п.).
- **Работа за прокси:**
  - `server.trusted_proxies` — список доверенных адресов, от которых сервер принимает `X-Forwarded-For` и `X-Forwarded-Proto`;
  - `server.base_path` — публикация под префиксом, например `/memory`;
  - корректные абсолютные ссылки и cookie `Secure`, если запрос пришёл через HTTPS.
- **Защита входа.** Ограничение частоты входа администратора (5 попыток в минуту на IP) и неверных токенов.


### 11.6. Совместный доступ к решению (M3, требование владельца 2026-10-19)
Владелец решения открывает его память другим пользователям с подтверждением. Решение владельца 2026-10-21: делать сразу в M3, чтобы не менять нижележащие уровни потом; память решения остаётся в базе владельца.

- **Идентификатор.** `agent_solution_id` (GUID, нижний регистр, с дефисами). Ключ в `.zeroaimemory/solution.toml` (старый `id` читается) и поле в API, CLI и WebUI.
- **Хранение.** Решение — пространство `solution` в базе владельца (§6.3). В `system.db` лежат реестр решений (`solutions`: GUID, владелец, пространство) и разрешения (`solution_access`: участник, режим, состояние). Сервер по GUID находит базу владельца и пускает участника **только в пространство этого решения**. Rules, Human, Knowledge и Vault владельца, его узлы вне решения и рёбра в другие пространства участнику недоступны (404).
- **Регистрация.** Первый зарегистрировавший GUID — владелец. Решения M1–M2 регистрируются при старте сервера по порядку создания пользователей. Если один GUID встретился у двух пользователей, владельцем становится первый, а пространство второго получает новый GUID (его заметки остаются на месте), и для исходного GUID создаётся ожидающий запрос второго пользователя; аудит `solution.guid_conflict` **[решение исполнителя]**.
- **Выдача.** Владелец узнаёт `agent_solution_id` из `solution.toml` (`zam init`) или `GET /solutions/{guid}` и передаёт его другим пользователям.
- **Подключение.** Другой пользователь прописывает идентификатор в своём `solution.toml`. При первом `POST /solutions` со своим токеном создаётся запрос на доступ: ответ `202 {agent_solution_id, state: "pending"}`. Пока запрос не одобрен, доступа нет (403 `/problems/solution-access` с `state`), и своё решение с этим GUID пользователю не создаётся.
- **Состояния и переходы.** `pending → approved | rejected`; `approved → revoked`; `approved → approved` (смена режима); `rejected → approved`; `revoked → approved`. Остальные переходы — 409. Повторный запрос после `rejected` или `revoked` состояние не меняет, чтобы не засорять владельца **[решение исполнителя]**. Владелец участником быть не может.
- **Режимы.** `rw` и `ro`; при одобрении по умолчанию `rw` **[решение исполнителя]**. Действующее право записи — режим токена и режим участника одновременно. Управлять доступом может владелец своим `rw`-токеном или администратор.
- **Подтверждение без WebUI.** WebUI только у администратора (§11.4), поэтому владелец управляет доступом из CLI и REST:
  - `zam solution access list|requests|approve <user> [--ro]|reject <user> [--reason R]|revoke <user> [--solution GUID]`;
  - `GET /solutions/{guid}/access`, `POST /solutions/{guid}/access/{user}/approve|reject|revoke` (§12);
  - число ожидающих запросов — поле `access_requests_pending` в `GET /spaces` и строка в `zam status`; дайджест старта сессии (§10.3) — M4;
  - те же операции есть у администратора в WebUI.
- **Отзыв.** Действует со следующего запроса, в том числе для уже выданных токенов: роль читается из `system.db` на каждый запрос, кэша нет; решение исключается из поиска с предупреждением `solution access revoked`. Запрос, одобрение, отклонение, смена режима и отзыв пишутся в аудит (`solution.register`, `solution.access.request|approve|reject|revoke|mode`).
- **Атрибуция.** Каждая ревизия заметки и записи журнала в базе владельца хранит `user_id` и токен автора, рядом сессию и машину (G6).
- **Vault.** Vault участника для общего решения лежит в его собственной базе и привязан к `agent_solution_id` (§7.6); владелец и другие участники его не видят.
- **Индекс и поиск.** Точки общего решения принадлежат владельцу базы (`user_id`) и несут `space_id` решения; запрос идёт одним обращением к Qdrant с дизъюнкцией областей (§6.4), FTS5 — по каждой базе в пределах её пространств с последующим слиянием (§9.2).
- **Кэш выжимок и проактивное вспоминание.** Для общего решения кэш общий на решение, личный Knowledge подмешивается только свой (§9.4, §10.3); реализация — этап M4.
- **Вне M3.** Связи между базами (§8.5), общий Vault, совместное редактирование в реальном времени (§2.2).

## 12. REST API (`/api/v1`)

- **Аутентификация:** для агентов и пользователей — `Authorization: Bearer zam_…`; для WebUI — cookie-сессия администратора с CSRF.
- **Формат:** JSON, ошибки по RFC 9457, пагинация курсором, gzip/br.
- **Заголовки:** `Idempotency-Key` на запись; `X-Zam-Session`, `X-Zam-Machine`, `X-Zam-Solution` (`agent_solution_id`) и `X-Zam-Area` для атрибуции и области по умолчанию (§11.2).
- **Администратор** работает с API любого пользователя, указывая `X-Zam-User: <id>`.

| Группа | Эндпоинты |
|---|---|
| Auth (WebUI) | `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` (с признаком `human`) |
| Админ | `GET/POST /admin/users`, `PATCH/DELETE /admin/users/{id}`, `GET/POST /admin/users/{id}/tokens {human?}`, `DELETE /admin/tokens/{id}`, `GET /admin/audit`, `GET /admin/stats`, `POST /admin/reindex`, `GET /admin/doctor`, `GET/PATCH /admin/settings` |
| Пространства и решения | `GET /spaces` (личные пространства и доступные решения с `agent_solution_id`, `role`, `shared`; владельцу — `access_requests_pending`), `POST /solutions {agent_solution_id \| id, name}` (201 создано, 200 владелец или участник, 202 запрос ждёт подтверждения, 403 `solution-access` при отказе или отзыве), `GET /solutions`, `GET/PATCH /solutions/{guid}`, `GET /solutions/{guid}/access`, `POST /solutions/{guid}/access/{user}/approve {access?}`, `…/reject {reason?}`, `…/revoke` (§11.6) |
| Дерево | `GET /spaces/{space}/tree?path=&depth=&tier=L0` |
| Рендер | `POST /render {md, base_node?}` → `{html, toc, links, warnings}` — предпросмотр для редактора тем же конвейером `zam-markdown`. Тело ограничено 1 МБ |
| Узлы | `GET /nodes/{id}?tier=&section=&format=md\|json\|html` (`html` — для WebUI, кэшируется по хэшу), `GET /nodes/by-path?space=&path=`, `GET /nodes/{id}/outline`, `POST /nodes`, `PUT /nodes/{id}` (If-Match), `PATCH /nodes/{id}` (секции), `POST /nodes/{id}/move`, `DELETE /nodes/{id}` (мягкое), `POST /nodes/{id}/restore`, `GET /trash` |
| Ревизии | `GET /nodes/{id}/revisions`, `GET /nodes/{id}/revisions/{rev}`, `GET /nodes/{id}/diff?from=&to=`, `POST /nodes/{id}/revert` |
| Журналы | `GET/POST /spaces/{space}/entries?kind=&status=&certainty=&area=&tag=&since=&until=`, `GET/PATCH/DELETE /entries/{id}`, `POST /entries/{id}/restore`, `POST /entries/{id}/supersede`, `POST /entries/{id}/retract`, `POST /entries/{id}/feedback`, `GET /entries/{id}/revisions`, `GET /releases/{id}/compare` |
| Vault | `GET /spaces/{space}/vault?q=` (метаданные), `POST /spaces/{space}/vault`, `GET /vault/{id}` (метаданные), `GET /vault/{id}?reveal=1` (значение, с аудитом), `PATCH/DELETE /vault/{id}`, `GET /vault/{id}/revisions` (`{space}` — `knowledge` или `agent_solution_id` доступного решения) |
| Граф | `GET /graph?node=\|entry=&depth=&types=`, `POST /edges`, `DELETE /edges/{id}`, `GET /nodes/{id}/backlinks`, `GET /entries/{id}/backlinks`, `GET /nodes/{id}/links` |
| Поиск | `POST /search`, `POST /recall`, `GET /triggers?solution=` (ETag) |
| Вложения | `POST /blobs` (multipart, с привязкой к узлу) → `{sha256, link}`, `GET /blobs/{sha256}/{filename}` (Range), `GET /blobs/{sha256}/preview?kind=thumb\|html\|sheet&page=` |
| Сессии | `POST /sessions`, `PATCH /sessions/{id}`, `GET /sessions?solution=` |
| Кэш выжимок | `POST /cache {query, summary, sources, promote?}`, `GET /cache?q=&solution=&session=`, `GET /cache/{id}`, `DELETE /cache/{id}`, `POST /cache/{id}/promote` |
| Чтение пачкой | `POST /read {items:[{id, tier?, section?, locator?, max_tokens?, if_rev?}], session_id, format}` |
| Подключение агента | `GET /agent-setup?user=&token=&agent=claude\|agents\|codex&solution=` → готовый текст блока и фрагменты конфигов (§15.5) |
| Индекс | `GET /index/status` (векторный канал с причиной и подсказкой, модель, устройство, RSS самого сервера `server.rss_bytes`, Qdrant: состояние, версия, `rss_bytes`, точки, перезапуски; очередь, до 20 ошибок (у узла в корзине — `deleted_at`), время воркера `worker` (инференс, запись в Qdrant; администратору ещё `worker.batch_running` и `worker.rollups_pending` — покой воркера), последний reindex, исключённые базы; токен — только свой пользователь). `POST /admin/reindex {user?, space?, full?}` → 202 `{job_count}` |
| Экспорт/импорт | `GET /spaces/{space}/export` (zip: `.md` + `_attachments/`), `POST /spaces/{space}/import` (zip или папка `.md`) |
| Служебное | `GET /health`, `GET /ready`, `GET /metrics` |

Ошибки доступа к решению и Vault: `403 /problems/solution-access` (`state`: `pending | rejected | revoked`), `403` на действие агента, запрещённое правилами `certainty` (§7.5), `422` при нехватке `evidence` или `reason`, `503 /problems/vault-locked`, `409 /problems/possible-duplicate` (дубль инсайта, §7.5).

Как это закрывает пункты API из наброска:
- регистрация и вход → Auth и Админ (по новой схеме §11.4);
- поиск чанков и документов без саммаризации → `/search` с `mode=chunks` или `mode=notes`;
- получение документа по идентификатору → `/nodes/{id}`;
- получение вложений → `/blobs`;
- добавление записей → `/nodes` и `/entries`.

## 14. Интеграция с агентами

### 14.1. `zam init`
1. Создаёт или читает `.zeroaimemory/solution.toml` и регистрирует решение.
2. Вставляет или обновляет блок между `<!-- zeroaimemory:begin -->` и `<!-- zeroaimemory:end -->` в `CLAUDE.md` и/или `AGENTS.md`. В блоке — URL, токен и правила работы.
3. После подтверждения прописывает хуки (§10) в `.claude/settings.json` и MCP-сервер в `.mcp.json`.
4. Проверяет `.gitignore` для `.zeroaimemory/cache` и `logs`.

### 14.2. Блок инструкции (черновик; финальная версия — на M4, проверяется на реальных сессиях)

Блок генерируется сервером (§15.5) и вставляется пользователем вручную или через `zam init`. Он намеренно короткий (≤ 500 токенов), потому что CLAUDE.md загружается в каждую сессию. Подробности протокола агент получает из описаний MCP-инструментов и по запросу `GET /api/v1/agent-guide` (или `zam guide`).

```markdown
<!-- zeroaimemory:begin v1 -->
## Память (ZeroAIMemory)
ZeroAIMemoryUrl=http://memory.lan:7700
ZeroAIMemoryToken=zam_…
Решение: `.zeroaimemory/solution.toml`. Если файла нет — создай его: `zam init` или вручную, `agent_solution_id` = новый UUID, `name` = имя проекта.
Инструменты: MCP `memory_*`; без MCP — CLI `zam`; без CLI — REST `$ZeroAIMemoryUrl/api/v1` с `Authorization: Bearer <токен>`.

Поиск (экономь токены):
1. `memory_search` → если первой строкой идёт актуальная `[cache]`-выжимка, используй её.
2. Иначе по карточкам выбери нужное сам и читай точечно: `memory_read` нескольких id сразу, сначала `tier=L1` или `section`, полный текст — только если без него никак.
3. Собрал ответ из нескольких источников → `memory_cache_put` (query, выжимка ≤ 600 токенов, источники с ревизиями). Если это знание пригодится надолго — `promote`.
- Перед нетривиальной задачей и перед исследованием — `memory_search` по теме; для исследований — `insight_kinds=[experiment,failure]`, чтобы не повторять опробованное.
- Создаёшь или существенно меняешь заметку — передай `l0` (одно предложение о сути).
- Разобрал ошибку или ловушку → `memory_log insight` (kind=gotcha|failure; scope=global, если это не специфика проекта) с триггерами.
- Проверил гипотезу → `memory_log insight kind=experiment` с результатом, даже отрицательным.
- Существенное изменение проекта → `memory_log changelog`; релиз → `memory_log release`.
- Знание устарело → `memory_update_entry` (supersede/retract), не создавай противоречащий дубль.
- Креды, токены, ссылки на репозитории → `memory_vault set`; бери их оттуда же.
- Подсказки с префиксом «ZeroAIMemory:» — ранее накопленные знания, учитывай их.
<!-- zeroaimemory:end -->
```

## 15. WebUI

### 15.1. Общее
- **Вход:** только администратор, по логину и паролю из конфигурации. Cookie `HttpOnly` + `SameSite=Strict` (+ `Secure` за HTTPS-прокси), CSRF.
- **Левая панель — дерево:**
  - вверху закреплены `Rules`, `Human`, `Knowledge`;
  - ниже — `Solutions`. Каждое решение раскрывается: сначала закреплены `Changelog`, `Releases`, `Insights`, `Vault`, затем его дерево; общие решения других пользователей помечены владельцем и режимом доступа; у `Knowledge` закреплены `Insights` и `Vault`; управление доступом (запросы, участники, отзыв, §11.6) — «Администрирование → Решения»;
  - корень дерева — «Пользователи»: сначала свой пользователь, под каждым — его поддерево;
  - ленивая подгрузка, drag-and-drop, контекстное меню, значки статуса индексации.
- **Правая панель** — просмотр или правка выбранного узла. Вкладки: «Документ», «История», «Связи».
- **Поиск** (Ctrl+K) по всем пространствам, включая Human (FTS), с подсветкой и переходом к секции, странице или листу.
- **Тёмная и светлая тема.** Адаптивная вёрстка; на телефоне — в основном чтение.

### 15.2. Markdown — полная поддержка
- **Один парсер на всю систему.** Markdown разбирает только сервер (`zam-markdown`, §5.3). WebUI получает готовый санитизированный HTML (`GET /nodes/{id}?format=html`, предпросмотр — `POST /render`) и лишь «оживляет» его: формулы, диаграммы, медиа, копирование кода, якоря. Поэтому заголовки, секции, якоря и ссылки в интерфейсе совпадают с тем, что индексирует и патчит сервер, а в начальном бандле нет Markdown-парсера. Офлайн-предпросмотр через WASM-сборку `zam-markdown` отложен до v2. **[решение исполнителя]**
- **Синтаксис:** CommonMark + GFM (таблицы, задачи, зачёркивание, автоссылки, сноски), якоря заголовков, оглавление.
- **Расширения:**
  - подсветка кода на сервере (syntect, CSS-классы под светлую и тёмную тему);
  - формулы `$…$`, `$$…$$`, ```` ```math ````: сервер размечает, клиент рендерит KaTeX (лениво);
  - диаграммы ```` ```mermaid ````: Mermaid загружается лениво, работает в режиме `securityLevel: 'strict'`, итоговый SVG проходит DOMPurify; диаграмма с `layout: elk` рисуется ленивой раскладкой ELK (`elkjs`, EPL-2.0 — исключение, разрешённое владельцем 2026-10-21; текст лицензии и ссылка на исходники — в `THIRD-PARTY-NOTICES.txt`), раскладка по умолчанию — dagre;
  - callout-блоки: 5 типов GitHub (`> [!NOTE]`, `> [!WARNING]`, …) и синтаксис Obsidian с произвольным типом и сворачиванием (`> [!info]-`);
  - wiki-ссылки `[[…]]` с автодополнением и обратными ссылками;
  - отображение frontmatter (теги, связи, description).
- **Встроенные медиа:** `![](…)` выбирает вид по MIME:
  - изображения — с лайтбоксом и масштабом;
  - видео (mp4, webm) и аудио (mp3, ogg, wav, m4a) — встроенный плеер с перемоткой (Range);
  - документы — встроенная карточка-превью (§15.3) с раскрытием в полноэкранный просмотр.
- **Безопасность:**
  - comrak работает с `render.unsafe = false`, итоговый HTML проходит `ammonia` на сервере с явным списком тегов и атрибутов;
  - на клиенте DOMPurify применяется только там, где клиент сам вставляет разметку: SVG Mermaid, превью DOCX;
  - CSP без `unsafe-inline` для скриптов.

### 15.3. Просмотр документов (минимум DOCX, XLSX, PDF)

| Формат | Просмотр | Механизм |
|---|---|---|
| PDF | Постранично, масштаб, поиск по тексту, переход к странице из результатов поиска (`locator`) | `pdf.js` в браузере |
| DOCX | Вёрстка, близкая к оригиналу: стили, таблицы, изображения, колонтитулы | `docx-preview` в браузере |
| XLSX / XLS / ODS / CSV | Таблица с переключением листов, виртуальной прокруткой, закреплённой шапкой, переходом к диапазону | Сервер: `calamine` → JSON по листам (`/preview?kind=sheet`) → таблица в браузере |
| PPTX | v1: текст слайдов; v2: визуальный просмотр | Сервер: извлечение текста |
| TXT, JSON, YAML, исходный код | С подсветкой | Сервер: syntect → HTML (кэш в `previews/`) |
| Изображения | Миниатюры, полноэкранный просмотр | Сервер: `image` → миниатюры в `previews/` |

- **Производительность.** Тяжёлые просмотрщики (pdf.js, docx-preview, Mermaid, KaTeX, CodeMirror) загружаются лениво, при первой необходимости.
- **Подбор библиотек.** Если на тестовом наборе документов (`eval/docs/`) клиентская библиотека отображает формат неудовлетворительно, допускается замена на серверную конвертацию в HTML или PDF. Внешние офисные пакеты (LibreOffice) запрещены — нарушают «вещь в себе».

### 15.4. Правка и прочее
- **Правка:**
  - CodeMirror 6: `minimalSetup` + `@codemirror/lang-markdown`, подсветка кода во fenced-блоках через Lezer. Свои расширения Lezer добавляют подсветку wiki-ссылок, callout, формул и сносок. На семантику они не влияют: её определяет сервер;
  - три режима: исходник, предпросмотр рядом (`POST /render` с debounce около 150 мс) и гибридный live-preview. В гибридном режиме разметка скрыта на всех строках, кроме строки с курсором; сделан на декорациях CM6, свой. Готовые пакеты незрелые и используются только как образец;
  - WYSIWYG-редакторы на модели документа (ProseMirror, Tiptap, Milkdown) запрещены: они пересериализуют Markdown и ломают побайтовую сохранность исходника;
  - вставка изображений и файлов из буфера или перетаскиванием, с загрузкой в blobs и вставкой ссылки;
  - автодополнение `[[…]]`;
  - сохранение с `If-Match`, при конфликте — окно с диффом.
- **История:** ревизии, дифф любых двух, откат, имя версии.
- **Журналы:**
  - Changelog — лента с фильтрами;
  - Releases — список и сравнение;
  - Insights — таблица с фильтрами (вид, статус, область, теги), правкой триггеров, «шумными» записями, очередью `proposed` (v2);
  - Vault — маска и раскрытие с аудитом.
- **Граф:** локальный граф узла (на 1–2 шага) и обратные ссылки — `d3-force` (SVG). Общий граф пространства на тысячи узлов — `sigma` 4 + `graphology` (WebGL, раскладка ForceAtlas2 в воркере). Обе библиотеки загружаются лениво.
- **Администрирование:**
  - пользователи и их токены: создать, выпустить, отозвать, последнее использование;
  - настройки сервиса;
  - состояние индекса, моделей и устройства;
  - аудит;
  - doctor и reindex;
  - бэкап.
- **Кэш выжимок:** список с фильтрами (решение, статус `valid/stale`, автор), просмотр выжимки и её источников, удаление, превращение в заметку.
- **Бюджет:** начальный бандл ≤ 300 КБ gzip без учёта ленивых модулей. Ленивые чанки, по замерам аудита (gzip): редактор около 105–130 КБ, KaTeX около 77 КБ плюс шрифты, Mermaid около 200 КБ на flowchart, pdf.js — несколько МБ вместе с воркером. Размеры проверяются в CI (`size-limit`).

### 15.5. «Подключение агента» — готовый текст для CLAUDE.md / AGENTS.md
Отдельная страница WebUI. Доступна в меню пользователя и сразу открывается после создания нового пользователя или выпуска токена.

**Что выбирает администратор:**
- пользователя и его токен; токен можно тут же выпустить;
- агента: **Claude Code** (CLAUDE.md), **AGENTS.md** (Codex, Cursor и др.) или «универсальный»;
- решение: существующее, новое (WebUI сгенерирует GUID) или «агент создаст сам»;
- опции: MCP да/нет, хуки да/нет, разрешена ли запись в Rules, язык инструкции (ru/en).

**Что получает** — блоки с кнопкой «Копировать» у каждого:
1. **Текст для CLAUDE.md / AGENTS.md.** Блок §14.2 с подставленными `ZeroAIMemoryUrl` (из `server.public_url`, а если он не задан — из адреса, по которому открыт WebUI) и `ZeroAIMemoryToken`, плюс правила работы. Блок обёрнут в маркеры с версией шаблона (`<!-- zeroaimemory:begin v1 -->`).
2. **`solution.toml`**, если решение выбрано или создано.
3. **Фрагмент `.mcp.json`**, если включён MCP.
4. **Фрагмент `.claude/settings.json` с хуками**, если они включены (для Claude Code).
5. **Команды установки `zam`** для Windows и Linux. Бинарники раздаёт сам сервер: `GET /downloads/zam/<os>-<arch>`.
6. **Однострочник** `zam init --url … --token …`, который делает пункты 1–4 автоматически.

**Шаблоны и версии:**
- Шаблоны текста хранятся в настройках сервиса, и администратор может их править: «Настройки → Шаблон инструкции», с предпросмотром и сбросом к значению по умолчанию.
- Номер версии шаблона растёт при каждом изменении.
- `zam status` и хук `session-start` сравнивают версию блока в CLAUDE.md с текущей. Если блок устарел, агент получает одно напоминание: «Блок ZeroAIMemory устарел (v1 → v2): обнови через `zam init` или WebUI».

**API.** Тот же текст отдаёт `GET /api/v1/agent-setup`. Так им пользуется и `zam init`.

## 16. Безопасность и эксплуатация

### 16.1. Безопасность
- Пароль администратора хранится как argon2id-хэш в конфигурации; токены — как sha256 в БД.
- Логи не содержат текста заметок, секретов и токенов (токены маскируются до префикса).
- В аудит пишутся: вход администратора, операции с пользователями и токенами, каждое раскрытие vault, удаление, откат, reindex.
- Раскрытие секретов по токену частотой не ограничивается: секреты нужны агенту. Каждое раскрытие видно в аудите и в WebUI.
- Содержимое Human недоступно по токену ни в каком виде.

### 16.2. Поставка и эксплуатация
- **Артефакты:**
  - **основной способ — архивы** `zam-server` (`cpu`/`gpu`, по желанию `-models`) для Windows x64 и Linux x64 (состав — §16.3). Docker не нужен;
  - `zam` для Windows x64 и Linux x64;
  - юнит systemd и служба Windows (`zam-server service install|uninstall`; Qdrant запускается сервером как дочерний процесс и отдельной службой не регистрируется). **На M2 не реализовано:** команда `service install|uninstall` — этап M7 (поставка); до неё служба ставится вручную по `deploy/README-install.md`;
  - **по желанию** — один Docker-образ `zam-server` с тем же нативным Qdrant внутри, в режиме `managed`. Отдельный контейнер Qdrant и docker-compose не нужны.
- **Бэкап** (`zam-server backup`, по расписанию из конфига; этап M7, на M2 не реализован):
  - `VACUUM INTO` каждой базы;
  - инкрементальный архив блобов;
  - манифест.

  Векторы приходят из таблицы `embeddings`, поэтому Qdrant восстанавливается через `reindex` без инференса. Мастер-ключ vault в бэкап не входит, его резервируют отдельно.
- **Миграции.** Каждая база имеет свою версию схемы (`PRAGMA user_version`). Миграция выполняется при открытии, перед ней делается копия файла.

### 16.3. Релизы: обязательные сборки (требование владельца)
Каждый релиз собирает **готовые к работе комплекты для Windows x64 и Linux x64**: в комплекте есть всё, что нужно для запуска. Релиз без любого из этих комплектов не публикуется.

- **Запуск.** Тег `vX.Y.Z` в git запускает конвейер CI (GitHub Actions; раннеры `windows-latest` и `ubuntu`). Результат — черновик GitHub Release со всеми файлами, `SHA256SUMS` и заметками к релизу из `CHANGELOG.md`.
- **Комплекты:**

  | Архив | Содержимое |
  |---|---|
  | `zam-server-<ver>-windows-x64-cpu.zip` | `zam-server.exe` (с встроенным WebUI), `onnxruntime.dll` (CPU), `pdfium.dll`, app-local MSVC runtime для ONNX Runtime (`msvcp140.dll`, `msvcp140_1.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`), `qdrant/<qver>/qdrant.exe` + `vcruntime140.dll`, `zam.exe` (для раздачи `GET /downloads/zam/…`), `config.example.toml`, `deploy/qdrant.toml`, `deploy/models.toml`, `README-install.md`, `LICENSES/` |
  | `zam-server-<ver>-windows-x64-gpu.zip` | то же, но ONNX Runtime с CUDA EP (`onnxruntime_providers_cuda`, `onnxruntime_providers_shared`), ещё `msvcp140_atomic_wait.dll` (его импортирует CUDA EP) и `deploy/cuda.toml`. Библиотек NVIDIA в комплекте нет (решение владельца): их ставит `zam-server cuda fetch` в `<exe_dir>/cuda/` по `deploy/cuda.toml` (sha256) или архив `zam-cuda-*`. Без GPU и без CUDA комплект работает на CPU |
  | `zam-server-<ver>-linux-x64-cpu.tar.gz` | `zam-server` (gnu; сборка на старой glibc, минимальная версия указывается в README), `libonnxruntime.so`, `libpdfium.so`, `qdrant/<qver>/qdrant` (musl), `zam` (musl, статический), юнит systemd, конфиг, лицензии |
  | `zam-server-<ver>-linux-x64-gpu.tar.gz` | то же + ORT CUDA EP и `deploy/cuda.toml`; библиотеки NVIDIA — так же, через `zam-server cuda fetch` или `zam-cuda-*` |
  | `zam-cuda-<ver>-windows-x64.zip`, `zam-cuda-<ver>-linux-x64.tar.gz` | каталог `cuda/`: redistributable-библиотеки CUDA 13 и cuDNN 9 по `deploy/cuda.toml` (cudart, cublas, cublasLt, cufft, cudnn; на Linux ещё curand и nvrtc), штампы `.<компонент>.sha256`, `cuda.toml` и лицензии NVIDIA — распаковывается в каталог `zam-server` (получается `<exe_dir>/cuda/`), после чего `cuda fetch` ничего не скачивает; для машин без интернета |
  | `zam-<ver>-windows-x64.zip`, `zam-<ver>-linux-x64.tar.gz` | только CLI |
  | `zam-models-<ver>-<id>.zip` | по архиву на ONNX-модель с `bundle = true` из `deploy/models.toml` (`bge-m3-int8`, `bge-m3-fp16`, `bge-reranker-v2-m3`): `<id>/` с файлами, `LICENSE` и `model.toml` плюс `models.toml` с sha256 — для машин без интернета, распаковывается в каталог моделей; при наличии интернета модели скачивает `zam-server models fetch`. Вместе модели больше 2 ГиБ, поэтому архив не один. Реранкер jina (CC-BY-NC-4.0) в архивы не входит |

  Каждый файл релиза меньше 2 ГиБ (предел GitHub): `cargo xtask package` и publish проверяют это до загрузки.

- **Откуда берутся зависимости.** Все сторонние бинарники скачиваются в CI по закреплённым версиям и SHA-256 из манифестов в `deploy/`: `qdrant.toml`, `onnxruntime.toml`, `onnxruntime-gpu.toml`, `pdfium.toml`, `cuda.toml`, `models.toml`. Без совпадения хэша сборка падает.
- **Проверка перед публикацией (smoke-тест, на обеих ОС, оба flavor).** Комплект распаковывается в чистый каталог и запускается с пустым `data_dir`. Тест проверяет, что Qdrant поднялся, записывает заметку, находит её через FTS и через векторный поиск (на маленькой тестовой модели: 5 заметок, перефраз в top-3 через векторный канал без `degraded`), запускает `zam status` и останавливает сервер. После остановки не должно остаться процессов Qdrant. GPU-комплект проверяется на CPU-раннере: без GPU он обязан работать на CPU; с распакованным `zam-cuda` команда `cuda fetch` не скачивает ничего. Архив `zam-cuda` проверяется отдельно (штампы, состав, формат библиотек). На Windows smoke проверяет, что MSVC runtime, который импортируют библиотеки комплекта, лежит рядом. Загрузка библиотек NVIDIA в CUDA EP проверяется вручную на машине с GPU (раннеров с GPU нет).
- **Версии.** SemVer для всех артефактов. `zam --version` и `GET /health` показывают версию, git-хэш и версии Qdrant и ORT.
- **Лицензии.** В `LICENSES/` комплекта лежат лицензии всех поставляемых в нём сторонних компонентов: Qdrant (Apache-2.0), ORT (MIT), pdfium (BSD/Apache), MSVC runtime (Windows), а также сводка Rust- и npm-зависимостей (`cargo-about`, `license-checker`). Библиотек NVIDIA в комплектах нет, поэтому лицензии CUDA/cuDNN (NVIDIA CUDA EULA, cuDNN SLA) лежат в архиве `zam-cuda` рядом с библиотеками, а `zam-server cuda fetch` печатает ссылку на них. Лицензия каждой модели — `LICENSE` в её архиве `zam-models` и в каталоге модели после `models fetch`.

Qdrant запускается параллельно с загрузкой модели; векторный канал готов, когда готовы оба. Замер M2 (код `d1d2521`): обычный старт — 1,1–2,0 с, выполнено. Первый старт после жёсткой остановки сразу за массовой индексацией 10 тыс. заметок на HDD — 5,4 с (GPU: повтор 39 операций WAL — 3,3 с) и 9,6 с (CPU: чтение сегментов 3,4 с и повтор 7 операций WAL 5,6 с при вытесненном кэше ОС); причина — повтор неподтверждённого WAL Qdrant после `TerminateProcess` (на Windows Qdrant иначе не останавливается) и конкуренция за HDD с чтением модели. Этот сценарий целью 5 с не покрывается; по решению владельца (2026-10-20) исследуются сброс WAL перед остановкой (`flush_interval_sec`) или меньший `wal_capacity_mb` коллекции и очерёдность чтения с HDD (Qdrant раньше модели) — с замером, на следующих этапах.
- Замеры — `cargo xtask bench --profile cpu|gpu` (корпус eval с компактными копиями до 10 тыс. заметок, итог в `eval/results/<дата>-bench-<профиль>.md`); сводка и невыполненные цели — в `docs/journal.md`. RSS сервера без моделей на 10 тыс. заметок — 54 МиБ при цели 50 МБ (кэш страниц SQLite): не выполнено, открыто. Замеры M2 сделаны при тёплом кэше ОС (модели и данные читались незадолго до этого); холодный старт после перезагрузки не мерился.
- Масштаб: до 20 пользователей, 1 млн чанков, 50 ГБ вложений.
- Сервер и клиент работают на Windows x64 и Linux x64; эти платформы обязательны для каждого релиза (§16.3). Другие платформы (Linux arm64, macOS) в v1 не поддерживаются.
- Содержимое на русском и английском, плюс код.

## 18. Качество

### 18.1. Тесты
- **Модульные:** чанкинг (golden-файлы), патчи секций (property-тест: байты вне секции не меняются), позиции и секции `zam-markdown` (сверка с pulldown-cmark, фаззинг), санитизация HTML (набор XSS-векторов), RRF, права, сканер секретов, триггеры, разбор ссылок графа, извлечение текста из документов.
- **Интеграционные:** SQLite во временных каталогах внутри `target/`. Qdrant — нативный бинарник по манифесту `deploy/qdrant.toml`, кэшируется в `target/deps/<платформа>/qdrant/` (`cargo xtask fetch-deps`; там же ONNX Runtime и pdfium), тестовые модели — в `target/models/<id>/` (`cargo xtask fetch-models --test`). Тестовая обвязка запускает его через тот же супервизор, что и в продакшне, с данными в `target/`. Docker для тестов не нужен.
- **e2e:**
  - сценарий CRLF (§1.1);
  - конфликт двух машин: 409, затем патч секции;
  - Qdrant остановлен → деградация;
  - процесс Qdrant убит → автоматический перезапуск; `zam-server` убит → Qdrant завершается вместе с ним (Windows и Linux);
  - смена версии Qdrant через несколько минорных → пересборка storage из `embeddings`;
  - удаление коллекции → reindex из `embeddings`;
  - изоляция Human и vault: нет в Qdrant, в выдаче по токену, в логах; vault нет и в FTS;
  - агент записывает и читает секрет;
  - просмотр и поиск по DOCX/XLSX/PDF;
  - fail-open хуков при выключенном сервере.
- **CI:** Windows и Linux.

### 18.2. Eval
- **Набор `eval/`:**
  - корпус заметок и документов на русском и английском;
  - запросы с ожидаемыми источниками, включая запросы на устаревание (ожидается действующий инсайт, а не замещённый);
  - набор для подсказок: релевантно / нерелевантно.
- **Метрики:** recall@5, MRR@10, nDCG@10, доля «вспомнил отменённое», точность подсказок. На M2 набор `eval/` (160 заметок, 197 запросов) и `cargo xtask eval` измеряют первые три; «вспомнил отменённое» добавляется в M3 вместе с инсайтами и `supersedes` (запросы на устаревание в наборе); точность подсказок отложена до M4 (триггеры подсказок) — тогда же в набор добавляется набор «релевантно / нерелевантно». В M3 добавляются также «надёжное выше гипотезы» (`reliable_first`: запросы, где ожидается `theorem`/`axiom`, а не противоречащая `hypothesis`) и chunk-recall@5 на длинных заметках с H4–H6 (лист целиком содержит дословное доказательство) — на них проверяется нарезка по силе границ (§8.2).
- **Гейт качества int8** (`cargo xtask eval --quality-gate`, решение владельца 2026-10-21): «пройден», если нижняя граница 95 % интервала парного бутстрепа (10 000 выборок, фиксированный seed) разности int8 − fp32 не ниже −0,01 и для nDCG@10, и для recall@5. Косинус dense (порог 0,99) и корреляция Спирмена sparse остаются в отчёте как справочные и на вердикт не влияют.
- **Регламент.** Прогон обязателен при изменении чанкинга, весов или моделей. Результаты сохраняются в `eval/results/`.

## 21. Решения исполнителя (на проверку владельцу)
1. UI — Svelte 5. Просмотрщики документов — pdf.js, docx-preview, `calamine` на сервере. Markdown разбирает и рендерит только сервер (comrak + ammonia + syntect); на клиенте Markdown-парсера нет (§15.2).
2. Пространство **Knowledge** для глобальных знаний.
3. Журналы привязаны к решению, а не к сессии.
4. Файл решения — `.zeroaimemory/solution.toml`; области задаются через `area.toml`.
5. Триггеры и хуки для проактивного вспоминания; каждый вид отключается отдельно.
6. Кэш выжимок работает и между сессиями одного решения (по умолчанию включено, отключается настройкой). Чужая выжимка помечается автором и датой. Серверный реранкер по умолчанию выключен.
7. Qdrant входит в поставку нативным бинарником, без Docker; процесс запускает и контролирует `zam-server` (§4.3). При отказе Qdrant поиск деградирует до FTS. Qdrant Edge — экспериментальный адаптер, решение о нём по прототипу на M2.
8. Граф хранится в SQLite (`edges`), без отдельной графовой СУБД.
9. Ссылки на вложения задаются относительно корня пространства.
10. Конкурентная запись — оптимистическая блокировка и патчи секций, без CRDT.
11. При первом запуске создаётся пользователь администратора с собственной памятью и первым токеном.
12. Rules по умолчанию пишет только человек (`rules.agent_write=false`).
13. Идентификаторы хранятся как UUIDv7, наружу отдаются в виде строки base32 из 26 символов.
14. Сервер `zam-server` на Linux собирается под glibc (`x86_64-unknown-linux-gnu`) на образе со старой glibc: ONNX Runtime и pdfium распространяются только под glibc, а musl-бинарник не может их загрузить. `zam` и Qdrant на Linux собираются под musl.
