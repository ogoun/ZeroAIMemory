# M5.5. Отчёты — спецификация

Статус: 2026-11-01, ответы владельца — §2; решения контроллера помечены. **Перенесено в ТЗ v1.21**
(2026-11-03, задача 8; итог этапа — `0.0.8-m5.5`, ТЗ §7.11 и §15.6); документ остаётся историей
решения. Этап идёт сразу после M5 «Документы»; карта кода сдвигается на M5.6. Решения исполнителя и
отступления — в журнале этапа `docs/plans/2026-11-01-m5.5-reports-log.md`; вопросы владельцу —
там же («Уточнить у владельца»). Отступления, перенесённые в ТЗ: токен на удаление и
восстановление отчёта получает **404, а не 403** (§4, §12 п. 5; решение исполнителя задачи 4 —
403 выдавал бы существование отчёта, §7); предел файла — `limits.blob_max_bytes` (ключа
`blobs.max_bytes` нет, §5); строка блока инструкции короче §6 (ТЗ §14.2).

## 1. Назначение

Отчёт — итог исследования или задачи, написанный для **человека**: «исследовал новую архитектуру
моделей, провёл обучение, вот результаты, сравнение с бейзлайном и другими моделями, графики».
Это не changelog (изменения проекта) и не releases (версии): отчёт фиксирует, *что получилось и как
это выглядит*.

Владелец: «Отчёты нужны постоянно, в исследованиях крайне важно видеть визуализацию работы и
сравнение с другими исследованиями».

## 3. Цели, не-цели, анти-цели

**Цели.**
- Журнал решения «Отчёты»: агент пишет отчёт (Markdown + картинки), пользователь читает его в WebUI
  с отрисованными формулами (KaTeX), диаграммами (Mermaid), таблицами, кодом и картинками.
- Лента отчётов по дате, поиск по заголовку, тексту и тегам — в WebUI.
- Выгрузка отчёта в PDF, который выглядит как на экране.

**Не-цели.**
- Шаблоны, обязательные разделы, структурированные метрики, сводные таблицы и графики по нескольким
  отчётам — системой не строятся (ответы 1–2).
- Серии и ссылки между отчётами (ответ 7).
- Правка отчёта после создания, ревизии (ответ 6).
- Отчёты в Knowledge (ответ 3).

**Анти-цели** (провал, даже если «работает»).
- Отчёты в выдаче агента: поиск по токену, дайджест `session_start`, recall, подсказки, кэш
  выжимок — они расходовали бы контекст агента на текст для человека (ответ 4).
- PDF, где формулы, диаграммы или картинки выглядят иначе, чем в WebUI, или пропадают.
- Возможность тихо изменить отчёт после записи.

## 4. Модель

**[решение контроллера]** Отчёт — запись журнала решения (`entries`), новый вид `report`, рядом с
`changelog`, `release`, `insight`, `term`, `task`, `question` (ТЗ §7.2). Так он получает
атрибуцию (агент, сессия, машина), дату, теги, область, корзину и права журналов без нового
механизма.

- **Поля:** `title`, `body` (Markdown, полный синтаксис памяти: формулы `$…$`/`$$…$$`/```` ```math ````,
  Mermaid, таблицы, код, callout), `tags`, `area`; `data.refs: {commits, files, notes, tasks}` —
  необязательные ссылки на то, на чём основан отчёт. `status` — нет (как у changelog/release).
- **Буква ссылки** — `p:` (`r:` занята release). Ссылка видна в WebUI и CLI, агенту не выдаётся.
- **Неизменность.** `PATCH` содержимого отчёта — 409 (`/problems/report-immutable`): заголовок,
  тело, теги, область, ссылки, файлы. Исправление — новый отчёт. Удалить (в корзину) и восстановить
  может только **владелец решения** в WebUI (ответ 11) — участник общего решения, в том числе с
  `rw`, получает 403, любой токен — 404 (**[решение исполнителя, задача 4]**: 403 выдавал бы
  токену существование отчёта, §7; при переносе в ТЗ v1.21 исправлено с «любой токен — 403»); это
  отличие от остальных журналов. Окончательное удаление из
  корзины и очистка блобов `entry_attachments` — вместе с общей сборкой мусора блобов в M7.
- **Где:** только пространства решений. `POST` с `kind: report` в Knowledge, Rules, Human — 422.
  Участник общего решения с `rw` может писать отчёты (через своего агента), с `ro` — читать в WebUI
  (общие права журналов, ТЗ §11.6); удалять — нет (ответ 11).

## 5. Картинки

**[решение контроллера]** Картинки отчёта хранятся в хранилище блобов (дедупликация по sha256, как
вложения заметок) и привязываются к записи новой таблицей `entry_attachments(entry_id,
blob_sha256, filename, mime, size, created_at)` — у `attachments` владелец — узел. Ссылка в Markdown —
та же форма, что у заметок: `![подпись](_attachments/<sha256[0..16]>/<имя>)`, сервер разрешает её
по `entry_attachments` этого отчёта. Картинки не индексируются (нет текста, ответ 4).

- **Картинки** (`![…](…)`) — растровые и SVG по MIME (`image/png`, `image/jpeg`, `image/webp`,
  `image/gif`, `image/svg+xml`), встраиваются в страницу. SVG — только как `<img>` (без исполнения
  скриптов), как вложения заметок в M5.
- **Прочие файлы** (CSV, ноутбук, лог; обычная ссылка `[данные](results.csv)`) **[решение
  контроллера]** — любой MIME, отдаются только на скачивание (`Content-Disposition: attachment`,
  `X-Content-Type-Options: nosniff`), без просмотрщика; в PDF — текстом с именем файла.
- CLI собирает и картинки, и прочие файлы по локальным относительным ссылкам тела; один механизм,
  одни лимиты: размер файла — `blobs.max_bytes`; на отчёт — не больше `reports.max_files` (64) и
  `reports.max_total_bytes` (200 МиБ).
- Файл отчёта, на который тело не ссылается, — 422 при создании (иначе мусор в хранилище).

## 6. Как агент пишет отчёт

**[решение контроллера]** MCP работает по HTTP, локальные файлы агента серверу недоступны, поэтому
основной путь — CLI:

```
zam report <файл.md> [--title T] [--tag X]… [--ref commit:<sha>|file:<путь>|note:<id>|task:k:<id>]…
```

- CLI читает Markdown, находит **локальные** картинки по относительным ссылкам `![…](figs/loss.png)`
  (от каталога файла), загружает их одним запросом `multipart` вместе с телом, сервер переписывает
  ссылки на `_attachments/…` и создаёт запись атомарно (всё или ничего). Без `--title` — первый
  заголовок `#` файла.
- MCP: `memory_log` с `kind: report` — тело и картинки в base64 (`images: [{name, data}]`), предел —
  `reports.mcp_max_bytes` (16 МиБ); для больших — CLI. Число инструментов MCP не растёт (10).
- Инструкция агенту (блок AGENTS.md/CLAUDE.md, ТЗ §15.5, `agent_block_version`+1): что журнал
  отчётов есть, для кого он (пользователь), когда уместен (итог исследования, эксперимента,
  обучения, сравнения — или по просьбе), что отчёт неизменяем и что выводы для себя агент
  по-прежнему пишет в insights. Напоминаний хуков нет (ответ 5).

## 7. Невидимость для агента

Отчёты не выдаются токенам (агентам) нигде: `POST /search` (в том числе явным `kinds ∋ report` —
вид не принимается от токена), recall, дайджест `session_start`, подсказки, кэш выжимок, граф,
`memory_read p:<id>`, `GET /entries?kind=report`. Агенту, создавшему отчёт, возвращается только
его id и ссылка для пользователя (URL WebUI). **[решение контроллера]** Токену с флагом
`include_human` (пользователь в CLI) — тоже нет: CLI для чтения отчётов не нужен.

- Обращение токена к отчёту (`memory_read p:<id>`, `GET /entries/{id}`, картинка) — **404**, как
  к Human: «нет такого» **[решение контроллера]**.
- `data.refs` отчёта — только данные: рёбер графа, обратных ссылок и `file_refs` отчёт не создаёт
  **[решение контроллера]** — так у заметок не появляются следы отчёта в выдаче агенту.

Индексация: FTS — да (поиск WebUI); векторы и Qdrant — нет (нужны только агентскому поиску).

## 8. WebUI

WebUI отчёты только показывает: создания и редактирования отчёта в WebUI нет (ответ 12).

- В дереве решения — закреплённый журнал «Отчёты» рядом с Changelog и Releases.
- Лента: дата, заголовок, автор (агент, сессия), теги, первая картинка миниатюрой
  **[решение контроллера]**; фильтр по тегам и области; поиск по заголовку и тексту (FTS); курсор.
- Страница отчёта: отрисованное тело (сервер — `zam-markdown`, клиент — KaTeX, Mermaid, картинки,
  как у заметок, ТЗ §15), метаданные, ссылки `data.refs`, кнопки «Скачать PDF» и «Удалить».
- Поиск Ctrl+K находит отчёты (вид `report`) — только в WebUI.

## 9. PDF

**[решение контроллера]** PDF делает браузер: «Скачать PDF» открывает вёрстку отчёта для печати и
вызывает `window.print()` (пользователь выбирает «Сохранить как PDF»). Причины: формулы, диаграммы и
картинки выглядят ровно как на экране; на сервере нет новых зависимостей (без внешних процессов,
ТЗ §15.3). Минус: из CLI и агентом PDF не получить — согласовано с владельцем.

- Печатная вёрстка (`@media print`): A4, поля, заголовок, дата, автор, проект; без навигации и
  кнопок; разрывы страниц не режут картинки, формулы и строки таблиц; длинный код переносится;
  тёмная тема не печатается.
- Печать — только после того, как догрузились все картинки, KaTeX и Mermaid (ленивые модули).
- Ссылки `data.refs` в PDF — текстом.

## 10. API (набросок для плана)

| Метод | Назначение |
|---|---|
| `POST /spaces/{space}/entries` `kind: report` (JSON или `multipart` с картинками) | создание |
| `GET /spaces/{space}/entries?kind=report` | лента (только cookie WebUI) |
| `GET /entries/{id}?format=html` | страница отчёта |
| `GET /entries/{id}/attachments/{sha}/{name}` | картинка |
| `DELETE /entries/{id}` | в корзину (только пользователь в WebUI) |

## 11. Что оставлено исполнителю

- Миграция (`entries.kind` += `report`, CHECK статусов, `entry_attachments`), номер — следующий за
  M5.
- Разбор ссылок на картинки в CLI (пути с пробелами, `..`, абсолютные — отказ, повторяющиеся картинки).
- Вёрстка ленты и печати — по стилю WebUI.
- Ключи конфига `[reports]` с умолчаниями выше.

## 12. Приёмка

1. Агент через CLI создаёт отчёт с тремя PNG, формулой и Mermaid → в WebUI всё отрисовано,
   «Скачать PDF» даёт PDF с картинками, формулой и диаграммой.
2. Тот же отчёт через MCP (base64) — то же.
3. `PATCH` отчёта — 409; повторный `zam report` — новый отчёт.
4. Токен агента: поиск, recall, дайджест, read `p:`, лента — отчёта нет; WebUI-поиск находит.
5. Отчёт в Knowledge — 422; участник `ro` читает, `rw` пишет, но не удаляет (403); удаление и
   восстановление — только владелец решения в WebUI; токен — 404 (было «403»; решение
   исполнителя задачи 4, см. §4).
6. Картинка без ссылки из тела — 422; лимиты картинок соблюдены.
