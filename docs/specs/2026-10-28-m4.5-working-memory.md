## 0. Принципы этапа

1. **Агентонезависимое ядро.** Каждая возможность — в REST, MCP и CLI одинаково для любого агента.
   События конкретного агента (Claude Code, Codex) — тонкие адаптеры `zam hook …`, которые только
   вызывают ядро и форматируют вывод. Где события нет — та же функция через MCP и правило блока
   инструкции (§10).
2. **Мало инструментов MCP.** Описания инструментов занимают контекст агента в каждой сессии. Новые
   виды записей идут через существующие `memory_log`, `memory_update_entry`, `memory_search`,
   `memory_recall`; новых инструментов MCP в этапе нет.
3. **Метаданные, не содержимое.** Локальный журнал сессии, хэши файлов и пакеты восстановления не
   несут текста промптов, команд целиком и содержимого файлов (§16 ТЗ, `hooks.log`).
4. **Fail-open** хуков — как в ТЗ §10.3: любая ошибка — пустой вывод и код 0.
5. **Вещь в себе** (решение владельца 2026-10-28): без новых внешних процессов; новые зависимости —
   только с аудитом по актуальным источникам.

## 1. Схема данных

### 1.1. Пересборка таблиц в миграциях

SQLite не меняет CHECK через `ALTER`. Загрузчик миграций (`zam-store/src/migrate.rs`) получает
признак миграции `rebuild: bool`. Для неё выполняется процедура из документации SQLite
(«Making Other Kinds Of Table Schema Changes»): `PRAGMA foreign_keys=OFF` вне транзакции → `BEGIN` →
SQL миграции (создать `X_new`, `INSERT … SELECT`, `DROP X`, `ALTER TABLE X_new RENAME TO X`,
пересоздать индексы и триггеры) → `PRAGMA foreign_key_check` (любая строка — откат и ошибка
`InvalidMigration` с таблицей) → `user_version` → `COMMIT` → `PRAGMA foreign_keys=ON`. Копия
`*.bak-v<N>` перед миграцией — как сейчас. Тест: пересборка таблицы с дочерними FK сохраняет строки
детей, нарушение FK откатывает миграцию.

### 1.2. Миграции базы пользователя

| № | Содержание |
|---|---|
| 0015 (`rebuild`) | `entries`: `kind` ∈ `changelog, release, insight, term, task, question`; статус по виду (§1.3); индексы и триггеры `entries` пересоздаются как в 0008. `edges`: тип `contradicts` (§5.2) |
| 0016 | `file_refs` (§6.1); `nodes.verified_at TEXT NULL`, `nodes.verified_at_commit TEXT NULL` |
| 0017 | `sessions.parent_id TEXT NULL`, `sessions.agent_type TEXT NULL`; `session_tokens` (§9.4) |
| 0018 | `vault_fts` — FTS5 по открытым полям Vault (§8) и дозаполнение для существующих записей |

Номера фиксируются порядком задач плана; если задача уходит из этапа, следующие сдвигаются.

### 1.3. Виды записей и статусы

| `kind` | Статусы (`status`) | Начальный | Пространства |
|---|---|---|---|
| `changelog`, `release` | NULL | — | решение |
| `insight` | `active, revisit, superseded, retracted` | `active` | решение, Knowledge |
| `term` | `active, superseded, retracted` | `active` | решение, Knowledge |
| `task` | `open, in_progress, blocked, done, dropped` | `open` | решение, Knowledge |
| `question` | `open, answered, obsolete` | `open` | решение, Knowledge |

CHECK: `status IS NULL` ⇔ `kind IN ('changelog','release')`; для остальных — допустимое множество
своего вида. Rules и Human — 422, как у insight. `scope: global` пишет в Knowledge — как у insight.
Supersede и retract — у `insight` и `term`; у `task`/`question` вместо них — переходы статуса.
`certainty` — у `insight`, `term` и у решения, созданного из ответа (§4). Ссылки в выдаче:
`t:<id>` — term, `k:<id>` — task, `q:<id>` — question (рядом с `i:`, `c:`, `r:`, `e:`).

Новые виды проходят все места, где перечислены виды записей (поиск `ENTRY_KINDS`, `KINDS`,
`DEFAULT_KINDS`, ссылки в `/read`, MCP, WebUI `EntryKind`, payload Qdrant). В поиске по умолчанию
(`DEFAULT_KINDS`) — `term` и `question` (со статусом `answered`), `task` — только явным `kinds`.

## 2. Словарь домена (`term`)

### 2.1. Запись
`title` — каноническое имя (≤ 200 символов); `body` — подробности (Markdown);
`data: {aliases: [строки ≤ 200, до 32], definition: строка ≤ 300 символов (обязательна),
not_to_confuse: [≤ 16], code: [идентификаторы ≤ 200, до 32]}`; `links` — как у insight.
- **Уникальность.** Нормализованное имя и псевдонимы (`normalize_title`) не пересекаются с именами и
  псевдонимами других действующих (`active`) терминов того же пространства — иначе
  `409 /problems/term-conflict` с `{conflicts: [{id, title, matched}]}`. Векторной дедупликации нет.
- **Индексация.** Текст чанков термина: `# <title>`, строка `Псевдонимы: …`, `definition`, `body`;
  L0 — `definition`. Псевдонимы и `code` — в префиксе контекста чанка (FTS их находит).

### 2.2. Что словарь даёт механически
1. **Расширение запроса.** Перед FTS сервер находит в запросе (по словам, без учёта регистра)
   имена и псевдонимы действующих терминов пространств области поиска и строит дополнительный FTS-
   канал `alias`: запрос, где совпавшее слово заменено группой «имя OR псевдонимы». Канал сливается
   с весом `search.w_fts_alias` (0,5; 0..=1) — ниже исходного. Векторный канал и ключ кэша выжимок
   не меняются. В ответе — `expanded: [{term, with: [..]}]`. Словарь пространства кэшируется в
   процессе сервера с инвалидацией по версии (счётчик в `meta`, растёт при любой записи `term`).
2. **Подсказка к промпту.** `/recall(prompt)`: имя или псевдоним термина в промпте — строка
   `ZeroAIMemory: термин «<title>» — <definition> — t:<id>`, не больше 2 за промпт, каждый термин
   раз за сессию (`session_seen`).
3. **Дайджест старта:** строка `Словарь: N терминов — memory_search kinds=[term]` (N > 0).
4. **Единообразие.** Ответ на запись заметки или записи журнала (кроме `term`) несёт
   `warnings: ["term_alias: «<alias>» → «<title>»", …]` (до 5), если в тексте встречен псевдоним
   вместо имени (по границе слова). Запись не отклоняется.
5. **Ссылки.** `[[Имя]]` без заметки с таким именем разрешается в термин того же пространства по
   имени или псевдониму (ребро `links_to` к записи).

CLI: `zam glossary [<term>]` (список или карточка), `zam log term --title … --definition … --alias …`.

## 3. Журнал задач и передача работы (`task`)

`title`; `body` — план (Markdown); `data: {next_step ≤ 1000, blocked_by ≤ 1000, owner: agent|human,
links: [ссылки], claimed_by: {session, agent, until}, started_at, done_at, estimate_min?}`.
- **Переходы:** любой между `open, in_progress, blocked`; в `done`/`dropped` — из любого; из
  `done`/`dropped` — только в `open` (переоткрытие, с `reason`). `started_at` ставит сервер при первом
  переходе в `in_progress`, `done_at` — при `done` (снимается при переоткрытии).
- **Захват** — `POST /entries/{id}/claim {ttl_min: 1..=1440 (по умолчанию 120)}`: свободна, срок
  истёк или захвачена той же сессией — `claimed_by` ставится или продлевается; иначе
  `409 /problems/task-claimed {claimed_by}`. `POST /entries/{id}/release` снимает свой захват
  (чужой — только человек). Захват не ревизия записи (без `If-Match`), пишется в аудит записи.
- **Дайджест старта** — раздел `### Задачи` первым после уведомлений: `in_progress` и `blocked`
  (до 5, захваченные этой сессией первыми) строкой `ZeroAIMemory: [<status>] <title> — далее:
  <next_step> — k:<id>`; `blocked` — с `blocked_by`.
- **Checkpoint** (`Stop`): есть задача `in_progress`, захваченная сессией, и правки в сессии —
  напоминание включает «обнови next_step задачи k:<id>» (то же одно напоминание за сессию).
- **Время.** `GET /entries?kind=task&status=done` отдаёт `duration_min` (`done_at − started_at`).
  Агент оценивает сроки по фактическим длительностям похожих задач (правило в протоколе).

MCP: `memory_log kind=task`; `memory_update_entry action: status|claim|release|append` (`status` —
с `next_step`, `blocked_by`). CLI: `zam task [list|show|new|status|claim|release]`.

## 4. Вопросы к человеку (`question`) — с двух сторон

`title` — вопрос (≤ 500); `body` — контекст; `data: {options: [{key, text}] ≤ 8,
recommendation?: key, answer?: {text, option?, by: human|agent, channel: webui|chat|cli,
answered_at, decision_id}}`.
- **Задать:** агент — `memory_log kind=question`; дубликат по нормализованному заголовку среди
  `open` — 409 `possible-duplicate` (как у insight).
- **Ответить** — `POST /entries/{id}/answer {text?, option?, channel}` (хотя бы одно из двух):
  - из WebUI (страница «Вопросы», ответ в один клик по варианту или текстом) — `by: human`,
    `channel: webui`;
  - в чате с агентом: человек ответил в диалоге — агент записывает вопрос (если его ещё нет) и ответ
    сам, `channel: chat`; `by: human` (ответ человека, записанный агентом по его словам — правило
    блока инструкции, как `axiom` по прямому указанию, §7.5 ТЗ).
  - Сервер одной транзакцией: статус `answered`, `data.answer`, и новый insight `decision`
    (`title` — «<вопрос> → <ответ кратко>», `body` — вопрос, варианты, ответ; `certainty: axiom` при
    `by: human`, иначе `hypothesis`; `data.decision.decided_by` = `by`; ребро `derived_from`
    решение → вопрос). `decision_id` — в ответе.
- **Устарел** — `memory_update_entry action=status status=obsolete` с `reason`.
- **Дайджест старта:** `### Ответы человека` — вопросы, отвеченные за последние 14 дней и ещё не
  показанные этой сессии (`session_seen`), до 5; `### Открытые вопросы` — число и до 3 заголовков
  (чтобы агент не задавал уже заданное).
- **Не задавать отвеченное:** `memory_log kind=question` при совпадении заголовка с `answered` —
  409 `possible-duplicate` с этим ответом в `candidates`.

## 5. Решения с обоснованием (ADR) и противоречия

### 5.1. `data.decision` у insight `decision`
`{context?, options?: [≤ 8 строк], chosen?, rationale?, consequences?, decided_by?: human|agent,
revisit_if?}` — все поля необязательны, но если `data.decision` задан, он проверяется (строки ≤ 2000,
неизвестные ключи — 422). Фильтр поиска `filters.decided_by: human|agent`; карточка показывает
`chosen` и `decided_by`.
- **Близкие аксиомы.** При записи агентом insight `decision` (создание, supersede) сервер ищет
  действующие `decision` с `certainty: axiom` той же области того же пространства и Knowledge по
  dense-косинусу ≥ `insights.decision_conflict_threshold` (0,80); найденные (до 3) — в
  `warnings: ["decision_near_axiom: i:<id> «<title>»"]`. Запись не отклоняется (сервер не судит о
  смысле, LLM на сервере нет). Модель недоступна — проверка по заголовку и `warnings` с `degraded`.

### 5.2. Связь `contradicts`
Новый тип ребра `contradicts` (явный: `POST /edges`, `links` записи, `relations:` заметки).
Правило блока: «несогласен с аксиомой — запись `hypothesis`/`theorem` с `contradicts` к ней».
- **Влияние на выдачу** — **вариант (2), решение владельца 2026-10-28** (п. 14 журнала M4): запись,
  у которой есть исходящее `contradicts` к действующей `axiom`, при `rerank=on` не поднимается выше
  этой аксиомы, если обе в выдаче (аксиома переставляется на позицию сразу перед ней); метрика eval
  `reliable_first` при `rerank=on` — цель 1,000 на наборе M4 (`r-08`, `r-12`, `r-13` размечаются
  связью). Если выбран (1) — задача плана заменяется отдельными бустами `boost_*_rerank`, тип ребра
  остаётся. Порядок действует при любом `rerank` и только на первые `top_k` элементов выдачи;
  на выдачу без рёбер `contradicts` не влияет.

## 6. Привязка к файлам, устарелость и знание о файле

### 6.1. Ссылки на файлы
Таблица `file_refs(id, owner_kind node|entry, owner_id, solution_guid, path, content_hash NULL,
git_commit NULL, recorded_at, state ok|stale, stale_at NULL, stale_reason NULL)`, уникально
`(owner_kind, owner_id, path)`. `path` — относительно корня решения, `/`, лексически нормализован,
без `..` выше корня (иначе 422), ≤ 1000 символов, до 64 на запись.
- **Откуда:** у записей журналов — поле запроса `refs: {files: [{path, hash?, commit?}]}` (у
  changelog — и прежние строки `data.refs.files`, они становятся ссылками без хэша); у заметок —
  frontmatter `refs:` (список путей) и `verified_at:` (дата), `verified_at_commit:` (sha). `zam`
  (CLI и хук) сам дописывает `hash` (blake3 содержимого файла, 64 hex) и `commit`
  (`git rev-parse HEAD`, если это git), когда файл существует в рабочей копии; MCP-клиент хэш не знает
  — ссылка без хэша.
- **Решение** ссылки — решение записи; ссылки в Knowledge без решения — путь относительно корня
  проекта, где писал агент, `solution_guid` из `X-Zam-Solution` (может быть NULL — тогда ссылка
  только справочная, устарелость не отслеживается).

### 6.2. Устарелость
- **Сообщение об изменении.** `POST /files/changed {solution, files: [{path, hash}]}` (до 500 за
  запрос): для ссылок этого решения на этот путь (у участника общего решения — только в
  пространстве решения и его Knowledge): `hash` ≠ записанного → `state = stale`,
  `stale_reason = source_changed`; совпал — `ok`. Ссылка без записанного хэша (MCP, заметки)
  получает присланный хэш как ориентир и остаётся `ok` **(решение контроллера, задача 7,
  раунд 1)**: иначе все такие ссылки ложно устаревали бы при первой проверке; цена — изменение
  файла между записью ссылки и первым сообщением не замечается. Ответ — `{stale: N}`. Пишет
  клиент `zam` (хук и `zam refs check`); тела файлов не уходят.
- **Подтверждение.** Перезапись заметки или правка записи с теми же путями ставит новые хэши и
  `ok`; `POST /files/verified {solution, files}` — «проверено, знание актуально» (`zam refs verify
  <path>`).
- **В выдаче.** Карточка поиска и `/read` записи или заметки со ссылкой `stale` несут
  `stale_refs: [path]` и пометку «возможно устарело: изменился <path>». Ранжирование не меняется.
- **Свежесть по git.** `zam refs check [--since <commit>]`: пути ссылок решения (из `GET /file-refs`)
  сверяются с рабочей копией (blake3), с `--since` — сначала `git diff --name-only <commit>..HEAD`
  и `git status --porcelain` сужают набор; результат — `POST /files/changed`. Отправляются пути,
  чей хэш отличается от последнего записанного (и ещё без хэша — ориентир); удалённый файл —
  хэш из 64 нулей, ссылка становится `stale` **(исполнитель, задача 8)**.
- **Хук и очередь (задача 8).** `post-tool` на правку пишет `{path, hash}` в
  `.zeroaimemory/cache/changed-<сессия>.jsonl`; `prompt`, `session-start` (очереди всех сессий) и
  `checkpoint` отправляют её `POST /files/changed` в своём бюджете (до 500 путей, повтор пути —
  последний хэш); успех — очередь очищается, ошибка — остаётся. Файл больше 8 МБ хук не хэширует
  (его поймает `zam refs check`).
- **Пути на клиенте (задача 8).** `zam` нормализует путь по правилам сервера (копия функции,
  совпадение проверяет тест), относительно корня проекта (как `pre-tool`; абсолютный путь внутри
  корня принимается); на Windows — регистр из файловой системы, хвостовые точки и пробелы
  сегментов срезаются, имена устройств (`CON`, `NUL`, `COM1`, …) и `:` в имени отклоняются, сравнение
  без учёта регистра. `zam write --ref` дописывает путь в `refs:` frontmatter и после записи шлёт
  `POST /files/verified` с хэшем; коммит у заметки не хранится.

### 6.3. Знание о файле при чтении и правке
- `GET /file-refs?solution=<guid>` — индекс `{etag, refs: [{path, hash?, items: [{id, kind, title,
  state}]}]}` (до 5 записей на путь, `ETag`, `If-None-Match` → 304), кэш хука
  `.zeroaimemory/cache/file-refs.json` обновляется вместе с триггерами на `session-start`.
- **Хук** (локально, без сети): при чтении файла (Claude `PostToolUse` matcher `Read`; Codex — нет
  отдельного инструмента чтения, см. §10) и перед правкой (`pre-tool`) — строка
  `ZeroAIMemory: о файле <path> в памяти: <title> [<kind>] — <ref>; …` (до 3, раз за сессию на файл);
  ссылки `stale` — с пометкой «возможно устарело».
- `zam links file:<path>` и `memory_search {filters: {file: "<path>"}}` — «что память знает об этом
  файле».

## 7. Заметки: проверенные команды, возраст, чтение изменений

- **Проверенные команды** — заметки с `verified_at` (и `verified_at_commit`) во frontmatter
  **(решение владельца 2026-10-28)**; заготовка папки «Команды» не создаётся
  автоматически. Дайджест старта: строка `Проверенные команды: <path> (проверено <дата>)` для заметок
  решения с `verified_at`, до 3.
- **Возраст.** Элементы выдачи поиска и строки подсказок несут `age_days` (от `updated_at`, у заметок
  с `verified_at` — от него); в Markdown-ответе MCP — «N дн. назад».
- **Чтение изменений.** `POST /read` элемент `{since_rev: N}`: если текущая ревизия > N — ответ
  `diff` (унифицированный, как `GET /nodes/{id}/diff`) и `rev`; дифф длиннее полного текста — полный
  текст с `diff_skipped: true`; N = текущей — `unchanged` (как `if_rev`). У записей журналов —
  по снимкам ревизий (`title`, `body`, `data`).

## 8. Окружение в Vault

Решение владельца: хосты, стенды, доступы живут в Vault.
- Новые типы `host` и `environment`; открытые поля `data`: `purpose ≤ 500`, `address ≤ 500`,
  `limits ≤ 1000`, `notes ≤ 2000` (плюс прежние `username`, `url`, `description`); `secret` у этих
  типов необязателен.
- **Поиск.** `vault_fts` (FTS5 unicode61) над `title` и открытыми полями, обновляется в транзакции
  записи; `GET /spaces/{space}/vault?q=` — FTS (префиксы слов), значение и шифротекст в индекс не
  попадают никогда. Векторного индекса у Vault по-прежнему нет.
- **Дайджест старта:** `### Окружение` — до 5 записей `host`/`environment` решения и Knowledge:
  `<title> — <purpose>; <address>; ограничения: <limits> — v:<id>` (секрет — только раскрытием,
  `memory_vault action=get`, с аудитом).

## 9. Сессии, восстановление, субагенты, учёт

### 9.1. Локальный журнал событий сессии
Хуки ведут `.zeroaimemory/cache/events-<сессия>.jsonl` — только метаданные, строка JSON:
`{ts, ev, …}`, где `ev`: `prompt {len}`, `read {path}`, `edit {path}`, `cmd {exe, ok, err_fp?}`
(`exe` — первое слово команды без аргументов; `err_fp` — blake3 нормализованной ошибки, 16 hex),
`error {tool, err_fp, text ≤ 200 нормализованной ошибки}`, `subagent {agent_type, agent_id}`,
`compact {trigger}`, `memory_write {kind}` (из ответов `zam` и MCP не видно — пишет только CLI).
`ts` — миллисекунды Unix; строка ≤ 4 КиБ пишется одним `write` с append (длинное поле
укорачивается); файл > 1 МБ усекается с головы до ≤ 512 КиБ по границе строки через временный файл и
rename (усекает один процесс — замок), битые строки при чтении пропускаются **(исполнитель,
задача 8)**. Файл ≤ 1 МБ (старые строки отбрасываются с головы), права 0600 на unix, удаляется
через 7 дней, как `shown-*`. Для этого регистрируется Claude `PostToolUse` (matcher `Read|Write|Edit|MultiEdit|
NotebookEdit|Bash`) — команда `zam hook post-tool` (успех) с бюджетом 50 мс, без сети; Codex —
`PostToolUse` `Bash|apply_patch`.

### 9.2. Восстановление после сжатия и `resume`
- `SessionStart` с `source: compact | resume` → `/recall(session_start)` строит **пакет
  восстановления** в бюджете `recall.recovery_tokens` (2000): `### Задачи` (захваченные сессией и
  `in_progress`/`blocked`, с `next_step`), `### Ответы человека` (без фильтра «показано» — контекст
  потерян), решения (`decision`) решения за 7 дней, затем обычный дайджест (правила и т. д.) в
  остатке бюджета.
- Хук добавляет к тексту сервера локальную сводку журнала сессии (≤ 1500 символов):
  «До сжатия в этой сессии: правились <файлы до 10>; ошибки: N (последняя: <text>); исправлены:
  <пары §9.3>; субагенты: <типы>; записей в память: N». `PreCompact` пишет в журнал `compact` —
  побочное действие, вывода нет (инъекция на `PreCompact` не подтверждена документацией).
- Агентам без `SessionStart compact` — `memory_recall {event: "recovery"}` (тот же пакет) и правило
  протокола.

### 9.3. Кандидаты в insight: «ошибка → исправление» и петли
- **Пара.** В журнале сессии ошибка `cmd`/`error` с `err_fp`, затем правки (`edit`), затем успех того
  же `exe` → кандидат «<ошибка> исправлена правкой <файлы>». На `Stop` (`checkpoint`) — если
  кандидаты есть и после них в сессии не было `memory_write insight` — напоминание включает
  «запиши gotcha/failure с error_regex: <ошибка> (правки: <файлы>)» (в рамках одного напоминания за
  сессию).
- **Петля.** Тот же `err_fp` третий раз за сессию — `post-tool` добавляет строку
  «ZeroAIMemory: эта ошибка повторяется N-й раз в сессии — проверь память (memory_search) или запиши
  разбор» (раз на `err_fp`).
- Записывает агент; сервер ничего не создаёт сам.

### 9.4. Субагенты и пакет под задачу (`brief`)
- `POST /recall {event: "brief", task, budget_tokens?}` — пакет контекста под задачу в бюджете
  `recall.brief_tokens` (800): правила (L0, не L1), действующие `decision` с `axiom`/`theorem` по
  поиску `task` (до 3), термины словаря, встреченные в `task` (до 5, с определением), `gotcha`/
  `failure` по поиску `task` (до 3), записи о файлах, упомянутых в `task` (`file_refs`, до 3).
  `task` — до 2000 символов; без `task` — общий мини-дайджест (правила L0, ловушки, задачи сессии).
  MCP: `memory_recall {event: "brief", task}` — им пользуется агент, составляя задание субагенту, и
  субагент первым вызовом.
- **Хук `subagent-start`** (Claude `SubagentStart`, Codex `SubagentStart`): `zam hook subagent-start`
  берёт `task` из локальной очереди `cache/spawn-<сессия>.json`, которую пополняет `pre-tool` при
  запуске субагента (Claude: инструмент `Agent`/`Task`, `tool_input.prompt` — первые 2000 символов и
  `subagent_type`; хранится до 10 мин, до 8 записей; выдаётся старейшая с тем же `agent_type`); нет
  — общий мини-дайджест. Вывод — `additionalContext` (у Claude попадает в контекст субагента —
  подтверждено документацией; у Codex адресат не подтверждён — ⚠️ проверить на машине владельца).
  Бюджет хука 300 мс. Журнал сессии: `subagent`.
- **Атрибуция.** `POST /sessions` принимает `parent_id`, `agent_type`; хук `subagent-start` создаёт
  сессию `<session>:<agent_id>` с `parent_id`. Записи субагента через MCP идут в неявную сессию
  (R13) — атрибуция записи именно субагенту не гарантируется и в этапе не требуется.

### 9.5. Учёт выданных токенов (сбор для M6)
`session_tokens(session_id, event, calls, tokens)` в базе пользователя: `/recall` прибавляет размер
`text` по событию (`session_start`, `recovery`, `prompt`, `post_tool`, `brief`); хуки с локальным
выводом (`pre-tool`, `post-tool` успеха, `subagent-start` без сети) сообщают свои токены пачкой при
следующем сетевом вызове (`POST /sessions {tokens: {event: n}}`). `GET /sessions/{id}` отдаёт
`tokens: {event: {calls, tokens}}`. Анализ «польза по исходу задачи» и агентный A/B — M6.

### 9.6. Настройки подсказок
Типы `hooks.<тип>` (ТЗ §10.3) дополняются: `subagent_start`, `file_context` (знание о файле),
`session_journal` (журнал §9.1 и подсказки §9.3), `recovery`. Отсутствующий ключ — `true` на обеих
сторонах (старый `hooks.json` и старый сервер не выключают новое).

## 11. Блок инструкции v3 и протокол

`AGENT_BLOCK_VERSION = 3`. Добавляются правила (одной строкой каждое): задачи — `memory_log task`,
`status` с `next_step`, захват перед работой; вопросы человеку — `memory_log question`, ответ в чате —
записать ответом (`channel: chat`); новое понятие — в словарь, писать каноническими терминами;
знания о коде — с `refs.files`; несогласие с аксиомой — `contradicts`; без хуков — `memory_recall
recovery` после сжатия и `brief` для субагента. Предел блока — 500 токенов (тест ru/en, ТЗ §14.2);
подробности — в протоколе (`zam guide`). `zam init` и `/agent-setup` регистрируют новые события:
Claude — `SubagentStart`, `PostToolUse` (§9.1), `PreCompact` (→ `checkpoint`, журнал); Codex —
`SubagentStart`, `PostToolUse apply_patch`.

## 13. Критерии готовности (приёмка M4.5)

e2e (`crates/zam-cli/tests/m45_acceptance.rs`, процессы `zam-server` и `zam`):
1. **Сжатие.** Агент (хуки, Claude-формат) создаёт задачу, захватывает, ставит `in_progress` с
   `next_step`, правит файл, получает ошибку и исправляет её; `SessionStart source=compact` — в
   выводе задача с `next_step`, сводка журнала (файл, ошибка, пара «ошибка → исправление»).
2. **Вопрос с двух сторон.** Агент задаёт вопрос; человек отвечает в WebUI (REST сессии WebUI) —
   следующий `session-start` показывает ответ, создан `decision` `axiom` с `derived_from`; второй
   вопрос агент записывает с ответом из чата — тот же результат.
3. **Словарь.** Термин «Выжимка» с псевдонимом «summary»; поиск «summary» находит заметку со словом
   «выжимка» (канал `alias`); запись заметки со словом «summary» — предупреждение `term_alias`.
4. **Файл.** Insight со ссылкой на `src/a.rs` (хэш); правка файла хуком → `POST /files/changed` →
   поиск показывает «возможно устарело»; чтение файла — подсказка о записи без сети.
5. **Субагент.** `pre-tool` на `Agent` с заданием про тему решения → `subagent-start` выдаёт пакет с
   нужным `decision` и термином; бюджет ≤ `recall.brief_tokens`.
6. **Окружение.** Vault `host` с открытыми полями находится `vault?q=` и виден в дайджесте без
   секрета; секрет — только раскрытием с аудитом.
7. Миграция базы M4 (0014) → 0018 без потери данных, `foreign_key_check` чист.

Eval: набор запросов RU↔EN к словарю (`eval/glossary.toml`, ≥ 20 запросов) — полнота@5 с каналом
`alias` не ниже, чем без него, на основном наборе Δ nDCG@10 ≥ −0,005; бюджеты хуков новых событий
(`hook_budgets`); `reliable_first` при `rerank=on` — по выбору владельца (§5.2).
