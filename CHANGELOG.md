## [Unreleased]

### Added
- Манифест моделей `deploy/models.toml`: bge-m3 int8 (CPU) и fp16 (GPU) от Xenova со sparse-головой BAAI, тестовая MiniLM-L6 int8, реранкеры `bge-reranker-v2-m3` (GPU) и `jina-reranker-v2` (CPU, CC-BY-NC-4.0: не входит в `zam-models`, загрузка только с `--accept-nc-license`). Каждый файл закреплён ревизией Hugging Face и SHA-256.
- `cargo xtask fetch-models [--test] [--id ID]… [--accept-nc-license]` — загрузка моделей в `target/models/<id>/` с проверкой SHA-256; при несовпадении временный файл удаляется.
- `deploy/onnxruntime-gpu.toml` (ONNX Runtime 1.31.0 gpu_cuda13): `cargo xtask fetch-deps` скачивает его в `target/deps/<платформа>/onnxruntime-gpu/`.
- `deploy/cuda.toml`: redist-архивы NVIDIA CUDA 13.4.3 и cuDNN 9.27.0 (sha256 из `redistrib_*.json`) и список библиотек для `zam-server cuda fetch`; `fetch-deps` манифест проверяет, но не скачивает.
- CI: кэш `target/deps` и `target/models`, `fetch-deps` и `fetch-models --test` перед тестами.
- Чанкер §8.2 в `zam-markdown` (`chunk_note`): секции H1–H3 без повтора текста подсекций, листы 300–500 токенов (не больше 800 никогда) с балансировкой размеров, перекрытие в одно предложение внутри секции, склейка коротких секций (< 100) со следующим соседом того же родителя (через пустых соседей), а без него — с предыдущим, если склейка не длиннее 500 токенов. Блоки кода, таблицы, списки и callout (GitHub и Obsidian, в том числе `> [!info]-` и `> [!заметка]`) не рвутся; длиннее 800 токенов режутся по строкам или элементам с повтором заголовка блока (ограждение с info, шапка таблицы с разделителем, строка маркера callout). Уровни `section` (L1 секций H1–H2 из двух и более листов) и `note` (L1 заметки, до 300 токенов); L1 из одних заголовков и L1 секции, совпавший с L1 заметки, не индексируются. Счётчик токенов — типаж `TokenCounter`, без токенизатора — `ApproxCounter` (`ceil(символы / 3,5)`).
- Крейт `zam-ml`: ONNX Runtime 1.31 через `ort =2.0.0-rc.14` (`load-dynamic`, только `init_from` с явным путём, проверка версии `probe`; без библиотеки — `NoRuntime` без паники), выбор устройства `auto|cpu|cuda` с откатом на CPU и причиной (`DeviceReport`), две сессии (индексация и запросы) с общим `PrepackedWeights`, токенизатор `tokenizers =0.23.2` (`fancy-regex`), эмбеддер bge-m3 (dense CLS + sparse-голова из `sparse_linear.pt` без pickle) и MiniLM (mean pooling), LRU-кэш запросов на 1024, точный счётчик `BgeTokenCounter` без спецтокенов. Модели с динамическим int8-квантованием активаций (`dynamic_quant = true` в `[model.spec]`) прогоняются по одному тексту: иначе соседи по батчу сдвигают вектор (косинус ≈ 0,99).
- `cargo xtask fetch-models` пишет `<id>/model.toml` (id, `device` и `[model.spec]`) для `zam-ml`. CPU-вариант модели (`device = "cpu"`, int8) работает только на CPU и при `ml.device = auto|cuda`: векторы CPU и CUDA под одним `model_id` не смешиваются.
- Сегментатор предложений `split_sentences` (UAX #29, `unicode-segmentation` 1.13) с правилами для русских и английских сокращений, инициалов, чисел, версий, путей, URL и кода; `note_l1` и `section_l1` — оглавление с первым предложением каждой секции.
- `zam-store`, миграция 0004: кэш эмбеддингов `embeddings` (dense — f16 LE, sparse — пары u32 id + f16 вес; `put_embeddings`/`get_embeddings`) и outbox `index_jobs` (одно активное задание на узел, приоритет, backoff `min(2^n с, 1 ч)`, после 5 неудач — `failed`; обработка узла сериализована: запись во время обработки помечает задание `dirty`, завершение принимается только от текущей выдачи (`claim_gen`, `JobOutcome`), выполненные задания удаляются; `claim_jobs`, `complete_job`, `fail_job`, `requeue_running`, `enqueue_reindex`, `job_stats`), `chunks_for_index` с payload узла для Qdrant, `set_index_state` по актуальной ревизии, глобальный `set_token_counter`.
- Крейт `zam-index`: трейт `VectorIndex` (dyn-совместимый, boxed-future `IndexFuture`; `ensure`, `upsert`, `delete_node`, `search`, `drop_all`, `health`) и адаптер `QdrantIndex` на `qdrant-client =1.19.0` (gRPC, API-ключ). Коллекция `zam_chunks`: именованные `dense` (Cosine, HNSW m=16, оригиналы `Memory::Cold`, int8 scalar quantile 0.99 `Memory::Pinned`, rescoring) и `sparse` (`Memory::Cached`), `on_disk_payload`, 2 сегмента, метаданные `{model_id, schema: 1}`, payload-индексы `user_id` (`is_tenant`), `space_id`, `node_id`, `path_ancestors`, `level`, `updated_at`. Поиск — prefetch dense и sparse top-50 по `level=chunk` и dense top-10 по `note`/`section`, слияние RRF k=60, limit 60; фильтр всегда с `user_id`, `space_ids` и `levels` — match any, `path_prefix` — точное совпадение с одним из `path_ancestors`. id точки — UUIDv5(`NAMESPACE_ZAM`, `chunk_id`). `ensure` при другом `model_id` коллекцию не меняет и возвращает её `model_id`. Upsert пачками по 256 с `wait=true`; точки пространства `human` отклоняются. Ошибки: `Unavailable`, `Auth`, `Corrupt`, `Other` без векторов, текста и ключа.
- CI release: `fetch-deps` перед тестами (тесты `zam-index` запускают настоящий Qdrant из `target/deps`).
- Супервизор нативного Qdrant `zam_index::supervisor` (§4.3): рабочий каталог `<data_dir>/qdrant/`, генерируемый `config/zam.yaml` (JSON-журнал, телеметрия выключена, `127.0.0.1`, CORS и статика выключены, `on_disk_payload`, `max_search_threads`/`optimizer_cpu_budget`), случайный API-ключ на каждый старт только в `QDRANT__SERVICE__API_KEY` (унаследованные `QDRANT*` и `RUN_MODE` убираются из окружения), `QDRANT_INIT_FILE_PATH` внутри каталога. Привязка к родителю: Windows — Job Object с `KILL_ON_JOB_CLOSE` и `CREATE_NO_WINDOW` (`process-wrap =10.0.1`), Linux — `PR_SET_PDEATHSIG` с проверкой `getppid` из долгоживущего потока «qdrant-supervisor» (свой `current_thread` runtime) и своя группа процессов. Лок `.zam-qdrant.lock`, pid-файл `qdrant.pid`; осиротевший процесс завершается, только если он жив, запущен из нашего бинарника (Linux — ещё и с нашим рабочим каталогом) и держит наш порт, иначе устаревший pid-файл просто удаляется. Готовность: `/readyz` → `GET /` (версия = `deploy/qdrant.toml`, иначе `Broken`) → gRPC health. Журнал Qdrant → `tracing` (`component="qdrant"`, уровни из JSON). Перезапуск 1→60 с с jitter, 5 падений за 10 минут — `Broken`. Метка `zam-storage.json` (атомарная запись с fsync; нечитаемая метка считается отсутствующей): откат или скачок больше чем на одну минорную версию → стирание `storage/` до запуска; panic «Collection version is greater» / «Cannot upgrade version» → стирание и один перезапуск; флаг `.zam-reindex` держится до `ack_storage_rebuilt`, состояние `Ready { version, rebuilt }`. Паника потока супервизора публикует `Broken`. Остановка: Linux SIGTERM → 10 с → SIGKILL, Windows `TerminateProcess`. Режим `external` — без процесса.
- `zam-server qdrant fetch [--manifest PATH]` (бинарник по встроенному `deploy/qdrant.toml` с проверкой SHA-256, только если его нет; соседние файлы вроде `vcruntime140.dll` не трогаются), `qdrant status` (режим, бинарник, порты, лок, pid, метка, ответ процесса; ничего не запускает), `qdrant reset --yes` (завершает осиротевший процесс и стирает хранилище остановленного Qdrant, при старте — пересборка из `embeddings`).
- Секция `[qdrant]`: `binary`, `max_search_threads = 2`, `optimizer_cpu_budget = 2`, `api_key` (только для `external`); `url` — gRPC-адрес внешнего Qdrant.
- Крейт `zam-fetch`: манифест зависимости, загрузка, SHA-256, извлечение из zip/tar.gz и атомарная установка — общие для `cargo xtask fetch-deps` и команд сервера.
- Модель и Qdrant в сервере (`IndexRuntime` в `AppState`): при старте `init_runtime` → `Embedder::load` (до первого открытия базы пользователя — счётчик токенов модели ставится через `set_token_counter` из `Embedder::token_counter`), затем супервизор Qdrant и клиент; без ORT, модели или Qdrant сервер стартует в режиме FTS-only, причина — одной строкой WARN с подсказкой (`zam-server models fetch`). `vector_available()` → `no_runtime | no_model | qdrant_down | broken | qdrant_locked | model_mismatch` (`qdrant_locked` — каталог Qdrant занят другим экземпляром). Модель по умолчанию — `bge-m3-fp16` в GPU-комплекте при поднявшейся CUDA, иначе `bge-m3-int8`. Без модели Qdrant не запускается. Остановка: воркер, ожидание перечанковки R1 (до 10 с), `Supervisor::shutdown`.
- Секции `[ml]` (`device = "auto"`, `models_dir` — по умолчанию `<data_dir>/models`, `embed_model`, `ort_dylib`, `index_threads = 0`, `query_threads = 2`, `unload_after = ""`) и `[index]` (`batch_tokens = 8192`, `yield_ms = 5`, `rollup_debounce_ms = 2000`).
- Воркер индексации `zam_index::worker` (одна задача tokio): базы пользователей по кругу, пачки по 8 заданий → `chunks_for_index` → кэш `embeddings` по `embed_key` — blake3 ровно той строки, что уходит в модель (`embed_input`: `context_prefix + "\n" + text`; тот же текст в другой заметке — отдельный вектор) → инференс промахов (`spawn_blocking`, пачки ≤ `batch_tokens`) → `delete_node` + `upsert` → `complete_job` → `indexed` только при `Done`. Qdrant недоступен или коллекции нет — задания возвращаются в очередь без траты попыток (`release_job`), новые не берутся до возврата Qdrant (пробуждение по состоянию супервизора и `notify` из записей API). Коллекция с чужим `model_id` не трогается: векторный канал выключен до reindex. Пересборка хранилища Qdrant (`storage_rebuilt`) и пересозданная коллекция при проиндексированных узлах → `enqueue_reindex` во всех базах (векторы из `embeddings`, без инференса); база, которая не открылась, пропускается и повторяется отдельно, остальные не перечанковываются повторно и индексируются; аудит `index.storage_rebuilt` (actor `system`) и `ack_storage_rebuilt` — когда прошли все базы. Паника задачи воркера выключает векторный канал (ERROR в журнале). Неудачное задание `delete` — WARN с id узла.
- L0 (§8.3): автоматический L0 заметки — предложение, ближайшее к центроиду эмбеддингов её листов (≤ 50 токенов), только при `l0_source = 'auto'`; L0 папок — свёртка L0 детей по свежести (≤ 50 строк, без `index: false`) с дебаунсом, без ревизии; при переносе узла API сообщает воркеру старого родителя — его свёртка и точка пересчитываются; точка папки уровня `folder` в Qdrant (кроме Human). `zam-store`: `set_auto_l0`, `set_folder_l0`, `release_job`, `indexed_count`.
- `VectorIndex::count(filter)`; `IndexError::NotFound` (коллекции нет).
- `zam-server migrate` перечанковывает (R1) точным счётчиком токенизатора модели, если он есть, и дожидается завершения перед выходом.
- Гибридный поиск `POST /api/v1/search` (§9.2): параллельно FTS5 и — если векторный канал доступен — эмбеддинг запроса (сессия запросов, `spawn_blocking`) и Qdrant (dense + sparse по листам, dense по сводкам) по пространствам области без Human. Векторные хиты проверяются по SQLite: чанк текущей ревизии, узел жив, не в корзине, не `index: false`, в области — точки, оставшиеся в Qdrant после неудачного `delete`, в выдачу не попадают. Слияние — новый крейт `zam-search`: weighted RRF трёх каналов (`vector`, `fts` — bm25, `trigram`), затухание по свежести `0,5 + 0,5·2^(−возраст/полупериод)`, сводка заметки сливается с найденным листом узла, сводка секции — с листом своей секции, иначе заменяется лучшим листом (ближайшим к запросу по косинусу из кэша `embeddings`, без вектора — листом с наибольшим числом слов запроса по индексу FTS; без совпадений сводка остаётся), затем не больше `max_per_node` элементов с узла; пути листов сводок читаются одним запросом, тексты — только у листов-кандидатов; сводка за окном кандидатов без листа в выдаче отбрасывается; упаковка в `budget_tokens` по токенам. Ответ: `degraded`/`degraded_reason` из `DegradedReason` (новые причины запроса — `embed_failed`, `search_failed`; сбой эмбеддинга или Qdrant не даёт 500), `timings {fts_ms, embed_ms, vector_ms, fuse_ms}`, у элементов `sources`, `level`, `tokens`, `score` 0..1. `expand`: `section` (собственный текст секции), `neighbors` (с соседними листами), `graph` → 400 (M3).
- Секция `[search]`: `rrf_k = 60`, `w_vector = 1.0`, `w_fts = 1.0`, `w_trigram = 0.7`, `recency_half_life_days = 180`, `max_per_node = 3`.
- `zam-store`: `search_fts_channels` (каналы bm25 и trigram без слияния), `live_chunks`, `node_leaves`, `neighbor_leaves`, `query_needles`, `text_snippet`, `count_tokens`; у `FtsHit` — `level` и `token_count`. `zam-index`: `embed_input_of`, `embed_key_of`.

- Реранкер `zam_ml::Reranker` (§9.2 п. 5): cross-encoder XLM-RoBERTa (`jina-reranker-v2` int8 для CPU, `bge-reranker-v2-m3` fp16 для GPU), пары «запрос — фрагмент» токенизатором модели, батч до 16 тыс. токенов, выход `logits` f32 или f16, балл `sigmoid` в 0..1; `score` и `score_capped` (предел фрагмента). Одна сессия на модель; потоки — `ml.index_threads`; вариант `device = "cpu"` на GPU не запускается. Замер (Ryzen 9 5900X, 12 ядер, release): jina 20 × 256 токенов — 1,6 с, bge-reranker-v2-m3 fp16 на CPU — 8,2 с, на CUDA (RTX 3090) — 79 мс. `RerankSpec` читает `role = "rerank"`; эмбеддер не грузится как реранкер и наоборот.
- `POST /search` с `"rerank": "on"` (по умолчанию `off`): первые `ml.rerank_top` (20) кандидатов после `note_to_leaf` и лимита на узел переставляются по баллу реранкера (заголовок секции и текст чанка, фрагмент до `ml.rerank_tokens` = 256 токенов), хвост — в порядке слияния, лимит на узел соблюдается и после перестановки. Модель — по устройству эмбеддера (CPU → `ml.rerank_model_cpu`, CUDA → `ml.rerank_model_gpu`), загружается при первом таком запросе в `spawn_blocking`; неудача запоминается на минуту (поставленная `models fetch` модель подхватится без перезапуска). Нет модели — ответ без реранка и `warnings: ["reranker not installed"]`, ошибка или паника загрузки и инференса — `["reranker failed"]`, не 500. В ответе — `warnings` (всегда), `timings.rerank_ms`, у переставленных элементов `rerank_score`; в `md` балл карточки — реранка, предупреждения — строками `> warning: …`.
- Секция `[ml]`: `rerank_model_cpu = "jina-reranker-v2"`, `rerank_model_gpu = "bge-reranker-v2-m3"`, `rerank_top = 20` (1..=100), `rerank_tokens = 256` (8..=1024).
- `zam-server models fetch [--device cpu|gpu] [--reranker] [--id ID]… [--accept-nc-license] [--manifest PATH]`: модель эмбеддингов устройства (по умолчанию — по `ml.device` и комплекту: CUDA EP рядом с ORT → gpu; `ml.embed_model`, если задана), с `--reranker` — реранкер устройства, в `ml.models_dir`. Каждый файл сверяется по размеру и SHA-256 встроенного `deploy/models.toml`; в каталоге модели пишутся `LICENSE` (SPDX, ссылка на текст лицензии и карточку модели) и последним `model.toml` (с `role`). Реранкер jina (CC-BY-NC-4.0) без `--accept-nc-license` не скачивается: команда завершается с текстом о лицензии до первой загрузки. `zam-server models status [--verify]` — модели манифеста, их состояние (установлена / нет / неполная) и устройство по умолчанию.
- `zam-server cuda fetch [--manifest PATH]`: библиотеки NVIDIA (CUDA 13.4.3, cuDNN 9.27.0) по встроенному `deploy/cuda.toml` плоско в `<каталог ORT>/cuda/` (оттуда их предзагружает zam-ml); размер и SHA-256 каждого архива сверяются, рядом пишется штамп `.<компонент>.sha256`. Архив пропускается, только если штамп совпал с манифестом и файлы на месте, иначе (новый выпуск в `cuda.toml`, файлы без штампа) библиотеки перекачиваются и заменяются. CPU-комплект (нет `onnxruntime_providers_cuda` рядом с ORT) — отказ с объяснением.
- `zam-fetch`: разбор и проверка `deploy/models.toml` и `deploy/cuda.toml` (`ModelsManifest`, `CudaManifest`, `fetch_model`, `install_cuda`, `model_state`) перенесены из xtask — один разбор у `cargo xtask fetch-models` и сервера. Архивы tar.xz (`lzma-rust2 =0.22.0`, чистый Rust, Apache-2.0); в tar под нужным именем допускается символическая ссылка на обычный файл того же каталога (SONAME NVIDIA `libcudart.so.13 → libcudart.so.13.4.92`, в cuBLAS — `./libcublas.so.13.8.0.4`; цепочки до 8 ссылок): под именем ссылки кладётся сам файл, ссылки наружу — ошибка. Размер из манифеста (`size`, в `PlatformEntry` — необязательный) сверяется, тело длиннее обрывает загрузку; `*.part` прерванных прошлых загрузок того же файла удаляются при следующей. Ошибки `SizeMismatch`, `LicenseNotAccepted`; контекст (компонент, модель и файл) добавляется без потери варианта ошибки. `install_archive(entry, dir, key)` пишет штамп `<dir>/.<key>.sha256` (SHA-256 архива, формат штампа `fetch-deps`) и пропускает установку только при совпавшем штампе (`is_installed`); `qdrant fetch` по-прежнему не трогает уже стоящий бинарник каталога версии.
- Тест zam-index: Qdrant убит посреди работы — `health`, `search`, `upsert`, `count`, `ensure`, `delete_node` того же клиента дают `IndexError::Unavailable`, после перезапуска клиент работает без пересоздания.
- `GET /api/v1/index/status`: векторный канал (`available`, `reason`, `hint`), устройство (`cpu`/`cuda` с причиной), модель (`id`, `dim`, `collection_model`), Qdrant (`state`, `version`, `rss_bytes` из ОС по pid — Windows `GetProcessMemoryInfo`, Linux `/proc/<pid>/statm`, `points`, `restarts`), очередь, до 20 неудавшихся заданий, последний reindex, базы, исключённые из пересборки. Токен видит только своего пользователя; администратор — `X-Zam-User` или сумму по всем.
- `POST /api/v1/admin/reindex {user?, space?, full?}` (администратор, аудит `index.reindex`, ответ 202 с `job_count`) и `zam-server reindex [--user ID] [--space REF] [--full]` для остановленного сервера (каталог данных под локом; запущенный сервер — понятная ошибка). ### Fixed
- Windows: каталог данных длиннее ~210 символов давал при старте невнятное «ошибка sqlite: unable to open database file» (база пользователя `users\<uuid>.db` и её журналы выходили за MAX_PATH). Теперь `DataDir::open` проверяет длину до создания каталогов и при пути длиннее 190 символов (запас на копии баз перед миграцией) отказывает с ошибкой `StoreError::DataDirTooLong`, в которой названы длина, предел и как его обойти (`data_dir`, `ZAM_DATA_DIR`, `--data-dir`); предел описан в `deploy/README-install.md`. Проверка (`zam_store::check_data_dir_len`, префикс `\\?\` не считается) выполняется и в CLI до работы: `migrate`, `reindex`, `qdrant …`, `models …`, `cuda fetch` отказывают сразу, а не после долгой загрузки.
- Повреждённая база одного пользователя больше не ломает `GET /index/status` администратора (сумма по всем), `POST /admin/reindex {}` и `zam-server reindex` без `--user`: при обходе всех баз неоткрывающиеся пропускаются и перечисляются (`unavailable_dbs` в ответах, строка в отчёте CLI); база, указанная явно, — по-прежнему ошибка.
- Исключение базы из пересборки индекса переживает перезапуск: отметка хранится в `system.db` (миграция system 0002, таблица `index_skipped`; API `SystemStore::index_skip/index_unskip/index_skipped`). Воркер загружает её при старте; когда база снова открывается, в ней ставится отметка reindex из кэша, а исключение снимается — точки возвращаются без инференса. Базы, которые не открыл reindex (в том числе при пересоздании коллекции), отмечаются так же и видны в `rebuild_skipped`.
- Прерванный reindex при чужой модели коллекции возобновляется: при запуске воркер обходит все базы и читает отметки `reindex_pending` до ворот коллекции.
- Служебные эмбеддинги до v5 (без владельца) при попадании в кэш присваиваются узлу (`adopt_owned_embeddings`) и сборкой мусора не снимаются; папка без эмбеддинга L0 в кэше получает свёртку воркера (`ReindexReport::missed_folders`), а в CLI — эмбеддинг моделью сразу.
- `UserDbs::get` держит глобальный замок только на поиск ячейки базы: открытие, миграции и дозаполнение ключей одной базы не задерживают другие.
- Статус воркера `batch_running` (пачка с auto-L0 после закрытия заданий): «покой» в тестах — пустая очередь, `batch_running == false` и `rollups_pending == 0`. Точки пачки строятся один раз.
- Нестабильные под нагрузкой HDD тесты: `zam-index worker::indexes_replaces_and_deletes_points_and_skips_excluded` (гонка теста: замер счётчика модели до отложенной свёртки L0 папки; теперь ожидание покоя воркера) и `zam-server index_worker::twenty_notes_indexed…` (медленные записи `wait=true` — по две на задание при десятке параллельных Qdrant; исправлено пакетной записью). Помощник тестов `TestQdrant` ограничивает число одновременно запущенных Qdrant в бинарнике теста (`ZAM_TEST_QDRANT_MAX`, по умолчанию 4): тесты zam-index worker — 128 с вместо 345 с.
- Windows: управляемый Qdrant ломался на длинном каталоге данных (от ~80 символов, например внутри `target/smoke/…`): относительные пути `./storage` в `zam.yaml` вместе с глубокими файлами payload-индексов превышали MAX_PATH (260), создание индекса `updated_at` давало «failed to open mutable numeric index on gridstore» (os error 3), векторная индексация не начиналась, а следующий запуск Qdrant падал при загрузке коллекции. Теперь на Windows `storage_path`, `snapshots_path` и `temp_path` пишутся абсолютными в форме `\\?\…` (UNC — `\\?\UNC\…`, пути `\\?\…` и `\\.\…` не меняются; относительный `data_dir` — от текущего каталога); на Linux — по-прежнему относительные. Найдено smoke-тестом комплекта.
- Windows: `onnxruntime.dll` (и CPU, и GPU) импортирует MSVCP140, MSVCP140_1, VCRUNTIME140 и VCRUNTIME140_1, а `onnxruntime_providers_cuda.dll` ещё MSVCP140_ATOMIC_WAIT; на чистой Windows без VC++ Redistributable ONNX Runtime не загружался и сервер работал только по полнотексту. Теперь эти библиотеки лежат app-local рядом с `zam-server.exe` (из VC Redist установленной Visual Studio, `LICENSES/MSVC-RUNTIME-NOTICE.txt`), smoke проверяет таблицы импорта.

## [0.0.2-m1] - 2026-10-18

Этап M1: заметки. Markdown-заметки с историей, патчами секций, корзиной, вложениями и полнотекстовым поиском — через REST API, CLI `zam` и WebUI.

### Added
- Markdown (`zam-markdown`, comrak): разбор с байтовыми позициями (BOM, CRLF, кириллица), frontmatter (`tags`, `description`, `l0`, `index`), секции H1–H3 с путями вида `Установка > Linux`, вики-ссылки и ссылки на вложения. PATCH секций — байтовый splice исходника: байты вне изменённого диапазона не меняются, переводы строк документа сохраняются.
- Рендер HTML на сервере: GFM, сноски, формулы, callout `> [!тип]` (тип — буквы любого алфавита, например `[!заметка]`), подсветка кода (syntect; не больше 256 КиБ кода на документ, остальные блоки — без подсветки), Mermaid и KaTeX на клиенте; HTML проходит ammonia (сырой HTML из заметок не исполняется), `POST /api/v1/render` для предпросмотра (до 1 МБ). Кэш HTML сразу видит появление, перенос, удаление и восстановление целей вики-ссылок и загрузку вложений.
- Заметки и папки в пространствах Knowledge, Rules, Human и решениях: создание, чтение (`md` как сохранён, `html`, `json`, L0 — сводка, L1 — оглавление, секция по пути), замена с `If-Match` (конфликт → 409 с текущей ревизией и диффом), PATCH секций (правка чужой секции с той же базовой ревизией проходит), перемещение, корзина и восстановление. Предел заметки — 5 МБ.
- История: каждая правка — новая ревизия (автор человек/агент/система, машина, сессия, сообщение), дифф между ревизиями, откат к ревизии; удаление, восстановление и откат пишутся в аудит. Ревизии неизменяемы и на уровне базы (триггеры запрещают UPDATE и DELETE). PATCH вставляет пустую строку там, где вставленный абзац иначе слился бы с соседним.
- Поиск `POST /api/v1/search`: FTS5 (слова + trigram для идентификаторов), область — текущее решение, Knowledge и Rules или все решения, режимы `brief`/`chunks`/`notes`, бюджет токенов, вывод JSON или Markdown, `pending_count` — заметки области, ждущие векторной индексации. Синтаксис FTS5 в запросе (`"`, `*`, `AND`, `NEAR`, …) ищется как обычные слова. Заметка без собственного текста (только заголовок) находится по названию. `index: false` во frontmatter исключает заметку только из будущего векторного индекса (§6.4), полнотекстовый поиск её находит.
- Запись: checkpoint WAL выполняется фоновым потоком, а не писателем; p95 записи на HDD — около 3 мс (см. `docs/journal.md`).
- Вложения: загрузка до 200 МБ (`POST /api/v1/blobs`, sha256, дедупликация), ссылки `_attachments/…` в заметках, выдача с Range (видео перематывается); HTML и SVG отдаются как `attachment` с CSP `sandbox` и не исполняют скрипты в origin сервиса.
- Доступ: Human по токену недоступен ни в каком виде (и не показывается в `GET /api/v1/spaces`); Rules токен только читает, если не включено `rules.agent_write`; токен `ro` не пишет; администратор видит заметки пользователей.
- CLI `zam`: `tree`, `read`, `write`, `history` (`--diff`, `--revert`), `search`, `attach`; цели `[пространство:]путь` или id узла, решение по `.zeroaimemory/solution.toml`; конфликт ревизий печатает дифф и завершается кодом 4. Коды выхода — в `deploy/README-install.md`.
- WebUI: дерево пространств (создание, перенос, корзина), просмотр документа (оглавление, подсветка, формулы, диаграммы, картинки, видео, копирование кода, вики-ссылки), редактор с предпросмотром (Ctrl+S, конфликт правок с диффом, переводы строк файла сохраняются), история с диффом и откатом, поиск Ctrl+K, вложения кнопкой, вставкой из буфера и перетаскиванием. Начальный бандл 55 КБ gzip, редактор грузится лениво.
- Smoke комплекта проверяет заметку через `zam`: запись, поиск, чтение побайтно.

### Known limitations
- Векторного поиска нет: `/search` отвечает `degraded: true` (FTS) — эмбеддинги и Qdrant в M2.
- Журналов, графа знаний и MCP пока нет — следующие этапы.
- Mermaid рисует без раскладки ELK (`layout: elk` показывает исходник): лицензия elkjs EPL-2.0 не входит в разрешённые.
- PDF, открытый по прямой ссылке, может не показываться встроенным просмотрщиком Chromium из-за CSP `sandbox` — просмотр PDF в M5.
- Повтор `POST /nodes` после обрыва связи даёт 409 (путь занят): Idempotency-Key — в M3.
- На HDD редкие записи (около 1 из 300 при непрерывной записи) ждут до 0.5–0.6 с — ввод-вывод фонового checkpoint WAL; p95 записи укладывается в цель (см. `docs/journal.md`).
- Чанкинг в M1 — один чанк на секцию; размеры чанков и слияние мелких секций (§8.2) — в M2.
- Внешние картинки (`![](https://…)`) не показываются: CSP страницы `img-src 'self'`; предупреждение в рендере — позже.
- Поиск цели вики-ссылки по имени учитывает регистр — в M3.
