## [Unreleased]

### Changed
- Права `certainty` (§7.5, решение владельца 2026-10-26): `axiom` ставит, правит и снимает и агент — по прямому указанию пользователя (правило инструкции, сервер не блокирует); агенту любая смена статуса — с `reason`, `→ theorem` — ещё и с доказательством; человеку в WebUI причина и доказательство для `theorem` необязательны; `system` статусы не проверяет. 403 `axiom-requires-human` и 422 `invalid-transition` упразднены — нарушения матрицы только 422 (`evidence-required`, `reason-required`). Insight человека без явного статуса — без статуса (было `axiom`). Рёбра от `axiom` агент создаёт и удаляет сам.
- `PATCH`/`DELETE /entries/{id}` требуют `If-Match: <rev>` (§11.3): без него 428 `/problems/precondition-required`, расхождение — 409 с `rev` текущей; `supersede`, `retract`, `restore` проверяют `If-Match`, если он передан. `zam insight certify|append|revisit` берут ревизию из `GET /entries/{id}`; при конфликте — «запись изменилась (rev N → M): перечитайте», код 4. WebUI Insights правит с ревизией открытой записи.

- Vault при заблокированном мастер-ключе (§7.6, решение владельца 2026-10-26): `GET /spaces/{space}/vault`, `GET /vault/{id}` без `reveal` и `GET /vault/{id}/revisions` отвечают 200 с полем `locked` (`true` и `reason` при блокировке; значений и шифротекста нет), значения, создание, правка и удаление — прежний 503 `vault-locked`. `zam vault list` печатает список и строку «Vault заблокирован: <причина>» в stderr; WebUI показывает список с баннером, «Показать» неактивна.
- `GET /triggers` при недоступном решении — как поиск (§10.3): `pending|rejected|revoked` — 200 с триггерами Knowledge и `warnings: ["solution access <state>"]`, неизвестный GUID (или нет запроса доступа) — `solution unknown`, недоступная база владельца — `solution unavailable`; параметр `solution` не GUID — 400, некорректный заголовок `X-Zam-Solution` игнорируется. Ответ несёт `warnings` (пустой массив без предупреждений), `ETag` — blake3 канонического JSON `{triggers, warnings}`.

- Умолчание `[index] chunk_boundary_lambda` — 0 (было 0,5; решение владельца 2026-10-26, §8.2): жадная упаковка M2 со структурными исправлениями M3, путь динамического программирования — при λ > 0. Базы при первом открытии `0.0.5-m4` разово перенарезаются в фоне (векторы — из кэша, инференс только для изменившихся листов).
- Умолчания Qdrant `flush_interval_sec = 3` (было 5) и `shutdown_flush_wait_ms = 14000` (было 10 000; §4.3, §17); юнит systemd — `TimeoutStopSec=94`, NSSM — `AppStopMethodConsole 94000` (`max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с, R4).
- `rerank=on` (§9.2 п. 5, решение владельца 2026-10-26): бусты вида, области и `certainty` применяются и к баллу реранкера (`score = rerank_score × boost_kind × boost_area × boost_certainty`, затем деление при переполнении; затухание и канал папок — нет); одна функция бустов `zam_search::apply_boosts_to` на оба пути. `rerank_score` — сырой балл реранкера, `score` (и балл карточки `md`) — с бустами.

Свои токены — `GET/POST /auth/tokens`, `DELETE /auth/tokens/{id}`. BOM в начале файлов сохраняется, файлы проекта пишутся атомарно, решение регистрируется после проверки всех файлов; `--agent codex` не пишет `.mcp.json` (MCP Codex — `~/.codex/config.toml`). `GET /api/v1/agent-setup?agent=claude|agents|codex&solution=<guid|new|auto>&name=&mcp=&hooks=&rules_write=&lang=ru|en` — блок, `solution.toml`, фрагменты `.mcp.json` и хуков (Claude Code — exec form, Codex — строкой с `--agent codex`, `PreToolUse` — `Bash|apply_patch`), команды установки `zam` и однострочник `zam init` для POSIX shell и PowerShell (`init_cmd: {linux, windows}`, аргументы в одинарных кавычках), `warnings` при блоке больше 500 токенов (имя решения в блоке — до 40 символов); `GET /api/v1/agent-guide` и `zam guide` — полный протокол работы с памятью. Шаблоны блока (ru/en, по агентам) — в `GET/PATCH /admin/settings` (`agent_setup.templates`, `null` — сброс); каждое сохранение увеличивает версию блока, `/recall(session_start)` и `zam status` напоминают об устаревшем блоке по ней.

Переключатели `[hooks] session_start|prompt|pre_tool|post_tool|checkpoint` в `~/.zeroaimemory/config.toml` и `.zeroaimemory/config.toml` проекта и настройка сервера из `/recall`. `zam triggers sync` — принудительное обновление кэша. Codex `apply_patch` — пути из заголовков патча. Команды `zam`, запущенные агентом (`CLAUDECODE=1`, переменные Codex, `ZAM_AGENT=1`), шлют `X-Zam-Session` текущей сессии хуков проекта; `ZAM_SESSION` — явно (`-` — без сессии).

Ответы — компактный Markdown (`format: "json"` — JSON), последняя строка `~N tok`; ошибки сервиса — результат `isError: true` с problem и подсказкой (409 — текущая ревизия и дифф, 428 — какую ревизию передать). Секция `[recall]` конфигурации.

Срок жизни — 30 дней без обращений и 2000 выжимок на базу (воркер обслуживания). Секция `[cache]` конфигурации; CLI `zam cache put|list|show|rm`.

### Fixed
- Проверка на стенде Debian 13 (2026-10-27): `zam read <путь> --section "Тесты"` находит секцию по однозначному хвосту пути заголовков (`Сборка > Тесты`), если полного пути нет (и в `GET /nodes`, `POST /read`, MCP `memory_read`); при 404 с `--section` CLI поясняет, что не найдена заметка или секция.
- `zam read` (и `--batch`) принимает ссылки выдачи `zam search`: `n:<id>` — узел, `i:|c:|e:|r:<id>` — запись журнала (без пачки — текст записи через `POST /read`, `--json` — элемент).
- Первый токен администратора больше не попадает в journald: если stderr не терминал (служба, перенаправление), токен пишется в `<data_dir>/first-admin-token.txt` (0600; на Windows — DACL владельца, как `master.key`), в stderr — путь к файлу; в терминале — рамка, как раньше.
- Журнал без ~160 строк INFO `memory_serve` при старте: цель ограничена `warn`, как `rmcp`.

### Removed
- Человеческие токены (§11.4): `human: true` при выпуске — 400, поле `human` убрано из токенов, `/auth/me`, `GET /spaces` и аудита; колонка `tokens.human` не читается (старые такие токены — агентские, при старте сервер пишет о них WARN). CLI: флаг `--human` и ключ `human_token` в `~/.zeroaimemory/config.toml`; WebUI: флажок «для человека».

## [0.0.4-m3] - 2026-10-26

Этап M3: журналы и граф. Совместный доступ к решению (память решения — в базе владельца,
разрешения — в `system.db`), журналы Changelog, Releases и Insights с замещением и отзывом,
эпистемический статус `axiom|theorem|hypothesis`, граф связей и wiki-ссылки, сканер
секретов перед индексацией, Vault с шифрованием и аудитом раскрытия, поиск по точкам папок,
нарезка с учётом силы границ, раскладка ELK для Mermaid, WebUI журналов и доступа. Качество
поиска на наборе M3 (182 заметки, 326 запросов, `eval/results/2026-10-25-*-m3-final.*`):
гибрид int8 CPU — recall@5 0,847, nDCG@10 0,824, `reliable_first` 1,000, «вспомнил
отменённое» (`cancelled@5`) 0,000, chunk-recall@5 0,971; с реранком на GPU — 0,906 / 0,869.

### Added
- Совместный доступ к решению (§11.6): реестр решений и разрешений в `system.db` (миграция system 0003), первый зарегистрировавший GUID — владелец; `POST /solutions` (201 — владелец, 202 — запрос `pending`), `GET /solutions/{guid}/access`, `POST /solutions/{guid}/access/{user}/approve|reject|revoke` (режим участника `rw` по умолчанию или `ro`), `zam solution access list|requests|approve|reject|revoke`. Участник работает только в пространстве решения базы владельца: Knowledge, Rules, Human и Vault владельца, его рёбра в другие пространства и узлы вне решения — 404; ожидающий, отклонённый и отозванный — 403 `/problems/solution-access` со `state`. Проверка — на каждом запросе, без кэша: отзыв действует со следующего запроса того же токена. Решения M1–M2 регистрируются при старте; конфликт GUID двух пользователей — локальное решение второго переименовывается, к исходному ставится запрос доступа. `GET /spaces` — `role`, `access`, `owner`, `shared`, `access_requests_pending`; `zam status` — роль в решении.
- Атрибуция автора ревизий `user_id` (миграция user 0007): правка участника ложится в базу владельца с его пользователем и токеном.
- `/admin/settings` — `rules.agent_write` (запись агентов в Rules).
- Поиск по личной памяти и доступным решениям владельцев одним запросом (`scope.solution`, `X-Zam-Solution`, `scope.spaces`, `all_solutions`): исключённое решение — `warnings: ["solution access pending|rejected|revoked"]` или `solution unavailable` (сбой базы владельца не даёт 500). Фильтр Qdrant — по областям `(user_id владельца, space_ids)` без пересборки коллекции; новые поля payload и индексы добавляются в существующую коллекцию.
- Записи журналов (миграция user 0008): `entries`, append-only `entry_revisions`, чанки, индексация и выдача в поиске (`entry_id`, `kind`, `status`, `insight_kind`, `certainty`, `title`); `filters.kinds`, `filters.status`, `include_history`; `Idempotency-Key` (повтор с другим телом — 422 `/problems/idempotency-mismatch`).

### Security
- Человеческий токен защищён только на стороне CLI: проверка интерактивного терминала, подтверждение вводом id и адрес только из `~/.zeroaimemory/config.toml` закрывают неинтерактивный и случайный вызов `zam … --human` агентом, но сервер этих проверок не видит и любой запрос с `human_token` записывает как запрос человека. Агент под той же учётной записью ОС может прочитать `~/.zeroaimemory/config.toml` (тот же файл CLI читает и для обычного токена) и поставить или изменить `axiom` запросом к REST напрямую. Рекомендация: подтверждать `axiom` в WebUI и не выпускать человеческий токен либо держать его вне досягаемости агента (другая машина, отдельная учётная запись ОС, запрет чтения `~/.zeroaimemory/` в песочнице агента) и отзывать после работы (`deploy/README-install.md`, ТЗ §11.4; варианты защиты — вопрос владельцу).
- Мастер-ключ Vault по умолчанию лежит в каталоге данных (`<data_dir>/master.key`) рядом с обёрнутыми ключами (`system.db`) и шифротекстами (`users/*.db`): бэкап каталога целиком вместе с ключом раскрывает Vault. Держите ключ вне каталога данных (`ZAM_MASTER_KEY` или `[vault] master_key_file` / `ZAM_VAULT__MASTER_KEY_FILE`) или исключайте `master.key` из бэкапа и храните отдельно; права восстановленного вручную файла ключа сервер сохраняет как есть.
- `master.key.tmp` на Windows создаётся сразу с DACL только владельцу, SYSTEM и администраторам (`CreateFileW` с дескриптором безопасности; раньше DACL ставился после записи ключа). При старте сервер предупреждает (WARN), если существующий файл мастер-ключа читают не только учётная запись сервера: Linux — права шире 0600, Windows — DACL с доступом на чтение для других учётных записей (все разрешающие типы ACE; владелец файла, если это не учётная запись сервера, тоже считается чужим); Vault при этом работает.
- Текст паники фоновых задач (`spawn_blocking`) не попадает в журнал: `expand=section` пишет только признаки `panic`/`cancelled`, 500 рендера Markdown и диффа ревизий — тоже (`ApiError::aborted`). При панике на срезе строки этот текст мог содержать до 256 символов незамаскированного исходника заметки.
- Журнал не получает текст паники разбора заметки при `expand=section` (в нём мог быть фрагмент заметки с секретом) — только признак паники.

### Known limitations
- Откат на 0.0.3-m2 по копиям `users/<id>.db.bak-v6` и `system.db.bak-v2` теряет **всё** записанное после обновления (заметки, ревизии, корзину, привязки вложений, пользователей и токены, настройки, аудит), а не только сущности M3; экспорта до M7 нет — нужное сохраняется `zam read` до отката. Базы открываются в режиме WAL: перед подкладыванием копии сервер останавливается штатно, а `*.db-wal` и `*.db-shm` заменяемых баз удаляются, иначе SQLite применит их к копии и испортит её. Сам откат тестом не проверялся (`deploy/README-install.md`, «Обновление»).
- Совместный доступ: связи между личной памятью участника и общим решением (в другой базе) отвечают 422; управление доступом владельцам-пользователям — через CLI и REST (WebUI — только администратору); Vault участника при `ro` и после отзыва недоступен ему самому, пока доступ не вернут.
- Гейт качества int8 на наборе M3 «не пройден» и невоспроизводим: нижняя граница Δ nDCG@10 −0,0108 при пороге −0,01; повторные прогоны того же кода проходят — критерий различает шум HNSW-индекса, а не квантование (вопрос владельцу, журнал решений M3).
- `rerank: on` заменяет балл баллом реранкера — бусты `certainty` и вида не действуют (`reliable_first` 1,000 → 0,571).
- Жёсткая остановка во время записи (сбой, снятие процесса) — следующий старт 6,6 / 13,8 с на GPU и 13,7–18,9 с на CPU (медиана / max, HDD) до готовности векторного поиска; ожидание WAL помогает только штатной остановке, а она сразу после записи длится дольше на 7–9 с (замер 2026-10-26). При увеличении `qdrant.shutdown_flush_wait_ms` до максимума 60 с стоп-таймаут менеджера служб нужно поднять примерно до 140 с.
- Корзина не очищается (срок хранения и окончательное стирание — M4+); старые ревизии хранят исходный текст, в том числе то, что сканер секретов маскирует при индексации.
- Сканер секретов: порог энтропии на 32 символах ловит около 66 % случайных base62-ключей (на 40 — около 97 %); подписи в query подписанных URL не маскируются.
- MCP, хуки и проактивное вспоминание по триггерам — этап M4; DOCX/XLSX/PDF — M5; `service install`, `doctor`, бэкап — M7.

### Changed
- Новый ключ `search.w_fts_relaxed = 0.25` (`ZAM_SEARCH__W_FTS_RELAXED`): вес канала bm25, когда ни один чанк не содержит всех слов запроса и сработал ослабленный запрос (любое слово); `FtsChannels::relaxed` и `FtsHit::index_state` в zam-store. Вес применяется только при работающем векторном канале и только к чанкам, которые он видит: FTS-only, Human и заметки в очереди индексации ранжируются с `w_fts` (иначе в смешанной области FTS-only находки тонули под векторными кандидатами). Оценка подобрана на том же наборе (in-sample) и завышена. Подобран по сетке eval (12 конфигураций весов и чанкинга на bge-m3 fp16): глобальный `w_fts = 0.25` давал nDCG@10 +0,032 (95 % интервал парного бутстрепа +0,016…+0,048), перефразы без общих слов +0,10, кросс-языковые +0,06 — при равных весах случайные совпадения ослабленного bm25 по одному слову вытесняли векторные находки. Но глобальный вес прятал FTS-only находки (Human не векторизуется): совпадение по точному слову проигрывало всем 60 векторным кандидатам (упал тест `human_deleted_and_excluded_not_in_vector_channel`). ### Fixed
- Windows: поиск сразу после падения управляемого Qdrant ждал 2–4 с (отказ соединения с закрытым портом localhost приходит через ~2 с на попытку, клиент повторяет запрос, а супервизор меняет состояние только после разбора журнала процесса). Теперь при `Ready` поиск сверяется с живостью процесса по pid (`Supervisor::process_alive`) и сразу отвечает из FTS с `degraded_reason: qdrant_down`; тесты `search_right_after_qdrant_kill_degrades_without_waiting` (без исправления — 4,07 с) и `process_alive_drops_right_after_kill`.
- `POST /nodes` под нагрузкой индексации на HDD отвечал 500 «database is locked» через 5,6 с: фоновый `RESTART` checkpoint держал блокировку записи дольше `busy_timeout` 5 с (тест `writer_waits_out_long_foreign_write_lock`).
- Баллы `jina-reranker-v2` зависели от соседей по батчу (динамическое квантование активаций по всему тензору): модель считалась батчем, потому что в манифесте не было `dynamic_quant`.
- Запись заметки падала с 500 («база закрыта или операция аварийно прервана»), если в тексте незакрытая обратная кавычка стояла перед многобайтовым символом (например, `` `--target — ``): сегментатор предложений сравнивал срез строки по байтовому индексу внутри символа UTF-8 и паниковал в потоке записи. Теперь сравнение побайтовое; тест `unclosed_backtick_before_multibyte_char`. Найдено на корпусе eval.
- Windows: каталог данных длиннее ~210 символов давал при старте невнятное «ошибка sqlite: unable to open database file» (база пользователя `users\<uuid>.db` и её журналы выходили за MAX_PATH). Теперь `DataDir::open` проверяет длину до создания каталогов и при пути длиннее 190 символов (запас на копии баз перед миграцией) отказывает с ошибкой `StoreError::DataDirTooLong`, в которой названы длина, предел и как его обойти (`data_dir`, `ZAM_DATA_DIR`, `--data-dir`); предел описан в `deploy/README-install.md`. Проверка (`zam_store::check_data_dir_len`, префикс `\\?\` не считается) выполняется и в CLI до работы: `migrate`, `reindex`, `qdrant …`, `models …`, `cuda fetch` отказывают сразу, а не после долгой загрузки.
- Повреждённая база одного пользователя больше не ломает `GET /index/status` администратора (сумма по всем), `POST /admin/reindex {}` и `zam-server reindex` без `--user`: при обходе всех баз неоткрывающиеся пропускаются и перечисляются (`unavailable_dbs` в ответах, строка в отчёте CLI); база, указанная явно, — по-прежнему ошибка.
- Исключение базы из пересборки индекса переживает перезапуск: отметка хранится в `system.db` (миграция system 0002, таблица `index_skipped`; API `SystemStore::index_skip/index_unskip/index_skipped`). Воркер загружает её при старте; когда база снова открывается, в ней ставится отметка reindex из кэша, а исключение снимается — точки возвращаются без инференса. Базы, которые не открыл reindex (в том числе при пересоздании коллекции), отмечаются так же и видны в `rebuild_skipped`.
- Прерванный reindex при чужой модели коллекции возобновляется: при запуске воркер обходит все базы и читает отметки `reindex_pending` до ворот коллекции.
- Служебные эмбеддинги до v5 (без владельца) при попадании в кэш присваиваются узлу (`adopt_owned_embeddings`) и сборкой мусора не снимаются; папка без эмбеддинга L0 в кэше получает свёртку воркера (`ReindexReport::missed_folders`), а в CLI — эмбеддинг моделью сразу.
- `UserDbs::get` держит глобальный замок только на поиск ячейки базы: открытие, миграции и дозаполнение ключей одной базы не задерживают другие.

- `zam-server qdrant fetch` при запущенном Qdrant на Linux (ETXTBSY) и на Windows отказывает до загрузки с подсказкой остановить сервер — та же проверка, что у `cuda fetch`.
- CI: `cargo test --workspace --no-fail-fast` — падение одного крейта больше не скрывает остальные тесты (в M2 красный `zam-ml` скрыл, что e2e Qdrant на Linux не выполнялись).
- `GET /index/status` в сессии администратора: `worker.batch_running` и `worker.rollups_pending` (покой воркера); `cargo xtask bench` оценивает по целям ТЗ v1.7.

- Заметки, записанные без моделей, оставались нарезанными оценкой токенов и после установки моделей: такие базы отмечаются (`meta.chunked_approx`), и при первом открытии с точным счётчиком все живые заметки перенарезаются в фоне с повторной индексацией.
- `index_state` мог остаться `indexed` при переносе или восстановлении узла сразу после закрытия задания (отметка шла отдельной транзакцией).
- Модель fp16 на CPU писала векторы под `model_id` варианта CUDA — они смешивались бы с векторами CUDA в одной коллекции.
- После reindex с папками без кэша `worker.rollups_pending` оставался 0 до следующего круга воркера: покой воркера наступал раньше построения их точек.

### Known limitations
- Не все цели §17 ТЗ выполнены; отступления приняты владельцем 2026-10-20 (ТЗ v1.7, `docs/journal.md`): индексация на CPU — 690–770 токенов/с (цель — 3 чанка по 400 токенов в секунду); поиск FTS-only — p95 30–32 мс на 10 тыс. заметок (цель 20 мс, HDD); поиск на GPU при полной очереди индексации — p95 52 мс (цель 50). Цели пересмотрены владельцем: RSS с bge-m3 на CPU — 1,5 ГБ (две сессии ORT), память реранкера jina — по факту `ml.rerank_sessions`, индексация на GPU — ≥ 3000 токенов/с (RTX 3090, HDD; замер 4323–7141).
- Не выполнено и открыто: RSS на GPU — 808–1248 МиБ при цели 0,6 ГБ (библиотеки CUDA/cuDNN, замер на Windows; на Linux не мерился); RSS без моделей на 10 тыс. заметок — 54 МиБ при 50 МБ (кэш страниц SQLite).
- Первый старт после жёсткой остановки сразу за массовой индексацией на HDD — 5,4 с (GPU) и 9,6 с (CPU) до готовности векторного поиска: Qdrant повторяет WAL после `TerminateProcess`; цель 5 с относится к штатному перезапуску (1,1–2,0 с). Сброс WAL перед остановкой и очерёдность чтения с HDD — исследуются.
- Перефразы без общих слов с запросом находятся плохо (recall@5 ≈ 0,11 у гибрида без реранка): bge-m3 на коротких заметках корпуса eval; реранк поднимает общую выдачу (nDCG@10 0,746 → 0,831).
- Гейт качества int8 по порогу косинуса dense 0,99 не пройден (Xenova int8 — 0,978); по поиску ухудшения нет, int8 оставлен решением владельца.
- Хвост записи до FTS при массовой загрузке во время индексации на HDD — до 8–10 с (фоновый `RESTART` checkpoint SQLite), p95 — 13–24 мс.
- `qdrant.mode = "edge"` — прототип за feature `edge`, в сервер и комплекты не входит (ADR 0001: не переходить; у qdrant-edge 0.8 WAL не воспроизводится при открытии — тест `confirmed_upsert_survives_process_exit` под `#[ignore]`).
- Первый старт с CUDA может занять больше 10 с: `/health` молчит, пока не загружены модель и библиотеки NVIDIA (~1,4 ГБ).
- RSS с bge-m3 на CPU после поиска — 1439 МиБ (1,509 ГБ) при цели 1,5 ГБ: превышение 0,6 % (в простое 1416 МиБ — в пределах).
- На Windows каталог данных — не длиннее 190 символов (MAX_PATH у SQLite и рабочего каталога Qdrant).
- `zam-server service install`, `doctor`, `backup`/`restore` — этап M7. Журналы, граф, vault — M3; MCP, хуки, проактивное вспоминание — M4.
- GPU на Linux с драйвером NVIDIA вручную не проверялся (в CI — сборка и smoke GPU-комплекта на CPU).
- Реранкер jina (CC-BY-NC-4.0) не входит в `zam-models` и скачивается только с `--accept-nc-license`; без него `rerank: on` на CPU отвечает предупреждением и прежним порядком.
- `ml.unload_after` не реализован: значение проверяется, сервер пишет WARN и держит модели в памяти. Модель эмбеддингов загружается при старте, реранкер — при первом `rerank: on`.
- Точки папок (`level = folder`) пишутся в Qdrant, поиск по ним — этап M3.
- Перенарезка базы, нарезанной без моделей, — полная: все живые заметки и повторная индексация (на CPU — часы на больших базах).

## [0.0.2-m1] - 2026-10-18

Этап M1: заметки. Markdown-заметки с историей, патчами секций, корзиной, вложениями и полнотекстовым поиском — через REST API, CLI `zam` и WebUI.

### Added
- Markdown (`zam-markdown`, comrak): разбор с байтовыми позициями (BOM, CRLF, кириллица), frontmatter (`tags`, `description`, `l0`, `index`), секции H1–H3 с путями вида `Установка > Linux`, вики-ссылки и ссылки на вложения. PATCH секций — байтовый splice исходника: байты вне изменённого диапазона не меняются, переводы строк документа сохраняются.
- Рендер HTML на сервере: GFM, сноски, формулы, callout `> [!тип]` (тип — буквы любого алфавита, например `[!заметка]`), подсветка кода (syntect; не больше 256 КиБ кода на документ, остальные блоки — без подсветки), Mermaid и KaTeX на клиенте; HTML проходит ammonia (сырой HTML из заметок не исполняется), `POST /api/v1/render` для предпросмотра (до 1 МБ). Кэш HTML сразу видит появление, перенос, удаление и восстановление целей вики-ссылок и загрузку вложений.
- Заметки и папки в пространствах Knowledge, Rules, Human и решениях: создание, чтение (`md` как сохранён, `html`, `json`, L0 — сводка, L1 — оглавление, секция по пути), замена с `If-Match` (конфликт → 409 с текущей ревизией и диффом), PATCH секций (правка чужой секции с той же базовой ревизией проходит), перемещение, корзина и восстановление. Предел заметки — 5 МБ.
- История: каждая правка — новая ревизия (автор человек/агент/система, машина, сессия, сообщение), дифф между ревизиями, откат к ревизии; удаление, восстановление и откат пишутся в аудит. Ревизии неизменяемы и на уровне базы (триггеры запрещают UPDATE и DELETE). PATCH вставляет пустую строку там, где вставленный абзац иначе слился бы с соседним.
- Поиск `POST /api/v1/search`: FTS5 (слова + trigram для идентификаторов), область — текущее решение, Knowledge и Rules или все решения, режимы `brief`/`chunks`/`notes`, бюджет токенов, вывод JSON или Markdown, `pending_count` — заметки области, ждущие векторной индексации. Синтаксис FTS5 в запросе (`"`, `*`, `AND`, `NEAR`, …) ищется как обычные слова. Заметка без собственного текста (только заголовок) находится по названию. `index: false` во frontmatter исключает заметку только из будущего векторного индекса (§6.4), полнотекстовый поиск её находит.
- Запись: checkpoint WAL выполняется фоновым потоком, а не писателем; p95 записи на HDD — около 3 мс (см. `docs/journal.md`).
- Вложения: загрузка до 200 МБ (`POST /api/v1/blobs`, sha256, дедупликация), ссылки `_attachments/…` в заметках, выдача с Range (видео перематывается); HTML и SVG отдаются как `attachment` с CSP `sandbox` и не исполняют скрипты в origin сервиса.
- Доступ: Human по токену недоступен ни в каком виде (и не показывается в `GET /api/v1/spaces`); Rules токен только читает, если не включено `rules.agent_write`; токен `ro` не пишет; администратор видит заметки пользователей.
- CLI `zam`: `tree`, `read`, `write`, `history` (`--diff`, `--revert`), `search`, `attach`; цели `[пространство:]путь` или id узла, решение по `.zeroaimemory/solution.toml`; конфликт ревизий печатает дифф и завершается кодом 4. Коды выхода — в `deploy/README-install.md`.
- WebUI: дерево пространств (создание, перенос, корзина), просмотр документа (оглавление, подсветка, формулы, диаграммы, картинки, видео, копирование кода, вики-ссылки), редактор с предпросмотром (Ctrl+S, конфликт правок с диффом, переводы строк файла сохраняются), история с диффом и откатом, поиск Ctrl+K, вложения кнопкой, вставкой из буфера и перетаскиванием. Начальный бандл 55 КБ gzip, редактор грузится лениво.
- Smoke комплекта проверяет заметку через `zam`: запись, поиск, чтение побайтно.

### Known limitations
