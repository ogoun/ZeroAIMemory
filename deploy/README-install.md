# ZeroAIMemory: установка

Комплект содержит сервер `zam-server`, клиент `zam`, библиотеки ONNX Runtime и pdfium,
Qdrant (`qdrant/<версия>/`), пример конфигурации `config.example.toml`, копии манифестов
`deploy/` (что и откуда скачивают `qdrant fetch`, `models fetch` и `cuda fetch`; в
`zam-server` они встроены) и лицензии (`LICENSES/`). Поддерживаются Windows x64 и Linux x64.

| Архив релиза | Что внутри |
|---|---|
| `zam-server-<версия>-<os>-x64-cpu` | комплект с ONNX Runtime для CPU |
| `zam-server-<версия>-<os>-x64-gpu` | то же, но ONNX Runtime с CUDA EP; библиотек NVIDIA нет (см. «GPU (CUDA)»), без GPU работает на CPU |
| `zam-<версия>-<os>-x64` | только клиент `zam` |
| `zam-models-<версия>-<модель>.zip` | одна модель с `bundle = true` — для машин без интернета (см. «Модели») |
| `zam-cuda-<версия>-<os>-x64` | библиотеки NVIDIA для GPU-комплекта — для машин без интернета |

`<os>` — `windows` (zip) или `linux` (tar.gz). Контрольные суммы всех архивов — в `SHA256SUMS`.

## Порты и данные

| Что | Значение по умолчанию |
|---|---|
| Сервер (WebUI и API) | `0.0.0.0:7700` (`[server] bind`) |
| Qdrant HTTP / gRPC (запускается сервером, начиная с этапа M2) | `6333` / `6334` (`[qdrant]`) |
| Каталог данных | `./data` (`data_dir`), относительный путь считается от текущего каталога |

В каталоге данных лежат базы, индексы и файл блокировки; второй экземпляр сервера на тот же
каталог не запустится. Делайте резервные копии каталога при остановленном сервере; мастер-ключ
Vault `master.key` из этой копии исключайте и храните отдельно (см. «Vault: секреты и мастер-ключ»).

На Windows полный путь каталога данных — не длиннее 190 символов. Внутри него лежат файлы,
пути к которым на 60–160 символов длиннее: базы SQLite открываются обычными путями Win32
(предел MAX_PATH = 260), рабочий каталог процесса Qdrant тоже ограничен MAX_PATH; хранилище
Qdrant пути длиннее 260 символов выдерживает. С более длинным путём `serve` и команды, которым
нужен каталог данных (`migrate`, `reindex`, `qdrant status`, `qdrant reset`, `models …` без
заданного `ml.models_dir`), сразу, до загрузок, завершаются с ошибкой «каталог данных …
слишком длинный для Windows» — перенесите каталог или укажите короче (`data_dir`,
`ZAM_DATA_DIR`, `--data-dir`). `cuda fetch`, `qdrant fetch` и `models …` с заданным
`ml.models_dir` каталог данных не используют и длину не проверяют. Префикс `\\?\` в длину не входит.
На Linux такого предела нет. Если Qdrant всё же падает с «os error 3» («системе не удаётся
найти указанный путь») в журнале (`component=qdrant`), причина та же — слишком длинный
реальный путь каталога данных (например, часть пути — символическая ссылка или точка
подключения): перенесите каталог данных ближе к корню диска.

## Первый запуск

Администратор задаётся не в базе данных, а в конфигурации. Два варианта:

1. Хэш пароля в `config.toml` (рекомендуется). Запустите команду без аргументов и введите
   пароль в ответ на приглашение (ввод не отображается и не попадает в историю оболочки):

   ```
   zam-server hash-password
   ```

   Результат (`$argon2id$...`) вставьте в `[admin] password_hash`. Не передавайте пароль
   через `echo ... |`: в Windows PowerShell 5.1 конвейер меняет кодировку не-ASCII символов,
   `cmd` добавляет к паролю пробел перед `|`, а сама команда остаётся в истории.
   Для скриптов в Linux — чтение без отображения:

   ```
   read -rs -p 'Пароль: ' PW && echo >&2 && printf '%s\n' "$PW" | zam-server hash-password; unset PW
   ```
2. Переменная окружения `ZAM_ADMIN_PASSWORD` (пароль хэшируется в памяти; удобно для проверки).

Скопируйте `config.example.toml` в `config.toml`, при необходимости измените значения и запустите:

```
zam-server serve --config config.toml
```

Параметры `--bind` и `--data-dir` переопределяют конфигурацию; переменные окружения
`ZAM_<РАЗДЕЛ>__<КЛЮЧ>` (например, `ZAM_SERVER__BIND`) тоже.

### Первый токен администратора

При самом первом старте сервер печатает в stderr (не в журнал) рамку:

```
==== ZeroAIMemory: первый токен администратора (показывается один раз) ====
ZeroAIMemoryToken=<токен>
==========================================================================
```

Сохраните токен: повторно он не показывается. Новые токены выпускаются в WebUI
(`http://<хост>:7700/`, вход администратора) или через админ-API.

Проверка подключения клиентом:

```
zam status --url http://127.0.0.1:7700 --token <токен>
```

Коды выхода `zam status`: 0 — всё в порядке, 1 — ошибка конфигурации,
2 — сервер недоступен, 3 — токен отклонён.

Без флагов `zam` ищет адрес и токен по порядку: `--url`/`--token`, переменные `ZAM_URL`/`ZAM_TOKEN`,
блок в файлах проекта от текущего каталога вверх (ближайший каталог важнее; внутри каталога —
`CLAUDE.local.md`, затем `CLAUDE.md`, затем `AGENTS.md`), затем `~/.zeroaimemory/config.toml`.
Адрес и токен ищутся независимо. Блок в `CLAUDE.md`:

```
<!-- zeroaimemory:begin v1 -->
ZeroAIMemoryUrl=http://<хост>:7700
ZeroAIMemoryToken=<токен>
<!-- zeroaimemory:end -->
```

**Человеческий токен** (ставит и меняет `axiom`, §7.5 ТЗ) выпускает администратор в WebUI
(«Пользователи» → флажок «для человека»). Его нельзя класть в `CLAUDE.md`/`AGENTS.md` и в
окружение агента: он хранится только в `~/.zeroaimemory/config.toml` вместе с адресом сервера:

```toml
url = "http://<хост>:7700"
human_token = "zam_…"
```

Его использует только команда с флагом `--human`, например
`zam insight certify <id> axiom --reason "проверено" --human`. Адрес для неё берётся только из
этого файла (`--url`, `ZAM_URL` и файлы проекта игнорируются, при расхождении — предупреждение).
Команда работает только в интерактивном терминале и просит подтвердить действие вводом id записи;
без терминала (например, при вызове агентом) — отказ с кодом 3: подтверждение аксиом — только
человеком, в WebUI или в интерактивном терминале.

**Что эта защита закрывает и что нет.** Проверка терминала и подтверждение вводом id — защита
клиента `zam`, сервер её не видит: любой запрос с человеческим токеном сервер записывает как
запрос человека (`author_kind = human`). Поэтому:
- закрыто: агент, который вызывает `zam` по правилам (неинтерактивно), и случайный вызов —
  `--human` откажет; токен не попадает в `CLAUDE.md`/`AGENTS.md`, окружение и флаги, а адрес
  сервера для него не подменить через файлы проекта;
- **не закрыто:** агент (например, Claude Code), который работает под той же учётной записью ОС,
  что и вы, может прочитать `~/.zeroaimemory/config.toml` и вызвать REST напрямую с
  `human_token` — тогда он создаст или изменит `axiom` от имени человека. Этот же файл CLI
  по умолчанию читает и для обычного токена (`token`), то есть агенту он открыт по устройству.

Рекомендации:
- надёжнее всего — подтверждать `axiom` в WebUI и не выпускать человеческий токен вовсе;
- если токен нужен, держите `config.toml` с `human_token` только там, куда агент не дотягивается:
  на машине без агента, под отдельной учётной записью ОС или с правилом песочницы агента,
  запрещающим чтение `~/.zeroaimemory/` (обычный токен агенту тогда передайте через
  `CLAUDE.local.md` или `ZAM_TOKEN`);
- после работы отзывайте человеческий токен (WebUI, «Пользователи»), его последнее
  использование видно там же. Каждая смена `certainty` остаётся в истории записи (ревизия с
  причиной, токеном и машиной) — по ней видно, каким токеном поставлена `axiom`.

Другие места хранения человеческого токена (хранилище секретов ОС, одноразовые коды
подтверждения) в 0.0.4-m3 не поддерживаются — это вопрос к следующему этапу.

Личный токен удобнее держать в `CLAUDE.local.md` (обычно не коммитится).

## Работа с заметками из CLI

Адрес и токен `zam` находит так же, как `zam status`; у каждой команды есть флаги `--url`,
`--token` и `--json` (вывод в JSON). Токен никогда не печатается.

**Цель** — `[пространство:]путь`: пространство `knowledge`, `rules`, `human`, `solution`
или GUID решения. Без префикса — решение из ближайшего вверх `.zeroaimemory/solution.toml`
(поля `id` и `name`), а если его нет — `knowledge`. В `read`, `history`, `write` и `attach`
вместо пути можно передать id узла (26 символов, как печатает `zam`). Пути с пробелами
и кириллицей берите в кавычки.

```
# дерево с краткими сводками (L0); --depth от 1 до 5
zam tree knowledge:
zam tree "knowledge:Инструменты" --depth 2

# запись: из stdin или --file; печатает <id>@<ревизия>
echo "# Bash скрипты" | zam write "knowledge:Инструменты/Bash скрипты" -m "первая версия"
zam write "knowledge:Инструменты/Bash скрипты" --file note.md --base-rev 3 --l0 "Полезные скрипты"

# чтение: Markdown как сохранён (байты, переводы строк не меняются)
zam read "knowledge:Инструменты/Bash скрипты"
zam read "knowledge:Инструменты/Bash скрипты" --section "Установка > Linux"
zam read <id> --tier L1                          # L0 — сводка, L1 — оглавление
zam read <id> --rev 2                            # конкретная ревизия
zam read knowledge:a knowledge:b                    # перед каждой — строка «--- цель ---»

# история: ревизии (rev, время, автор, машина, сообщение), дифф, откат
zam history "knowledge:Инструменты/Bash скрипты"
zam history "knowledge:Инструменты/Bash скрипты" --diff 1..3
zam history "knowledge:Инструменты/Bash скрипты" --revert 1

# поиск: Markdown, в области — текущее решение, Knowledge и Rules; --all — все решения
zam search "bash скрипты"
zam search docker --all --mode notes --top-k 5

# вложение: печатает ссылку _attachments/… для вставки в заметку
zam attach "knowledge:Инструменты/Bash скрипты" ./схема.png
```

`write` создаёт заметку, если её нет, и заменяет текст существующей с проверкой ревизии
(`--base-rev` или текущая). Если заметку успели изменить с другой машины, команда
печатает в stderr дифф от вашей базовой ревизии к текущей и завершается с кодом 4.
Перед первой записью в решение оно регистрируется на сервере по `solution.toml`.
Имя машины (`COMPUTERNAME` в Windows, `HOSTNAME` в Linux, если переменная экспортирована)
попадает в историю ревизий.

Коды выхода команд: 0 — успех, 1 — конфигурация (нет адреса, битый `solution.toml`),
2 — сервер недоступен, 3 — нет токена или он отклонён (в том числе нет прав на запись),
4 — конфликт ревизий, 5 — не найдено, 6 — неверный ввод (аргументы, путь, не UTF-8).

## Vault: секреты и мастер-ключ

Vault хранит креды, токены и ссылки (§7.6 ТЗ). Значение шифруется (XChaCha20-Poly1305) ключом
данных пользователя, а тот — мастер-ключом сервера. В поиск, FTS, Qdrant, журнал сервера и
аудит значения не попадают; каждое раскрытие пишется в аудит (`vault.reveal`: токен, сессия,
машина, время).

**Мастер-ключ** — 32 байта в base64:
- `ZAM_MASTER_KEY` (важнее файла), иначе
- файл `[vault] master_key_file`, по умолчанию `<data_dir>/master.key`. Файл создаётся сам при
  первом запуске, пока в `system.db` нет ключей Vault: атомарно (через `master.key.tmp` и
  жёсткую ссылку, без перезаписи существующего). На Linux права файла — 0600. На Windows файл
  получает защищённый DACL: полный доступ только владельцу, SYSTEM и администраторам
  (наследование от каталога отключено). Права ставятся до записи ключа: ключ не лежит ни
  мгновения в файле с правами каталога. Ключ, положенный вручную, сохраняет свои права —
  ограничьте их сами (сервер проверяет их при старте, см. ниже).

**Резервируйте мастер-ключ отдельно от бэкапа каталога данных.** Бэкап без ключа секреты не
раскрывает, но и восстановить их без ключа нельзя.

**По умолчанию ключ лежит в самом каталоге данных** (`<data_dir>/master.key`), рядом с
обёрнутыми ключами пользователей (`system.db`) и шифротекстами (`users/*.db`). Поэтому бэкап
каталога данных целиком (`tar data/`, копия папки) **вместе с `master.key` раскрывает весь
Vault** тому, у кого он окажется. Чтобы этого не было:
- храните ключ вне каталога данных: переменная `ZAM_MASTER_KEY` (base64 32 байт; задаётся в
  окружении службы, не в `config.toml`) или путь `[vault] master_key_file` /
  `ZAM_VAULT__MASTER_KEY_FILE` на другом томе или в каталоге с ограниченным доступом;
- если ключ остаётся в `<data_dir>`, исключайте `master.key` из бэкапа каталога данных и
  храните его копию отдельно (менеджер паролей, отдельный носитель);
- при восстановлении из бэкапа верните ключу права только для владельца (Linux — `chmod 600`;
  Windows — доступ только учётной записи службы и администраторам): права восстановленного
  файла сервер сохраняет как есть.

**Проверка прав при старте.** Если файл мастер-ключа могут прочитать не только владелец, сервер
пишет в журнал предупреждение (WARN) и продолжает работать, Vault не блокируется:

```
WARN файл мастер-ключа Vault доступен не только владельцу: ограничьте права (Linux: chmod 600;
     Windows: только владелец, SYSTEM и администраторы) path=… access=…
```

`access` — что именно не так: на Linux `права 644` (любой бит группы или прочих, то есть шире
0600), на Windows `DACL разрешает чтение: S-1-5-32-545, …` — SID учётных записей и групп, кроме
владельца файла, SYSTEM, администраторов и `OWNER RIGHTS`, которым DACL даёт чтение (например,
`S-1-5-32-545` — «Пользователи», `S-1-1-0` — «Все», `S-1-5-11` — «Прошедшие проверку»).
Предупреждение повторяется при каждом старте, пока права не исправлены. Как исправить:

```bash
# Linux (владелец — пользователь службы)
chmod 600 <data_dir>/master.key
```

```powershell
# Windows: отключить наследование и оставить только владельца, SYSTEM и администраторов
icacls "<data_dir>\master.key" /inheritance:r /grant:r "*S-1-3-4:F" "*S-1-5-18:F" "*S-1-5-32-544:F"
```

Права, выставленные намеренно (например, 0640 для агента бэкапа), сервер сам не меняет — только
предупреждает. Если файл не удаётся проверить, в журнале — WARN «не удалось проверить права
файла мастер-ключа Vault».

Перенос ключа в `master_key_file` или `ZAM_MASTER_KEY` — то же значение, новый ключ не нужен:
скопируйте содержимое `master.key` (сервер остановлен), задайте путь или переменную, удалите
файл из каталога данных и запустите сервер. Значение должно совпасть с прежним, иначе Vault
заблокируется (см. ниже). Если ключ потерян, подменён или
`ZAM_MASTER_KEY` расходится с прежним, сервер работает, а Vault заблокирован: эндпоинты Vault
отвечают 503 `/problems/vault-locked`, причина — одной строкой WARN в журнале. Новый ключ при
этом молча не создаётся. Верните прежний файл или переменную и перезапустите сервер.

```
# значение — только из stdin или скрытого ввода с терминала, никогда из аргументов
printf '%s' "$GITHUB_TOKEN" | zam vault set github --type token --link https://github.com --global
zam vault set postgres --type connection_string --username app      # Vault текущего решения; ввод скрыт
zam vault list --global --q git                                      # без значений
zam vault get github --global --raw                                  # в stdout только значение
```

`--global` — личный Vault (Knowledge, для всех проектов), без него — Vault решения из
`solution.toml` (`--solution GUID`). Vault решения лежит в вашей базе пользователя: владелец и
другие участники общего решения его не видят. Повторный `set` с тем же именем создаёт новую
ревизию; прежние значения раскрывает только администратор (`GET /vault/{id}/revisions?reveal=1&rev=N`).

Если `ZAM_MASTER_KEY` задан, файл ключа не создаётся и не читается: резервируйте значение
переменной так же, как файл. Смена ключа (перешифровка) в M3 не поддерживается.

## Совместный доступ к решению

Решение (проект агента, `agent_solution_id` из `solution.toml`) хранится в базе пользователя,
который первым его зарегистрировал, — владельца (§11.6 ТЗ). Другой пользователь, чей агент
обращается к тому же GUID, получает запрос доступа `pending` и, пока владелец не ответит, —
403 `/problems/solution-access` (`state: pending`) на чтение и запись решения; поиск исключает
решение с предупреждением `solution access pending`.

```
zam solution access requests               # владелец: ожидающие запросы текущего решения
zam solution access approve Борис          # одобрить (rw); --ro — только чтение
zam solution access reject Борис --reason "не наш проект"
zam solution access revoke Борис           # отзыв — со следующего запроса того же токена
zam solution access list                   # все запросы и участники
```

То же — `POST /api/v1/solutions/{guid}/access/{user}/approve|reject|revoke` и страница WebUI
«Администрирование → Решения» (администратору). Участник видит в базе владельца только
пространство решения: Knowledge, Rules, Human и Vault владельца ему недоступны (404); его
правки ложатся в базу владельца ревизиями с его пользователем и токеном, а свой Vault для
решения он хранит в своей базе. Права проверяются на каждом запросе: после отзыва уже
следующий запрос того же агента получает 403 (`state: revoked`). `zam status` показывает роль
в текущем решении и число ожидающих запросов к вашим решениям.

## WebUI: заметки

WebUI открывается по адресу сервера (`http://<хост>:7700/`) после входа администратора.

- Слева — дерево пользователей и их пространств (Knowledge, Rules, Human, решения).
  Создание заметок и папок, перенос и удаление в корзину — из контекстного меню.
- Документ показывается с оглавлением, подсветкой кода, формулами, диаграммами Mermaid,
  картинками и видео.
- «Править» открывает редактор с предпросмотром, сохранение — Ctrl+S. Если заметку успели
  изменить с другой машины, показывается дифф и выбор: перезаписать поверх, скопировать
  свой текст и открыть текущую или вернуться к правке.
- Вкладка «История» — ревизии, дифф и откат.
- Поиск — Ctrl+K или кнопка «Поиск» в шапке.
- Файл прикрепляется кнопкой «Прикрепить файл», вставкой из буфера или перетаскиванием
  в редактор; в текст вставляется ссылка `_attachments/…`.

## Qdrant

Векторный индекс — нативный Qdrant из комплекта (`qdrant/<версия>/`), без Docker. Его запускает
и контролирует сам `zam-server` (`[qdrant] mode = "managed"`):

- рабочий каталог — `<data_dir>/qdrant/` (конфиг `config/zam.yaml` генерируется при каждом
  старте, хранилище `storage/`, pid-файл `qdrant.pid`, метка `zam-storage.json`);
- Qdrant слушает только `127.0.0.1` на портах `http_port`/`grpc_port`; API-ключ новый при
  каждом старте и передаётся только через окружение процесса;
- Qdrant завершается вместе с сервером, даже если сервер убит (Windows — Job Object,
  Linux — `PR_SET_PDEATHSIG`); оставшийся после сбоя процесс завершается при следующем старте;
- при падении Qdrant перезапускается (задержка 1→60 с); после 5 падений за 10 минут
  перезапуски прекращаются, поиск работает по полнотексту с пометкой `degraded`;
- индекс производный: при откате версии Qdrant, скачке больше чем на одну минорную версию
  или ошибке миграции хранилище стирается и индекс пересобирается из базы без инференса.

Команды (с теми же `--config`/`--data-dir`, что и `serve`):

```
zam-server qdrant status --config config.toml     # режим, версия, порты, pid, хранилище (--json — для скриптов)
zam-server qdrant fetch                           # скачать бинарник (SHA-256), если его нет
zam-server qdrant reset --yes --config config.toml   # стереть хранилище (сервер остановлен)
```

Внешний Qdrant: `mode = "external"`, `url` — его gRPC-адрес (например `http://10.0.0.5:6334`),
ключ — `api_key` или переменная `ZAM_QDRANT__API_KEY`.

## Модели

Векторный поиск работает на встроенных ONNX-моделях (§8.4 ТЗ). Без моделей сервер стартует
в режиме полнотекстового поиска (FTS-only): `degraded: true` в ответах поиска, причина и
подсказка — в журнале.

| Модель | Назначение | Устройство | Лицензия | Размер |
|---|---|---|---|---|
| `bge-m3-int8` | эмбеддинги | CPU | MIT | 586 МБ |
| `bge-m3-fp16` | эмбеддинги | GPU (CUDA) | MIT | 1,15 ГБ |
| `bge-reranker-v2-m3` | реранкер (`rerank=on`) | GPU (CUDA) | Apache-2.0 | 1,15 ГБ |
| `jina-reranker-v2` | реранкер (`rerank=on`) | CPU | CC-BY-NC-4.0, по согласию | 297 МБ |

Модели скачиваются с Hugging Face по ревизиям и SHA-256, закреплённым в `deploy/models.toml`
(манифест встроен в `zam-server`); при несовпадении размера или хэша загрузка падает, а
частичные файлы удаляются. Каталог — `ml.models_dir`, по умолчанию `<data_dir>/models`:

```
zam-server models fetch --config config.toml               # модель эмбеддингов устройства
zam-server models fetch --config config.toml --reranker    # и реранкер устройства
zam-server models fetch --device gpu --reranker            # явно: набор для GPU
zam-server models status --config config.toml [--verify]   # что установлено (--verify — SHA-256)
```

Устройство по умолчанию — `gpu`, если рядом с ONNX Runtime лежит CUDA EP (GPU-комплект) и
`ml.device` не `cpu`, иначе `cpu`. GPU-комплект без доступной CUDA работает на CPU с
`bge-m3-int8`, поэтому на такой машине поставьте и CPU-набор (`--device cpu`). Модель для GPU
(`bge-m3-fp16`) на CPU не запускается: если CUDA не поднялась, а `bge-m3-int8` не установлена
(или `ml.embed_model = "bge-m3-fp16"` при `ml.device = "cpu"`), сервер работает в режиме
FTS-only с причиной `gpu_model_on_cpu` и подсказкой `zam-server models fetch --device cpu` —
векторы CPU не смешиваются в одной коллекции с векторами CUDA. В каталоге
каждой модели лежат `LICENSE` (лицензия и ссылки) и `model.toml`. Повторный запуск не
перекачивает файлы с верным хэшем. После загрузки перезапустите сервер; смена модели
выключает векторный поиск до reindex (векторы разных моделей не смешиваются).

Заметки режутся на чанки по токенам модели (`[index] chunk_*`). Без установленных моделей
токены считаются оценкой (символы / 3,5); такие базы отмечаются, и при первом запуске после
`models fetch` их заметки перенарезаются токенизатором модели в фоне (с повторной индексацией;
поиск всё это время работает). Если `tokenizer.json` модели на месте, а ONNX Runtime нет,
чанки сразу режутся точно. `chunk_hard_max` не превышает окна модели минус 64 токена на
префикс контекста (bge-m3: 1024 → 960); пороги больше — уменьшаются с WARN в журнале.

Для машин без интернета модели с `bundle = true` выложены архивами `zam-models-<версия>-<id>.zip`,
по одному на модель (вместе они больше предела 2 ГиБ на файл релиза): `bge-m3-int8` — для
CPU, `bge-m3-fp16` и `bge-reranker-v2-m3` — для GPU. Распакуйте нужные в каталог моделей
(`<data_dir>/models`): появятся `<id>/` с файлами модели, `LICENSE` и `model.toml`, а рядом
`models.toml` — копия манифеста с SHA-256 каждого файла (во всех архивах он одинаковый,
замену можно подтвердить). Проверка — `zam-server models status --verify`. Реранкер
`jina-reranker-v2` (CC-BY-NC-4.0) в архивы не входит.

## Состояние индекса и reindex

`GET /api/v1/index/status` (любой токен; токен видит только своего пользователя,
администратор — пользователя из `X-Zam-User` или сумму по всем) показывает: включён ли
векторный поиск и почему нет (`vector.reason`, текст по-русски `vector.text` и `vector.hint` с командой, например
`zam-server models fetch`), модель и устройство (`cpu`/`cuda` с причиной), Qdrant
(состояние, версия, резидентная память процесса `rss_bytes`, число точек, перезапуски),
очередь индексации, до 20 неудавшихся заданий, последний reindex и базы, исключённые из
пересборки (`rebuild_skipped`).

То же в WebUI — раздел «Индекс» (`http://<хост>:7700/#/admin/index`): страница обновляется
раз в 5 секунд, причину выключения векторного поиска пишет по-русски вместе с командой
(например, «скачайте модели: `zam-server models fetch`»), показывает повреждённые базы
(`unavailable_dbs`) и исключённые из пересборки, а кнопки «Переиндексировать из embeddings»
и «Полная переиндексация» запускают reindex (с подтверждением). Поиск Ctrl+K при выключенном
векторном канале пишет над результатами, что показаны результаты полнотекстового поиска.

Векторы хранятся в SQLite (кэш `embeddings`), поэтому индекс Qdrant пересобирается без
модели. Reindex нужен после смены модели или устройства (коллекция другой модели выключает
векторный поиск: `vector.reason = "model_mismatch"`), после потери или ручной очистки
хранилища Qdrant, после восстановления базы пользователя из копии.

На работающем сервере — администратор, ответ 202 и `job_count` (заметок области):

```
POST /api/v1/admin/reindex  {}                                   # все базы, из кэша
POST /api/v1/admin/reindex  {"user": "<id>", "space": "rules"}   # одно пространство
POST /api/v1/admin/reindex  {"full": true}                       # перечанковка и задания
```

На остановленном сервере — та же операция из командной строки (каталог данных открывается
под локом: если сервер запущен, команда откажет и подскажет API):

```
zam-server reindex --config config.toml                      # все базы, из кэша
zam-server reindex --config config.toml --user <id> --space knowledge
zam-server reindex --config config.toml --full               # перечанковать, задания — серверу
```

Без `--full`/`full` точки области удаляются и пишутся заново из кэша эмбеддингов, пачками
по 256 (цель — не меньше 2000 чанков/с); заметки, для которых в кэше нет эмбеддинга
(например, после смены модели), получают задания и векторизуются воркером сервера. С
`--full` все заметки области перечанковываются и ставятся в очередь (модель прогоняется
только для текстов, которых нет в кэше). Коллекция другой модели пересоздаётся для текущей,
и тогда пересобираются все базы. Прерванный reindex (остановка, сбой) повторяется
автоматически при следующем запуске. После пересборки всей базы пользователя из кэша
удаляются эмбеддинги, на которые больше не ссылается ни один чанк; сервер делает это и сам,
в простое, раз в час. Итог пишется в аудит (`index.reindex`, `index.reindex_done`) и в
`reindex.last` статуса.

Если база пользователя повреждена (файл не SQLite, схема новее программы) или не
открывается пять раз подряд при пересборке после стирания хранилища Qdrant, она
исключается из пересборки (WARN в журнале, аудит `index.rebuild_skipped`, поле
`rebuild_skipped` статуса), а остальные базы пересобираются и флаг пересборки снимается.
Исключение хранится в `system.db` и переживает перезапуск. Когда база снова откроется
(восстановлена из копии `users/<id>.db.bak-v*` или бэкапа), сервер сам поставит ей reindex
из кэша и снимет исключение. Восстанавливайте при остановленном сервере и удалите рядом
`users/<id>.db-wal` и `users/<id>.db-shm` прежнего файла, иначе SQLite применит их к копии и
испортит её; копия `bak-v*` — снимок на момент обновления, всё записанное в базу после него
теряется (см. «Обновление» → «Как подложить копию»). Статус администратора, reindex всех баз и
`zam-server reindex` без `--user` повреждённую базу пропускают и называют
(`unavailable_dbs`, строка отчёта CLI); базу, указанную явно, — нет: это ошибка.

## GPU (CUDA)

GPU-комплект содержит ONNX Runtime с CUDA EP, но не библиотеки NVIDIA (CUDA 13, cuDNN 9).
Их ставит команда (около 1,9 ГБ архивов на Windows и 2,2 ГБ на Linux):

```
zam-server cuda fetch --config config.toml
```

Архивы redist NVIDIA скачиваются с `developer.download.nvidia.com` по `deploy/cuda.toml`
(размер и SHA-256 сверяются), нужные библиотеки кладутся в `<каталог ONNX Runtime>/cuda/`
(по умолчанию — `cuda/` рядом с `zam-server`), рядом с ними — штампы `.<компонент>.sha256`.
Повторный запуск пропускает архив, только если штамп совпал с манифестом; после обновления
`zam-server` с новым `cuda.toml` старые библиотеки заменяются.

Запускайте `cuda fetch` при остановленном сервере. На Windows работающий `zam-server` держит
загруженные библиотеки CUDA, и заменить их нельзя: команда проверяет это до загрузки и
завершается с ошибкой «файл … занят или недоступен для замены … Остановите zam-server»,
ничего не меняя (штампы и прежние библиотеки остаются). Если все штампы совпадают, команда
ничего не заменяет и при работающем сервере тоже проходит. Так же ведёт себя `zam-server qdrant
fetch` при запущенном Qdrant (на Linux — ошибка «Text file busy», на Windows — файл занят).

Первый старт с CUDA может занять больше 10 с: сервер отвечает на `/api/v1/health` только после
загрузки модели, а с CUDA — ещё и библиотек NVIDIA (~1,4 ГБ). Обычный старт — 4–5 с.

Без интернета — архив `zam-cuda-<версия>-<os>-x64` той же версии, что и `zam-server`:
распакуйте его в каталог `zam-server` (в архиве один каталог `cuda/`, он ляжет рядом с ONNX
Runtime):

```
# Windows: содержимое zip (каталог cuda) — в каталог с zam-server.exe
# Linux:
sudo tar -xzf zam-cuda-<версия>-linux-x64.tar.gz -C /opt/zeroaimemory
```

В `cuda/` лежат библиотеки, штампы `.<компонент>.sha256`, `cuda.toml` и `LICENSES/` (CUDA
Toolkit EULA, лицензия cuDNN). По штампам `zam-server cuda fetch` видит библиотеки
установленными и ничего не скачивает — это и проверка распаковки: команда должна сообщить
«загружено архивов 0» (с `--json` — `"downloaded": 0`). Нужен драйвер NVIDIA с поддержкой CUDA 13 (ветка R580 и
новее); устанавливать CUDA Toolkit не нужно. Лицензия библиотек NVIDIA —
https://docs.nvidia.com/cuda/eula/index.html.

`ml.device = "auto"` (по умолчанию) включает CUDA, если она поднялась, иначе работает на CPU;
`"cuda"` — то же с предупреждением в журнале при откате; `"cpu"` — без попытки CUDA.
Фактическое устройство и причина отката пишутся в журнал при старте. В CPU-комплекте
команда `cuda fetch` отказывает: библиотеки NVIDIA ему не нужны.

## Реранкер и лицензия

Серверный реранк включается в запросе поиска (`"rerank": "on"`, по умолчанию выключен; в
хуках не используется): первые 20 кандидатов (`ml.rerank_top`) переставляются по баллу
реранкера, у них в ответе появляется `rerank_score`. Модель выбирается по устройству модели
эмбеддингов и загружается при первом таком запросе: на CPU — `ml.rerank_model_cpu`
(`jina-reranker-v2`), на CUDA — `ml.rerank_model_gpu` (`bge-reranker-v2-m3`). Если реранкер
не установлен, поиск отвечает без реранка и с `warnings: ["reranker not installed"]`.

**Лицензия jina-reranker-v2 — CC-BY-NC-4.0: только некоммерческое использование.** Поэтому
модель не входит в комплект `zam-models` и скачивается только с явным согласием:

```
zam-server models fetch --device cpu --reranker --accept-nc-license
```

Без флага команда завершается с объяснением и ничего не скачивает. Для коммерческого
использования на CPU задайте `ml.rerank_model_cpu = "bge-reranker-v2-m3"` (Apache-2.0) и
скачайте её (`zam-server models fetch --id bge-reranker-v2-m3`); на CPU она заметно медленнее
(около 8 с на 20 кандидатов против 1,3–1,5 с у jina на 12 ядрах; на GPU RTX 3090 — 0,08 с).

jina — модель с динамическим int8: пары «запрос — фрагмент» считаются по одной (в батче баллы
зависели бы от соседей), параллельно в `ml.rerank_sessions` сессиях (по умолчанию 0 — авто:
до 2, ядра `ml.index_threads` делятся между ними). Каждая
сессия держит свою копию весов, около 0,3 ГБ: больше сессий — быстрее и больше памяти (1 —
1,9 с, 2 — 1,4 с, 4 — 1,15 с на 20 кандидатов на 12 ядрах). После обновления сервера
повторите `zam-server models fetch --device cpu --reranker --accept-nc-license`: команда
перепишет `model.toml` модели (признак `dynamic_quant`), веса не перекачиваются. Устаревший
описатель видно в `zam-server models status` («model.toml устарел … нужен `models fetch`») и
в журнале сервера (WARN при загрузке модели).

## Windows

1. Распакуйте архив `zam-server-<версия>-windows-x64-cpu.zip` (или `-gpu.zip`), например в
   `C:\ZeroAIMemory`.
2. `zam-server.exe` и `zam.exe` собраны со статическим CRT, а библиотеки MSVC runtime, которые
   нужны ONNX Runtime (`msvcp140*.dll`, `vcruntime140*.dll`) и Qdrant (`vcruntime140.dll` рядом с
   `qdrant.exe`), лежат в комплекте app-local: отдельная установка VC++ Redistributable не нужна.
3. Создайте `config.toml` и запустите `zam-server.exe serve --config config.toml`.
4. Для работы в фоне зарегистрируйте запуск в Планировщике заданий или через менеджер служб (например, NSSM).

Остановка: Ctrl+C в окне сервера; сервер понимает и Ctrl+Break. Штатная остановка сразу после
записи ждёт подтверждения журнала Qdrant до 10 с (`[qdrant] shutdown_flush_wait_ms`): обычно
остановка после записи занимает 10–15 с, в худшем случае (недоделанная пачка инференса на CPU) —
до 90 с. NSSM по умолчанию шлёт Ctrl+C и ждёт лишь 1,5 с, затем снимает процесс — для `zam-server`
задайте больше: `nssm set <имя службы> AppStopMethodConsole 90000`.
Предел 90 с рассчитан на ожидание WAL Qdrant `shutdown_flush_wait_ms = 10000` (10 с). Если
увеличить ожидание до максимума 60 с, поднимите стоп-таймаут примерно до 140 с
(`AppStopMethodConsole 140000`).
Жёсткое снятие процесса удлиняет следующий старт (см. «Известные ограничения»).

## Linux

1. Распакуйте архив `zam-server-<версия>-linux-x64-cpu.tar.gz` (или `-gpu.tar.gz`) в
   `/opt/zeroaimemory` (лишний верхний каталог архива отбрасывается):

   ```
   sudo install -d /opt/zeroaimemory
   sudo tar -xzf zam-server-<версия>-linux-x64-cpu.tar.gz --strip-components=1 -C /opt/zeroaimemory
   ```

   Исполняемые файлы: `/opt/zeroaimemory/zam-server`, `/opt/zeroaimemory/zam`,
   `/opt/zeroaimemory/qdrant/<версия>/qdrant`.
2. Создайте пользователя и каталоги:

   ```
   sudo useradd --system --home /var/lib/zeroaimemory --shell /usr/sbin/nologin zam
   sudo install -d -o zam -g zam /var/lib/zeroaimemory
   sudo install -d /etc/zeroaimemory
   sudo cp /opt/zeroaimemory/config.example.toml /etc/zeroaimemory/config.toml
   ```

   В `config.toml` укажите `data_dir = "/var/lib/zeroaimemory"` и `[admin] password_hash`
   (хэш: `/opt/zeroaimemory/zam-server hash-password`, пароль вводится по приглашению).
3. Установите юнит systemd и запустите службу:

   ```
   sudo cp /opt/zeroaimemory/systemd/zam-server.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now zam-server
   sudo journalctl -u zam-server -n 50      # первый токен в рамке (stderr)
   ```

   В юните `ReadWritePaths` должен совпадать с `data_dir`; остановка — `SIGTERM`,
   `TimeoutStopSec=90`: худший случай — недоделанная пачка инференса (до 60 с), перечанковка
   (до 10 с), ожидание WAL Qdrant `shutdown_flush_wait_ms = 10000` (10 с) и SIGTERM Qdrant
   (до 10 с); обычно после записи — 10–15 с. Если увеличить `shutdown_flush_wait_ms` до
   максимума 60 с, поднимите `TimeoutStopSec` примерно до 140 с.
4. `zam-server` собран под `x86_64-unknown-linux-gnu` на Ubuntu 22.04 (glibc 2.35 и новее);
   `zam` — статический (musl).

## За обратным прокси (Traefik)

Сервер можно опубликовать по HTTPS под префиксом пути, например `https://example.com/memory`.

1. В `config.toml` сервера:

   ```
   [server]
   bind = "0.0.0.0:7700"
   public_url = "https://example.com/memory"
   base_path = "/memory"                 # префикс без завершающего "/"
   trusted_proxies = ["172.18.0.2"]      # адрес (или подсеть) Traefik, как его видит сервер
   ```

   `X-Forwarded-For` и `X-Forwarded-Proto` принимаются только от адресов из `trusted_proxies`:
   по ним определяются IP клиента (лимиты и аудит) и HTTPS. Если последний `X-Forwarded-Proto`
   от доверенного прокси равен `https`, cookie сессии WebUI получает атрибут `Secure`.
   Без `trusted_proxies` все клиенты за прокси выглядят как один IP (сервер один раз
   предупреждает об этом в журнале), а cookie остаётся без `Secure`.
2. Traefik передаёт путь как есть: префикс **не** срезается (`StripPrefix` не нужен), сервер
   сам обслуживает маршруты под `base_path`. Пример меток Docker:

   ```
   labels:
     - traefik.enable=true
     - traefik.http.routers.zam.rule=Host(`example.com`) && PathPrefix(`/memory`)
     - traefik.http.routers.zam.entrypoints=websecure
     - traefik.http.routers.zam.tls=true
     - traefik.http.services.zam.loadbalancer.server.port=7700
   ```

   Тот же маршрут в файловом провайдере (`dynamic.yml`):

   ```
   http:
     routers:
       zam:
         rule: "Host(`example.com`) && PathPrefix(`/memory`)"
         entryPoints: [websecure]
         tls: {}
         service: zam
     services:
       zam:
         loadBalancer:
           servers:
             - url: "http://10.0.0.5:7700"
   ```

   Traefik по умолчанию добавляет `X-Forwarded-For` и `X-Forwarded-Proto`.
3. Клиенты указывают полный адрес с префиксом: `ZeroAIMemoryUrl=https://example.com/memory`.

## Известные ограничения (0.0.4-m3)

- Не все цели производительности §17 ТЗ на CPU выполнены — отступления приняты владельцем:
  индексация bge-m3 int8 — 690–770 токенов/с (цель — 3 чанка по 400 токенов в секунду), поиск
  только по полнотексту — p95 30–32 мс на 10 тыс. заметок (цель 20 мс; данные на HDD).
  Подробно — `docs/journal.md` в репозитории.
- Первый запуск после жёсткой остановки (сбой, снятие процесса) во время массовой индексации
  на HDD может занять 5–14 с (замер: медиана 6,6 с, максимум 13,8 с) до готовности векторного поиска: Qdrant повторяет журнал (WAL) и
  синхронно сбрасывает сегменты. Поиск в это время отвечает из полнотекста с `degraded: true`.
  Штатная остановка (Ctrl+C, SIGTERM) сразу после записи ждёт подтверждения WAL до 10 с
  (`[qdrant] shutdown_flush_wait_ms`), после неё старт — около 2 с (Windows, HDD; замерено с ожиданием 6 и 15 с,
  умолчание 10 с отдельно не замерялось).
- Реранкер jina на CPU добавляет к памяти сервера около 0,6 ГиБ при одной сессии и
  0,9 ГиБ при двух (`ml.rerank_sessions`, по умолчанию 0 — авто, до 2): меньше сессий — меньше памяти, но
  медленнее.
- Команды `zam-server service install`, `doctor` и `backup` — этап M7. На Windows запуск в фоне
  — Планировщик заданий или NSSM (см. «Windows»), на Linux — юнит systemd из комплекта.
- Режим `qdrant.mode = "edge"` — прототип, в сервер не подключён: векторный поиск с ним
  выключен (см. `docs/adr/0001-qdrant-edge.md`).
- GPU на Linux (драйвер NVIDIA и `zam-cuda`) проверен сборкой и smoke на CPU в CI; ручного
  прогона на Linux с GPU ещё не было.
- `ml.unload_after` (выгрузка моделей по простою) не реализован: значение принимается, сервер
  пишет WARN и держит модель в памяти. Модель эмбеддингов загружается при старте сервера,
  реранкер — при первом запросе с `rerank: on`.
- Совместный доступ: связи между личной памятью участника и общим решением отвечают 422;
  владельцы-пользователи управляют доступом через CLI и REST (страница WebUI «Решения» —
  администратору). Vault участника при доступе `ro` и после отзыва недоступен ему самому, пока
  доступ не вернут (записи остаются в его базе).
- Человеческий токен (`human_token`) защищён только на стороне CLI (терминал, подтверждение
  вводом id): агент под той же учётной записью ОС может прочитать `~/.zeroaimemory/config.toml`
  и поставить `axiom` запросом к REST напрямую. Подтверждайте `axiom` в WebUI или держите токен
  вне досягаемости агента (см. «Первый токен администратора»).
- Мастер-ключ Vault по умолчанию лежит в каталоге данных: бэкап каталога вместе с
  `master.key` раскрывает Vault (см. «Vault»).
- Откат на прежнюю версию по копиям `bak-v<N>` теряет всё записанное после обновления;
  `-wal`/`-shm` текущих баз перед подкладыванием копии нужно удалить (см. «Обновление»).
- Корзина не очищается автоматически; старые ревизии хранят исходный текст, в том числе то, что
  сканер секретов маскирует при индексации. Значения Vault в ревизиях только зашифрованы.
- Реранк (`rerank: on`) заменяет балл баллом реранкера: бусты надёжности (`axiom`, `theorem`)
  и вида insight при нём не действуют.
- Проактивное вспоминание по триггерам insight, MCP и хуки агентов — этап M4: в M3 триггеры
  хранятся и отдаются `GET /triggers`.
- Во время reindex и пересборки индекса векторная выдача неполна: `/search` добавляет
  `warnings: ["index rebuilding"]` (CLI и WebUI пишут это по-русски), `pending_count` — сколько
  заметок области ещё ждут индексации.

## Обновление

Остановите сервер, замените файлы комплекта (конфигурацию и каталог данных не трогайте),
запустите сервер: миграции баз применяются автоматически, копия файла создаётся перед миграцией.

**Копии перед миграцией.** Каждая база, схему которой обновляет новая версия, копируется
рядом с собой: `system.db.bak-v<N>` и `users/<id>.db.bak-v<N>`, где `N` — версия схемы до
обновления (копия делается `VACUUM INTO`, на HDD — секунды на сотню мегабайт). Копии
сервер не удаляет: при каждом следующем обновлении схемы прибавляется копия с новым `N`
(копия той же версии перезаписывается), поэтому место под них нужно на размер баз за каждое
обновление. Удаляйте копии вручную, когда убедились, что новая версия работает.

**С 0.0.2-m1 на 0.0.3-m2** (появляется векторный индекс):

1. Скачайте модели (`zam-server models fetch`, см. «Модели») — до или после обновления:
   без них сервер работает как в M1, только полнотекстом, и сообщает об этом.
2. Первое открытие каждой базы — дольше обычного: миграции user 0004–0006 (копия
   `users/<id>.db.bak-v3`, `system.db.bak-v1`), затем в фоне разовая перенарезка всех
   заметок новым чанкером (на 10 тыс. заметок — около 30 с на HDD; поиск и запись в это
   время работают). Пока база не открыта, её первый запрос ждёт миграцию.
3. Затем — полная векторизация всех заметок: кэша эмбеддингов в M1 не было, каждый чанк
   проходит через модель. Длительность ≈ объём заметок в токенах / скорость: CPU (bge-m3
   int8) — около 700 токенов/с, т. е. порядка часа на 2,5 млн токенов (≈ 10 тыс. заметок по
   250 токенов); GPU (RTX 3090, fp16) — 4–7 тыс. токенов/с. Ход — `GET /api/v1/index/status`
   и раздел «Индекс» WebUI (очередь), у поиска — `pending_count`. До конца векторный поиск
   находит не всё; полнотекстовый — всё сразу.
4. Первый перезапуск сразу после массовой индексации может занять 5–10 с до готовности
   векторного поиска (Qdrant повторяет журнал), дальше — 1–2 с.

**С 0.0.3-m2 на 0.0.4-m3** (журналы, граф, Vault, совместный доступ):

1. Первое открытие базы применяет миграции system 0003–0005 и user 0007–0012 (копии
   `system.db.bak-v2` и `users/<id>.db.bak-v6`). Решения M2 регистрируются в реестре при
   старте сервера (одна строка INFO с итогом); у одного GUID у двух пользователей владельцем
   становится первый, у второго решение переименовывается под новый GUID, а к исходному
   ставится запрос доступа.
2. В фоне, без остановки поиска и записи: перенарезка заметок с учётом силы границ (векторы
   берутся из кэша, инференс — только для изменившихся листов), выведенные рёбра графа из
   wiki-ссылок, пересканирование секретов, дозаполнение `certainty` из frontmatter.
3. При первом старте создаётся мастер-ключ Vault `<data_dir>/master.key` — сразу сохраните его
   копию отдельно от бэкапа каталога данных и исключите из бэкапа: бэкап каталога вместе с
   ключом раскрывает Vault. Чтобы ключ сразу лежал вне каталога данных, задайте до первого
   старта `[vault] master_key_file` (см. «Vault»).
4. Юнит systemd из комплекта — с `TimeoutStopSec=90`; для NSSM — `AppStopMethodConsole 90000`
   (см. «Windows», «Linux»).

**Что теряет откат.** Копии `bak-v<N>` — снимки баз на момент обновления (первого открытия
базы новой версией). Откат на копию теряет **всё**, что записано после этого момента, а не
только новые сущности этапа: новые и изменённые заметки и их ревизии, корзину, привязки
вложений (их файлы в `blobs/` остаются без ссылок), пользователей и токены, выпущенные после
обновления (у новых пользователей копии нет вовсе), настройки и аудит. Экспорта в M2 и M3 нет
(экспорт и импорт — этап M7), поэтому до отката:
- сохраните нужное, пока работает новая версия: `zam read <цель> > файл.md` по нужным
  заметкам (`zam tree` — их список), после отката запишите их снова (`zam write --file`);
  в Windows PowerShell 5.1 `>` перекодирует вывод в UTF-16 — перенаправляйте из `cmd.exe`;
  заметки Human по токену не читаются (404) — изменённые после обновления сохраняйте из WebUI
  администратора;
- сохраните текущие базы целиком, чтобы можно было вернуться на новую версию: при
  остановленном сервере скопируйте каталог данных или хотя бы `system.db`, `users/*.db`
  **вместе с их `-wal` и `-shm`**, если они есть.

**Как подложить копию (для любого отката).** Базы открываются в режиме WAL: рядом с
`system.db` и `users/<id>.db` живут `system.db-wal`/`system.db-shm` и
`users/<id>.db-wal`/`users/<id>.db-shm`. Журнал WAL не привязан к файлу базы: если оставить
его рядом с подложенной копией, SQLite применит к старой схеме кадры новой — база будет
повреждена. Порядок:
1. Остановите сервер штатно (Ctrl+C, `systemctl stop`, остановка службы) и дождитесь выхода
   процесса; убедитесь, что `zam-server` не запущен.
2. Уберите из каталога данных текущие `system.db`, `users/<id>.db` **и их `*-wal`, `*-shm`**
   (перенесите в сохранённую копию из предыдущего шага или удалите).
3. Переименуйте копии: `system.db.bak-v<N>` → `system.db`, `users/<id>.db.bak-v<N>` →
   `users/<id>.db`. Базы пользователей без копии нужной версии (созданных после обновления)
   уберите из `users/`: в восстановленном `system.db` таких пользователей нет.
4. Верните файлы прежнего комплекта. Если для целевой версии нужен сброс индекса (откат на
   0.0.3-m2 — см. ниже), выполните `zam-server qdrant reset --yes` прежнего комплекта сейчас,
   до запуска.
5. Запустите прежний комплект.

Так же — при восстановлении одной базы из копии `bak-v*` или бэкапа (см. «Состояние индекса и
reindex»): сервер остановлен, `-wal`/`-shm` этой базы удалены.

**Откат на 0.0.3-m2.** Копии `users/<id>.db.bak-v6` и `system.db.bak-v2` — порядок выше.
На шаге 4 перед первым стартом прежней версии сбросьте индекс — `zam-server qdrant reset --yes`: точек
записей журналов M2 не знает; индекс пересоберётся из кэша эмбеддингов без инференса.
Сам откат на 0.0.3-m2 тестом не проверялся.

**Откат на 0.0.2-m1.** Копии `users/<id>.db.bak-v3` и `system.db.bak-v1` — порядок выше (M1 не
открывает базы новой схемы и откажет с ошибкой). Каталог `<data_dir>/qdrant/` и
`<data_dir>/models/` прежней версии не нужны, их можно удалить.
