# ZeroAIMemory: установка

Комплект содержит сервер `zam-server`, клиент `zam`, библиотеки ONNX Runtime и pdfium,
Qdrant (`qdrant/<версия>/`), токенизатор bge-m3 (`tokenizers/bge-m3-int8/tokenizer.json`, 17 МБ;
лицензия MIT — `LICENSES/BGE-M3-TOKENIZER-LICENSE-MIT.txt`), пример конфигурации
`config.example.toml`, копии манифестов `deploy/` (что и откуда скачивают `qdrant fetch`,
`models fetch` и `cuda fetch`; в `zam-server` они встроены) и лицензии (`LICENSES/`).
Поддерживаются Windows x64 и Linux x64.

| Архив релиза | Что внутри |
|---|---|
| `zam-server-<версия>-<os>-x64-cpu` | комплект с ONNX Runtime для CPU |
| `zam-server-<версия>-<os>-x64-gpu` | то же, но ONNX Runtime с CUDA EP; библиотек NVIDIA нет (см. «GPU (CUDA)»), без GPU работает на CPU |
| `zam-<версия>-<os>-x64` | только клиент `zam`; с 0.0.11-m6 — и `LICENSES/`: сводка лицензий его зависимостей (`THIRD-PARTY-RUST.html`) и уведомления запросов тегов карты кода (`TREE-SITTER-QUERIES-MIT.txt`) |
| `zam-models-<версия>-<модель>.zip` | одна модель с `bundle = true` — для машин без интернета (см. «Модели») |
| `zam-cuda-<версия>-<os>-x64` | библиотеки NVIDIA для GPU-комплекта — для машин без интернета |

`<os>` — `windows` (zip) или `linux` (tar.gz). Контрольные суммы всех архивов — в `SHA256SUMS`.

## Порты и данные

| Что | Значение по умолчанию |
|---|---|
| Сервер (WebUI и API) | `0.0.0.0:7700` (`[server] bind`) |
| Qdrant HTTP / gRPC (запускается сервером, начиная с этапа M2) | `6333` / `6334` (`[qdrant]`) |
| Каталог данных | `./data` (`data_dir`), относительный путь считается от текущего каталога |

В каталоге данных лежат базы, индексы и файл блокировки; второй экземпляр сервера на тот же
каталог не запустится. Резервную копию без остановки сервера снимает `zam-server backup` (с
0.0.11-m6, см. «Перенос на другую машину»); копию каталога файлами делайте только при остановленном
сервере. Мастер-ключ Vault `master.key` в копию не входит: храните его отдельно (см. «Vault:
секреты и мастер-ключ»). Автокопии раз в сутки — `[backup] schedule = "daily"` (время — `at`,
UTC; хранится `keep` последних копий; по умолчанию выключены: копия на том же диске размером с
базы может его заполнить). Время последней копии — поле `backup` в `GET /api/v1/index/status`;
предупреждение `no_recent_backup` там стоит, пока копии нет или она старше `warn_days` суток (7).
Считаются только копии-каталоги в `[backup] dir` (по умолчанию `<data_dir>/backups`): архив
`--zip` и копия `--dir` в другое место предупреждение не снимают, и `keep` их не удаляет. С
0.0.15-m7.2 копию снимают и из WebUI, а предупреждение видно там же: плашка над страницами
администратора и блок «Копии» на «Индексе» (см. «Копии из WebUI»).

На Windows полный путь каталога данных — не длиннее 190 символов. Внутри него лежат файлы,
пути к которым на 60–160 символов длиннее: базы SQLite открываются обычными путями Win32
(предел MAX_PATH = 260), рабочий каталог процесса Qdrant тоже ограничен MAX_PATH; хранилище
Qdrant пути длиннее 260 символов выдерживает. С более длинным путём `serve` и команды, которым
нужен каталог данных (`migrate`, `reindex`, `qdrant status`, `qdrant reset`, `models …` без
заданного `ml.models_dir`), сразу, до загрузок, завершаются с ошибкой «каталог данных …
слишком длинный для Windows» — перенесите каталог или укажите короче (`data_dir`,
`ZAM_DATA_DIR`, `--data-dir`). `cuda fetch`, `qdrant fetch` и `models …` с заданным
`ml.models_dir` каталог данных не используют и длину не проверяют. Префикс `\\?\` в длину не входит.
На Linux такого предела нет. Если Qdrant всё же падает с «os error 3» («системе не удаётся
найти указанный путь») в журнале (`component=qdrant`), причина та же — слишком длинный
реальный путь каталога данных (например, часть пути — символическая ссылка или точка
подключения): перенесите каталог данных ближе к корню диска.

**Малая машина** (с 0.0.17-m7.4). Большие JSON-тела — отчёт MCP с картинками в base64 до
`[reports] mcp_max_bytes` и тела `/mcp` больше `[limits] note_max_bytes` — держатся в памяти
целиком, пока запрос обрабатывается; одновременно таких — не больше `[limits] big_body_permits`
(по умолчанию 2, от 1 до 8), лишнее получает 503 `/problems/busy` с `Retry-After`. На малой
машине (LXC 8 ГБ) поставьте `big_body_permits = 1`; большие отчёты всё равно лучше слать `zam
report` (multipart потоком, без base64). При откате на 0.0.16-m7.3 ключ из конфигурации уберите.

## Первый запуск

Администратор задаётся не в базе данных, а в конфигурации. Два варианта:

1. Хэш пароля в `config.toml` (рекомендуется). Запустите команду без аргументов и введите
   пароль в ответ на приглашение (ввод не отображается и не попадает в историю оболочки):

   ```
   zam-server hash-password
   ```

   Результат (`$argon2id$...`) вставьте в `[admin] password_hash`. Не передавайте пароль
   через `echo ... |`: в Windows PowerShell 5.1 конвейер меняет кодировку не-ASCII символов,
   `cmd` добавляет к паролю пробел перед `|`, а сама команда остаётся в истории.
   Для скриптов в Linux — чтение без отображения:

   ```
   IFS= read -rs -p 'Пароль: ' PW && echo >&2 && printf '%s\n' "$PW" | zam-server hash-password; unset PW
   ```
2. Переменная окружения `ZAM_ADMIN_PASSWORD` (пароль хэшируется в памяти; удобно для проверки).

Скопируйте `config.example.toml` в `config.toml`, при необходимости измените значения и запустите:

```
zam-server serve --config config.toml
```

Параметры `--bind` и `--data-dir` переопределяют конфигурацию; переменные окружения
`ZAM_<РАЗДЕЛ>__<КЛЮЧ>` (например, `ZAM_SERVER__BIND`) тоже.

### Первый токен администратора

При самом первом старте сервер выпускает токен администратора и показывает его **один раз**,
мимо журнала (`zam-server.log`). Куда — зависит от того, терминал ли stderr:

- **stderr — терминал** (запуск вручную в консоли): рамка с токеном, файл не пишется:

  ```
  ==== ZeroAIMemory: первый токен администратора (показывается один раз) ====
  ZeroAIMemoryToken=<токен>
  ==========================================================================
  ```

- **stderr не терминал** (служба systemd — её stderr уходит в journald и хранится там, служба
  Windows, перенаправление `2> файл`): токен в stderr **не печатается**, а записывается в
  `<data_dir>/first-admin-token.txt` с правами только владельца (Linux — `0600`, Windows — DACL
  владельца, SYSTEM и администраторов, как у `master.key`). В stderr — путь к файлу:

  ```
  ==== ZeroAIMemory: первый токен администратора записан в файл (показывается один раз) ====
  ZeroAIMemoryTokenFile=/var/lib/zeroaimemory/first-admin-token.txt
  Прочитайте токен, сохраните его и удалите файл: в журнал службы токен не пишется.
  ```

  Прочитайте и **удалите файл** после того, как сохраните токен:

  ```
  sudo cat /var/lib/zeroaimemory/first-admin-token.txt
  sudo rm /var/lib/zeroaimemory/first-admin-token.txt
  ```

  Пока файл лежит в каталоге данных, каждый старт пишет в журнал WARN «удалите файл после
  прочтения» (содержимое не выводится).

  Если файл записать не удалось (каталог только для чтения, нет места), токен **не
  печатается** и сразу отзывается, а в stderr — предупреждение «не удалось записать <путь>:
  <ошибка>». Доступ не теряется: войдите в WebUI паролем администратора и выпустите токен
  (Аккаунт или Пользователи).

Сохраните токен: повторно он не показывается. Новые токены выпускаются в WebUI
(`http://<хост>:7700/`, вход администратора) или через админ-API.

**Первый токен — агентский, админ-API он не открывает.** Любой токен, в том числе этот, — токен
агента (решение владельца 2026-10-26, §11.4 ТЗ): с ним работают `zam`, хуки и MCP, а
`/api/v1/admin/*` отвечают на него 403 «администраторский маршрут: нужен вход администратора
(POST /api/v1/auth/login, cookie и x-csrf-token); токен — агентский»; выпуск своих токенов
(`/api/v1/auth/tokens`) по токену — тоже 403: агент токены не выпускает. Админ-API — только по
входу администратора, как в WebUI:

1. `POST /api/v1/auth/login` с телом `{"login": "<логин>", "password": "<пароль>"}` (логин —
   `[admin] login`, по умолчанию `admin`) → 200, cookie `zam_session` (сессия на 12 часов) и
   тело `{"csrf": "…"}`. Попыток входа — 5 в минуту с одного адреса.
2. Чтение (`GET`) — с этой cookie; изменяющие запросы (`POST`, `PATCH`, `DELETE`) — с cookie и
   заголовком `x-csrf-token: <csrf>` (без него — 403).
3. Свой токен администратора — `POST /api/v1/auth/tokens {"name": "…", "access": "rw"|"ro"}`,
   токен пользователю — `POST /api/v1/admin/users/<id>/tokens` с тем же телом (`id` — из
   `GET /api/v1/admin/users`), отзыв — `DELETE /api/v1/admin/tokens/<id токена>`. Ответ выпуска
   — 201 `{"info": {…, "prefix": "zam_XXXXXXXX"}, "plaintext": "<токен>"}`: токен целиком
   показывается один раз. Человеческих токенов нет: `"human": true` — 400.

Пример (Linux, `curl` и `jq`): пароль вводится без отображения и не попадает ни в историю, ни в
аргументы команд (`printf` — встроенная команда bash, `jq` читает пароль из stdin); cookie — в
файле `jar`, доступном только владельцу (`umask 077` — на время примера: команды можно
выполнять по одной, подставив `<id>` из списка, а прежний umask возвращает последняя строка):

```bash
old_umask=$(umask); umask 077
IFS= read -rs -p 'Пароль администратора: ' PW && echo >&2
CSRF=$(printf '%s' "$PW" | jq -Rs '{login: "admin", password: .}' |
  curl -sf -c jar -H 'Content-Type: application/json' --data-binary @- \
    http://localhost:7700/api/v1/auth/login | jq -r .csrf); unset PW
curl -sf -b jar http://localhost:7700/api/v1/admin/users | jq '.[] | {id, name}'
curl -sf -b jar -H "x-csrf-token: $CSRF" -H 'Content-Type: application/json' \
  -d '{"name": "laptop", "access": "rw"}' \
  http://localhost:7700/api/v1/admin/users/<id>/tokens | jq -r .plaintext
curl -sf -b jar -H "x-csrf-token: $CSRF" -X POST http://localhost:7700/api/v1/auth/logout
rm -f jar; umask "$old_umask"
```

То же в Windows PowerShell 5.1 (`-WebSession` хранит cookie; логин — из
`GetNetworkCredential().UserName`, без префикса домена: диалог 5.1 может вернуть `\admin`, и вход
ответил бы 401; тело — байтами UTF-8, чтобы пароль с не-ASCII символами не перекодировался).
Логин с `@` или `\` `GetNetworkCredential()` делит на домен и имя — такой логин впишите строкой:
`login = '<логин>'`:

```powershell
$c = Get-Credential -UserName admin -Message 'Вход администратора ZeroAIMemory'
$n = $c.GetNetworkCredential()
$b = @{ login = $n.UserName; password = $n.Password } | ConvertTo-Json
$r = Invoke-RestMethod -Method Post http://localhost:7700/api/v1/auth/login -SessionVariable zam `
  -ContentType 'application/json' -Body ([Text.Encoding]::UTF8.GetBytes($b))
Remove-Variable b, c, n
Invoke-RestMethod http://localhost:7700/api/v1/admin/users -WebSession $zam
(Invoke-RestMethod -Method Post http://localhost:7700/api/v1/admin/users/<id>/tokens `
  -WebSession $zam -Headers @{ 'x-csrf-token' = $r.csrf } -ContentType 'application/json' `
  -Body '{"name": "laptop", "access": "rw"}').plaintext
Invoke-RestMethod -Method Post http://localhost:7700/api/v1/auth/logout -WebSession $zam `
  -Headers @{ 'x-csrf-token' = $r.csrf } | Out-Null
```

Сессия пользователя WebUI (не администратора) на админ-маршруты получает 403 «только
администратору».

Проверка подключения клиентом:

```
zam status --url http://127.0.0.1:7700 --token <токен>
```

Коды выхода `zam status`: 0 — всё в порядке, 1 — ошибка конфигурации,
2 — сервер недоступен, 3 — токен отклонён.

`zam status` печатает адрес сервера и откуда он взят, токен, пользователя, решение, роль в нём и
версию блока инструкции. Токен целиком не печатается: `zam status` и `--json` показывают префикс
`zam_XXXXXXXX…` — тот же, что в списке токенов WebUI, по нему токен узнают и отзывают. Решение (с
0.0.13-m6.6) — строкой `Решение:  «<имя>» (<GUID>) — <путь solution.toml>`, в `--json` — поля
`solution_id` и `solution_name`; переименованное на сервере (`zam solution rename`) — имя реестра с
пометкой «(в solution.toml — «<имя файла>»)» (в `--json` — `solution_name` реестра и
`solution_file_name` файла); файл не читается — путь и причина (`solution_error`).

Без флагов `zam` ищет адрес и токен по порядку: `--url`/`--token`, переменные `ZAM_URL`/`ZAM_TOKEN`,
блок в файлах проекта от текущего каталога вверх (ближайший каталог важнее; внутри каталога —
`CLAUDE.local.md`, затем `CLAUDE.md`, затем `AGENTS.md`), затем `~/.zeroaimemory/config.toml`.
Адрес и токен ищутся независимо, но токен из `~/.zeroaimemory/config.toml` (с 0.0.14-m7.1) — только
для найденного адреса: ключом `[servers."<адрес>"]` или прежними `url`/`token` верхнего уровня,
если `url` — этот адрес. Токен другого сервера на этот не отправляется (подробно — «Токены
нескольких серверов» ниже). Поиск файлов вверх (и `.zeroaimemory/` проекта) не заходит в
каталоги из `ZAM_CEILING_DIRECTORIES` и выше них (список путей, как `PATH`; смысл — как у
`GIT_CEILING_DIRECTORIES`, с 0.0.12-m6.5): так тесты и вложенные проекты не подхватывают
подключение внешнего каталога. Прокси `zam` берёт из окружения по схеме адреса, как curl:
`http://` — `http_proxy`/`HTTP_PROXY`, `https://` — `https_proxy`/`HTTPS_PROXY`, затем
`ALL_PROXY`; `NO_PROXY` — имена (с поддоменами), IP и подсети (`10.0.0.0/8`); loopback —
всегда без прокси (до 0.0.12-m6.5 `HTTPS_PROXY` применялся и к `http://`). Блок в `CLAUDE.md`:

```
<!-- zeroaimemory:begin v1 -->
ZeroAIMemoryUrl=http://<хост>:7700
ZeroAIMemoryToken=<токен>
<!-- zeroaimemory:end -->
```

**Аксиомы** (`certainty: axiom`, §7.5 ТЗ) ставит человек в WebUI или агент по прямому
указанию пользователя — обычным токеном (`zam insight certify <id> axiom --reason "…"`); смена
статуса агентом — только с причиной, она остаётся в истории записи. Человеческих токенов и флага
`--human` с 0.0.5 нет (решение владельца 2026-10-26): ключ `human_token` в
`~/.zeroaimemory/config.toml` больше не читается, ранее выпущенные человеческие токены работают
как обычные (агентские) — сервер пишет о них одну строку WARN при старте.

Личный токен удобнее держать в `CLAUDE.local.md` (обычно не коммитится) или в
`~/.zeroaimemory/config.toml` (так делает `zam init`). Блок v2, который пишет `zam init`, токена не
содержит, а с `zam init --url-to home|local` (с 0.0.13-m6.6) — и адреса сервера (см. «Подключение
агента»).

## Подключение агента (`zam init`)

Клиент `zam` раздаёт сам сервер, без входа: `GET /downloads/zam/windows-x64` и
`GET /downloads/zam/linux-x64` (комплект сервера содержит `zam` обеих ОС: своей — рядом с
`zam-server`, другой — в `downloads/<платформа>/`; каталог можно переопределить
`server.downloads_dir`). Команды установки с адресом сервера выдаёт `GET /api/v1/agent-setup`
(поле `install`) и страница WebUI «Подключение агента»:

```
# Windows (PowerShell)
$d = "$env:LOCALAPPDATA\Programs\zam"; New-Item -ItemType Directory -Force $d | Out-Null
Invoke-WebRequest 'http://<хост>:7700/downloads/zam/windows-x64' -OutFile "$d\zam.exe"
$p = [Environment]::GetEnvironmentVariable('Path', 'User'); if (($p -split ';') -notcontains $d) { [Environment]::SetEnvironmentVariable('Path', $(if ($p) { "$p;$d" } else { $d }), 'User') }
# zam, хуки и zam mcp (.mcp.json) берут токен из ~/.zeroaimemory/config.toml (zam init --token); ZAM_TOKEN — для MCP по HTTP
[Environment]::SetEnvironmentVariable('ZAM_TOKEN', '<токен>', 'User')
# имя машины для X-Zam-Machine — одно для zam, хуков и MCP
[Environment]::SetEnvironmentVariable('ZAM_MACHINE', $env:COMPUTERNAME, 'User')

# Linux
mkdir -p ~/.local/bin && curl -fsSL 'http://<хост>:7700/downloads/zam/linux-x64' -o ~/.local/bin/zam && chmod +x ~/.local/bin/zam
case ":$PATH:" in *":$HOME/.local/bin:"*) ;; *) echo 'Добавьте ~/.local/bin в PATH' ;; esac
# токен: zam init --token сохранит его в ~/.zeroaimemory/config.toml (права 0600) — для zam,
# хуков и zam mcp; MCP по HTTP берёт его из ZAM_TOKEN — задайте её в файле, доступном только вам
# имя машины для X-Zam-Machine — одно для zam, хуков и MCP
[ -n "$ZAM_MACHINE" ] || echo "Добавьте в профиль оболочки: export ZAM_MACHINE=$(uname -n)"
```

Токен `zam`, хуки и `zam mcp` берут из `~/.zeroaimemory/config.toml` (права 0600) — его ключом
адреса сервера `[servers."<адрес>"]` записывает `zam init --token`. `ZAM_TOKEN` нужна только MCP
по HTTP (см. ниже).

**Токены нескольких серверов (с 0.0.14-m7.1).** Один проект ходит в один сервер: адрес — из
проекта (или `url` домашнего конфига), токен — по этому адресу. Домашний конфиг хранит токен для
каждого адреса:

```toml
url = "http://<хост>:7700"          # адрес для каталогов без своего

[servers."http://<хост>:7700"]
token = "zam_…"

[servers."http://<хост-стенда>:7700"]
token = "zam_…"
```

Адрес ключа нормализован: схема и хост — в нижнем регистре, без `/` в конце, порт и путь — как
есть (`http://Host:7700/` и `http://host:7700` — один сервер). Псевдонимы одного сервера — имя
хоста и IP, `localhost` и `127.0.0.1`, явный порт `:80` — разные адреса: ключ у каждого свой.
`zam init --token` второго сервера
пишет свою запись и не трогает токен первого. `url` верхнего уровня `zam init` в режиме `block`
записывает, если его ещё нет (другой адрес не заменяется), `--url-to home` — свой, `--url-to
local` его не трогает. Прежний формат (`url` и `token` верхнего уровня) читается как раньше —
токен принадлежит `url` верхнего уровня; первая запись токена `zam init` переводит его в
`[servers."<url>"]` (`url` остаётся). `token` верхнего уровня без `url` — ключ без адреса (так
его записывал `zam init --url-to local` 0.0.13-m6.6) — уходит на любой адрес, как раньше, пока
в конфиге нет записей `[servers]` с токеном; с ними он больше не используется. `zam status` в
обоих случаях пишет примечание «ключ без адреса … — привяжите: `zam init --url <адрес> --token
…`». `zam init --token` с тем же ключом привязывает его к адресу проекта (ключ уходит с верхнего
уровня), с другим — оставляет как есть, предупреждает, что прежний ключ больше не используется,
и не пишет рядом с ним `url` (тот сделал бы его ключом этого адреса); то же предупреждение — у
`zam init` без `--token` и у повтора без записи. `zam init --url-to home` пишет `url` верхнего
уровня, поэтому ключ без адреса ему нужно решить: тот же токен (записываемый или найденный для
адреса, например `ZAM_TOKEN`) — ключ переносится в `[servers."<адрес>"]`; другой — отказ (код 1)
до любой записи: привяжите ключ к его серверу (`zam init --url <адрес> --token …`) или удалите
строку `token` и повторите. Для адреса без
токена (в конфиге токены только других серверов) `zam`, `zam status` и `zam init` отвечают кодом 1
до обращения к сети с подсказкой `zam init --url <адрес> --token <токен>`; токена нет вовсе —
код 3, как раньше. Хуки в таком проекте на сервер не ходят: подсказка пишется в
`.zeroaimemory/logs/hooks.log` и одной строкой «ZeroAIMemory: … нет токена для <адрес> … zam init
--url <адрес> --token …» в выводе `session-start` — агент и человек видят её на старте сессии. Флаг `--token`, `ZAM_TOKEN` и токен в файлах проекта по-прежнему сильнее
домашнего конфига. `zam status` пишет источник:
`Источник токена: ~/.zeroaimemory/config.toml [servers."<адрес>"]`.

В корне проекта:

```
zam init --url http://<хост>:7700 --token <токен> --agent claude   # claude | codex | both
```

`zam init`:
- создаёт `.zeroaimemory/solution.toml` (новый GUID и имя каталога; `--id`, `--name` — свои) или
  читает существующий и регистрирует решение на сервере;
- вставляет блок инструкции между `<!-- zeroaimemory:begin vN -->` и `<!-- zeroaimemory:end -->` в
  `CLAUDE.md` (`claude`) и/или `AGENTS.md` (`codex`); текст вне блока не меняется;
- после подтверждения (`--yes` — без вопроса) добавляет хуки `zam hook …` в
  `.claude/settings.json` / `.codex/hooks.json` и сервер `zeroaimemory` в `.mcp.json` (с M6 —
  stdio-прокси `"command": "zam", "args": ["mcp"]`); чужие хуки и серверы остаются; `--no-hooks`, `--no-mcp` — пропустить.
  События хуков: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`,
  `SubagentStart`, `Stop`, `PreCompact`, `SessionEnd`, у Claude Code ещё `PostToolUseFailure` и
  `PostCompact`. `SessionEnd` и `PostCompact` — с M6: снимок сессии (см. «Снимок сессии» ниже)
  и отметка конца сессии; без вывода агенту;
- пишет `.zeroaimemory/.gitignore` (`cache/`, `logs/`);
- сохраняет токен в `~/.zeroaimemory/config.toml` ключом адреса сервера `[servers."<адрес>"]`
  (не в файлы проекта; с 0.0.14-m7.1): из `--token` или из прежнего блока v1 (тогда советует
  выпустить новый токен — старый лежал в файле проекта); другой токен того же адреса заменяет
  только явный `--token`, токены других адресов не трогаются. В режиме `block` (по умолчанию)
  проект берёт адрес из строки `ZeroAIMemoryUrl=` блока — это `server.public_url` сервера (или
  адрес запроса); если он отличается от `--url` (прокси, имя хоста вместо IP), тот же токен
  пишется и под адресом блока, если там токена нет, — `Токен сохранён … [servers."<--url>"] и
  [servers."<адрес блока>"]`; повтор `zam init` без `--token` дописывает адрес блока, если его
  нет. Другой токен под адресом блока не заменяется и с `--token` (адрес назвал сервер — он может
  вести на другой сервер): `zam init` пишет «под адресом <адрес> уже другой токен — не заменён;
  проект с блоком этого адреса пойдёт с прежним токеном» — проверьте `server.public_url`;
- для `--agent codex` `.mcp.json` не пишет (Codex читает MCP из `config.toml`, см. ниже).

Однострочник `zam init` из `GET /api/v1/agent-setup` (`init_cmd.linux` / `init_cmd.windows`) уже
экранирован для своей оболочки (одинарные кавычки).

**Адрес сервера вне файлов репозитория (`--url-to`, с 0.0.13-m6.6).** По умолчанию блок содержит
строку `ZeroAIMemoryUrl=<адрес>` (`--url-to block`, как раньше), а `CLAUDE.md` обычно коммитится:
в публичном репозитории это адрес внутренней сети. Блок без адреса:

```
zam init --url http://<хост>:7700 --token <токен> --url-to home    # адрес — в ~/.zeroaimemory/config.toml
zam init --url http://<хост>:7700 --token <токен> --url-to local   # адрес — в CLAUDE.local.md
```

- `home` — адрес ключом `url` в `~/.zeroaimemory/config.toml` (токен — в `[servers."<адрес>"]`);
  токены других адресов и прочие ключи файла не трогаются. Адрес там один на машину: уже записан
  другой — отказ (код 1) с советом `--url-to local`; тот же (без учёта регистра хоста и `/` в
  конце) — ничего не меняется. Режим годится и для worktree: файл общий.
- `local` — строка `ZeroAIMemoryUrl=<адрес>` в `CLAUDE.local.md` корня проекта (свой текст файла
  сохраняется, прежняя строка адреса заменяется). `CLAUDE.local.md` вносится в `info/exclude`
  репозитория (путь — `git rev-parse --git-path info/exclude`, файл общий для всех worktree;
  строка — `/<каталог проекта от корня репозитория>/CLAUDE.local.md`, символы шаблонов `[`, `]`,
  `*`, `?`, `\` в пути экранируются) после вопроса, `--yes` — без вопроса; отказ — предупреждение.
  Строка уже есть — без вопроса. После записи `zam init` проверяет `git check-ignore`: правило `!`
  в `.gitignore` сильнее `info/exclude`, тогда вместо «внесён» — предупреждение. Если
  `CLAUDE.local.md` уже в индексе git (закоммичен), исключение не действует, и адрес ушёл бы в
  репозиторий: `zam init` откажет (код 1) до записи файлов и регистрации решения — `git rm
  --cached CLAUDE.local.md` или `zam init --url-to home`. Адрес домашнего конфига не
  меняется — режим для нескольких серверов на одной машине. `CLAUDE.local.md` есть только в своём
  worktree: в новом worktree — `zam init --url-to local` (без флага повтор там выберет `home`:
  строки адреса в новом worktree ещё нет). С Codex (`--agent codex|both`) `zam init`
  предупредит: `CLAUDE.local.md` агент Codex не читает и адреса сервера в контексте не увидит (как
  и в режиме `home`), а `zam`, хуки и `zam mcp` адрес находят — порядок поиска адреса от агента не
  зависит.
- Строку адреса из блока вырезает сам `zam`, поэтому режимы работают с сервером любой версии.
  Если адрес есть в блоке ещё где-то (свой шаблон администратора, «Настройки → Шаблон
  инструкции»), `home` и `local` откажут (код 1) до записи файлов: уберите `{url}` из остального
  текста шаблона или подключите с `--url-to block`.
- Повторный `zam init` без флага сохраняет режим: в прежнем блоке нет строки адреса — адрес вне
  блока (в `CLAUDE.local.md`, если там есть строка адреса, иначе в домашнем конфиге). Поэтому
  обновление блока до новой версии не возвращает адрес в `CLAUDE.md`. Вернуть адрес в блок —
  `--url-to block`.
- Переход с `local` (`--url-to home` или `--url-to block`) убирает строку адреса из
  `CLAUDE.local.md`: она важнее и домашнего конфига, и блока, а повтор без флага выбрал бы по ней
  `local`. Свой текст файла остаётся; файл, где кроме строки адреса ничего не было, удаляется.
  В `block` строка убирается, только если в блоке есть строка `ZeroAIMemoryUrl=` (у своего
  шаблона, где `{url}` стоит в другом месте, её нет — тогда строка остаётся с предупреждением,
  иначе адрес потерялся бы). Символическая ссылка `CLAUDE.local.md` не удаляется: в её цель
  внутри проекта пишется текст без строки адреса, а ссылку за пределы проекта `zam init` не
  трогает и предупреждает.
- Своя строка `ZeroAIMemoryUrl=` вне блока в `CLAUDE.md`/`AGENTS.md` (ручная настройка) в
  режимах `home` и `local` остаётся — это текст пользователя, — но `zam init` предупредит: адрес
  уйдёт в репозиторий вместе с файлом.
- В режиме `block` в репозитории git `zam init` предупреждает, если `CLAUDE.md` (у Codex —
  `AGENTS.md`) не исключён из git или уже в индексе: «адрес сервера окажется в репозитории: zam
  init --url-to home».

После `home` или `local` в `CLAUDE.md`, `.mcp.json` и `.claude/settings.json` нет ни адреса, ни
токена — их можно коммитить, тогда они есть и в worktree, и у коллег. Коллеге на другой машине
адрес задаёт его `zam init --url-to home` (или переменная `ZAM_URL`).

Повторный запуск ничего не ломает: так же обновляется устаревший блок (о нём напоминают
`zam status` и дайджест в начале сессии агента). Битый JSON в `.claude/settings.json` или
`.mcp.json` `zam init` не перезаписывает — исправьте файл и повторите.

**MCP Claude Code (M6).** `.mcp.json` подключает stdio-прокси `zam mcp`: адрес, токен
(`~/.zeroaimemory/config.toml` или `ZAM_TOKEN`), решение и имя машины он берёт так же, как `zam`,
токена в файле нет. Прокси — подпроцесс агента, как и хуки, поэтому находит сессию агента (см.
«Сессия `zam mcp`» ниже): без неё нет пометок «уже выдавалось» и учёта токенов по сессии.
`.mcp.json` прежних версий (`"type": "http"`, `Bearer ${ZAM_TOKEN}`) продолжает работать, но без
сессии — пересоздайте его: `zam init` или фрагмент страницы «Подключение агента». HTTP-транспорт
по-прежнему годится агентам без хуков; ему нужна переменная `ZAM_TOKEN` в окружении агента
(Windows — команда выше; Linux — `export ZAM_TOKEN=<токен>` в файле профиля с `chmod 600`).

**Страница WebUI «Подключение агента»** собирает те же фрагменты по выбранным опциям (агент,
решение, MCP, хуки, запись в Rules, язык) с кнопкой «Копировать» у каждого; токен можно выпустить
там же — он попадёт в команды установки и `zam init`, но не в блок и не в `.mcp.json`. После
создания пользователя или выпуска токена WebUI открывает эту страницу сам. Там же — «Подсказки
хуков»: какие типы подсказок (`session_start`, `prompt`, `pre_tool`, `post_tool`, `checkpoint`)
показывать агенту этого пользователя; тип выключен, если он выключен здесь или в `[hooks]`
файла `config.toml` клиента. Текст блока администратор правит в «Настройки → Шаблон инструкции».

**Токены в WebUI (с 0.0.19).** «Название токена» — подпись для себя, а не сам токен: сам токен
сервер показывает один раз сразу после выпуска. Без названия токен не выпускается (ошибка под
полем); на «Подключении агента» название уже заполнено «<агент> · <решение> · <дата>», пока его не
правили. Ошибочно выпущенный токен отзывается там же кнопкой «Отозвать этот токен» (после отзыва
в командах снова заглушка `<токен>`) или в списках: «Аккаунт» → «Мои токены», у администратора —
«Администрирование» → «Пользователи». Отозванный токен перестаёт работать сразу и навсегда, строка
не удаляется (история, аудит) и уходит в свёрнутый список «Отозванные (N)».

**Подключение с переносом данных (с 0.0.19).** Проект, в котором агент уже работал, удобно
подключить вместе с переносом наработанного: на странице «Подключение агента» отметьте
«Подключить с переносом данных» — под текстом для CLAUDE.md/AGENTS.md появится «Задание агенту на
перенос». Скопируйте его и дайте агенту в корне проекта: он подключит проект (`zam init` без
токена — адрес и токен `zam` берёт из `~/.zeroaimemory/config.toml`), перенесёт свою память и
историю сессий, документацию, решения, ловушки, задачи и термины, синхронизирует карту кода,
проверит дайджест и поиск и пришлёт отчёт (`zam report`) с числами, рисками и вопросами. Это
долго и расходует токены; секреты агент кладёт только в Vault; кандидатов в Rules принимаете вы
(«Предложения»), аксиом агент не ставит. Текст зависит от выбранных агента, решения и языка; тот
же текст — `GET /api/v1/agent-setup?migrate=true` (поле `migration_prompt`). Сервер старше 0.0.19
задания не отдаёт — галочка выключена.

**Codex.** Хуки — `.codex/hooks.json` (Codex попросит подтвердить их в `/hooks`). MCP Codex
читает из `config.toml`, `zam init` его не пишет. Рекомендуемый вариант (M6) — stdio-прокси
`zam mcp`: адрес, токен и решение — как у остальных команд `zam`, сессия — из привязки хука
`session-start`; пример для `~/.codex/config.toml` или `.codex/config.toml` доверенного проекта:

```toml
[mcp_servers.zeroaimemory]
command = "zam"
args = ["mcp"]
```

HTTP-транспорт тоже работает, но без сессии (без пометок «уже выдавалось» и учёта по сессии):

```toml
[mcp_servers.zeroaimemory]
url = "http://<хост>:7700/mcp"
bearer_token_env_var = "ZAM_TOKEN"
http_headers = { "X-Zam-Solution" = "<agent_solution_id из solution.toml>" }
```

**Порядок ответов `zam mcp`.** Прокси выполняет до 16 запросов параллельно, поэтому ответы
приходят **не в порядке запросов** — JSON-RPC это допускает, ответ сопоставляется с запросом по
`id`. Клиент, который шлёт зависимые запросы (например, `memory_vault set`, затем `get` того же
имени, или запись заметки и её чтение), должен **дождаться ответа** на первый, прежде чем
отправлять второй; иначе второй может выполниться раньше. Клиенты MCP (Claude Code, Codex) ждут
ответа сами; это важно для своих скриптов поверх stdio.

**Сессия `zam mcp` (M6).** Пометки «уже выдавалось» и учёт токенов по сессии работают только
с явной сессией. `zam mcp` берёт её по порядку: переменная `ZAM_SESSION_ID` (скрипты, прогоны
замеров), затем файл привязки `.zeroaimemory/cache/agent-<pid>.json`, который пишет хук
`session-start` (`zam mcp` ищет его по общему с хуком процессу агента, не чаще раза в секунду;
файл не старше 12 ч, из нескольких подходящих — самый свежий; новая сессия после `/clear`
подхватывается со следующим вызовом). MCP-подпроцессу Claude Code переменной с id сессии не
передаёт. Без сессии MCP работает, но без пометок «уже выдавалось» и без учёта по сессии:
выданные токены идут в общий счётчик пользователя (`GET /api/v1/sessions/unattributed`; с
0.0.15-m7.2 — `zam sessions tokens --unattributed`). Долгие вызовы (вложения, реранк на CPU)
`zam mcp` ждёт до 10 мин. `zam` должен быть в `PATH` агента — `zam init` предупредит, если
его там нет. Сколько память выдала каждой сессии — `zam sessions tokens [<id> | --last N]`
(таблица «событие · вызовов · токенов · уже выдавалось» и доля повторных чтений; `--subagents` —
вместе с субагентами сессии; с 0.0.18-m7.5 — строка «открыто подсказок: N/M (p %)»: сколько
показанных подсказок агент открыл, у сервера 0.0.17 — «—») и страница WebUI «Сессии».

**Свой клиент MCP или REST (M6).** Агент без `zam` передаёт сессию сам: заголовком
`X-Zam-Session` или аргументом `session_id` у `memory_search`, `memory_read` и `memory_recall` —
один постоянный id на сессию, до 128 символов. Заданы оба и различаются — ошибка 400 (до M6 у
`memory_recall` побеждал аргумент). Без сессии всё работает, но без пометок «уже выдавалось», а
запись засчитывается последней сессии хуков пользователя (только сессии верхнего уровня, не
субагента). Что умеет сервер, клиент узнаёт по списку `features` в `GET /api/v1/health`; правила
совместимости и смысл каждого флага — [`docs/api-compat.md`](../docs/api-compat.md).

**Снимок сессии (M6).** Сессия агента может оборваться (лимит, закрытое окно, сбой) раньше, чем
агент запишет итог. На этот случай хуки `zam` по ходу сессии — на `Stop` (не чаще раза в минуту,
если журнал вырос на 16 КиБ или пришёл новый запрос), сжатии контекста и `SessionEnd`, а после
обрыва — при следующем старте
— снимают из журнала агента (`transcript_path`; без LLM и без токенов агента) короткий снимок:
хвост конспекта сжатия, последние запросы человека (до 5, по 500 символов), изменённые файлы (до
20 путей внутри проекта) и команды (до 10, только первая строка, без вывода). Ответы и рассуждения
агента, вывод инструментов и содержимое файлов не берутся. Секреты маскируются (`‹secret›`)
клиентом до отправки и ещё раз сервером; в командах клиент маскирует и значения флагов, которых
не знает сканер (`--password X`, `--token X`, `-pXXX` у mysql и `sshpass`, `-u user:pass` у
curl, wget и подобных, заголовки `Authorization:` и `X-Api-Key:`). Снимок — до 16 КиБ, один на
сессию; хранится на сервере в базе пользователя 14 дней (`[snapshot] keep_days`) и виден на
странице WebUI «Сессии». Следующая сессия того же решения получает его в дайджесте разделом
«Последнее известное состояние» — только если прежняя сессия оборвалась (после обычного конца
сессии и после `/clear` раздела нет) и её задача давно не обновлялась (или задачи нет, а файлы
менялись); после сжатия контекста — в пакете восстановления (без конспекта). Пароль, названный
словами, сканер не узнаёт — не диктуйте секреты в чат.

Выключатель — в `~/.zeroaimemory/config.toml` (или `<проект>/.zeroaimemory/config.toml`, он
сильнее):

```toml
[hooks]
session_snapshot = false   # журнал агента не открывается вовсе; по умолчанию true
```

Там же `snapshot_tail_kb` (2048 — сколько КиБ хвоста журнала читать, 64..16384) и
`snapshot_ms` (25 — срок сборки снимка, 5..50 мс). Прочие ключи клиента `[hooks]`: типы подсказок
`session_start`, `prompt`, `pre_tool`, `post_tool`, `checkpoint`, `subagent_start`,
`file_context`, `session_journal`, `recovery`, `code_map` (`false` — выключить; см. «Подсказки
хуков» выше), с M6 — `checkpoint_impact`
(`false`; `true` — перед завершением хук называет знания, которые правка могла сделать неверными)
и `holdout` (0; доля сессий контрольной группы замеров A/B, до 0,5). На сервере показ снимка
выключает `recall.snapshot_tokens = 0` (снимок при этом хранится). Агент без хуков снимает снимок
сам: `zam session snapshot --transcript <файл> [--format claude|codex] [--session <id>]`.

Полный протокол работы агента с памятью — `zam guide` (`GET /api/v1/agent-guide`).

**Шаблоны блока** правит администратор: `PATCH /api/v1/admin/settings
{"agent_setup": {"templates": {"claude.ru": "…"}}}` (ключи `<claude|agents|codex>.<ru|en>`,
`null` — вернуть шаблон по умолчанию; обязательна подстановка `{url}`, ещё есть `{solution}` и
`{rules}`). Каждое сохранение увеличивает версию блока — агенты получают напоминание обновить его.

## Работа с заметками из CLI

Адрес и токен `zam` находит так же, как `zam status`; у каждой команды есть флаги `--url`,
`--token` и `--json` (вывод в JSON). Токен целиком не печатается (`zam status` показывает префикс
`zam_XXXXXXXX…`, как список токенов WebUI).

**Цель** — `[пространство:]путь`: пространство `knowledge`, `rules`, `human`, `solution`
или GUID решения. Без префикса — решение из ближайшего вверх `.zeroaimemory/solution.toml`
(поля `id` и `name`), а если его нет — `knowledge`; одно имя без `/` (`zam read Сборка`)
разрешается так же. В `read`, `history`, `write` и `attach` вместо пути можно передать id узла
(26 символов, как печатает `zam`) или ссылку `n:<id>`. `zam read` принимает и ссылки выдачи
`zam search` на записи журналов — `i:<id>` (insight), `c:<id>` (changelog), `e:<id>`, `r:<id>`;
печатается текст записи (`--tier L0` — заголовок), с `--json` — элемент ответа `/read`.
Пути с пробелами и кириллицей берите в кавычки.

```
# дерево с краткими сводками (L0); --depth от 1 до 5
zam tree knowledge:
zam tree "knowledge:Инструменты" --depth 2

# запись: из stdin или --file; печатает <id>@<ревизия>
echo "# Bash скрипты" | zam write "knowledge:Инструменты/Bash скрипты" -m "первая версия"
zam write "knowledge:Инструменты/Bash скрипты" --file note.md --base-rev 3 --l0 "Полезные скрипты"

# чтение: Markdown как сохранён (байты, переводы строк не меняются)
zam read "knowledge:Инструменты/Bash скрипты"
zam read "knowledge:Инструменты/Bash скрипты" --section "Установка > Linux"
zam read "knowledge:Инструменты/Bash скрипты" --section "Linux"   # однозначный хвост пути заголовков (правка PATCH — только полный путь)
zam read n:<id> i:<id> --batch                   # ссылки из выдачи zam search, одной пачкой
zam read <id> --tier L1                          # L0 — сводка, L1 — оглавление
zam read <id> --rev 2                            # конкретная ревизия
zam read knowledge:a knowledge:b                    # перед каждой — строка «--- цель ---»
zam read n:<id> --focus "настройка прокси"       # фокус (с 0.0.11-m6): оглавление и ближайшие к запросу части
zam read n:<id> --range r7:1200-3400             # дочитать пропуск «[пропущено: range:r7:1200-3400 …]» фокуса

# история: ревизии (rev, время, автор, машина, сообщение), дифф, откат
zam history "knowledge:Инструменты/Bash скрипты"
zam history "knowledge:Инструменты/Bash скрипты" --diff 1..3
zam history "knowledge:Инструменты/Bash скрипты" --revert 1

# поиск: Markdown, в области — текущее решение, Knowledge и Rules; --all — все решения
zam search "bash скрипты"
zam search docker --all --mode notes --top-k 5
# бюджет и фильтры (с 0.0.13-m6.6): ловушки и провалы о файле, с историей; бюджет срезал
# карточки — в stderr «показано K из L: бюджет — ещё N (--budget), слабые — M»
zam search "сборка" --kind insight --insight-kind gotcha --insight-kind failure \
  --file src/build.rs --history --budget 2000

# вложение: печатает ссылку _attachments/… для вставки в заметку
zam attach "knowledge:Инструменты/Bash скрипты" ./схема.png
```

`write` создаёт заметку, если её нет, и заменяет текст существующей с проверкой ревизии
(`--base-rev` или текущая). Если заметку успели изменить с другой машины, команда
печатает в stderr дифф от вашей базовой ревизии к текущей и завершается с кодом 4.
Перед первой записью в решение оно регистрируется на сервере по `solution.toml`.
Имя машины попадает в историю ревизий: `ZAM_MACHINE`, иначе `COMPUTERNAME` (Windows),
`HOSTNAME` или `/etc/hostname` (Linux). `ZAM_MACHINE` задаёт команда установки `zam`. Так же
имя машины находит `zam mcp`, поэтому хуки и MCP одной машины относятся к одной сессии. MCP по
HTTP знает машину только из заголовка `X-Zam-Machine` (прежний фрагмент `.mcp.json` передавал
`"X-Zam-Machine": "${ZAM_MACHINE:-}"`).

Коды выхода команд: 0 — успех, 1 — конфигурация (нет адреса, битый `solution.toml`),
2 — сервер недоступен, 3 — нет токена или он отклонён (в том числе нет прав на запись),
4 — конфликт ревизий, 5 — не найдено, 6 — неверный ввод (аргументы, путь, не UTF-8).

**Журналы из CLI** (`zam log insight`, `zam task`, `zam question`, `zam idea`). Общая область —
Knowledge: флаг `--global` у лент, записей и Vault (у `zam log insight` — `--scope global`);
`--knowledge` — его синоним (с 0.0.13-m6.6; у `zam idea` раньше было только `--knowledge`). Ленты
`zam insight|task|question|idea list` печатают одну страницу — insight по 50 записей (умолчание
сервера), задачи, вопросы и идеи по 200; есть ещё — строка в stderr «показано N, есть ещё:
--limit 200 или --all», `--all` проходит ленту до конца. С 0.0.13-m6.6:

```
# решение с полями ADR (только --kind decision; --option — отвергнутый вариант, до 8)
zam log insight --kind decision --title "Кэш сборки: sccache" --context "сборка 20 минут" \
    --option ccache --option "без кэша" --chosen sccache --rationale "работает с MSVC" \
    --decided-by human --revisit-if "появится удалённый кэш" < решение.md
# проверенный вывод: доказательство без файла — три флага вместе (или --evidence-file F)
zam log insight --kind discovery --title "sccache ускоряет сборку вдвое" --certainty theorem \
    --evidence-checked "3 сборки" --evidence-method "чистая и повторная сборка" \
    --evidence-result "20 мин → 9 мин" < вывод.md
# задача: кто ведёт, оценка в минутах, ссылки, приоритет (сервер 0.0.12-m6.5 и новее)
zam task new --title "Кэш сборки" --next "замерить" --owner human --estimate 90 \
    --link https://example.invalid/pr/1 --priority high < план.md
zam insight list --global --all
```

Флаги решения у другого вида (у `zam insight supersede` без `--kind` — вид замещаемой записи) —
код 6 до записи. Без `--certainty` insight агента получает `hypothesis`, и `zam` пишет об этом
строку в stderr «certainty: hypothesis (умолчание агента; проверено — --certainty theorem и
доказательство)»; stdout — по-прежнему `<id>@<rev>`. Значение флага, начинающееся с «-»,
передаётся через «=»: `zam log term … --code=--dry-run`.

**Польза подсказок** (с 0.0.16-m7.3). `zam insight show` печатает «показы: N · открыто: M ·
полезно: K · бесполезно: L». «Открыто» — сколько сессий агента прочитали запись (`memory_read`,
`zam read`, `zam insight show` в сессии агента) после того, как она пришла им подсказкой в той же
сессии. Это нижняя граница: агенту может хватить самой строки подсказки, и тогда он «не открывал».
Открытия считаются с обновления сервера до 0.0.16-m7.3; сервер прежней версии — строка без
«открыто». «Шумные» записи (часто показываются, но их не открывают и не отмечают полезными) сервер
отбирает лентой `kind=insight&noisy=1` (`docs/api-compat.md`, «Открытие подсказок»).

## Vault: секреты и мастер-ключ

Vault хранит креды, токены и ссылки (§7.6 ТЗ). Значение шифруется (XChaCha20-Poly1305) ключом
данных пользователя, а тот — мастер-ключом сервера. В поиск, FTS, Qdrant, журнал сервера и
аудит значения не попадают; каждое раскрытие пишется в аудит (`vault.reveal`: токен, сессия,
машина, время).

**Мастер-ключ** — 32 байта в base64:
- `ZAM_MASTER_KEY` (важнее файла), иначе
- файл `[vault] master_key_file`, по умолчанию `<data_dir>/master.key`. Файл создаётся сам при
  первом запуске, пока в `system.db` нет ключей Vault: атомарно (через `master.key.tmp` и
  жёсткую ссылку, без перезаписи существующего). На Linux права файла — 0600. На Windows файл
  получает защищённый DACL: полный доступ только владельцу, SYSTEM и администраторам
  (наследование от каталога отключено). Права задаются при создании файла (Linux — `0600`,
  Windows — DACL в самом `CreateFileW`): файла с правами каталога не бывает ни мгновения. Ключ, положенный вручную, сохраняет свои права —
  ограничьте их сами (сервер проверяет их при старте, см. ниже).

**Резервируйте мастер-ключ отдельно от бэкапа каталога данных.** Бэкап без ключа секреты не
раскрывает, но и восстановить их без ключа нельзя.

**По умолчанию ключ лежит в самом каталоге данных** (`<data_dir>/master.key`), рядом с
обёрнутыми ключами пользователей (`system.db`) и шифротекстами (`users/*.db`). Поэтому бэкап
каталога данных целиком (`tar data/`, копия папки) **вместе с `master.key` раскрывает весь
Vault** тому, у кого он окажется. Чтобы этого не было:
- храните ключ вне каталога данных: переменная `ZAM_MASTER_KEY` (base64 32 байт; задаётся в
  окружении службы, не в `config.toml`) или путь `[vault] master_key_file` /
  `ZAM_VAULT__MASTER_KEY_FILE` на другом томе или в каталоге с ограниченным доступом;
- если ключ остаётся в `<data_dir>`, исключайте `master.key` из бэкапа каталога данных и
  храните его копию отдельно (менеджер паролей, отдельный носитель);
- при восстановлении из бэкапа верните ключу права только для владельца (Linux — `chmod 600`;
  Windows — доступ только учётной записи службы и администраторам): права восстановленного
  файла сервер сохраняет как есть.

**Проверка прав при старте.** Если файл мастер-ключа могут прочитать не только владелец, сервер
пишет в журнал предупреждение (WARN) и продолжает работать, Vault не блокируется:

```
WARN файл мастер-ключа Vault доступен не только владельцу: ограничьте права (Linux: chmod 600;
     Windows: только владелец, SYSTEM и администраторы) path=… access=…
```

`access` — что именно не так: на Linux `права 644` (любой бит группы или прочих, то есть шире
0600), на Windows `DACL разрешает чтение: S-1-5-32-545, …` — SID учётных записей и групп, кроме
учётной записи сервера, SYSTEM и администраторов, которым DACL даёт чтение (например,
`S-1-5-32-545` — «Пользователи», `S-1-1-0` — «Все», `S-1-5-11` — «Прошедшие проверку»).
Владелец файла (и `OWNER RIGHTS`) не считается чужим, только если это учётная запись сервера
или администраторы: ключ, восстановленный из бэкапа другим пользователем и оставшийся его
собственностью, даст WARN с SID этого пользователя — смените владельца
(`icacls "<data_dir>\master.key" /setowner <учётная запись службы>`) или пересоздайте файл
от имени службы.
Предупреждение повторяется при каждом старте, пока права не исправлены. Как исправить:

```bash
# Linux (владелец — пользователь службы)
chmod 600 <data_dir>/master.key
```

```powershell
# Windows: отключить наследование и оставить только владельца, SYSTEM и администраторов
icacls "<data_dir>\master.key" /inheritance:r /grant:r "*S-1-3-4:F" "*S-1-5-18:F" "*S-1-5-32-544:F"
```

Права, выставленные намеренно (например, 0640 для агента бэкапа), сервер сам не меняет — только
предупреждает. Если файл не удаётся проверить, в журнале — WARN «не удалось проверить права
файла мастер-ключа Vault».

Перенос ключа в `master_key_file` или `ZAM_MASTER_KEY` — то же значение, новый ключ не нужен:
скопируйте содержимое `master.key` (сервер остановлен), задайте путь или переменную, удалите
файл из каталога данных и запустите сервер. Значение должно совпасть с прежним, иначе Vault
заблокируется (см. ниже). Если ключ потерян, подменён или
`ZAM_MASTER_KEY` расходится с прежним, сервер работает, а Vault заблокирован: эндпоинты Vault
отвечают 503 `/problems/vault-locked`, причина — одной строкой WARN в журнале. Новый ключ при
этом молча не создаётся. Верните прежний файл или переменную и перезапустите сервер.

```
# значение — только из stdin или скрытого ввода с терминала, никогда из аргументов
printf '%s' "$GITHUB_TOKEN" | zam vault set github --type token --link https://github.com --global
zam vault set postgres --type connection_string --username app      # Vault текущего решения; ввод скрыт
zam vault list --global --q git                                      # без значений; поиск по открытым полям
zam vault set stage --type host --purpose 'приёмочный стенд' --address 192.0.2.5:22 --limits 'только ночью' --global  # окружение: значение необязательно (--secret-stdin)
zam vault get github --global --raw                                  # в stdout только значение
zam vault rename stage stage-old --global                            # новое имя — новая ревизия (If-Match)
zam vault mv postgres --to global                                    # из Vault решения в личный: --to global|solution|<GUID>
zam vault rm stage-old --global                                      # мягкое удаление
```

`add` — синоним `set`, `delete` — синоним `rm`.

`--global` — личный Vault (Knowledge, для всех проектов), без него — Vault решения из
`solution.toml` (`--solution GUID`). Vault решения лежит в вашей базе пользователя: владелец и
другие участники общего решения его не видят. Повторный `set` с тем же именем создаёт новую
ревизию; прежние значения раскрывает только администратор (`GET /vault/{id}/revisions?reveal=1&rev=N`).

Хост или стенд, общий для проектов (рабочая станция, сервер памяти), — в личный Vault
(`--global`); только этого проекта — в Vault решения (без флага). Умолчание — Vault решения, поэтому
`zam vault set --type host|environment` без `--global` и `--solution` при создании записи печатает
в stderr строку «записано в Vault решения «<имя решения>»; общий для проектов — --global
(перенести: zam vault mv "<имя>" --to global)»; новая ревизия существующей записи её не печатает.
Запись легла не туда — `zam vault mv <имя> --to global|solution|<GUID>`
(откуда — `--global` или `--solution`, как у других команд; `--to solution` — решение из
`solution.toml`): нужны права записи в обеих областях и разблокированный Vault; перенос — новая
ревизия с тем же именем, данными и значением (id и история сохраняются, значение через клиента
не проходит), перенос в ту же область ревизии не создаёт, аудит — `vault.move` с `from` и `to`.
Имя уже занято в цели — код 4, запись остаётся на месте. Сервер до `0.0.13-m6.6` переноса не знает
(нет флага `vault_move` в `GET /health`): код 1 «сервер не поддерживает перенос записей Vault:
нужен zam-server 0.0.13-m6.6 или новее».

`rename` передаёт `If-Match` прочитанной ревизии: имя занято в той же области или запись
изменилась между чтением и правкой — код 4. Удаление (`rm`) мягкое: имя освобождается, ревизии
и аудит `vault.delete` остаются (историю удалённой записи видит администратор). Агент через MCP
(`memory_vault action=delete|rename|move`, поля `new_name` и `to`) по протоколу `zam guide`
удаляет только свою ошибочную запись или по просьбе человека.

При заблокированном Vault список и метаданные отвечают: `GET /spaces/{space}/vault`,
`GET /vault/{id}` без `reveal` и `GET /vault/{id}/revisions` — 200 с полем `locked: true` и
`reason` (только открытые поля: имя, вид, привязка, даты), `zam vault list` печатает список и
в stderr строку «Vault заблокирован: <причина>», WebUI показывает список с баннером и неактивной
кнопкой «Показать». Значения (`reveal=1`), создание, правка, удаление и перенос — 503
`vault-locked`.

Если `ZAM_MASTER_KEY` задан, файл ключа не создаётся и не читается: резервируйте значение
переменной так же, как файл. Смена ключа (перешифровка) в M3 не поддерживается.

## Совместный доступ к решению

Решение (проект агента, `agent_solution_id` из `solution.toml`) хранится в базе пользователя,
который первым его зарегистрировал, — владельца (§11.6 ТЗ). Другой пользователь, чей агент
обращается к тому же GUID, получает запрос доступа `pending` и, пока владелец не ответит, —
403 `/problems/solution-access` (`state: pending`) на чтение и запись решения; поиск исключает
решение с предупреждением `solution access pending`; `GET /triggers?solution=` при недоступном
решении (`pending|rejected|revoked`, неизвестный GUID) отвечает 200 с триггерами Knowledge и
`warnings` вместо отказа.

```
zam solution access requests               # владелец: ожидающие запросы текущего решения
zam solution access approve Борис          # одобрить (rw); --ro — только чтение
zam solution access reject Борис --reason "не наш проект"
zam solution access revoke Борис           # отзыв — со следующего запроса того же токена
zam solution access list                   # все запросы и участники
zam solution rename "Новое имя"            # переименование решения (владелец или администратор)
```

То же — `POST /api/v1/solutions/{guid}/access/{user}/approve|reject|revoke` и страницы WebUI
«Администрирование → Решения» (администратору) и «Мои решения» (пользователю — свои решения). Участник видит в базе владельца только
пространство решения: Knowledge, Rules, Human и Vault владельца ему недоступны (404); его
правки ложатся в базу владельца ревизиями с его пользователем и токеном, а свой Vault для
решения он хранит в своей базе. Права проверяются на каждом запросе: после отзыва уже
следующий запрос того же агента получает 403 (`state: revoked`). `zam status` показывает роль
в текущем решении и число ожидающих запросов к вашим решениям.

## WebUI: вход пользователей

Вход в WebUI общий: администратор входит логином и паролем из конфигурации (`[admin]`),
пользователь — своим именем (без учёта регистра) и паролем, который задал администратор.

1. «Администрирование → Пользователи» → «Задать пароль» у пользователя (не короче 10 символов;
   то же — `POST /api/v1/admin/users/{id}/password {"password": "…"}`). Пароль хранится
   в `system.db` как argon2id.
2. Передайте пароль пользователю. При первом входе WebUI попросит сменить его; до смены другие
   разделы закрыты (403 `password-change-required`).
3. «Закрыть вход» (`DELETE /api/v1/admin/users/{id}/password`) стирает пароль и закрывает
   сессии пользователя; токены его агентов продолжают работать. Отключённый пользователь
   не входит (401), его открытые сессии перестают действовать.

Пользователь видит только свою память (Rules, свой Human, Knowledge, свои решения) и доступные
ему общие решения. Разделов «Пользователи», «Администрирование», «Настройки» и полного
«Индекса» у него нет (на сервере — 403); есть «Мои решения» (запросы доступа к своим
решениям), «Аккаунт» (смена пароля, выпуск и отзыв своих токенов `rw`/`ro` —
`GET/POST /api/v1/auth/tokens`, `DELETE /api/v1/auth/tokens/{id}`) и баннер перенарезки своей
базы. Пишет он как человек (`author_kind = human`): причина смены `certainty` ему необязательна.
Лимит попыток входа общий с администратором — 5 в минуту на IP. В аудит пишутся
`auth.login.user`, `auth.login.user_failed` (без введённого логина и пароля),
`user.password.set|clear|change`.

## WebUI: заметки

WebUI открывается по адресу сервера (`http://<хост>:7700/`) после входа администратора или
пользователя.

- Слева — дерево пользователей и их пространств (Knowledge, Rules, Human, решения).
  Создание заметок и папок, перенос и удаление в корзину — из контекстного меню; у
  пространства в нём же — «Экспорт (.zip)» и «Импорт (.zip)…» (см. «Перенос на другую машину»).
- Документ показывается с оглавлением, подсветкой кода, формулами, диаграммами Mermaid,
  картинками и видео.
- «Править» открывает редактор с предпросмотром, сохранение — Ctrl+S. Если заметку успели
  изменить с другой машины, показывается дифф и выбор: перезаписать поверх, скопировать
  свой текст и открыть текущую или вернуться к правке. В окне от 1024 px текст и предпросмотр —
  рядом, в окне уже (телефон, планшет) — вкладками «Текст | Предпросмотр».
- Вкладка «История» — ревизии, дифф и откат.
- Поиск — Ctrl+K или кнопка «Поиск» в шапке.
- Журналы (с 0.0.15-m7.2): «Изменить» — у записи Changelog, релиза, задачи и открытого вопроса;
  «Удалить» (в корзину) — у них и у insight и термина, у вопроса ещё «Неактуален» (с причиной);
  «Корзина» журнала — удалённые записи с «Восстановить». Корзину видит тот, кто может
  восстановить: у отчётов — владелец решения, у прочих — все с правом записи (участник `rw`
  общего решения тоже); участнику `ro` — отказ. Набранное в форме журнала (правка записи, замена,
  отзыв и надёжность insight, формы идей и терминов) молча не теряется: «← <журнал>» на телефоне,
  переход по ссылке или Ctrl+K, «назад» и другая форма карточки сначала спрашивают, закрыть ли
  форму без сохранения.
- Числа доски задач (с 0.0.16-m7.3). Число журнала «Задачи» в дереве и полосе журналов — все
  записи, а доска по умолчанию показывает задачи без шагов планов (подзадач `part_of`): шаги
  свёрнуты под общими задачами («Подзадачи ▸»). Разницу объясняет строка над доской — «37 задач ·
  72 шага планов внутри них — показать на доске» — и «+K шагов» у числа колонки (на узком экране —
  строка в панели вкладки статуса: «Ещё 4 шага планов этого статуса — внутри общих задач»; пустая —
  «Задач нет — 2 шага планов …» с «Показать на доске»); подсказка числа журнала — «109 записей:
  37 задач и 72 шага планов».
  «показать на доске» (или переключатель «Подзадачи на доске») ставит шаги в колонки по статусам —
  тогда числа колонок в сумме равны числу журнала; «свернуть» возвращает прежний вид. С фильтром
  «Из идей» строка говорит, сколько задач и шагов из идей на доске.
- Файл прикрепляется кнопкой «Прикрепить файл», вставкой из буфера или перетаскиванием
  в редактор; в текст вставляется ссылка `_attachments/…`.

## Документы (вложения)

Вложения DOCX, PPTX, XLSX, XLS, ODS, CSV/TSV, PDF и текстовые файлы (`.txt`, `.text`, `.md`,
`.markdown`, `.log`, `.json`, `.jsonl`, `.yaml`, `.yml`, `.toml`, `.ini`, `.cfg`, `.conf`, `.xml`,
`.html`, `.htm`, `.rst`, `.adoc` — UTF-8 без нулевых байтов) разбираются в текст со ссылкой на место — `locator`: `page:12` (страница PDF), `slide:3`, `sheet:Итоги!A1:F40`
(лист и диапазон), `para:40` (абзац DOCX). Фрагменты индексируются как уровень `attachment`:
находятся поиском (`zam search`, `POST /search`, MCP `memory_search`) вместе с заметками и
читаются по `locator` (`zam read`, `POST /read`, MCP `memory_read`); WebUI показывает их
просмотрщиками (вкладка «Вложения» заметки). Вид файла определяется по содержимому, а не по
расширению; остальные файлы (картинки, архивы, исходный код, DOC/PPT старых форматов) хранятся и скачиваются,
но не индексируются (`unsupported`). Вложения пространства Human — только в полнотекстовом
индексе, без векторов.

**Что в комплекте.** `pdfium.dll` (Windows) или `libpdfium.so` (Linux) рядом с `zam-server` —
сборка [pdfium-binaries](https://github.com/bblanchon/pdfium-binaries) `chromium/8100` без V8:
JavaScript и вложения PDF не исполняются и не извлекаются. Лицензии — `LICENSES/PDFIUM-LICENSE.txt`
(PDFium — BSD-3-Clause, сборка pdfium-binaries — MIT) и `LICENSES/PDFIUM-THIRD-PARTY.txt`
(компоненты внутри pdfium). Другое место библиотеки — `[docs] pdfium_dylib` (относительный путь —
от каталога `zam-server`). Без pdfium PDF не индексируются (`failed`, причина
`pdfium_unavailable`), остальные форматы работают; вернув библиотеку, перезапустите сервер — PDF
извлекутся заново. Внешних офисных пакетов (LibreOffice и т. п.) не нужно.

**Изоляция и лимиты.** Каждый файл разбирается в рабочем процессе `zam-server doc-worker` (тот же
исполняемый файл, запускается сервером) с лимитом памяти и сроком; падение или зависание разбора
не роняет сервер — вложение получает `failed` с причиной, процесс перезапускается. Умолчания
секции `[docs]` (`config.example.toml`):

| Ключ | Умолчание | Что ограничивает |
|---|---|---|
| `max_bytes` | 100 МиБ | размер файла: больше — отказ (`too_large`) |
| `max_unpacked`, `max_ratio`, `max_entries` | 500 МиБ, 100, 10 000 | zip-бомбы в DOCX/XLSX/PPTX/ODS |
| `max_cells`, `max_chars`, `max_pages` | 2 млн, 20 млн, 5000 | ячеек листа, символов текста, страниц PDF |
| `workers`, `preview_workers` | 2, 1 | одновременных разборов для индексации и для превью |
| `worker_memory_mb` | 2048 | память процесса (Windows — Job Object, Linux — `RLIMIT_AS`) → `parse_oom` |
| `timeout_ms` | 60 000 | срок разбора файла → `parse_timeout` |

Превышение лимитов объёма даёт частичный текст с предупреждением `truncated: <лимит>`. Причины
неудач: `parse_error: …` (испорченный файл), `parse_crash`, `parse_timeout`, `parse_oom`,
`pdfium_unavailable`, `too_large`, `blob_missing` (файла блоба нет на диске). Рабочий процесс
не может запускать дочерние процессы (Windows — Job Object с одним процессом; Linux —
`no_new_privs`, рабочий каталог `/`); полной песочницы ОС (seccomp/landlock, AppContainer) в
этой версии нет — она запланирована на M7. Вложения JavaScript и CSS скачиваются как
`application/octet-stream`: подключить их к странице с адреса сервера нельзя. Скан без текстового слоя индексируется пустым с признаком
`ocr_needed` (в WebUI — «нужно распознавание»): распознавания текста (OCR) в этой версии нет.

**Как проверить.**

```bash
zam write knowledge:test/docs <<< "# Документы"
zam attach knowledge:test/docs ./отчёт.pdf
# состояние извлечения: extract_state = pending → done | failed (с extract_error)
curl -s -H "Authorization: Bearer $ZAM_TOKEN" http://127.0.0.1:7700/api/v1/nodes/<id>/attachments
zam search "фраза со страницы отчёта"
#   a:<фрагмент> knowledge/test/docs › отчёт.pdf · стр. 3
zam read a:<фрагмент> --locator page:3
```

`<id>` — то, что `zam write` печатает до `@`. Неудачи видны в `failed_items`
`GET /api/v1/index/status` (вложение, путь заметки, причина); причина отказа pdfium — там же в
`docs.pdfium_error` (только администратору: в ней путь на сервере). Smoke-тест комплекта
(`cargo xtask smoke`) проверяет то же самое: pdfium из каталога комплекта грузится рабочим
процессом, PDF и DOCX находятся по фрагменту с `locator`, читаются по нему, лист XLSX и миниатюра
PDF показываются.

## Вложения: сборщик мусора (с 0.0.17-m7.4)

Файлы вложений и отчётов лежат в `<data_dir>/blobs/<пользователь>/<aa>/<sha256>`, одинаковое
содержимое — один раз. Раз в сутки (первый проход — через час после старта) воркер обслуживания
удаляет у каждого пользователя:

- блоб без ссылок (`refcount = 0`: вложение откреплено) — строку и файл, если файл не менялся
  `limits.blob_gc_days` суток (по умолчанию 7);
- файл без строки (отклонённая загрузка, откат отчёта, прерванный импорт) того же возраста;
- `.incoming/*.part` старше суток (оборванные загрузки);
- строку без ссылок и без файла (после `restore` копии, где такого файла нет).

Не трогаются файлы, на которые есть ссылки, — в том числе заметок и отчётов в корзине
(окончательного удаления из корзины нет), кэш извлечения текста и `previews/`. Возраст — время
изменения файла: открепление последней ссылки и повторная загрузка того же содержимого ставят его
на «сейчас», поэтому блоб, к которому обращались за `blob_gc_days` суток, не удаляется.

```toml
[limits]
blob_gc_days = 7   # 0..=365; 0 — сборщик выключен
```

Удаление двухфазное: файл сначала переносится в `blobs/<пользователь>/.gc/`, затем строка
удаляется из базы, и только после этого файл стирается. Если сервер упал между шагами, файлы в
`.gc/` разбирает следующий проход или `zam-server doctor --fix`: файл со строкой возвращается на
место, без строки — удаляется. Пока идёт копия (признак `.zam-backup` или копия из WebUI), проход
пропускается целиком; пользователь, чьи вложения в эту минуту загружаются или импортируются,
пропускается до следующего прохода. Итог — строка журнала
`blob gc: user=… rows=… files=… bytes=…` и аудит `blobs.gc {users, rows, files, bytes}`. Копия
(`zam-server backup`, «Копии» в WebUI) берёт только блобы со ссылками: мусор в неё не идёт. Что
сборщик удалит при следующем проходе, показывает `zam-server doctor` (строка `blobs:<user>`).

Откат на 0.0.16-m7.3: уберите `blob_gc_days` из `[limits]` — прежний сервер ключа не знает.

## Карта кода (`zam code`, с 0.0.9-m5.6)

Карту кода строит клиент `zam` на машине агента: разбирает рабочую копию (Rust, TypeScript/TSX,
JavaScript/JSX, Python, Go, Java, C#) и отправляет на сервер только метаданные символов — имена,
виды, строки, сигнатуры (первая строка определения, ≤ 160 символов; секреты сервер маскирует) и
ссылки по именам. Тела файлов на сервер не уходят. Карта хранится в базе владельца решения.

```
zam code sync                 # первая — все файлы, дальше — только изменившиеся
zam code status               # файлы по языкам, пропуски, центральные символы
zam code map --focus crates/zam-store/src/lib.rs --tokens 1000
zam code sym Store::open      # карточка: определение, кто ссылается, знания
zam code impact               # что затронут правки рабочей копии
```

- Синхронизация запускается из каталога решения (корень с `.zeroaimemory/solution.toml`); писать
  может владелец решения и участник `rw`, читать — любой с доступом. Хуки `session-start` и
  `checkpoint` сами запускают фоновую синхронизацию не чаще раза в 30 мин или при смене `HEAD`
  (итог — строкой в `.zeroaimemory/logs/hooks.log`).
- Настройки клиента — секция `[code]` в `~/.zeroaimemory/config.toml` или
  `.zeroaimemory/config.toml` проекта: `enabled`, `auto` (фоновая синхронизация), `auto_interval_min`
  (30), `languages`, `exclude` (маски, например `["gen/**"]`; дополняют исключение по умолчанию
  `**/tests/fixtures/**` — эталоны тестов с общими именами мешали ранжированию карты),
  `exclude_defaults` (`true`; `false` — эталоны тестов в карте), `exclude_gitattributes` (`true`;
  `false` — вендорный и созданный код в карте), `max_file_bytes` (1 МиБ), `max_files` (50 000),
  `parse_timeout_ms` (200), `send_signatures` (`false` — без сигнатур).
  С M6 файлы под `**/tests/fixtures/**` уходят из карты при первой синхронизации (если их больше
  половины карты — нужен `zam code sync --prune`), а клиент перезагружает карту целиком один раз
  (новая версия разбора: вызовы по получателю `x.f()` весят меньше прямых).
  С 0.0.18 в карту не входят файлы с атрибутами `linguist-vendored` или `linguist-generated` из
  `.gitattributes` корня проекта и подкаталогов (`vendor/** linguist-vendored`, `*.pb.go
  linguist-generated`; `-linguist-vendored` и `=false` возвращают файл); `zam code status`
  показывает «исключено по .gitattributes: N», а уход таких файлов из карты `--prune` не требует.
  Сервер 0.0.18 ранжирует карту точнее: ссылка из другого файла не засчитывается закрытому
  (без `pub`, `export`, `public`) определению с тем же именем. Ранги карт, посчитанные прежней
  версией, пересчитываются сами при первом запросе карты.
  Сервер — секция `[code]` в `config.toml` (см. `config.example.toml`); `enabled = false` —
  маршруты карты отвечают 404.
- Знание о функции привязывается ссылкой `путь#Тип::метод` (`zam log … --ref
  crates/a.rs#Store::open`, `refs:` заметки): оно устаревает только при изменении тела этого
  символа.
- Подсказки карты (строка в дайджесте, раздел «Код» пакета субагенту, фоновая синхронизация)
  выключаются типом `code_map` («Подключение агента» → «Подсказки хуков» или `[hooks] code_map =
  false`).
- Очистить карту решения может только владелец — кнопкой на странице «Код» в WebUI.

## Идеи (`zam idea`, с 0.0.10-m5.7; разбор агентом — с 0.0.12-m6.5)

Журнал «Идеи» — замыслы человека, которые ещё не начаты. В WebUI — журнал «Идеи» решения и
Knowledge. Что агент делает с новой идеей человека, задаёт режим `ideas.mode` («Подключение
агента» → «Подсказки хуков» → «Идеи: разбирать сам / предлагать мне»):

- **`review` — разбирать сам** (по умолчанию с 0.0.12-m6.5). Новая идея приходит
  «Непросмотрено»; агент узнаёт об очереди из дайджеста старта сессии (раздел `### Идеи на
  разбор`), когда закончит текущий шаг, получает пакет разбора (идея, прежние разборы и доводы
  человека, похожие записи решения — в том числе отклонённые идеи), сверяет идею с планом, ТЗ и
  сделанным и выносит исход с разбором для человека: «В плане» (задача `open` в «Задачах» со
  связью на идею, план шагов — в её теле), «На доработку» (что дописать), «Отклонена» (почему)
  или «Сделано» (ссылка на сделанное). Пункт плана из идеи агент берёт сам, когда закончит
  текущую работу и вы не дали другой; снять или отложить его можно в «Задачах».
- **`propose` — предлагать мне** (поведение 0.0.10-m5.7): агент предлагает идею к месту вопросом
  «начать / отложить / отказаться»; «начать» создаёт задачу.

```
zam idea new "Экспорт отчётов в PDF" --priority high --tag pdf   # идея человека
zam idea list [--status S]… [--origin human|agent] [--global] [--limit N | --all]   # --global — Knowledge
zam idea queue [--limit N]                                       # агент: пакет разбора (1–20, по умолчанию 5)
zam idea review w:<id> --plan|--return|--decline|--done --summary-file F \
    [--missing T] [--basis ID]… [--similar w:ID]… \
    [--task k:ID | --task-title T --task-body-file F --task-priority low|normal|high] [--key K]
                                    # агент: исход разбора (review), печатает «Разобрано w:<id>: …»
zam idea propose w:<id> [--text "почему сейчас"] [--space <guid>]   # агент: вопрос человеку
                                    # (задача идеи снята или удалена — вопрос «вернуть», --text обязателен)
zam idea accept w:<id> [--by human] [--channel chat|cli] [--space <guid>]   # начать → задача k:<id>
zam idea defer w:<id> [--until ГГГГ-ММ-ДД]                      # отложить (дата — UTC)
zam idea decline w:<id> [--reason R]
```

- **Разбор** (`zam idea review`, MCP `memory_update_entry action=review`): разбор
  (`--summary-file`) — от `[ideas] review_min_chars` (по умолчанию 200) до 8000 символов; у
  `--return` обязателен `--missing` (вопросы человеку, до 2000 символов); у `--done` в `--basis`
  нужна ссылка на сделанное (`c:`, `r:`, `commit:<sha>`, `k:` задачи `done`); `--task k:<id>` —
  идею уже покрывает незакрытая задача плана, новой задачи нет; `--key` — ключ повтора одного
  разбора (повтор после сбоя связи не заводит вторую задачу; тот же ключ после правки идеи —
  код 6, новому разбору — новый ключ). Разбирается только идея человека в статусе
  «Непросмотрено» в решении: идея «от агента», уже разобранная или решённая человеком — код 4
  (409), идея Knowledge — код 6. Сервер без разбора идей (до 0.0.12-m6.5) — код 1 «сервер не
  поддерживает разбор идей: нужен zam-server 0.0.12-m6.5 или новее».
- **Что видит человек** в WebUI: чипы статусов со счётчиками и «Группировать по статусу», в
  строке — решение («В план → k:<id> «…»», «Не хватает: …», «Отклонена: …»); в карточке — раздел
  «Разбор агента» (исход, чей агент разбирал — «ваш агент» или «агент <имя>» участника общего
  решения, разбор, на что опирался, похожие, задача) и свёрнутая «История разборов». У
  возвращённой — «Агент просит дописать:» и «Изменить»: после сохранения идея снова
  «Непросмотрено» («Отправлено на разбор»), агент разберёт её заново; можно и решить самому —
  «Начать», «Отложить», «Отказаться». У отклонённой — «Удалить» (в корзину), оставить как есть
  (агент не примет повтор без новых доводов) или «Вернуть на разбор» с доводом. В «Задачах» у
  задачи из идеи — пометка «из идеи», фильтр «Из идей».
- Решение человека («Начать», «Отложить», «Отказаться» в WebUI или его слова в чате — `--by human
  --channel chat`) агент не пересматривает. Ваши слова из чата агент дописывает к возвращённой
  идее с `by: human` — MCP `memory_update_entry action=append` с `by: human`, CLI `zam insight
  append w:<id> --by human` (REST — `PATCH` с `by: human`): она тоже снова уходит на разбор;
  дописка самого агента статус не меняет.

- Под агентом (`CLAUDECODE`, переменные Codex, `ZAM_AGENT=1`) `--origin` у `new` и `--by` у
  решений обязательны (код 6): идея со слов человека — `--origin human`, своя — `--origin agent`
  (такую не предлагают, пока человек не примет её как свою в WebUI); решение человека из чата —
  `--by human --channel chat`. Коды: 403 — 3, повторный `accept` — 4 (с задачей), 422 — 6.
- Задачу из идеи сняли (`dropped`) или удалили — идея остаётся «начатой»; агент видит её с
  пометкой «задача снята, можно предложить вернуть» и может спросить человека «Вернуть идею?»
  (`zam idea propose w:<id> --text "почему пора"`, печатает `Предложено вернуть w:<id> → вопрос
  q:<id>`). Ответ «вернуть» возвращает идею в новые (следующий «начать» — новая задача),
  «отказаться» — снимает её; решает только человек (WebUI «Вопросы» или его слова в чате).
- Выключить и разбор, и предложения (раздел дайджеста, подсказки, строку плана): пользователю —
  флажок «Подключение агента» → «Подсказки хуков» → «Идеи: раздел дайджеста и подсказки (разбор
  и предложения)» (`ideas.proactive`); всем — `[ideas] proactive = false` сервера. Переключатель
  «Идеи: разбирать сам / предлагать мне» ниже флажка разбор не выключает, а только выбирает режим
  (`ideas.mode`). Режим по
  умолчанию для всех — `[ideas] default_mode` (`review` или `propose`); в общем решении действует
  режим его владельца.

## Внутренние работы и ночная проверка (с 0.0.16-m7.3)

Внутренняя работа — работа памяти над своими записями, где нужен текст модели: пробные вопросы
ночной проверки (вид `probes`) и кандидаты в Rules (`rules`). Итог работ — только пробы и
предложения человеку: знания модель и агент не меняют, заметку Rules создаёт человек, приняв
кандидата в WebUI. Модели в комплекте сервера нет, и без неё работает всё.

**Режим исполнителя** — у каждого пользователя (WebUI «Внутренние работы»; `PATCH
/api/v1/auth/settings` `{"works": {"mode": "…", "kinds": {…}}}` — сессия WebUI, по токену — 403):
- `off` — работы нет; так у всех, пока режим не выбран (`[works] default_mode = "off"`);
- `agent` — работу делает агент в своей сессии: на первом старте сессии строка дайджеста
  «Внутренние работы ждут: …», агент берёт пакет `memory_recall event=work` (`zam work next`) и
  сдаёт итог `memory_log kind=work` (`zam work put`) — правила в протоколе `zam guide`,
  «Внутренние работы»; захват работы — только токеном `rw`;
- `model` — работу делает подключённая модель (раздел «Подключённая модель» ниже): ночью в окне
  и по «Запустить сейчас» (ручной запуск — сразу, с теми же пределами; свой предел — 4 пакета вида
  за сутки UTC).

Режим можно задать и по видам (`kinds: {probes: …, rules: …}`). `[works] enabled = false`
выключает всё сразу: ни работ, ни ночной проверки, ни обращений к модели, ручные запуски — 409.
`[works] model_access` — куда можно слать данные (`any`, `lan`, `off`); пояснения ключей —
`config.example.toml`, секция `[works]`.

**Время ночи.** `[works] at` (`HH:MM`) в поясе `tz` (имя IANA — `Europe/Moscow`, `UTC` или
`±HH:MM`; база поясов встроена в сервер, пакет `tzdata` не нужен), окно — `window_min` минут
(10..720, по умолчанию 120); окно через полночь не обрывается, переход на летнее время
учитывается. Вне окна ночные работы не выполняются, пропущенная ночь (сервер был выключен) днём не
догоняется; ручной запуск окном не ограничен. Ночь — сначала проверка всех пользователей, затем
работы; идущую копию проверка ждёт, при переиндексации прогон пропускается. `[backup] tz` — пояс
времени автокопии (по умолчанию `UTC`, поведение прежнее). WebUI показывает время ночи в поясе
сервера и рядом — в поясе браузера («04:30 Europe/Moscow (у вас 04:30)»).

**Ночная проверка памяти** (`[works] check = "nightly"` — по умолчанию включена; у пользователя —
свой выключатель на странице «Внутренние работы», `works.check`). Сервер прогоняет пробы каждой
базы — вопросы из действующих выжимок кэша, 30 посторонних вопросов и пробы исполнителя — тем же
поиском и подсказками, что у агента, изнутри процесса и без следов: учёт показов, сессии и кэш
выжимок не меняются. Модели проверка не требует; предел прогона — `check_max_min` (30 мин).
Итог сравнивается с медианой пяти последних ночных прогонов того же отпечатка (модель,
устройство, реранкер, режим Qdrant); первые пять ночей — накопление базы. При регрессии (поиск
или подсказки находят на 8 п. п. меньше, посторонних подсказок на 10 п. п. больше, p95 — в 1,5 раза
и на 500 мс медленнее, потеряны устойчивые пробы, поиск ушёл в режим без векторов) агент на первом
старте сессии видит строку «Ночная проверка памяти: ухудшение … — zam check report» и сообщает
человеку. Ожидаемое ухудшение (сменили модель, правили `[search]`) снимает только человек:
«Принять как норму» на странице «Проверка памяти» (аудит `check.accept`) — база начинается
заново. Вручную — «Проверить сейчас» или `zam check run` (`check = "off"` выключает только ночной
прогон); отчёт — `zam check report` (метрики к медиане, проваленные пробы с советами). Прогоны
хранятся 365 суток.

**Ручные пробы** (с 0.0.17-m7.4). Вопрос, который память должна находить, можно добавить в
набор и вручную: `zam check probes add "<вопрос>" --target n:<id> [--target i:<id> …] [--space
knowledge]` (агентом или из консоли — любой токен `rw`; `ro` — 403) или страница «Проверка
памяти». Цель — живая заметка или запись журнала того же пространства; повтор вопроса (без учёта
регистра и пробелов) и предел 500 активных проб — отказ 409. Список — `zam check probes list
[--kind manual] [--status active]`. **Снимает пробу только человек** — на странице «Проверка
памяти» с причиной (аудит `check.probe.retire`): агентский токен получает 403, ошибочную пробу
агент описывает человеку, а не снимает — так регрессию не спрятать. С сервером 0.0.16-m7.3
`add` и `retire` — код 1 с подсказкой обновить `zam-server`.

**Кандидаты в Rules.** Агент предлагает правило (`memory_write {path: "rules:/…", content,
candidate: {reason}}`, `zam rules candidate`), модель — ночной работой `rules`. На странице
«Предложения», вкладка «Правила» (до 0.0.18-m7.5 — страница «Кандидаты в Rules»; в шапке —
«Предложения N», с уборкой вместе) человек принимает кандидата — путь и текст можно поправить,
заметка Rules пишется от его имени, происхождение — в сообщении ревизии, — или отклоняет его
(этот источник больше не предлагается). Открытых кандидатов — до 50 на пользователя.

**Уборка памяти** (с 0.0.18-m7.5). Ночью сервер находит в ваших решениях и Knowledge почти-дубли,
неразрешённые противоречия, устаревшие и шумные записи и записи, которых не находят пробы, —
до 20 за ночь; агент или подключённая модель (вид «Уборка памяти» на странице «Внутренние
работы») предлагает для каждой одну операцию: объединить, отозвать, отправить на пересмотр,
заменить триггеры, завести термин или псевдонимы, дописать — или оставить. Само ничего не
меняется: на странице «Предложения», вкладка «Уборка», видно, что и почему предложено (сигналы,
тексты записей, у объединения — различия), и «Применить» выполняет операцию от вашего имени на
текущей ревизии записи (текст объединения и дописки можно поправить), «Отклонить» — кандидат по
этим записям больше не предлагается. Удаления нет: история записей остаётся. Запись изменилась
после предложения — «Применить» недоступно, кандидат вернётся следующей ночью.

**Что уходит модели.** Только пакет работы: инструкция вида и тексты записей решений, Knowledge и
Rules владельца базы — в виде агента, секреты под маской `‹secret›`. Никогда не уходят: Human,
значения и имена Vault, вложения, снимки сессий, журнал событий, аудит, токены, записи других баз
и записи, которые хоть раз правил участник общего решения (участник о настройке владельца не
знает). Перед отправкой сервер ещё раз проверяет тело сканером секретов: элемент с находкой
выбрасывается. Журнал отправок (`GET /api/v1/works/calls`, страница «Внутренние работы») — без
текста.

**Команды.** `zam work status | next | put | release`, `zam check status | report | run | probes`,
`zam rules candidate | candidates`; с сервером старше 0.0.16-m7.3 (у `zam check probes add` и
`retire` — старше 0.0.17-m7.4) — код 1 с подсказкой обновить его.

**Пример: рабочий сервер памяти** (так развёрнут сервер владельца; адрес и ключ модели — только в
Vault). В конфигурации сервера:

```toml
[works]
tz = "Europe/Moscow"   # ночь — 04:30 по Москве (at = "04:30" — умолчание)
```

Остальное — умолчания (`allow_loopback = false`: модель — на другой машине локальной сети).
Владелец в WebUI «Внутренние работы» подключает локальную модель владельца в LAN через запись
личного Vault (`data.url` — базовый адрес сервера модели с `/v1`) с рецептом «Qwen без
размышлений» — `body_extra` `{"chat_template_kwargs": {"enable_thinking": false}}`; «Сохранить и
проверить» — `ok` без `thinking`; режим — «модель». Тестовый стенд — без `[works]`: работ и
обращений к модели нет, ночная проверка идёт на посторонних вопросах и кэше.

## Подключённая модель (внутренние работы, с 0.0.16-m7.3)

Внутренние работы памяти (пробы ночной проверки, кандидаты в Rules) делает агент в своей сессии
или модель, которую подключил пользователь (`works.mode = "model"`). Модели в комплекте сервера
нет. Протокол один — **OpenAI-совместимый Chat Completions** (`POST <адрес>/chat/completions`,
без потока и инструментов); родной протокол Anthropic — в 0.0.19-m7.6.

**Подключение.**
1. Запись **личного Vault** (WebUI «Vault» или `POST /api/v1/spaces/knowledge/vault`): `data.url`
   — базовый адрес поставщика с `/v1`, как он дан в его документации (без `user@`, `?…`, `#…`;
   запасное поле — `data.address`), значение — ключ API. Локальному серверу без ключа — любое
   значение и `auth: "none"` в подключении.
2. `PATCH /api/v1/auth/settings` (сессия WebUI; по токену — 403):
   `{"works": {"model": {"protocol": "openai", "vault": "<имя записи или v:<id>>", "model":
   "<имя модели>", "max_tokens": 4000, "token_field": "auto", "body_extra": {…}}, "mode":
   "model"}}`. `max_tokens` — 256..=32000; `token_field` — `auto` (у `api.openai.com` —
   `max_completion_tokens`, иначе `max_tokens`), `max_tokens` или `max_completion_tokens`;
   `body_extra` — JSON до 4 КиБ, сливается в тело запроса (ключи `model`, `messages`, `stream`,
   `max_tokens`, `max_completion_tokens` — 422). `temperature` и прочие параметры выборки сервер не
   шлёт.
3. Сервер проверяет адрес записи и **закрепляет** его (схема, хост, порт, путь). Если `data.url`
   записи потом изменится (например, токеном агента), обращения встают на паузу `vault_changed`
   («был → стал» — полные адреса: схема, хост, порт, путь; при новой смене «стал» обновляется).
   Подтверждает только человек и только явно: сохранение подключения с полем
   `"confirm_url": "<адрес, который он видит в «стал»>"` — сверяется весь адрес (схема, хост,
   порт, путь); без него или с устаревшим (адрес успели поменять ещё раз) — 409 `{code:
   "vault_changed", was, now}`, пауза остаётся. Смена одного ключа паузы не даёт.
4. Проверка: `POST /api/v1/works/model/test` → `{ok, ms, class?, hint?, thinking?}` —
   фиксированный запрос без данных памяти; `thinking` и `hint` подсказывают выключить
   размышления модели (рецепты — в таблице ниже). Без обращения: `[works] enabled = false` или
   `model_access = "off"` — 409 `/problems/works-disabled` (причина — в `detail`), пауза
   `vault_changed` — 409 `{code: "vault_changed", was, now}`, уже идёт обращение — 409
   `model_busy`, подключения нет — 422.

**Куда можно.** Проверяются **все** адреса имени, соединение идёт только по проверенным
(подмена DNS после проверки запрос не уводит — кроме обращения через прокси, см. ниже),
редиректы не выполняются (3xx — `bad_response`):
- вне LAN — только `https://`; сохранение отвечает `warnings: ["works_model_external: <хост>"]`
  (аудит `works.model.external`), строки журнала отправок — с `external: true`;
- LAN (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`) — можно и `http://`;
- петля (`127.0.0.1`, `localhost`, `0.0.0.0`, `::1`), собственные адреса машины сервера (в том
  числе её адрес LAN) и link-local (`169.254/16`, `fe80::/10`) — только при `[works]
  allow_loopback = true` (администратор): так подключается модель на той же машине, что сервер;
- IPv6 со вложенным IPv4 (`::a.b.c.d`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`): петля, свой адрес
  и link-local внутри — как IPv4, прочее (и частный IPv4) — вне LAN: такой адрес уходит наружу;
- `[works] model_access = "lan"` — вне LAN нельзя, `"off"` — режима `model` нет.

**Прокси.** Как у загрузки зависимостей: `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` и `NO_PROXY`
из окружения службы — только для адресов вне LAN; к LAN и петле — напрямую. Через прокси имя
поставщика разрешает **сам прокси**: привязки соединения к проверенным адресам там нет (вне LAN
разрешён только `https` — подменённый адрес без сертификата на имя поставщика данных и ключа не
получит). **SOCKS-прокси не поддерживается** (клиент собран без `socks-proxy`) — нужен HTTP
CONNECT-прокси.

**Пределы и паузы.** Потолки сервера `[works] max_daily_tokens`, `max_monthly_tokens` (сутки и
месяц UTC; 0 — обращений нет), пределы пользователя `works.limits` — не выше потолков. Перед
вызовом — оценка «вход + `max_tokens`»: не помещается в остаток — `limit`, стоп до следующей
ночи. Одновременно — `max_parallel` обращений на сервер, у пользователя — одно; срок —
`call_timeout_s`. Перед **каждым** обращением (и перед повтором) сервер сверяет режим и паузу:
выключили режим, пока шло ожидание повтора, — обращений больше нет. Классы: `auth`,
`not_found`, `blocked`, `vault` (в том числе ключ с переводом строки), `vault_changed` — пауза;
`quota`, `limit`, `rate` (кроме одного повтора при `retry-after` ≤ 60 с) и три `unavailable` за
ночь (повторы через 10 и 60 с) — стоп до следующей ночи, его помнит журнал отправок (строки
своей ночи или своего ручного запуска), перезапуск сервера его не снимает; `bad_request`,
`thinking`, `max_tokens`, `refused`, `bad_response`, `bad_json` — работа не удалась. Паузу
снимает сохранение подключения или успешная проверка (у `vault_changed` — только сохранение с
`confirm_url`). Остановка сервера висящий вызов модели не ждёт: он брошен (строка `aborted`).

**Журнал отправок** — `GET /api/v1/works/calls?days=` (1..=180, по умолчанию 7; администратор —
`&user=<id>`; по токену — 403): время, работа, вид (`test` — проверка подключения), хост,
модель, токены (`estimated` — оценка, когда поставщик не вернул `usage`), мс (`null`, в WebUI —
«—»: ответа не было), исход (`ok`, класс, `aborted` — оборвано остановкой, `internal` — сбой
сервера без отправки), код HTTP, `external`, число элементов, запуск (`run`: `night:<дата>` или
`manual:<id>`) — **без текста** пакета и ответа; хранится 180 суток. Аудит (от имени того, кто действовал: человека или
`system`; не записался — WARN, а обращение с ключом без строки `key_use` не уходит):
`works.model.key_use {vault, host}` (раз за ночь, ручной запуск и проверку), `works.model.paused
{class}`, `works.model.vault_changed {from, to}`, `works.model.pause_cleared {class, by}`,
`works.model.external {host}` (сохранено подключение вне LAN).

**Данные наружу.** Модели уходит только пакет работы — маскированный вид агента без Human,
Vault, вложений и записей участников общего решения; перед отправкой тело ещё раз проверяет
сканер секретов: элемент с находкой выбрасывается, остальное уходит.

## Qdrant

Векторный индекс — нативный Qdrant из комплекта (`qdrant/<версия>/`), без Docker. Его запускает
и контролирует сам `zam-server` (`[qdrant] mode = "managed"`):

- рабочий каталог — `<data_dir>/qdrant/` (конфиг `config/zam.yaml` генерируется при каждом
  старте, хранилище `storage/`, pid-файл `qdrant.pid`, метка `zam-storage.json`);
- Qdrant слушает только `127.0.0.1` на портах `http_port`/`grpc_port`; API-ключ новый при
  каждом старте и передаётся только через окружение процесса;
- Qdrant завершается вместе с сервером, даже если сервер убит (Windows — Job Object,
  Linux — `PR_SET_PDEATHSIG`); оставшийся после сбоя процесс завершается при следующем старте;
- при падении Qdrant перезапускается (задержка 1→60 с); после 5 падений за 10 минут
  перезапуски прекращаются, поиск работает по полнотексту с пометкой `degraded`;
- индекс производный: при откате версии Qdrant, скачке больше чем на одну минорную версию
  или ошибке миграции хранилище стирается и индекс пересобирается из базы без инференса.

Команды (с теми же `--config`/`--data-dir`, что и `serve`):

```
zam-server qdrant status --config config.toml     # режим, версия, порты, pid, хранилище (--json — для скриптов)
zam-server qdrant fetch                           # скачать бинарник (SHA-256), если его нет
zam-server qdrant reset --yes --config config.toml   # стереть хранилище (сервер остановлен)
```

Внешний Qdrant: `mode = "external"`, `url` — его gRPC-адрес (например `http://10.0.0.5:6334`),
ключ — `api_key` или переменная `ZAM_QDRANT__API_KEY`.

## Модели

Векторный поиск работает на встроенных ONNX-моделях (§8.4 ТЗ). Без моделей сервер стартует
в режиме полнотекстового поиска (FTS-only): `degraded: true` в ответах поиска, причина и
подсказка — в журнале.

Размеры и бюджеты ответов агенту (`budget_tokens`, `~N tok`) считаются в токенах bge-m3. Счётчик
берётся по порядку: токенизатор установленной модели; без модели — `tokenizer.json` из
`tokenizers/` комплекта; без него — оценка с запасом (бюджет соблюдается, ответ на ~15 %
короче). Активный счётчик — поле `token_counter` в `GET /api/v1/health` (`model`, `bundled`,
`estimate`). Нарезку заметок без модели токенизатор комплекта не меняет: она считается оценкой и
перенарезается после установки модели.

| Модель | Назначение | Устройство | Лицензия | Размер |
|---|---|---|---|---|
| `bge-m3-int8` | эмбеддинги | CPU | MIT | 586 МБ |
| `bge-m3-fp16` | эмбеддинги | GPU (CUDA) | MIT | 1,15 ГБ |
| `bge-reranker-v2-m3` | реранкер (`rerank=on`) | GPU (CUDA) | Apache-2.0 | 1,15 ГБ |
| `jina-reranker-v2` | реранкер (`rerank=on`) | CPU | CC-BY-NC-4.0, по согласию | 297 МБ |

Модели скачиваются с Hugging Face по ревизиям и SHA-256, закреплённым в `deploy/models.toml`
(манифест встроен в `zam-server`); при несовпадении размера или хэша загрузка падает, а
частичные файлы удаляются. Каталог — `ml.models_dir`, по умолчанию `<data_dir>/models`:

```
zam-server models fetch --config config.toml               # модель эмбеддингов устройства
zam-server models fetch --config config.toml --reranker    # и реранкер устройства
zam-server models fetch --device gpu --reranker            # явно: набор для GPU
zam-server models status --config config.toml [--verify]   # что установлено (--verify — SHA-256)
```

Устройство по умолчанию — `gpu`, если рядом с ONNX Runtime лежит CUDA EP (GPU-комплект) и
`ml.device` не `cpu`, иначе `cpu`. GPU-комплект без доступной CUDA работает на CPU с
`bge-m3-int8`, поэтому на такой машине поставьте и CPU-набор (`--device cpu`). Модель для GPU
(`bge-m3-fp16`) на CPU не запускается: если CUDA не поднялась, а `bge-m3-int8` не установлена
(или `ml.embed_model = "bge-m3-fp16"` при `ml.device = "cpu"`), сервер работает в режиме
FTS-only с причиной `gpu_model_on_cpu` и подсказкой `zam-server models fetch --device cpu` —
векторы CPU не смешиваются в одной коллекции с векторами CUDA. В каталоге
каждой модели лежат `LICENSE` (лицензия и ссылки) и `model.toml`. Повторный запуск не
перекачивает файлы с верным хэшем. После загрузки перезапустите сервер; смена модели
выключает векторный поиск до reindex (векторы разных моделей не смешиваются).

Заметки режутся на чанки по токенам модели (`[index] chunk_*`). Без установленных моделей
токены считаются оценкой (символы / 3,5); такие базы отмечаются, и при первом запуске после
`models fetch` их заметки перенарезаются токенизатором модели в фоне (с повторной индексацией;
поиск всё это время работает). Если `tokenizer.json` модели на месте, а ONNX Runtime нет,
чанки сразу режутся точно. `chunk_hard_max` не превышает окна модели минус 64 токена на
префикс контекста (bge-m3: 1024 → 960); пороги больше — уменьшаются с WARN в журнале.

Для машин без интернета модели с `bundle = true` выложены архивами `zam-models-<версия>-<id>.zip`,
по одному на модель (вместе они больше предела 2 ГиБ на файл релиза): `bge-m3-int8` — для
CPU, `bge-m3-fp16` и `bge-reranker-v2-m3` — для GPU. Распакуйте нужные в каталог моделей
(`<data_dir>/models`): появятся `<id>/` с файлами модели, `LICENSE` и `model.toml`, а рядом
`models.toml` — копия манифеста с SHA-256 каждого файла (во всех архивах он одинаковый,
замену можно подтвердить). Проверка — `zam-server models status --verify`. Реранкер
`jina-reranker-v2` (CC-BY-NC-4.0) в архивы не входит.

## Состояние индекса и reindex

`GET /api/v1/index/status` (любой токен; токен видит только своего пользователя,
администратор — пользователя из `X-Zam-User` или сумму по всем) показывает: включён ли
векторный поиск и почему нет (`vector.reason`, текст по-русски `vector.text` и `vector.hint` с командой, например
`zam-server models fetch`), модель и устройство (`cpu`/`cuda` с причиной), Qdrant
(состояние, версия, резидентная память процесса `rss_bytes`, число точек, перезапуски),
очередь индексации, до 20 неудавшихся заданий, последний reindex и базы, исключённые из
пересборки (`rebuild_skipped`).

То же в WebUI — раздел «Индекс» (`http://<хост>:7700/#/admin/index`): страница обновляется
раз в 5 секунд, причину выключения векторного поиска пишет по-русски вместе с командой
(например, «скачайте модели: `zam-server models fetch`»), показывает повреждённые базы
(`unavailable_dbs`) и исключённые из пересборки, а кнопки «Переиндексировать из embeddings»
и «Полная переиндексация» запускают reindex (с подтверждением). Поиск Ctrl+K при выключенном
векторном канале пишет над результатами, что показаны результаты полнотекстового поиска.

Векторы хранятся в SQLite (кэш `embeddings`), поэтому индекс Qdrant пересобирается без
модели. Reindex нужен после смены модели или устройства (коллекция другой модели выключает
векторный поиск: `vector.reason = "model_mismatch"`), после потери или ручной очистки
хранилища Qdrant, после восстановления базы пользователя из копии.

На работающем сервере — администратор, ответ 202 и `job_count` (заметок области):

```
POST /api/v1/admin/reindex  {}                                   # все базы, из кэша
POST /api/v1/admin/reindex  {"user": "<id>", "space": "rules"}   # одно пространство
POST /api/v1/admin/reindex  {"full": true}                       # перечанковка и задания
```

На остановленном сервере — та же операция из командной строки (каталог данных открывается
под локом: если сервер запущен, команда откажет и подскажет API):

```
zam-server reindex --config config.toml                      # все базы, из кэша
zam-server reindex --config config.toml --user <id> --space knowledge
zam-server reindex --config config.toml --full               # перечанковать, задания — серверу
```

Без `--full`/`full` точки области удаляются и пишутся заново из кэша эмбеддингов, пачками
по 256 (цель — не меньше 2000 чанков/с); заметки, для которых в кэше нет эмбеддинга
(например, после смены модели), получают задания и векторизуются воркером сервера. С
`--full` все заметки области перечанковываются и ставятся в очередь (модель прогоняется
только для текстов, которых нет в кэше). Коллекция другой модели пересоздаётся для текущей,
и тогда пересобираются все базы. Прерванный reindex (остановка, сбой) повторяется
автоматически при следующем запуске. После пересборки всей базы пользователя из кэша
удаляются эмбеддинги, на которые больше не ссылается ни один чанк; сервер делает это и сам,
в простое, раз в час. Итог пишется в аудит (`index.reindex`, `index.reindex_done`) и в
`reindex.last` статуса.

На Windows удаление коллекции другой модели иногда не проходит с первого раза: Qdrant не может
переименовать каталог коллекции, пока её файлы держит другой процесс (антивирус, индексатор
поиска). Reindex повторяет удаление до 5 раз с паузой от 0,5 до 2 с. Если и это не помогло,
reindex завершается ошибкой «коллекция zam_chunks удалена частично …», и новая коллекция поверх
остатков не создаётся. Управляемый Qdrant: остановите сервер, выполните
`zam-server qdrant reset --yes` и запустите сервер снова — индекс пересоберётся из кэша
эмбеддингов. Внешний Qdrant (`qdrant.mode = "external"`): удалите коллекцию `zam_chunks` на своём
Qdrant (`DELETE /collections/zam_chunks`) или переключитесь на управляемый Qdrant, затем
повторите reindex.

С 0.0.18 коллекцию, удалённую наполовину (в списке Qdrant её нет, а каталог
`storage/collections/zam_chunks` остался), сервер восстанавливает сам при первой же проверке
коллекции: один раз удаляет остаток (с теми же повторами на Windows), создаёт коллекцию заново и
ставит во всех базах reindex из кэша эмбеддингов (без модели; прерванный повторится при
следующем запуске). В журнале — WARN «коллекция удалена частично — остаток убран, индекс
пересоберётся». Так и с внешним Qdrant: коллекция `zam_chunks` принадлежит серверу памяти, не
держите под этим именем ничего своего. Если удалить остаток не вышло, остаётся прежняя ошибка
«… удалена частично» с советом выше, а сервер повторяет проверку сам.

Если база пользователя повреждена (файл не SQLite, схема новее программы) или не
открывается пять раз подряд при пересборке после стирания хранилища Qdrant, она
исключается из пересборки (WARN в журнале, аудит `index.rebuild_skipped`, поле
`rebuild_skipped` статуса), а остальные базы пересобираются и флаг пересборки снимается.
Исключение хранится в `system.db` и переживает перезапуск. Когда база снова откроется
(восстановлена из копии `users/<id>.db.bak-v*` или бэкапа), сервер сам поставит ей reindex
из кэша и снимет исключение. Восстанавливайте при остановленном сервере и удалите рядом
`users/<id>.db-wal` и `users/<id>.db-shm` прежнего файла, иначе SQLite применит их к копии и
испортит её; копия `bak-v*` — снимок на момент обновления, всё записанное в базу после него
теряется (см. «Обновление» → «Как подложить копию»). Статус администратора, reindex всех баз и
`zam-server reindex` без `--user` повреждённую базу пропускают и называют
(`unavailable_dbs`, строка отчёта CLI); базу, указанную явно, — нет: это ошибка.

## GPU (CUDA)

GPU-комплект содержит ONNX Runtime с CUDA EP, но не библиотеки NVIDIA (CUDA 13, cuDNN 9).
Их ставит команда (около 1,9 ГБ архивов на Windows и 2,2 ГБ на Linux):

```
zam-server cuda fetch --config config.toml
```

Архивы redist NVIDIA скачиваются с `developer.download.nvidia.com` по `deploy/cuda.toml`
(размер и SHA-256 сверяются), нужные библиотеки кладутся в `<каталог ONNX Runtime>/cuda/`
(по умолчанию — `cuda/` рядом с `zam-server`), рядом с ними — штампы `.<компонент>.sha256`.
Повторный запуск пропускает архив, только если штамп совпал с манифестом; после обновления
`zam-server` с новым `cuda.toml` старые библиотеки заменяются.

Запускайте `cuda fetch` при остановленном сервере. На Windows работающий `zam-server` держит
загруженные библиотеки CUDA, и заменить их нельзя: команда проверяет это до загрузки и
завершается с ошибкой «файл … занят или недоступен для замены … Остановите zam-server»,
ничего не меняя (штампы и прежние библиотеки остаются). Если все штампы совпадают, команда
ничего не заменяет и при работающем сервере тоже проходит. Так же ведёт себя `zam-server qdrant
fetch` при запущенном Qdrant (на Linux — ошибка «Text file busy», на Windows — файл занят).

Первый старт с CUDA может занять больше 10 с: сервер отвечает на `/api/v1/health` только после
загрузки модели, а с CUDA — ещё и библиотек NVIDIA (~1,4 ГБ). Обычный старт — 4–5 с.

Без интернета — архив `zam-cuda-<версия>-<os>-x64` той же версии, что и `zam-server`:
распакуйте его в каталог `zam-server` (в архиве один каталог `cuda/`, он ляжет рядом с ONNX
Runtime):

```
# Windows: содержимое zip (каталог cuda) — в каталог с zam-server.exe
# Linux:
sudo tar -xzf zam-cuda-<версия>-linux-x64.tar.gz -C /opt/zeroaimemory
```

В `cuda/` лежат библиотеки, штампы `.<компонент>.sha256`, `cuda.toml` и `LICENSES/` (CUDA
Toolkit EULA, лицензия cuDNN). По штампам `zam-server cuda fetch` видит библиотеки
установленными и ничего не скачивает — это и проверка распаковки: команда должна сообщить
«загружено архивов 0» (с `--json` — `"downloaded": 0`). Нужен драйвер NVIDIA с поддержкой CUDA 13 (ветка R580 и
новее); устанавливать CUDA Toolkit не нужно. Лицензия библиотек NVIDIA —
https://docs.nvidia.com/cuda/eula/index.html.

`ml.device = "auto"` (по умолчанию) включает CUDA, если она поднялась, иначе работает на CPU;
`"cuda"` — то же с предупреждением в журнале при откате; `"cpu"` — без попытки CUDA.
Фактическое устройство и причина отката пишутся в журнал при старте. В CPU-комплекте
команда `cuda fetch` отказывает: библиотеки NVIDIA ему не нужны.

## Реранкер и лицензия

Серверный реранк включается в запросе поиска (`"rerank": "on"`, по умолчанию выключен; в
хуках не используется): первые 20 кандидатов (`ml.rerank_top`) переставляются по баллу
реранкера, у них в ответе появляется `rerank_score`. Модель выбирается по устройству модели
эмбеддингов и загружается при первом таком запросе: на CPU — `ml.rerank_model_cpu`
(`jina-reranker-v2`), на CUDA — `ml.rerank_model_gpu` (`bge-reranker-v2-m3`). Если реранкер
не установлен, поиск отвечает без реранка и с `warnings: ["reranker not installed"]`.

**Лицензия jina-reranker-v2 — CC-BY-NC-4.0: только некоммерческое использование.** Поэтому
модель не входит в комплект `zam-models` и скачивается только с явным согласием:

```
zam-server models fetch --device cpu --reranker --accept-nc-license
```

Без флага команда завершается с объяснением и ничего не скачивает. Для коммерческого
использования на CPU задайте `ml.rerank_model_cpu = "bge-reranker-v2-m3"` (Apache-2.0) и
скачайте её (`zam-server models fetch --id bge-reranker-v2-m3`); на CPU она заметно медленнее
(около 8 с на 20 кандидатов против 1,3–1,5 с у jina на 12 ядрах; на GPU RTX 3090 — 0,08 с).

jina — модель с динамическим int8: пары «запрос — фрагмент» считаются по одной (в батче баллы
зависели бы от соседей), параллельно в `ml.rerank_sessions` сессиях (по умолчанию 0 — авто:
до 2, ядра `ml.index_threads` делятся между ними). Каждая
сессия держит свою копию весов, около 0,3 ГБ: больше сессий — быстрее и больше памяти (1 —
1,9 с, 2 — 1,4 с, 4 — 1,15 с на 20 кандидатов на 12 ядрах). После обновления сервера
повторите `zam-server models fetch --device cpu --reranker --accept-nc-license`: команда
перепишет `model.toml` модели (признак `dynamic_quant`), веса не перекачиваются. Устаревший
описатель видно в `zam-server models status` («model.toml устарел … нужен `models fetch`») и
в журнале сервера (WARN при загрузке модели).

## Windows

1. Распакуйте архив `zam-server-<версия>-windows-x64-cpu.zip` (или `-gpu.zip`), например в
   `C:\ZeroAIMemory`.
2. `zam-server.exe` и `zam.exe` собраны со статическим CRT, а библиотеки MSVC runtime, которые
   нужны ONNX Runtime (`msvcp140*.dll`, `vcruntime140*.dll`) и Qdrant (`vcruntime140.dll` рядом с
   `qdrant.exe`), лежат в комплекте app-local: отдельная установка VC++ Redistributable не нужна.
3. Создайте `config.toml` и запустите `zam-server.exe serve --config config.toml`.
4. Для работы в фоне зарегистрируйте службу Windows — из PowerShell или cmd **от имени
   администратора** (без прав — ошибка и код 3):

   ```
   C:\ZeroAIMemory\zam-server.exe service install --config C:\ZeroAIMemory\config.toml
   C:\ZeroAIMemory\zam-server.exe service start
   C:\ZeroAIMemory\zam-server.exe service status
   ```

   Служба `zam-server` (`--name` — другое имя): автозапуск, учётная запись LocalSystem,
   `binPath = "<exe>" service run --config <абсолютный путь>`, восстановление — перезапуск через
   10 с, три раза. Без `--config` берётся `config.toml` рядом с `zam-server.exe`; относительный
   `data_dir` — от каталога `zam-server.exe`. `service install --print` показывает параметры,
   ничего не регистрируя. Консоли у службы нет: журнал — в `<data_dir>\logs\zam-server.log.*`,
   ошибка до журнала (конфиг не читается) — в `zam-server-service-error.log`, первый токен
   администратора — в `<data_dir>/first-admin-token.txt` (прочитайте и удалите файл). Пароль
   администратора службе — только `[admin] password_hash` в конфиге (`ZAM_ADMIN_PASSWORD` из вашей
   консоли служба не видит). `service stop` дожидается штатного выхода сервера, `service
   uninstall` останавливает и удаляет службу. `zam-server service run` вручную не вызывается
   (из консоли — ошибка и код 2). Запуск дольше 300 с или остановка дольше стоп-таймаута (ниже)
   считаются зависанием: сервер пишет ERROR, помечает службу остановленной с ошибкой и выходит —
   Windows перезапустит службу. Переменные `ZAM_*` вашей консоли служба не видит (`install`
   предупреждает о них): всё нужное — в конфиге.

   Служба работает под LocalSystem: если `master.key` создан запуском из шага 3 под вашим
   пользователем, сервер на каждом старте предупредит, что ключ читает ваш пользователь —
   передайте файл учётной записи службы (`icacls "<data_dir>\master.key" /setowner SYSTEM`, см.
   «Vault: секреты и мастер-ключ») или первый запуск делайте сразу службой.

   Альтернатива — NSSM или Планировщик заданий. Если служба NSSM работает под другой учётной
   записью (по умолчанию LocalSystem), действует то же замечание про `master.key`.

Остановка: Ctrl+C в окне сервера; сервер понимает и Ctrl+Break; служба — `service stop` или
оснастка «Службы». Все пути ведут в одну штатную остановку: сразу после записи она ждёт
подтверждения журнала Qdrant до 14 с (`[qdrant] shutdown_flush_wait_ms`): обычно остановка после
записи занимает 10–20 с, в худшем случае (недоделанная пачка инференса на CPU) — до 94 с.
Стоп-таймаут — `max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с: 80 с запаса (пачка
инференса, перенарезка, SIGTERM Qdrant) плюс ожидание WAL Qdrant; при умолчании
`shutdown_flush_wait_ms = 14000` — 94 с, при максимуме 60000 — 140 с. `service install` ставит
его таймаутом `Preshutdown` службы (остановка при выключении Windows), во время остановки служба
сообщает SCM `StopPending` с ростом `checkpoint` каждые 2 с. После смены
`shutdown_flush_wait_ms` выполните `service install` повторно — иначе сервер на старте под службой
предупредит, что таймаут мал. NSSM по умолчанию шлёт Ctrl+C и ждёт лишь 1,5 с, затем снимает
процесс — для `zam-server` задайте больше: `nssm set <имя службы> AppStopMethodConsole 94000`
(при 60000 — `140000`). Жёсткое снятие процесса удлиняет следующий старт (см. «Известные
ограничения»).

## Linux

1. Распакуйте архив `zam-server-<версия>-linux-x64-cpu.tar.gz` (или `-gpu.tar.gz`) в
   `/opt/zeroaimemory` (лишний верхний каталог архива отбрасывается):

   ```
   sudo install -d /opt/zeroaimemory
   sudo tar -xzf zam-server-<версия>-linux-x64-cpu.tar.gz --strip-components=1 -C /opt/zeroaimemory
   ```

   Исполняемые файлы: `/opt/zeroaimemory/zam-server`, `/opt/zeroaimemory/zam`,
   `/opt/zeroaimemory/qdrant/<версия>/qdrant`.
2. Создайте пользователя и каталоги:

   ```
   sudo useradd --system --home /var/lib/zeroaimemory --shell /usr/sbin/nologin zam
   sudo install -d -o zam -g zam /var/lib/zeroaimemory
   sudo install -d /etc/zeroaimemory
   sudo cp /opt/zeroaimemory/config.example.toml /etc/zeroaimemory/config.toml
   ```

   В `config.toml` укажите `data_dir = "/var/lib/zeroaimemory"` и `[admin] password_hash`
   (хэш: `/opt/zeroaimemory/zam-server hash-password`, пароль вводится по приглашению).
3. Установите юнит systemd и запустите службу:

   ```
   sudo /opt/zeroaimemory/zam-server service install --config /etc/zeroaimemory/config.toml
   sudo systemctl start zam-server          # или: sudo /opt/zeroaimemory/zam-server service start
   sudo journalctl -u zam-server -n 50      # путь к файлу первого токена
   sudo cat /var/lib/zeroaimemory/first-admin-token.txt && sudo rm /var/lib/zeroaimemory/first-admin-token.txt
   ```

   `service install` пишет `/etc/systemd/system/zam-server.service` из шаблона
   `systemd/zam-server.service` комплекта (`--name` — другое имя, `--user` — пользователь службы,
   по умолчанию `zam`; он должен существовать) и выполняет `systemctl daemon-reload` и `enable`;
   без root — ошибка и код 3. По конфигу подставляются `ExecStart` (`zam-server serve --config …`),
   `WorkingDirectory` (каталог `zam-server`), `ReadWritePaths` (`data_dir` и каталог
   `[vault] master_key_file`, если он вне `data_dir`; если что-то из путей лежит в `/home` или
   `/root` — `ProtectHome=read-only`) и `TimeoutStopSec` —
   `max(90, ceil(shutdown_flush_wait_ms / 1000) + 80)` с (94 с при умолчаниях): недоделанная пачка
   инференса (до 60 с), перечанковка (до 10 с), SIGTERM Qdrant (до 10 с) и ожидание WAL Qdrant
   `shutdown_flush_wait_ms = 14000` (14 с); обычно после записи — 10–20 с. Остановка — `SIGTERM`
   (`KillSignal=SIGTERM`; SIGINT сервер тоже понимает). После смены `shutdown_flush_wait_ms`
   выполните `service install` повторно: сервер на старте под systemd сверяет `TimeoutStopUSec`
   юнита и при нехватке пишет WARN. `service install --print` выводит юнит без записи;
   `service start|stop|status` — обёртки `systemctl` (код выхода — его), `service uninstall` —
   `systemctl disable --now`, удаление юнита и `daemon-reload`.

   Вручную: `sudo cp /opt/zeroaimemory/systemd/zam-server.service /etc/systemd/system/`, затем
   `sudo systemctl daemon-reload && sudo systemctl enable --now zam-server`; `ReadWritePaths`
   должен совпадать с `data_dir`, при `shutdown_flush_wait_ms = 60000` — `TimeoutStopSec=140`.
4. `zam-server` собран под `x86_64-unknown-linux-gnu` на Ubuntu 22.04 (glibc 2.35 и новее);
   `zam` — статический (musl).

## За обратным прокси (Traefik)

Сервер можно опубликовать по HTTPS под префиксом пути, например `https://example.com/memory`.

1. В `config.toml` сервера:

   ```
   [server]
   bind = "0.0.0.0:7700"
   public_url = "https://example.com/memory"
   base_path = "/memory"                 # префикс без завершающего "/"
   trusted_proxies = ["172.18.0.2"]      # адрес (или подсеть) Traefik, как его видит сервер
   ```

   `X-Forwarded-For` и `X-Forwarded-Proto` принимаются только от адресов из `trusted_proxies`:
   по ним определяются IP клиента (лимиты и аудит) и HTTPS. Если последний `X-Forwarded-Proto`
   от доверенного прокси равен `https`, cookie сессии WebUI получает атрибут `Secure`.
   Без `trusted_proxies` все клиенты за прокси выглядят как один IP (сервер один раз
   предупреждает об этом в журнале), а cookie остаётся без `Secure`.
2. Traefik передаёт путь как есть: префикс **не** срезается (`StripPrefix` не нужен), сервер
   сам обслуживает маршруты под `base_path`. Пример меток Docker:

   ```
   labels:
     - traefik.enable=true
     - traefik.http.routers.zam.rule=Host(`example.com`) && PathPrefix(`/memory`)
     - traefik.http.routers.zam.entrypoints=websecure
     - traefik.http.routers.zam.tls=true
     - traefik.http.services.zam.loadbalancer.server.port=7700
   ```

   Тот же маршрут в файловом провайдере (`dynamic.yml`):

   ```
   http:
     routers:
       zam:
         rule: "Host(`example.com`) && PathPrefix(`/memory`)"
         entryPoints: [websecure]
         tls: {}
         service: zam
     services:
       zam:
         loadBalancer:
           servers:
             - url: "http://10.0.0.5:7700"
   ```

   Traefik по умолчанию добавляет `X-Forwarded-For` и `X-Forwarded-Proto`.
3. Клиенты указывают полный адрес с префиксом: `ZeroAIMemoryUrl=https://example.com/memory`.

## Проверка сервера: doctor (с 0.0.17-m7.4)

```bash
zam-server doctor [--full] [--fix] [--json] [--config <файл>] [--data-dir <каталог>]
```

**Режимы.** Без `--fix` команда только читает: базы открываются без миграций и без записи, лок
каталога не берётся — её можно запускать и при работающем сервере (база, которую сервер открыл
посреди проверки, проверяется повторно — ложной ошибки из-за этого нет). `--full` — полная
проверка баз (`integrity_check` вместо `quick_check`) и SHA-256 файлов модели эмбеддингов: на
больших базах и гигабайтных моделях это минуты. `--fix` работает только на остановленном сервере
(иначе «каталог данных занят: zam-server запущен — остановите сервер», код 1).

**Проверки** — строки `ok | info | warn | error <код>: <текст>`:

- `data_dir` — каталог; лок (сервер запущен — `info` с pid, где ОС его отдаёт); признак
  незавершённого восстановления или отката — `error` с командой, которую надо повторить
  (`restore` или `rollback`); признак копии (идёт — `info`, брошен — `warn`); остатки
  `.restore-staging` — `warn`.
- `disk` — свободное место тома каталога данных: меньше 512 МиБ — `error`, меньше 2 ГиБ — `warn`.
- `db:system`, `db:<user>` — открытие, `quick_check`, версия схемы (старше программы — `info`
  «обновится при запуске», новее — `error`), контрольные суммы миграций (изменились — `error`,
  база до 0.0.17 — `info`), сверка схемы с эталоном (различия — `error`, первые пять), FTS5
  (`error`), `-wal`/`-shm` без базы — `warn`, копии `bak-v*` — `info`.
- `vault_key` — мастер-ключ против ключей Vault: ключа нет или он не подходит — `error`.
- `qdrant` — режим; у управляемого — бинарник и отметка `.zam-reindex` (`info`); базы,
  исключённые из пересборки векторов, — `warn`.
- `models` — модель эмбеддингов (как `models status`): нет — `warn`, поиск без векторов.
- `blobs:<user>` — строки вложений без файла — `error` (файл в `.gc/` — «вернёт --fix»); сколько
  удалит сборщик мусора и что лежит в `.incoming` — `info`.
- `links:<user>` — явные и системные связи живых записей к удалённой или несуществующей цели —
  `warn` (число и первые пять); неразрешённые wikilink — `info`.
- `backup` — последняя копия против условия `no_recent_backup` (`backup.warn_days`) — `warn`.
- `check:<user>` — последний ночной прогон проверки памяти: открытая регрессия — `warn` с
  вердиктом; при `works.check = "nightly"` и активных пробах нет законченного прогона двое суток
  — `warn`.

`--json` — `{checks: [{code, level, text, data}], errors, warnings}` (в `data` — подробности:
пути, списки различий, версии). Последняя строка текста — `итого: ошибок N, предупреждений M (T
мс)`.

**`--fix`** делает только безопасное: удаляет остатки `.restore-staging`, брошенный признак копии
(процесс копии мёртв, срок вышел) и `.incoming/*.part` старше суток, пересобирает FTS5 (`rebuild`)
у таблиц с ошибкой, возвращает файлы из `.gc/` их строкам и выполняет проход сборщика мусора
(«Вложения: сборщик мусора»; аудит `blobs.gc` с `by: "doctor"`). Сборщик и разбор `.gc/` идут
только по базам, проверенным начисто (версия программы, суммы, схема, `quick_check`). Схему,
суммы миграций и повреждённые базы `--fix` не правит: строка проверки называет `zam-server restore`
(копия) или `zam-server rollback --to v<N>` (копии перед миграцией). Итог исправлений — строки
`fix:…` в конце; проверки после них показывают уже исправленное состояние.

**Коды выхода:** 0 — ошибок нет (предупреждения допустимы), 1 — есть `error` (или `--fix` при
запущенном сервере), 2 — конфигурация не прочитана. Удобно до и после обновления:

```bash
zam-server doctor && echo "можно обновлять"
```

  шлёт снимок не больше 3 раз за сессию и держит его в локальной очереди.

## Копии из WebUI

С 0.0.15-m7.2 «Администрирование → Копии» (только администратор) снимает и удаляет копии сервера,
не выходя из браузера:

- **Снять.** «Снять копию сейчас» → «Снять копию»: сервер снимает полную копию каталога данных в
  каталог копий (`[backup] dir`, по умолчанию `<data_dir>/backups`) тем же кодом, что
  `zam-server backup`, — в своём процессе, не останавливаясь: запись и поиск работают. Пока копия
  идёт, страница пишет «Копия идёт с ЧЧ:ММ» и раз в 3 с обновляет ход; итог — строкой, как у
  команды: «копия 2026-11-23_101500: баз 3, блобов 120 (связано 118, скопировано 2), 1,2 ГБ, 40 с».
  Копия одна за раз. Пока она идёт, второй запуск не начинается — страница отвечает «копия уже
  идёт» и показывает ход идущей; автокопия в свой срок `at` откладывается до следующей минуты и
  снимается, когда замок освободится. Копия из WebUI, начатая после сегодняшнего срока `at`,
  засчитывается как сегодняшняя автокопия: вторая в этот день не снимается. При
  `schedule = "daily"` после копии из WebUI лишние копии сверх `keep` удаляются, как у автокопии;
  при `off` копии копятся — удаляйте лишние сами.
- **Удалить.** «Удалить» у строки списка → подтверждение. Удаляется только готовая копия
  каталога копий — каталог `yyyy-MM-dd_HHmmss[-N]` с `manifest.json` (`-N` — вторая и следующие
  копии в ту же секунду); архивы `--zip`, копии `--dir` в другие места, недостроенные
  `*.partial`, неудачные `*.failed` и ссылки (symlink, junction) на каталоги копий страница не
  видит и не удаляет.
- **Восстановить и скачать — нельзя.** В копии — хэши токенов и шифротексты Vault, поэтому через
  браузер она не отдаётся; восстановление — по-прежнему командой `zam-server restore` на
  остановленном сервере (порядок — «Перенос на другую машину», шаги 8–9: мастер-ключ — до
  `restore`). Для переноса на другую машину архив снимайте на машине сервера:
  `zam-server backup --zip <файл>`.

Каждая копия и удаление — в журнале аудита («Администрирование → Аудит»): `server.backup` (кто
начал — `webui` или `schedule`, итог, имя копии, размер, время) и `server.backup.delete`. Путь
каталога копий виден только на странице «Копии»; плашка «Копий нет» / «Последняя копия N дн.
назад» над страницами администратора и блок «Копии» на «Индексе» — без путей.

## Перенос на другую машину

Сервер переезжает целиком копией `zam-server backup` → `zam-server restore` (с 0.0.11-m6), в том
числе на машину другой ОС (Windows ↔ Linux). Копия переносит базы (`system.db`,
`users/*.db`: заметки, журналы, идеи, отчёты, Vault в зашифрованном виде, карту кода, токены,
кэш эмбеддингов) и блобы вложений, на которые есть ссылки (с 0.0.17-m7.4 откреплённые — нет: их
убирает сборщик мусора, см. «Вложения: сборщик мусора»). В копию **не входят**: мастер-ключ
Vault (переносится отдельно, шаги 2 и 8), конфигурация сервера (на новой машине — своя, шаг 5),
модели (шаг 6), хранилище Qdrant и превью (пересобираются из баз сами), журналы. Абсолютных
путей старой машины в базах нет: пути заметок, вложений и карты кода относительны; имя машины
остаётся только в атрибуции ревизий (кто и откуда писал). Cookie входа в WebUI после `restore` не
действуют — войдите заново; токены агентов прежние.

Команды ниже — для комплекта в `C:\ZeroAIMemory` с каталогом данных `C:\ZeroAIMemory\data`
(Windows) и `/opt/zeroaimemory` с конфигом `/etc/zeroaimemory/config.toml` и каталогом данных
`/var/lib/zeroaimemory` (Linux), как в разделах «Windows» и «Linux». Подставьте свои пути.

**Не запускайте сервер на новой машине до шага 9 (`restore`).** Первый запуск на пустом каталоге
данных создаёт новые базы, первого администратора и — если ключа ещё нет — новый `master.key`.
`restore` после этого откажет («каталог данных не пуст…»), а с `--replace` уберёт созданные базы
в `<data_dir>/backups/pre-restore-<время>/`, но созданный сервером `master.key` останется на
месте и к восстановленным секретам не подойдёт. Если сервер всё же запускали: остановите его,
замените `master.key` прежним (шаг 8) и выполните шаг 9 с `--replace`: с 0.0.17-m7.4 он
переносит в `backups/pre-restore-<время>/` и `<data_dir>/first-admin-token.txt` (токен из него
остался в убранных базах); у прежних выпусков удалите этот файл сами.

**На старой машине**

1. **Копия** — без остановки сервера (запись продолжается; копия каждой базы согласованна).
   Удобнее один архив: его проще перенести.

   ```powershell
   # Windows (PowerShell)
   New-Item -ItemType Directory -Force D:\zam-transfer
   C:\ZeroAIMemory\zam-server.exe backup --config C:\ZeroAIMemory\config.toml --zip D:\zam-transfer\zam-backup.zip
   ```

   ```bash
   # Linux: каталог копии принадлежит пользователю службы и закрыт для остальных
   sudo install -d -o zam -g zam -m 700 /var/backups/zam-transfer
   sudo -u zam /opt/zeroaimemory/zam-server backup --config /etc/zeroaimemory/config.toml --zip /var/backups/zam-transfer/zam-backup.zip
   ```

   Итог — строка с числом баз, блобов и байт; код 0 — копия проверена (суммы SHA-256 в
   `manifest.json` внутри архива). Без `--zip` копия — каталог
   `<data_dir>/backups/<yyyy-MM-dd_HHmmss>/` (`--dir` — другой каталог). Перед записью команда
   проверяет место: нужно не меньше размера баз и блобов плюс 10 %, а с `--zip` — вдвое больше
   (копия собирается рядом с архивом, в `<архив>.partial`, и затем упаковывается).
2. **Мастер-ключ — отдельно.** Команда напоминает об этом: «Мастер-ключ Vault не входит в
   копию…». Без прежнего ключа секреты Vault на новой машине не раскрыть, остальное работает.
   Ключ — файл `[vault] master_key_file` (по умолчанию `<data_dir>/master.key`) или значение
   `ZAM_MASTER_KEY`. Переносите его другим путём, чем копию (менеджер паролей, отдельный
   носитель): копия вместе с ключом раскрывает весь Vault. Пример — на съёмный носитель
   (`E:` и `/media/usb` — ваш носитель; каталог создаётся первой командой):

   ```powershell
   # Windows
   New-Item -ItemType Directory -Force E:\zam-key
   Copy-Item C:\ZeroAIMemory\data\master.key E:\zam-key\master.key
   ```

   ```bash
   # Linux
   sudo install -d -m 700 /media/usb/zam-key
   sudo install -m 600 /var/lib/zeroaimemory/master.key /media/usb/zam-key/master.key
   ```

   Посмотрите и запишите модель эмбеддингов старой машины — на новой нужна та же (шаг 6):

   ```powershell
   C:\ZeroAIMemory\zam-server.exe models status --config C:\ZeroAIMemory\config.toml
   ```

   ```bash
   sudo -u zam /opt/zeroaimemory/zam-server models status --config /etc/zeroaimemory/config.toml
   ```

3. **Перенос копии** на новую машину — любым способом: носитель, общая папка, `scp` (в
   Windows 10/11 он встроен):

   ```powershell
   # с Windows
   scp D:\zam-transfer\zam-backup.zip admin@new-host:
   ```

   ```bash
   # с Linux: копия закрыта для всех, кроме пользователя службы, — сначала возьмите её себе
   sudo install -m 600 -o "$USER" /var/backups/zam-transfer/zam-backup.zip ~/zam-backup.zip
   scp ~/zam-backup.zip admin@new-host:
   rm ~/zam-backup.zip
   ```

   Файл окажется в домашнем каталоге пользователя `admin` новой машины (`~/zam-backup.zip` на
   Linux, `C:\Users\admin\zam-backup.zip` на Windows с OpenSSH).

**На новой машине**

4. **Комплект своей ОС** — архив `zam-server-<версия>-<os>-x64-cpu` (или `-gpu`) той же или
   более новой версии, что на старой машине (базы старше программы мигрируют при первом
   открытии; новее — `restore` откажет). Распакуйте как в разделе «Windows» (шаг 1) или «Linux»
   (шаг 1); на Linux создайте пользователя и каталоги (шаг 2 «Linux»). Сервер не запускайте.
5. **Свой конфиг.** `config.toml` старой машины содержит её пути — не копируйте его вслепую.
   Возьмите `config.example.toml` комплекта, задайте `data_dir` (пустой каталог), `[admin]
   password_hash` (пароль администратора хранится в конфиге, а не в копии: задайте прежний или
   новый — `zam-server hash-password`) и перенесите нужные настройки старого конфига (порт,
   `[qdrant]`, `[ml]`, `[vault] master_key_file`).

   ```powershell
   # Windows
   Copy-Item C:\ZeroAIMemory\config.example.toml C:\ZeroAIMemory\config.toml
   notepad C:\ZeroAIMemory\config.toml      # data_dir = 'C:\ZeroAIMemory\data', [admin] password_hash
   ```

   ```bash
   # Linux
   sudo cp /opt/zeroaimemory/config.example.toml /etc/zeroaimemory/config.toml
   sudo nano /etc/zeroaimemory/config.toml  # data_dir = "/var/lib/zeroaimemory", [admin] password_hash
   ```

6. **Модель — до `restore`**, та же, что на старой машине (`model_id` векторов записан в описи
   копии, `embedding_models`). Тогда индекс собирается из кэша эмбеддингов копии без инференса.
   Другая модель (например, `bge-m3-fp16` на GPU вместо `bge-m3-int8` на CPU) или другая
   нарезка (`[index] chunk_*`) — векторы будут посчитаны заново: это правильно, но долго — на
   CPU около 700 токенов/с, на 2 ядрах — часы на большой базе.

   ```powershell
   C:\ZeroAIMemory\zam-server.exe models fetch --config C:\ZeroAIMemory\config.toml
   ```

   ```bash
   sudo -u zam /opt/zeroaimemory/zam-server models fetch --config /etc/zeroaimemory/config.toml
   ```

   Без интернета — архив `zam-models-<версия>-<модель>.zip` (см. «Модели»).
7. **Qdrant — до `restore`.** Управляемый Qdrant лежит в комплекте; команда проверит его и
   докачает, если его нет. Внешний Qdrant — `[qdrant] mode = "external"` и `url` в конфиге.

   ```powershell
   C:\ZeroAIMemory\zam-server.exe qdrant fetch --config C:\ZeroAIMemory\config.toml
   ```

   ```bash
   sudo /opt/zeroaimemory/zam-server qdrant fetch --config /etc/zeroaimemory/config.toml    # пишет в каталог комплекта
   ```

8. **Мастер-ключ — до `restore`**: на место `[vault] master_key_file` (по умолчанию
   `<data_dir>/master.key`) с правами только владельца. Файл ключа в пустом каталоге данных
   `restore` не мешает, зато `restore` сам сверит ключ с восстановленными секретами (шаг 9).

   ```powershell
   New-Item -ItemType Directory -Force C:\ZeroAIMemory\data
   Copy-Item E:\zam-key\master.key C:\ZeroAIMemory\data\master.key
   icacls "C:\ZeroAIMemory\data\master.key" /inheritance:r /grant:r "*S-1-3-4:F" "*S-1-5-18:F" "*S-1-5-32-544:F"
   ```

   ```bash
   sudo install -o zam -g zam -m 600 /media/usb/zam-key/master.key /var/lib/zeroaimemory/master.key
   ```

   На Windows владельцем файла остаётся ваш пользователь — так и нужно на этом шаге: `restore`
   (шаг 9) читает ключ от вашего имени, из обычной консоли. Службе файл передаётся позже, на
   шаге 10.

   Ключ задан переменной `ZAM_MASTER_KEY`, а не файлом, — задайте её и в окружении сервера, и
   в консоли, где запускаете `restore` (иначе `restore` ключа не увидит).
9. **Восстановление** — сервер не запущен, в каталоге данных нет баз и блобов (каталог моделей
   и `master.key` в нём не мешают). `restore` проверяет суммы и версии схем всех файлов до первой
   записи, копирует базы и блобы, очищает сессии WebUI и ставит каждой базе отметку
   «пересобрать векторный индекс из кэша». Он заранее пишет, что ждёт векторы: «из кэша» или
   «пересчёт: другая модель / другая нарезка, N чанков».

   ```powershell
   C:\ZeroAIMemory\zam-server.exe restore $HOME\zam-backup.zip --config C:\ZeroAIMemory\config.toml
   ```

   ```bash
   sudo install -o zam -g zam -m 600 ~/zam-backup.zip /var/lib/zeroaimemory/zam-backup.zip
   sudo -u zam /opt/zeroaimemory/zam-server restore /var/lib/zeroaimemory/zam-backup.zip --config /etc/zeroaimemory/config.toml
   sudo rm /var/lib/zeroaimemory/zam-backup.zip
   ```

   Итог — число баз и блобов, версии схем и ожидание векторов:

   ```
   восстановлено: баз 2, блобов 3; схемы: system.db=7, users/<id>.db=25
   векторы: векторы из кэша
   ```

   **Ключ подошёл — третьей строки нет.** Если после этих строк напечатано

   ```
   Vault: мастер-ключа нет (ни ZAM_MASTER_KEY, ни C:\ZeroAIMemory\data\master.key) — секреты недоступны, положите прежний master.key
   ```

   значит, `restore` ключа не нашёл: файла нет по пути из строки (`[vault] master_key_file`, по
   умолчанию `<data_dir>/master.key`) или он не читается, а переменной `ZAM_MASTER_KEY` в консоли
   нет. Если напечатано

   ```
   Vault: ключ не подходит — секреты недоступны, положите прежний master.key
   ```

   значит, ключ найден, но он не тот, что был на старой машине (до 0.0.17-m7.4 эта строка
   печаталась и тогда, когда ключа не было). Данные при этом восстановлены полностью, повторять
   `restore` не нужно. Проверьте:
   - файл лежит там, куда указывает `[vault] master_key_file` (по умолчанию
     `<data_dir>/master.key`), и читается пользователем, от имени которого шёл `restore`;
   - это файл старой машины, скопированный без изменений (не открывался в редакторе, не
     обрезан; сервер, запущенный до шага 9, мог создать свой ключ — см. предупреждение в
     начале раздела);
   - в консоли нет другой `ZAM_MASTER_KEY`: переменная важнее файла.

   Положите верный ключ и продолжайте с шага 10: при старте сервер сверит ключ ещё раз — в
   журнале не должно быть WARN «Vault заблокирован: …», а `zam vault get` на шаге 12 выдаст
   секрет.

   Каталог данных не пуст — отказ; `--replace` переносит прежние базы, блобы и (с 0.0.17-m7.4)
   `first-admin-token.txt` в `<data_dir>/backups/pre-restore-<время>/` (ничего не удаляется).
   Хранилище управляемого Qdrant `restore` стирает при первом запуске (отметка пересборки); с
   `--replace --no-reindex` оно остаётся с точками прежних данных — `restore` пишет строку
   «хранилище Qdrant прежних данных остаётся: zam-server qdrant reset --yes или reindex».

   **Переезд без ключа.** Если прежнего ключа нет (или он приедет позже), пропустите шаг 8:
   строка «Vault: мастер-ключа нет…» (до 0.0.17-m7.4 — «Vault: ключ не подходит…») тогда
   ожидаема. Сервер работает, но Vault заблокирован:
   `zam vault get` и раскрытие отвечают `503 /problems/vault-locked` («Vault заблокирован: файл
   мастер-ключа ([vault] master_key_file) не найден, а ключи Vault уже есть: новый ключ не
   создаётся…»), список секретов — с `locked: true`; заметки, поиск, вложения, журналы и карта
   кода работают. Когда ключ появится — положите его командами шага 8 и перезапустите сервер.
10. **Запуск.** Сервер при первом открытии каждой базы пересобирает Qdrant из кэша эмбеддингов
    (без модели, тысячи чанков в секунду); пока идёт пересборка, поиск отвечает с
    `warnings: ["index rebuilding"]` и `pending_count`. Ход — `GET /api/v1/index/status` или
    раздел «Индекс» WebUI.

    ```powershell
    C:\ZeroAIMemory\zam-server.exe serve --config C:\ZeroAIMemory\config.toml
    # или службой: см. «Windows», шаг 4
    ```

    Windows, сервер службой (LocalSystem): ключ, скопированный на шаге 8, остался
    собственностью вашего пользователя, и сервер на каждом старте писал бы WARN «файл
    мастер-ключа Vault доступен не только владельцу…» с SID вашего пользователя. Перед запуском
    службы — уже **после** `restore` — передайте файл ей (консоль администратора):

    ```powershell
    icacls "C:\ZeroAIMemory\data\master.key" /setowner SYSTEM
    ```

    После этого из обычной консоли файл не читается (см. «Vault: секреты и мастер-ключ»); если
    `restore` придётся повторить — запускайте его из консоли администратора.

    ```bash
    sudo /opt/zeroaimemory/zam-server service install --config /etc/zeroaimemory/config.toml
    sudo systemctl start zam-server
    ```

11. **Клиенты** — новый адрес, токены прежние: `ZeroAIMemoryUrl` в `CLAUDE.md`/`CLAUDE.local.md`,
    `url` в `~/.zeroaimemory/config.toml`.
    GUID решений (`.zeroaimemory/solution.toml`) едут с репозиториями; локальный кэш
    `.zeroaimemory/cache/` строится заново.
12. **Проверка** — после окончания пересборки: раздел «Индекс» WebUI или
    `GET /api/v1/index/status` — векторный поиск включён, очередь пуста,
    `reindex.running = false`, в `reindex.last` нет ошибок. В первые секунды после запуска поиск
    отвечает полнотекстом с `degraded: qdrant_down` и предупреждением «индекс пересобирается» —
    это не сбой. Адрес и токен — переменными окружения (так токен не попадает в список
    процессов); `zam` — из комплекта или с машины агента:

    ```powershell
    $env:ZAM_URL = 'http://new-host:7700'; $env:ZAM_TOKEN = '<токен>'
    zam status                                              # код 0
    zam search "<слово из вашей заметки>"                   # те же заметки
    zam vault get <имя секрета> --raw --solution <GUID>     # значение секрета; --global — личный Vault
    ```

    ```bash
    export ZAM_URL=http://new-host:7700 ZAM_TOKEN='<токен>'
    zam status                                              # код 0
    zam search "<слово из вашей заметки>"                   # те же заметки
    zam vault get <имя секрета> --raw --solution <GUID>     # значение секрета; --global — личный Vault
    ```

    В WebUI — вложения, идеи и отчёты.

**Одно пространство: `export` / `import`.** Когда переезжает не весь сервер, а одно
пространство (например, Knowledge на чужой сервер, где у вас уже есть пользователь), —
архив `.zip` пространства:

```
zam export --space knowledge -o knowledge.zip                     # на старом сервере
zam import knowledge.zip --space knowledge --own                  # на новом: ZAM_URL и ZAM_TOKEN нового сервера
```

С 0.0.14-m7.1 `zam export` по токену заменяет значения секретов в текстах меткой `‹secret›`
(опись `secrets_masked: true`, строка в stderr «архив без значений секретов»): такой архив
переносит пространство без значений. Если в заметках и записях есть секреты, архив для переноса
снимите в WebUI — пункт «Экспорт (.zip)» меню пространства (сессия человека, тексты как есть), —
и импортируйте его тем же `zam import … --own` на новом сервере.

В архив входят заметки (`.md` с frontmatter), вложения, записи журналов, связи и история; Vault,
карта кода (`zam code sync` строит её заново), эмбеддинги и корзина — нет. По токену (`zam
export`) — ещё и без пространства Human и отчётов: их выгружает пункт «Экспорт (.zip)» меню
пространства в WebUI, а переносит на другой сервер только `backup` → `restore` (`zam import`
отчёты пропускает, см. «Известные ограничения»). На новом сервере у
вас другой `user_id`, поэтому свой архив импортируйте **с `--own`**: тогда id и аксиомы
сохраняются. Без флага архив считается чужим — новые id, аксиомы понижены до `theorem`.
`zam import` отправляет архив и опрашивает задание импорта до конца (ход — в stderr);
эмбеддинги считаются заново моделью нового сервера — на CPU это время индексации всего
пространства. Повтор того же архива безопасен (совпавшее пропускается).

**Импорт из WebUI** (с 0.0.15-m7.2) — пункт «Импорт (.zip)…» меню пространства (правый клик
или «⋯» у строки пространства в дереве), рядом с «Экспорт (.zip)»: у своих пространств и
решений, у администратора — в пространства любого пользователя; у чужого решения участника
пункта нет (импорт пишет от имени владельца базы, сервер ответил бы 403). В окне — файл (архив
экспорта или zip папки с `.md`) и флаги, как у `zam import`: «Это мой архив (перенос с другого
сервера)» — `--own`; «Если запись уже есть: пропустить / новой ревизией» — `--on-conflict`;
«Аксиомы чужого архива: понизить до theorem / оставить» — `--axioms` (свой архив — по описи или
с флажком — аксиомы сохраняет при любом выборе). «Проверить без записи» показывает, что сделал
бы импорт, и ничего не пишет (`--dry-run`); «Импортировать» — записывает. Пока окно открыто,
видны отправка, этап (в очереди, проверка архива, вложения, запись с ходом) и итог: создано,
новых ревизий, пропущено, конфликты (первые 50 с причиной и «всего»), понижено аксиом, заменено
id, пропущено связей, неразрешённые ссылки, предупреждения (в том числе «секреты в архиве
замаскированы и не восстановятся» у архива, снятого по токену); после импорта дерево и числа
разделов перечитываются. **Отчёты переносятся только так** — импортом из WebUI и только в
пространство решения (в Knowledge отчёт архива уходит в конфликты: «отчёты — только в
пространство решения»); `zam import` их пропускает. Отказ приёма окно называет по коду: 403 —
«импорт — только владельцу пространства», 413 — архив больше `[import] max_bytes`, 503 —
«сервер занят, повторите через N с», 507 — мало места, 408 — отправка слишком медленная.
Закрыть окно, пока архив ещё отправляется, — окно спросит «Прервать отправку?»: «Прервать
отправку» обрывает передачу, задание не создаётся (под строкой пространства — «Импорт: отправка
прервана, задание не создано.»), «Продолжить отправку» — окно остаётся. После начала задания
закрытие окна импорт не отменяет — он идёт на сервере, но итог после закрытия не показывается:
результат видно по журналам и в «Администрирование → Аудит» (`space.import.done`).

## Обновление

Порядок: копия каталога данных (`zam-server backup` — на работающем сервере; ручная копия —
только после остановки), остановка сервера, замена файлов комплекта (конфигурацию и каталог
данных не трогайте), запуск: миграции баз применяются автоматически, копия файла создаётся перед
миграцией.

**Сначала — копия каталога данных до обновления.** Лучше — `zam-server backup` прежнего
комплекта (с 0.0.11-m6; сервер можно не останавливать): копия каждой базы согласованна и
проверена — код 0 означает, что суммы SHA-256 из `manifest.json` сошлись (см. «Перенос на другую
машину», шаг 1):

```
zam-server backup --config <config.toml>                    # каталог <data_dir>/backups/<время>/
zam-server backup --config <config.toml> --dir <каталог>    # или --zip <архив>.zip
```

Восстанавливает её `zam-server restore` версии 0.0.11-m6 и новее; для отката на версию до
0.0.11-m6 она не годится (см. «Что теряет откат» ниже). Мастер-ключ Vault в копию не входит.

Ручная копия каталога (сервер старше 0.0.11-m6 или нужна копия файлами) — только при
остановленном сервере, базы — вместе с `-wal` и `-shm`. Проверяйте её **не** `du -sh`: на ZFS и
Btrfs со сжатием он показывает место на диске, а не объём файлов (при обкатке 0.0.12-m6.5 —
251 КБ у каталога в 503 МБ), и копия на другой файловой системе выглядит «не того размера».
Сравнивайте объём файлов — `du -sh --apparent-size <каталог>` (GNU coreutils) у оригинала и копии
— или список и размеры всех файлов (базы, блобы вложений и прочее):

```bash
# Linux: размер и путь от корня каталога; diff молчит — скопировано всё
find /var/lib/zeroaimemory -type f -printf '%s %P\n' | sort -k2 > orig.txt
find /backup/zam-data -type f -printf '%s %P\n' | sort -k2 > copy.txt
diff orig.txt copy.txt && echo 'копия совпадает'
```

Быстрая сверка только баз — то же с `-name '*.db*'` вместо `-type f`.

```powershell
# Windows: объём файлов оригинала и копии (Length — размер файла, не место на диске)
(Get-ChildItem C:\ZeroAIMemory\data -Recurse -File | Measure-Object Length -Sum).Sum
(Get-ChildItem D:\zam-data -Recurse -File | Measure-Object Length -Sum).Sum
```

**Копии перед миграцией.** Каждая база, схему которой обновляет новая версия, копируется
рядом с собой: `system.db.bak-v<N>` и `users/<id>.db.bak-v<N>`, где `N` — версия схемы до
обновления (копия делается `VACUUM INTO`, на HDD — секунды на сотню мегабайт). Копии
сервер не удаляет: при каждом следующем обновлении схемы прибавляется копия с новым `N`
(копия той же версии перезаписывается), поэтому место под них нужно на размер баз за каждое
обновление. Удаляйте копии вручную, когда убедились, что новая версия работает.

**Откат командой (с 0.0.17-m7.4).** Базы к этим копиям возвращает `zam-server rollback` — на
остановленном сервере, комплектом, которым базы обновлялись (или новее):

```
zam-server rollback --config <config.toml> --to v26 --dry-run       # только план
zam-server rollback --config <config.toml> --to v26 --yes           # базы пользователей — к bak-v26
zam-server rollback --config <config.toml> --to v26 --system v6 --yes   # и system.db — к bak-v6
```

- `--to v<N>` — базы пользователей `users/<id>.db` к копиям `users/<id>.db.bak-v<N>`; `system.db`
  меняется только с `--system v<M>` (номера схем у баз разные: у `system.db` — свои). База уже на
  схеме N — пропуск строкой.
- **До первого изменения** команда проверяет все нужные копии (`integrity_check`, версия схемы,
  контрольные суммы миграций, сверка схемы с эталоном программы) и место под них; любая проблема
  — код 1 с причинами, каталог данных не тронут. База ниже N или без копии (например, пользователь
  создан после обновления — копии у его базы нет) — тоже отказ: такую базу перенесите из
  `users/` сами (выпуск со старой схемой её не откроет) и повторите.
- Без `--yes` (и без `--dry-run`) — план и код 1: строки по базам и «всё записанное в эти базы
  после <время копии> теряется» (см. «Что теряет откат»). `--json` — тот же итог в JSON.
- **Ничего не удаляется:** текущие базы вместе с `-wal`/`-shm` переносятся в
  `<data_dir>/backups/pre-rollback-<время>/`, копия `bak-v<N>` копируется на место и остаётся для
  повтора; векторы всех баз пересобираются из кэша при первом запуске; в аудит пишется
  `server.rollback`.
- Сбой посреди (питание, `kill`) — каталог помечен незавершённым откатом: сервер и
  `zam-server backup` отказывают («откат … не завершён: повторите ту же команду zam-server
  rollback»); повтор той же команды продолжает в тот же `pre-rollback-…`.
- Затем **замените файлы комплекта на выпуск со схемой N** и запустите его — этот `zam-server`
  при запуске снова обновил бы базы (итог команды напоминает об этом). Конфигурацию — как для
  ручного отката нужного выпуска (ниже, «Откат» каждого перехода).

Ручной порядок («Как подложить копию» ниже) остаётся для выпусков до 0.0.17: их комплекты команды
`rollback` не знают.

**Что теряет откат.** Копии `bak-v<N>` — снимки баз на момент обновления (первого открытия
базы новой версией). Откат на копию теряет **всё**, что записано после этого момента, а не
только новые сущности этапа: новые и изменённые заметки и их ревизии, корзину, привязки
вложений (их файлы в `blobs/` остаются без ссылок), пользователей и токены, выпущенные после
обновления (у новых пользователей копии нет вовсе), настройки и аудит. С 0.0.11-m6 есть
экспорт пространства (`zam export`), но импорт — тоже только с 0.0.11-m6: версия, на которую вы
откатываетесь, архив не примет (`zam import` ответит «сервер не поддерживает импорт пространства:
нужен zam-server 0.0.11-m6 или новее»). Поэтому до отката:
- сохраните нужное, пока работает новая версия, — архивом пространства из WebUI: пункт «Экспорт
  (.zip)» меню пространства (сессия человека: тексты как есть, с секретами; Human и отчёты —
  тоже). Это обычный zip с файлами `.md`: заметку из него можно записать в прежнюю версию
  `zam write --file`, убрав из начала файла служебный блок frontmatter (первый блок `---`), а
  после нового обновления до 0.0.11-m6 архив импортируется целиком (`zam import`, совпавшее
  пропускается). По токену так не сохранить: с 0.0.14-m7.1 `zam read` и `zam export` отдают
  агенту `‹secret›`/`‹secret-T-N›` вместо значений, и записанная после отката заметка получит
  метки, а не секреты (`zam export` пишет об этом строку в stderr); заметки без секретов можно и
  так — `zam read <цель> > файл.md` (`zam tree` — их список; в Windows PowerShell 5.1 `>`
  перекодирует вывод в UTF-16 — перенаправляйте из `cmd.exe`), после отката — `zam write
  --file`. Копия `zam-server backup` для отката не годится: её восстанавливает только 0.0.11-m6
  и новее;
- сохраните текущие базы целиком, чтобы можно было вернуться на новую версию: при
  остановленном сервере скопируйте каталог данных или хотя бы `system.db`, `users/*.db`
  **вместе с их `-wal` и `-shm`**, если они есть (сейчас работает 0.0.11-m6 или новее — удобнее
  `zam-server backup`). Копию проверяйте не `du -sh`, а объёмом файлов или сверкой списка
  файлов — см. «Сначала — копия каталога данных до обновления» в начале раздела.

**Как подложить копию (для любого отката).** С 0.0.17-m7.4 это делает `zam-server rollback --to
v<N>` (выше, «Откат командой»): шаги 1–3 ниже — его работа, с проверкой копий до изменений.
Вручную — комплектами до 0.0.17. Базы открываются в режиме WAL: рядом с
`system.db` и `users/<id>.db` живут `system.db-wal`/`system.db-shm` и
`users/<id>.db-wal`/`users/<id>.db-shm`. Журнал WAL не привязан к файлу базы: если оставить
его рядом с подложенной копией, SQLite применит к старой схеме кадры новой — база будет
повреждена. Порядок:
1. Остановите сервер штатно (Ctrl+C, `systemctl stop`, остановка службы) и дождитесь выхода
   процесса; убедитесь, что `zam-server` не запущен.
2. Уберите из каталога данных текущие `system.db`, `users/<id>.db` **и их `*-wal`, `*-shm`**
   (перенесите в сохранённую копию из предыдущего шага или удалите).
3. Переименуйте копии: `system.db.bak-v<N>` → `system.db`, `users/<id>.db.bak-v<N>` →
   `users/<id>.db`. Базы пользователей без копии нужной версии (созданных после обновления)
   уберите из `users/`: в восстановленном `system.db` таких пользователей нет.
4. Верните файлы прежнего комплекта. Если для целевой версии нужен сброс индекса (откат на
   0.0.3-m2 — см. ниже), выполните `zam-server qdrant reset --yes` прежнего комплекта сейчас,
   до запуска.
5. Запустите прежний комплект.

Так же — при восстановлении одной базы из копии `bak-v*` или бэкапа (см. «Состояние индекса и
reindex»): сервер остановлен, `-wal`/`-shm` этой базы удалены.

**Откат на 0.0.3-m2.** Копии `users/<id>.db.bak-v6` и `system.db.bak-v2` — порядок выше.
На шаге 4 перед первым стартом прежней версии сбросьте индекс — `zam-server qdrant reset --yes`: точек
записей журналов M2 не знает; индекс пересоберётся из кэша эмбеддингов без инференса.
Сам откат на 0.0.3-m2 тестом не проверялся.

**Откат на 0.0.2-m1.** Копии `users/<id>.db.bak-v3` и `system.db.bak-v1` — порядок выше (M1 не
открывает базы новой схемы и откажет с ошибкой). Каталог `<data_dir>/qdrant/` и
`<data_dir>/models/` прежней версии не нужны, их можно удалить.
