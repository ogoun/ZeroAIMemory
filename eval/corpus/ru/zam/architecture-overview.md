# Архитектура ZeroAIMemory: из чего состоит сервер

Короткая шпаргалка для новых людей в команде: что такое ZeroAIMemory, какие у него части и
почему они устроены именно так. Подробности всегда сверяйте с ТЗ (`docs/specs/`), здесь —
пересказ своими словами.

## Зачем это всё

ZeroAIMemory — общая память для AI-агентов (Claude Code, Codex и т. п.), которая живёт на одном
сервере в локальной сети. Знания хранятся деревом Markdown-заметок, как в Notion или Obsidian.
Агент ходит в память по токену через API, человек — через WebUI, встроенный в тот же бинарник.

Мотивация простая: в долгих проектах агент забывает уже разобранные ошибки, повторно пробует
проваленные гипотезы и не знает, что решили вчера на соседней машине. Сервис должен быть
«вещью в себе»: никакого облака, никаких внешних энкодеров, никакого отдельного Python. Модели
лежат рядом с сервером и исполняются в его процессе.

## Принципы, на которые опирается всё остальное

1. **Источник истины — SQLite и файлы вложений.** Qdrant — производный индекс, его всегда
   можно пересобрать из базы.
2. **На сервере нет генеративной модели.** Поиск, триггеры и хуки детерминированы. Выжимку
   из найденного делает сам агент, а сервер её только хранит и следит за актуальностью.
3. **Запись явная и атрибутированная**: кто, когда, из какой сессии и с какой машины.
4. **История только дописывается.** Ревизии не перезаписываются, удаление мягкое (корзина).
5. **Ядро — REST.** CLI, WebUI и будущий MCP — тонкие адаптеры поверх одного API.
6. **Деградация вместо отказа.** Нет модели или Qdrant — запись работает, поиск идёт по FTS5
   с флагом `degraded: true`.
7. **Самодостаточность.** Модели скачиваются по закреплённым ревизиям и SHA-256, ONNX Runtime
   подгружается динамически.

## Компоненты

Сервер `zam-server` написан на Rust (edition 2024) и внутри делится на такие части:

| Часть | Что делает |
|---|---|
| REST `/api/v1` | ядро: узлы, ревизии, поиск, админка, `/index/status` |
| MCP `/mcp` | streamable HTTP для агентов (этап M4) |
| WebUI | Svelte 5 + Vite, собирается в `web/dist` и вшивается в бинарник |
| Auth | администратор из конфига + bearer-токены пользователей |
| Store | `system.db` и по базе на пользователя `users/<user_id>.db`, FTS5 |
| Blobs | вложения по SHA-256, дедупликация в пределах пользователя |
| ML | ONNX Runtime: bge-m3 и опциональный реранкер, CPU или CUDA |
| Воркер индексации | забирает задания из outbox `index_jobs`, считает векторы |
| Search | FTS5 + Qdrant + (позже) граф, слияние RRF, опциональный реранк |
| Супервизор Qdrant | запускает, перезапускает и гасит дочерний процесс Qdrant |

Клиент `zam` — отдельный маленький бинарник. В нём нет tokio и ONNX, HTTP идёт через
синхронный `ureq`, поэтому холодный старт порядка единиц миллисекунд. Это важно для хуков:
они запускаются на каждое событие агента и не должны его тормозить.

## Раскладка по крейтам

```
crates/
  zam-core/      идентификаторы (UUIDv7 наружу как Crockford base32, 26 символов), токены
  zam-store/     SQLite: миграции, узлы, ревизии, FTS5, вложения, эмбеддинги, очередь
  zam-markdown/  comrak: разбор, секции, PATCH-splice, HTML, чанкер, предложения, L0/L1
  zam-ml/        ORT, устройство CPU/CUDA, токенизатор, эмбеддер, реранкер
  zam-index/     трейт VectorIndex, адаптер Qdrant, супервизор, воркер, reindex
  zam-search/    гибридное слияние, поправки, упаковка в бюджет токенов
  zam-fetch/     загрузка по манифестам с проверкой SHA-256
  zam-server/    axum: REST, auth, WebUI, команды сервера
  zam-cli/       клиент zam
```

Markdown во всей системе разбирает один парсер — comrak внутри `zam-markdown`. WebUI получает
готовый санитизированный HTML (ammonia + syntect на сервере), своего Markdown-парсера у клиента
нет. Благодаря этому секции, якоря и ссылки в интерфейсе совпадают с тем, что сервер
индексирует и патчит.

## Каталог данных

```
<data_dir>/
  system.db                      пользователи, токены, сессии WebUI, аудит, настройки
  users/<user_id>.db             вся память пользователя: узлы, ревизии, чанки, FTS, эмбеддинги, очередь
  blobs/<user_id>/<aa>/<sha256>  вложения
  models/<id>/                   ONNX-модели, в каждой LICENSE и model.toml
  qdrant/                        рабочий каталог управляемого Qdrant
  previews/  backups/  logs/
```

У каждого файла базы свой актор-писатель и пул читателей; PRAGMA: `journal_mode=WAL`,
`synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`.

## Как проходит запись заметки

- **Синхронно, в одной транзакции:** ревизия, узел, разбор comrak, секции, чанки с
  контекстным префиксом, строки FTS5, автоматические L0/L1 и задание в `index_jobs`. Поэтому
  только что записанная заметка сразу находится по словам.
- **Асинхронно, с низким приоритетом:** воркер берёт задание, ищет векторы в кэше `embeddings`,
  при промахе прогоняет модель батчами, делает upsert в Qdrant и ставит `index_state = 'indexed'`.

Ответ на запись содержит `index_state`, а ответ поиска — `pending_count`: сколько заметок
области ещё ждут векторизации. Агент видит, почему свежая запись пока не находится по смыслу.

## Чего в системе нет намеренно

Список «не-целей», о который регулярно спотыкаются в обсуждениях:

- **LLM на сервере.** Ни сводок, ни синтеза, ни автоматического извлечения памяти из диалогов.
  Запись всегда явная и делается агентом через инструменты.
- **Отдельная графовая СУБД.** Граф связей между заметками (этап M3) живёт в таблице `edges`
  SQLite с рекурсивными CTE; трейт `GraphStore` оставляет дверь открытой.
- **CRDT и совместное редактирование в реальном времени.** Вместо них оптимистическая
  блокировка: `PUT` с `If-Match: <rev>`, при конфликте 409 с диффом, плюс PATCH отдельных
  секций, который меняет только байты своей секции.
- **TLS и публикация в интернет.** Сервер слушает локальную сеть (`0.0.0.0:7700`), внешний
  доступ и HTTPS — забота обратного прокси вроде Traefik.
- **WYSIWYG-редакторы на модели документа** (ProseMirror, Tiptap): они пересериализуют
  Markdown и ломают побайтовую сохранность исходника. В WebUI — CodeMirror 6.

## Как запрос поиска проходит через части

1. CLI или WebUI шлёт `POST /api/v1/search` с токеном или cookie администратора.
2. Auth определяет пользователя и открывает его базу.
3. Параллельно: FTS5 в базе пользователя и, если векторный канал жив, эмбеддинг запроса в
   отдельной ONNX-сессии и запрос в Qdrant по gRPC.
4. `zam-search` сливает каналы через RRF, применяет поправки и упаковывает ответ в бюджет
   токенов.
5. Если вектора нет — ответ всё равно приходит, но с `degraded: true` и кодом причины.

## Масштаб и платформы

Ориентир ТЗ: до 20 пользователей, до миллиона чанков и 50 ГБ вложений. Обязательные платформы
каждого релиза — Windows x64 и Linux x64; GPU — только NVIDIA через CUDA, DirectML не
используется. Docker не нужен ни для работы, ни для тестов.

## Этапы

M0 — каркас, M1 — заметки и FTS (оба выпущены), M2 — индекс и ML (идёт сейчас), дальше M3
журналы и граф, M4 агенты (MCP, хуки, кэш выжимок), M5 документы, M6 экономия токенов,
M7 полировка. До версии 1.0 API и формат данных могут меняться.
