# Reindex: пересборка Qdrant из таблицы embeddings и полная перечанковка

Qdrant у нас производный. Всё, что нужно для его восстановления, лежит в SQLite, включая уже
посчитанные векторы. Поэтому пересборка индекса — дешёвая операция без модели.

## Кэш embeddings

Таблица `embeddings(text_hash, model_id, dense, sparse, …)`, первичный ключ
`(text_hash, model_id)`. Dense хранится в f16, sparse — парами (u32 id, f16 вес).
Ключ кэша — blake3 от строки, которая реально ушла в модель (контекстный префикс + текст), он
лежит в `chunks.embed_key`. Отсюда два следствия:

- одинаковый текст в двух заметках модель считает один раз;
- модель снова прогоняется только для новых текстов или при смене `model_id`.

Строки, на которые больше не ссылается ни один чанк, удаляет сборка мусора: после reindex всей
базы и раз в час в простое.

## Два вида reindex

**Из кэша (по умолчанию).** Точки области удаляются из Qdrant и пишутся заново из `embeddings`
пачками по 256. Цель — не меньше 2000 чанков/с. Заметки, для которых в кэше нет вектора
(например, после смены модели), получают задания и векторизуются воркером.

**Полный (`full`).** Все заметки области заново проходят чанкер и ставятся в очередь. Модель
вызывается только для текстов, которых нет в кэше. Нужен, когда поменялись правила чанкинга
или контекстного префикса.

Если коллекция создана другой моделью, она пересоздаётся под текущую, и тогда пересобираются
все базы. Прерванный reindex (остановка, сбой) автоматически повторяется при следующем запуске.

## Как запустить

На работающем сервере — администратор, ответ 202 с `job_count`:

```
POST /api/v1/admin/reindex  {}                                   # все базы, из кэша
POST /api/v1/admin/reindex  {"user": "<id>", "space": "rules"}   # одно пространство
POST /api/v1/admin/reindex  {"full": true}                       # перечанковка
```

На остановленном сервере — из командной строки; каталог данных открывается под локом, и если
сервер запущен, команда откажет и подскажет API:

```
zam-server reindex --config config.toml
zam-server reindex --config config.toml --user <id> --space knowledge
zam-server reindex --config config.toml --full
```

В WebUI на странице «Индекс» те же две кнопки: «Переиндексировать из embeddings» и «Полная
переиндексация».

## Когда это нужно

- сменили модель или устройство (CPU int8 ↔ GPU fp16);
- хранилище Qdrant потеряно, стёрто вручную или после скачка версии;
- база пользователя восстановлена из копии.

## Повреждённые базы

Если база пользователя не SQLite, имеет схему новее программы или пять раз подряд не
открылась при пересборке после стирания хранилища, она исключается из пересборки: WARN в
журнале, аудит `index.rebuild_skipped`, поле `rebuild_skipped` в статусе. Остальные базы
пересобираются. Исключение хранится в `system.db` и переживает перезапуск; когда база снова
открылась (например, из `users/<id>.db.bak-v*`), сервер сам ставит ей reindex и снимает
исключение. Явно указанная повреждённая база (`--user`) — ошибка, а не пропуск.

Итог каждого запуска пишется в аудит (`index.reindex`, `index.reindex_done`) и в поле
`reindex.last` статуса индекса.
