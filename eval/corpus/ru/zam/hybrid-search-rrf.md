# Гибридный поиск: каналы, weighted RRF, свежесть и лимит на узел

Разбор того, как `POST /api/v1/search` превращает запрос в список карточек. Код — крейт
`zam-search` (`hybrid`, `adjust`, `pack`) и `crates/zam-server/src/api/search.rs`.
Генеративной модели на этом пути нет вообще.

## Что приходит в запросе

Основные поля:

- `query` — текст;
- `scope` — решение, `include_knowledge`, `include_rules`, `all_solutions`, `path_prefix`, `area`;
- `filters` — виды, теги, статусы, `since`;
- `mode` — `brief` (по умолчанию: компактные карточки), `chunks` (карточки с текстом в
  пределах бюджета) или `notes` (только узлы с L0);
- `top_k` (10) и `budget_tokens` (800);
- `rerank` — `off` по умолчанию, `on` включает серверный cross-encoder;
- `expand` — `none`, `section`, `neighbors`, `graph`;
- `format` — `md` (компактный текст для агентов) или `json`.

Из CLI то же самое: `zam search "перевод строки в sh" --mode chunks --top-k 5 [--rerank]`.

## Шаг 1. Общий фильтр области

Пользователь, пространства, решение, префикс пути, статус — один и тот же фильтр для всех
каналов. В векторном канале он превращается в фильтр payload (`user_id` — tenant-индекс,
`space_id`, `path_ancestors`, `level`), в FTS — в условия SQL.

## Шаг 2. Кандидаты из каналов

**Векторный канал (Qdrant, коллекция `zam_chunks`).** Один запрос Query API с тремя prefetch:

- `dense` top-50 по листовым чанкам;
- `sparse` top-50 по листовым чанкам;
- `dense` top-10 по сводкам уровней `note` и `section`.

Внутри Qdrant они уже сливаются через RRF с k=60, наружу выходит до 60 точек. Dense-векторы
ищутся по int8-копии в RAM с пересчётом по оригиналам с диска, у sparse IDF-модификатора нет.

**FTS5 в SQLite.**

- `bm25` top-50 по таблице с токенизатором `unicode61 remove_diacritics 2` — обычные слова;
- `trigram` top-20 — подстроки, выручает на идентификаторах, кодах ошибок, путях.

FTS и эмбеддинг запроса с векторным поиском запускаются параллельно.

## Шаг 3. Слияние в приложении

Каналы сливаются weighted RRF:

```
score(чанк) = Σ по каналам  w_канала / (rrf_k + место_в_канале)
```

Место считается с единицы. Чанк, который нашёлся в двух каналах, почти всегда выше чанка из
одного. Почему RRF, а не сумма нормированных баллов: у bm25, косинуса и trigram несравнимые
шкалы, а ранги сравнимы всегда.

### Пример на пальцах

Чанк A — третий в векторном канале и первый в bm25. Чанк B — первый в векторном канале, в
FTS не нашёлся. Чанк C — второй только в trigram. При умолчаниях:

| Чанк | Вклад vector | Вклад fts | Вклад trigram | Итог |
|---|---|---|---|---|
| A | 1/(60+3) ≈ 0,0159 | 1/(60+1) ≈ 0,0164 | — | ≈ 0,0323 |
| B | 1/(60+1) ≈ 0,0164 | — | — | ≈ 0,0164 |
| C | — | — | 0,7/(60+2) ≈ 0,0113 | ≈ 0,0113 |

A уверенно впереди, хотя ни в одном канале не был «самым-самым» по сырому баллу. Большое
`rrf_k` сглаживает разницу между соседними местами, поэтому согласие каналов важнее, чем
первое место в одном из них. Вес trigram ниже единицы: подстрочный канал шумнее на обычном
тексте и должен влиять в основном там, где запрос похож на идентификатор.

## Шаг 4. Поправки

- **Затухание по свежести.** Множитель `0,5 + 0,5 · 2^(−возраст / полупериод)`, полупериод
  180 дней. Давняя заметка теряет не больше половины балла — старое знание не исчезает, но
  при прочих равных свежее выше.
- `superseded` и `retracted` выкидываются, если не запрошен `include_history`.
- Бусты для `gotcha`/`failure` и текущей области приедут вместе с журналами (M3).

## Шаг 5. Реранк (опционально)

Только при `rerank=on`: первые 20 кандидатов (`ml.rerank_top`) по 256 токенов
(`ml.rerank_tokens`) прогоняются через cross-encoder, в ответе появляется `rerank_score`.
В хуках не используется никогда. По умолчанию реранжирует сам агент: он лучше знает свою
задачу. Модели нет — ответ приходит без реранка и с `warnings: ["reranker not installed"]`.

## Шаг 6. Группировка

- Не больше `max_per_node` (3) чанков с одного узла — иначе одна длинная заметка забивает
  весь top-10.
- Если сработала сводка уровня заметки или секции, вместо неё в выдачу ставится лучший
  листовой чанк этой заметки.

## Шаг 7. Расширение и упаковка

`expand=section` подставляет секцию целиком, `neighbors` — соседние чанки, `graph` — соседей
по графу (M3, пока отвечает 400). Затем всё упаковывается в `budget_tokens` по
`token_count` чанков; минимум один элемент попадает всегда.

У каждого элемента: `node_id`, `space`, `path`, `heading_path`, `rev`, `chunk_ids`, `score`,
`updated_at`, `text` и `sources` — метки каналов `vector`/`fts`. У ответа в целом:
`degraded`, `pending_count`, `timings {fts_ms, embed_ms, vector_ms, fuse_ms}`.

## Карточка в режиме brief

```
1. n:01J… Solutions/parser/deploy.md › Docker › Сборка  [0.82] rev7 · 2026-10-10 · ~340 tok
   Сборка образа идёт multi-stage; для arm64 нужен buildx…
```

Тип и id, путь и секция, балл, ревизия, дата, размер полного текста в токенах и строка
фрагмента. Цель — 10 карточек не дороже 500 токенов.

## Настройки

```toml
[search]
rrf_k = 60.0
w_vector = 1.0                 # Qdrant: dense + sparse + сводки
w_fts = 1.0                    # FTS5 bm25
w_trigram = 0.7                # FTS5 trigram
recency_half_life_days = 180.0 # 0 — без затухания
max_per_node = 3
```

Любая правка весов, чанкинга или модели — только с прогоном eval (recall@5, MRR@10, nDCG@10).

## Частые вопросы

**Почему свежая заметка находится по словам, но не по смыслу?** Чанки и FTS пишутся в
транзакции записи, а векторы считает воркер позже. Пока заметка в очереди, её видит только FTS;
в ответе это отражает `pending_count`.

**Почему одна и та же заметка не занимает весь top-10?** Срабатывает `max_per_node`. Если
нужно больше текста из найденной заметки, правильный путь — `expand=section` или точечное
чтение, а не увеличение лимита.

**Зачем отдельный канал trigram, если есть bm25?** Токенизатор `unicode61` режет
`zam_qdrant_rss_bytes` или `rebuild_skipped` на куски и теряет точное совпадение, а trigram ищет подстроку
как есть. Канал включается, когда в запросе есть код или идентификаторы.

**Можно ли отключить векторный канал руками?** Достаточно `w_vector = 0`; но тогда теряется
весь смысловой поиск, и перефразы перестанут находиться. Для отладки удобнее смотреть метки
`sources` у элементов выдачи.

## Целевые времена (p95)

| Сценарий | CPU | GPU |
|---|---|---|
| только FTS | ≤ 20 мс | ≤ 20 мс |
| `chunks` без реранка | ≤ 120 мс | ≤ 50 мс |
| с реранком 20×256 | ≤ 1,5 с | ≤ 150 мс |

Эмбеддинг запроса идёт в отдельной ONNX-сессии с зарезервированными потоками
(`ml.query_threads = 2`), а индексация уступает между батчами (`index.yield_ms`), чтобы эти
цифры держались даже при полной очереди индексации.
