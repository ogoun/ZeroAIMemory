# Arc<Mutex<T>> и взаимоблокировки: разбор инцидента и правила

## Что случилось

Сервис индексации раз в несколько дней переставал отвечать: процесс жив, CPU около нуля,
логи молчат. Снимок стеков (`gdb -p <pid> -batch -ex "thread apply all bt"`) показал два
потока, каждый висел в `futex_wait` внутри `std::sync::Mutex::lock`. Классика: поток A
держал `queue` и ждал `stats`, поток B держал `stats` и ждал `queue`.

```rust
// поток A
let mut q = shared.queue.lock().unwrap();
let mut s = shared.stats.lock().unwrap();   // ждёт B

// поток B (в другом модуле, написан позже)
let mut s = shared.stats.lock().unwrap();
let q = shared.queue.lock().unwrap();       // ждёт A
```

Компилятор Rust защищает от гонок данных, но **не от взаимоблокировок**: это логическая
ошибка, и система типов её не видит.

## Типовые сценарии

### 1. Разный порядок захвата

Как в инциденте выше. Решение — один глобальный порядок. Мы записали его в комментарии к
структуре и проверяем на ревью: сначала `queue`, потом `stats`, потом `cache`.

### 2. Повторный захват в том же потоке

`std::sync::Mutex` не реентерабельный. Документация прямо говорит, что повторный `lock()`
из потока, который уже держит блокировку, может привести к взаимоблокировке или панике —
поведение не определено. Обычно это происходит неявно:

```rust
impl Index {
    fn add(&self, doc: Doc) {
        let mut g = self.inner.lock().unwrap();
        g.docs.push(doc);
        self.flush_if_needed();          // внутри снова self.inner.lock() — повисли
    }
}
```

Лечение: внутренние функции принимают `&mut Inner` (уже захваченные данные), а публичные
методы захватывают блокировку ровно один раз.

### 3. Временный guard живёт дольше, чем кажется

```rust
match self.state.lock().unwrap().mode {
    Mode::Idle => self.start(),   // start() тоже берёт state.lock() — взаимоблокировка
    _ => {}
}
```

Временное значение в выражении `match` живёт до конца всего `match`. То же было с
`if let` до редакции 2024: в Rust 2024 временные значения условия `if let` уничтожаются до
ветки `else`, но внутри тела `if let` guard всё ещё жив. Надёжно — сначала скопировать
значение в локальную переменную:

```rust
let mode = self.state.lock().unwrap().mode;   // guard уничтожен в конце оператора
match mode { ... }
```

### 4. Блокировка плюс ожидание канала или join

Поток держит mutex и ждёт `rx.recv()` или `handle.join()`, а отправитель или дочерний
поток пытается взять тот же mutex. Правило: внутри критической секции не ждать ничего
внешнего — ни канала, ни сети, ни другого потока.

### 5. Колбэки под блокировкой

Вызов пользовательского замыкания или подписчика, пока держим guard. Подписчик может
сделать что угодно, включая обращение к тому же объекту. Сначала собрать список
подписчиков (клонировать `Arc`), отпустить блокировку, потом вызывать.

## Правила, которые мы приняли

1. **Критическая секция — минимальная.** Взять, скопировать или подменить данные
   (`std::mem::take`), отпустить. Вычисления и ввод-вывод — снаружи.
2. **Единый порядок захвата** для объектов, которые берутся вместе. Лучше — объединить их
   в одну структуру под одним mutex, если они почти всегда меняются вместе.
3. **Никаких вызовов методов `self`, которые сами берут блокировку**, изнутри секции.
4. **Явная область видимости guard** через блок `{ ... }`, а не через надежду на `drop`.
5. **Каналы вместо разделяемого состояния**, где это естественно: один поток владеет
   данными, остальные шлют сообщения.
6. **Отравление (poisoning).** Если поток паникует с guard в руках, mutex помечается
   отравленным, и `lock()` возвращает `Err(PoisonError)`. `unwrap()` превращает одну панику
   в каскад. Для данных, которые остаются корректными после паники, используем
   `lock().unwrap_or_else(|e| e.into_inner())`.

## Инструменты диагностики

| Инструмент | Что даёт |
|---|---|
| `gdb`/`lldb`, `thread apply all bt` | стеки всех потоков висящего процесса |
| Windows: дамп через Диспетчер задач + WinDbg `~*k` | то же на Windows |
| `parking_lot` с фичей `deadlock_detection` | фоновая проверка циклов ожидания, `parking_lot::deadlock::check_deadlock()` |
| `try_lock_for(Duration)` в `parking_lot` | таймаут вместо вечного ожидания, удобно для логирования подозрительных мест |
| `tokio-console` | для асинхронного кода: задачи, которые давно не продвигаются |

В тестах полезно запускать нагрузочный сценарий с `parking_lot` и включённой проверкой: она
раз в N секунд ищет циклы и печатает стеки участников.

## parking_lot против std

`parking_lot::Mutex` не отравляется, компактнее и раньше был заметно быстрее; после
переписывания std-примитивов на futex (Rust 1.62) разница в обычных сценариях небольшая.
Берём `parking_lot`, когда нужны таймауты, `ReentrantMutex` или детектор взаимоблокировок.
Реентерабельный mutex — крайняя мера: он скрывает проблему архитектуры (сценарий 2), а не
решает её.

## Async-код

В tokio-коде те же правила плюс одно: не держать `std::sync::Mutex` через `.await`. Это
отдельная тема (Send и guard через await), здесь лишь отмечу, что `tokio::sync::Mutex`
тоже может взаимно блокироваться при разном порядке захвата — асинхронность от этого не
спасает, просто вместо висящих потоков будут висящие задачи.

## Condvar: ещё один способ зависнуть

`Condvar::wait(guard)` атомарно отпускает mutex и засыпает, а при пробуждении захватывает
его снова. Ошибки, которые мы встречали:

- **Ожидание без цикла.** Пробуждения бывают ложными, а уведомление могло прийти до
  `wait`. Условие проверяем в цикле, удобнее всего через `wait_while`:

```rust
let (lock, cvar) = &*pair;
let guard = cvar.wait_while(lock.lock().unwrap(), |s| !s.ready).unwrap();
```

- **`notify_one` вместо `notify_all`**, когда ждут потоки с разными условиями: будится не
  тот, засыпает снова, а нужный так и не узнаёт о событии.
- **Изменение условия без блокировки.** Флаг меняется атомиком вне mutex, уведомление
  уходит, а ожидающий ещё не успел заснуть — пробуждение потеряно. Условие меняем только под
  тем же mutex, с которым работает `Condvar`.

Для большинства задач вместо пары `Mutex + Condvar` проще канал (`std::sync::mpsc`,
`crossbeam-channel`) или `std::sync::Barrier`.

## Как писать код, который легко проверить

- Каждая структура с несколькими блокировками документирует порядок захвата в
  doc-комментарии.
- Методы с суффиксом `_locked` принимают уже захваченные данные (`&mut Inner`) и никогда не
  берут блокировку сами; методы без суффикса берут её ровно один раз.
- Guard не возвращается из публичных функций: иначе область удержания блокировки
  определяет вызывающий код, и порядок захвата уже не контролируется.
- В ревью ищем глазами `lock()` внутри цикла и внутри `match` по выражению с `lock()`.

## Итог инцидента

Объединили `queue` и `stats` в одну структуру под одним mutex (они менялись вместе в 90 %
мест), добавили в CI прогон стресс-теста с детектором `parking_lot`. Повторов не было.
