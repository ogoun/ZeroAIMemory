# cargo test: параллельный запуск, нестабильные тесты и proptest

## Почему тесты «то падают, то нет»

`cargo test` запускает тесты одного тестового бинарника **параллельно в потоках одного
процесса** (по числу ядер). Всё, что разделяется между потоками процесса, становится
источником гонок:

- **Переменные окружения.** `std::env::set_var` в одном тесте видна всем остальным. В
  редакции 2024 `set_var` и `remove_var` стали `unsafe` именно потому, что это гонка.
- **Текущий каталог.** `std::env::set_current_dir` меняет его для всего процесса.
- **Файлы с фиксированными именами** (`target/test.db`), общий порт (`127.0.0.1:8080`).
- **Глобальные синглтоны**: логгер, инициализируемый дважды, `static` со счётчиком.

Отдельные файлы в `tests/` — отдельные бинарники; cargo запускает их по очереди, а тесты
внутри каждого — параллельно.

## Как чинить

1. Убрать общее состояние: каталог из `tempfile::tempdir()` на каждый тест, порт `0`
   (система выдаст свободный, адрес узнаём через `local_addr()`), конфигурацию передавать
   параметром, а не через окружение.
2. Если убрать нельзя — сериализовать только конфликтующие тесты: крейт `serial_test`,
   атрибут `#[serial]` (или `#[serial(env)]` для группы).
3. `cargo test -- --test-threads=1` — диагностика, а не решение: если с ним всё зелёное,
   значит, проблема в общем состоянии.
4. `cargo nextest run` запускает каждый тест в отдельном процессе: окружение и текущий
   каталог больше не общие. Плюс повторы упавших тестов (`--retries 2`) и отчёт о
   нестабильных.

Полезные флаги: `-- --nocapture` (видеть вывод), `-- --exact имя`, `RUST_BACKTRACE=1`.

## proptest: тесты на свойствах

Вместо пары ручных примеров — генерация сотен входов и проверка инварианта:

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn roundtrip(s in "\\PC{0,64}") {
        let encoded = encode(&s);
        prop_assert_eq!(decode(&encoded).unwrap(), s);
    }

    #[test]
    fn sort_is_idempotent(mut v in prop::collection::vec(any::<i32>(), 0..100)) {
        v.sort();
        let once = v.clone();
        v.sort();
        prop_assert_eq!(v, once);
    }
}
```

Что важно знать:

- При падении proptest **сжимает** (shrinking) вход до минимального контрпримера — в отчёте
  обычно короткая строка или вектор из пары элементов.
- Упавшие входы сохраняются в каталоге `proptest-regressions/` рядом с исходником. Этот
  каталог **коммитим**: при следующих запусках эти случаи проверяются первыми.
- Число случаев по умолчанию 256; меняется переменной `PROPTEST_CASES` или
  `ProptestConfig::with_cases(..)`.
- Внутри `proptest!` используем `prop_assert!` / `prop_assert_eq!`, а не `assert!`: так
  сжатие работает корректнее и сообщение понятнее.
- Случайность proptest — тоже источник «нестабильности»: тест может упасть через неделю на
  новом входе. Это находка, а не шум — добавить случай в регрессии и исправить код.
