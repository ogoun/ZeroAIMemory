# revert против reset: как правильно откатывать изменения

Шпаргалка для команды после того, как на прошлой неделе кто-то сделал `git reset --hard` на
опубликованной ветке и затем `push --force`, а трое коллег потом полдня разбирались со своими
локальными копиями. Главное правило в одной строке: **опубликованное откатываем через revert,
неопубликованное — через reset**.

## Чем они отличаются по сути

`git revert <коммит>` создаёт **новый** коммит, который вносит обратные изменения. История не
переписывается: старый коммит остаётся, рядом появляется его «антипод». Это безопасно для
веток, которые уже скачали другие, — у них обычный fast-forward.

`git reset <коммит>` **передвигает указатель текущей ветки** назад (или вообще куда угодно).
Коммиты после этой точки перестают быть доступными из ветки. Если их уже кто-то получил, их
история разойдётся с вашей.

| Вопрос                          | revert                         | reset                               |
|---------------------------------|--------------------------------|-------------------------------------|
| Меняет историю                  | нет, добавляет коммит          | да, двигает ветку                   |
| Подходит для общей ветки        | да                             | нет (нужен принудительный push)     |
| Можно отменить коммит из середины | да                           | только вместе со всеми последующими |
| Трогает рабочий каталог         | применяет обратный патч        | зависит от режима                   |
| Как вернуть обратно             | revert на revert-коммит        | через reflog                        |

## Три режима reset

Удобно думать о трёх «слоях»: указатель ветки (HEAD), индекс и рабочий каталог.

| Режим     | Ветка | Индекс     | Рабочий каталог | Когда нужен                                    |
|-----------|-------|------------|-----------------|------------------------------------------------|
| `--soft`  | назад | не трогает | не трогает      | склеить несколько последних коммитов в один    |
| `--mixed` | назад | сбрасывает | не трогает      | режим по умолчанию: «раскоммитить», правки целы |
| `--hard`  | назад | сбрасывает | **сбрасывает**  | выбросить всё, включая незакоммиченные правки   |
| `--keep`  | назад | сбрасывает | сохраняет правки, если не конфликтуют | безопасная замена `--hard` |

Примеры, которые нужны чаще всего:

```bash
# отменить последний коммит, но оставить правки в рабочем каталоге
git reset HEAD~1

# то же, но правки остаются проиндексированными — чтобы сразу закоммитить заново
git reset --soft HEAD~1

# склеить последние три коммита в один
git reset --soft HEAD~3
git commit -m "Импорт отчётов: парсер, валидация и тесты"

# убрать файл из индекса, не трогая его содержимое
git restore --staged config/local.toml     # современный вариант git reset -- <файл>

# полностью вернуть ветку к состоянию origin (локальные коммиты и правки пропадут)
git reset --hard origin/main
```

Незакоммиченные правки после `--hard` не восстанавливаются ничем: их нет ни в reflog, ни в
объектах (кроме того, что успели добавить в индекс — те можно поискать через `git fsck`).
Закоммиченное же восстанавливается через `git reflog` в течение срока хранения.

## revert на практике

```bash
# отменить один коммит
git revert 4e1d2c7

# несколько коммитов одним коммитом отмены
git revert --no-commit 4e1d2c7 9ab03f1
git commit -m "Откат: новая схема кэша ломает экспорт"

# диапазон (A не включается, B включается)
git revert A..B
```

Если отменяемые изменения успели перекрыться более поздними правками, revert даст конфликт —
решается как обычный: правим, `git add`, `git revert --continue`. Прервать — `git revert --abort`.

### Откат слияния

Merge-коммит имеет двух родителей, и git должен знать, относительно какого считать обратный
патч:

```bash
git revert -m 1 <merge-коммит>
```

`-m 1` означает «основная линия — первый родитель», то есть ветка, в которую сливали. Это
почти всегда то, что нужно.

Подвох: после такого отката git считает, что коммиты фичи **уже есть** в main. Если потом
исправить фичу в той же ветке и снова слить, придут только новые коммиты, а старые останутся
откаченными. Правильно — сначала откатить сам revert-коммит (`git revert <revert-коммит>`),
затем слить исправления.

## amend — частный случай переписывания

`git commit --amend` заменяет последний коммит новым: добавляет проиндексированные правки и
даёт поправить сообщение (`--no-edit` — оставить как есть). По сути это `reset --soft HEAD~1`
плюс новый коммит. Значит, и правило то же: только пока коммит не отправлен. Если уже
отправлен — исправление отдельным коммитом.

## Что делать, если reset уже сделан на общей ветке

1. Не паниковать и не делать новых принудительных пушей.
2. У того, у кого есть правильное состояние, найти его в `git reflog` или в `origin/<ветка>`
   до fetch.
3. Восстановить ветку на сервере обычным push (если это fast-forward от испорченного
   состояния) или согласованным `--force-with-lease`.
4. Коллегам: `git fetch`, затем `git reset --keep origin/<ветка>` или `git rebase` своих
   локальных коммитов на восстановленную ветку.
5. Включить на сервере защиту ветки от принудительных пушей.

## Разбор того самого инцидента

Хронология, чтобы было понятно, где именно ошиблись:

1. В `develop` попал коммит с неудачной миграцией схемы. Его уже скачали три человека, а CI
   успел собрать образ.
2. Автор решил «убрать коммит, будто его не было»: `git reset --hard HEAD~1` и
   `git push --force`.
3. Коллеги сделали `git pull`. У двоих git молча создал merge-коммит, который вернул
   удалённую миграцию обратно; у третьего возник конфликт, и он разрешил его в пользу своей
   версии.
4. В итоге миграция оказалась в `develop` дважды с разными хешами, а пайплайн собрал образ из
   ветки, которой ни у кого не было локально.

Правильно было сделать один `git revert <хеш>` — обычный коммит, который все получили бы
fast-forward, без единого вопроса. После разбора мы запретили принудительный push во все общие
ветки на сервере, а в `git config` у всех включили `pull.ff only`, чтобы расхождение истории
было видно сразу, а не пряталось в автоматическом слиянии.

## Короткий алгоритм выбора

- Коммит ещё не отправлен, правки нужны → `git reset HEAD~1` (или `--soft`).
- Коммит ещё не отправлен, всё выбросить → `git reset --hard HEAD~1` (подумать дважды,
  лучше `--keep`).
- Нужно только поправить сообщение или дописать файл в последний коммит → `git commit --amend`.
- Коммит уже на сервере → `git revert <хеш>`.
- Отменить слияние на сервере → `git revert -m 1 <хеш>`.
- Одну незакоммиченную правку в файле → `git restore <файл>`.
