# cherry-pick диапазона коммитов: перенос исправлений в релизную ветку

У нас исправления сначала попадают в main, а потом переносятся в поддерживаемые релизные ветки
`release/3.x` и `release/2.x`. Переносим через cherry-pick. Здесь — всё, на чём мы спотыкались.

## Один коммит и диапазон

```bash
git switch release/3.x
git cherry-pick -x 5d1e0a2
```

Флаг `-x` дописывает в сообщение строку `(cherry picked from commit 5d1e0a2...)`. Потом по ней
легко понять, откуда пришло исправление; мы требуем `-x` для всех переносов.

Диапазон задаётся как в `git log`:

```bash
git cherry-pick A..B      # коммиты после A до B включительно; сам A НЕ входит
git cherry-pick A^..B     # от A до B включительно
```

Самая частая ошибка — написать `A..B` и потерять первый коммит. Перед переносом полезно
посмотреть, что именно попадёт: `git log --oneline A^..B`.

Если в диапазоне есть слияния, cherry-pick остановится с ошибкой
`is a merge but no -m option was given`. Либо пропустить их, либо указать `-m 1`, либо
перенести только коммиты фичи без merge-коммита.

## Конфликты

Перенос идёт по одному коммиту; при конфликте процесс останавливается:

```bash
# правим файлы
git add src/report.rs
git cherry-pick --continue
# или
git cherry-pick --skip     # пропустить текущий коммит
git cherry-pick --abort    # вернуться к исходному состоянию
```

`--no-commit` (`-n`) применяет изменения без создания коммитов — удобно, чтобы собрать
несколько исправлений в один коммит для релизной ветки.

## Что уже перенесено

Хеши при переносе меняются, поэтому сравнивать по ним бесполезно. Git умеет сравнивать по
содержимому патча:

```bash
git cherry -v release/3.x main          # «+» — ещё не перенесено, «-» — эквивалент уже есть
git log --cherry-pick --right-only --oneline release/3.x...main
```

## Когда cherry-pick — плохая идея

- Нужно перенести целую ветку из десятков коммитов. Тогда лучше `git rebase --onto`.
- Исправление зависит от рефакторинга, которого нет в старой ветке. Перенос пройдёт без
  конфликтов, но код не соберётся или будет работать иначе. Проверяем сборкой и тестами.
- Один и тот же коммит переносится в ветку, которую потом сольют обратно в main: появятся
  дубликаты изменений с разными хешами. Обычно git справляется, но история становится
  запутанной.
