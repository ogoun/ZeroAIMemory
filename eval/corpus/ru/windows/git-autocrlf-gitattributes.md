# Переводы строк в git: core.autocrlf, .gitattributes и нормализация

Эту заметку я держу как справочник для команды, где одни сидят на Windows, другие на Linux и
macOS, а CI собирает на обеих платформах. Цель — чтобы в репозитории лежал LF, у каждого в
рабочем каталоге было то, что нужно его инструментам, и чтобы diff не показывал «изменён
весь файл» из-за невидимых символов.

## Как git думает о переводах строк

У git есть два представления файла: в индексе (то, что уходит в коммит) и в рабочем
каталоге. Преобразование переводов строк происходит на границе между ними:

- при `git add` (рабочий каталог → индекс) CRLF может превращаться в LF;
- при checkout (индекс → рабочий каталог) LF может превращаться в CRLF.

Применяется это только к файлам, которые git считает текстовыми. Бинарные файлы не трогаются,
и именно поэтому важно, чтобы git правильно определял тип.

## core.autocrlf — настройка на машине

| Значение | При коммите | При checkout | Кому подходит |
|---|---|---|---|
| `true` | CRLF → LF | LF → CRLF | Windows, если всё окружение ждёт CRLF |
| `input` | CRLF → LF | ничего | Linux/macOS, Windows с редакторами, понимающими LF |
| `false` | ничего | ничего | когда всё решает `.gitattributes` |

Установщик Git for Windows по умолчанию предлагает `true`. Из-за этого shell-скрипты в
рабочем каталоге получают CRLF и ломаются в bash (см. заметку про CRLF в bash-скриптах).

Главный недостаток autocrlf — это настройка конкретного человека. Новый разработчик,
CI-агент или контейнер сборки получит другое поведение, и в репозиторий снова попадут CRLF.
Поэтому правило переводов строк должно жить в самом репозитории.

## .gitattributes — правило в репозитории

Минимальный рабочий вариант:

```
# автоопределение текста; в индексе всегда LF
* text=auto

# что должно иметь LF даже на Windows
*.sh   text eol=lf
*.bash text eol=lf
Makefile text eol=lf

# что должно иметь CRLF даже на Linux
*.bat text eol=crlf
*.cmd text eol=crlf
*.sln text eol=crlf

# точно бинарные
*.png binary
*.zip binary
*.onnx binary
```

Смысл атрибутов:

- `text=auto` — git сам решает, текст это или нет, и нормализует текст до LF в индексе;
  рабочая копия получает перевод строки по `core.eol` (по умолчанию `native`, на Windows —
  CRLF при включённом преобразовании).
- `text eol=lf` / `eol=crlf` — жёстко задаёт перевод строки в рабочем каталоге независимо
  от платформы и от `core.autocrlf`.
- `binary` — это `-text -diff`: не нормализовать и не показывать текстовый diff.
- `-text` — не трогать переводы строк, но diff оставить.

Атрибуты из `.gitattributes` имеют приоритет над `core.autocrlf`, поэтому при наличии
полного файла атрибутов личная настройка разработчика почти ни на что не влияет.

## Нормализация существующего репозитория

После добавления `.gitattributes` в старый репозиторий файлы в индексе остаются с CRLF, пока
их не перезапишут. Нормализовать одним коммитом:

```bash
git add --renormalize .
git status          # увидите файлы, у которых поменялись переводы строк
git commit -m "Нормализация переводов строк"
```

Чтобы рабочий каталог тоже обновился согласно новым правилам:

```bash
git rm --cached -r .
git reset --hard
```

Второй шаг уничтожает незакоммиченные правки — делать на чистом дереве.

Такой коммит лучше вынести отдельно и добавить его хеш в `.git-blame-ignore-revs`, чтобы
`git blame` не приписывал все строки автору нормализации.

## Диагностика

```bash
git ls-files --eol
```

Выводит по каждому файлу три колонки: `i/` — что в индексе (`lf`, `crlf`, `mixed`, `-text`),
`w/` — что в рабочем каталоге, `attr/` — какие атрибуты применились. Это самый быстрый
способ понять, кто виноват: индекс, рабочая копия или правило.

```bash
git check-attr -a -- scripts/deploy.sh
git config --show-origin --get core.autocrlf
```

Первая команда показывает итоговые атрибуты для файла, вторая — откуда пришла настройка
(системный, глобальный или локальный конфиг).

## Предупреждения, которые все видели

```
warning: in the working copy of 'src/app.ts', LF will be replaced by CRLF the next time Git touches it
```

Это не ошибка: git сообщает, что при следующем checkout файл получит CRLF из-за текущих
настроек. Если это нежелательно — значит, правило для этого типа файлов не задано.

`core.safecrlf=true` превращает необратимое преобразование (файл со смешанными
переводами строк) в ошибку при `git add`; `warn` — в предупреждение.

## Разбор частых ситуаций

### «Изменён весь файл», хотя я поменял одну строку

Редактор сохранил файл с другими переводами строк, чем лежат в рабочей копии, а для этого
типа файла нет правила. `git diff` показывает каждую строку удалённой и добавленной.
Проверка: `git diff --ignore-cr-at-eol` (или `-w`) показывает реальные правки. Лечение —
правило в `.gitattributes` плюс настройка редактора, а не `--ignore` в привычке.

### Бинарный файл испорчен после клонирования

Git принял файл за текст (например, дамп с длинными ASCII-участками или файл модели без
известного расширения) и при checkout вставил `\r` перед каждым байтом `0x0A`. Файл стал
длиннее и не открывается. Лечение — пометить расширение как `binary`, затем
`git rm --cached` по этому файлу и повторный checkout.

### Скрипт работает у меня и не работает на CI

На машине разработчика `core.autocrlf=input`, и скрипт лежит с LF. CI-агент на Windows
работает с умолчанием установщика `true` и получает CRLF. Симптомы — ошибки вида `$'\r'`
в bash. Правило `*.sh text eol=lf` убирает зависимость от настроек агента.

### bat-файл ведёт себя странно на Linux-сборке

Обратная ситуация: `.bat` с LF внутри. cmd в большинстве случаев переживает LF, но метки
(`goto`, `call :label`) иногда не находятся, если файл длиннее 512 байт и строки
заканчиваются на LF. Правило `*.bat text eol=crlf` закрывает вопрос.

## Чек-лист для нового репозитория

1. Сразу положить `.gitattributes` с `* text=auto` и явными `eol=lf` для скриптов.
2. Явно пометить бинарные форматы, которые git может принять за текст (модели, дампы).
3. Добавить `.editorconfig` с `end_of_line = lf`, чтобы редакторы не спорили с git.
4. В CI проверять, что в индексе нет CRLF: `git ls-files --eol | grep 'i/crlf'` должен
   ничего не выводить.
5. Не полагаться на `core.autocrlf` у участников: считать его значение неизвестным.

## Что запомнить

`core.autocrlf` — персональная настройка и источник хаоса; `.gitattributes` — договор
репозитория. Нормализация делается один раз, отдельным коммитом, через
`git add --renormalize .`. Для диагностики хватает `git ls-files --eol` и
`git check-attr`.
