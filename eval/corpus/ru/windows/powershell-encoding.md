# Кодировка в PowerShell: BOM, Out-File, Set-Content и $OutputEncoding

Кодировки в PowerShell ломаются в четырёх местах: как читается сам скрипт `.ps1`, в какой
кодировке пишутся файлы, как PowerShell передаёт текст внешним программам и как он
декодирует их вывод. Это четыре разные настройки, и путать их — главный источник
«кракозябр». Ниже — то, что я выяснил на Windows PowerShell 5.1 и PowerShell 7.

## 1. Чтение скрипта .ps1

Windows PowerShell 5.1 читает скрипт без BOM в системной ANSI-кодировке (для русской
локали — Windows-1251). Если скрипт сохранён в UTF-8 без BOM и в нём есть кириллица в
строках, она превратится в мусор, а иногда скрипт вообще не распарсится, потому что
кириллическая буква «съест» кавычку.

Правило: скрипты, которые могут запускаться в 5.1, сохраняем в **UTF-8 с BOM**. PowerShell 7
читает UTF-8 без BOM корректно, но BOM ему не мешает.

## 2. Запись файлов: `>`, Out-File, Set-Content

Самая неприятная часть — умолчания отличаются у разных командлетов и версий:

| Способ записи | Windows PowerShell 5.1 | PowerShell 7 |
|---|---|---|
| `>` и `>>` | UTF-16 LE с BOM | UTF-8 без BOM |
| `Out-File` | UTF-16 LE с BOM | UTF-8 без BOM |
| `Set-Content` / `Add-Content` | ANSI (системная кодовая страница) | UTF-8 без BOM |
| `-Encoding utf8` | UTF-8 **с** BOM | UTF-8 без BOM |
| `-Encoding utf8NoBOM` | нет такого значения | UTF-8 без BOM |

Типичный инцидент: в 5.1 сделали `git log > log.txt`, а потом Python-скрипт или `grep`
читает файл с нулевыми байтами через каждый символ — это UTF-16. Другой инцидент:
`Set-Content` записал конфиг с кириллицей в 1251, а сервис ждал UTF-8.

Как писать UTF-8 без BOM в 5.1, где такого значения нет:

```powershell
$utf8NoBom = New-Object System.Text.UTF8Encoding $false
[System.IO.File]::WriteAllText($path, $text, $utf8NoBom)
```

Чтобы не указывать кодировку каждый раз, можно задать значения по умолчанию в профиле:

```powershell
$PSDefaultParameterValues['Out-File:Encoding'] = 'utf8'
$PSDefaultParameterValues['Set-Content:Encoding'] = 'utf8'
```

В 5.1 это всё равно даст BOM, но хотя бы не UTF-16 и не ANSI.

## 3. Текст во внешние программы: $OutputEncoding

Переменная `$OutputEncoding` определяет, в какой кодировке PowerShell отдаёт строки в
стандартный ввод внешней программы при конвейере:

```powershell
"привет" | python -c "import sys; print(sys.stdin.read())"
```

В 5.1 по умолчанию это ASCII, и вся кириллица превращается в `?`. Исправление:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
```

## 4. Вывод внешних программ: [Console]::OutputEncoding

Обратное направление — как PowerShell декодирует байты, которые напечатала внешняя
программа (`git`, `cargo`, `node`). Здесь работает `[Console]::OutputEncoding`, по умолчанию
это OEM-кодовая страница консоли (866 для русской локали). Программа пишет UTF-8, PowerShell
читает как 866 — получаем «╨┐╤А╨╕╨▓╨╡╤В».

```powershell
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
```

Обычно я ставлю обе переменные в профиль (`$PROFILE`) одной строкой:

```powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
```

## 5. Чтение файлов: Get-Content

Чтение — зеркальная проблема. `Get-Content` в 5.1 без BOM считает файл ANSI-файлом, поэтому
UTF-8 без BOM с кириллицей читается с искажениями, а потом эти искажения записываются
обратно уже «навсегда». Явно указывать:

```powershell
Get-Content .\config.toml -Encoding UTF8 -Raw
```

`-Raw` возвращает одну строку вместо массива строк — удобно для поиска и замены по всему
файлу. В PowerShell 7 умолчание для чтения — UTF-8, BOM распознаётся автоматически.

Типичная «правка конфига на месте», которая ломает кодировку в 5.1:

```powershell
(Get-Content app.toml) -replace 'debug', 'info' | Set-Content app.toml
```

Здесь два умолчания сразу: чтение как ANSI и запись как ANSI. Если файл был в UTF-8,
кириллица в комментариях превращается в мусор. Правильно — указать `-Encoding UTF8` и там,
и там, а если BOM недопустим, писать через `[System.IO.File]::WriteAllText`.

## 6. Где именно запускается скрипт

Одна и та же команда даёт разный результат в зависимости от хоста:

- **Windows Terminal** и **VS Code** умеют показывать UTF-8, но кодировку процесса
  PowerShell не меняют — `[Console]::OutputEncoding` всё равно надо настроить.
- **PowerShell ISE** использует собственный хост, и `[Console]` там почти ни на что не
  влияет. ISE поддерживает только 5.1, для новых скриптов лучше не использовать.
- **Задание планировщика или служба** запускают `powershell.exe` без профиля пользователя
  (часто с `-NoProfile`), и настройки из `$PROFILE` не применяются. Кодировку нужно задавать
  в начале самого скрипта.
- **CI-агенты** перехватывают вывод через канал, а не консоль; результат зависит от того,
  как агент декодирует поток. Надёжнее явно ставить UTF-8 первой строкой скрипта.

## Глобальный вариант

В «Региональных стандартах» есть флажок «Бета-версия: использовать Юникод (UTF-8) для
поддержки языка во всем мире». Он переводит ANSI- и OEM-кодовые страницы системы на 65001.
Многие проблемы исчезают сразу, но старые программы, рассчитанные на 1251, начинают
показывать мусор. На рабочей машине включал, на машинах пользователей — не рекомендую.

## Как быстро понять, что сломалось

- Мусор вида `Ð¿Ñ€Ð¸Ð²ÐµÑ‚` — UTF-8, прочитанный как 1252/1251.
- Мусор вида `╨┐╤А╨╕` — UTF-8, прочитанный как 866: чинится `[Console]::OutputEncoding`.
- Знаки `?` вместо букв — текст прошёл через ASCII: проверить `$OutputEncoding`.
- Нулевые байты между символами, файл в два раза больше — UTF-16 от `>` или `Out-File` в 5.1.
- Посмотреть первые байты: `Format-Hex file.txt | Select-Object -First 1`. `EF BB BF` —
  BOM UTF-8, `FF FE` — UTF-16 LE.

## Перекодировать существующий файл

Файл, который уже записан в UTF-16 или ANSI, можно привести к UTF-8 без BOM так:

```powershell
$text = Get-Content .\log.txt -Raw            # BOM UTF-16 распознаётся автоматически
[System.IO.File]::WriteAllText((Resolve-Path .\log.txt), $text,
    [System.Text.UTF8Encoding]::new($false))
```

Для файла в 1251 без BOM в 5.1 достаточно `-Encoding Default` при чтении. Путь передаётся
через `Resolve-Path`, потому что методы .NET отсчитывают относительные пути от текущего
каталога процесса, а он не всегда совпадает с текущим каталогом сессии PowerShell.

## Итог

Для 5.1: скрипты — UTF-8 с BOM, запись — всегда с явным `-Encoding`, в профиле — обе
переменные консоли на UTF-8. В PowerShell 7 большинство проблем ушло, но про
`[Console]::OutputEncoding` для вывода внешних программ всё равно надо помнить.
