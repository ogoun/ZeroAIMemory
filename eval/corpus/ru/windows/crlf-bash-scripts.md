# CRLF в bash-скриптах: `$'\r': command not found`

Скрипт, который написали или сохранили на Windows, падает в Git Bash, WSL или на Linux-сервере
со странными ошибками:

```
deploy.sh: line 2: $'\r': command not found
deploy.sh: line 5: syntax error near unexpected token `$'do\r''
/bin/bash^M: bad interpreter: No such file or directory
```

Причина одна: строки файла заканчиваются на `\r\n` (CRLF), а bash считает концом строки только
`\n`. Символ `\r` остаётся частью последнего слова строки: пустая строка превращается в
команду `$'\r'`, `do` превращается в `do\r`, а в шебанге интерпретатор ищется по пути
`/bin/bash\r` — отсюда `^M` в сообщении `bad interpreter`.

## Как убедиться

```bash
file deploy.sh              # "... with CRLF line terminators"
cat -A deploy.sh | head     # в конце строк видно ^M$
grep -c $'\r' deploy.sh     # число строк с \r
```

## Как починить один файл

```bash
dos2unix deploy.sh
# если dos2unix нет:
sed -i 's/\r$//' deploy.sh
```

В VS Code достаточно щёлкнуть по `CRLF` в строке состояния, выбрать `LF` и сохранить.

## Откуда берётся снова и снова

Чаще всего виноват не редактор, а git на Windows: при `core.autocrlf=true` он при checkout
переписывает LF в CRLF, и скрипт портится уже в рабочем каталоге. Исправлять надо
правилом в репозитории, а не руками после каждого клона:

```
# .gitattributes
*.sh text eol=lf
```

Подробно про autocrlf и атрибуты — в отдельной заметке про переводы строк в git. Здесь
важно запомнить связку симптомов: `$'\r'`, `^M`, `bad interpreter` — это не ошибка
логики скрипта, а невидимый символ в конце строки.

## Грабли

- Heredoc внутри скрипта тоже получает `\r`, и в сгенерированный конфиг уезжают лишние
  символы — ошибка всплывает позже и в другом месте.
- Переменная, прочитанная через `read` из файла с CRLF, содержит хвостовой `\r`;
  сравнение `[ "$x" = "yes" ]` молча не срабатывает. Лечится `x=${x%$'\r'}`.
- `bash -n deploy.sh` (проверка синтаксиса) эту проблему не всегда ловит: синтаксис может
  оказаться корректным, а команда — другой.
