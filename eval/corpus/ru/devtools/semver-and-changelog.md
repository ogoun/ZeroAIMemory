# Семантическое версионирование и Keep a Changelog

Заметка для команды: как мы нумеруем релизы библиотек и сервисов и как ведём журнал изменений.
Появилась после того, как «минорное» обновление нашего клиента API сломало сборку трём
командам-потребителям.

## SemVer в двух словах

Версия `MAJOR.MINOR.PATCH`:

- **PATCH** (`1.4.2` → `1.4.3`) — исправления ошибок, публичный API не меняется;
- **MINOR** (`1.4.3` → `1.5.0`) — новая функциональность с обратной совместимостью; PATCH
  сбрасывается в 0;
- **MAJOR** (`1.5.0` → `2.0.0`) — несовместимые изменения публичного API; MINOR и PATCH
  сбрасываются.

Дополнительно:

- **pre-release** через дефис: `2.0.0-rc.1`, `2.0.0-beta.3`. Такая версия *ниже* релизной:
  `2.0.0-rc.1 < 2.0.0`. Сравнение идентификаторов — по точкам, числовые части численно:
  `rc.2 < rc.10`.
- **метаданные сборки** через плюс: `1.4.2+build.517`. При сравнении версий игнорируются.
- **Нулевая мажорная** `0.y.z` — начальная разработка, API может меняться в любой момент.
  На практике большинство пакетных менеджеров трактуют `0.MINOR` как мажорную: каретка в
  npm `^0.4.1` не пустит `0.5.0`, Cargo ведёт себя так же.

### Что такое «публичный API»

Спецификация требует его явно объявить, иначе версии ничего не значат. Мы записали в README
каждой библиотеки, что входит:

- экспортируемые функции, классы и их сигнатуры;
- формат конфигурационного файла и переменных окружения;
- формат вывода CLI, если его парсят скрипты;
- минимальная поддерживаемая версия рантайма.

Последний пункт — частая причина спора. Мы решили: **поднятие минимальной версии рантайма —
мажорное изменение**. Пользователь на старом рантайме после `^`-обновления получит неработающий
пакет, это ровно та несовместимость, от которой SemVer должен защищать.

### Пограничные случаи

| Изменение | Наше решение | Почему |
|-----------|--------------|--------|
| Исправили баг, на который кто-то опирался | PATCH, но с заметкой в журнале | Поведение было ошибочным по документации |
| Добавили необязательный параметр | MINOR | Старые вызовы работают |
| Добавили метод в интерфейс, который реализуют пользователи | MAJOR | Их реализации перестанут компилироваться |
| Пометили функцию устаревшей | MINOR | Работает, но даёт предупреждение |
| Удалили устаревшую функцию | MAJOR | Даже если предупреждали год |
| Обновили зависимость с её мажорной сменой, тип из неё торчит в нашем API | MAJOR | Типы пользователей поменяются |

### Ошибки, которые мы делали

- Выпустили несовместимость в MINOR. Правильная реакция по спецификации: выпустить новый
  MINOR, который возвращает совместимость, и уже потом MAJOR с изменением. Опубликованную
  версию не перезаписывать никогда — только новая версия (в npm ещё и `npm deprecate` на
  сломанную).
- Боялись поднимать мажорную и копили изменения в `0.x` три года. Если пакетом пользуются в
  продакшене, пора `1.0.0`.

## Keep a Changelog

Журнал изменений пишется для людей, а не для машин. Список коммитов — не журнал: в нём
«поправил опечатку» соседствует с изменением формата данных.

### Формат

Файл `CHANGELOG.md` в корне:

```markdown
# Changelog

All notable changes to this project will be documented in this file.
The format is based on Keep a Changelog, and this project adheres to Semantic Versioning.

## [Unreleased]

### Added
- Параметр `timeout` у `Client.fetch`.

## [1.5.0] - 2024-03-18

### Added
- Повторы с экспоненциальной задержкой.

### Deprecated
- `Client.get_raw`, будет удалён в 2.0.0.

### Fixed
- Утечка соединений при отмене запроса.

[Unreleased]: https://example.com/compare/v1.5.0...HEAD
[1.5.0]: https://example.com/compare/v1.4.3...v1.5.0
```

Правила формата:

- новые версии сверху, даты в ISO 8601 (`ГГГГ-ММ-ДД`);
- раздел `[Unreleased]` всегда есть; при релизе его содержимое переносится под новый номер;
- группы строго из списка: **Added, Changed, Deprecated, Removed, Fixed, Security**;
- каждая версия — ссылка на сравнение в системе контроля версий;
- отозванный релиз помечается `[YANKED]`.

### Как пишем записи

- Запись добавляется в `[Unreleased]` в том же PR, что и изменение. Ревьюер проверяет её
  наравне с тестами.
- Формулировка — с точки зрения пользователя: «Добавлен параметр timeout», а не
  «Отрефакторил HttpLayer».
- Для MAJOR — раздел миграции: что было, что стало, как переписать вызов.
- Внутренние изменения (рефакторинг, CI) в журнал не попадают.

## Автоматизация

Две школы, обе рабочие:

1. **Из истории коммитов.** Сообщения в формате Conventional Commits, инструмент
   (release-please, semantic-release, git-cliff) сам считает следующую версию и собирает
   раздел журнала. Плюс — ничего не забывается. Минус — качество журнала равно качеству
   сообщений коммитов.
2. **Фрагменты изменений.** Каждый PR кладёт маленький файл в `changes/` (towncrier, changesets),
   при релизе они склеиваются. Плюс — текст пишется осознанно, нет конфликтов слияния в
   `CHANGELOG.md`. Минус — ещё один файл в каждом PR.

Мы для библиотек используем changesets: в файле фрагмента автор явно указывает тип
изменения (major/minor/patch), и спор о номере версии происходит на ревью, а не после релиза.

## Версии в монорепозитории

Когда в одном репозитории лежит десяток пакетов, возникает выбор:

- **Единая версия** (fixed/locked): все пакеты выпускаются вместе с одним номером, как в
  Angular или Babel. Просто объяснить пользователям, но патч в одном пакете поднимает номер
  у всех, и номер перестаёт что-то сообщать о конкретном пакете.
- **Независимые версии**: каждый пакет версионируется сам. Честнее, но нужно следить за
  внутренними зависимостями: если `core` получил MAJOR, все пакеты, которые реэкспортируют
  его типы, тоже получают MAJOR, а остальные зависимые — хотя бы PATCH с обновлённым
  диапазоном.

Мы используем независимые версии; changesets сам поднимает зависимые пакеты внутри
репозитория. Теги ставятся с префиксом пакета: `core@2.0.0`, `client@1.6.0`, а журнал
изменений — отдельный файл в каталоге каждого пакета.

## Версии сервисов

Для развёртываемых сервисов, у которых нет потребителей-библиотек, SemVer менее полезен:
мажорная версия у веб-сервиса мало что значит, совместимость обеспечивается версией API
(`/v2/`) и контрактными тестами. Там мы используем календарную схему `2024.03.18.1` и тот
же формат журнала — он нужен поддержке и эксплуатации, чтобы понимать, что приехало в
продакшен.

## Релизный чек-лист

1. Перенести `[Unreleased]` под новый номер, поставить дату.
2. Поднять версию в манифесте пакета.
3. Тег `vX.Y.Z` на релизный коммит, аннотированный.
4. Опубликовать артефакты из CI по тегу, не с ноутбука.
5. Проверить установку опубликованной версии в чистом окружении.
