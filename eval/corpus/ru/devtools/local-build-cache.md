# Кэш сборки на рабочей машине: ccache, tsbuildinfo, webpack

Не путать с кэшем CI. Кэш в CI (actions/cache и аналоги) переносит скачанные зависимости между
запусками на чистых раннерах. Кэш сборки — это когда сам компилятор или сборщик запоминает
результаты по хешу входов и не повторяет работу, если входы не изменились. Он полезен прежде
всего локально, хотя его тоже можно класть в кэш CI.

## ccache для C и C++

ccache оборачивает компилятор: считает хеш препроцессированного исходника, флагов и версии
компилятора; при совпадении отдаёт готовый объектный файл.

```bash
# CMake
cmake -B out -DCMAKE_C_COMPILER_LAUNCHER=ccache -DCMAKE_CXX_COMPILER_LAUNCHER=ccache
ccache -s          # статистика попаданий
ccache -M 20G      # предел размера
```

Грабли: макросы `__DATE__`/`__TIME__` и абсолютные пути в отладочной информации ломают
попадания между разными каталогами. Помогают `CCACHE_BASEDIR` и опция `sloppiness`.

## TypeScript: incremental

```json
{ "compilerOptions": { "incremental": true, "tsBuildInfoFile": ".cache/tsbuildinfo" } }
```

`tsc` сохраняет граф модулей и сигнатуры; следующий запуск перепроверяет только изменённое и
зависящее от него. В монорепозитории с project references — `tsc -b`. Если после смены
версии TypeScript появились странные ошибки, удалить `.tsbuildinfo`.

## webpack 5: persistent cache

```js
module.exports = {
  cache: {
    type: "filesystem",
    buildDependencies: { config: [__filename] },
  },
};
```

`buildDependencies` обязательно: без него изменение конфигурации не инвалидирует кэш, и
сборщик отдаёт устаревший результат. Кэш лежит в `node_modules/.cache/webpack`.

## Когда кэш сборки вредит

- нестабильные ключи (время, случайные значения в генерируемом исходнике) — ноль попаданий,
  только трата диска;
- слишком широкие ключи — кэш отдаёт результат для других флагов, ошибки «чинятся» удалением
  каталога. Правило: любое подозрение — сначала сборка с чистым кэшем, потом разбор.
