# Квантование int8: динамическое, статическое, per-channel, SmoothQuant

Конспект по квантованию трансформеров-энкодеров в int8 для CPU-инференса: что существует, как работает, где теряется точность и как это мерить.

## Базовое отображение

Аффинное квантование переводит вещественное `x` в целое `q`:

```
q = clamp( round(x / scale) + zero_point, qmin, qmax )
x ≈ (q − zero_point) · scale
```

- **Симметричное**: `zero_point = 0`, диапазон `[−127, 127]`, `scale = max|x| / 127`. Удобно для весов: распределения примерно симметричны вокруг нуля.
- **Асимметричное**: `zero_point ≠ 0`, `uint8 [0, 255]`, диапазон `[min, max]` отображается целиком. Подходит для активаций после ReLU/GELU, у которых сдвинутое распределение.

Ошибка округления — до `scale/2` на элемент. Чем шире диапазон (выбросы), тем больше `scale` и тем грубее сетка для «обычных» значений. Почти все проблемы точности int8 — это проблемы выбросов.

## Гранулярность

- **per-tensor** — один `scale` на весь тензор весов;
- **per-channel** — свой `scale` на каждый выходной канал (строку матрицы весов). Для линейных слоёв трансформера это почти всегда заметно лучше: нормы строк различаются в разы.
- **per-group / block-wise** — `scale` на группу из 32–128 элементов; используется в 4-битных схемах для LLM, для int8 энкодеров обычно избыточно.

## Динамическое квантование

Веса квантуются заранее, офлайн. Активации — во время выполнения: для каждого входа считается свой диапазон, `scale` и `zero_point` вычисляются на лету, затем умножение идёт в целых, результат деквантуется.

В ONNX Runtime:

```python
from onnxruntime.quantization import quantize_dynamic, QuantType

quantize_dynamic(
    model_input="model.onnx",
    model_output="model.int8.onnx",
    weight_type=QuantType.QInt8,
    per_channel=True,
)
```

Плюсы: не нужны калибровочные данные, точность для энкодеров BERT/XLM-R обычно хорошая. Минусы: накладные расходы на вычисление диапазонов при каждом вызове; ускорение затрагивает в основном MatMul/Gemm, остальное остаётся во float.

## Статическое квантование

Диапазоны активаций определяются заранее по калибровочному набору: модель прогоняется на нескольких сотнях типичных входов, собираются статистики (MinMax, энтропийная, перцентильная), фиксируются `scale` и `zero_point`. В рантайме пересчёта нет.

```python
from onnxruntime.quantization import quantize_static, CalibrationDataReader, QuantFormat

quantize_static(
    "model.onnx", "model.qdq.onnx",
    calibration_data_reader=my_reader,   # отдаёт словари входов
    quant_format=QuantFormat.QDQ,
    per_channel=True,
)
```

Плюсы: быстрее динамического, квантуются и другие операторы. Минусы: качество зависит от калибровочных данных; если в продакшене длины и тематика входов другие, диапазоны неверны. Для трансформеров статическое квантование активаций чаще портит точность, чем динамическое.

Форматы: **QDQ** (пары QuantizeLinear/DequantizeLinear вокруг операторов, провайдер сам решает, что сливать) и **QOperator** (специальные операторы `QLinearMatMul` и т. п.). QDQ переносимее между провайдерами.

## Почему трансформеры квантуются плохо: выбросы

В активациях больших трансформеров есть немногие каналы с величинами в десятки–сотни раз больше остальных (Dettmers и др., LLM.int8(), 2022). Если квантовать per-tensor, весь бюджет int8 уходит на эти каналы. Для энкодеров размера BERT-base эффект слабее, но у моделей на основе XLM-R large уже заметен.

## SmoothQuant

Xiao и др. (2022) предложили перенести трудность квантования с активаций на веса. Для линейного слоя `Y = X·W` вводится поканальный множитель `s`:

```
Y = (X · diag(s)^−1) · (diag(s) · W)
s_j = max|X_j|^α / max|W_j|^(1−α)
```

Выбросы в активациях делятся на `s_j`, соответствующие строки весов умножаются; произведение математически не меняется. `α` около 0.5 балансирует трудность; для моделей с сильными выбросами берут больше. Множители вносятся в веса заранее, рантайм не меняется, после чего можно делать W8A8 статическое квантование.

## Как мерить потерю точности

Для моделей эмбеддингов недостаточно смотреть на «похожесть» векторов, но начинать стоит с неё:

1. Косинус между fp32- и int8-эмбеддингами на нескольких тысячах текстов: среднее, минимум, 1-й перцентиль. Значения выше 0.99 в среднем — типичны для удачного квантования, хвост ниже 0.95 — тревожный сигнал.
2. Совпадение топ-k: доля общих документов в топ-10 у fp32 и int8 на одних запросах.
3. Метрики поиска на размеченных запросах (recall@k, nDCG@10) — единственное, что действительно важно. Сравнивать парным бутстрепом: разница в 0.5 пункта на 100 запросах обычно не значима.

Ориентир из опубликованных отчётов и своих прогонов: динамическое int8 per-channel для энкодеров размера base–large даёт потерю в пределах 1 пункта nDCG и ускорение на CPU в 1.5–3 раза; размер модели уменьшается примерно в 4 раза. Это ориентир, не гарантия.

## Порядок работы на практике

1. Экспортировать модель в ONNX с динамическими осями по батчу и длине последовательности; проверить, что выходы совпадают с исходным фреймворком (максимальная абсолютная разность порядка 1e-5).
2. Прогнать оптимизатор графа для трансформеров и сохранить оптимизированную fp32-модель — она же эталон.
3. Сделать динамическое int8 per-channel. Это базовый вариант, с которого стоит начинать: он почти всегда работает с первого раза.
4. Посчитать косинусы fp32/int8 и метрики поиска на размеченных запросах; записать задержку на батче 1 и на типичном батче индексации.
5. Только если ускорения не хватает — пробовать статическое квантование с калибровкой на реальных текстах, исключая чувствительные узлы (часто это последние слои и выходная проекция).
6. Если статическое теряет точность из-за выбросов — SmoothQuant или исключение отдельных MatMul из квантования.

Каждый вариант фиксировать в таблице: формат, гранулярность, исключённые узлы, размер файла, задержка, метрики с интервалами. Без такой таблицы через месяц невозможно вспомнить, почему выбран именно этот файл модели.

| Вариант | Размер | Задержка CPU | Риск точности |
|---|---|---|---|
| fp32 | 1× | 1× | эталон |
| int8 динамическое per-channel | ≈0.25× | 0.35–0.7× | низкий |
| int8 статическое QDQ | ≈0.25× | 0.3–0.6× | средний |
| int8 статическое + SmoothQuant | ≈0.25× | 0.3–0.6× | ниже, чем без него |

Значения в таблице — порядок величин из чтения и собственных прогонов, не замер.

## Грабли

- `reduce_range`: на старых CPU без VNNI инструкции AVX2 могут насыщаться при 8-битных весах; ONNX Runtime предлагает квантовать веса в 7 бит. На современных процессорах с VNNI не нужно.
- Квантованная модель на GPU-провайдере может работать медленнее fp16: целочисленные ядра есть не для всех операторов, появляются лишние преобразования.
- Перед квантованием полезно прогнать оптимизатор графа (слияние LayerNorm, Attention): квантование слитых операторов даёт другое ускорение.
- Слой эмбеддингов (Gather) квантовать обычно не стоит: экономия памяти есть, ускорения нет, а точность на редких токенах падает.

## Открытые вопросы

- Даёт ли SmoothQuant выигрыш для энкодеров размера large при статическом квантовании, или динамического достаточно.
- fp16 на GPU против int8 на CPU: где точка перелома по задержке для батча 1.
