# Метрики информационного поиска: recall@k, MRR, nDCG

Шпаргалка с формулами, разобранными примерами и типичными ошибками при подсчёте. Писал, когда несколько раз подряд получил «разные nDCG» у одного и того же прогона из-за разных соглашений.

## Обозначения

- Для запроса `q` система возвращает ранжированный список документов `d_1, d_2, …`.
- `rel(d)` — оценка релевантности: бинарная (0/1) или градуированная (0–3).
- `R(q)` — множество всех релевантных документов для запроса по разметке.
- Итоговая метрика — среднее по запросам (макроусреднение).

## Precision@k и Recall@k

```
P@k = |релевантные среди первых k| / k
R@k = |релевантные среди первых k| / |R(q)|
```

Recall@k отвечает на вопрос «нашлось ли то, что нужно, в первых k». Порядок внутри k не важен. Это главная метрика для этапа отбора кандидатов: если дальше работает реранкер на 50 кандидатах, важен recall@50.

Грабли:

- Если у запроса одна релевантная заметка, R@k — это просто «есть ли она в топ-k» (0 или 1).
- Если у запроса пять релевантных, а k = 3, максимум R@3 = 0.6. Некоторые библиотеки нормируют на `min(k, |R|)` — это уже другая метрика; в отчёте надо писать, какая.

## MRR (Mean Reciprocal Rank)

```
RR(q) = 1 / позиция первого релевантного документа   (0, если его нет в пределах k)
MRR@k = среднее RR(q) по запросам
```

MRR смотрит только на первый релевантный результат. Подходит для сценария «нужен один правильный ответ» — поиск по заметкам агентом, навигация. Пример: позиции первого релевантного у трёх запросов 1, 3, нет в топ-10 → MRR@10 = (1 + 0.333 + 0) / 3 ≈ 0.444.

## nDCG@k

Учитывает и градации, и позиции всех релевантных:

```
DCG@k  = Σ_{i=1..k}  gain(rel_i) / log2(i + 1)
nDCG@k = DCG@k / IDCG@k
```

`IDCG@k` — DCG идеального упорядочивания (все релевантные сверху, по убыванию оценки). Две распространённые формы выигрыша:

- линейная: `gain = rel`;
- экспоненциальная: `gain = 2^rel − 1` (сильнее награждает высокие оценки, принята в TREC-скриптах и многих библиотеках).

При бинарной разметке обе формы совпадают.

### Разобранный пример

Бинарная релевантность, у запроса две релевантные заметки, система поставила их на позиции 1 и 4:

| Позиция i | rel | log2(i+1) | вклад |
|---|---|---|---|
| 1 | 1 | 1.000 | 1.000 |
| 2 | 0 | 1.585 | 0 |
| 3 | 0 | 2.000 | 0 |
| 4 | 1 | 2.322 | 0.431 |

`DCG@10 = 1.431`. Идеал — позиции 1 и 2: `IDCG@10 = 1 + 1/1.585 = 1.631`. `nDCG@10 ≈ 0.877`.

Если бы обе стояли на 1 и 2 — 1.0; если только одна на позиции 1, а вторая за пределами топ-10 — `1/1.631 ≈ 0.613`.

## Какую метрику выбирать

| Вопрос | Метрика |
|---|---|
| Попадёт ли нужное в окно кандидатов для реранкера или LLM | Recall@k (k = размер окна) |
| Насколько быстро пользователь или агент увидит первый верный ответ | MRR@10 |
| Насколько хорош весь порядок, в том числе при нескольких релевантных | nDCG@10 |
| Насколько точна выдача (мало шума) | Precision@k |

На практике отчёт содержит минимум recall@k для этапа кандидатов и nDCG@10 или MRR@10 для финального порядка. Метрики сильно коррелируют, но не одинаковы: изменение, поднимающее recall@50, может слегка опустить nDCG@10, если в верх списка попадает больше шума.

## Типичные ошибки подсчёта

1. **Дубликаты в выдаче.** Если система возвращает фрагменты, а релевантность размечена на уровне документов, одна заметка может встретиться трижды. Нужно схлопывать до документа (оставлять лучшую позицию) до подсчёта, иначе DCG завышается.
2. **Неразмеченные релевантные.** Документ, отвечающий на запрос, но не попавший в разметку, считается нерелевантным. Метрика занижена, причём сильнее у лучшей системы, которая находит «неожиданные» ответы. Лечится пулингом: просмотром объединённых топов нескольких систем.
3. **Нули при пустой выдаче.** Запрос, на который система ничего не вернула, должен входить в среднее с нулём, а не выпадать.
4. **Ничьи.** При равных баллах порядок произволен; без детерминированного разрешения (например, по идентификатору) метрика скачет между прогонами.
5. **Разные k.** MRR без отсечения и MRR@10 — разные числа.

## Мини-реализация

Чтобы не зависеть от соглашений библиотек, держу короткую проверочную реализацию для бинарной разметки:

```python
import math

def metrics(ranked, relevant, k=10):
    """ranked — список id документов без повторов, relevant — множество id."""
    top = ranked[:k]
    hits = [1 if d in relevant else 0 for d in top]
    recall = sum(hits) / len(relevant) if relevant else 0.0
    rr = next((1 / (i + 1) for i, h in enumerate(hits) if h), 0.0)
    dcg = sum(h / math.log2(i + 2) for i, h in enumerate(hits))
    ideal = sum(1 / math.log2(i + 2) for i in range(min(k, len(relevant))))
    ndcg = dcg / ideal if ideal else 0.0
    return recall, rr, ndcg
```

Сверяю с ней любую библиотеку на десятке вручную посчитанных запросов, прежде чем доверять числам.

## Макро- и микроусреднение

Стандарт — макроусреднение: метрика считается для каждого запроса, затем берётся среднее. Каждый запрос весит одинаково. Микроусреднение (суммировать попадания по всем запросам и делить на сумму релевантных) даёт больший вес запросам с многими релевантными документами и в IR почти не используется. Если запросы делятся на группы (перефразы, идентификаторы, кросс-языковые), полезно публиковать средние по группам отдельно: общее среднее скрывает, что один вид запросов улучшился, а другой просел.

## Статистика

Средние по 50–200 запросам шумные. Разницу между системами нужно сопровождать доверительным интервалом (бутстреп по запросам) или парным тестом — подробности в отдельной заметке про бутстреп. Без этого изменение nDCG@10 на 0.01 ничего не значит.

## Открытые вопросы

- Стоит ли переходить на градуированную разметку (0/1/2) — она дороже, но лучше различает «отвечает частично» и «отвечает полностью».
- Как учитывать запросы, на которые правильный ответ — «ничего не найдено».
