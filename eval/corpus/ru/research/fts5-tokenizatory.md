# Токенизаторы SQLite FTS5: unicode61, porter, trigram

Сравнительный разбор встроенных токенизаторов FTS5 с точки зрения полнотекстового поиска по смешанному русско-английскому тексту с идентификаторами из кода. Цель — понять, что каждый из них делает с текстом, какие запросы после этого находятся, а какие нет, и сколько это стоит по размеру индекса.

## Как токенизатор участвует в поиске

Токенизатор вызывается дважды: при вставке документа (текст разбивается на токены, которые попадают в инвертированный индекс) и при разборе запроса `MATCH` (строка запроса проходит через тот же токенизатор). Совпадение — это равенство токенов после нормализации. Отсюда главное правило: всё, что токенизатор «склеил» или «потерял» при индексации, нельзя найти никаким запросом.

Токенизатор задаётся при создании таблицы и потом не меняется без пересоздания:

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(
    title, body,
    tokenize = "unicode61 remove_diacritics 2 tokenchars '_'"
);
```

## unicode61 — токенизатор по умолчанию

Делит текст по классам символов Unicode: буквы и цифры образуют токены, всё остальное (пробелы, знаки препинания) — разделители. Регистр приводится к нижнему по таблицам Unicode, то есть «Поиск» и «поиск» совпадают, кириллица обрабатывается так же, как латиница.

Опции:

| Опция | Значения | Что делает |
|---|---|---|
| `remove_diacritics` | 0, 1, 2 | 0 — не трогать, 1 — снимать диакритику (кроме некоторых составных случаев), 2 — снимать корректно во всех случаях; по умолчанию 1 |
| `tokenchars` | строка символов | дополнительные символы, которые считаются частью токена |
| `separators` | строка символов | дополнительные символы-разделители |
| `categories` | список категорий Unicode | какие категории считать символами токена (появилось в 3.25) |

Практические следствия:

- `split_at_mut` по умолчанию превращается в три токена `split`, `at`, `mut`. Запрос `split_at_mut` разобьётся так же и найдёт документ как фразу, но найдёт и текст «split ... at ... mut» в другом порядке, если запрос не взят в кавычки. С `tokenchars '_'` идентификатор станет одним токеном, но тогда запрос `split` его уже не найдёт.
- Флаги вида `--force-with-lease` дробятся по дефисам. Дефис внутри запроса без кавычек FTS5 воспринимает как синтаксис, поэтому такие строки нужно экранировать двойными кавычками.
- «ё» в Unicode раскладывается как «е» + умляут, но объединяет ли их `remove_diacritics`, зависит от таблиц конкретной версии SQLite. Не рассуждать, а проверять запросом на своей сборке; надёжнее нормализовать «ё» → «е» до вставки и в запросе.

## porter — стемминг поверх другого токенизатора

`porter` — обёртка: `tokenize = 'porter unicode61'`. Сначала работает внутренний токенизатор, затем к каждому токену применяется английский стеммер Портера: `connections`, `connected`, `connecting` сводятся к `connect`.

Плюсы: заметно растёт полнота для английских запросов в свободной форме. Минусы:

- Стеммер только английский. Русские слова проходят без изменений — «индексация» и «индексации» остаются разными токенами.
- Стеммер иногда склеивает разные по смыслу слова (`university` и `universe` → `univers`), точность падает.
- Идентификаторы тоже стеммятся: `tokens` и `token` совпадут, что для кода обычно нормально, но `process` и `processing` перестают различаться.

Для русского языка во FTS5 встроенного стеммера нет. Варианты: собственный токенизатор через C API (`fts5_tokenizer`) со Snowball-стеммером, префиксные запросы `индекс*` или лемматизация текста до вставки в отдельный столбец.

## trigram — подстроки

Появился в SQLite 3.34.0. Каждая последовательность из трёх символов — отдельный токен: «поиск» → «пои», «оис», «иск». Это позволяет:

- искать подстроки внутри слов и идентификаторов: `MATCH 'at_mu'` найдёт `split_at_mut`;
- использовать индекс для `LIKE '%...%'` и `GLOB` (оптимизатор переписывает их в обращение к FTS5-таблице);
- не думать о морфологии: общий корень даёт общие триграммы.

Ограничения:

- Запросы короче трёх символов индексом не обслуживаются.
- Опция `case_sensitive 0|1` (по умолчанию 0 — регистр не важен); `remove_diacritics` для trigram добавили позже, в 3.45.
- Индекс заметно больше: число токенов примерно равно числу символов. На моих текстах база выросла примерно в 3–4 раза по сравнению с unicode61; цифра сильно зависит от данных.
- BM25 по триграммам ранжирует хуже: частые триграммы («ени», «ова») имеют низкий IDF, но их много, и короткие документы с удачным набором триграмм поднимаются выше осмысленных.

## Запросы и экранирование

Строка после `MATCH` — это мини-язык, а не просто текст. Что важно помнить при генерации запросов программно:

- Слова через пробел объединяются неявным `AND`. Есть `OR`, `NOT`, `NEAR(a b, 5)` и фильтр по столбцу `title : поиск`.
- Фраза в двойных кавычках требует токены подряд и в том же порядке.
- `*` в конце слова — префиксный запрос: `индекс*` найдёт «индексация», «индексы». Без префиксного индекса (`prefix='2 3'`) такой запрос медленнее, но работает.
- Символы `-`, `:`, `(`, `)`, `^` и одиночные кавычки внутри пользовательского ввода ломают разбор или меняют смысл. Самый надёжный способ — разбить ввод на слова самостоятельно и каждое обернуть в двойные кавычки (удвоив внутренние кавычки), затем соединить через пробел или `OR`.
- Пустой запрос и запрос только из разделителей дают ошибку разбора, их надо отсекать до обращения к базе.

```sql
SELECT rowid, bm25(notes_fts, 5.0, 1.0) AS score,
       snippet(notes_fts, 1, '[', ']', '…', 12)
FROM notes_fts
WHERE notes_fts MATCH '"split_at_mut" OR "заимствование"'
ORDER BY score
LIMIT 20;
```

Здесь `bm25` получает веса столбцов (заголовок весит в пять раз больше тела), а `snippet` возвращает фрагмент тела с подсвеченными совпадениями. Сортировка по возрастанию, потому что у `bm25()` лучшие совпадения отрицательнее.

## Как я сравнивал

Небольшой набор из нескольких десятков запросов трёх типов (свободный русский текст, английский текст, идентификаторы из кода) прогонялся по трём копиям одной таблицы с разными токенизаторами. Смотрел, найдена ли нужная заметка в первой десятке. Набор маленький, поэтому выводы ниже качественные, а не количественные.

| Задача | unicode61 | porter unicode61 | trigram |

## Вывод для себя

Один токенизатор не закрывает все случаи. Разумная схема — две FTS5-таблицы над одними данными: `unicode61` (или `porter unicode61`) для ранжирования и `trigram` как запасной путь для подстрок и коротких фрагментов кода, с объединением результатов. Альтернатива — `detail=column` или `detail=none` для экономии места на триграммной таблице, если фразовые запросы по ней не нужны.

Открытые вопросы:

2. Стоит ли писать свой токенизатор со Snowball ради русского или это перекрывается векторным поиском.
