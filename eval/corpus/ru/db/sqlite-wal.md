# SQLite в режиме WAL: что меняется и о чём помнить

Включаем почти всегда для серверных приложений на SQLite:

```sql
PRAGMA journal_mode = WAL;     -- сохраняется в файле базы, достаточно один раз
PRAGMA synchronous = NORMAL;   -- в WAL безопасно для целостности, быстрее FULL
```

## Как работает

В режиме по умолчанию (rollback journal, `DELETE`) запись блокирует всю базу и для
читателей. В WAL изменения дописываются в отдельный файл `база.db-wal`, а основной файл
не трогается до контрольной точки (checkpoint). Итог:

- читатели не блокируют писателя и писатель не блокирует читателей;
- каждый читатель видит снимок на момент начала своей транзакции;
- писатель по-прежнему один — две одновременные записи всё равно упорядочиваются.

Рядом появляются файлы `-wal` и `-shm` (разделяемая память с индексом WAL). Копировать
базу во время работы простым `cp` одного `.db` нельзя — свежие данные могут быть только в
`-wal`. Для копии использовать `VACUUM INTO 'backup.db'` или online backup API
(`sqlite3 app.db ".backup backup.db"`).

## Контрольные точки и рост файла WAL

По умолчанию автоматический checkpoint запускается, когда WAL достигает 1000 страниц
(`PRAGMA wal_autocheckpoint`). Но checkpoint не может перенести страницы, которые ещё нужны
какому-то открытому читателю. Если в приложении есть долгая транзакция чтения (например,
забытый открытый курсор или итератор), WAL растёт без ограничений — у нас он однажды
дорос до 6 ГБ при базе на 300 МБ.

Что помогает:

- не держать транзакции чтения открытыми дольше нужного;
- периодически `PRAGMA wal_checkpoint(TRUNCATE);` в спокойный момент — переносит всё и
  обрезает файл до нуля;
- `PRAGMA journal_size_limit` — ограничивает размер, до которого обрезается WAL после
  checkpoint.

## Ограничения

- WAL не работает на сетевых файловых системах (NFS, SMB): нужна общая память между
  процессами на одной машине.
- Все процессы, работающие с базой, должны быть на одном хосте.
- Режим только для чтения требует доступа на запись к `-shm` или заранее существующих файлов.

Конфликты записи в WAL всё равно возможны — для них нужен `busy_timeout`, это отдельная заметка.
Место после массового удаления WAL не возвращает — это задача VACUUM.
