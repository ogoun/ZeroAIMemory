# SQLite: почему файл не уменьшается после DELETE и что делать с VACUUM

Удалили 80 % строк из таблицы событий, а файл базы остался 12 ГБ. Это нормально: SQLite
помечает освободившиеся страницы как свободные (freelist) и переиспользует их под новые
данные, но файлу их не возвращает.

Посмотреть, сколько свободного места:

```sql
PRAGMA page_count;
PRAGMA freelist_count;
PRAGMA page_size;
```

`freelist_count * page_size` — столько байт можно вернуть.

## VACUUM

`VACUUM` пересобирает базу целиком в новый временный файл и подменяет им старый. Плюсы:
файл сжимается, страницы таблиц и индексов идут подряд (меньше фрагментации). Минусы:

- нужно свободное место до двух размеров базы (временная копия плюс журнал);
- на всё время работы берётся эксклюзивная блокировка, запись невозможна;
- на больших базах — минуты и десятки минут;
- может поменять `rowid` у таблиц без явного `INTEGER PRIMARY KEY`.

`VACUUM INTO 'compact.db'` пишет сжатую копию в новый файл и не трогает исходный — удобно
для бэкапа и для обслуживания без остановки: собрать копию, потом подменить в окно.

## auto_vacuum

```sql
PRAGMA auto_vacuum = INCREMENTAL;  -- для существующей базы вступит в силу только после VACUUM
VACUUM;
-- потом периодически:
PRAGMA incremental_vacuum(1000);    -- вернуть до 1000 свободных страниц
```

- `FULL` — после каждой транзакции свободные страницы переносятся в конец и файл обрезается.
  Не дефрагментирует, а наоборот, усиливает фрагментацию; лишняя работа на каждый коммит.
- `INCREMENTAL` — место возвращается только по явному вызову `incremental_vacuum`. Наш выбор
  для баз с периодической чисткой старых данных.

Поменять `auto_vacuum` с `NONE` на другое значение у существующей базы можно только с
последующим полным `VACUUM`.
