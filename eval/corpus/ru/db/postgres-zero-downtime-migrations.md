# Миграции PostgreSQL без простоя

Набор правил, после того как миграция «добавить индекс» положила оформление заказов на
семь минут. Таблица `orders` на 180 млн строк, обычный `CREATE INDEX` взял блокировку
`SHARE`, все `INSERT` и `UPDATE` встали в очередь, пул соединений приложения переполнился,
и дальше всё как обычно: таймауты, 502, повторы.

## Главное про блокировки

Почти любой DDL берёт блокировку на таблицу. Опасна не только долгая операция, но и
**очередь блокировок**: если `ALTER TABLE` ждёт `ACCESS EXCLUSIVE`, потому что идёт долгий
отчётный `SELECT`, то все новые запросы к таблице, даже чтение, встают в очередь за `ALTER`.
Мгновенная по сути операция (например, добавление столбца без значения по умолчанию) так
вызывает простой на всё время, пока работает тот отчёт.

Поэтому в каждой миграции первым делом:

```sql
SET lock_timeout = '3s';
SET statement_timeout = '15min';
```

Не получили блокировку за 3 секунды — миграция падает, а не вешает прод. Повторить в другое
время или с ретраем в скрипте миграции.

## Индексы: CREATE INDEX CONCURRENTLY

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_customer_created
    ON orders (customer_id, created_at);
```

- Строится без блокировки записи (берёт `SHARE UPDATE EXCLUSIVE`, которая конфликтует только с
  другим DDL и `VACUUM`).
- Работает дольше обычного: два прохода по таблице и ожидание завершения всех транзакций,
  которые видели таблицу до начала.
- **Нельзя внутри транзакции.** Многие инструменты миграций по умолчанию оборачивают каждую
  миграцию в `BEGIN … COMMIT` — получите `CREATE INDEX CONCURRENTLY cannot run inside a
  transaction block`. В Rails — `disable_ddl_transaction!`, в Alembic — `autocommit_block()`,
  в sqlx/refinery — отдельный файл без транзакции.
- Если упал (дубликат при уникальном индексе, отмена, таймаут) — остаётся индекс в состоянии
  `INVALID`. Он не используется для чтения, но обновляется при записи. Найти и удалить:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_orders_customer_created;
```

Удалять индекс тоже `DROP INDEX CONCURRENTLY`. Пересобрать раздутый индекс —
`REINDEX INDEX CONCURRENTLY` (PostgreSQL 12+).

## Добавление столбцов и ограничений

| Операция | Безопасно? | Как делать |
|----------|-----------|------------|
| `ADD COLUMN` без DEFAULT | да, мгновенно | с `lock_timeout` |
| `ADD COLUMN ... DEFAULT 0` | с PG 11 мгновенно для константы | для `now()`, `random()` — переписывает таблицу |
| `ADD COLUMN ... NOT NULL DEFAULT ...` | с PG 11 да | |
| `ALTER COLUMN TYPE` | обычно переписывает таблицу | новый столбец + перенос + переключение |
| `SET NOT NULL` | сканирует таблицу под `ACCESS EXCLUSIVE` | сначала `CHECK ... NOT VALID`, см. ниже |
| `ADD FOREIGN KEY` | проверяет всё под блокировкой | `NOT VALID` + `VALIDATE` |
| `ADD UNIQUE` | строит индекс под блокировкой | уникальный индекс `CONCURRENTLY` + `USING INDEX` |

Шаблон для ограничений:

```sql
ALTER TABLE orders
    ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id)
    REFERENCES customers (id) NOT VALID;          -- мгновенно, проверяет только новые строки

ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;  -- без блокировки записи
```

Для `NOT NULL` на большой таблице: добавить `CHECK (col IS NOT NULL) NOT VALID`, провалидировать,
затем `SET NOT NULL` — с PG 12 он увидит валидный CHECK и не будет сканировать таблицу; после
этого CHECK можно удалить.

## Переименования и смена типа: expand / contract

Приложение и схема выкатываются не одновременно: какое-то время работают старая и новая
версии кода. Поэтому несовместимые изменения делаем в несколько релизов:

1. **Расширить**: добавить новый столбец `amount_cents bigint`, код пишет в оба столбца.
2. **Перенести**: заполнить новый столбец для старых строк пачками.
3. **Переключить**: код читает из нового столбца.
4. **Сузить**: следующим релизом убрать запись в старый столбец, затем удалить его.

Заполнение пачками, чтобы не держать долгую транзакцию и не раздувать WAL и реплики:

```sql
UPDATE orders SET amount_cents = amount * 100
WHERE id IN (
    SELECT id FROM orders
    WHERE amount_cents IS NULL
    LIMIT 5000
);
-- повторять, пока затронуто > 0 строк, с паузой и контролем лага реплик
```

## Порядок выката и откат

Миграция схемы и релиз кода — разные шаги, и их порядок определяется совместимостью:

- **Аддитивные изменения** (новая таблица, столбец, индекс) — миграция до выката кода.
  Старый код новую схему не замечает.
- **Удаляющие изменения** (убрать столбец, таблицу, ограничение) — только после того, как
  весь работающий код перестал их использовать, то есть релизом позже.
- ORM, которые кэшируют список столбцов (ActiveRecord, некоторые конфигурации Hibernate),
  падают при удалении столбца, даже если код его не читает. В Rails перед удалением
  столбец помечают `ignored_columns` и выкатывают это отдельно.

Откат миграции на проде почти никогда не делается «обратной миграцией»: `DROP COLUMN`
теряет данные, записанные после выката. Вместо отката — новая миграция вперёд. Поэтому
каждая миграция должна быть совместима с предыдущей версией кода: тогда откат релиза
кода безопасен без отката схемы.

Долгие операции (построение индекса на часы, перенос данных) лучше выносить из
автоматического прогона миграций при старте приложения. Если приложение при запуске ждёт
окончания `CREATE INDEX CONCURRENTLY`, проверка готовности не пройдёт, оркестратор
перезапустит контейнер, и миграция начнётся заново, оставив невалидный индекс. Такие шаги
запускаются отдельной задачей, а приложение проверяет только, что схема не старше
ожидаемой.

Полезные инструменты: `squawk` — линтер SQL-миграций, ловит `CREATE INDEX` без
`CONCURRENTLY`, добавление `NOT NULL`, смену типа; `pg_repack` — пересборка раздутых таблиц
без долгой блокировки.

## Чек-лист ревью миграции

- [ ] Есть `lock_timeout`.
- [ ] Индексы — только `CONCURRENTLY`, и миграция не обёрнута в транзакцию.
- [ ] Нет переписывания таблицы (смена типа, `DEFAULT` с волатильной функцией).
- [ ] Ограничения — через `NOT VALID` + `VALIDATE`.
- [ ] Удаление столбца — только после релиза, в котором код его уже не читает.
- [ ] Массовые `UPDATE`/`DELETE` — пачками, не в одной транзакции.
- [ ] Прогон на копии прод-данных с замером времени.

## Как найти, кто кого блокирует

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, state,
       now() - xact_start AS xact_age, left(query, 80)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Мешающий долгий запрос можно отменить `pg_cancel_backend(pid)` или, если не помогает,
завершить сессию `pg_terminate_backend(pid)`.
