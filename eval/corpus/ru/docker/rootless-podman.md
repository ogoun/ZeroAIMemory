# Контейнеры без root: rootless Docker и Podman на сборочных машинах

Решали задачу: разработчики и CI-агенты на общих Linux-серверах запускают контейнеры, а
членство в группе `docker` фактически равно root на хосте — `docker run -v /:/host` даёт
полный доступ к файловой системе. Сравнили два варианта: rootless-режим Docker и Podman.
Ниже — что выяснили, как настроили и какие грабли собрали.

## Почему группа docker — это root

Демон `dockerd` в классической установке работает от root, а клиент лишь отправляет ему
команды через сокет `/var/run/docker.sock`. Кто может писать в сокет, тот может попросить
демон смонтировать любой каталог хоста, запустить привилегированный контейнер или
добавить устройство. Отсюда правило: доступ к сокету выдавать только тем, кому выдали бы
sudo. Тот же сокет, проброшенный внутрь контейнера (частая практика для CI), даёт
контейнеру управление хостом.

## Как устроен rootless

Обе реализации используют **пространства имён пользователей** (user namespaces). Внутри
контейнера процесс видит себя uid 0, а на хосте он работает от обычного пользователя.
Остальные uid контейнера отображаются в диапазон подчинённых идентификаторов из
`/etc/subuid` и `/etc/subgid`:

```
builder:100000:65536
```

Строка означает: пользователю `builder` выделены uid 100000–165535. uid 0 в контейнере —
это сам `builder`, uid 1 — 100000, uid 1000 — 100999 и так далее. Если строки нет, образы
с файлами разных владельцев не распаковываются с ошибкой вида «potentially insufficient
UIDs or GIDs available in user namespace».

Сеть без root делается в пространстве пользователя: раньше через `slirp4netns`, в новых
версиях Podman — через `pasta`. Это медленнее сети в режиме root, что заметно на
сетевых тестах с высокой нагрузкой.

## Вариант 1: rootless Docker

```sh
sudo apt install uidmap dbus-user-session docker-ce-rootless-extras
dockerd-rootless-setuptool.sh install      # от обычного пользователя
systemctl --user enable --now docker
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
```

У каждого пользователя свой демон, свой каталог образов в `~/.local/share/docker` и свой
сокет. Чтобы демон жил без активной сессии (для CI-агента), нужно
`loginctl enable-linger builder`.

## Вариант 2: Podman

Podman не имеет демона: каждая команда — отдельный процесс, контейнер становится
дочерним процессом `conmon`. Интерфейс командной строки совместим с Docker почти
полностью, многие ставят `alias docker=podman`.

```sh
sudo apt install podman
podman run --rm -it docker.io/library/alpine id
podman build -t app .
```

Особенности, которые пришлось учесть:

- **Короткие имена образов.** Podman спрашивает, из какого реестра тянуть `alpine`, или
  берёт список из `/etc/containers/registries.conf`. В скриптах пишем полное имя с
  `docker.io/library/`.
- **compose.** Есть `podman compose` (обёртка над внешним провайдером) и сокет-служба
  `podman.socket`, совместимая с API Docker: `systemctl --user enable --now podman.socket`,
  после чего обычный `docker compose` работает через `DOCKER_HOST`.
- **Автозапуск.** Вместо `restart: always` демона — юниты systemd. Современный способ —
  Quadlet: файл `~/.config/containers/systemd/app.container` превращается в службу
  при `systemctl --user daemon-reload`.
- **Поды.** `podman pod create` объединяет контейнеры в общий сетевой namespace, как в
  Kubernetes; `podman kube generate` выдаёт манифест.

## Права на смонтированные каталоги

Самая частая жалоба в rootless — «Permission denied» на bind mount. Файлы, созданные в
контейнере от uid 0, на хосте принадлежат пользователю `builder`, а от uid 1000 —
пользователю 100999, которого на хосте не существует, и `builder` не может их удалить.

Решения:

| Способ | Как |
|---|---|
| Запускать процесс в контейнере от root (внутреннего) | на хосте файлы будут свои |
| Podman: сохранить свой uid внутри | `--userns=keep-id` |
| Сменить владельца в пространстве контейнера | `podman unshare chown 1000:1000 ./data` |
| Удалить «чужие» файлы | `podman unshare rm -rf ./data` |

`podman unshare` запускает команду в том же пространстве имён, что и контейнеры, и там
отображённые uid снова «свои».

## Ограничения rootless

- Порты ниже 1024 недоступны без `sysctl net.ipv4.ip_unprivileged_port_start=80` или
  `setcap` на вспомогательный бинарник.
- Ограничения ресурсов (`--memory`, `--cpus`) требуют cgroup v2 и делегирования
  контроллеров пользовательской сессии systemd; на старых системах с cgroup v1 они
  молча не работают.
- Драйвер хранилища: `overlay` в rootless доступен на ядрах от 5.13 (или через
  `fuse-overlayfs`), иначе используется `vfs`, который копирует слои целиком и быстро
  съедает диск.
- Некоторые образы ждут реальных привилегий (например, монтирование внутри контейнера,
  `--privileged` для DinD) — в rootless они не заработают или заработают частично.

## Миграция CI-агента по шагам

1. Создать отдельного пользователя `builder` без sudo и проверить строки в `/etc/subuid`
   и `/etc/subgid` (useradd в современных дистрибутивах добавляет их сам).
2. Включить linger, чтобы пользовательские службы жили без входа в систему.
3. Установить Podman, запустить `podman info` от `builder` и проверить в выводе
   `graphDriverName: overlay` и `cgroupVersion: v2`.
4. Перенести кэш образов: `docker save` на старом агенте и `podman load` на новом, чтобы
   первая сборка не тянула всё из реестра.
5. В конфигурации CI заменить `docker` на `podman` или выставить `DOCKER_HOST` на сокет
   `podman.socket`, если инструмент жёстко вызывает Docker API.
6. Прогнать все пайплайны по разу и сравнить время и размер образов.

На шаге 6 вылезли две проблемы. Первая — тесты, которые поднимали контейнер с портом 80;
перевели их на 8080. Вторая — сборка, монтировавшая сокет Docker внутрь контейнера для
вложенных сборок; её переписали на `podman build` снаружи.

## Как проверить, что всё действительно без root

```sh
ps -o user,pid,cmd -C conmon          # владелец — builder, а не root
podman unshare cat /proc/self/uid_map # отображение uid в пространстве имён
podman info --format '{{.Host.Security.Rootless}}'
```

## Итог

Для CI-агентов выбрали Podman: нет долгоживущего демона с правами root, сборки через
`podman build` совместимы с нашими Dockerfile, а для двух проектов с compose включили
`podman.socket`. Разработчикам на рабочих станциях оставили обычный Docker, но убрали
из группы `docker` тех, кому root на общих серверах не нужен. Время сборки выросло
примерно на 10 % из-за сети в пространстве пользователя — приемлемая цена.
